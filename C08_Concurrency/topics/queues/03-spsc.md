# 队列 03：SPSC 用角色所有权消除竞争

假设采集线程持续生成记录，只有一个处理线程消费。这时 MPMC 接口提供了应用根本不需要的自由度。我们可以将“谁允许修改下标”写入契约：生产者独占写 tail，消费者独占写 head。这是场景切换，不是同一组任意线程调用突然变得更快。

代码在 [`queue_versions.hpp`](../../exercises/include/concurrency_study/queue_versions.hpp) 的 `spsc_ring<T,Cached>`；[G3 Reference](../../exercises/G3_spsc_ringbuffer/solution.cpp) 分别运行普通与缓存版。T 必须可默认构造，复制赋值和析构不抛异常。所有存储构造后固定存在，不向使用者暴露槽位引用。一个队列最多同时有一个 push 调用者和一个 pop 调用者，析构前必须停止并 join 二者。

## 1. 为什么要多分配一格

没有受共同锁保护的 size，我们需要从 head、tail 区分满和空。约定 tail 指向下一次写入位置，head 指向下一次读取位置：相等表示空；tail 前进一步将追上 head 表示满。这样必须留一个未使用槽。

构造参数给的是可用容量 C，实现实际分配 C+1 个 T。传入 2 就真的能存两个元素，便于和 Q0 比较。合法容量为正且小于 `size_t` 最大值；本版通过条件回到零，不要求容量是 2 的幂。数组下标一直在 `[0,C]` 内，不使用无限递增的票据，因此没有 MPMC 的半范围序号比较问题。

底层是 `std::unique_ptr<T[]>`，由 `std::make_unique<T[]>(C+1)` 一次构造真正独立的 T 对象，另存实际槽数用于回到零。这一点对 `T=bool` 尤其重要：`vector<bool>` 可以把几个逻辑元素压进同一个存储字，修改一位可能读改写整个字，与另一线程访问不同逻辑下标发生冲突。槽位所有权协议只分开了逻辑位置，不能替压位代理分开实际存储。因此普通和缓存版都保持 bool 合法，同时使用真实 bool 数组；本课程不依赖一次压力测试没有撞到竞争来批准压位实现。[N5050](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/n5050.pdf) `[container.requirements.dataraces]` 明确把 vector<bool> 排除在不同元素并发修改的通常保证之外。

容量 2 的完整轨迹如下，底层有 3 格：

| 操作后 | head | tail | 逻辑内容 |
|---|---:|---:|---|
| 初始 | 0 | 0 | 空 |
| push 10 | 0 | 1 | 10 |
| push 20 | 0 | 2 | 10,20 |
| push 30 失败 | 0 | 2 | 10,20 |
| pop 10 | 1 | 2 | 20 |
| push 30 | 1 | 0 | 20,30 |

只有生产者写 tail，所以它读自己的 tail 后，到下一次 store 之间不存在另一个合法生产者抢走同一位置。这里不需要 read-modify-write 原子操作；但是生产者和消费者仍在共享槽位，所有权必须通过同步交接。

## 2. 一个槽位有两条同步方向

第一条方向是发布数据：生产者先对 `data_[tail]` 赋值，再 `tail_.store(next, release)`；消费者用 acquire 读 tail，确认有已发布数据后读取 `data_[head]`。这个 release/acquire 连接的是普通 T 对象的写与读，而不只是下标数字。

第二条方向是归还存储：消费者必须先复制完 `data_[head]`，再 release 更新 head；生产者 acquire 看到这个进展，才可以覆盖已经读完的槽。若把消费者的 store 提到复制之前，生产者可能开始写同一个普通对象，导致数据竞争。即使每个整数都能单指令访问，也不能省略这条 C++ 层面的关系。

读自己独占写入的原子下标用 relaxed，因为它不是跨线程获取对方数据的通道。读对方下标用 acquire，提交自己的新下标用 release。Acquire 并不等于“必须读到墙钟意义上的最新值”；保守观察可能导致一次尝试返回 false。课程对原子环的失败采用“本次观察没有可用项/空间，输出保持不变”的契约，使用者应重试或通过独立结束协议确认生产者已经停止。

出队赋值使用 `value = std::as_const(data_[head])`。入队源本来就是 `const T&`；出队也显式选择相同的 const 复制重载，才能和 `is_nothrow_copy_assignable_v<T>` 的检查一致。存在额外可变源赋值重载的类型仍然合法，不能让它在 noexcept 出队中意外触发。完整反例和回归类型见[上一章的元素约束推导](02-bounded-and-batch.md)。

成功元素保持 FIFO。单生产者的发布顺序与单消费者的槽位前进顺序一致。不要用这个结论掩盖角色前提：第二个生产者若也读到同一个 tail，即使 tail 是 atomic，两者仍可能同时写同一个普通 T，并且覆盖彼此的 store。仅给 tail 的 store 改成 CAS 也不能自动补出预订与发布协议。

## 3. 缓存对方下标为什么安全

普通版每次操作都 acquire 读取对方下标。缓存版维护两个线程私有字段：生产者的 `cached_head_`，消费者的 `cached_tail_`。生产者先按缓存判断空间足够，就直接使用已经获得的空槽许可；只有将要追上缓存 head 时，才 acquire 重读真实 head。消费者对称。

关键不是“缓存通常够新”，而是旧缓存只会少给许可。生产者不能越过自己最后确认的 head，因此在获得新 head 之前不会绕一整圈覆盖尚未确认释放的槽。消费者不能越过最后确认的 tail，因此不会凭旧缓存读取尚未发布的数据。一旦获得新的 acquire 观察，这个边界以内的相应槽位都有同步依据。

缓存版和普通版可用容量、线程角色、顺序、失败时输出保持不变的承诺相同；它属于 SPSC 分支内部的同步次数改进。缓存字段只被各自角色访问，不能由监控线程随意读取。当前代码也没有强加 64 字节缓存行假设；布局优化应在缓存章节结合机器和基准证据研究。

## 4. 进展保证应怎样表述

两版单次 try 都没有重试循环，最多执行固定数量的原子 load/store 与一次 T 赋值。若这些原语本身具有有界步数，它们的核心步骤是 wait-free 的常见例子；[Boost 官方 SPSC 文档](https://www.boost.org/doc/libs/latest/doc/html/doxygen/classboost_1_1lockfree_1_1spsc__queue.html)也提供单写者/单读者接口作为对照。

但本课程不能从这一点推出“任意平台、任意 T 的整个调用严格 wait-free”。`atomics_lock_free()` 只检查两个实际原子的无锁属性；不抛异常的赋值可能在内部阻塞；原子无锁也不等于每次原子操作都有统一步数上界。外部 `while (!try_push(...))` 还在等待消费者提供空间，这个重试传输操作显然依赖对方运行。

## 5. 运行与解释

从 `C08_Concurrency/exercises` 执行：

```powershell
cmake -S G3_spsc_ringbuffer -B build/g3 -G "Visual Studio 18 2026" -A x64
cmake --build build/g3 --config Release
ctest --test-dir build/g3 -C Release --output-on-failure
```

Reference 对可用容量 1、2、7、64 分别验证填满、满拒绝、FIFO 清空，然后对两版各传输 20003 个 ID。单消费者保存完整序列，每个值必须恰好等于下一个期望值。容量 7 用来检查实现确实没有偷偷依赖幂次掩码。零容量必须抛出 invalid_argument。

补充回归对普通/缓存 bool 两版在同样四种容量下各传输 20003 个非恒定真/假值，并核对每一位的预期顺序、满空和复用。这个检查直接使用 bool 对象，没有再用 vector<bool> 记录结果；生产者只执行不抛操作，主线程检查失败时取消并 join。两版另用 `copy_overload_probe` 验证不会选择抛异常的可变源赋值。TSan 未在本机运行，因此 bool 的无竞争依据仍是真实数组对象与双向交接协议，回归运行提供补充证据。

输出的原子属性是本机实测。执行时间和缓存版加速比不是验收条件，缓存版在很小数据量上更慢也不表示协议错误。基准必须把两版和 mutex 对照都限制为 P=1、C=1、相同可用容量，而不是拿多生产者工作量去调用 SPSC。

`spsc` 和 `spsc-cached` 明确列为 SPSC 分支内对照。诊断入口记录两者完成同一 1P/1C 工作量时的公开调用次数和实际远端下标 load 次数。若缓存版远端下标 load 明显更少，只能支持“缓存减少远端下标刷新”，不等于已经测得 cache miss 下降。当前头文件如有变化，需按[队列基准篇](08-validation-and-benchmark.md)重新正式采样。

## 自测与答案

**消费者的 release 是否只是优化？** 不是。它把“已完成读”发布给后续覆盖者，是槽位重复使用的必要同步方向。

**缓存 head 过时会越界吗？** 在合法 SPSC 协议下不会，它最多阻止生产者进一步前进；碰到缓存边界必须重读。不能把它改成无条件信任缓存并跨过边界。

**多个消费者的需求能否用同一个类满足？** 不能；需改变算法或在外部序列化消费者。后续 MPMC 可以运行于 SPMC 拓扑，但这不意味着它是专用 SPMC 最优解。

**这里的环绕和票据回绕一样吗？** 不一样。这里是数组边界内有明确满空约束的循环索引；后续 ticket 算法还比较不同代次的有限宽度计数，需要额外的距离前提。

内存序的规范入口是 [N5050](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/n5050.pdf) `[atomics.order]`。所有权、缓存边界与两条交接链是对本篇真实实现的推导。
