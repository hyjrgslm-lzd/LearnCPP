# 队列 01：先得到一个可以信任的基线

假设几个工作线程生成记录，另一些线程负责处理记录。我们需要把“生成”与“处理”分开，又希望成功加入的记录最终被取走。先给这个问题选一个小而具体的接口：容量固定，生产者尝试放入一个整数，消费者尝试取出一个整数。空间不足或暂时没有数据时，函数返回 false，由调用者决定接下来怎么办。

本篇的完整实现是 [`queue_baseline.hpp`](../../exercises/include/concurrency_study/queue_baseline.hpp)，观察程序和检查程序在 [Q0](../../exercises/Q0_queue_baseline/README.md)。先把实现的行为讲清楚，再研究什么场景值得增加复杂度。

## 1. 单线程时，一次操作实际做了什么

`std::queue<int>` 已经提供了先进先出的存储顺序。成功加入 10，再加入 20，随后取出时先得到 10，再得到 20。取出需要先读取 `front()`，再 `pop()`；`pop()` 本身不返回元素。

```cpp
std::queue<int> values;
values.push(10);
values.push(20);
int first = values.front();
values.pop();
```

这里“读取首元素”和“移除首元素”是两个动作。单线程没有其他访问者插进来，我们很容易把它们看成一次取出。但多线程程序必须显式定义哪些动作属于同一次操作。

设两个消费者都看到队列非空。第一个消费者拿走最后一个元素，第二个才执行 `front()`。第二个消费者先前看到的事实已经失效，访问空队列不满足接口前提。即使分别为 `empty()` 和 `pop()` 加锁，锁释放后仍然存在这个空隙。

因此，我们把“检查是否有元素、取得值、移除元素”合并为 `try_pop(out)`。这是接口设计先于选用原子操作的一步：先定义一件不可被其他访问者拆开的事情。

## 2. 固定本篇的契约

| 项目 | 本篇选择 |
|---|---|
| 线程角色 | 允许多个生产者、多个消费者 |
| 容量 | 构造时给定，必须大于零 |
| `try_push(value)` | 有空间则复制加入并返回 true；满则返回 false |
| `try_pop(out)` | 有数据则移出队首并返回 true；空则返回 false，out 不变 |
| 顺序 | 成功操作可按持锁临界区内的生效顺序解释为 FIFO |
| 进展 | 获取 mutex 可能阻塞；try 表示不等待空间或数据，不表示无锁 |
| 元素前提 | 可复制插入、移动赋值和析构不抛异常；示例使用 int |
| 退出 | 调用者先停止并 join 全部参与线程，再析构队列 |

容量、失败语义、异常和退出方式都是契约的一部分。以后如果换成无界队列、批量操作、允许暂时失败的协议，必须明确告诉读者变了什么。它们不能仅凭类名都叫 queue 就当成完全相同的性能对照。

## 3. 给整次操作加一把锁

核心代码并不长：

```cpp
bool try_push(const T& value) {
    std::lock_guard lock(mutex_);
    if (queue_.size() == capacity_) return false;
    queue_.push(value);
    return true;
}

bool try_pop(T& value) {
    std::lock_guard lock(mutex_);
    if (queue_.empty()) return false;
    value = std::move(queue_.front());
    queue_.pop();
    return true;
}
```

锁覆盖检查和修改，因此消费者不能在另一个消费者的检查与取出之间改变队首。生产者也不能在另一个生产者检查容量后，抢占那个尚未使用的空间。由这个边界可以维护 `0 <= size <= capacity`。

`lock_guard` 的生命周期覆盖整个临界区。提前返回或插入过程中抛出异常时，它仍会释放 mutex。本教学实现限制移动赋值和析构不抛异常；插入的复制或存储分配仍可能抛异常，由调用者处理。RAII 不会自动让任意元素类型的操作都拥有相同异常保证。

一个成功 push 的生效位置在持锁完成插入时；成功 pop 的生效位置在持锁移除队首时。失败操作则在锁内观察到满或空时生效。这给出了线性化的解释：虽然不同调用的起止区间可能重叠，我们能为每次调用找到区间内的一个位置，把它们排列成符合串行接口的执行。

互斥还有可见性的作用：对同一 mutex 的解锁和后续成功加锁建立相应同步关系。只要对受保护队列的访问都遵守这把锁，后一个访问者就能使用前一个临界区留下的状态。这个论证依赖程序的同步关系，不依赖“恰好在 x86 上没出错”。

## 4. 先预测，再运行

容量取 2，预测这段序列：

| 操作 | 返回值 | 操作后逻辑内容 |
|---|---|---|
| 对空队列 pop | false | 空 |
| push 10 | true | 10 |
| push 20 | true | 10, 20 |
| push 30 | false | 10, 20 |
| pop | true，取出 10 | 20 |
| push 30 | true | 20, 30 |

这一轮暂时不用多线程。一个数据结构如果连基本容量和失败语义都没对齐，并发压力测试很难告诉我们错在哪里。

从 `C08_Concurrency/exercises` 配置和运行：

```powershell
cmake -S Q0_queue_baseline -B build/q0 -G "Visual Studio 18 2026" -A x64
cmake --build build/q0 --config Release
./build/q0/Release/Q0_queue_baseline.exe
ctest --test-dir build/q0 -C Release --output-on-failure
```

最后一条命令运行 Reference 并设置进程级超时。Reference 验证刚才的顺序情形，再让三个生产者各生成 1000 个不同 ID，用一个消费者保存取出序列。每个生产者的 ID 范围互不重叠，所以可以查出遗漏、重复、越界及同一生产者的顺序错误。

这比“push 次数等于 pop 次数”更强：丢掉 17、重复取出 18，次数仍然可能相等。它也比简单求和更强，因为不同错误可能相互抵消。不过，这组运行仍不能证明所有并发历史都线性化。正确性论证来自完整的锁协议；后续版本要分别补充它们新增的状态和交错检查。

## 5. 这把锁可能花掉什么

所有生产者和消费者都经过同一把锁，所以一次临界区内最多推进一个队列操作。负载较小、元素操作较短时，这通常很合适。负载变化后，应该先提出可检验的问题：

- 持锁时间是否主要花在复制元素、分配存储或调用外部代码上？
- 是否频繁在满/空状态重试，把时间消耗在无效的锁获取上？
- 单次只搬一个元素，是否让同步成本占了大头？
- 多消费者是否真的需要共享同一条全局 FIFO？

这些问题指向不同的改进。长复制可以通过调整数据表示研究；空/满重试可以与条件变量等待比较；批量交接可以摊薄每元素的同步成本，但会增加凑批等待；专用 SPSC 队列则通过限制访问角色简化协议，属于场景切换。

不能仅看到耗时增加，就断言每次争用都产生了内核上下文切换。实际锁实现、调度、分配器和负载共同影响结果。需要观察或 profiler 证据时，性能附录应记录测量方法和可用证据；缺少证据时把原因标为待验证假设。

## 6. 下一步怎样选择

如果需求是“没有数据时等待”，先学习条件变量和关闭协议；如果需求是固定的一对生产者/消费者，进入 SPSC 槽位所有权实验；如果需要多生产者、多消费者，研究预订与发布之间的空隙；如果改用动态节点，则必须把节点摘除和内存回收分开。

这些路线都保留本篇作为可运行基线。每条路线重新检查容量、顺序、失败与生命周期约定，再决定怎样公平比较。最终选择应由问题、契约和实测结果共同支持。

## 自测与解析

**try_pop 是否保证不阻塞？** 不保证。它不等待一个元素出现，但仍要获取 mutex。命名不能替代进展契约。

**可以先调用 empty，再决定线程是否睡眠吗？** 单独观察不能完成安全的等待协议。观察以后状态可能变化，需要把谓词检查与进入等待的动作连接起来，条件变量章节会展开这一关系。

**为什么复制元素时不立即解锁？** 队首及其对象寿命由当前临界区保护。在没有转移所有权或其他保护协议之前，解锁后再使用队首引用会给其他消费者留下修改或销毁它的机会。

**这组压力检查通过后，证明了什么？** 证明本次输入和实际交错没有违反这些检查。它支持实验记录；对任意合法交错的结论仍要从 mutex 覆盖范围、同步关系和对象寿命推导。
