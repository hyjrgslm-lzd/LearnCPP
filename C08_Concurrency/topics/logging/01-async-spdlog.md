# 异步日志：从同步前端到有界队列

C05 的 spdlog 单元已经讲清楚 logger 前端、sink、pattern、格式化后端和 `error_handler`。C08 只关心并发契约：消息什么时候从调用线程交给队列，队列满时谁承担代价，worker 什么时候真正写 sink，关闭时怎样让已接受的消息收束。

同步日志的心智模型很短：调用线程检查 level，格式化参数，调用 sink，必要时 flush。异步日志多了一个运行时边界。调用线程格式化出 `log_msg` 后，把消息投递到 `details::thread_pool` 的 MPMC 队列；worker 线程再执行 `backend_sink_it_`。因此“调用已返回”只说明消息已经被接受或按策略丢弃，不说明 sink 已写入。

满队列策略要写进需求，而不是留给库默认值。`block` 保留消息但把背压传给调用线程，适合不能丢日志的审计路径，但可能放大请求延迟。`overrun_oldest` 保留最新现场，适合状态流、采样流和调试流，但会抹掉队列里较早的上下文。`discard_new` 保留既有队列，适合避免新日志冲掉已排队的关键阶段，但调用者通常只看到计数器，不会得到逐条失败。

单 worker 可以把“入队顺序”转成“sink 完成顺序”。多 worker 只能说队列取出有顺序；一旦两个 worker 同时执行 sink，慢消息可能晚于后入队的快消息完成。若业务需要全局日志顺序，应使用单 worker、下游序号重排，或在 sink/聚合端明确按序处理。

`flush()` 是请求，不是完成通知。它进入同一个队列，排在之前已接受的消息之后；但它返回时 worker 可能还没执行它。在非阻塞策略下，flush 请求本身也可能因为队列满而被丢弃。需要确认 durable flush 时，要另建完成信号，或在停止 producer 后通过关闭流程等待队列排空。

关闭按所有权顺序做：先停 producer，拒绝新日志入口；再释放可能阻塞 worker 的 I/O 或门闩；然后让已接受消息和 flush 请求排空；最后销毁 thread pool 并 join worker。logger 只弱引用 pool，pool 提前消失后日志和 flush 都会进入错误处理路径。

本专题不主讲服务观测。metrics、trace、远程日志确认、采样策略和故障告警属于 C11；这里只把本地进程内的同步、队列、错误和生命周期讲完整。
