# 04：动态库、装载与运行时

C1 已经把问题推进到链接器：多个对象文件怎样组成一个程序，符号为什么会重复或缺失。本章继续往后走一步。链接成功以后，程序仍然不一定能启动，因为动态库的代码可能要到运行时才被装载。静态库、动态库、导入库、导出符号和运行时初始化，解决的是“代码最终从哪里来、什么时候进进程、谁负责找到它”。

先只看一个很小的 C 形状函数：

```cpp
extern "C" int lesson_runtime_value();
```

这个函数没有类、异常、STL、所有权和 ABI 版本。它的用途只是让动态库机制本身变得可观察。下一章才引入 opaque handle 和跨边界所有权。

## 静态库是什么

静态库不是一个运行时会被装载的程序模块。它更像一包对象文件归档。链接可执行文件时，链接器从归档中取出满足未解析符号的对象，把需要的代码放进最终可执行文件。程序启动时不需要再找到这份 `.lib` 或 `.a`。

在 Windows/MSVC 下，静态库常见扩展名是 `.lib`。在 ELF 工具链下常见扩展名是 `.a`。扩展名只能说明惯例，不能单独说明库的角色；Windows 的导入库也常叫 `.lib`。

配套练习里的 `D1_static_reference` 链接静态库。它运行成功说明 `lesson_runtime_value()` 的定义已经在链接阶段进入最终程序，不需要运行时搜索 DLL。

## 动态库和导入库分工

动态库把实现留在一个独立文件中。Windows 上实现文件通常是 `.dll`，ELF 平台通常是 `.so`。可执行文件链接时只记录“我需要这个动态库里的这个符号”，程序启动或显式装载时才把库映射进进程。

Windows 还有一个容易混淆的文件：导入库。导入库通常也是 `.lib`，但它不包含完整实现，只给链接器一组跳板和导入信息。链接器用它生成可执行文件的导入表；真正的代码还在 DLL 里。于是一个 Windows 动态库工程常同时产出：

- `lesson_shared.dll`：运行时要装载的实现。
- `lesson_shared.lib`：链接时使用的导入库。

如果可执行文件能链接成功，但运行时找不到 DLL，它仍然会启动失败。这个失败不是“链接器没找到符号”，而是“装载器没找到运行时模块”。配套练习把 exe 单独复制到一个没有 DLL 的目录运行，用这个受控方式复现缺 DLL。

## 导出和可见性

动态库里的函数不一定自动成为外部消费者可见的 API。Windows 通常用 `__declspec(dllexport)` 标记生产 DLL 时导出，用 `__declspec(dllimport)` 标记消费 DLL 时导入。静态库消费不能带 `dllimport`，因为没有 DLL 导入表，函数定义在静态链接阶段进入程序。

ELF 平台常用默认可见性或 `__attribute__((visibility("default")))` 控制导出。本课保留 ELF 条件分支和命令，但本轮主验收只跑 Windows/MSVC。

D1 使用自己的简单宏，只证明“导出符号能被链接和显式查找”。E/J 使用更完整的 `lesson_api.h`，其中 `LESSON_STATIC` 让静态消费时 `LESSON_API` 为空，shared producer 使用 `dllexport`，shared consumer 使用 `dllimport`。

## 隐式装载和显式装载

链接到导入库的 exe 使用隐式装载。Windows 装载器会在程序启动时根据导入表寻找 DLL。找不到时，程序甚至进不了 `main()`。这类问题常被误判成“程序逻辑失败”，但实际失败发生在代码运行前。

显式装载由程序自己控制。Windows 使用 `LoadLibraryW` 打开 DLL，用 `GetProcAddress` 找导出函数，用 `FreeLibrary` 释放模块引用。ELF 平台对应 `dlopen`、`dlsym`、`dlclose`。显式装载让你能把“库不存在”和“函数不存在”报告成普通错误，而不是让进程启动直接失败。

配套练习里的 loader 程序接收 DLL 的绝对路径，然后查找 `lesson_runtime_value`。另一个负例故意查找不存在的导出名，检查器要求错误来自缺导出，而不是 configure 失败、编译失败或 timeout。

## 初始化和退出不是函数第一次调用

动态库被装载时，运行时会执行它自己的初始化。C++ 全局对象构造、运行库状态准备、Windows DLL 入口、ELF init array 都属于这类阶段。库卸载或进程退出时，对应清理也会发生。

这说明两个事实：

第一，动态库的副作用可能在 API 函数第一次调用前就发生。第二，退出顺序也是工程契约的一部分。如果库 A 的全局对象析构时调用库 B，而库 B 已经卸载，结果就不再是普通函数调用问题。

D1 的示例只用一个全局计数对象记录初始化和退出，并通过显式 loader 观察装载、调用、释放的顺序。它不是建议把业务逻辑放进全局对象；它只是把“动态库有自己的运行时阶段”变成可验证的事实。

## CRT 边界

CRT 是 C/C++ 运行库。Windows Debug/Release、动态/静态 CRT、不同编译器版本，都可能影响分配器、异常机制、stdio 状态和全局对象管理。最危险的误用是让一边分配，另一边用不同运行库释放；或者让 C++ 异常跨越不匹配的二进制边界。

本章只建立观察：动态库有自己的装载和退出阶段，DLL 找不到和符号找不到是不同故障。下一章会给出更保守的 ABI 设计：同库 create/destroy，错误用 status 返回，不跨边界传 STL 或异常，不运行跨 CRT 释放这种真实 UB 来证明问题。

## 自测

1. Windows 下 `.lib` 为什么不能直接说明它是静态库？

   **解析：** MSVC 静态库和 DLL 的导入库都常用 `.lib` 扩展名。静态库提供可被链接进 exe 的对象代码；导入库提供 DLL 导入信息和跳板，真正实现仍在 DLL 中。要结合目标类型、是否有对应 DLL、链接和运行行为判断。

2. 为什么链接成功的 exe 仍可能启动失败？

   **解析：** 链接只证明导入库或符号在构建阶段满足要求。动态库实现要到运行时由装载器找到。DLL 不在 exe 目录、当前子进程 PATH 或其他搜索位置时，程序可能在进入 `main()` 前失败。

3. 显式装载相比隐式装载多证明了什么？

   **解析：** 显式装载把“打开哪个库”和“查找哪个导出”变成程序可检查的步骤。它能分别报告库不存在、导出不存在和函数调用失败；隐式装载缺 DLL 时常在程序启动前失败。

4. 为什么本章不用 opaque handle？

   **解析：** 本章目标是库类型、导出、装载和初始化退出。opaque handle 涉及所有权、版本、错误通道和 ABI 边界，放在下一章能避免把两个问题混在一起。
