# 16：把可信字段组合成资源清单包

前面各章回答了局部问题：字节怎样还原为整数，文本何时才是合法UTF，配置如何拒绝不完整输入，时间怎样选定纪元，路径怎样跨过字符类型边界，schema怎样给未知字段留出空间。本章让这些责任在一条真实数据流中相遇，而不是再造一个“万能序列化框架”。

综合项目只打包资源元数据。Manifest里的`assets/模型.bin`是逻辑资源路径，不意味着本程序要读取该文件，更不是可以直接拼接到任意目录打开的授权。网络连接、资源解包、数据库和崩溃恢复分别留给C11/C12/C15；这里建立它们需要的数据边界。

## 1. 先画出责任流

```mermaid
flowchart LR
  A[类型化资源fixture] --> V[Manifest校验与编码]
  C[UTF8配置文本] --> P[严格配置解析]
  P --> V
  V --> F[独占临时目录中的新包]
  F --> B[有界文件回读]
  B --> D[版本化解码]
  D --> R[时间与文本报告]
```

Manifest由C++ fixture构造，是为了避免给同一课引入第二套清单文本语法；配置和二进制decoder仍接受真正外部输入。类型化fixture也不能跳过不变量检查：公共struct允许调用者改出重复ID、零ID、无效路径或非法UTF，encoder必须在这个边界拒绝它们。C03的强类型模型可以把部分条件提前，但不会自动证明外部字节符合schema。

输入视图只在调用期间借用。解码结果包含自己的string、optional和vector，报告也拥有文本。保存返回值之后修改原fixture不应改变结果；checker专门改变原name检查这一点。optional note的缺失和有值但空串不同，不能用empty()把它们合并。

## 2. 准备完成以后才创建输出

pipeline先parse_config，再验证和编码Manifest，最后确认时间可以按展示zone格式化。这些步骤都还在内存中。未知配置键、重复资源ID或者无法使用的展示zone，不应该留下一个看似成功的新包。空Manifest也要验证已配置的zone，不能因为没有进入逐记录循环就跳过检查。只有准备完成后才进入文件I/O。

这并不意味着存在一个跨配置、内存、磁盘和时区数据库的全局事务。它只是把可提前发现的错误放到副作用之前。文件写入可能发生设备满、权限变化或中途失败，仍需返回明确I/O错误。程序不会把bad_alloc自动吞成“非法输入”；expected和异常分别承担各自的失败范围。

报告格式使用编译期固定format string，名称和路径通过debug字符串表示转义换行、引号等字符。不要把来自配置或资源名称的文本直接当format string执行。时区只用于表示同一instant，包中始终保存UTC Unix毫秒；改变display_zone不改变modified_at_ms或资源标识。

## 3. 文件名和资源路径是两回事

`package_file`是配置中的单个basename，它在调用者新建并独占的scratch目录内解释。资源记录中的path只是包内元数据，完全不参与本章的文件打开操作。这条责任边界让逻辑路径校验与实际文件I/O可以分别教学和测试。

在Windows上，不能把UTF8的std::string直接交给假定原生窄编码的path构造，然后声称所有非ASCII名称都能往返。提供的utf8_path逐字节构造u8string，再由path按UTF8转换成平台表示。它没有把char*强转char8_t*并据此读取另一种类型对象，也没有对文本执行NFC或casefold。编码转换、规范化和身份策略仍然是独立步骤。

对输出路径使用`ios::noreplace`。先`exists()`再以普通ofstream打开会留下检查到使用之间的窗口；而noreplace要求创建新文件，遇到既有路径时直接失败。本题不覆盖旧文件，keeper测试先写入`keep`，尝试pipeline后再检查四个字节仍然存在。它是当前创建语义的测试，不是对所有文件系统竞争或权限模型的证明。

## 4. 写完内存数据不等于读过文件

一个容易伪装成成功的实现是：调用encoder，生成一段报告，然后把输入Manifest原样返回。观察输出似乎没问题，甚至可以通过只比较input==result的测试，却完全没有执行真实文件I/O。P1的bad就是这一条有界错误路径；checker必须检查文件存在，并读取其实际字节。

写入方先检查bytes<=1MiB且能表示为streamsize，再写入、flush和close并检查状态。`flush()`成功不等同于持久化到物理介质，close成功也不证明断电恢复；这些保证需在C12结合平台原语另行讨论。

回读方先取得文件大小，确认限制后才分配vector；读取不足或额外字节都拒绝。初始file_size只是某个时点的观察，不能假设随后文件永远不变。这里的额外检查让明显的长度变化被报告，但不是文件快照机制。本项目的正常前提是目录由本次实验独占，不拿有限测试推导恶意并发修改场景下的完整安全性。

真实回读字节随后进入decode_manifest。payload是来自磁盘的输入，不能因为文件由本程序刚写出便跳过边界、UTF或schema检查。返回报告使用解码结果，因而失败通道与实际数据流一致。

## 5. 为什么要有手写golden bytes

如果writer把u32写成小端，reader也错按小端读，`decode(encode(x))==x`仍可能成立。这个性质可以检查自洽，却不能证明遵守约定的wire格式。

课内[黄金输入](../exercises/fixtures/README.md)独立手写了v1的68个octet和v2空note的74个octet，并在Manifest实现之前由独立整数解析预检长度和字段。v2空备注比v1多一个tag6和零长度，共六字节；这六字节不是可随意省略的“空值”，因为有值空串与缺失含义不同。

P1比较实际文件与v2黄金输入，同时用另一个中文名称、路径、较大byte_size及负epoch的Manifest检查变化输入。单个固定输出不足以通过两组数据；源码审查还必须确认检查程序真的调用被选中的Student操作。检查器不能证明学生从未抄答案，其声明范围只到实际接线和所覆盖的行为。

## 6. 失败时仍要收尾

本项目采用basic文件保证：创建前的校验失败不产生文件，已有输出不被覆盖；新文件写失败可能留下部分内容，其独占scratch拥有者负责清理。我们没有声称rename事务、断电一致性或回滚所有外部副作用。

测试程序先收集失败，再清理自己成功新建的绝对临时目录，最后报告失败。不能在创建目录之后立即调用会std::exit的check并期望局部析构自动发生：exit不展开当前自动对象栈。负例被预期拒绝和Student未完成都必须遵守清理责任。

清理范围只包含create_directory明确成功创建的直接子目录；清理失败是测试失败，并且优先于预期的Student/bad失败诊断。Windows临时目录返回值可能带末尾分隔符，而child.parent_path()不带，直接比较会误拒绝清理。实现先canonical已有临时父目录并去掉末尾空元素，再创建和验证其直接子目录。这是路径表示差异的实际例子，不是通过放宽检查允许删除任意路径。它不遍历和删除Manifest中的资源路径，也不修改已有用户目录。

## 7. 作业与解析

在[P1练习](../exercises/P1_resource_manifest/README.md)实现run_pipeline。提供的低层操作是前面课程已经建立的能力，允许直接复用；评分对象是组合顺序、实际文件数据流、错误传播和返回所有权。

1. **为何先验证展示zone？** 它可以在创建输出之前失败。固定UTC不需要外部tzdb，具名时区使用实际数据库；缺环境不能偷偷改为UTC后宣称原请求成功。
2. **可以直接返回原Manifest吗？** 即使值恰好相等，也没有完成回读任务。必须把实际文件字节交decoder，检查器与源码审查共同验证这条路径。
3. **为什么保留note为空的黄金输入？** 它击中optional空态与空字符串混淆，属于schema语义而非容器小细节。
4. **一次磁盘往返通过证明什么？** 证明当前环境、输入与版本下这条路径通过约定检查；不证明跨版本无损、断电恢复或所有文件系统等价。
5. **何时把本项目接到RPC/数据库？** C11补齐分帧、连接和资源责任，C12补齐格式兼容、事务与恢复之后。这里的DataError与有限字节边界可复用，但不得把同步文件调用直接当成异步网络完成模型。

项目文件存在只能算材料存在；是否通过要按构建指南重新运行当前源码并核对失败边界。
