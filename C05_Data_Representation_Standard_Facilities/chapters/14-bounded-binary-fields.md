# 14：从四个长度字节到一个可信文本字段

一个资源名称跨过文件或网络边界后，不再是已经满足不变量的std::string。接收端先看见字节，随后才有长度、文本和业务含义。本章实现这条链中最小而完整的一段：从一个输入缓冲区读取`u32be length + UTF-8 bytes`，成功返回拥有型字符串，失败保留调用前游标。它既是本课复杂样章，也是下一章TLV和结课资源清单的先修。

硬先修为01—03的对象表示、显式端序与整数边界，04—06的借用、Unicode和严格转码，以及C03的expected/异常基础。这里不需要先学完整配置解析、时区或泛型课程。使用的模板只有指定无符号整数类型读取固定宽度字段；不把模板技巧藏在答案里。

## 1. 先区分三个层次的正确性

输入`00 00 00 02 C3 A9`有六个octet。前四个表示整数2，后两个是U+00E9的UTF-8序列。length数的是payload的字节，不是码点、UTF-16码元或字素。如果写入方把“é有一个字符”当成length=1，接收方会得到截断的UTF-8，即使双方使用同一台小端机器也无法正确交换数据。

读取器依次承担三种责任。结构层要求长度头完整、长度有限且payload实际存在。文本层要求payload是合法UTF-8。业务层可能进一步要求名称非空、禁止NUL、某些字段必填；这些规则属于Manifest，不应该偷塞进通用UTF转换器。L14允许空串和NUL，后续Manifest明确拒绝名称中的NUL，两个契约没有矛盾。

字节层的输入是`span<const byte>`，它不拥有缓冲。返回的string拥有拷贝，调用者销毁或改写原缓冲不影响文本。返回指向payload的string_view也可以形成另一种接口，但它会增加后续调用者的存活责任；本课固定拥有型输出，没有对借用版本作速度排名。

## 2. 正确但有限的基线：只读取有界字节片段

从最简单的有界读取开始。已知游标pos和请求的n，先证明pos没有越过输入，再用减法检查剩余量：

```cpp
if (pos > input.size() || n > input.size() - pos) {
    // 拒绝；没有下标访问或分配发生。
}
auto slice = input.subspan(pos, n);
```

这个基线能正确返回任意字节片段，但没有声称片段是文本。不能把它对字节契约的正确性偷换成“所有名称已经可信”。`c05::take_bytes`提供这一层的可运行入口，L02检查正常、零长度、剩余不足和越界游标。返回的span仍然借用原输入。

为什么不用`pos + n <= input.size()`？size_t的加法可能模回绕，结果小并不说明原请求小。一个安全的算术实验可以用`numeric_limits<size_t>::max()`附近的值观察回绕而不访问任何内存；它证明的是判定表达式不可靠，不是假称实际越界程序必定崩溃。减法检查也有前提：必须先验证pos<=size，否则减法本身会回绕。短路`||`把这两步顺序固定下来。

长度头通过`read_be<uint32_t>`逐octet累积：已有值左移8位，再合入下一octet。字段宽度和端序来自格式，不来自本机对象布局。先保证四字节存在，再进行读取；不能把byte指针强转uint32_t指针，因为那同时引入对齐、对象存活、别名与本机端序假设。`bit_cast`也不会自动检查缓冲长度或替你选择协议端序。

## 3. 先复现状态问题，再推导提交点

L14的独立bad变体先消耗四字节长度头，再检查payload是否存在。对`00 00 00 03 78`，它正确发现三个payload字节不足，却留下cursor=4。调用者若根据失败保留输入并等待更多字节，下一次就会把`78`附近的数据误当成新长度头。

这是确定的状态契约错误，可以在安全有限输入上复现，不需要真实socket、sleep、竞态或UB。检查器先证明正常输入能读，再在这组截断输入上检查失败和cursor保持不变。bad由诊断`truncated payload keeps cursor`拒绝。该变体保留长度上限、访问边界与UTF验证，只改变游标提交时机；一次进程在第一条失败处终止，不能把这一条拒绝日志说成已分别运行完所有失败路径。

改进只针对已识别的状态问题：先复制游标到probe，所有中间操作都推进probe。直到长度检查、文本构造和UTF验证全部成功，才提交一次`cursor = probe`。不必为每个return手写回滚，新增失败分支时也不会忘记恢复游标。

```cpp
auto probe = cursor;
auto length = c05::read_be<std::uint32_t>(input, probe);
// 检查length、取得payload、构造string、严格验证UTF-8。
// 所有失败出口只影响局部对象。
cursor = probe; // 最后一个不抛操作提交解析位置。
return text;
```

完整实现位于[bytes.hpp](../exercises/include/c05/bytes.hpp)。这里的省略段不是作业接口：正文以下逐一推导，练习提供完整签名和真实检查。字符串构造可能抛bad_alloc；局部probe仍能使外部cursor不变。expected描述的是可诊断输入错误，不代表所有异常都被捕获。外部缓冲本身从不被写入。

## 4. 字段长度不是分配指令

读取u32成功后，马上检查length<=4096；随后检查输入还剩这么多字节，最后才为拥有型字符串分配。上限4096是本课程文本字段的格式约定，不能推广为Unicode本身的限制。过大的长度应报告limit_exceeded，即使输入也不够长；验证顺序使这一诊断稳定。

为什么既有限额又检查实际剩余长度？前者约束资源承诺，后者约束当前访问是否合法。只有实际剩余检查时，攻击者仍可以提供一个合法但过大的缓冲使读取器分配大量内存；只有上限时，小于上限的截断输入仍会越界。两者都成立才允许推进。

本章读取一个字段，不要求消耗整个外层输入。例如`00 00 00 02 6F 6B 99`读取后得到`ok`、cursor=6，最后的99留给外层协议。后续完整Manifest解码器在预期记录全部读完后另行拒绝尾随字节。把“单字段可以有后续数据”和“完整消息拒绝尾随数据”混在一起，会造成内外层接口互相矛盾。

## 5. 编码验证与错误位置

构造std::string只是保存字节，不是UTF验证。对payload `E2 28 A1`，首字节要求两个continuation byte，但28不符合10xxxxxx形式；读取器必须失败。严格检查还包括不允许overlong序列、UTF-16代理区标量、超出U+10FFFF和截断序列。未分配码点及Unicode noncharacter不因此变成非法UTF。

通用验证函数返回payload内坏序列起点。本层将它加到payload在整个buffer中的起点。例如字段从buffer偏移0开始，长度头四字节，则上述错误offset=4；如果字段从偏移7开始，错误应为11。不要把UTF-16码元下标或码点计数当成byte offset。DataError明确记录位置单位，映射后保留字段上下文。

遇到坏文本不自动替换为U+FFFD。替换是另一个有损策略，需要调用者明确选择，并规定消耗多少坏字节。资源标识若偷偷替换，两个不同坏输入可能变成同一个有效名称；因此本课包格式采用严格拒绝。ICU扩展也必须先验证输入，再调用可能执行替换的便利接口。

| Part | 必须完成 | 解析与常见误区 |
|---|---|---|
| 有界头/payload | 局部游标、显式大端、零长度与剩余检查 | 先证明pos<=size，再作size-pos；零长度是合法通用字段，不是默认错误 |
| 资源上限 | 在字符串分配前拒绝4097字节请求 | 不能用最终抛bad_alloc代替输入限额，也不能只检查vector容量 |
