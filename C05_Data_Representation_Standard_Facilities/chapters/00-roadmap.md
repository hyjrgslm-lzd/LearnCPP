# 00：数据表达这门课到底解决什么

C05的主线是“资源清单与数据包”。程序里的一条资源记录有id、名称、路径、大小和修改时间；一旦它写入文件、跨进程传递或从配置中读回，就不再是已经满足C++类型不变量的对象，而是一段需要重新解释的字节。C05从对象表示、整数、文本、时间、路径、配置和二进制字段一路推进到完整Manifest包。每一章都回答同一个工程问题：这个值在内存里、在字节流里、在文本里、在操作系统边界里分别是什么，谁拥有它，谁验证它，失败时保留什么证据。

本课不是“常用标准库API速查”。`std::string`、`std::span`、`std::expected`、`std::filesystem`、`std::chrono`、`std::format`和可选ICU都只是工具。真正要建立的是契约意识：对象表示不是序列化格式，字符个数不是字节数，路径的词法相等不是同一个文件，UTC时间点不是本地显示，解析成功不是全消费，格式化输出不是协议。

## 1. 课程边界

默认语言标准为C++23，练习命名空间为`c05`或`c05_ex`。核心路径不依赖ICU；ICU只在后续文本语义扩展中显式启用。错误使用`std::expected<T, c05::DataError>`表示可诊断的外部输入问题，例如编码非法、长度不足、版本不支持、字段缺失或超过资源上限。内存分配失败这类系统异常可以传播，不强行塞进`DataError`。

`DataError`有四类信息：

- `code`说明错误类别。
- `offset`和`unit`说明位置，单位可能是byte，也可能是UTF-16 code unit。
- `field`是拥有型字符串，用来指出上下文，不能借用临时输入。
- `line`用于配置文件诊断。

这门课统一采用“输入视图只在调用期间借用，成功结果拥有数据”的默认契约。`std::span<const std::byte>`和`std::string_view`可以减少复制，但它们不延长底层缓冲生命期；一旦值要离开调用边界，返回`std::string`、`std::u16string`或结构体对象。

## 3. 构建与运行入口

从本课练习目录运行核心验证：

```powershell
cmake --preset verify-core
cmake --build --preset verify-core
ctest --preset verify-core
```

Debug路径：

```powershell
cmake --preset verify-debug
cmake --build --preset verify-debug
ctest --preset verify-debug
```

学生实现路径默认关闭Reference，避免作业不小心包含答案。刚拿到Starter时，`ctest --preset student`会在未完成的实现题上失败；完成对应`src/student/...`后再用它验收：

```powershell
cmake --preset student
cmake --build --preset student
ctest --preset student
```

单题也能独立配置。例如L06：

```powershell
cmake -S L06_transcoding -B build/leaf-L06 -G "Visual Studio 18 2026" -A x64
cmake --build build/leaf-L06 --config Release --parallel 2
ctest --test-dir build/leaf-L06 -C Release --output-on-failure
```

观察题通过只说明观察程序实际跑完，不说明你已经理解了解析；实现题通过说明检查器覆盖了当前声明的契约，不说明所有可能平台和所有输入空间都被穷尽。

## 4. 练习分类

观察题提供完整程序，目标是让你把输出和正文里的规则对应起来。L01、L02、L04、L05属于这一类。你不需要改代码，但需要能解释每个`check`为什么是这个断言。

实现题要求只改`src/student/...`。L03和L06属于这一类。检查器通过包含路径选择学生实现；改checker、改Reference、硬编码结果或直接转发Reference都不是完成作业。

每个实现题还有两个控制样本：`validation/good`是独立正确实现，用来证明检查器不会只接受Reference；`validation/bad`是代表性错误，用来证明检查器能拒绝常见坏法。`bad_rejected`通过的含义是“坏实现按预期被拒绝”，不是“坏实现正确”。

## 5. 证据边界

C05会频繁使用“示意模型”：例如用安全整数表达式说明`pos + n`会回绕，用对象表示观察说明`bit_cast`复制的是表示，用固定字节序列说明UTF非法。示意模型证明的是规则和推理链，不假称真实未定义行为一定在本机崩溃。真正访问越界、违反对象生命期、违反严格别名或依赖未初始化padding的程序没有稳定结果，本课不会用一次运行现象冒充标准保证。

源码导读同样要分层：标准规则说明哪些行为被允许；当前MSVC/STL或ICU观察说明本机实现怎样表现；协议推导说明本课格式在这些规则上选择了什么。不把实现细节写成标准，也不把标准允许行为写成当前工具链必然输出。

## 6. 自测与解析

**问：为什么C05从对象表示讲起，而不是直接讲序列化？**

答：因为很多序列化错误都来自把“对象内存”误当成“协议字节”。C++对象可能有padding，整数有本机端序，某些表示可能不是目标值的合法表示；对象生命期、对齐和别名规则还限制你能不能用某个类型的指针读取那段内存。先讲对象表示，才能解释为什么C05的wire format必须显式规定字段宽度、端序、长度和文本编码。

**问：`std::expected`是不是意味着函数不会抛异常？**

答：不是。本课用`expected`返回可诊断的输入错误，例如UTF-8非法或长度不足。分配失败、系统资源失败等异常可以传播。这个区分避免把外部数据坏了和本机资源耗尽混在一个错误码里。

**问：为什么通用UTF转换保留NUL和BOM，而Manifest名称又拒绝NUL？**

答：这是分层。UTF转换只判断编码是否合法，并把码元变成另一种UTF表示。NUL是合法Unicode scalar value，开头BOM是否作为签名处理是上层文本格式规则。Manifest名称是业务字段，它额外规定拒绝NUL、非空、长度上限等。下层少做业务判断，才能被配置、日志、测试数据等不同场景复用。

**问：为什么单字段读取允许尾随字节，而完整包解码要拒绝尾随数据？**

答：单字段读取只消费它负责的字段，后面可能还有下一个字段。完整包解码已经知道消息边界，读完后还有字节说明外层格式没有被完全解释，应该拒绝。内外层契约不同，不矛盾。
