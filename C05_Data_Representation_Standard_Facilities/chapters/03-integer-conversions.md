# 03：整数转换、提升与长度边界

协议字段最终会进入C++表达式。这里最容易丢证据：先把`uint64_t`窄化成`uint32_t`再检查，越界值已经变了；把`signed`和`unsigned`混在同一个比较里，负数可能先转换成很大的无符号数；用`pos + len <= size`判断空间，和可能回绕的加法赌运气。C05把这些问题放在解析之前讲，是因为后续每个长度、计数、版本和offset都依赖它。

## 1. 转换不同于溢出

有符号整数算术溢出是未定义行为，例如`int`最大值再加一。无符号整数算术按模`2^N`回绕，例如`uint32_t`最大值加一得到0。整数转换又是另一件事：把一个大`uint64_t`转成`uint32_t`会按目标宽度截断，得到某个可表示的`uint32_t`值。这个结果看起来“合法”，但原始越界证据已经消失。

L03的坏实现通常这样写：

```cpp
auto narrowed = static_cast<std::uint32_t>(value);
if (narrowed != value) fail();
```

当`value == uint32_max + 1`时，`narrowed`已经是0。后面的比较还会触发整型提升和类型转换，推理更绕。正确做法是先在源类型里比较边界：

```cpp
if (value > std::numeric_limits<std::uint32_t>::max()) {
    return std::unexpected(c05::DataError{c05::Errc::out_of_range});
}
return static_cast<std::uint32_t>(value);
```

## 2. 整型提升和通常算术转换

`uint8_t`和`uint16_t`在表达式里通常会先提升到`int`或`unsigned int`。这让很多“看起来是8位”的计算实际在更宽类型里完成。提升本身不是坏事，但如果你以为每一步都在原宽度里，边界判断就会错。

混合`signed`和`unsigned`更危险。表达式`-1 < 1u`通常不是按数学整数比较；`-1`会转换成无符号大值，结果为false。C++20起提供`std::cmp_less`、`std::cmp_equal`等比较函数，也提供`std::in_range<T>`检查值是否能放进目标整数类型。它们能表达意图，减少手写转换错误。

本课L03输入是`uint64_t`转`uint32_t`，不需要复杂比较工具；直接在`uint64_t`域里比较`uint32_t::max()`已经足够。工具不是越多越好，关键是边界检查发生在信息丢失之前。

## 3. 长度计算先做减法检查

所有外部长度都要先证明不会越界，再访问或分配。错误形状：

```cpp
if (pos + len <= buffer.size()) use(buffer.subspan(pos, len));
```

`pos + len`可能回绕。正确形状：

```cpp
if (pos > buffer.size() || len > buffer.size() - pos) fail();
```

这和02章`read_be`完全一致。先证明`pos`在范围内，再用剩余量判断`len`。后续文本字段、TLV字段、配置行和包大小都沿用这个形状。

## 4. 资源上限和实际剩余量是两条规则

长度字段合法不等于应该分配。C05的通用文本字段上限是4096字节，完整包上限是1MiB，记录数上限是1024。读到`length = 500000`时，即使输入缓冲真的有这么多字节，也应该先拒绝文本字段上限。读到`length = 100`时，即使小于上限，也要检查当前输入是否还有100字节。

上限控制资源承诺，剩余量控制访问安全。两条都要有。

## 5. 浮点转换也要先检查范围

后续格式化和解析会遇到浮点。整数转浮点通常能表示更大范围，但不能精确表示所有整数；浮点转整数如果值不在目标范围内，行为不是你想要的“自动报错”。因此从外部文本或二进制读到浮点，再转整数前必须检查：

- 是否为finite，排除NaN和无穷。
- 是否在目标整数可表示范围内。
- 是否满足业务要求，例如必须是整数、非负或不超过字段上限。

不要用“不恰当的`max -> double`比较”写范围检查。某些最大整数转换成`double`后会因为舍入变成相邻值，边界判断不再精确。保守做法是优先在整数域解析整数；如果输入语法允许小数，先把业务规则讲清，再用能覆盖边界的检查和测试数据验证。

## 7. 自测与解析

**问：为什么不能先`static_cast<uint32_t>`，再看结果是不是变小？**

答：窄化已经丢掉高位。`uint32_max + 1`会变成0，之后你只能看见0，看不见原始输入越界。边界检查必须发生在源值还完整的时候。

**问：无符号回绕是定义良好的，为什么仍然要避免？**

答：定义良好只说明语言规定了结果，不说明这个结果符合业务。长度、offset和容量表达的是范围证明；回绕会把“不够空间”伪装成“小数字”。协议解析里它通常是安全漏洞或数据损坏入口。

**问：什么时候用`std::in_range`？**

答：当源类型和目标类型可能符号不同或宽度不同，而你想表达“这个值能否无损放进目标整数类型”时使用。L03的源是`uint64_t`，目标是`uint32_t`，手写`value > max`简单且清楚；更复杂的signed/unsigned比较可优先用`std::cmp_*`和`std::in_range`。

**问：`float`或`double`能不能作为通用中转类型检查整数范围？**

答：不能默认这么做。浮点有舍入，不能精确表示所有大整数。边界附近尤其容易出错。外部整数最好直接解析到足够宽的整数域，再检查目标范围。
