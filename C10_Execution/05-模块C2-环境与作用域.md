# 05 模块 C2：环境与作用域

## 模块目标

模块 C1 解决了"非正常路径怎么处理"。这个模块解决另外两个框架级问题：

- 执行上下文不是普通参数，environment 查询才是异步框架传递上下文的正确方式
- 生命周期必须有人拥有并收束，`async_scope` 是结构化并发的关键工具

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- 为什么 `get_scheduler()`、`get_stop_token()` 更像 environment 查询，而不是业务参数。
- 为什么 `async_scope` 一类对象对结构化并发是必需的。
- 为什么 `start_detached` 比 `async_scope::spawn` 更危险。

## 练习 9：environment 不是普通参数

### 目标

用 `get_scheduler()` 与 `get_stop_token()` 直接练 environment 查询，建立"执行上下文是从 receiver 一侧传下来的"这件事的直觉。

### 前置理解

- 你已经做完模块 B，知道 scheduler 可以显式进入图。
- 你知道 `get_scheduler()`、`get_stop_token()` 不是普通函数调用结果，而是 query sender。
- 你接受本题的重点是"上下文怎么被查询"，不是"取消机制细节全覆盖"。

### 必做任务

1. 创建一个线程池，并准备一个最小 payload，例如 `task_id`、计数值或请求编号。
2. 让一段 sender 在该线程池上开始执行。
3. 在这段图中显式读取当前 environment，至少读取两项：
   - `get_scheduler()`
   - `get_stop_token()`
4. 把 payload、当前 scheduler 查询结果、stop token 查询结果汇总成一个你自己定义的结构体，例如 `RuntimeContextSnapshot`。
5. 再利用查询到的 scheduler，继续构造一小段新 sender，让它在"当前 scheduler"上追加一段日志或处理。
6. 最终同步等待并输出快照信息。

### 进阶任务

- 把读取 environment 的逻辑封装成一个独立函数，返回 sender，再在主流程中组合它。
- 如果你固定的 `stdexec` 版本支持更明显的 stoppable 场景，额外实验 stop token 的可观察状态。
- 再做一个反例版本：把 scheduler 和 token 都当普通参数层层手动传，比较接口噪音。

### 验收点

- 你能运行出包含 scheduler 与 stop token 查询痕迹的结果。
- 你能解释这些值不是业务 payload，而是执行上下文。
- 你能说明为什么 environment 查询比手动逐层传参数更适合异步框架。
- 你能指出查询结果是在 sender 图的哪个阶段进入后续逻辑的。

### 观察点

- environment 更像"系统上下文"而不是"业务输入"。
- 通过 query sender 读取环境，可以让下游阶段在不破坏接口的前提下感知执行条件。
- 当你能从环境里拿到 scheduler，再返回一段 sender 时，会非常直观地感受到"上下文通过 receiver 侧传播"的设计。

### 常见坑

- 把 scheduler/token 直接写成外部捕获变量，结果没练到 query 模型。
- 把 query sender 当成立即求值的普通函数，导致心智模型混乱。
- 让快照结构体承担太多业务字段，反而看不清 environment 本身。
- 把停止语义理解成"肯定等于异常"。

### 提示

- 参考 `hello_world` 中 `when_all(just(...), get_scheduler(), get_stop_token())` 这一类形状。
- 你的快照结构体不需要真的打印 scheduler 的内部细节，只要能记录"我拿到了当前 scheduler 对象"以及相关阶段信息即可。
- 如果 stop token 的可视化不明显，可以至少记录"当前图能够读取 stop token"。
- 不要把这题做成取消系统实现题，重点是 query 机制。

### 复盘问题

- 为什么 environment 更适合承载 scheduler 和 stop token，而不是普通业务参数？
- 如果后续某个库适配器也需要知道 scheduler，你更希望它怎么拿到这个信息？
- 为什么 query sender 的存在会让算法层更解耦？
- 这题里，receiver 和 environment 的关系是什么？

### 对应官方参考

- `stdexec/examples/hello_world.cpp`
- `NVIDIA/stdexec` README 中 `get_scheduler` / `get_stop_token` 的示意

## 练习 10：作用域和生命周期

### 目标

用 `async_scope` 或同类作用域对象管理一组异步工作，真正回答"这些 operation_state 到底归谁拥有、谁来等它们收尾"。同时通过对比 `start_detached`，理解为什么结构化并发比 fire-and-forget 更安全。

### 前置理解

- 你已经知道 sender 不是执行实例，`operation_state` 才是一次具体执行。
- 你已经接触过并列分支与显式调度。
- 你理解这题的重点是结构化并发，不是"如何最快启动更多任务"。

### 必做任务

1. 创建一个线程池和一个 `async_scope`。
2. 构造至少 5 个独立 sender，每个 sender 都带任务编号，并在池上执行一小段可观察工作。
3. 至少做两类任务：
   - 一类只需要完成即可
   - 一类需要返回结果给主流程
4. 对前者使用 `scope.spawn(...)` 一类接口，对后者使用 `scope.spawn_future(...)` 一类接口。
5. 在准备销毁线程池之前，显式等待 scope 为空，例如等待 `scope.on_empty()` 或同类收束点。
6. 记录并画出：scope、线程池、sender、operation_state 之间的拥有关系。
7. 做一个对比实验：如果你的版本支持 `start_detached`，用它替换 `scope.spawn()` 启动同一批任务。观察：
   - 谁拥有这些 operation_state 的生命周期？
   - 你还能等待它们全部完成吗？
   - 如果提前销毁线程池会怎样？
   - 对比之后写下：`start_detached` 为什么是"fire-and-forget"，为什么在结构化并发里应该避免使用它。

### 进阶任务

- 让返回结果的那部分任务形成一个小型结果汇总。
- 再做一个故意写坏的版本：提前销毁线程池或跳过等待，观察为什么结构上不安全。
- 如果你愿意，再试一次把前面模块 B 的流水线放进 scope 中，感受"图"和"拥有者"如何配合。

### 验收点

- 你能保证所有任务在执行资源销毁前被收束。
- 你能清楚区分"启动工作"和"拥有工作生命周期"是两件不同的事。
- 你能解释 `spawn` 与 `spawn_future` 在语义上的差异。
- 你能指出作用域对象解决的是哪类 bug 风险。
- 你能说明 `start_detached` 与 `scope.spawn` 的核心差异：前者无人拥有生命周期，后者被 scope 收束。

### 观察点

- scope 的价值不在于多一个容器，而在于把异步生命周期显式组织起来。
- 一旦 sender 图变复杂，谁拥有 operation_state 就不再是小问题。
- 结构化并发的本质是：每条工作最终都要能被某个上层对象收束。
- `start_detached` 是结构化并发的"逃逸阀"——它让你绕过生命周期管理，代价是失去收束保证。

### 常见坑

- 把 sender 构好就以为生命周期问题已经解决了。
- 线程池先析构，scope 还没空，结果留下悬挂工作。
- 只关注 `spawn` 的便捷，而不去区分有没有结果需要回收。
- 把 scope 当成"另一个线程池"，概念上完全错位。
- 认为 `start_detached` 只是 `scope.spawn` 的简写——它们在生命周期保证上完全不同。

### 提示

- 参考官方 `scope.cpp` 的思路，先从最小版本开始。
- 任务内容不需要复杂，只要能清晰展示生命周期即可。
- 先把等待收束路径跑通，再去补日志和结果汇总。
- 画图时重点标注"谁拥有谁"，不要只画调用顺序。
- `start_detached` 的对比实验可以先看编译是否通过，再分析行为差异。

### 复盘问题

- 为什么结构化并发强调的是"拥有关系"而不是"启动技巧"？
- 如果没有 scope，你会把这些 operation_state 交给谁负责？
- 为什么 fire-and-forget 常常意味着"谁也不真正负责它直到结束"？
- `start_detached` 在什么极少数场景下是合理的？在一般工程中为什么应该避免？
- 这题里，sender 图与生命周期拥有者之间是什么关系？

### 对应官方参考

- `stdexec/examples/scope.cpp`

## 做完模块 C2 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- scheduler、stop token 这类信息更像 environment 查询值，而不是业务参数。
- `async_scope` 的核心价值是结构化收束一组 operation_state。
- `start_detached` 放弃了生命周期管理，是结构化并发的逃逸阀。
- 真正的异步框架设计，不仅要会"怎么启动"，还要会"怎么传播上下文、怎么管理生命周期、怎么处理非正常完成"。
