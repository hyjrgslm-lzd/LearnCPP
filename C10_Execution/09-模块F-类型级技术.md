# 09 模块 F：类型级技术

## 模块目标

前面的模块让你学会了怎么使用 sender 组合器、手写 sender/receiver、理解 CPO 机制。这个模块要把你拉进更深的一层：

- 理解 sender 组合为什么能在编译期完成类型安全检查
- 亲手实现类型列表（type list）及其编译期操作
- 理解 `completion_signatures` 不只是"声明一下签名"，而是 sender adaptor 做类型推导的基础设施
- 从零实现 sender/receiver concept，把"concept 约束到底检查了什么"刻进直觉
- 理解为什么整个 `std::execution` 框架是"类型驱动"的——类型在编译期流动，值在运行期流动

如果你跳过这一层，就很难理解 `then`、`let_value`、`when_all` 等 adaptor 是如何在不运行任何代码的情况下推导出输出签名的。你也很难自己写出能融入标准生态的 sender adaptor。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- 为什么 sender 组合器需要在编译期操作类型列表。
- 为什么 `completion_signatures` 是 sender 可组合性的类型级基础设施。
- 为什么 `make_completion_signatures` 的本质是"给定输入签名和变换规则，算出输出签名"。
- 为什么 sender 和 receiver 的 concept 约束不是"可有可无的接口检查"，而是组合正确性的编译期保证。
- 为什么类型级技术是理解 `std::execution` 实现的必经之路。

## 使用建议

- 本模块全程在编译期工作。你的主要验证手段是 `static_assert`，而不是运行期打印。
- 如果你对模板元编程不熟悉，不要慌——每道题都从最小的类型操作开始，逐步搭建。
- 先做出能编译通过的最小版本，再追求泛化和优雅。
- 编译错误信息在这个模块里是你最重要的调试工具。学会读它们。

## 练习 F-1：类型列表基础设施

### 目标

亲手实现 `type_list<Ts...>` 及其编译期操作（合并、去重、变换、过滤），建立"类型列表是 sender 框架的编译期容器"的直觉。

### 前置理解

- 你知道 C++ variadic template 的基本语法：`template <typename... Ts> struct type_list {};`。
- 你知道 `static_assert` 可以在编译期检查条件。
- 你接受这题的重点是编译期类型操作，不涉及运行期行为。
- 你大致知道 `std::is_same_v` 可以用来比较两个类型是否相同。

### 必做任务

1. **定义 `type_list<Ts...>`**：一个空的模板结构体，只用来承载类型参数包。它没有任何数据成员，纯粹是编译期的类型容器。

   ```cpp
   template <typename... Ts>
   struct type_list {};
   ```

2. **实现 `concat<TypeList1, TypeList2>`**：把两个 type_list 的类型参数合并成一个新的 type_list。例如：
   - `concat<type_list<int, float>, type_list<double>>` 应该得到 `type_list<int, float, double>`
   - 用偏特化（partial specialization）来拆开两个 type_list 的参数包

   ```cpp
   // 提示骨架
   template <typename L1, typename L2>
   struct concat_impl;

   template <typename... Ts, typename... Us>
   struct concat_impl<type_list<Ts...>, type_list<Us...>> {
       using type = type_list<Ts..., Us...>;
   };

   template <typename L1, typename L2>
   using concat = typename concat_impl<L1, L2>::type;
   ```

3. **实现 `unique<TypeList>`**：去除 type_list 中的重复类型。例如：
   - `unique<type_list<int, float, int, double, float>>` 应该得到 `type_list<int, float, double>`
   - 实现思路：递归遍历，对每个类型检查它是否已经在结果列表中出现过
   - 你需要一个辅助模板 `contains<TypeList, T>` 来检查某个类型是否在列表中

4. **实现 `transform<TypeList, MetaFn>`**：对 type_list 中的每个类型应用一个元函数，生成新的 type_list。例如：
   - 定义元函数 `add_pointer`：`template <typename T> struct add_pointer { using type = T*; };`
   - `transform<type_list<int, float>, add_pointer>` 应该得到 `type_list<int*, float*>`
   - 元函数是一个模板，它接受一个类型参数，内部定义 `using type = ...`

5. **实现 `filter<TypeList, Pred>`**：保留 type_list 中满足谓词的类型。例如：
   - 定义谓词 `is_integral_pred`：`template <typename T> struct is_integral_pred : std::is_integral<T> {};`
   - `filter<type_list<int, float, long, double>, is_integral_pred>` 应该得到 `type_list<int, long>`

6. **用这些工具模拟 `when_all` 的值类型合并**：
   - 假设 sender A 的值类型为 `type_list<int>`
   - 假设 sender B 的值类型为 `type_list<float, std::string>`
   - 用 `concat` 合并两个列表，得到 `type_list<int, float, std::string>`
   - 这就是 `when_all(just(int), just(float, string))` 的 `set_value_t` 参数列表的简化模型

7. **手动验证**：`when_all(just(int), just(float, string))` 应该产出 `set_value_t(int, float, string)`。用 `static_assert` 加 `std::is_same_v` 来验证合并后的类型列表与预期一致。

8. **所有验证通过 `static_assert`**：本题不需要 `main()` 里有运行期代码。如果所有 `static_assert` 通过，编译成功就是验收。

### 进阶任务

- 实现 `size<TypeList>` 编译期常量，返回类型列表的长度。
- 实现 `at<TypeList, N>` 编译期索引，返回第 N 个类型。
- 实现 `flatten<TypeListOfTypeLists>`：把嵌套的 type_list 展平成一层。例如 `flatten<type_list<type_list<int>, type_list<float, double>>>` 得到 `type_list<int, float, double>`。
- 用 `transform` + `filter` + `unique` 的组合来模拟一个更复杂的签名变换场景。
- 思考：为什么 `stdexec` 内部需要这些操作？哪些 sender adaptor 在推导签名时会用到合并、去重、变换？

### 验收点

- 你能实现 `concat`、`unique`、`transform`、`filter` 四个类型列表操作。
- 你能用 `static_assert` 证明每个操作的正确性。
- 你能用这些工具模拟 `when_all` 的值类型合并。
- 你能说明为什么 sender 框架需要在编译期做这些类型列表操作。

### 观察点

- `type_list` 就是编译期的 `std::vector`——只不过它装的是类型，不是值。
- `concat` 就是编译期的 `push_back` / `append`。
- `transform` 就是编译期的 `std::transform`。
- `filter` 就是编译期的 `std::copy_if`。
- `unique` 就是编译期的去重。
- 整个 sender 框架的类型推导层，本质上就是在对这种"类型容器"做各种编译期算法。
- 当你理解这一层之后，再看 `stdexec` 源码里那些看似复杂的模板元编程，就会发现它们其实在做很朴素的事情。

### 常见坑

- 忘记递归终止条件，导致模板递归无限展开，编译器报"超出最大模板深度"。
- `contains` 的实现漏掉了空列表的 base case。
- `unique` 的实现逻辑倒置：应该是"如果不在结果中，才加入"，而不是"如果在结果中，才加入"。
- `transform` 的元函数忘了定义 `type` 成员，导致 `::type` 无法访问。
- `filter` 的条件谓词返回类型不对——谓词应该有一个 `value` 编译期常量。
- 一开始就追求"完美通用实现"，忽略了先做最小可编译版本。

### 提示

- 每实现一个操作，就立刻用 `static_assert` 测试它。不要写完所有代码再一起编译。
- 递归模板的关键是：base case + 递归 case。先写 base case。
- 如果编译错误看不懂，把模板参数手动展开一两层，在纸上画出递归树。
- `std::is_same_v<type_list<int, float>, type_list<int, float>>` 就是 `true`——可以直接用来比较两个 type_list。
- 元函数的标准形式是：`template <typename T> struct MetaFn { using type = ...; };`。
- 谓词的标准形式是：`template <typename T> struct Pred { static constexpr bool value = ...; };`，或者继承自 `std::true_type` / `std::false_type`。

### 复盘问题

- 为什么 sender 框架不在运行期做这些操作，而是坚持在编译期完成？
- 如果没有类型列表操作，`when_all` 的实现者如何知道汇合后的值类型是什么？
- `transform` 操作在 sender adaptor 里对应什么现实场景？（提示：`then(f)` 会把输入类型变换成输出类型。）
- 你觉得 `filter` 操作在什么场景下有用？（提示：`upon_error` 只关心 error channel，需要把 value channel 和 stopped channel "过滤"出来分别处理。）
- 编译期类型操作与运行期容器操作，在思维方式上最大的差异是什么？

### 对应官方参考

- `stdexec` 内部的 `__types` / `__type_list` 工具
- P2300 中 `completion_signatures` 的类型操作说明
- Boost.Mp11 或类似元编程库的设计思路

## 练习 F-2：completion_signatures 定义与变换

### 目标

亲手定义和变换 `completion_signatures`，理解 sender adaptor 是如何在编译期从输入签名推导出输出签名的。这是 sender 可组合性的类型级核心。

### 前置理解

- 你已经完成练习 F-1，能够操作类型列表。
- 你知道 sender 需要声明 `completion_signatures`（模块 D 练习 12 中已接触过）。
- 你理解 `completion_signatures` 描述的是"这个 sender 可能以哪些方式完成"。
- 你接受这题先用自己的简化版实现，不需要完全对齐标准库的所有细节。

### 必做任务

1. **定义简化版 `completion_signatures`**：

   先定义表示三种 completion 的标签类型：

   ```cpp
   template <typename... Args>
   struct set_value_t {};    // set_value_t(int) 表示 set_value(int)
   
   template <typename Err>
   struct set_error_t {};    // set_error_t(exception_ptr) 表示 set_error(exception_ptr)
   
   struct set_stopped_t {};  // set_stopped_t() 表示 set_stopped()
   ```

   然后定义：

   ```cpp
   template <typename... Sigs>
   struct completion_signatures {};
   ```

   例如：`completion_signatures<set_value_t<int>, set_error_t<std::exception_ptr>, set_stopped_t>` 表示一个可能以 `set_value(int)`、`set_error(exception_ptr)` 或 `set_stopped()` 三种方式完成的 sender。

2. **实现 `value_types_of<Sigs>`**：从 `completion_signatures` 中提取所有 `set_value_t<...>` 签名。
   - 输入：`completion_signatures<set_value_t<int>, set_error_t<std::exception_ptr>, set_stopped_t>`
   - 输出：`type_list<set_value_t<int>>`
   - 实现思路：用 F-1 中的 `filter`，谓词是"是否为 `set_value_t` 的特化"

3. **实现 `error_types_of<Sigs>`**：从 `completion_signatures` 中提取所有 `set_error_t<...>` 签名。
   - 输入同上
   - 输出：`type_list<set_error_t<std::exception_ptr>>`

4. **实现 `sends_stopped<Sigs>`** 编译期谓词：检查 `completion_signatures` 中是否包含 `set_stopped_t`。
   - 结果是一个编译期 `bool` 常量
   - 用 F-1 中的 `contains` 来实现

5. **实现简化版 `make_completion_signatures`**：给定输入 completion_signatures 和一个类型变换规则，计算输出 completion_signatures。

   核心思路：
   - 取出输入签名中的 value types
   - 对每个 value type 应用变换规则，得到新的 value type
   - 保留原来的 error types 和 stopped
   - 组装成新的 completion_signatures

   ```cpp
   // 概念性伪代码（不是最终实现）
   // make_completion_signatures<InputSigs, ValueTransform>
   //   = completion_signatures<
   //       transform(value_types_of<InputSigs>, ValueTransform)...,
   //       error_types_of<InputSigs>...,
   //       (sends_stopped ? set_stopped_t : nothing)
   //     >
   ```

6. **用它模拟 `then(f)` 的签名推导**：
   - 假设输入签名为 `completion_signatures<set_value_t<int>, set_error_t<std::exception_ptr>, set_stopped_t>`
   - 函数 `f` 的类型为 `int -> std::string`
   - 那么 `then(f)` 的输出签名应该是 `completion_signatures<set_value_t<std::string>, set_error_t<std::exception_ptr>, set_stopped_t>`
   - 即 `set_value_t<int>` 变成了 `set_value_t<std::string>`，其余不变
   - 用 `static_assert` 验证

7. **处理 `f` 返回 `void` 的情况**：
   - 如果 `f: int -> void`，那么输出签名中的 value completion 应该变成 `set_value_t<>`（无参数的 set_value）
   - 这对应于 `then` 的语义："调用 f，如果 f 返回 void，则下游收到的是无参 set_value"
   - 在你的 `ValueTransform` 中特殊处理这种情况
   - 用 `static_assert` 验证

### 进阶任务

- 实现对多个 value completion 的变换。例如输入签名有 `set_value_t<int>` 和 `set_value_t<float>` 两种 value completion，`f` 是 `auto -> string`，那么两种 value completion 都变成 `set_value_t<std::string>`。最终 `unique` 去重。
- 尝试模拟 `let_value` 的签名推导：`f: int -> sender<string>` 时，输出的 value completion 取决于 f 返回的 sender 的签名，而不是 f 本身的返回类型。思考这比 `then` 的签名推导复杂在哪里。
- 实现 `add_error_type<Sigs, NewErr>`：给现有签名增加一种新的 error type。这在 sender adaptor 可能引入自己的错误时很有用。
- 思考：为什么标准中 `make_completion_signatures` 还需要接受一个 environment 参数？这和 `dependent_completion_signatures` 有什么关系？

### 验收点

- 你能从 `completion_signatures` 中提取 value types、error types，并检测 stopped。
- 你能实现简化版 `make_completion_signatures`，用它推导 `then(f)` 的输出签名。
- 你能处理 `f` 返回 `void` 的特殊情况。
- 你能用 `static_assert` 证明所有签名变换的正确性。
- 你能说明 `make_completion_signatures` 在 sender adaptor 实现中扮演什么角色。

### 观察点

- `completion_signatures` 是 sender 的"类型级合同"——它告诉下游 receiver 和组合器："我可能以这些方式完成"。
- `make_completion_signatures` 是 sender adaptor 的"类型级核心"——每个 adaptor 本质上都在做"给定上游签名，算出我的输出签名"。
- `then(f)` 只变换 value channel 的类型，不改变 error 和 stopped。
- `upon_error(f)` 只变换 error channel 的类型。
- `let_value(f)` 更复杂：f 返回的是 sender，所以输出签名取决于那个 sender 的签名。
- 当你理解了签名变换，就能理解为什么组合器能在编译期做完类型检查——一切都是类型级别的函数组合。
- 编译器看到 `then(f)` 时，不需要运行 f，只需要看 f 的返回类型，就能算出输出签名。

### 常见坑

- 把 `set_value_t<int>` 和 `set_value_t<>` 搞混——前者表示 `set_value(int)`，后者表示 `set_value()`（无参数）。
- 忘记处理 `void` 返回类型的特殊情况，导致 `set_value_t<void>` 这种不合法的签名出现。
- 在 `filter` 谓词中匹配 `set_value_t` 时，忘记它是一个模板，需要用模板模板参数或偏特化来检测。
- `make_completion_signatures` 的实现把 error types 和 stopped 弄丢了。
- 试图在一个步骤里完成所有变换，结果代码很混乱。应该分步：先提取、再变换、再组装。
- 编译错误信息很长，但通常最有用的信息在最后几行（"note: ..."），不要只看第一行。

### 提示

- 先把 `completion_signatures` 当成一个特殊的 `type_list` 来操作。
- 检测"是否为 `set_value_t` 的特化"可以用偏特化：
  ```cpp
  template <typename T>
  struct is_set_value : std::false_type {};
  
  template <typename... Args>
  struct is_set_value<set_value_t<Args...>> : std::true_type {};
  ```
- `f` 返回 `void` 时，用 `std::is_void_v<ReturnType>` 来分支处理。
- 先硬编码一个具体的变换（比如 `int -> string`），跑通后再泛化。
- 如果模板参数太多导致头疼，给中间结果起好名字：`using input_values = value_types_of<InputSigs>;` 等。

### 复盘问题

- 为什么每个 sender adaptor 都需要做签名变换？如果不做会怎样？
- `then(f)` 和 `let_value(f)` 的签名推导规则有什么本质区别？
- 为什么 `void` 返回类型需要特殊处理？在 sender 模型中，`set_value()` 和 `set_value(void)` 有什么区别？
- 如果一个 sender 有多种 value completion（比如 `set_value(int)` 和 `set_value(string)`），`then(f)` 的签名推导会变得更复杂吗？为什么？
- 你觉得 `make_completion_signatures` 这个名字反映了什么设计意图？

### 对应官方参考

- P2300 中 `completion_signatures` 的定义
- P2300 中 `make_completion_signatures` 的规范
- `stdexec` 中 `__make_completion_signatures` 的实现
- `stdexec` 中 `then` adaptor 如何使用签名变换

## 练习 F-3：sender/receiver Concepts 实现

### 目标

从零实现 sender 和 receiver 的 concept 约束，理解"concept 不是装饰性注释，而是 sender 图在编译期能自动检查类型匹配的基础"。

### 前置理解

- 你已经完成练习 F-1 和 F-2，理解类型列表操作和 completion_signatures。
- 你知道 C++20 concept 的基本语法：`template <typename T> concept MyConcept = requires(T t) { ... };`。
- 你在模块 D 中手写过 sender 和 receiver，知道它们需要满足哪些结构要求。
- 你接受本题的 concept 是简化版，不需要覆盖标准的所有细节。

### 必做任务

1. **实现 `my_sender<S>` concept**：检查类型 S 是否是一个合法的 sender。

   最小检查项：
   - S 内部定义了 `sender_concept` 类型别名（或 `using sender_concept = ...;`）
   - S 能提供 `completion_signatures`（即存在 `typename S::completion_signatures`，或通过 `get_completion_signatures` 可查询）

   ```cpp
   template <typename S>
   concept my_sender = requires {
       typename S::sender_concept;
       typename S::completion_signatures;
   };
   ```

   用 `static_assert` 测试：
   - 你在模块 D 中写的 `single_value_sender` 应该满足 `my_sender`
   - 一个普通的 `int` 不应该满足 `my_sender`
   - 一个只有 `sender_concept` 但没有 `completion_signatures` 的类型也不应该满足

2. **实现 `my_receiver<R>` concept**：检查类型 R 是否是一个合法的 receiver。

   最小检查项：
   - R 内部定义了 `receiver_concept` 类型别名
   - R 支持 `set_value` 调用（至少对某种参数可调用）
   - R 支持 `set_error` 调用
   - R 支持 `set_stopped` 调用

   ```cpp
   template <typename R>
   concept my_receiver = requires(R&& r) {
       typename std::remove_cvref_t<R>::receiver_concept;
       // 注意：这里我们只检查 stopped（无参数），
       // value 和 error 的参数类型检查留给 my_receiver_of
   };
   ```

   用 `static_assert` 测试：
   - 你在模块 D 中写的 `logging_receiver` 应该满足 `my_receiver`
   - 一个空结构体不应该满足

3. **实现 `my_receiver_of<R, Sigs>` concept**：检查 receiver R 是否能处理特定的 completion_signatures Sigs。

   这是更精细的检查：不仅要求 R 是 receiver，还要求 R 能处理 Sigs 中声明的每一种 completion。

   例如，如果 `Sigs = completion_signatures<set_value_t<int>, set_error_t<exception_ptr>, set_stopped_t>`，那么 R 必须：
   - 可以被调用 `set_value(R&&, int)`
   - 可以被调用 `set_error(R&&, exception_ptr)`
   - 可以被调用 `set_stopped(R&&)`

   实现思路：
   - 从 Sigs 中提取 value types、error types
   - 对每种 completion 检查 R 是否支持对应的调用
   - 这里需要把 F-2 的签名提取与 concept 约束结合起来

4. **用 `static_assert` 测试有效和无效的类型组合**，观察编译期诊断：

   ```cpp
   // 应该通过
   static_assert(my_receiver_of<logging_receiver, 
       completion_signatures<set_value_t<int>, set_error_t<std::exception_ptr>, set_stopped_t>>);
   
   // 应该失败——receiver 不接受 string 类型的 value
   // static_assert(my_receiver_of<int_only_receiver, 
   //     completion_signatures<set_value_t<std::string>>>);
   ```

   写一个只接受 `int` 的受限 receiver，验证当签名要求 `set_value(string)` 时，`my_receiver_of` 检查失败。

5. **实现 `my_sender_to<S, R>` concept**：检查 sender S 是否能连接到 receiver R。

   核心检查：
   - S 满足 `my_sender`
   - R 满足 `my_receiver`
   - R 满足 `my_receiver_of<R, typename S::completion_signatures>`——即 R 能处理 S 声明的所有 completion
   - S 和 R 之间可以调用 `connect`（即 `connect(S, R)` 是合法表达式）

   ```cpp
   template <typename S, typename R>
   concept my_sender_to = 
       my_sender<S> && 
       my_receiver<R> && 
       my_receiver_of<R, typename S::completion_signatures>;
       // 可以再加 connect 的检查
   ```

6. **进阶讨论：`dependent_completion_signatures`**：

   在标准中，某些 sender 的 completion_signatures 取决于连接它的 receiver 提供的 environment。例如：
   - `schedule(scheduler)` 的签名可能取决于 scheduler 的类型
   - `read_env(query)` 的签名取决于 environment 中 query 的结果类型

   这意味着 `get_completion_signatures(sender, env)` 需要一个额外的 `env` 参数。

   在笔记中讨论：
   - 为什么有些 sender 的签名不能独立确定？
   - 这对 concept 检查意味着什么？（提示：`my_sender_to` 检查时才能确定签名，因为此时 receiver 的 environment 已知。）
   - `dependent_completion_signatures` 的存在如何影响 sender 的可组合性？

### 进阶任务

- 实现一个更强的 `my_receiver_of`，能处理多个 value completion 签名的情况（例如 sender 可能以 `set_value(int)` 或 `set_value(string)` 完成）。
- 给你的 concept 加上更好的诊断信息：当检查失败时，用 `static_assert` 配合消息字符串来提示具体哪个 completion channel 不匹配。
- 尝试实现 `my_operation_state<O>` concept：检查类型 O 是否有 `start()` 方法。
- 用你的 concept 约束模块 D 中手写的 sender 和 receiver，观察约束后编译错误信息是否更清晰。
- 思考：如果 C++ 没有 concept，`std::execution` 的实现者会用什么替代方案？（提示：SFINAE、`enable_if`、`static_assert`。）concept 相比这些替代方案的优势是什么？

### 验收点

- 你能实现 `my_sender`、`my_receiver`、`my_receiver_of`、`my_sender_to` 四个 concept。
- 你能用 `static_assert` 对合法和非法类型组合进行编译期检查。
- 你能说明每个 concept 检查了什么，以及为什么这些检查对 sender 图的正确性很重要。
- 你能讨论 `dependent_completion_signatures` 的存在意义和设计影响。
- 你能在笔记中回答：如果没有这些 concept 约束，使用者在拼错 sender 图时会遇到什么样的编译错误？

### 观察点

- concept 让编译错误信息从"一堆模板展开失败"变成"类型 X 不满足 concept Y"。
- `my_receiver_of` 是最关键的 concept——它把 sender 的签名声明和 receiver 的能力绑定在一起。
- `my_sender_to` 是最终检查——它把 sender、receiver、signatures 三者的匹配关系一次性验证。
- 在标准库实现中，`connect(sender, receiver)` 内部会自动做这些 concept 检查。如果检查失败，编译器会告诉你"这个 receiver 不能处理这个 sender 的 completion"。
- `dependent_completion_signatures` 引入了一个复杂度层次：签名不再是 sender 的固有属性，而是 sender + environment 的联合属性。这就是为什么有些签名推导要推迟到 connect 时刻。

### 常见坑

- concept 检查写得太宽泛（只检查 `sender_concept` 是否存在），导致不合法的类型也能通过。
- concept 检查写得太严格（要求 receiver 必须接受所有可能的参数类型），导致合法的类型被拒绝。
- 忘记 `std::remove_cvref_t`：concept 检查时 R 可能是引用类型，需要去掉引用和 cv 限定符再检查成员。
- `my_receiver_of` 中对 value types 的检查写成了"检查每个 value type 都可以单独调用"，但实际上一个 `set_value_t<int, float>` 意味着需要同时传两个参数。
- 混淆 `set_value_t<int>` 和 `set_value_t<int, float>`：前者是一个参数的 value completion，后者是两个参数的。
- 在讨论 `dependent_completion_signatures` 时，误以为所有 sender 的签名都依赖 environment。实际上大多数 sender 的签名是固定的，只有少数需要查询 environment。

### 提示

- 从最简单的 `my_sender` 开始，逐步增加复杂度。
- `my_receiver_of` 可以先只处理单个 value completion 的情况，再扩展到多个。
- 测试时准备至少三种类型：完全合法的、缺少某个 channel 的、类型不匹配的。
- 如果 `static_assert` 失败时看不懂错误信息，把 concept 拆成多个小 concept，逐个 `static_assert`，找出具体哪个条件不满足。
- C++20 concept 的 `requires` 表达式可以嵌套：`requires { requires some_concept<T>; }`。
- 对于 `dependent_completion_signatures` 的讨论，不需要实现——理解它的存在理由和设计影响就够了。

### 复盘问题

- 为什么 concept 约束不是"可有可无的文档注释"，而是 sender 组合正确性的编译期保证？
- 如果没有 `my_receiver_of` 这种精细检查，sender 和 receiver 的类型不匹配会在哪里暴露出来？（提示：模板展开深处。）
- `my_sender_to` 综合了哪几层检查？每一层的意义是什么？
- `dependent_completion_signatures` 的存在意味着 sender 的"类型级合同"不总是静态固定的。这对框架设计有什么影响？
- 你觉得 concept 约束在 `std::execution` 中最大的价值是什么——是性能、安全性、还是可读性？

## 做完模块 F 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- `type_list` 是编译期的类型容器，`concat`、`transform`、`filter`、`unique` 是编译期的容器算法。sender 框架在编译期做的大量类型推导，本质上就是对这种类型容器的操作。
- `completion_signatures` 是 sender 的类型级合同——它在编译期声明"我可能以哪些方式完成"。没有它，下游组合器和 receiver 无法做类型安全检查。
- `make_completion_signatures` 是 sender adaptor 的类型级核心——每个 adaptor 都需要回答"给定上游签名，我的输出签名是什么"。`then(f)` 变换 value type，`upon_error(f)` 变换 error type，`let_value(f)` 取 f 返回的 sender 的签名。
- sender 和 receiver 的 concept 不是装饰——它们是编译期的契约检查。`my_sender` 确保类型提供签名，`my_receiver_of` 确保 receiver 能处理对应签名，`my_sender_to` 确保 sender 和 receiver 可以配对。
- `dependent_completion_signatures` 表明少数 sender 的签名需要在 connect 时刻才能确定，因为它们依赖 receiver 提供的 environment。这增加了一个复杂度层次，但也增加了表达能力。
- 整个 `std::execution` 框架是"类型驱动"的：类型在编译期流动（通过签名变换），值在运行期流动（通过 completion channel）。理解了类型级这一层，才能理解框架为什么能在编译期保证组合的正确性。
