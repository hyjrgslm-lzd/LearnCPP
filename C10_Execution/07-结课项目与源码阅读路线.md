# 07 结课项目与源码阅读路线（第一阶段）

## 这份文件怎么用

前面 12 道题是把局部能力拆开练。这份文件负责两件事：

- 把前面的局部能力重新组合成完整项目。
- 给你一条最小但有效的源码阅读路线，避免直接冲进大仓库后被实现细节淹没。

本文件包含 2 个结课项目：

1. `CPU 数据流水线项目`
2. `源码对照项目`

建议顺序是：先做项目 1，再做项目 2。这样你读官方示例和参考实现时，会更容易把“源码结构”和“自己已经做过的图”对上。

## 结课项目 1：CPU 数据流水线项目

### 项目目标

把前面模块 A 到 C 的主要能力串起来，做一个完整但不复杂的 sender-receiver 小系统。这个项目的重点不是业务真实度，而是让你同时管理：

- 多阶段 value flow
- 显式 scheduler
- error path
- environment 查询
- 结构化并发收束

### 固定题面

实现一个“批量导入并汇总记录”的小型 CPU 流水线。输入是一组原始文本记录，输出是一份汇总报告。

你至少要包含下面四类阶段：

1. `ingest`：接收原始记录集合
2. `parse`：把原始文本变成结构化记录
3. `enrich`：补充派生字段或做轻量计算
4. `merge/report`：把多条分支结果合成总报告

### 必须包含的设计约束

1. 至少使用两个 scheduler
   - 一个可以叫 `ingest_pool`
   - 一个可以叫 `compute_pool`
2. 至少有三条并列分支
3. 至少有一个 `when_all` 合流点
4. 至少有一个 `upon_error` 恢复点
5. 至少读取一次 environment
   - `get_scheduler()` 或 `get_stop_token()`
6. 至少有一组任务被某个作用域对象收束
   - 例如 `async_scope`
7. 禁止使用裸 `std::thread` 作为主实现手段

### 推荐输入模型

为了把注意力留给框架结构，建议输入模型固定得非常小：

- 每条原始记录是一行文本
- 字段数固定
- 允许一小部分非法数据
- 不涉及文件 I/O、网络 I/O 或数据库

你可以把每条记录设计成例如：

- `name,category,value`
- `sensor_id,timestamp,reading`
- `user_id,region,score`

### 推荐输出模型

最终报告至少包含：

- 总记录数
- 合法记录数
- 非法记录数
- 聚合结果一项或多项
- 错误恢复统计一项

### 必做任务

1. 先画全局 sender graph，再写代码。
2. 把至少三条原始记录处理成三条并列分支。
3. 在 `parse` 阶段允许非法输入直接抛异常。
4. 用 `upon_error` 把非法记录转换为可统计的兜底结果。
5. 在 `enrich` 或 `merge` 阶段显式切换 scheduler。
6. 至少有一次通过 environment 读取当前 scheduler 或 stop token。
7. 使用作用域对象管理一批异步工作，确保线程池销毁前图已收束。
8. 输出最终报告，并附一张对象关系图。

### 进阶任务

- 增加一个 `filter` 阶段，只保留符合条件的记录。
- 把最终报告拆成“机器可读摘要”和“展示用模型”两层。
- 加一个轻量 tracing 字段，沿 value path 传递，观察它与 environment 的区别。
- 写一份 1 页以内的小结：如果以后把这个项目接到真实 I/O，哪些抽象边界最值得保留。

### 验收点

- 你能指出所有显式调度边界。
- 你能指出 error path 与 value path 的汇合方式。
- 你能指出谁拥有 operation_state 的生命周期。
- 你没有使用共享可变大对象让多条分支并发写字段。
- 你能拿着对象图解释整个项目，而不是只展示代码运行结果。

### 项目复盘问题

- 这套图里，最关键的组合节点是哪几个？
- 哪一处最能体现 sender 图相对普通回调或裸线程写法的优势？
- 哪一处最容易在没有结构化并发时出 bug？
- 哪些信息属于业务 payload，哪些信息属于 environment？
- 如果未来增加 cancellation 或重试，图里最自然的插入点在哪里？

## 结课项目 2：源码对照项目

### 项目目标

把你已经写过和想明白的对象关系，拿去对照官方示例和参考实现，不再只看“这一段代码怎么写”，而是看“它到底在表达哪类对象关系”。

### 固定交付物

这个项目最终必须产出三份东西：

1. 一张对象关系图
2. 一份示例对照表
3. 一页读书笔记

### 必做任务

1. 依次阅读下面四个示例：
   - `hello_world.cpp`
   - `scope.cpp`
   - `hello_coro.cpp`
   - `retry.cpp`（注意：这个示例展示的是 sender adaptor 模式，即一个 sender 包装另一个 sender 并在错误时重新连接。如果你还没有做第二阶段的模块 G，阅读目标是识别结构模式——包装 sender、错误时重连——而非理解每个模板细节。做完模块 G 后建议回来重读一次。）
2. 每读一个示例，都回答同样五个问题：
   - 这个示例主要在练哪类对象？
   - sender 图长什么样？
   - receiver / environment 在哪里出现？
   - 谁拥有 operation_state 的生命周期？
   - 哪个语法点最容易遮蔽真实模型？
3. 把四个示例整理成一个对照表。
4. 再读 P3090R0 与 P3143R0，只提炼与你当前练习最直接相关的部分，不追求完整通读。
5. 写一页读书笔记，题目固定为：
   - `我现在如何向别人解释 std::execution 的骨架`

### 推荐对照表格式

| 示例 | 你看到的主要概念 | 你自己的对应练习 | 最大收获 | 最大误区 |
| --- | --- | --- | --- | --- |
| hello_world | 调度、查询、基础组合 | 模块 B / 模块 C |  |  |
| scope | 生命周期、结构化并发 | 模块 C |  |  |
| hello_coro | 协程桥接 | 模块 D |  |  |
| retry | 适配器与组合思想 | 模块 A / 模块 D |  |  |

### 进阶任务

- 再把 README 或一个论文示例中的对象关系手画一遍。
- 选一个你最喜欢的示例，重新用自己的话写 10 行以内摘要，要求不提具体 API 名，只讲对象关系。
- 如果你已经手写了最小 sender，可以尝试对照实现，看自己缺了哪些概念元信息。

### 验收点

- 你不再只是“看懂这段代码在干嘛”，而是能指出它在实现哪一层抽象。
- 你能把官方示例和自己的练习题一一映射起来。
- 你的读书笔记里出现了 sender、receiver、operation_state、scheduler、environment 五个对象，而且关系清楚。
- 你能指出至少两个你以前容易误解、现在已经改正的点。

### 项目复盘问题

- 哪个示例最能帮助你理解 `operation_state`？为什么？
- 哪个示例最能帮助你理解 environment？为什么？
- 协程示例和普通 sender 图示例最大的表达差异是什么？
- 如果以后你要审阅别人写的 sender-receiver 代码，你会优先检查什么？

## 源码阅读路线

## 第一轮：只看形状，不抠细节

阅读顺序固定如下：

1. `hello_world.cpp`
2. `scope.cpp`
3. `hello_coro.cpp`
4. `retry.cpp`

第一轮只做三件事：

- 画 sender graph
- 标出 scheduler / environment 出现的位置
- 标出生命周期拥有者

不要一开始就陷进概念检查或模板细节。

## 第二轮：只补对象关系

第二轮再做下面这些事：

- 找出哪里发生了 `connect` / `start` 的封装
- 找出 receiver 是如何隐式或显式出现的
- 找出 completion channel 在哪里被转接或消费
- 找出哪些 API 只是语法便利，哪些是真正的骨架对象

## 第三轮：对照论文，不对照语法糖

当你去看 P3090R0 和 P3143R0 时，不要试图把每个字面接口都逐条映射到你当前 commit 的 `stdexec` 实现。第三轮只做：

- 对照对象角色
- 对照调用阶段
- 对照 completion 传播思路
- 对照 environment 与 scheduler 的设计意图

## 推荐阅读问题清单

每次打开一个源码文件，都先回答：

1. 这里哪一段是在描述工作？
2. 这里哪一段是在消费工作？
3. 这里哪一个对象最像 operation_state 的拥有者？
4. 这里哪一段最容易让人误以为 sender 已经开始执行？
5. 这里如果加错误恢复，最自然的插入点在哪里？

## 学完之后下一步该练什么

如果你只完成了第一阶段（模块 A 到 D + 本文件的两个结课项目），推荐直接进入第二阶段（模块 E 到 H），那里会训练 std::execution 的实现技巧和架构设计模式。

如果你已经完成了全部两个阶段，推荐按这个顺序继续扩展：

1. **`any_sender` 类型擦除**：把不同类型的 sender 存入统一容器或通过虚接口返回。理解小缓冲优化、虚 connect、type-erased operation_state。
2. **`bulk` 执行模型**：`bulk(sender, shape, f)` 的数据并行语义。理解 shape 参数、共享值引用、scheduler/domain 如何定制 bulk 的并行策略。
3. **`timeout` 模式**：组合 `when_first`（或手动实现）与定时器 sender，在超时后走 stopped 或 error channel。
4. **`retry` + `timeout` 组合**：用已有的 retry 组合器加上 timeout，实现生产级的弹性模式。
5. **Domain 定制化**：通过 `get_domain` + `transform_sender` 让算法在不同执行域上有不同实现（如 GPU 上的 bulk）。
6. **真实 I/O 场景**：把骨架对象练透后，再去接触 io_uring、网络 I/O 等真实异步场景。

不要反过来。先把骨架对象练透，再去加场景复杂度。

## 最后一句提醒

真正理解 `std::execution`，不是你会背多少名字，而是你能不能在一段异步代码里立刻指出：

- 图在哪里
- 调度在哪里
- 生命周期在哪里
- 环境在哪里
- 完成通道在哪里

如果这五件事都能快速指出来，这套练习就已经达到目的了。
