# 01. 字节、整数编码与提交游标

先修是 [C05 字节和端序](../../C05_Data_Representation_Standard_Facilities/chapters/02-bits-and-endian.md)与整数范围，以及 C03 的 expected。练习入口为 [L01](../exercises/L01_varints/README.md)。C12 从已经会安全读取一个字段继续前进：格式为什么这样设计，它给兼容、存储和 CPU 增加了什么责任？

## 对象、格式与值域是三个不同的东西

一个 ResourceRecord 在内存里包含整数、string 和 optional；对象中的指针不是资源名称的内容，padding 也不是协议字段。持久格式必须给出字段的意义、整数宽度、字节序和长度。C05 的固定宽度大端格式提供了一个可比较的正确起点，C12 继续复用它，不把 memcpy 一个 struct 当作另一种合法序列化方案。

固定宽度使偏移和随机访问容易推导。变长整数则把较小的值写得更短，但读取需要找到终止字节，损坏和边界处理也更复杂。选型至少比较合法值域、编码长度、解码工作量和访问方式；文件小不自动意味着端到端更快。

## 从 300 推导 base-128 varint

每个字节的低 7 位保存数据，高位表示后面还有字节。300 = 44 + 2×128，所以字节是 AC 02。这里的低位组先出现，不能把它与固定宽度大端 read_be 混用。

读取第 n 个数据组时，贡献是 payload×2^(7n)。uint64 最多使用 10 个字节，第十个字节只能携带最高的那一位，并且必须结束。先检查第十个字节，再进行移位；不能等移位到 70 位以后才判断溢出。

L01 的读取接口是：

```cpp
c12::result<std::uint64_t> read(
    std::span<const std::byte> input, std::size_t& cursor);
```

成功只消费一个整数，后续字节留给上层字段解析。失败时 cursor 保持进入函数时的值。实现方式是用 probe 试读，全部验证成功后再提交 cursor。这个小提交点会在整条记录、事务和数据库服务中重复出现。

## “能算出数值”不等于“属于本格式”

80 00 也能被宽松的 base-128 算法算成 0，但不是最短编码。本练习选择只接受最短表示，因此必须拒绝它。这是 C12 数值练习的格式契约；不能据此声称真实 Protobuf 一定按同样的策略拒绝冗余编码。后面的 Protobuf 单元直接运行对应版本的官方解析器，并单独解释其行为。

需要分别检查：没有终止字节、输入在中途结束、第十字节溢出、冗余终止组，以及初始 cursor 已经越界。错误时不修改游标，才能让上层区分“尝试读取失败”与“已经消费了一部分不可恢复的数据”。

写入函数返回新的 bytes。它的 vector 分配仍可能抛 bad_alloc；这个接口没有承诺永不分配或永不抛异常。调用者在发布完整消息前先建立局部输出，不能把内部暂存区的半成品当作成功结果。

## 有符号整数为什么需要另一个映射

直接把 -1 转为 uint64 后编码，会得到需要十字节的大正整数。ZigZag 把接近零的正负数交错映射：

| 有符号值 | 无符号编码值 |
|---|---|
| 0 | 0 |
| -1 | 1 |
| 1 | 2 |
| -2 | 3 |

实现必须覆盖 INT64_MIN。对 signed 值执行左移或取绝对值容易越过可表示范围；本课先转成 uint64，在无符号域进行位操作。解码负数使用 -1-magnitude，magnitude 由右移一位得到并保证在 int64 范围内。wire.hpp 的静态断言和运行检查同时覆盖两端极值。

这解释了为什么 Protobuf 的 int64 与 sint64 不能仅凭“都表示整数”就互换：字段编号相同也不能替代编码语义兼容。

## 验证入口与成本边界

```powershell
cmake -S C12_Serialization_Databases_Storage/exercises/L01_varints -B build/c12-l01 -G "Visual Studio 18 2026" -A x64
cmake --build build/c12-l01 --config Release
ctest --test-dir build/c12-l01 -C Release --output-on-failure
```

检查器既有独立的 AC 02 黄金输入，也覆盖 0、127/128、16383/16384、2^63 和 UINT64_MAX，并逐个截断合法编码。仅让自己的 writer 与 reader 往返，可能让两个相同的错误互相掩盖，因此不能替代独立输入。

bad 实现有一个真实缺陷：接受冗余表示。bad 测试被拒绝才意味着检查器有效；它不属于学生成功计数。计时实验放在成本系列中，先统一值域和输入分布，再比较每值字节数、解码工作量及实际耗时；不从这个两字节例子推导通用性能结论。

## 自测与解析

1. **为什么不能用 cursor 本身边读边加？** 失败可能发生在最后一字节；此时上层原始边界已经丢失。使用试探游标可以一次提交或完全拒绝。
2. **第十字节为 02 能否通过截断得到正确 uint64？** 不能。截断会把超范围输入变成另一个值，破坏长度、ID 等字段的信任边界。
3. **所有小负数用 sint64 都更适合吗？** 它改善的是特定数值分布下的编码长度；既有格式不能无版本策略地换类型，还需测量实际分布和解码成本。
4. **reader 返回成功是否说明整个包合法？** 只说明从起点读取了一个符合本练习契约的整数。包内剩余字段、总长度、重复字段和业务约束由外层继续验证。
