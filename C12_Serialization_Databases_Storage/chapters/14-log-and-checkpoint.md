# 14. 批量提交、确认丢失与检查点恢复

先修：C02 的 RAII 与异常安全、C05 的有界字段读取、C07 的短写和刷盘。进入本章不要求先实现数据库页管理器。配套是 [P1 练习](../exercises/P1_log_store/README.md)，完整实现位于 [log_store.hpp](../exercises/include/c12/log_store.hpp)。

我们要保存一个有限的键值字典。一次请求可以修改多个键；调用者只有收到成功确认，才把这批修改当作持久接纳。进程可能在任意一次写入之后退出，下一次启动必须知道哪些批次可以完整重放。这里的“事务”首先是一个准确的失败契约，不是给函数起一个 commit 名字。

## 1. 从正确的内存批次开始

设字典原来是 `{old: kept}`，请求依次写 `new: value` 和一个非法空键。逐条修改原字典，最后返回错误，会把第一条修改泄漏出去。这个失败可以在单线程、没有磁盘的程序中复现。P1 的 bad 实现正是这种真实错误：检查器先保存原状态，实际调用待测 apply，再比较原状态是否仍存在。

正确基线先复制字典，在副本中依次校验和应用操作，全部成功后 swap。复制可能失败，但原字典尚未改变。相同键出现多次按请求顺序生效，删除不存在的键没有副作用；每一步都不能越过键数上限，不能用稍后的删除掩盖已经越界的中间状态。

本课限制最多 1024 个键，键 1—256 字节，值最多 4096 字节，一批 1—256 个操作。键和值是任意字节字符串，不默认 Unicode，也不执行字符串规范化。空值与删除分别用有值的空 string 和 nullopt 表示。实例中的全部操作必须由同一线程执行或由调用者外部串行化；单写者不表示无锁并发读安全。这个复制基线有 O(n) 的 staging 成本；它解决的是异常安全和原子发布，本章没有把它宣传为高吞吐数据库。

学生 Part 1 实现这一阶段。学习者先写自己的验证和发布逻辑，再打开 Reference。独立 good 使用另一种容器更新方式；两个正确实现共享输入与检查器，学生入口没有通向它们的调用。

## 2. 外部承诺改变以后，内存发布点必须后移

只在内存中 swap 不会让字典越过进程退出而存在。增加持久接纳是场景和失败契约的扩展。我们选择逻辑追加日志：每条记录保存整批操作，不直接修改持久索引页。

一次写入的顺序是：

```mermaid
flowchart LR
  A[检查输入并准备新字典] --> B[完整追加一批日志]
  B --> C[检查刷盘结果]
  C --> D[swap 发布内存状态]
  D --> E[返回持久确认]
  B --> F[写入失败: outcome_unknown]
  C --> F
  F --> G[实例停止读写并要求重新打开]
```

staging 在 I/O 前完成，避免日志已确认后才发现 map 分配失败。swap 使用本课固定的默认分配器字典，不会在成功刷盘后重新分配。发送响应发生在 write_batch 返回成功之后。

必须区分三类返回：

| 情况 | 原状态与调用者责任 |
|---|---|
| 输入或容量在 I/O 前被拒绝 | 没有追加本批日志，旧状态保持 |
| 完整写入且刷盘成功，函数返回序号 | 在声明的存储模型下必须恢复该批 |
| 已开始 I/O 后失败，或响应在途中丢失 | 结果不确定；重开后查询，不能把“没看到成功”推断成回滚 |

P1 的故障注入在 before_flush 抛出带原生错误码的 failure，检查实例是否进入不可继续使用的状态。这证明错误分支与状态转换，不能写成“本机磁盘真的发生了刷盘故障”。

## 3. 为什么不是 dump struct

对象布局包含填充、指针和实现相关表示。日志使用大端字段，复用 C05 的 read_be/append_be，并给每条记录建立独立边界。

| 字段 | 字节数与作用 |
|---|---|
| magic、version | 各 4 字节；日志与快照使用不同 magic，当前版本为 1 |
| sequence | 8 字节；日志从 1 连续递增 |
| payload_length | 4 字节；普通日志载荷最多 2 MiB |
| header_crc | 4 字节；校验前 20 字节，先验证它再相信长度 |
| payload | 操作数、操作种类、有界键和可选值 |
| payload_crc、CMIT | 各 4 字节；完整性校验与结束标记 |

操作种类只接受 put/delete，操作数量、长度和整个载荷的完整消费都需要检查。CRC-32/ISO-HDLC 的独立核对向量是 ASCII `123456789 → 0xcbf43926`；恢复驱动还用 Python zlib 验证真实文件。CRC 检测意外损坏，不提供身份认证，也不能保证检测所有错误。

头部 CRC 有具体用途：如果损坏的长度把一个完整记录伪装成“还没写完的尾巴”，不能直接截断它。先验证头部，再判断完整记录是否存在。完整头部或完整记录校验失败属于损坏，恢复报错并保留原日志。

## 4. 短写、进程崩溃与机器掉电

[文件封装](../exercises/include/c12/file.hpp)循环完成短读写，拒绝零进展，并检查每个系统调用。Windows 使用 WriteFile 和 FlushFileBuffers；Linux 路径使用 write 和 fsync，处理 EINTR。当前实际验收以 Windows 为准。

四种状态不能混用：

1. C++ 用户缓冲中存在字节。
2. write 系统调用接纳字节，数据进入系统缓存。
3. 同步请求成功，操作系统报告完成持久化责任。
4. 设备在电源故障后兑现该承诺。

关闭一个进程不会清空机器的系统缓存。所以 before_flush 之后杀进程，重启经常仍能看到完整 B；这不能证明 flush 没用。真实实验只声称验证进程终止后的状态。持久化字节模型另行构造“已刷盘的 A + B 的不同持久前缀”，把这些字节交给真实恢复程序检查。

初始文件创建、目录元数据、设备缓存和扇区行为属于存储模型前提。本章没有做真实断电实验，也没有宣称某个 Windows 重命名操作具有完整的掉电事务语义。[FlushFileBuffers 官方契约](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)与[SQLite 原子提交假设](https://www.sqlite.org/atomiccommit.html)给出了进一步核对入口。

## 5. 恢复不是忽略尾巴以后继续 append

完整有效记录依次恢复；没有收到确认的完整记录也可能成为真实历史。下一序号必须来自最后恢复出的完整批次，而不是来自客户端记得的最后一个 ACK。

在本章声明的尾部写入模型下，最终不完整记录可以被当作未完成写入。恢复先检查所有完整记录及需要恢复的状态，随后将文件截断到最后有效边界并刷盘。只有这个步骤成功，才允许继续写入。完整 CRC 坏记录或中段损坏不进入截断路径。

必做时序是：

```text
A 完整写入、刷盘、父进程收到 ACK
B 只写了一部分，父进程终止子进程
重新打开：得到 A，修复不完整 EOF 尾部
写 C，父进程收到 ACK
再次重新打开：A 与 C 都存在，B 不得部分可见
```

再把 B 改成“完整刷盘、尚未返回 ACK”。此时恢复应保留 B，C 使用下一个序号。这两种情况共同阻止“只按客户端确认号决定下一序号”的错误。

对任意介质破坏，有限校验不能总是区分崩溃尾写和被截断的既有数据。课程把可容忍前缀模型与损坏检测用例分开；不声称恢复算法能自动修复所有物理损坏。父驱动的已确认集合仍是检查是否发生数据丢失的独立依据。

## 6. 检查点保存什么，为什么需要两个槽

一直重放日志可以正确恢复，但随着历史增多，重建当前字典需要应用越来越多的旧操作。检查点保存一个已提交状态和它对应的日志序号。逻辑日志方案与 SQLite 的页式 WAL 是不同机制，后续生产源码导读会解释页面版本、读者终点与 WAL 回收。

P1 使用两个轮换快照文件，每个包含完整校验、applied sequence、当前字典以及对应日志前缀的 CRC。后者避免把另一段历史的快照直接配到当前日志；它仍是意外错误检测，不是防恶意篡改的 MAC。

写入非当前槽，完整写入并刷盘后才在内存中切换槽位。若新槽半写，旧槽仍存在；若新槽完整但确认未返回，恢复可选择它。恢复选择序号有效且历史匹配的最新完整快照，再重放之后的批次；两个槽都坏时，保留的完整日志仍可重建字典。

实现继续扫描和校验完整日志，快照主要减少字典操作，不保证减少磁盘读取量。文件总量上限是 64 MiB 日志加两个有界快照。到达日志上限明确拒绝写入；不在本课教学实现中偷偷截掉已确认历史。SQLite 系列实际验证检查点、长读者阻碍回收和安全备份。

### 先定位完整重放，再启用快照恢复

[replay_cost.cpp](../exercises/P1_log_store/replay_cost.cpp)保留两个可执行分支：full_replay 验证快照但仍从日志起点构建字典，checkpoint 使用选中的快照再应用后续批次。相同工作负载写 256 批、每批更新 16 个键，在第 240 批建立检查点；两个分支都用独立的最终键值预期检查恢复结果。

先运行 full_replay，观察 scanned_bytes、decoded_batches、applied_batches；再运行 checkpoint。这个固定负载的判定条件是：扫描字节数相同，实际应用批数从 256 变为 16，解码次数还包含日志检查阶段。计数把变化定位到状态重建工作，不能据此声称磁盘 I/O 减少，也不能把 256/16 当成耗时加速比。

```powershell
ctest --test-dir build/c12-p1 -C Release -V -R "C12_P1_(replay_cost|checkpoint_cost)$"
```

输出中的单次 recovery_seconds 是诊断观测；正式性能结论仍需要后续成本章节的一次预热、五次独立进程采样、同口径核对和离散情况。这里先根据实际执行计数检验改进假设，保留 full_replay 作为可复验基线。

### 分配失败不能被讲成文件损坏

[boundaries.cpp](../exercises/P1_log_store/boundaries.cpp)只在它自己的进程中替换普通 operator new，按预算触发一次 bad_alloc；随后关闭注入，再核对真实 API 的返回和原数据。它覆盖准备批次及恢复路径，并区分 allocation、capacity、corrupt。

这也检查对象移动的异常规格。不能仅因为文件句柄移动不抛异常，就把包含 map 的整个存储对象移动声明为 noexcept；某些标准库实现会为 map 的哨兵分配内存。让默认移动从所有成员推导异常规格，才能把分配失败返回为资源错误，而不是终止进程。该测试没有修改系统分配器或其他进程。

cmake --build build/c12-p1 --config Release

P1_apply_reference/good 验证实际批处理实现；P1_apply_bad 的成功表示检查器拒绝了指定错误，不能计作学生解答通过。P1_store 验证文件实现，P1_recovery 的父驱动持有测试目录，启动并回收自己的子进程。父驱动外还有课程监督器超时，内部等待故障点不能代替进程外保护。

用 ctest -V -R C12_P1_recovery 显示逐案例 JSON：command 记录实际 ACK 和查询结果，fault_ready 记录父进程观测到的故障点；inspect 输出 LSN、SNAP、REPAIRED 和 BAD（拒绝的快照数）。驱动对这些字段有明确断言，half_snapshot 应回退到序号 1，snapshot_flushed 应选择序号 2，损坏的唯一快照应被拒绝并全量重放。程序会清理自有临时库，但逐例观测由外部监督器保留。

逐项记录：执行命令、平台、实际 ACK、故障点、退出状态、恢复序号与键值、是否发生清理失败。运行产物留在忽略的 build；这里给出的状态表是判断规则，不是需要复制到答案里的预填结果。测试通过也不能替代下面的推理题。

## 8. 自测与完整解析

**问题一：为什么不能在写完日志后立刻 swap，再检查 flush？** 如果 flush 失败，内存已经发布新状态，读者可能把未确认的数据当成已提交。正确顺序在失败时冻结实例，重开判断实际日志；不能仅把错误码返回上层而继续使用旧索引。

**问题二：两个键的字节都出现了，是否已经形成事务？** 不一定。恢复必须验证整批的头、长度、载荷和结束标记，解码并校验全部操作，再发布整个结果。仅查到某个键的字符串不能证明批次完整。

**问题三：为什么没有 ACK 的 B 不能一律删除？** ACK 是外部观察，持久化可以先完成而响应随后丢失。删除 B 可能破坏后续已经依赖 B 的历史。业务层应通过稳定的幂等键查询和消除重试歧义，P2 会完成这个闭环。

**问题四：快照槽写失败是否必须把数据库全判坏？** 在本设计中，提交历史仍保存在独立日志；坏槽可以被拒绝，并使用旧槽或完整重放。日志自身完整记录损坏则不同，不能因为“有一个快照”就默默跳过它。

**问题五：这是否实现了 MVCC、完整 WAL 或高并发数据库？** 没有。本实现是单写者、逻辑批日志和内存索引；它提供被检查的原子性与恢复契约。SQLite 系列继续教授生产页式 WAL、并发读者、检查点与回收。读者应能准确说出两种机制各自的状态，而不是只记住“写日志就安全”。
