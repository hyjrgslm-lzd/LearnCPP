# 06. 多条语句如何成为一个业务动作

先读客户端生命周期，再进入 [L05](../exercises/L05_transactions/README.md)。本章用两个库存计数演示事务，不涉及真实支付系统。输入是源 ID、目标 ID 和移动单位数；业务要求两个计数都在 0—1000 内，总量保持，失败时不能留下半次更新。

## 从一个确实会泄漏状态的错误开始

如果先减源库存，再发现目标不存在，第一条 UPDATE 可能已经自动提交。程序返回“失败”，数据库却从 (10,20) 变成 (7,20)。这不是线程调度问题，单线程顺序执行两条语句就能复现。L05 bad 省去了事务，检查器先提交这个反例，再查询两个实际行，确认错误实现被拒绝。

只比较总行数毫无帮助；即使只比较总库存，也可能错过两个方向互相补偿的错误。检查器保存每个行的独立预期，并检查事务是否真正结束。

## 事务的四个维度

原子性关心操作是否整体可见；一致性依赖定义好的约束和业务不变量；隔离性约束并发事务能观察到什么；持久性关心确认后的结果在故障模型中是否保留。一次成功测试不能把这四个问题合并成“数据库保证正确”。

L05 先明确单个事务的原子更新，隔离交错在下一章展开，WAL 和同步保证则进入恢复系列。SQL CHECK 约束保护存储值域，应用还要拒绝源与目标相同、非正数量、缺失行等请求。

## 先取得写事务，再读改写

Reference 用 BEGIN IMMEDIATE 取得 SQLite 的写事务，然后执行有条件更新：

```sql
UPDATE accounts SET units=units-?1
WHERE id=?2 AND units>=?1;
```

只有实际修改一行才继续更新目标，目标更新也带容量条件。任一步失败，事务守卫回滚；两步成功才 COMMIT。独立 good 先在同一写事务里读取两行，检查条件后分别更新。两者选择不同的实现表达，但都把“读取/验证/修改/提交”放进同一事务。

不要把 read-modify-write 的读取移到事务外，再以为两个 UPDATE 被包住就足够。另一个事务可能在读取和修改之间改变值；下一章的快照与冲突实验会明确合法结果。

## 数据库自己的失败也要进入回滚路径

L05 使用真实触发器，在目标值变成 13 时执行 RAISE(ABORT)。源行已经更新，第二条语句由数据库拒绝。程序必须保留 SQLITE_CONSTRAINT_TRIGGER，让守卫回滚整个业务事务，最后两个实际行仍等于失败前状态。

异常处理不能在事务内部吞掉错误后继续 commit。一个“catch 后打印错误”的分支，也可能把已完成的部分语句提交出去。原生错误、应用拒绝和提交结果不确定应该分别解释；资源回收失败还会冻结共享连接，具体实验见上一章。

## 为什么保存点不等于嵌套 BEGIN

SQLite 不允许用 BEGIN 套 BEGIN 来获得独立嵌套事务。SAVEPOINT 建立事务内的回退位置，ROLLBACK TO 回退该位置之后的修改，但不会结束整个外层事务，也不会自动移除保存点；RELEASE 处理保存点层级。

因此，局部可选步骤失败后可以回到保存点，外层已接受的其他工作仍在同一事务里。能否继续是业务契约，不能把所有错误都默认降格为“可选步骤失败”。如果连接已经处于资源失败或不可判断状态，应停止使用。

## Schema 迁移也是数据操作

添加一个列并不是迁移完成。需要回答：旧行如何解释，新字段缺失代表什么，旧读者和旧写者是否还能工作，失败发生在 DDL 和版本登记之间怎么办？

应用可以用自己的版本表或 SQLite user_version 登记 schema 版本。它与 SQLite 内部的 schema_version cookie 不同，不能随意改内部 cookie。每次迁移在明确事务内完成 DDL、回填和应用版本更新；只在提交成功后报告新版本，重复执行已完成版本应有明确定义，未知未来版本应拒绝。

添加可为空的 note 列通常能允许旧写者继续指定旧列列表；使用 INSERT INTO table VALUES(...) 或依赖 SELECT * 列顺序的客户端则可能不兼容。兼容是实际表达式与字段含义的性质，不能只看 ALTER TABLE 成功。

迁移前的备份必须是可恢复备份。运行失败留下的文件、尚未完成的 online backup 或遗漏 WAL 的主文件副本，都不能作为“已经有备份”的证据。

## 自测与解析

1. **为什么 Reference 要检查 sqlite3_changes？** UPDATE 找不到行也可能正常返回 DONE；语句执行成功不代表业务条件满足。
2. **只有 CHECK(units>=0) 是否足以保证库存移动？** 它不能保证目标存在、总量守恒或两个更新一起生效。
3. **重试 COMMIT 能否修复读取旧值的问题？** 不能。发生快照或序列化冲突后，必须按该数据库契约重新读取和执行整个事务。
4. **为什么迁移版本不能先写成 2，再慢慢改表？** 崩溃后读者会按 v2 解释仍是 v1 的结构；版本更新必须和实际迁移处于同一个提交边界。
