# 23：新解释器模型与反射桥接

“支持多解释器”“支持关闭 GIL”“使用 Stable ABI”是三种不同承诺。将它们混成一个开关，会在恰好不触发问题的环境里得到过于乐观的结论。先沿 F01 的实际入口建立各自可证明的边界，再看原生扩展需要承担什么。

## 隔离的解释器不等于隔离的 C++ 全局

F01 创建两个真实子解释器，各自在自己的全局命名空间保存 marker。第二个解释器看不到第一个的值，这是可运行观察。若扩展模块把某个 `PyObject*` 放进进程级 static，两个解释器仍可能通过同一C++地址共享它；Python globals 隔离不能替扩展修复这个问题。

从对象来源开始修复：状态应该属于具体模块/解释器实例，跨解释器传递的是明确支持的值或显式消息，而不是把借用的 `PyObject*` 换个线程继续使用。多阶段初始化为模块实例建立状态的机会，不会自动使已有静态缓存正确。

命名空间实验使用固定 CPython3.10/3.12 的私有 `_xxsubinterpreters` 入口，目的在于观察模型。生产 embedding 的线程状态和解释器配置要按相应版本 C API 处理；不能把旧 `PyGILState_*` 的主解释器假设直接套到所有解释器。

## 关闭 GIL 后，借用的前提发生变化

在传统GIL模型中，一段不释放GIL的代码可能依赖其他Python线程不能同时修改容器。free-threaded构建改变了这个前提。容器内部锁不等于任意“取出借用引用再使用”的多步协议都安全；对象可能在两步之间被另一个线程移除。

官方 [CPython3.13 free-threaded 扩展指引](https://docs.python.org/3.13/howto/free-threading-extensions.html)区分构建宏、模块支持声明、对象访问及线程状态责任。F01原生主体故意只接收 exact immutable bytes，并在函数返回前保持参数引用、独占构造输出。这个简化消除了当前转换任务不需要的可变共享输入，而不是声称一般容器绑定已安全。

`Py_mod_gil` 支持声明必须与实现匹配。若导入扩展导致GIL重新启用，测试直接失败；若当前不是匹配的free-threaded构建，能力探针跳过，而不是编译一份常规扩展充数。此主体使用CPython3.13 Full C API，不把它与L09的常规Stable ABI二进制混用。

## 线程状态仍然存在

没有GIL不意味着可以从任意原生线程拿裸指针调用Python。运行时仍需要正确线程状态，解释器和对象仍须存活；可能阻塞的操作仍要遵守该版本运行时对线程状态切换的要求。F01由Python创建线程并调用扩展，因此每次调用已经处在相应运行时上下文；它不冒充“外部线程附着”的完整实验。

四个线程在屏障处同时开始，分别执行真实原生转换，并验证结果。这个有限实验不能证明所有并发历史；正确性同时来自无可变全局业务状态、immutable输入及未发布输出的独占性。以后若增加共享缓存，必须重新设计同步与检查，不能继承当前支持声明。

## Clang AST 与语言反射各提供什么

C04讨论语言内部的编译期元信息及生成能力；C18的Clang工具从真实编译命令解析既有C/C++源码，还需要源位置、宏与模板上下文。若目标是迁移源文件，只有生成某种元数据还不够；若目标是编译期类型组合，也不应为了读取几个字段先搭一个源文件重写系统。

二者相遇于同一验收原则：生成物必须由真实消费者编译/使用。一个漂亮的导出清单不能证明函数签名可调用；一段生成的binding也不能替代owner、异常及线程边界。标准反射状态沿[C04](../../C04_Generic_CompileTime_Reflection/README.md)固定版本核对，不在本课重新发明一套相似命名的宏系统。

## 自测与解析

1. **子解释器marker隔离为何仍不足以批准扩展？** C/C++ static状态不一定属于解释器；必须检查所有对象来源与销毁路径。
2. **声明不需要GIL后能共享可变输入吗？** 声明不是同步机制。当前主体主动拒绝mutable buffer；更广输入需要新的协议、实现和受控验证。
3. **为何free-threaded扩展有独立构建入口？** 它依赖不同解释器ABI和支持声明；常规Python3.10扩展通过不能替代它。
4. **生成代码后，哪些检查仍然必要？** 编译、链接、运行时契约、失败清理和实际所有权；代码来源于工具不使这些责任消失。
