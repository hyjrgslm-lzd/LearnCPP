# 02：运行时版本协商与结构前缀

部署场景与 L01 不同：host 已经编译完成，磁盘上的插件可能被换成另一版。重新编译调用方不再是可用的自动修复，因此兼容信息必须能在第一次业务调用之前读到。

## 从单函数到函数表

正确的最小插件有一个约定好的入口 `c18_get_api`。入口先检查请求的版本及调用方提供的表大小，然后填写一张只包含 C 兼容字段和函数指针的表。调用方复制表的已知部分，不长期借用插件内部的表对象；函数指针仍依赖模块存活。

```text
找到协商入口
  → 版本与表大小都满足
  → 得到 create/process/request_stop/destroy
  → 检查必需函数非空
  → 创建状态
  → 业务调用
```

真实声明以 `exercises/include/c18/abi.h` 为准。不能在不同包装器里各自手抄一份大小、字段顺序或调用约定；Python `ctypes.Structure` 必须逐字段对照它，Clang 工具也读取这同一份头。

## 先观察错配，再决定兼容规则

第一种受控输入是“不支持的版本”。预期是协商失败，尚未创建业务状态，不发生转换。第二种是“表缓冲太小”。预期是拒绝而不是把新字段写到调用方对象之外。第三种是“表声明成功但必需函数为空”。host 在调用前拒绝它，而不是跳到空地址。

这些问题都是边界信息不足，不需要真的执行损坏调用来证明。用真实共享库夹具返回错误版本或缺失函数，观察 host 是否在业务调用之前停止；用哨兵验证协商失败不越界写入。仅把常量改成 `unsupported` 再说“兼容验证成功”，没有检查调用顺序和写入范围。

本课 V1 只保证约定的 V1 表；未知版本拒绝。正文中的“结构前缀”是解释演进方式，不表示 V1 自动接受任意未来字段。要发布 V2，先决定新增字段是否可选、旧字段语义是否保持，再给出旧 host/新 plugin 和新 host/旧 plugin 的独立检查。没有对应实现和检查时，不宣称向前兼容。

## 大小不能替代语义

两个结构体可能同样大，但字段顺序不同；两个函数指针也可能同样大，但参数完全不同。`struct_size` 只能避免一类访问超出可用前缀的问题。`abi_version` 表达双方同意的语义版本，二者不能互相替代。

不要为了看起来紧凑就对公共表随意 `pack(1)`。这会改变成员偏移和对齐，还可能制造非自然对齐访问。用 C11 与 C++ 消费者编译实际头，记录目标位宽，检查必要的字段偏移；不是把编译器内部对象表示当成跨机器网络格式。

对于可失败的转换，ABI 中使用明确数值状态码；C++ 内部可以转换成 enum 或 `std::expected`。固定宽度的整数让数值范围明确，但结构布局仍属于目标 ABI。若在不同进程、不同机器传输这些信息，应回到 C05/C11 的序列化协议，而不是把函数指针和结构体内存直接发出去。

## 初始化的提交点

创建插件状态之前先完成版本检查。创建失败时，输出 handle 保持空，调用方没有需要释放的半成品；创建成功才交付一个必须配对销毁的对象。实现中可先在局部 RAII 对象中准备状态，再在最后转移给 opaque handle。这是 C03 的“失败不提交”在 ABI 边界的应用。

调用方不能对 opaque handle 使用 `delete`，也不能推断它是某个 public class 的地址。只有创建它的模块知道表示与销毁方法。若 create 后又发生 host 初始化失败，host 必须在模块仍加载时调用匹配的 destroy，再释放模块句柄。

## 练习预测与完整解析

1. **同一个 DLL 文件名是否保证 ABI 相同？** 不保证。文件名是发现入口，版本协商才表达协议。测试用相同加载流程面对不同夹具，不能只凭名称判断。
2. **只增加结构尾字段是否天然兼容？** 不是。还要保证旧字段布局/语义不变、双方按大小访问、可选能力有明确默认。当前 V1 未实现的协商分支保持未验证。
3. **为什么先检查函数表，再 create？** 这样拒绝阶段还没有业务资源；如果 destroy 指针不存在但已经创建对象，host 无法安全完成回滚。
4. **结构大小合适却缺函数，能跳过该功能继续吗？** 只有协议明确把它列为可选能力才行。V1 的必需操作不能静默变成空操作。
