# 22：成本来自哪一层

一个绑定调用通常至少包含参数检查、对象/字节转换、原生分派、业务处理、返回值构造和引用清理。优化业务循环并不一定能改善小记录吞吐，因为前后两端的固定工作可能占据较大比例；但这仍是待验证假设，不能凭接口看起来复杂就认定它是瓶颈。

## 先把问题缩到可归因范围

[B01](../exercises/B01_boundary_cost/README.md) 首先保留一个正确的逐记录基线。输入含 NUL 和高位字节，转换结果与独立期望逐字节一致。驱动报告调用次数、完成字节数和稳态计时。将每轮总输入固定为65536字节，记录分别为16、1024、65536字节时，每轮调用分别为4096、64、1次。

这些计数直接定位了重复分派/检查/循环的次数，不直接测量其中单个指令的耗时。若时间也随粒度变化，就获得了关于这组固定成本的实测问题；若时间没有稳定变化，则应保留无收益或干扰结论。不要把记录变长后产生的编译器向量化收益错误命名为“少了一次 C ABI 调用”。

## 提出一个受控替换，而不是先采用优化

接下来让 `batch` 对同一完整输入调用一次相同函数。ASCII转换没有跨记录状态，且本实验不注册 callback，因此合并边界保持数据结果相同。一个真实插件若每条记录触发回调、更新事务状态或承担延迟约束，就不再拥有这个简化条件，必须重新建立协议和基线。

`copy_batch` 则单独增加一次显式复制，缓冲分配仍放在计时外。若把分配也移入循环，就是另一项实验，不能仍声称只改变复制成本。复制可能使后续数据进入缓存；“多复制一次”不必然等于按内存带宽算出的净增加时间，因此依然看同口径结果和离散程度。

## 代码如何避免自证

计时和正确性检查调用同一份转换内核。程序在计时后独立比较完整输出，在计时内只检查必要状态和长度。函数指针为显式间接分派入口；这不等于保证某一种机器指令，若要对反汇编作结论，应保存实际编译选项并查看目标代码。

```text
进程创建 → 固定输入/输出/预期 → 开始单调时钟
    → iterations × 完整工作量 → 停止时钟
    → 完整结果检查 → 输出结构化样本 → 进程退出
```

五个样本来自五个独立进程，每次重建状态。一个进程打印五行只能得到同一进程的五段观察，不能冒充独立采样。runner 保存预热和所有失败，不静默剔除异常值；测量期间被绑定的源码和二进制发生变化，整组标记失败。

## 回到真实 FFI 时怎样继续

先运行 P1 的某个真实后端，确认确实经过该运行时。然后测量：传入已经拥有的 bytes 与构造新的 bytes；一次处理完整连续 buffer 与多次小调用；Python持GIL与合法释放GIL的长原生计算；Lua每次建state与复用同一state。每组都要固定相同输入、所有权和关闭责任。

这些方向是后续实验规格，不是 B01 已取得的结果。本次没有 pybind11/Lua 开发库时，不能用 native 结果填上它们的测量栏，也不能从“未测”推断它们更慢。生命周期正确性先于计时，带有悬空借用或错误清理的版本不能成为有效性能基线。

## 自测与解析

1. **batch 快于 per_record 是否证明 C ABI 很慢？** 不证明。本实验是本地原生函数分派，差异还包括检查、循环及编译优化；没有测得任意语言/动态库边界的通用成本。
2. **copy_batch 偶尔更快应删除吗？** 不应。保留样本、观察范围和桌面干扰；若要归因为缓存预热，须再用可重复对照/profile支持。
3. **可以只报告中位数吗？** 中位数有用，但必须同时保存样本及范围，否则读者无法知道结果是否稳定，或者是否挑选了有利场景。
4. **何时可以把批量策略用于主项目？** 当实际协议允许合并、问题已复现并定位、同口径复验支持收益且等待/取消/回调代价已解释之后。
