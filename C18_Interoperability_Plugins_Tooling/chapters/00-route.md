# 00：从一段字节到两个运行时

本课面向能写普通 C++ 程序、已经理解 RAII 和基本线程同步的工程师。你不需要先学完 UE、Qt、协程或编译器理论。需要的是：遇到一条指针时能回答它指向什么、谁负责存活、哪次操作结束后不能再使用；遇到失败时能回答哪些状态已经改变。

主案例只有一个业务操作：按显式长度读取一条二进制记录，将 ASCII 小写字母转成大写，其他字节不变。`61 00 7a ff` 应变成 `41 00 5a ff`。这不是自然语言大小写转换，UTF-8 高位字节原样保留；Unicode 语义由 C05 主讲。本课把业务计算保持简单，以便把错误归因到边界而不是算法。

最初，调用方和实现一起链接。随后，实现成为动态插件；Python 或 Lua 包装它；最后，Clang 工具检查接口、迁移受控调用点并生成契约检查代码。每次增加一层都多出一种失败：符号不存在、ABI 不匹配、对象已经死亡、异常无法跨越、回调到达关闭中的运行时、编辑位置不是你看到的位置。课程必须让这些失败可观察，并给出足以解释结果的机制。

## 用三个对象看清整条链

把一次调用画成 `调用方缓冲 → 包装器 → 插件状态 → 函数返回`。缓冲所有者、插件状态所有者、代码所在模块所有者可能是三个不同对象。函数指针没有自动持有动态库；`PyObject*` 不自动代表拥有引用；`lua_State*` 也不代表可以从任意线程调用。

先问正常调用时谁活着，再问失败和关闭如何改变这张图。不要从“用了智能指针”推导安全：如果智能指针的析构函数自己位于已卸载的 DLL，释放对象同样会跳入不存在的代码。解决办法不是再包一层类型，而是使对象的最后一次释放发生在代码所属模块仍被持有的时候。

## 学习动作与检查的含义

每道实现题只编辑 Student。先预测空输入、NUL、容量不足和关闭中的结果，再执行检查。Reference 是独立答案；good 是检查器的独立正确控制，bad 证明检查器能拒绝一种具体错误。运行通过不代表书面解释已经完成，也不代表未运行的后端获得验证。

观察题可以预先提供完整程序：任务是预测、执行、定位和解释。真正的实现题则必须调用学生自己的逻辑。未完成 Student 返回明确失败，不用 SKIP，也不把参考实现藏在包装器中。

本机可能没有 Lua、pybind11 或 LibTooling 开发文件。阅读、代码和检查规格仍然完整；未构建运行的主体保持未验证。`clang -ast-dump` 是理解语法树的真实入口，但不是自己编写的 LibTooling 工具已经通过验证。

## 出口自测与解析

1. **为何业务选择二进制 ASCII 转换？** 它允许独立给定精确答案，同时暴露 NUL 截断、字符有符号性、长度和复制成本；没有把编码库或数值算法的错误混进 FFI 实验。
2. **为何一门课程保留多个错误模型？** status、Python error indicator、Lua protected call 的控制流不同。统一成一个名称会隐藏必须学习的清理责任；只在各自边界完成转换。
3. **哪条路线必须等待其他路线？** P1 的某个脚本后端必须等待该语言的生命周期与错误练习；P2 只等待 ABI 头与 Clang 基础。没有要求 Python 等待 Lua，也没有要求整课等待前沿解释器。
