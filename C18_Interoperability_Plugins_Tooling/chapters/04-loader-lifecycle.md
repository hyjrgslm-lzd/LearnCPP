# 04：加载不是获得永久可调用的代码

C07 已介绍系统装载原语。本章承接它们，解决插件的一组连续责任：确定目标文件、持有模块、查找入口、协商协议、创建状态、在失败时按相反顺序回滚。线程和回调收束在下一章增加，不能在这里暗中假定并发关闭已经安全。

## 串行正确基线

串行 host 在一次作用域中加载插件、完成所有调用、销毁所有插件对象，再释放模块句柄。这种方案简单且正确；问题不是它“太原始”，而是扩展为跨线程或跨语言长期对象后，原来隐含在一个作用域中的顺序不再成立。

```text
module owner
  └─ function table
      └─ plugin state
          └─ one synchronous process call
```

先验证这条基线：输入包括空记录和二进制记录，结果完整；关闭后不再使用表中的函数指针。创建失败时不调用业务函数；如果模块已经加载却找不到入口，仍须释放本次持有的句柄。每个阶段有独立失败状态，而不是统一打印“插件打不开”。

## 从哪里加载

课程 host 要求显式绝对路径。Windows 使用受限的 `LoadLibraryExW` 搜索标志，Linux 使用 `dlopen` 的 `RTLD_NOW | RTLD_LOCAL`。这使当前目录不再是选择顶层插件文件的隐含输入；依赖库如何解析仍取决于平台与加载策略，不能把绝对顶层路径说成完整的信任验证。

最小负例有两个：同一插件用相对路径传入应被课程 host 拒绝；一个不存在的绝对路径应产生加载错误。这只验证课程的路径政策，不证明目标插件可信。进程内加载的原生代码拥有进程权限；本课自动实验只使用自己构建的夹具。

## 查到地址之后还缺什么

Windows 的 `GetProcAddress` 和 Linux 的 `dlsym` 得到符号地址。Linux 使用 `dlerror()` 区分查找错误，不能只看返回指针是否为空。协商入口的函数类型来自公共头；用任意 cast 去“适配”另一个签名不是 ABI 适配器。

找到入口后仍需检查 ABI 版本、表大小及必需函数。然后 create；只有成功创建的状态才进入业务阶段。把这些检查放到第一次 process 中会让失败发生得更晚，也增加清理分支；它并不会让错误更容易恢复。

## 回滚按已经获得的资源逐层进行

如果 load 失败，尚无模块句柄；如果 symbol 或协商失败，只有模块 owner；如果 create 失败，协议应保持输出状态为空；如果后续 host 准备失败，先 destroy 已创建状态，再放弃模块 owner。RAII 可以表达这个顺序，但仍需明确是哪一个 owner 先销毁。

不要在动态库初始化回调里启动整套插件业务，再期待 host 一定能安全回滚。把可失败的工作放进显式 create，让调用方看到状态及错误。初始化/退出钩子的限制由平台规定，不是一般 C++ 构造函数的运行环境。

## handle release 和物理卸载不同

成功执行 `FreeLibrary` 或 `dlclose` 表示释放了本次句柄/引用；别的组件可能仍持有引用，平台也可能因运行时条件保留映射。Linux 的相关语义见 [dlopen/dlclose 手册](https://man7.org/linux/man-pages/man3/dlopen.3.html)。因此检查器不能一边保留 observer handle 读取计数，一边声称“模块已全局卸载”。

本课证明的是：业务资源按协议先结束，host 不再使用函数表，然后释放自己持有的句柄。即使模块仍映射，也不能把“暂时还调用得动”当作继续使用已释放函数指针的授权。

## 新场景为何需要下一章

当 Python 对象持有插件状态，或者 worker 正在执行会触发 callback 的 process 时，C++ 管理对象的作用域结束不等于这些使用都结束。不能只给 loader 的析构函数加一把锁：若 callback 在持锁期间回到关闭函数，可能等待自己。

下一章先记录一个明确交错，再从准入、在途操作、回调与借用的责任推导关闭协议。它是场景扩展，需要新的状态和检查；不是证明串行基线有错，也不是预设复杂方案更快。

## 自测与解析

- **库存在却加载失败，先检查什么？** 保留原生错误，再区分架构/依赖解析/权限等可能原因；文件存在仅证明路径可见，不能直接归因为符号错误。
- **为什么协商前不能保存一个长期业务对象？** 还不知道匹配的创建、销毁和版本语义。先获得完整协议再获得业务资源，失败分支更少。
- **为什么不在加载器返回裸函数指针？** 它容易逃出模块 owner 的作用域。若必须返回可调用对象，应同时持有明确模块 lease，并把关闭策略写进对象协议。
