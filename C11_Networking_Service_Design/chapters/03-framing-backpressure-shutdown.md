# 从一段字节到可关闭的连接

先修：[C05 的数据表达](../../C05_Data_Representation_Standard_Facilities/README.md)、[C07 的同步与非阻塞 I/O](../../C07_OS_Memory_System_IO/README.md)。读者应能区分字节长度与字符数、拥有对象与借用视图，以及一次系统调用与完整操作。本章不要求会写协程。

我们要写一个会回送完整消息的连接。它接受有限长度的字节消息，在对方停止发送后仍送完已接受的响应；慢读者不能把应用内存无限撑大。正文里的模型可以逐步推进，真实 socket 驱动验证它与操作系统的接线。对应 [L01 分帧](../exercises/L01_framing/README.md)和 [L02 连接](../exercises/L02_connections/README.md)。

## 1. 正确的最小基线是什么

TCP 给应用的是有序字节流。应用写两次，并不建立接收方两次读取的边界；接收缓冲中的可用量和调用方的空间都会影响一次读取长度。发送成功也不意味着远端应用已处理内容。这是 [TCP 规范](https://www.rfc-editor.org/rfc/rfc9293.html)和 [Winsock send/recv 接口](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-recv)给出的责任边界。

本章帧格式为 `8 个 ASCII 十进制数字 + body`，长度只计算 body 的字节数，最大 4096。body 可以含零字节；空 body 是合法的传输帧，是否为合法 RPC 请求由上层解析决定。沿用这一格式便于与 C09 的 RPC 做真实互操作，但这里不借用 C09 的运行时。

单请求基线可以顺序完成以下操作：循环读满八字节头 → 严格解析并检查长度 → 循环读满 body → 回送整帧 → 处理下一帧。它没有宣称一次 `recv` 读满；每轮只保留一个有界消息，所以在单连接同步场景中确实正确。[baseline.cpp](../exercises/L02_connections/baseline.cpp) 是完整可运行的一次请求/响应实例。`socket.hpp` 中的 `receive_exact`/`send_all` 实现“循环直至完成或失败”的公共操作，所有重试共享同一个单调时钟截止时间。

对端在帧边界关闭发送方向意味着没有更多请求；在头或 body 中间结束则意味着截断。把两种情况都当作“正常结束”会将破损输入伪装成成功。系统错误、协议错误和业务错误应保留各自含义。

## 2. 先构造能检验错误假设的输入

消息 `hello` 编码为 `00000005hello`。假设第一次读取只有 `000`：这既不是完整头，也不是完整请求。再令第二次读取包括剩余头、body 和下一帧的开头，就同时击穿了“一个 read 一条消息”和“只保留本轮完整消息”两种方案。

实验不依赖两次 `send` 在 TCP 上碰巧拆成两次 `recv`。L01 将同一 wire 按 1、2、7、8、13、4096 字节切片后直接喂给被检验解码器；输出应完全相同。L02 的安全模型直接给出残头；真实回环测试另行运行 socket。前者证明解析对分片的处理，后者证明本机传输与驱动接线，不互相冒充。

这里不是“同步方案错误，所以必须异步”。顺序读满的基线仍正确；进入多连接后，一个未完成头就可能占用整个执行线程，才需要将这个等待位置显式表示为状态。

## 3. 把局部变量变成增量状态

解析器需要保留：已读头位数 `digits`、累积长度 `length`、body 和不可恢复错误。对每个十进制位 `d` 更新 `length = 10 * length + d`。先检查 `d` 的范围，再检查累积长度上限；未验证长度不参与大块分配。

本格式最多八位，即使先读全头也不会超过 99,999,999；Reference 还会在前缀已经超限时提前拒绝。good 实现选择收齐头后 `from_chars`，两者都满足“读 body 前拒绝超限”。接口没有要求两者在同一字节报告失败。

```cpp
auto step = decoder.push(byte);
if (!step) { /* 按协议错误关闭当前连接 */ }
else if (*step) { /* 一帧完成，移动拥有的 string 给上层 */ }
else { /* 输入已消费，仍需后续字节 */ }
```

`push` 每次消费一个字节，因此消费量固定为一。外层可以按任意切片调用它，不需要把视图保存到下一次 I/O。完成时移动出拥有的字符串并重置下一帧状态；如果返回的是内部 `string_view`，下一帧写入或容器扩容会使旧结果失效。

`finish()` 只检查当前状态：空状态成功，残帧为 `truncated`，之前的解析错误继续失败。错误是 sticky 的：课程协议没有重新同步标记，不能随意跳过一个坏字节后继续解释。若应用需要恢复，它必须定义可验证的同步规则。

每个字节只经过常数次检查，累计工作量 O(n)。保留一个 body 最多 4096 字节，加八字节头状态；实际 `std::string` 容量和分配器元数据不是“精确 4104 字节 RSS”。完整实现见 [frame.hpp](../exercises/include/c11/frame.hpp)。

## 4. 发送完成量与消息拥有量不同

非阻塞 socket 可能只接受 `abcdef` 的前两个字节。正确后续输入为 `cdef`；重发整条会产生重复，直接弹出队首会丢失后缀。

因此队列保存拥有消息和队首偏移。`enqueue(string_view)` 只在调用期间借用输入，并复制到队列自有的精确长度字节数组；`front()` 借出未发送部分。完成 n 字节后只前移偏移，只有整条消息完成才释放它。多个发送者不能分别拿着同一 socket 随意写帧，否则字节会交错；一条连接使用一个串行 writer。

内存计费不能按“剩余未发送字节”偷换为“仍持有的分配”。一个 64 KiB 缓冲即使只剩一个字节没发送，整个分配仍活着。另外，`string.reserve(1 MiB); string="x"` 的 size 只有一，但移动它可能保留一 MiB 分配；因此直接按 size 计费并 move 字符串不能兑现本章的缓冲约束。当前接口借用输入并申请精确 payload 长度，拒绝继承调用者的备用 capacity；这是为资源正确性付出的复制成本，未声称它更快。

本章 `bytes()` 在完整弹出前一直包含整条自有 payload 申请量；分配器元数据、容器节点和借用输入不计入这个数。空输入不产生节点，非空节点至少持有一字节，故节点数也有有限上界。`enqueue` 先做减法形式的容量检查，成功插入后再更新计数；分配失败时旧队列保持有效，外层需按失败路径结束该连接。

L02 的 bad 是真实算法缺陷：只要发送成功就弹出整条。相同 checker 先发送两字节，再检查队首是否仍为 `cdef`，用它校准检查器。另一 bad_lifo 颠倒多条消息的出队顺序，必须被内容顺序检查拒绝；只检查水位和总长度识别不了它。L01 另保留忽略长度头高四位的反例，验证大长度不会被截断成合法小帧。崩溃或任意退出码不算正确识别错误。

## 5. 场景切换：慢读者如何把局部队列变成系统问题

现在允许多请求和多连接。如果持续读入并回送，而对方长时间不接收，响应先积压在内核，随后 `send` 返回 would-block，再积压到应用队列。TCP 流控限制传输，并不会自动给你的 `deque` 设置上限。

先用状态模型复现增长：连续输入十二个 4096 字节 wire，每次产生一个待发送响应，不消费输出。于是用户态队列达到 48 KiB。此时暂停读取；排空至 32 KiB 后再恢复。64 KiB 是硬上限，48/32 KiB 是避免频繁开关的高低水位，三者不是同一个参数。

硬上限留出余量还有协议原因：收到一个 4096 字节输入块时，解析器可能已有最多 4095 字节残 body。这个输入可能完成旧帧并包含新帧，所以输出增长不一定只等于本次输入块大小。本章每次只在低于高水位时读入最多 4096 字节；16 KiB 余量覆盖残帧完成和新输入。违反入口契约直接拒绝，不静默丢掉一个已解析响应。

```text
可读事件 → 有读取配额且未背压？ → recv → 增量解析 → 有界 writer
可写事件 → send(front) → 更新偏移 → 整帧释放 → 低水位恢复读取
```

L02 `states.cpp` 证明慢连接达到水位后暂停、下降后恢复，并且另一连接具有独立可推进状态。这还不是多连接调度公平性的实测；后续 Reactor 实验要验证每轮预算、就绪队列和真实连接进度。ET 后端如果因为预算用尽提前停止，必须显式排入可运行队列，不能等待未必再次产生的边沿。

这里没有得出“64 KiB 是最快值”。水位首先实现可解释的资源契约；改变批量、布局或缓冲大小来优化性能，必须先做同口径负载和定位实验。`SO_SNDBUF`/`SO_RCVBUF` 的请求值与操作系统实际值另行记录，不将用户态预算扩展为整个内核的精确内存保证。

## 6. 关闭是一条完成路径

连接模型包含 `open`、`peer_eof`、`draining`、`closed`。

| 事件 | 转换及责任 |
|---|---|
| 完整读取到 EOF | 验证无残帧；停止读，已有响应仍须发送 |
| 残帧 EOF 或解析错误 | 协议失败，当前连接结束，不冒充一次成功调用 |
| 服务主动 drain | 停止接纳当前连接的新请求，保留已有 writer |
| 非 open 状态下最后一帧发送完成 | 进入 closed，驱动释放 socket |
| 重复 drain | 不重开读取，不重发消息，不重复拥有资源 |

客户端 `shutdown(SEND)` 只关闭自己的发送方向，仍能读取响应。L02 的真实回环检查按字节写入两帧，半关闭后验证响应内容，然后继续观察服务端 EOF。全部线程在进程退出前 join。内部五秒 deadline 防止正常逻辑无限等待，外层运行器和 CTest 另有超时，覆盖退出和清理。

本章 writer 的底层是就绪通知：`send` 返回后，这次同步系统调用不再借用用户 buffer。换到 IOCP 等完成通知时，提交返回不等于借用结束；即使请求取消，也必须保留 operation 和 buffer，直到目标操作的最终完成被消费。后续完成模型单元在这个地方增加状态，不能直接提前释放本章的队列节点。

## 7. 自测与解析

1. **空帧和 EOF 有何不同？** 空帧仍有八个头字节，产生一次空字符串结果；EOF 来自非空接收请求返回零，表示该方向没有更多字节。把二者合并会漏掉合法消息。
2. **接收了七个头字节后，下一轮是否可以重新解析？** 不可以丢掉前七字节。保留头状态后继续；否则长度字段改变，后续 body 会被错当头。
3. **已经发送 4095/4096 字节，能否只计费一字节？** 若仍持有原 4096 字节字符串则不能。可以换成不同缓冲布局，但要重新分析对象和分配责任，并测量复制成本。
4. **取消是否允许立即销毁异步缓冲？** 不允许仅凭取消请求推断。必须先确认目标操作终结、所有可能访问它的回调均已收束。
5. **高水位暂停后，是否永久不再读？** writer 排空到低水位要恢复兴趣或可运行状态；否则即便内存空出来也会停滞。恢复逻辑必须与停止逻辑一起检查。
6. **回环实验成功是否证明所有网络交错正确？** 它验证当前环境里的实际 socket 路径；任意切片解析和水位状态另外由确定性输入验证。完整正确性仍依赖接口契约、所有权和状态推导。
