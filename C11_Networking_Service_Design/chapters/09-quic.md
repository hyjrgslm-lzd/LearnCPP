# 09 QUIC：将可靠流从 TCP 字节队列中分离

先修 TCP、UDP、TLS 和 HTTP/2。实践 [L09](../exercises/L09_quic/README.md)使用 MsQuic2.6.1 的实际回环连接。QUIC 是传输，HTTP/3 是其上的 HTTP 映射；本实验传送自定义 ALPN 的任务示意数据，不冒称 HTTP/3 实现。

## 1. 包和流使用不同序号

TCP 的统一字节顺序把丢包恢复与所有应用流绑在一起。QUIC 在 UDP 上自行维护连接、加密、确认、重传和拥塞状态；STREAM frame 以 stream ID、offset、length 描述某个流的字节。包号标识一次发送的包，流偏移标识稳定的内容位置。丢包后重传的是尚需交付的 frame 内容，放进新的包号，不复用旧包号。

接收方可在各流内重组并有序交付；一个流缺少某个 offset，不必阻止另一个已经连续的流交付。但连接拥塞窗口、总流控、CPU 和路径容量仍共享，不能把“无跨流字节顺序阻塞”讲成“完全互不影响”。协议责任由 [RFC9000](https://www.rfc-editor.org/rfc/rfc9000.html)、TLS 映射 RFC9001 和恢复 RFC9002 分别定义。

流 ID 的低位编码发起者和单向/双向属性，同类型递增步长 4。L09 客户端前两个双向流为 0、4。双向流有独立收发方向；FIN 给出发送结束和最终长度，RESET_STREAM 终止发送并携带最终大小，STOP_SENDING 请求对方停止发送。取消一个方向和销毁整个连接不是同一操作。

## 2. 可靠性和拥塞反馈

ACK frame 可表达已收到包号的区间，发送方据此更新 RTT 和丢失推断。包阈值/时间阈值检测与 PTO 探测针对不同情况；PTO 不是宣布整条连接失败，而是发送探测帮助获得新反馈。实际重传调度、拥塞窗口增长和降速由 MsQuic 实现，应用不应在它上面再做逐包重发。

可以用一个安全纸面轨迹检查理解：包 10 含流 A 的 offset0，包 11 含流 B 的 offset0；10 丢失、11 到达。B 可以交付连续内容，A 等待重传。重传包 12 仍含 A 的 offset0，接收方按流偏移去重。若把包号当业务消息号，重传会看起来是新消息；若重复收到同一业务提交，即使传输已去重，应用仍需自己的幂等键。

本次 L09 不使用网络损伤驱动，没有实测公网丢包恢复、拥塞算法优劣或路径迁移。可复现实验规格是使用双向有界 UDP 转发器，按确定包序丢一次、记录转发计数及 MsQuic transport counters，再验证精确 payload 与退出；不能用应用层丢弃消息代替传输丢包证据。未执行的扩展不参与性能结论。

## 3. 握手、地址验证和反放大

QUIC 使用 TLS1.3 握手消息生成密钥，但不使用 TLS record 层承载 QUIC 应用数据。CRYPTO frame 按加密级别传递握手内容，包保护和头部保护作用于 QUIC 包。Initial、Handshake、应用数据有相应包号/密钥阶段；丢弃旧密钥后不能再处理该阶段的新合法数据。

尚未验证地址的服务器要限制向该地址发送的量，避免伪造源地址制造放大攻击。Retry/token 和路径验证是相关机制，和证书认证不同：地址能接收报文不表示用户获授权，证书可信也不证明新路径已经验证。

L09 固定私有 CA，检查可信 localhost 握手和不相关 CA 拒绝。Windows OpenSSL 后端显式使用 TLS 内建验证与 CA 文件选项，不能给一个 CaCertificateFile 却让平台信任路径忽略它。示例没有安装系统证书，也没有禁用验证。

## 4. 接收信用与发送内存寿命

MAX_STREAM_DATA 限制一个流可发送到的偏移，MAX_DATA 限制连接级总信用。应用消费太慢应延后归还信用。L09 在大流 RECEIVE 回调返回 pending，保持该接收缓冲的借用；小流仍完成 ack。应用决定恢复时调用 StreamReceiveComplete，再验证完整 32768 字节和回送。

关闭 send buffering 后，应用发送缓冲必须保留到 SEND_COMPLETE。StreamSend 成功只说明库接纳了请求；缓冲不能立刻 clear 或重用。取消发送仍等待 canceled SEND_COMPLETE，再等待 stream shutdown complete 才关闭 handle 和释放回调 context。主线程和库回调可能并发，实验用 mutex 保护 handle/state；可能内联触发回调的调用不能持锁造成递归死锁。

## 5. 迁移、恢复与 HTTP/3

connection ID 让连接身份不完全依赖地址四元组，因此网络地址改变后可以识别候选连接。但迁移还要验证新路径并调整拥塞/RTT 状态，不能仅凭收到相同 CID 就信任源地址。NAT rebinding、主动迁移与多路径不是可随意混用的术语。

会话恢复降低再握手成本，0-RTT 仍有重放边界。HTTP/3 将请求映射到 QUIC 流，QPACK 用单独指令流同步动态表，允许可控的字段块阻塞；其引用计数/已知接收插入计数是避免无界等待的重要状态。它和 HPACK 不是改个协议名，HTTP/3 也需要自己的控制流与 SETTINGS。本课在源码和推导层展开映射，运行入口保持为 QUIC 传输实验。

## 6. 自测与解析

1. **重传能复用包号吗？** 不应这样设计；重发 frame 内容使用新包号，流 offset 保持内容身份。
2. **SEND_COMPLETE 表示远端业务已处理吗？** 不表示；它终止本次发送缓冲借用，业务完成由响应或任务查询确认。
3. **慢流 pending 的缓冲能保存 string_view 后立刻归还吗？** 若继续使用数据，应先复制或保持借用；归还后 view 不再拥有存活保证。
4. **有 CID 就无需验证新地址吗？** 不，连接识别和路径可达性是两个责任。
5. **L09 成功能否证明 HTTP/3 正确？** 不能，实验没有 HTTP/3/QPACK 层；这部分以规范推导和源码对照学习。
