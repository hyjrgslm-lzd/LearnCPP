# 01 从端点到传输契约

先修是 C05 的字节序与 C07 的系统调用。目标是看到一次“请求超时”时，能区分寻址、建立连接、传输和远端业务四个阶段。实践使用 [L03](../exercises/L03_transport/README.md)，不需要公网服务器。

## 1. 先把层次分开

应用将字节交给传输层；IP 负责将分组送往地址；链路只负责相邻节点。地址不等于进程身份，端口也不是业务请求号。TCP 连接由本地/远端地址和端口及协议上下文区分。同一服务器端口能服务很多连接，因为远端端点不同。IPv6 地址有 128 位，IPv4 有 32 位；序列化必须按网络字节序，不能把主机整数布局直接写入协议。

绑定 `127.0.0.1:0` 表示只接受本机访问并让系统选择端口；随后用 `getsockname` 取得实际端口。`0.0.0.0` 是通配绑定，不是本课的默认监听地址。IPv6 link-local 地址还需要接口 scope，不能只保留一段地址文本。L03 的 IPv4/IPv6 分支使用各自地址结构，避免假定二者长度相同。

## 2. TCP 可靠的是字节流

顺序调用 `send("abc")`、`send("def")`，远端合法观察包括 `abcdef`、`a` 加 `bcdef` 等分片。TCP 的序列号跟踪字节位置，ACK 确认到达对端 TCP 的数据；应用消息边界由应用协议定义。即使 send 返回全部长度，也只能说明本地接受了这些数据，不能据此提交一次支付或删除幂等记录。[TCP 规范 RFC9293](https://www.rfc-editor.org/rfc/rfc9293.html)定义了这些传输状态。

最小正确客户端是：连接 → 循环发完整帧 → 循环收完整响应 → 校验响应 → 关闭。每步都可能部分完成或失败。因此第 3 章不从“一次 read 就一条消息”的错误基线开始，而从顺序读满的正确基线进入多连接。

三次握手让双方建立初始序列空间和状态；它不验证应用层用户。正常关闭的 FIN 只关闭一个发送方向。收到 EOF 后仍可能需要写完响应，因而连接应分别记录读结束和写排空。RST 表示中断，残留未发送响应不能记为成功。主动关闭方可能保留 TIME_WAIT 以隔离旧连接报文；这解释短连接端口压力，不能据此盲目开启地址复用或缩短系统超时。

## 3. 流量控制与拥塞控制不是同一个限制

接收窗口表达接收端还能接受多少字节；拥塞窗口是发送端根据网络反馈决定可在途多少字节。粗略看，一次可发送量受 `min(rwnd, cwnd) - 已在途字节` 限制。应用队列又是第三层：send 暂时不能推进时，上游还在生产响应，会在用户态积压。增加 socket 缓冲只能移动等待位置，不能消除供给长期大于消费的问题。

假设链路吞吐 10 MB/s，往返 20 ms，带宽时延积约 200 kB。窗口低于这个量可能限制吞吐；加到更大仍不保证更快，因为对端处理或拥塞窗口可能是限制。这个计算是容量推导，不是本机性能观察。若总等待预算 100 ms，允许无限排队再增加缓冲反而可能使尾延迟恶化。

Nagle 合并少量未确认数据，延迟 ACK 减少确认流量；两者和应用小写入模式可能相互作用。`TCP_NODELAY` 是可测的选项，不是正确性修补：先保持相同消息和调用次数测量，再解释时延分布。启用它不会恢复消息边界，也不会让 write 成为远端确认。

## 4. UDP 保留报文，却不给业务可靠性

一次 UDP 接收对应一个报文，报文可能丢失、重复或乱序。零字节报文合法，不能套用 TCP 的“recv 为零就是 EOF”。目标缓冲太小时会截断或报告消息过大，具体 API 返回形式有平台差异；不能把截断前缀交给业务当完整消息。L03 在真实回环上检查空报文和截断，再用显式输入序列演示遗漏的请求序号。后者是交付缺口模型，不声称回环真的发生了随机丢包。

UDP 上的可靠协议至少需要消息标识、去重、重传预算和接收容量。直接“没收到就每毫秒重发”会在拥塞时增加拥塞。过大的 UDP 报文还可能触发 IP 分片，一片丢失即失去整条报文；应用应控制报文尺寸并处理路径 MTU 变化。QUIC 在第 9 章以成熟实现承担这些责任，而非给 UDP 加一个 ACK 就算完成。

## 5. 自测与解析

1. **收到 TCP ACK 能否说明任务完成？** 不能。ACK 属于传输层；至少需要业务响应或查询任务记录才能知道服务状态，响应丢失时还需要幂等重试。
2. **UDP recv 返回 0 后要关闭吗？** 若接收缓冲非空且 API 成功，可能是一条空报文。TCP 相同返回值才按字节流 EOF 解释；空目标缓冲本身不能用作 EOF 探测。
3. **连接成功后 DNS 是否仍参与每次 send？** 不参与这条已建立连接的寻址；重新解析只影响以后候选连接。池化连接可能比 DNS TTL 活得久，需单独制定轮换策略。
4. **为什么慢读者能让快请求变慢？** 单线程若在慢连接上阻塞写，其他连接得不到服务；即使非阻塞，若一次回调无限循环处理它，也会饿死其他连接。第 4 章用事件预算与就绪队列修复执行公平性。
