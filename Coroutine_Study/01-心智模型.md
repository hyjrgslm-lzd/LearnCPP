# 01 心智模型

## 为什么先讲心智模型

如果你一上来就找 `co_await` 的语法示例，你很容易陷入两个误区：

- 误把协程当成"另一种写回调的方式"，以为 `co_await expr` 只是 `expr.then(callback)` 的语法糖。
- 误把协程帧当成"编译器帮你管理的线程栈"，然后用线程的思维模型去理解挂起和恢复。

这两个误区都会让后面的练习变成"抄例子"，而不是"理解协程设计"。

所以在开始写任何代码之前，先把这套模型里的对象关系钉牢。

## 先分清四件不同的东西

协程不是"一个东西"，而是四个独立概念在编译器、运行时、用户代码三个层面的协作。在最初阶段最容易混淆的就是这四个词：

### 1. 协程（coroutine）

协程是 C++ 语言层面的一种**函数**。判断标准只有一个：函数体里是否出现了 `co_await`、`co_yield`、`co_return` 三个关键字之一。出现了，它就是协程；没出现，它就是普通函数。

注意：协程**不是**线程。协程不创建新的执行栈（至少在操作系统层面）。协程的"挂起"和"恢复"完全在用户态完成。

### 2. 协程帧（coroutine frame）

协程帧是协程在**运行期**对应的那块内存。当一个协程在某个点挂起时，所有需要在恢复后继续使用的局部变量、参数、临时对象，都会被保存在协程帧里。

默认情况下，协程帧在堆上分配（通过 `operator new`）。但在满足 HALO 条件时，编译器可能把帧优化在栈上。帧的大小、布局、分配方式都是编译器决定的，不在标准规定范围内。

### 3. promise_type

`promise_type` 是协程内部的一个**用户可定制**对象。它由编译器在创建协程帧时自动构造，在协程帧销毁时自动析构。它不是 `std::promise`，名字相同但概念不同。

`promise_type` 提供了一组可定制点：必有的 `get_return_object`、`initial_suspend`、`final_suspend`、`unhandled_exception`、以及 `return_value`/`return_void`（互斥二选一）；可选的 `yield_value`、`await_transform`、`operator new` / `operator delete`、`get_return_object_on_allocation_failure`。协程的几乎每一个关键行为——启动、挂起、返回值、异常处理、`co_await` 表达式的类型变换、协程帧分配——都由这些定制点决定。模块 D 中会按"必有 hook"和"可选 hook"两类分别列时序与职责。

### 4. coroutine_handle

`coroutine_handle` 是指向协程帧的一个轻量句柄。你可以通过它做三件事：

- `.resume()`：恢复被挂起的协程。
- `.done()`：查询协程是否已经在 final_suspend 点。
- `.destroy()`：销毁协程帧，释放内存。

`coroutine_handle` 本质是一个指针。它的复制、传递、生命周期管理，直接决定了协程帧的生死。

把这四个概念分开后，第一阶段你主要和"协程函数 + coroutine_handle"打交道；第二阶段你会深入"promise_type + 协程帧"。

## 八个核心对象

除了上面四个概念，还有四个对象会在协程的每一次"挂起-恢复"中出现。

### 5. awaitable

awaitable 是**可被 `co_await` 消费**的对象。`std::suspend_always`、`std::suspend_never`、你自定义的 awaiter 类型、甚至一个 `std::future<T>`（在你给它加了 `operator co_await` 之后）都是 awaitable。

### 6. awaiter

awaiter 是 `co_await` 表达式经过编译器变换后真正执行控制的对象。awaitable 通过三步查找（见下文）被转换为 awaiter。awaiter 必须提供三个方法：

- `await_ready()`：在挂起前检查。返回 `true` 表示"不用挂起，直接继续"。
- `await_suspend(coroutine_handle)`：真正挂起时被调用，接收当前协程的 handle。这个方法可以做三件事之一：保存 handle 稍后 resume、或者直接返回一个 `coroutine_handle` 做 symmetric transfer、或者返回 void/bool 让编译器决定。
- `await_resume()`：协程被恢复后、`co_await` 表达式的返回值。这是挂起点"返回"给协程体的值。

### 7. 挂起点（suspend point）

挂起点是协程执行流中**可能暂停**的位置，即 `co_await`、`co_yield` 表达式所在的行。注意"可能"——如果 `await_ready()` 返回 `true`，这个点就不会真正挂起，协程会直接跳过 `await_suspend` 继续执行。

### 8. 恢复点（resume point）

恢复点是 `await_suspend` 被调用之后、协程再次获得执行权的位置。从协程体内看，恢复点就是 `co_await` 表达式返回的位置——`auto result = co_await something;` 中的 `result` 获得值的那一行。

这八个对象——协程函数、协程帧、promise_type、coroutine_handle、awaitable、awaiter、挂起点、恢复点——是你理解协程的完整词汇表。任何协程行为都可以用它们的组合来解释。

## 三种完成方式

一个协程可以以三种方式结束它的生命周期：

### 1. value 完成（co_return）

协程体执行到 `co_return expr;`（或 `co_return;` 对于返回 void 的协程）。编译器调用 `promise_type::return_value(expr)`（或 `return_void()`），然后进入 `final_suspend`。

### 2. exception 完成（unhandled_exception）

协程体中抛出了一个未被 try-catch 捕获的异常。编译器会自动 catch 这个异常，调用 `promise_type::unhandled_exception()`。通常的做法是在这里面把异常存起来，等协程的调用方通过 `coroutine_handle` 取走。

关键规则：`unhandled_exception()` 中不能再 throw。因为此时协程帧还未销毁，二次异常会直接 `std::terminate`。

### 3. cancel 完成（stop_token + set_stopped）

这不是语言层面的原生通道，而是一种工程约定：协程接收一个 `std::stop_token`，在每次 `co_await` 点检查 `token.stop_requested()`，如果已请求取消，则提前 `co_return` 或抛出一个内部约定异常。在 C++26 sender-receiver 体系中，这对应于 `set_stopped()` 通道。

三种完成方式对应三种"协程结束的原因"，它们是互斥的：一条协程的执行路径最终只走其中一种。

## co_await 的三步查找

当你写下 `co_await expr` 时，编译器并不是直接去找 `expr` 的 `await_ready`。它要经过三步查找，将 `expr` 这个 awaitable 转换为 awaiter：

1. **promise.await_transform(expr)**：编译器首先检查当前协程的 `promise_type` 是否提供了 `await_transform` 方法。如果提供了，就用 `await_transform` 的返回值替代 `expr` 作为 awaitable。这是 promise 唯一能拦截和变换 `co_await` 操作数的钩子。

2. **成员 operator co_await**：如果 `await_transform` 没有提供（或不存在），编译器在上一步得到的 awaitable 类型上查找成员函数 `operator co_await()`。

3. **ADL operator co_await**：如果成员也没有，编译器通过参数依赖查找（ADL）在 awaitable 类型所在的命名空间中查找自由函数 `operator co_await()`。

经过这三步得到的对象就是 awaiter。编译器随后按顺序调用它的 `await_ready()`、`await_suspend()`、`await_resume()`。

理解这三步查找的优先级非常重要，因为在第二阶段你会自己实现 `await_transform` 来做拦截，在第三阶段你会利用这个机制做 sender 桥接。

## 一次执行的四步

你可以把一次协程的完整生命周期拆成四步：

1. **创建协程**：调用协程函数。编译器生成代码分配协程帧（可能堆分配，也可能 HALO 优化成栈分配），在帧上构造 `promise_type`，然后调用 `promise.get_return_object()` 获取返回给调用方的对象（通常是一个 `task<T>` 或 `generator<T>`）。

2. **initial_suspend**：编译器调用 `promise.initial_suspend()`，得到第一个 awaiter。如果这个 awaiter 选择挂起（`suspend_always`），协程的执行就停在这里，控制权返回给调用方。这就是 lazy task 的起点。如果选择不挂起（`suspend_never`），协程体立即开始执行。这就是 eager task 的起点。

3. **执行体（含多次 suspend/resume）**：协程体开始执行。每遇到一个 `co_await` 或 `co_yield`，awaiter 的 `await_ready/suspend/resume` 三方法决定这次是挂起还是继续。如果挂起，控制权离开协程帧，进入 awaiter 的 `await_suspend` 逻辑。当外部调用 `coroutine_handle::resume()` 时，协程从上次的挂起点恢复执行。

4. **final_suspend + 销毁帧**：协程体执行到 `co_return`（或隐式结束）。`promise.return_value()`/`return_void()` 被调用。然后编译器调用 `promise.final_suspend()`，得到最后一个 awaiter。这个 awaiter 的 `await_suspend` 通常会做一件事：把当前协程的 `coroutine_handle` 交给等待它的父协程（symmetric transfer）或通知等待者。在 `final_suspend` 完成后，协程帧被销毁，`promise_type` 析构。

## symmetric transfer 与栈深度

最朴素的多层协程 resume 模式是这样的：A `co_await` B，B `co_await` C。C 完成后，通过 `coroutine_handle::resume()` 恢复 B，B 再通过 `resume()` 恢复 A。问题在于：如果链很长（比如 100 层），每次 resume 都是一个普通的函数调用，会导致调用栈不断加深。

symmetric transfer 解决了这个问题。核心机制是：`await_suspend` 可以返回一个 `coroutine_handle`。当编译器看到 `await_suspend` 返回了一个 handle，它不会在当前的调用栈帧里调用 `.resume()`，而是执行一个**尾调用**（tail call）跳转到下一个协程的恢复点。这确保了无论链多长，栈深度都不会累积。

你会在模块 B-1（递归 generator）和模块 D-3（自写 final_suspend symmetric transfer）中亲自体验这一点。

## 帧的所有权：谁负责销毁

这是协程中最容易出问题的工程问题。协程帧在堆上分配（默认），`coroutine_handle::destroy()` 是唯一合法的销毁方式。那么，谁负责调用 `destroy()`？

- 对于 `std::generator<T>`：`generator` 的析构函数会调用 `destroy()`。你有 generator 对象，就拥有帧。
- 对于 `task<T>`：取决于 final_suspend 的返回类型。如果 `final_suspend` 返回 `suspend_always`，那么协程在 final_suspend 点挂起，**不自动销毁帧**。这时，谁持有了 `coroutine_handle`，谁就要在合适的时机调用 `destroy()`。通常是由等待这个 task 的父协程（或 sync_wait 的调用方）来做。
- 对于 detached 协程（`final_suspend` 返回 `suspend_never` 且没有人持有 handle）：帧在 final_suspend 后自动销毁。但这也意味着没有任何外部方可以安全地等待它完成或获取它的结果。

核心原则：**永远不要让你持有的最后一个 `coroutine_handle` 超出协程帧的生命周期之前被丢弃或遗忘**。这相当于内存泄漏（在堆上）。

## HALO 是优化，不是语义

HALO（Heap Allocation eLision Optimization，堆分配消除优化）是编译器的一种优化：当编译器可以**静态证明**协程帧的地址不会逃逸出创建它的作用域时，它可以把帧分配在调用方的栈上，而不是堆上。

这意味着：

- 你不能在代码逻辑里假设"帧是堆分配的所以我可以把 handle 存到全局变量中"。如果 HALO 被触发了，帧在栈上，函数返回后 handle 指向已释放的栈内存。
- 反过来，你也不应该因为"怕 HALO"而把所有协程都写成逻辑上不允许 HALO 的形状。正确的做法是：**逻辑上就当帧在堆上**，通过正确管理 `coroutine_handle` 的所有权来保证正确性；性能上期待 HALO，但不依赖它。
- HALO 的触发条件因编译器而异，而且可能随版本变化。Clang 可以用 `-Rpass=coroutine-elide` 查看 HALO 是否触发。

模块 F 会专门带着你用编译器 flag 观察 HALO。

## 与 sender-receiver 的精确对应

如果你已经学过 sender-receiver 模型（P2300），下面的对应表会帮你快速建立协程视角：

| sender-receiver 对象 | 协程对应物 | 关键相似点 | 关键差异 |
| --- | --- | --- | --- |
| sender | awaitable | 都描述一段可组合的异步工作 | sender 是"图节点"，awaitable 是"暂停令牌"；sender 通过 `connect` 实例化，awaitable 通过 `co_await` 变换为 awaiter |
| receiver | promise_type | 都接收三种完成信号（value/error/stopped） | receiver 是独立对象，promise 在协程帧内与协程生命周期绑定 |
| connect(sndr, rcvr) | `await_suspend(coro_handle)` | 都是"把消费端和执行端连起来" | connect 生成 operation_state；await_suspend 直接交出协程的 coroutine_handle |
| operation_state | 协程帧 | 都代表一次具体的执行实例 | operation_state 是独立的生命周期对象；协程帧是从协程创建就存在 |
| start(op) | `coroutine_handle::resume()` | 都是"启动/恢复执行" | start 只能调用一次；resume 可以多次调用，直到协程 done |
| scheduler | executor（Asio 等框架中的概念） | 都提供"在特定执行资源上运行"的能力 | scheduler 是 P2300 的标准概念；协程本身不内置调度器，executor 由框架注入 |
| environment | promise_type::await_transform 或外部注入的 context | 都负责传播执行上下文 | environment 通过 receiver 的 get_env 查询；协程的上下文通常通过 promise 构造时传入或 await_transform 隐式获取 |
| completion_signatures | 协程的返回类型 `task<T>` / `generator<T>` | 都声明异步操作的产出类型 | completion_signatures 是编译期集合；协程返回类型是单一的 `T`（或 void） |

粗略地说：**promise_type 约等于 receiver + operation_state 的合体**（promise 既负责接收完成信号，又在帧内嵌着），**awaiter 的 `await_suspend` 约等于 connect + start**（把协程 handle 交给异步操作，并启动等待），**coroutine_handle 约等于 operation_state 的句柄**（持有者可恢复或销毁协程）。

## 每做一题都画这五样东西

从现在开始，你每做完一题，都至少画或写出下面五项：

1. 协程帧的持有者（谁拿着 coroutine_handle）
2. co_await 链的调用图（哪个协程在等待哪个协程）
3. 每个 awaiter 的 `await_ready/await_suspend/await_resume` 分别做了什么
4. 协程的启动策略（initial_suspend 是 always 还是 never，决定了 lazy 还是 eager）
5. 协程的销毁路径（final_suspend 的 awaiter 做了什么，谁最终调用 destroy）

这五项会把你的注意力从"语法像不像例子"拉回到"对象关系是否清楚"。

## 做题时的四个固定提问

每题都问自己：

1. 这段代码里，协程在哪个位置真正被创建？在哪个位置第一次被 resume？
2. 协程帧的所有权属于谁？挂起期间，帧为什么没有被销毁？
3. 如果 co_await 的异步操作抛异常，它会走协程的哪条路径——`unhandled_exception` 还是直接被 try-catch 捕获？
4. 这里的 awaiter 的 `await_suspend` 返回了什么类型（void / bool / coroutine_handle），分别意味着什么？

如果这四个问题里有任意一个回答不清，这题就不算真正做完。
