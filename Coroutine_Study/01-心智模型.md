# 01 心智模型

## 从普通函数开始

先看一个普通函数：

```cpp
int step(int x) {
    int a = x + 1;
    int b = a * 2;
    return b;
}
```

调用 `step(10)` 时，函数在当前线程的调用栈上执行。它一路跑到 `return`，把值交回调用方；如果抛异常，异常沿调用栈向外传播。局部变量 `a`、`b` 的生命期很短，函数返回后这段栈帧就没了。

协程要解决的问题是：函数执行到一半时，先把现场保存起来，把控制权还给外部；等外部事件完成后，再从中间那一行继续跑。普通函数的栈帧做不到这一点，因为返回以后栈帧就不存在了。

你可以手写一个状态机模拟这个能力：

```cpp
struct TwoStep {
    int state = 0;
    int x = 0;
    int a = 0;

    bool resume() {
        switch (state) {
            case 0:
                a = x + 1;
                state = 1;
                return true;   // 暂停，等下一次 resume
            case 1:
                x = a * 2;
                state = 2;
                return false;  // 完成
            default:
                return false;
        }
    }
};
```

这段代码已经具备协程的核心形状：状态字段保存执行位置，成员字段保存挂起后还要继续使用的变量，外部通过 `resume()` 推动它前进。C++ 协程让编译器替你生成这个状态机，并把关键行为开放给库类型定制。

## 协程函数如何被识别

一个函数体里只要包含 `co_await`、`co_yield` 或 `co_return`，它就是协程函数。它仍然是一个函数：有参数、有返回类型、有局部变量，也在某个线程上执行。区别在于，编译器会把它改写成可挂起的状态机。

标准把这个改写描述成一个 replacement body：创建 promise，执行 `co_await promise.initial_suspend()`，然后执行你写的函数体；正常 `co_return` 会调用 `promise.return_value` 或 `return_void`，未捕获异常会调用 `promise.unhandled_exception`，最后执行 `co_await promise.final_suspend()`。这个顺序来自 C++ 草案的 coroutine definitions 规则。

所以协程的第一条直觉是：协程不自动创建线程，也不自动并发。协程只是一个能保存现场、交出控制权、后来继续执行的函数状态机。它在哪个线程恢复，由 awaiter、调度器或手动调用 `coroutine_handle::resume()` 的代码决定。

## 协程帧保存什么

协程挂起时，后续还要用到的局部变量、参数副本、临时对象、当前执行位置和 promise 都需要存活。这些东西组成 coroutine state，教学里常叫协程帧。

普通函数的局部变量随着调用栈返回而消失；协程帧的生命期由协程返回类型、库对象和它们定义的契约管理。`coroutine_handle` 本身只是非拥有句柄，像一把能操作帧的钥匙；真正负责销毁的是持有并声明所有权的返回对象、scope、task 或运行时结构。实现通常会为协程状态申请额外存储，也允许在能证明生命期严格嵌套时省掉动态分配。你写代码时不依赖“它在堆上”或“它在栈上”，只追踪所有权契约和每个 handle 的使用期。

这个模型能解释很多常见 bug。比如，一个协程 lambda 如果捕获了局部变量，而协程创建后立即挂起，lambda 闭包可能先析构，协程帧里却只保存了对闭包成员的引用。恢复后读这个引用就是悬挂访问。安全写法是用命名协程函数，或把需要跨挂起点存活的数据显式传值进协程帧。

## 返回对象与 promise

协程函数的返回类型会通过 `std::coroutine_traits<R, Args...>::promise_type` 找到 promise 类型。promise 是协程帧里的定制对象，负责定义这些关键动作：

- `get_return_object()`：创建交给调用方的返回对象，比如 `lazy_task<int>` 或 `std::generator<int>`。
- `initial_suspend()`：决定协程创建后是立即执行，还是先挂起等待外部启动。
- `return_value()` / `return_void()`：接收 `co_return` 的结果。
- `unhandled_exception()`：保存未捕获异常，之后让消费者重新抛出。
- `final_suspend()`：协程体结束后的最后挂起点，常用于通知等待者。

`lazy_task<T>` 的惰性来自 `initial_suspend()` 返回 `std::suspend_always`。调用 `compute_async(5)` 只创建帧和返回对象，协程体第一行还没运行。`coroutine_study::sync_wait(std::move(task))` 才启动 root 协程，并等待它通过完成通知结束。

`std::generator<T>` 也是同样的语言机制，只是返回对象变成 range。调用 generator 函数时先得到 generator 对象；迭代器 `begin()` 和后续 `++it` 恢复协程；每次 `co_yield` 把值交给 `operator*`，然后再次挂起。

## coroutine_handle 是控制杆

`std::coroutine_handle<>` 是指向协程帧的轻量非拥有句柄。它能做三件事：

- `resume()`：让挂起的协程继续执行。
- `done()`：查询协程是否已经到达 final suspend。
- `destroy()`：销毁协程帧。

handle 可以复制，复制出来的 handle 仍指向同一个协程帧。复制 handle 不代表复制协程，也不自动取得所有权。这个性质让 handle 很强，也让它危险：如果两个库对象都自认为拥有同一帧并各自 `destroy()`，会 double destroy；如果没有任何拥有者负责销毁，会泄漏；后台线程拿着 handle 时拥有者提前销毁帧，会形成 use-after-free。

课程里的练习都要求你画“谁拥有协程帧，谁只是暂存 handle”。这张图能最小成本暴露生命周期错误。

## co_await 的运行顺序

`co_await expr` 的操作数先被转换成 awaiter。标准顺序是：如果当前 promise 有可用的 `await_transform`，先调用它；然后对得到的对象做 `operator co_await` 重载决议；如果没有可行重载，就把对象本身当 awaiter。最终 awaiter 要提供三个方法：

```cpp
bool await_ready();
void await_suspend(std::coroutine_handle<> h); // 也可以返回 bool 或 coroutine_handle
T await_resume();
```

执行顺序是固定的：

1. 调用 `await_ready()`。返回 `true` 时直接跳到 `await_resume()`，协程不挂起。
2. 返回 `false` 时，协程被视为已经挂起，然后调用 `await_suspend(h)`。
3. `await_suspend` 保存 handle、提交异步操作、注册回调，或直接恢复别的协程。
4. 外部某处调用 `h.resume()` 后，协程回到这个 `co_await` 表达式。
5. 调用 `await_resume()`，它的返回值就是 `co_await` 表达式的值。

A-3 的 `std::future` awaiter 就是这个模式：ready 的 future 走快路径，跳过 `await_suspend`；未 ready 的 future 把等待交给可 join 的 worker；worker 拿到结果或异常后恢复协程；`await_resume()` 把值返回给协程体，或重新抛出 `future.get()` 的异常。

## co_yield 与 co_return

`co_yield value` 可以理解为 `co_await promise.yield_value(value)`。generator 的 promise 把当前值保存起来，迭代器 `operator*` 读取它；下一次 `++it` 恢复协程，从 `co_yield` 后继续执行。

`co_return value` 调用 `promise.return_value(value)`，然后进入 `final_suspend`。它不像普通 `return` 那样直接把值塞回调用栈；值通常先存在 promise 里，再由 `await_resume()` 或 `sync_wait()` 取走。

这也是 A-1 和 A-2 的分界：A-1 观察“每次迭代只生产一个值”；A-2 观察“协程最终只完成一次，结果被返回对象消费”。

## 取消和组合建立在同一个模型上

取消通过共享 stop state 传播。`std::stop_source::request_stop()` 设置请求；协程、awaiter 或调度框架在自己定义的检查点读取 `stop_token.stop_requested()`，然后选择提前返回、走 stopped 通道，或在教学代码里抛一个特定异常做对比。

组合器由库定义调度和收束语义。本课程当前 `when_all` 示例启动多个子 task，等齐后汇合结果；`runtime.hpp` 的 `when_any_cancel_join` 返回两个任务中首个 value 或 exception 完成者，并请求取消、等待另一条任务收束。`task_scope`/`async_scope` 给动态产生的任务一个明确拥有者。

模块 C 的重点就是把这些工程约束放回到协程帧所有权上：每个飞行中的协程都要有人负责等待完成、传播取消、处理异常和销毁帧。

## 每做一题都记录五件事

1. 协程函数在哪里被调用，协程体第一行在哪里开始执行。

   **答案解析：** 合格记录要把“调用协程函数”和“协程体开始执行”分开写。以 A2 为例，`compute_async(5)` 在 main 中被调用，但 `lazy_task` 停在 `initial_suspend`，协程体第一行要等 `sync_wait(std::move(task))` 恢复 root 协程后才执行。以 A3 为例，等待 future 的协程也先由 `sync_wait` 启动，之后可能在 worker 调用 `resume()` 的线程上继续。

2. 挂起点是哪一行，`await_ready()` 是否可能让它跳过挂起。

   **答案解析：** 记录时要写具体行或具体表达式。A2 的初始挂起来自 `initial_suspend`，完成后还有 `final_suspend`；A3 的挂起点是 `co_await await_future(...)`。A3 还必须写 ready 快路径：`future.wait_for(0s) == ready` 时直接进 `await_resume()`，不会进入 `await_suspend()`。

3. `await_suspend()` 把 handle 交给了谁，后续谁调用 `resume()`。

   **答案解析：** A2 的 root task 由 `sync_wait` 驱动，没有把 handle 交给后台 worker。A3 未 ready 路径中，`await_suspend(h)` 把非拥有 handle 交给 `worker_group` 提交的 worker；worker 等 future 完成后调用 `h.resume()`。这里要写清 handle 的暂存者和实际恢复者，不能只写“系统恢复”。

4. 值、异常、取消分别通过什么路径回到调用方。

   **答案解析：** A2 的 25 通过 `co_return -> promise.return_value -> sync_wait` 回到 main，异常则会经 `promise.unhandled_exception -> sync_wait` 重新抛出。A3 的值先由 future 产生，再由 awaiter 的 `await_resume()` 交回协程体；future 里的异常也在 `await_resume()` 处重新抛出。取消在 A/B 不是主线，到 C1 才通过 `stop_token` 检查点返回 value、抛异常或走 stopped 语义。

5. 协程帧最后由哪个拥有者销毁，销毁前是否还有线程或回调暂存 handle。

   **答案解析：** A2 中协程帧由 move-only `lazy_task`/`sync_wait` 契约拥有，`sync_wait` 消费 task 后等待完成并取值。A3 中 future awaiter 在协程帧里，worker 暂存的是非拥有 handle；回调保存结果并 `resume()` 后不再访问 awaiter，外层 `state` 和 `worker_group` 活到 main 后续 join。合格记录要分别写 frame owner、后台线程 owner、以及后台路径是否还会碰 frame。

能把这五件事说清，后面的 promise hook、symmetric transfer、allocator、sender bridge 都只是局部扩展；说不清这些，代码能跑也只是碰巧。

## 进入模块 A 前的自测

1. `auto t = compute_async(5);` 为什么可能不执行协程体？哪个 hook 决定这件事？

   **答案解析：** 因为协程函数调用先创建协程帧和返回对象，然后执行 `co_await promise.initial_suspend()`。如果返回类型的 `promise_type::initial_suspend()` 返回 `std::suspend_always`，协程会停在初始挂起点，函数体第一行还没开始。A2 的 `lazy_task` 就用这个契约让 `compute_async(5)` 只产生 task，直到 `sync_wait(std::move(task))` 才恢复它。

2. `co_await` 的返回值来自哪个方法？异常通常在哪里重新抛出？

   **答案解析：** 返回值来自 awaiter 的 `await_resume()`。如果异步操作失败，awaiter 通常先保存 `std::exception_ptr` 或底层 future 的异常，再在 `await_resume()` 里重新抛出；这样异常位置对协程体来说就是那一行 `co_await`。父 task 若没有捕获，会由自己的 `promise.unhandled_exception()` 继续保存并传给外层消费者。

3. `await_ready()` 返回 `true` 时，`await_suspend()` 会不会被调用？

   **答案解析：** 不会。`await_ready()` 为 `true` 表示结果已经可用，协程直接执行 `await_resume()`，没有稳定挂起，也不会把 handle 交出去。A3 的 ready future 路径正是这样跳过 worker 和 `await_suspend()`。

4. `std::future<T>` 为什么需要用户命名空间里的包装 awaitable，而不能靠你给 `std::future` 增加成员？

   **答案解析：** `std::future<T>` 是标准库类型，用户不能给它添加成员方法，也不应该改 `std` 命名空间里的类型定义。协程的扩展点可以放在你自己的包装对象上：包装对象持有 future，并实现 `await_ready/await_suspend/await_resume`。调用点写成 `co_await await_future(std::move(fut))`，语义也更清楚。

5. 一个后台 worker 保存了 `coroutine_handle`，协程帧拥有者什么时候可以安全析构？

   **答案解析：** 安全条件是：后台路径后续不会再访问或恢复这个协程帧，并且销毁动作符合协程契约。`coroutine_handle` 本身不拥有帧，只是指向帧的控制杆；如果 frame owner 先销毁，而 worker 后面再 `resume()`，就是 use-after-free。A3 当前代码里，回调在 worker 中保存结果、调用 `resume()`，完成发布后不再访问 awaiter；`state` 和 `worker_group` 是外层对象，活到 main 后续 `workers.join()`。安全判断依据是后续恢复和访问 frame 的路径已经结束；join 是实现这种收束的一种组织方式。

6. generator 的 `co_yield` 后，谁负责下一次恢复协程？

   **答案解析：** 消费者负责。`co_yield` 把当前值交给 generator 的 promise 后挂起，`operator*` 只读取当前值；下一次 `++it` 或 range-for 的下一轮推进才恢复协程。A1 的日志应能看到“main 消费一个值 -> 迭代器推进 -> generator 从上一个 yield 后继续”。

这些问题都能回答后，再开始写 A-1。第一遍做题时，先遮住本页解析自己作答，再对照解析补齐 owner、挂起点、恢复点和值/异常路径，比多看一篇文章更有用。
