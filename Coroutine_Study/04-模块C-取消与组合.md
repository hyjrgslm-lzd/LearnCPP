# 04 模块 C：取消与组合

## 模块目标

前两个模块让你熟悉了 `generator` 的惰性语义和 `lazy_task<T>` 的串行异步组合。这个模块开始进入协程在工程中真正重要的部分：

- 取消是协作式的，不是抢占式的——`stop_token` 需要在协程作者选定的检查点主动检查，I/O awaiter 通常把 `co_await` 点也设计成 cancellation point
- `when_all` / `when_any` 让并发组合从"手写线程同步"变成"声明式描述"
- `async_scope` 是结构化并发的载体——每条异步工作都要有明确的生命周期归属

如果你跳过了这个模块，后续写任何涉及并发协程的代码都会在"谁负责收束、取消如何传播"这两个问题上反复踩坑。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- 为什么 `set_stopped` 和抛异常是两件完全不同的事。
- 为什么很多 `co_await` 点会被库设计成 cancellation point，以及 CPU 循环为什么仍要显式检查。
- `when_all` 和 `when_any` 的语义差异，以及它们在超时、竞速场景下的适用性。
- 为什么 `async_scope` 析构前必须等齐所有 fire-and-forget 任务，以及 `detach` 为什么在工程中几乎总是错的。
- 结构化并发的三条原则在协程世界中如何落地。

## 练习 C-1：协作式取消

### 目标

让一个 `lazy_task` 接收 `stop_token`，在 `co_await` 前后或长循环中主动检查取消请求，建立"取消是协作式的、由检查点响应、stopped 不等于 error"的直觉。

### 前置理解

- 你已经会用附带的 `lazy_task<T>` 写串行异步逻辑。建议先将 A-2 的 `lazy_task` 复制到 `my_task.hpp` 作为本练习的起点，在其中扩展 stop_token 支持。
- 你知道 `std::stop_token` / `std::stop_source` 来自 `<stop_token>`（C++20），`std::stop_source::request_stop()` 可以发出取消请求。（C++26 / stdexec 另有不分配的 `std::inplace_stop_source`，本题用 C++20 的 `std::stop_source` 即可。）
- 你接受本题的重点是**取消的协作性**，不是实现完整的取消框架。
- 关键概念：`stop_token.stop_requested()` 返回 `true` 表示取消已被请求；协程通过在库定义的 cancellation point 或自己插入的检查点读取这个标志，决定提前返回、走 stopped 通道，或按教学简化返回部分结果。stopped 表示"有意停止"，error 表示"故障"。

### 必做任务

1. 给附带 `lazy_task<T>` 的 `promise_type` 增加 `stop_token` 支持：
   - 在 promise 中增加一个 `std::stop_token` 成员字段。
   - 提供一种方式让调用者在启动 task 时传入 `stop_token`（例如通过 `task.with_stop_token(token)` 或构造参数）。
   - 在每个可能长时间等待的 `co_await` 前后，以及纯 CPU 长循环内部检查 `stop_token.stop_requested()`，如果已请求取消，则走停止路径。

2. 写一个模拟长计算的协程函数，例如分批处理 10 个数据块，每批之间 `co_await` 一个延迟 awaiter：
   ```cpp
   lazy_task<int> batch_process(std::stop_token st, int total_batches) {
       int processed = 0;
       for (int i = 0; i < total_batches; ++i) {
           if (st.stop_requested()) {
               co_return processed; // 早退，返回已完成的部分
           }
           co_await async_sleep(100ms); // 模拟每批耗时
           ++processed;
       }
       co_return processed;
   }
   ```

3. 在主函数中创建 `std::stop_source`，启动 task，在短暂等待后调用 `stop_source.request_stop()`，观察协程提前返回。

4. 记录并回答：
   - 取消请求发出后，协程是在哪个 `co_await` 点退出的？
   - 协程返回值是已处理的批次数，不是抛异常——为什么这是正确的设计？
   - 如果协程不在 `co_await` 点检查 token，而是在纯 CPU 计算循环中，取消请求能被响应吗？

5. 再写一个版本：让协程在收到取消请求时抛出一个特定异常（如 `task_cancelled`），对比 stopped 路径和 error 路径在调用侧的区别。写一段笔记：为什么在协程中把取消映射成 `set_stopped` 比抛异常更合理？

### 进阶任务

- 实现 `stop_callback`：在 `stop_source.request_stop()` 被调用时自动触发一个回调，打印日志或设置标志位。观察回调与协程 `co_await` 点的时序关系。
- 让 `lazy_task` 的 `co_await` 点自动传播 `stop_token`：当 task A `co_await` task B 时，如果 A 的 stop_token 被取消，B 是否也应该感知到？
- 写一个嵌套协程场景：parent task 持有 `stop_source`，child task 持有 `stop_token`。parent 取消后，child 是否能在自己的 `co_await` 点跳出？

### 验收点

- 你能亲手触发取消，观察到协程在明确检查点提前退出。
- 你区分了 stopped（有意终止）和 error（故障），并能在代码中体现这个区分。
- 你能说明为什么取消是协作式的——没有人在中途强行杀死协程帧。
- 你能解释为什么库通常把 `co_await` 点设计成 cancellation point，也能说明这不是语言自动强制的行为。

### 观察点

- 取消的发生时机完全由协程、awaiter 或调度框架协作决定——这是"协作"的含义。
- 如果协程体中没有等待点（例如纯 CPU 循环），取消检查永远不会发生，除非你显式调用 `stop_token.stop_requested()`。
- `co_await` 点在工程中常有双重身份：既是挂起点，也是库定义的 cancellation point。但语言本身不会自动替你检查 token。
- 将 stopped 与 error 混为一谈会把调用侧的恢复逻辑弄得很奇怪——你要同时处理"真的故障"和"被取消了"。

### 常见坑

- 以为 `request_stop()` 会立刻终止协程——实际上要等协程或 awaiter 主动检查 token 才会响应。
- 在 `stop_token` 检查后抛异常模拟取消，导致调用侧必须用 try/catch 处理正常取消——这让 stopped 和 error 的边界模糊了。
- 忘记给嵌套的子协程传递 `stop_token`，导致取消只传播了一层。
- 在纯计算循环中没插入任何检查点，取消请求被完全忽略。

### 提示

- 模拟"延迟"可以用一个简单的 `async_sleep` awaiter：`await_suspend` 中用 `std::this_thread::sleep_for` + 立刻 resume。这在本次练习中够用。
- 先让 task 在收到取消时 `co_return` 一个默认值或已完成计数，跑通后再尝试 `set_stopped` 的完整语义。
- 如果你的 `lazy_task` 还没有 `stop_token` 通道，可以通过闭包捕获或构造参数传入。重点是观察取消行为。

### 复盘问题

- 为什么说协程取消是"协作式"的？如果协程作者不配合，取消机制会失效吗？
- 为什么 `set_stopped` 需要独立于 `set_error` 存在？如果只有 error，取消场景会带来什么困扰？
- 为什么 I/O 框架喜欢把 `co_await` 点设计成 cancellation point？这对协程调度器和资源回收意味着什么？
- 如果你要设计一个支持取消的协程库，stop_token 应该放在哪里——promise 内部？还是作为每个 awaiter 的隐式参数？
- 做完这题后，你对 `<stop_token>` 的理解比之前深了多少？

### 对应官方参考

- cppreference `<stop_token>`：`std::stop_token` / `std::stop_source` / `std::stop_callback` 用法（C++20）
- P2300R10 `std::execution`：sender-receiver 体系中的 `set_stopped` 完成通道
- Lewis Baker "Structured Concurrency" CppCon 2019
- `<stop_token>` 标准库头文件（C++20）

## 练习 C-2：when_all / when_any 使用

### 目标

用 `when_all` 并行启动 3 个 task 并汇合结果，用 `when_any` 实现超时竞速模式，建立并行组合与取消传播的直觉。

### 前置理解

- 你已经能独立写出 `lazy_task<T>` 的串行异步流程。
- 你知道 `when_all` 的语义是"等所有子 task 到达完成状态后汇合结果"；`when_any` 是"先返回第一个完成者的结果，同时必须请求取消并收束其余 loser task"。
- 本题中 `when_all` / `when_any` 可以使用简化实现（例如基于 `atomic<int>` 计数 + 回调 resume），重点是使用它们的语义，不是实现它们。
- 关键概念：`when_all` 中的取消传播——如果某一个子 task 抛异常，其他子 task 是否应该被通知取消？`when_any` 中的"竞速"语义——第一个完成的 task 决定整体结果，其余 task 的资源需要被释放。

### 必做任务

1. 实现或使用一个简化版 `when_all(tasks...)`：
   - 接受 3 个 `lazy_task<int>`。
   - 并行启动它们（每个可以通过不同的线程或同线程交错执行来模拟并行）。
   - 在最后一个 task 完成时，将 3 个结果汇合成 `std::tuple<int, int, int>`。
   - 如果任一 task 抛异常，`when_all` 应该通知其余 task 取消，然后传播异常。

2. 写 3 个模拟 task，例如分别模拟"从缓存读取"、"从数据库读取"、"从远程 API 读取"，每个有不同的模拟延迟：
   ```cpp
   lazy_task<int> fetch_cache()   { co_await async_sleep(50ms);  co_return 100; }
   lazy_task<int> fetch_db()      { co_await async_sleep(150ms); co_return 200; }
   lazy_task<int> fetch_remote()  { co_await async_sleep(300ms); co_return 300; }
   ```
   用 `when_all(fetch_cache(), fetch_db(), fetch_remote())` 汇合它们，记录总耗时和各 task 完成时间。

3. 实现或使用一个简化版 `when_any(tasks...)`：
   - 接受若干 task，返回第一个完成者的结果。
   - 其余未完成的 task 应收到取消通知，并且必须被等待到停止/完成后再释放资源。

4. 用 `when_any` 实现超时模式：将一个真正的 task 和一个"延迟 N 毫秒后返回 timeout 标记"的 task 放入 `when_any`：
   ```cpp
   auto result = co_await when_any(fetch_remote(), timeout_after(200ms));
   ```
   如果 `fetch_remote` 在 200ms 内完成，取到数据；否则取到超时标记。

5. 画一张图，对比串行执行（3 个 task 依次 await）、`when_all` 并行、`when_any` 竞速这三种模式的时序差异。

### 进阶任务

- 在 `when_all` 中实现**部分失败处理**：如果 3 个 task 中 1 个抛异常，但另 2 个的结果仍然有用（例如它们是独立的缓存更新），如何设计 API 来暴露这种"部分成功"语义？
- 在 `when_any` 中实现**取消并收束剩余 task**：第一个完成后，主动调用 `stop_source.request_stop()` 取消其他 task，然后等待它们到达 stopped/value/error 中的一种完成状态。观察需要怎样的协程结构才能让其余 task 响应取消。
- 用 `when_all` 组合 `when_any`：例如并行发起 3 组请求，每组内部都有一个超时保护。体会嵌套组合带来的表达能力。

### 验收点

- 你能区分 `when_all`（汇合）和 `when_any`（竞速）的语义。
- 你能用 `when_any` 正确实现超时模式。
- 你能画图解释串行、并行汇合、竞速三种模式的时序。
- 你能说明当一个子 task 抛异常时，其余子 task 应该发生什么。

### 观察点

- `when_all` 让"等齐 N 个异步操作"从手写计数器 + 条件变量变成了声明式表达。
- `when_any` 的超时模式是一个非常自然的组合——超时本身就是一个"延迟后完成"的 task。
- 并行组合之所以安全，前提是每个子 task 有独立的生命周期（没有共享可变状态）。
- 组合子的价值不仅在于"减少代码行数"，更在于让并发意图在类型层面可见。

### 常见坑

- 在 `when_all` 中用一个子 task 的异常直接吞掉其他 task 的结果，没有提供"部分结果"访问途径。
- `when_any` 中第一个完成后只取消、不收束其余 task，导致 loser task 仍持有资源或悬空访问。
- 把 `when_all` 用于有先后依赖关系的 task——那应该用串行 co_await。
- 以为 `when_all` 内部的 task 一定是真正并行执行的——协程的交错执行取决于调度器和线程模型。

### 提示

- 先实现 `when_all`，跑通并行汇合，再去做 `when_any`。两者共享相似的计数/callback 基础设施。
- 超时 task 可以用一个简单的 `co_await async_sleep(N)` + `co_return timeout_marker` 实现。
- 如果你使用的 `lazy_task` 尚不支持并行启动（例如 initial_suspend 是 suspend_always 且只被一个消费者驱动），可以先用多个 `std::jthread` 分别驱动每个 task，本模块不要求无锁实现。

### 复盘问题

- 在什么场景下 `when_all` 比逐次 `co_await` 更合适？什么场景下相反？
- `when_any` 的超时模式为什么比"在 task 内部传一个 timeout 参数"更干净？
- 如果 `when_all` 中一个子 task 抛异常但另一个已经完成了 90%，丢弃后者的结果合理吗？你有什么替代设计？
- 协程中的 `when_all` / `when_any` 与 sender-receiver 模型中的同名组合器，在语义上有哪些共通之处？

### 对应官方参考

- Lewis Baker "Structured Concurrency" CppCon 2019（`when_all` / `when_any` 部分）
- cppcoro 中 `when_all.hpp` / `when_any.hpp` 的接口设计
- P3149R4：async scope、spawn 与动态非顺序并发；P3296R1 补充自动 join 的 `let_async_scope`

## 练习 C-3：async_scope 与生命周期

### 目标

用一个 `async_scope` 管理 N 个并发协程任务，确保 scope 析构前所有任务都已完成。同时通过生命周期图和受控反例分析理解悬挂引用与 detach 风险；默认构建不执行 UB。

### 前置理解

- 你已经知道协程帧的生命周期不由协程体代码决定，而是由 `coroutine_handle` 的拥有者决定。
- 你知道 "fire-and-forget" 的问题在于没有一个明确的对象负责等待这个协程完成。
- 你接受本题的重点是结构化并发的生命周期管理，不是 scope 的高性能实现。
- 关键概念：`async_scope` 是一个作用域对象。对它调用 `spawn(task)` 会将 task 的生命周期纳入 scope 管理。scope 退出前要请求停止（如果需要）并等待所有已 spawn 的协程完成。这就建立了明确的归属关系：每个协程都有一个明确的"拥有者"。

### 必做任务

1. 实现一个最小 `async_scope`：
   - `spawn(lazy_task<void>)`：接收一个 task，将它移动到一个内部管理的协程句柄列表中。
   - 在 `join()` / `on_empty()` 中等待所有 task 完成；析构函数只做兜底断言或同步 join，不要通过 blind-resume 任意 handle 来“跑完”真实异步任务。
   - 一个简化版 `on_empty()`：一个可 `co_await` 的 awaiter，当 scope 内所有 task 都完成时 resume 等待者。

2. 写一个场景：启动 N 个（N >= 5）fire-and-forget task 到 scope 中，每个 task 有不同模拟延迟：
   ```cpp
   async_scope scope;
   for (int i = 0; i < 5; ++i) {
       scope.spawn([](int id) -> lazy_task<void> {
           co_await async_sleep(id * 50ms);
           std::print("task {} done\n", id);
       }(i));
   }
   // 离开作用域前调用 scope.join()/co_await scope.on_empty()，确认所有 task 完成
   ```

3. 验证 scope 退出前的等待行为：在 `main` 中调用 `scope.join()`（或在协程中 `co_await scope.on_empty()`）前后记录时间戳，确认所有 task 都已打印完成。析构只验证没有遗留任务。

4. **推演悬挂引用反例（默认不运行）**：画出“task 捕获局部引用，而局部对象先于 task 完成”的时间线，标出引用失效点和潜在恢复点。若你确实要用 ASan 观察，只能把反例放进 `COROUTINE_STUDY_ENABLE_UNSAFE_DEMOS` 控制的独立目标；普通 Starter/Reference/CTest 不执行 UB。

5. **detach 对比分析**：不要在默认实现里写裸 detach；分别画出下面两条 ownership 链并解释 shutdown 条件：
   - `scope.spawn(task)`：你知道谁在等待它，什么时刻它保证完成了
   - `detach(task)`：你不知道它什么时候结束，也不知道谁拥有它的协程帧
   - 写一段笔记：只有当进程级 owner、错误通道和 shutdown drain 都另有明确协议时，所谓 detached operation 才可能成立；否则为什么它会让生命周期不可证明？

### 进阶任务

- 为 `async_scope` 添加 `spawn_with_future(task)`：类似 spawn，但返回一个可以 `co_await` 的句柄，让调用者可以获取 task 的返回值。对比 spawn（fire-and-forget）和 spawn_with_future（有返回值需要回收）在 scope 析构时行为的差异。
- 为 scope 添加取消支持：`scope.request_stop()` 通知所有已 spawn 的 task 取消。验证取消传播的时序：scope 退出前 request_stop，然后 join/on_empty 等待所有 task 停止。
- 实现 scope 的嵌套：一个 scope 内部可以创建子 scope。父 scope 析构时先等子 scope 收束。画出嵌套 scope 的树形结构。

### 验收点

- 你能让 scope 在退出前等待所有已 spawn 的 task 完成，并让析构阶段不遗留飞行任务。
- 你能清晰区分 scope 中的 fire-and-forget 任务和需要回收结果的任务。
- 你能说明 `detach` 与 `scope.spawn` 的核心差异：前者无人拥有生命周期，后者被 scope 收束。
- 你理解为什么超出 scope 引用会导致 UB，以及 scope 的设计如何帮助避免这种情况。

### 观察点

- scope 的价值不在于多了一个容器，而在于把异步生命周期显式组织起来。
- 结构化并发的本质是：每一条异步工作最终都要能被某个上层对象收束。scope 就是这个"上层对象"的协程等价物。
- `detach` 不是"简洁版本"，而是"放弃了生命周期管理"——代价是程序正确性在规模增长后不可追踪。
- 一旦协程图变复杂（嵌套 scope、条件 spawn、动态任务数），谁拥有每个协程帧就不再是小问题。

### 常见坑

- scope 析构后还有 task 引用 scope 内部的资源——在协程中，这种悬挂比裸指针更难发现。
- 把 scope 当成"线程池的替代品"——scope 管理的是协程生命周期，不管理执行资源。
- 只 spawn 了 task，但忘记在 scope 退出前 join/on_empty，导致析构时仍有飞行任务。
- 在 scope 的 `spawn` 中将局部变量的引用传给 task，然后在 scope 析构前这个局部变量已经销毁。
- 以为 scope 能自动处理所有生命周期问题——scope 只管"等齐"，不能阻止你传悬挂引用进协程。

### 提示

- 最小 scope 也必须拥有 task/operation state，而不是只保存可随时悬空的裸 handle；可复用本仓库共享 runtime 的 task ownership 结构。
- 先实现显式 `join()` 或 `on_empty()` 等齐所有 task，再考虑析构兜底策略。
- detach 反例优先做 ownership 图与静态分析；需要动态观察时只在 unsafe demo gate 下运行。
- 画图时重点标注"谁拥有谁"，不要只画调用顺序。

### 复盘问题

- 为什么结构化并发强调的是"拥有关系"而不是"启动技巧"？
- 如果没有 scope，你会把这些协程帧交给谁负责销毁？
- 为什么 `detach` 在工程中几乎总是错的？它违反了结构化并发的哪条原则？
- `async_scope` 与 `std::jthread` 的析构行为（jthread 析构时 join）有何相似之处？这种设计为什么是正确的默认行为？
- 你现在能否解释 P3149R4 的 counting scope 为什么能收束动态并发，以及 P3296R1 的 `let_async_scope` 如何保证异常路径也完成 join？

## 做完模块 C 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- 取消是协作式的，通过 `stop_token` 在库定义或你显式插入的检查点传播。
- `stopped` 表示"有意义的终止"，不等于 error。
- `when_all` 用于并行汇合，`when_any` 用于竞速（含超时模式）。
- `async_scope` 的核心价值是结构化收束——每条协程工作都有明确的"拥有者"。
- `detach` 放弃了生命周期管理，是结构化并发的逃逸阀，在工程中几乎总是错误的。
- 协程的并发安全建立在每个协程帧有独立生命周期 + 组合子管理并发拓扑的基础上。
