# 04 模块 C：取消与组合

模块 C 讨论协程工程里最容易出事故的三件事：取消如何被看到，多个异步任务如何汇合，动态启动的任务由谁收束。它们都建立在前两章的同一套对象关系上：协程帧保存现场，awaiter 管理挂起点，返回对象或 scope 定义所有权。

本模块仍使用教学 runtime：[lazy_task.hpp](exercises/include/coroutine_study/lazy_task.hpp) 与 [runtime.hpp](exercises/include/coroutine_study/runtime.hpp)。先掌握语义，再考虑库级抽象。

<a id="c1"></a>

## 一、`stop_source`、`stop_token` 与协作检查

C++20 `<stop_token>` 提供一份共享 stop state。`std::stop_source` 能请求停止；`std::stop_token` 能观察停止是否已被请求。

```text
std::stop_source -- request_stop() --> [stop state] <-- stop_requested() -- std::stop_token
```

`request_stop()` 不会抢占线程，也不会销毁协程帧。它只是把 stop state 切到“已请求停止”。协程要在自己定义的检查点读取 token：

```cpp
coroutine_study::lazy_task<int>
batch_process(std::stop_token st, int total) {
    int processed = 0;
    for (int i = 0; i < total; ++i) {
        if (st.stop_requested()) co_return processed;
        co_await async_sleep(50ms);
        if (st.stop_requested()) co_return processed;
        ++processed;
    }
    co_return processed;
}
```

这叫协作式取消。协程作者决定哪些位置是 cancellation point。I/O awaiter 通常会在挂起前后检查 token；CPU 长循环需要自己插入检查。没有检查点时，取消请求只能停在 stop state 中，业务代码不会自动停下。

在 [练习 C-1](exercises/C1_stop_token_cancel/README.md) 中，先用显式参数传 `std::stop_token`，保留共享 `lazy_task` promise。main 创建 `std::stop_source`，另一个 `std::jthread` 延迟调用 `request_stop()`。你要观察：协程收到请求后继续运行到下一次 token 检查，再提前 `co_return processed`。

### stopped 与 error

取消是调用方有意发出的控制信号。异常通常表示故障。教学代码会让你写两个版本：一个收到取消后返回已处理批次数，一个收到取消后抛 `task_cancelled`。两个版本用于对比调用侧如何分别处理正常停止和故障路径。

返回部分结果时，调用方按普通值路径处理：

```cpp
int done = coroutine_study::sync_wait(std::move(task));
```

抛异常时，调用方必须走 `try/catch`。在 sender-receiver 体系中，取消对应独立的 stopped 通道；本课程第一阶段用显式返回或特定异常帮助观察，后续再实现更完整的通道。

## 二、`when_all`：多条任务等齐后汇合

串行写法：

```cpp
int a = co_await fetch_cache();
int b = co_await fetch_db();
int c = co_await fetch_remote();
```

这表示后一步依赖前一步完成。若三件事没有数据依赖，就可以并发启动，再等齐结果。`when_all` 的语义是：所有子任务到达完成状态后，整体才完成；整体结果包含每个子任务的结果。

教学版 `when_all3` 可以很朴素：为每个 `lazy_task<int>` 起一条 `std::jthread`，在线程中调用 `coroutine_study::sync_wait(std::move(task))`，主路径等待三条线程 join，再返回 tuple。

```text
when_all3
  -> thread 0 drives cache task
  -> thread 1 drives db task
  -> thread 2 drives remote task
  -> join all
  -> return tuple(cache, db, remote)
```

如果某个子任务抛异常，组合器要保存第一个异常，并请求其它任务停止。请求停止后仍要等待其它任务走到 value/error/stopped 中的一种完成状态。只请求取消但不 join，会留下还在访问资源的 loser 任务。

在 [练习 C-2](exercises/C2_when_all_when_any/README.md) 中，测量 `50ms/150ms/300ms` 三个模拟 fetch。串行约 500ms；并发汇合应接近最慢任务。这个耗时差异是 when_all 语义的可观察证据。

## 三、`when_any_cancel_join`：当前 helper 的竞速与收束

`when_any` 表达竞速。最常见用法是超时：

```cpp
auto winner = coroutine_study::when_any_cancel_join(
    stop_source,
    fetch_remote(stop_source.get_token()),
    timeout_after(200ms, stop_source.get_token()));
```

第一个完成的 task 成为 winner。若 timeout 先完成，整体返回超时标记，并请求停止真实请求。若真实请求先完成，整体返回数据，并请求停止 timeout task。无论哪边赢，另一边都叫 loser；loser 需要收到取消并被 join。

本仓库 [runtime.hpp](exercises/include/coroutine_study/runtime.hpp) 提供二选一 helper `when_any_cancel_join(stop_source, first, second)`。它为两个 task 各起一条 `std::jthread`，共享一个带 mutex/cv 的状态；第一个成功或失败的子任务写入结果或异常，请求 stop，并唤醒等待者。函数返回前，局部 `jthread` 析构会 join 两条执行路径。

你要关注三条边：

```text
winner -> 写 result/exception -> notify parent
winner -> request_stop() -> loser token 可观察到取消
scope/jthread -> join loser -> 资源可释放
```

少掉第三条边，竞速就是不完整的。超时返回得再快，如果慢任务还在后台持有引用，生命周期仍然不可证明。

## 四、scope：动态任务也要有上层 owner

有些任务数量运行时才知道，例如为每个 URL 启动一个 fetch。它们看起来像 fire-and-forget，但“忘记”只能是调用方不等待单个返回值，不能是系统中没有 owner。

`coroutine_study::task_scope` 的最小语义是：

- `spawn(lazy_task<void>)`：把 task 移动进 scope 管理的 worker。
- `join()`：等待所有 spawned task 完成。
- 子任务抛异常时，scope 保存第一个异常并请求停止，join 后重新抛出。
- 析构兜底请求停止并 join，不留下飞行任务。

在 [练习 C-3](exercises/C3_async_scope/README.md) 中，启动 5 个不同延迟的 task。`scope.join()` 前后打印时间戳；只有全部 task 完成，scope 才能离开。这个行为和 `std::jthread` 的 RAII 思路一致：对象离开作用域前收束它负责的执行。

### 悬挂引用时间线

scope 只能收束任务，不能替你修复错误引用。看这个反例的时间线：

```text
创建 std::string msg
spawn task，task 捕获 msg&
msg 所在作用域结束，msg 析构
task 后来恢复，读取 msg&
```

即使有 scope，捕获关系仍然错了。正确做法是让被 task 使用的数据活得比 task 更久，或按值移动进协程帧。C3 要求默认不运行 UB；画出时间线已经足够说明问题。

**答案解析：** 正确时间线是：局部对象先创建，task 捕获引用并挂起，随后局部对象离开作用域析构，最后 task 被恢复并读取那条引用。scope 的 join 只能保证 task 会被等齐，不能让已经析构的局部对象复活。图里如果没有“引用指向的对象先死、协程后读”这条边，就没有抓到这个 bug 的核心。

### detach 为什么危险

`detach` 会断开所有权链：

```text
scope.spawn(task)
  parent scope owns task lifetime
  join/drain point is visible
  exception/stop path has a home

detach(task)
  no visible owner
  no required join point
  error path often disappears
  shutdown 时不知道它是否还在访问资源
```

只有当进程级 owner、错误通道和 shutdown drain 都另有明确协议时，detached operation 才可能成立。第一阶段课程不走这条路。

## 模块 C 完成后

你应该能解释：

- stop 请求只是共享状态变化；协程通过明确检查点响应。

  **答案解析：** `std::stop_source::request_stop()` 只把共享 stop state 标成 requested。运行中的协程不会被抢占终止，必须在 `co_await` 前后或循环里主动读 `stop_token.stop_requested()`。C1 因此要求两个检查点：一个处理等待前已经取消，一个处理等待期间发生取消。

- stopped、value、error 是三种不同完成原因。

  **答案解析：** value 表示正常产生结果，error 表示异常传播，stopped 表示收到取消并协作停止。C1 用“返回已处理数量”和“抛 `task_cancelled`”对照，是为了看见 API 形状差异；更完整的组合库会把 stopped 作为独立完成通道。区分这三者后，组合器才能决定是继续汇总、传播错误，还是请求其它分支停止。

- `when_all` 等齐所有子任务，`when_any` 返回 winner 并取消/收束 loser。

  **答案解析：** C2 的 `when_all` 同时启动 cache/db/remote，最终返回 `(100, 200, 300)`，耗时接近最慢的 300ms。当前共享 `runtime.hpp` 的 `when_any_cancel_join(stop_source, first, second)` 是二选一 helper：首个 value 或 exception 完成者成为 winner，然后请求 stop，并等待另一条任务收束。它和 Capstone5 的 `mini_ref` 高阶契约不完全相同，本阶段按当前 helper 理解。

- scope 把动态并发纳入上层所有权，确保任务完成、异常和取消都有归宿。

  **答案解析：** C3 的 `task_scope.spawn(task)` 把动态创建的 task 交给 scope 管理，`join()` 是显式等待点；子任务异常由 scope 保存，join 后回到调用侧。scope 只能保证任务被收束，不能自动修复悬挂引用，所以跨挂起点数据仍要按值进入协程帧，或由更长寿命对象拥有。
