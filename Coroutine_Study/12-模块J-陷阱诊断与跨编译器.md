# 12 模块 J：陷阱诊断与跨编译器

## 模块目标

前面两个模块让你掌握了协程与 sender-receiver 的桥接以及真实异步 I/O 框架的对接。这个模块要解决协程工程中最容易被忽视的三件事：

- 协程的生命周期陷阱：你以为 co_await 只是一行代码，但它实际上是多个对象的存活期交叉点。
- 跨编译器 ABI：协程 ABI 不在 C++ 标准内，MSVC / Clang / GCC 各自有不同实现，跨 DLL 传 coroutine_handle 是地雷。
- 调试与 tracing：协程挂起后调用栈几乎消失，没有工具支持就是盲调。

如果你不经过这道题，就很容易在生产环境里踩中那些"编译通过、运行偶发崩溃"的协程深坑。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- 为什么 co_await 表达式里的临时量生命周期比你直觉认为的更短。
- 为什么 lock_guard + co_await 是未定义行为，以及应该用什么替代。
- 为什么 coroutine_handle 不能跨 DLL 安全传递。
- 为什么 HALO 在不同编译器上的触发条件不同，且不能作为性能保证依赖。
- 如何用 GDB 14+ 或 MSVC Parallel Stacks 定位挂起的协程。
- 如何实现一个轻量 awaiter wrapper 在 await_suspend / await_resume 自动打 trace。

## 使用建议

- 本模块的 J-1 是协程工程面试最常见的陷阱集合。每个陷阱先动手重现崩溃，再读修复方案。
- J-2 适合在你有多个编译器环境时做对比实验；如果只有 MSVC，可以先读完对比数据，留到有环境时验证。
- J-3 的 tracing wrapper 是生产环境中非常有用的基础设施，建议完成后保留为个人工具库片段。

## 练习 J-1：八大经典陷阱重现

### 目标

亲手重现协程工程中最常见的八个生命周期陷阱，每个陷阱给出最小复现代码和修复方案。通过这道题把"co_await 不是普通函数调用"刻进肌肉记忆。

### 前置理解

- 你已经完成模块 D（promise_type 全解）和模块 E（awaitable 三层与 co_await 变换）。
- 你理解 co_await 表达式会挂起当前协程，在挂起期间协程栈上的局部变量已被保存到协程帧，但表达式内部的临时量遵循普通 C++ 临时量规则。
- 你理解 coroutine_handle 是一个拥有协程帧生命周期的句柄，但它不拥有协程帧（帧由编译器生成的堆分配管理）。

#### 陷阱 1：lambda capture by reference 跨 co_await

**复现代码**：

```cpp
// 外部函数——调用者栈上的局部变量
task<void> bad_lambda_outer() {
    int value = 42;              // 在 bad_lambda_outer 的栈帧上
    auto t = bad_lambda_inner(value);
    co_await t;                  // 挂起，但 value 仍存活于 caller 栈帧
    // 如果 t 的生命周期超出 bad_lambda_outer，value 悬空
    co_return;
}

task<void> bad_lambda_inner(int& value) {
    auto lambda = [&value]() { return value; };
    co_await some_async_op();   // 协程挂起，frame 保存 lambda
    // 恢复时，如果 bad_lambda_outer 已经返回，
    // value（caller 栈上引用）已经析构 → UB
    std::cout << lambda();
    co_return;
}
```

**根本原因**：lambda 按引用捕获的是**协程外部的**局部变量 `value`（来自 `bad_lambda_outer` 的栈）。当协程挂起后，如果 `bad_lambda_outer` 先返回，`value` 被析构，协程恢复时 lambda 内部的引用指向已销毁的栈位置——这正是协程生命周期独立于创建者的核心风险。

**修复方案**：按值捕获或使用 `shared_ptr` 延长生命周期，使数据生命周期与协程帧绑定。

```cpp
task<void> good_lambda() {
    auto value = std::make_shared<int>(42);
    auto lambda = [value]() { return *value; };
    co_await some_async_op();
    std::cout << lambda();
    co_return;
}
```

#### 陷阱 2：临时量在 co_await 表达式中析构

**复现代码**：

```cpp
task<void> bad_temp() {
    co_await awaitable_that_stores_pointer(std::string("hello").c_str());
    // std::string 临时量在 co_await 表达式末尾已析构
    // awaitable 内部存储的 c_str() 指针成为悬空指针
}
```

**根本原因**：`co_await expr` 中，`expr` 是完整表达式。`std::string("hello")` 这个临时量在 awaitable 构造时就调用了 `c_str()`，但 `std::string` 本身在分号处析构。如果 awaitable 的 `await_suspend` 保存了这个指针，后续 `await_resume` 就会读取已释放的内存。

**修复方案**：

```cpp
task<void> good_temp() {
    std::string s("hello");
    co_await awaitable_that_stores_pointer(s.c_str());
    // s 的寿命覆盖整个 co_await 表达式
}
```

#### 陷阱 3：co_await 期间 lock_guard 上下文切换的 mutex UB

**复现代码**：

```cpp
task<void> bad_lock() {
    std::mutex mtx;
    {
        std::lock_guard<std::mutex> lock(mtx);
        co_await async_operation();  // 协程挂起，但 lock_guard 仍持有 mutex
        // 恢复时可能在另一个线程，lock_guard 在错误的线程解锁 -> UB
    }
    co_return;
}
```

**根本原因**：`lock_guard` 的析构（解锁）必须在获取锁的同一线程执行。`co_await` 挂起后恢复时，执行线程可能已经改变，导致解锁发生在错误的线程上，这是未定义行为。

**修复方案**：在 co_await 之前释放锁；如果必须跨挂起点持有锁，使用可重入的异步锁或 `std::unique_lock` 在挂起前手动解锁。

```cpp
task<void> good_lock() {
    std::mutex mtx;
    {
        std::unique_lock<std::mutex> lock(mtx);
        auto data = shared_state;  // 在锁保护下读取
        lock.unlock();             // 挂起前释放锁
        // data 按值进入协程帧，不依赖锁
    }
    co_await async_operation();
    co_return;
}
```

#### 陷阱 4：initial_suspend 抛异常的 frame 泄漏

**复现代码**：

```cpp
struct leaking_promise {
    // ...
    auto initial_suspend() {
        throw std::runtime_error("oops");
        return std::suspend_always{};
    }
};

task<void> bad_init() {
    // initial_suspend 抛出异常
    // 协程帧已经分配，但 get_return_object() 尚未完成
    // -> frame 泄漏
    co_return;
}
```

**根本原因**：编译器在调用 `initial_suspend()` 之前已经分配了协程帧并构造了 promise。如果 `initial_suspend()` 抛出异常，`get_return_object()` 还没有返回 task 对象给调用者，没有人持有 coroutine_handle，帧无法被销毁。

**修复方案**：确保 `initial_suspend` 不抛出异常；或者在 `get_return_object()` 中记录 handle，在析构时兜底。
截至 MSVC 17.10+ / Clang 17+ / GCC 14+，主流编译器在 initial_suspend 抛异常时已能调用 promise 析构与 operator delete，但具体清理保证与 promise 是否完成构造、是否暴露 frame 都相关。安全的工程做法仍是不让 initial_suspend 抛异常。

#### 陷阱 5：detached coroutine 越过创建者生命周期

**复现代码**：

```cpp
void bad_detach() {
    auto t = fire_and_forget_coro();  // 返回 task<void>
    // t 的析构函数没有等待协程完成
    // 协程可能仍在运行，访问已销毁的栈变量 -> UB
}  // t 在此析构

task<void> fire_and_forget_coro() {
    int local = 42;
    co_await timer(5s);
    // local 是 frame 内的，这里安全
    // 但如果协程捕获了 bad_detach 的局部变量引用 -> UB
}
```

**根本原因**：协程的生命周期独立于创建它的作用域。如果协程作为 task 返回后没有被等待（未被 co_await 或 sync_wait），它可能在创建者函数返回后继续运行。更危险的是：如果协程捕获了创建者栈上的引用，恢复时这些引用已经悬空。

**修复方案**：永远不要 detach 协程。使用 `async_scope` 管理所有非直接等待的协程，确保在作用域退出前所有协程已完成。

#### 陷阱 6：generator 返回引用的 dangling

**复现代码**：

```cpp
generator<const int&> bad_gen() {
    for (int i = 0; i < 10; ++i) {
        co_yield i;  // i 在 co_yield 后继续存活于 frame 中，这个安全
    }
    // 但这个就危险了：
    co_yield std::max(1, 2);  // 临时量的引用！
}
```

**根本原因**：`generator<T&>` 的 `co_yield` 返回引用时，被引用对象必须在协程 frame 中或具有更长的生命周期。`co_yield` 一个临时量的结果是：临时量在 `co_yield` 表达式结束时析构，返回的引用立即悬空。

**修复方案**：generator 按值返回 `T` 而非 `const T&`，或者将临时量存入协程 frame 的局部变量。

```cpp
generator<int> good_gen() {
    for (int i = 0; i < 10; ++i) {
        co_yield i;
    }
    int max_val = std::max(1, 2);
    co_yield max_val;  // 安全：max_val 在 frame 中
}
```

#### 陷阱 7：promise destructor 中 throw

**复现代码**：

```cpp
struct throwing_promise {
    // ...
    ~throwing_promise() {
        if (has_error) throw std::runtime_error("cleanup failed");
        // 析构函数中抛出异常 -> std::terminate
    }
};
```

**根本原因**：在协程帧销毁（`coroutine_handle::destroy()`）过程中，promise 的析构函数被调用。如果析构函数抛出异常，C++ 运行时调用 `std::terminate()`。这是不可恢复的。

**修复方案**：promise 析构函数必须 `noexcept`。所有清理逻辑需要"吞下"异常或在析构前单独处理。

```cpp
~throwing_promise() noexcept {  // 必须 noexcept
    if (has_error) {
        // 记录日志，但不抛出
    }
}
```

#### 陷阱 8：自写 generator 的 co_yield 临时量引用

**前置说明**：标准 `std::generator<T>` 的 promise 会将 yield 值（含临时量）拷贝/移动到协程帧内的 `_M_value` 存储中，因此 `co_yield` 字面量临时量在标准 generator 中是安全的。本陷阱针对的是**自己手写的 generator**——如果你的 `yield_value` 只保存了引用而非拷贝值，就会出现悬空引用。

**复现代码**：

```cpp
// 自写 generator（仅示意——promise 的 yield_value 按引用存储）
generator<std::string_view> bad_co_yield() {
    co_yield "hello"s;            // std::string 临时量
    co_yield std::format("v{}", 1);  // std::string 临时量
    // 每个临时量在 co_yield 表达式结束时析构
    // 如果 promise 的 yield_value 只存引用 → 悬空引用
}
```

**根本原因**：`co_yield expr` 中，如果 `expr` 是 prvalue 临时量，编译器将其作为 yield_value 的参数传入。这个临时量在 yield_value 返回后析构。如果你的自写 generator 的 promise 存储的是临时量的引用而非值的拷贝，消费者拿到的就是悬空引用。标准 `std::generator` 不存在此问题——它的 promise 做了值拷贝。

**修复方案**：

```cpp
// 方案 A：按值返回（推荐——与 std::generator 一致）
generator<std::string> good_co_yield() {
    co_yield "hello"s;            // 按值返回，移动语义
    co_yield std::format("v{}", 1);
}

// 方案 B：用局部变量延长生命周期
generator<std::string_view> good_co_yield2() {
    auto s1 = "hello"s;
    co_yield s1;                  // s1 存活于协程 frame 中
    // ...
}
```

### 观察点

- 八个陷阱中，有五个和"引用/指针的生命周期超出预期"有关——协程的核心认知障碍不是语法，而是对象存活期模型。
- `co_await` 不是普通函数调用：它会挂起当前上下文，但 C++ 的临时量规则并不会因为"这是协程"就放宽。
- 协程 frame 的布局是编译器实现细节。同一份代码在 MSVC 上可能碰巧不崩溃，在 Clang 上崩溃，因为 frame 中变量的相对布局不同。
- 理解协程的生命周期模型，本质是理解"哪些对象入帧、哪些对象在帧外、以及 awaiter 内部存储了什么"。

### 常见坑

- 只读别人的陷阱总结，不亲自写代码重现崩溃——这题的肌肉记忆来自 Segmentation Fault。
- 用 `shared_ptr` 无差别包裹所有变量，虽然不会崩溃，但也失去了协程帧的栈分配优势。
- 误以为 `co_await` 后代码一定在同一线程恢复——这是 mutex 陷阱的根因。
- 对 `initial_suspend` 抛异常的处理在不同编译器上行为不同，不要依赖某一编译器的"宽容"。
- 混淆 `co_yield x` 和 `co_yield std::move(x)`：前者不总是安全的，后者在 x 被多次 yield 时更危险。

### 提示

- 用 AddressSanitizer（`-fsanitize=address`）运行每个复现代码，它能捕捉至少一半的陷阱。
- 先重现、再截图崩溃信息、再读修复方案。不要反过来。
- 给每个陷阱写一个单文件复现，文件名如 `trap1_lambda_ref.cpp`。
- 陷阱 3（lock_guard）是工程中最隐蔽的——它常常不在开发环境崩溃，因为单线程测试恰好不触发线程切换。

## 练习 J-2：跨编译器 ABI 与符号问题

### 目标

同一份最小 task<T> 实现，分别在 MSVC、Clang、GCC 上编译，对比协程帧大小、HALO 触发情况、调试信息质量。尝试跨 DLL 传递 coroutine_handle 并观察崩溃。建立"协程 ABI 不是标准的一部分，跨编译器/跨模块传递 coroutine_handle 是危险操作"的清晰认知。

### 前置理解

- 你已经完成模块 F（协程帧与 allocator），知道 HALO 的触发条件和帧布局的基本概念。
- 你知道 C++ 标准没有规定协程帧的 ABI 布局、名字修饰（name mangling）规则、或异常处理在协程中的实现方式。
- 你知道 MSVC 使用 SEH（Structured Exception Handling）实现协程异常路径，Clang/GCC 使用 Itanium ABI 风格的表驱动异常。
- 你接受这题主要是观察与记录，不要求写出"跨编译器安全的协程库"。

### 必做任务

1. 准备一份最小但功能完整的 task<T> 实现（可从模块 D-1 练习题中复用），约 80-120 行，包含 `promise_type`、`initial_suspend`、`final_suspend`（symmetric transfer）、`return_value`、`unhandled_exception`。

2. 用同一份源码，分别在三个编译器上编译：
   - MSVC 17.10+（`/std:c++latest /O2`）
   - Clang 17+（`-std=c++23 -O2`）

3. 对每种编译器，记录以下数据：

   | 指标 | MSVC | Clang | GCC |

   | 协程帧大小（空 body） |  |  |  |

   | HALO 是否触发（空 body，同步返回） |  |  |  |
   | HALO 是否触发（含 co_await） |  |  |  |

   获取帧大小：MSVC 用 `/d1reportSingleClassLayout`，Clang 用 `-Xclang -fdump-record-layouts`，GCC 用 `-fdump-tree-coro`。
   获取 HALO 信息：Clang 用 `-Rpass=coroutine-elide`，GCC 用 `-fdump-ipa-coro`。

4. 跨 DLL 实验：
   - 在一个 DLL 中定义一个返回 `task<int>` 的工厂函数。
   - 在 EXE 中调用该函数获取 task，然后 `sync_wait` 等待结果。
   - 观察：如果 DLL 和 EXE 使用不同编译选项（如 Debug DLL + Release EXE），是否正常工作。
   - 更危险的实验：在 DLL 中分配协程帧，将 `coroutine_handle` 通过函数参数传给 EXE，在 EXE 中 `destroy()`。观察是否崩溃 / 堆损坏。

5. 阅读三个编译器的协程帧生成汇编代码，对比：
   - 帧指针的传递方式
   - promise 在帧中的偏移量
   - resume 时的寄存器保存/恢复策略

6. 在笔记中写出你的核心结论：
   - 为什么协程 ABI 不在标准内
   - 跨 DLL 传递 coroutine_handle 的具体风险

### 验收点

- 你填完了至少两份对比表（帧大小 + HALO 触发）。
- 你亲自跑过了跨 DLL 传递 coroutine_handle 的实验，且能解释为什么崩溃（或为什么不崩溃但不可靠）。
- 你能用一句话解释"为什么协程 ABI 不在标准内"：因为帧布局、名字修饰、异常处理实现都是编译器的私有选择，标准化它们会锁死所有实现方的优化空间。
- 你能为团队制定一条规则：不允许在 DLL 边界上暴露 coroutine_handle 或依赖协程帧布局兼容性。

### 观察点

- 三个编译器的协程帧大小差异通常在 20%-50% 之间。这不是 bug，而是每个编译器对"最小帧"和"对齐策略"的选择不同。
- HALO 是优化而非保证。即使你的代码今天触发了 HALO，下一版编译器或一行新增的局部变量都可能打破前提条件。
- 跨 DLL 的 coroutine_handle 崩溃本质上和"跨模块 delete 由不同堆分配的指针"是同一类问题：生命周期所有者和释放者的堆上下文不一致。
- MSVC 的调试信息对协程支持最好（Parallel Stacks 原生展示协程调用链），Clang/GCC 在 GDB 14+ 上也有显著改善。

### 常见坑

- 以为"只要能编译通过"就意味着 ABI 兼容——协程帧是完全的编译器内部实现，标准不保证任何跨编译器的兼容性。
- 在 DLL 接口中暴露 `coroutine_handle<>` 作为参数类型。
- 误认为 HALO 是协程的"默认性能特征"，在性能预算中依赖它。
- 用 `sizeof(task<int>)` 推测协程帧大小——task 通常只持有一个 `coroutine_handle<void>` 指针（8 字节），帧大小远大于此。

### 提示

- 先在一个编译器上跑通全部实验，再扩展到另外两个。
- 帧大小对比时，确保三个编译器使用相同优化级别（O2）和相同 C++ 标准版本。
- 跨 DLL 实验用一个很小的 task（如 `task<int>` 只 co_return 42），减少干扰因素。
- 如果你只有 MSVC 环境，至少完成 MSVC 的帧大小分析和 HALO 观察，再阅读网络上其他人的 Clang/GCC 对比数据。

### 复盘问题

- 如果让你设计一个"跨模块安全的协程包装"，你会禁止哪些操作、封装哪些接口？
- 为什么标准委员会选择不标准化协程 ABI，而标准化了 coroutine_handle 的接口？
- HALO 是协程独有的优化吗？在其他语言（Rust async、C# async）中是否有等价物？
- 跨 DLL 传递 coroutine_handle 和跨 DLL 传递 `std::unique_ptr<T>`（自定义 deleter）有什么本质相似性？

### 对应官方参考

- Microsoft "Debugging C++ coroutines" 官方文档
- GDB 14+ 协程支持文档
- P0912R5（协程帧与 allocator 提案）
- Clang `-Rpass=coroutine-elide` 文档
- GCC `-fdump-tree-coro` / `-fdump-ipa-coro` 文档

## 练习 J-3：协程调试与 tracing

### 目标

用 GDB 14+ / MSVC Parallel Stacks 调试挂起的协程，并实现一个轻量 awaiter wrapper 在 await_suspend / await_resume 时自动打 trace，建立"协程调试不是玄学，有章可循"的信心。

### 前置理解

- 你已经知道协程挂起后，普通调用栈（backtrace）中看不到协程的"逻辑调用链"。
- 你知道 coroutine_handle 可以通过 `handle.address()` 获取帧地址，帧中包含了 promise 和局部变量。
- 你理解在协程调试中，你需要同时追踪"物理线程栈"和"协程逻辑链"两层信息。
- 你接受这题的重点是建立调试能力，而不是写一个生产级 tracing 框架。

### 必做任务

1. 在 MSVC（Visual Studio 2022+）中，创建一段包含 3 个嵌套协程调用的程序：
   ```
   task_c() -> task_b() -> task_a()
   ```
   在 task_a 内部 co_await 一个永远不 ready 的 awaitable（模拟挂起），然后在调试器中暂停。使用 Debug > Windows > Parallel Stacks 选择 "Tasks" 视图，观察协程调用链的展示。截图并标注：物理线程 vs 协程逻辑链。

2. 在 GDB 14+（Linux / WSL）上，用相同程序验证：
   ```
   (gdb) info coroutines
   (gdb) bt
   ```
   观察 GDB 是否能展示协程的调用者-被调用者关系。

3. 实现一个 `traced_awaitable<InnerAwaitable>` 包装器：
   ```cpp
   template <typename Inner>
   struct traced_awaitable {
       Inner inner_;
       const char* name_;
       void* frame_addr_ = nullptr;

       bool await_ready() { return inner_.await_ready(); }

       auto await_suspend(std::coroutine_handle<> h) {
           frame_addr_ = h.address();
           // trace: 协程挂起
           log("SUSPEND", name_, frame_addr_);
           return inner_.await_suspend(h);
       }

       auto await_resume() {
           // trace: 协程恢复
           log("RESUME", name_, frame_addr_);
           return inner_.await_resume();
       }
   };
   ```
   其中 `log()` 函数输出时间戳、awaitable 名称、协程帧地址、当前线程 ID。

4. 把 traced_awaitable 应用到一段至少包含 3 个 co_await 点的协程，运行并输出 trace 日志。日志中应该能清楚看到：
   - 每个 awaitable 在什么时间挂起/恢复
   - 恢复发生在哪个线程上
   - 哪个帧地址对应哪个协程实例

5. 扩展：实现一个 `traced_task<T>` 包装，在 promise 的 `initial_suspend` 和 `final_suspend` 中也打 trace，标记协程的创建与销毁。

6. 用 trace 日志回答以下问题：
   - 你的程序中有多少协程同时处于挂起状态？
   - 哪些 co_await 点是最长的等待点？
   - 有没有同一个协程在不同线程上恢复的情况？

### 进阶任务

- 实现一个全局协程注册表（`std::unordered_map<void*, CoroutineInfo>`），以帧地址为 key，记录协程名、创建时间、当前状态（运行/挂起/销毁），用于运行时查询"当前有哪些协程在等待"。
- 用 perf / ETW 对比"有 tracing wrapper"和"无 tracing wrapper"的协程帧大小和运行时间，量化 tracing 的运行时开销。
- 实现 `traced_awaitable` 的编译期注入：通过 `promise_type::await_transform` 自动对所有 awaitable 包裹 tracing wrapper，通过编译宏控制在 Release 构建中去掉。
- 对比 folly 的 coroutine tracing 基础设施和你的实现，标注设计差异。

### 验收点

- 你至少在 MSVC 或 GDB 中成功观察过一次协程的逻辑调用链。
- 你的 traced_awaitable 能够输出清晰的 SUSPEND / RESUME 日志，包含协程标识和线程 ID。
- 你能解释为什么协程调试需要同时观察两层信息（线程栈 + 协程链）。
- 你知道 MSVC Parallel Stacks 中 "Tasks" 视图的原理：它通过帧链（frame chain）将协程的 resume 关系组织成树形结构。

### 观察点

- 协程挂起后，从线程的回调栈中只能看到最底层的等待点，看不到"谁在等我"——这就是 tracing 的价值。
- MSVC 的 Parallel Stacks 是截至 2025 年对协程调试支持最好的工具，它通过编译器生成的元数据重建协程树。
- GDB 14+ 引入的 `info coroutines` 命令是协程调试的重要基础设施，但功能仍不如 MSVC Parallel Stacks 丰富。
- tracing wrapper 的运行时开销主要在日志 I/O 本身（每次挂起/恢复约 100-500ns），帧地址记录几乎是零开销。

### 常见坑

- 在 `await_resume` 中做大量日志操作导致性能测试失真。
- trace 日志没有包含线程 ID，导致跨线程调度的协程 trace 无法分析。
- 全局注册表没有用线程安全的数据结构，在多线程协程调度中产生数据竞争。
- 在析构函数中访问已经被移除注册的协程帧，导致 use-after-free。

### 提示

- 先用 `std::cerr` 或 `OutputDebugStringA`（Windows）输出简单 trace，确认逻辑正确后再换更高效的日志库。
- tracing wrapper 的 `name_` 字段在 Debug 模式下用 `__PRETTY_FUNCTION__`，Release 模式下用手写字符串常量。
- 如果日志量太大，给 traced_awaitable 加一个按帧地址过滤的开关。
- 不要在 tracing wrapper 的内存分配路径上再加 trace——这会形成无限递归。

### 复盘问题

- 为什么传统的 backtrace 对于协程调试不够用？
- MSVC Parallel Stacks 的协程视图在什么条件下能正常工作（需要编译器生成什么元数据）？
- 如果让你设计一个生产环境的协程 tracing 系统，你会怎么权衡"信息密度"和"性能开销"？
- tracing wrapper 也能帮助发现 J-1 中的哪些陷阱？为什么？

- Microsoft "Debugging C++ coroutines"（官方文档）
- GDB 14+ "info coroutines" 手册
- folly/experimental/coro 中的 tracing 基础设施

## 做完模块 J 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- C++ 协程的八个经典陷阱中，五个和"引用/指针生命周期跨越 co_await"有关。协程的核心风险不是语法，而是对象存活期模型和编译器实现细节的交互。
- `lock_guard + co_await` 是 UB，因为 co_await 恢复时的线程可能与获取锁的线程不同。替代方案是在 co_await 前释放锁。
- coroutine_handle 不能安全地跨 DLL 传递，因为协程帧的堆分配和销毁必须在同一个堆上下文中。协程 ABI 不在标准内是设计选择而非缺陷。
- HALO 是优化而非保证。依赖 HALO 作为性能假设，等于绑定在特定编译器版本和特定代码形状上。
- 调试协程需要同时追踪"物理线程栈"和"协程逻辑链"两层。MSVC Parallel Stacks 和 GDB 14+ `info coroutines` 是目前最佳的工具支持。
- traced_awaitable 是协程调试的基础设施，实现简单但价值很高。在 await_suspend / await_resume 自动打 trace 可以回答"谁在等谁、等了多久、在哪个线程恢复"。
- 模块 J 是第三阶段的"工程必修课"。协程语法学起来快，但把这些陷阱都踩一遍才算真正毕业。
