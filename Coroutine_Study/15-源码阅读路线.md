# 15 源码阅读路线

这份路线把 34 个独立练习和 3 个项目接到真实源码。读源码的目标是把“练习里的对象角色”映射到工业库：promise、awaiter、operation state、receiver、scheduler、frame、continuation、scope、cancel token。

读任何协程源码前，先固定六个问题：

1. 这个类型是 lazy 还是 eager？谁启动它？
   **答案解析：** 先看 `initial_suspend()`：本课程 `lazy_task` 和 `mini_ref::task` 都返回 `std::suspend_always`，所以调用协程函数只创建返回对象和 frame，启动点在 `sync_wait`、父协程 `co_await` 或 sender operation 的 `start`。Asio `co_spawn(ctx, awaitable, token)` 则把 awaitable 提交给 `io_context` executor，真正推进发生在 `ctx.run()` 调度 handler 时。判断步骤是先找 `initial_suspend`，再找第一个外部 `resume/start/co_spawn/run`。
2. 协程帧由谁拥有，谁 destroy？
   **答案解析：** 先找返回对象或 operation state 里保存的 `coroutine_handle`，再找析构函数、scope join 或 completion handler。课程 `lazy_task` 拥有一个 frame，析构时 `destroy()`；`mini_ref::task` 也由 task 对象持有 handle，`sync_wait(task<T>)` 按值接收 task 后在函数结束时释放 owner；Asio frame 由 `co_spawn` 创建的内部 operation 和 completion token 管理，`use_future` 给调用方一个可等待的完成入口。判断步骤是画出 handle 从 `get_return_object()` 到析构/完成回调的路径，区分“保存 handle”和“拥有 frame”。
3. `initial_suspend` 和 `final_suspend` 返回什么？
   **答案解析：** `initial_suspend` 决定协程体是否立即执行；`final_suspend` 决定完成后如何通知等待者或外部 receiver。课程 `lazy_task` 的 `initial_suspend` 是 `suspend_always`，`final_suspend` 返回自定义 final awaiter，按 continuation 或 `sync_wait` 通知恢复等待方；`mini_ref::task` 同样在 final awaiter 中处理 continuation、stopped 和完成通知；Asio awaitable 的这些细节藏在库实现里，要从 `use_awaitable/co_spawn` 的 frame 实现追。判断步骤是先读两个 suspend hook 的返回类型，再追 `final_awaiter::await_suspend`。
4. `co_await` 经过 `await_transform`、成员 `operator co_await` 还是 ADL？
   **答案解析：** 先从当前协程 promise 查 `await_transform`，找到就看它返回的对象；然后查成员或非成员 `operator co_await`；最后才把表达式本身当 awaiter。课程 H1/H3 通过 promise `await_transform(sender)` 把 sender 变成 `sender_awaitable`，H3 又用 `await_transform(my_task&&)` 限定自家 task 的 await 路径；普通 `lazy_task` 直接提供 awaiter 路径；Asio 的 `async_read(..., use_awaitable)` 由 completion token 生成可等待操作。判断步骤是按语言查找顺序写下“原始表达式 -> 转换对象 -> 三方法对象”。
5. value/error/stopped/cancel 分别走哪条通道？
   **答案解析：** 课程 `lazy_task` 把 value 存在 promise 的 result，异常存在 `exception_ptr` 并在 `await_resume/sync_wait` 重抛；`mini_ref` 额外把 stopped 表达成 `std::optional` 为空或 stopped completion；stdexec sender 明确区分 `set_value/set_error/set_stopped`；Asio 常见路径用 `error_code`、异常或 `as_tuple` 返回错误，RPC reference 用 `std::expected<response, error>` 表达 timeout、protocol、connection_lost、server_error。判断步骤是找 result storage、`unhandled_exception`、receiver completion signatures、stop token/cancel frame，以及 `await_resume` 如何把它们交给调用方。
6. completion 后恢复哪个 continuation，在哪个 scheduler 上恢复？
   **答案解析：** 先找 `await_suspend` 保存的 continuation，再找 completion 或 `final_suspend` 调用谁的 `resume`。课程 `lazy_task` 在 child awaiter 中保存 caller，child `final_suspend` 返回 caller；`sync_wait` 路径保存一个完成通知函数并唤醒阻塞线程；`mini_ref` 在 task、when_all、when_any 中保存 parent continuation；Asio completion 在对应 executor 上恢复 awaitable，单线程 `io_context::run()` 下 handler 顺序执行，多线程 run 时要看 strand 或共享状态保护。判断步骤是标出 continuation 字段、恢复调用点和 scheduler/executor 来源。

## 第一阶段后：A-C / Capstone1

你刚学完 `std::generator`、`lazy_task`、callback awaiter、`stop_token`、`when_all/when_any`、`async_scope`。此时读源码只看形状。

### `std::generator` / libstdc++ generator

带着 A-1/B-1 的问题读：`co_yield` 如何把值交给 iterator？递归 generator 为什么需要 active stack？`final_suspend` 为什么要恢复上一个 active generator？

读法：

- 找 `promise_type::yield_value`，看保存的是值、引用还是 view。
- 找 `begin()`，看第一次 resume 发生在哪里。
- 找 `iterator::operator++`，看推进 generator 时如何 resume。
- 找 `final_suspend`，看递归 yield 结束后如何回到 caller。

读完后回答：消费者保存 `operator*` 得到的引用到下一次 `++it` 之后是否安全？答案要来自源码保存策略。

**答案解析：** 跨下一次 `++it` 的安全性取决于被引用对象的实际生命周期和更新方式。推进会继续执行 producer，可能结束当前 yield 的临时对象、重建当前值槽，或修改仍存活的局部变量；这些情况下旧引用可能悬空，或已经观察到另一个值。如果 generator 产出的是外部长寿数组元素的引用，数组仍有效且未发生使引用失效的操作，该引用也可以继续有效。阅读时追踪 `yield_value` 保存的对象与递增后的存活路径；若要保存“这一次产出的旧值”，应当按值保存快照。

### cppcoro `task.hpp` / `sync_wait.hpp`

带着 A-2/B-2/G-3 的问题读：lazy task 如何从普通 `main()` 启动？`sync_wait` 如何把“异步完成”转成阻塞等待？

读法：

- 找 task 的 `initial_suspend`，确认是否 lazy。
- 找 task awaiter 的 `await_suspend`，看它如何保存 continuation。
- 找 `final_suspend`，看 completion 如何唤醒等待者。
- 找 `sync_wait` 内部 receiver 或 event，确认异常如何重新抛出。

读完后回答：如果 task 从未被 await/sync_wait，它的协程体会不会运行？谁负责销毁 frame？

**答案解析：** 本仓库固定的 cppcoro 版本中，[task.hpp](https://github.com/andreasbuhr/cppcoro/blob/8642e98596a92be30a2b061d3ed306d959d3214e/include/cppcoro/task.hpp) 的 `initial_suspend()` 返回 `suspend_always`，所以未被等待的 task 保持初始挂起，协程体尚未运行。持有非空 handle 的 `task` 返回对象在析构时调用 `destroy()`，这也负责释放从未启动的 frame。[sync_wait.hpp](https://github.com/andreasbuhr/cppcoro/blob/8642e98596a92be30a2b061d3ed306d959d3214e/include/cppcoro/sync_wait.hpp) 则创建内部等待 task，执行 `task.start(event)`、`event.wait()`，最后通过 `task.result()` 消费结果或重抛异常。

## 第二阶段后：D-G / Capstone5 core

你已经能手写 promise hook、awaiter 三层、frame allocator、HALO、shared_task、when_all、sync_wait。此时开始读对象关系。

### cppcoro `shared_task.hpp`

带着 G-1 的问题读：多个 awaiter 如何挂到同一个结果上？

读法：

- 找共享 state 的引用计数或 handle 所有权。
- 找等待者链表，确认多 awaiter 如何入队。
- 找完成路径，确认结果如何缓存，后来的 awaiter 是否同步拿结果。
- 找异常缓存方式。

读完后回答：第一个 awaiter 和第二个 awaiter 的 `await_suspend` 路径有什么不同？

**答案解析：** 第一个 awaiter 通常负责启动 producer 或把共享 state 从 idle 推到 running，并把自己的 continuation 挂入等待者结构。第二个 awaiter 看到 state 已经运行时只登记等待者；如果结果已经完成，它会走 ready 快路径或同步恢复，直接从缓存读取 value/error。

### cppcoro `when_all.hpp`

带着 C-2/G-2 的问题读：N 个 child task 如何汇合？

读法：

- 找 tuple/variant 结果 storage。
- 找 atomic countdown 或 completion counter。
- 找第一个异常如何记录。
- 找所有 child 完成后恢复 parent 的位置。

读完后回答：一个 child 抛异常时，其他 child 会继续跑、被取消，还是只在最终 await_resume 抛出？按源码版本回答。

**答案解析：** 本仓库固定 cppcoro 版本的 [when_all.hpp](https://github.com/andreasbuhr/cppcoro/blob/8642e98596a92be30a2b061d3ed306d959d3214e/include/cppcoro/when_all.hpp) 先通过 `when_all_ready` 启动并等齐输入。每个内部 `when_all_task` 保存自己的异常，其他 child 继续执行；这个组合器本身没有请求 sibling 停止的步骤。等齐后，`fmap` 在提取各 task 的 `result()/non_void_result()` 时遇到保存的异常并抛出；多个失败时，观察到哪个异常由结果提取路径决定。作为对照，课程 `mini_ref::when_all` 在左右 runner 中记录首个错误，同样等 `remaining_` 归零后恢复 parent，并由 `await_resume()` 重抛。

### `async_scope` / P3149 / P3296

带着 C-3 和 Capstone5 的问题读：scope 如何保证 spawn 出去的工作在作用域退出前 join？

读法：

- 找 `spawn` 如何把 operation state 注册到 scope。
- 找 `join` 或 `on_empty` 如何等待计数归零。
- 找 cancel source/token 如何进入 child。
- 找异常路径：child error 是否影响 sibling，scope 何时完成。

读完后回答：scope 析构时如果还有 child，源码选择 terminate、block、cancel+join，还是要求显式 join？

**答案解析：** 固定 cppcoro 版本的 [async_scope.hpp](https://github.com/andreasbuhr/cppcoro/blob/8642e98596a92be30a2b061d3ed306d959d3214e/include/cppcoro/async_scope.hpp) 要求先完成 `co_await scope.join()` 再析构 scope：join 登记 continuation，最后一个 child 使计数归零时恢复它。析构函数只断言曾登记 join 的 continuation，等待工作由 join 完成；析构本身不执行自动等待或取消。课程的 `mini_ref::task_scope` 采用另一项明确约定：`spawn` 增加 `in_flight_` 并在线程中等待 task，`wait_empty()` 等计数归零后 join 线程，再传播保存的错误；其 `noexcept` 析构调用 `wait_empty()`，捕获异常以完成清理。需要观察 child 错误时，应显式调用 `wait_empty()`。

## 第三阶段后：H-I-J / Capstone4

你已经接触 stdexec、Asio、io_uring/IOCP、Folly、Cobalt、cppcoro 和 RPC。此时读源码要按控制流和 completion channel 来读。

### stdexec `exec/task.hpp` 和 awaitable bridge

带着 H-1/H-2/H-3 的问题读：task 如何同时是 coroutine return object 和 sender？

读法：

- 找 task 的 completion signatures。
- 找 `connect(task, receiver)`，看 operation state 拥有什么。
- 找 task promise 如何保存 receiver environment。
- 找 sender-to-awaitable 适配，确认 `set_value/set_error/set_stopped` 如何映射到 `await_resume`。
- 找同步完成处理，确认是否存在防 reentrant resume 的握手。

读完后回答：`get_stop_token` 是从哪个 environment 读取的？`starts_on` 后 completion 在什么 scheduler 上交付？

**答案解析：** `get_stop_token` 要沿 task promise 保存的 receiver environment 或 operation environment 查找，H2 reference 只证明当前 stdexec task 能读到可停止状态。`starts_on(scheduler, sender)` 约束输入 sender 从该 scheduler 的 execution resource 启动；completion 后续在哪交付，还要继续看输入 sender 内部是否又用了 `continues_on`、`schedule_from` 或其它切换资源的 adaptor。

### Asio awaitable / `co_spawn`

带着 I-1/Capstone4 的问题读：completion token 如何把 callback 变成 coroutine resume？

读法：

- 找 `use_awaitable` 的 token handler。
- 找 awaitable frame 与 executor 的绑定位置。
- 找 `co_spawn` 如何处理 completion token：`use_future`、handler、detached 的差异。
- 找 cancellation state：`this_coro::cancellation_state`、`bind_cancellation_slot`、`operation_aborted`。

读完后回答：`co_spawn(..., use_future)` 和 `co_spawn(..., detached)` 在异常观察和 shutdown drain 上差在哪里？

**答案解析：** `use_future` 给调用方一个可等待的完成对象，异常会在 `future.get()` 中重新出现，也能作为 shutdown drain 的证据。`detached` 没有返回可观察 owner，异常处理和后台完成只能依赖额外 handler、scope、in-flight 计数或进程级协议；缺少这些补充机制时，shutdown 很难证明所有协程已经结束。

### liburing / Windows IOCP

带着 I-2 的问题读：kernel completion 如何把身份还给用户态？

读法：

- liburing：看 SQE/CQE，重点是 `user_data`、submit、wait、seen。
- IOCP：看 `OVERLAPPED*`、completion key、`GetQueuedCompletionStatus` 的成功和失败返回组合。
- 对照本仓库 awaiter：awaiter 何时写 continuation，何时写 result，何时 resume。

读完后回答：如果 completion 到达后先 resume 再 consume CQE，会给下一次提交留下什么风险？

**答案解析：** 恢复后的协程可能立刻提交下一次 SQE 或继续驱动 loop。旧 CQE 若尚未 `seen`，队列状态会混入已经处理但未消费的 completion，后续 pending 计数、CQ 空间和事件归属都更难保证。reference 先写 result、`io_uring_cqe_seen()`、再 resume，就是为了让协程恢复时看到的是已清理的 completion 边界。

### Folly `Task.h` / `SafeTask.h` / `AsyncScope.h`

带着 I-3/J-1 的问题读：大型代码库如何把生命周期风险放进类型和 scope？

读法：

- `Task.h`：找 executor 绑定、child task 继承 executor、final awaiter。
- `SafeTask.h`：看 `value_task`、`now_task`、`member_task`、`closure_task`、`co_cleanup_safe_task` 的注释和约束。
- `AsyncScope.h`：看 scope 如何注册任务、取消、join。

读完后回答：`now_task` 为什么要求立即 await？`async_closure` 解决的是哪类 lambda capture 风险？

**答案解析：** `now_task` 把安全窗口限制在创建它的 full-expression 内，避免协程对象被保存后才启动，导致引用参数或临时对象已经离开作用域。`async_closure` 把闭包和参数按库定义的安全方式绑定进协程执行，针对的是 lambda 捕获跨挂起后悬空、detached 启动后 owner 不清的问题。

### Boost.Cobalt

带着 I-4 的问题读：channel 和 race 如何表现协程间通信？

读法：

- 找 `channel` 的 read/write 等待队列。
- 找缓冲满/空时谁挂起。
- 找 `gather` 如何等待多个 awaitable。
- 找 `race` 的返回类型和 winner index 规则。

读完后回答：zero-buffer channel 的背压发生在哪里？producer 为什么不会 busy wait？

**答案解析：** 背压发生在 `channel.write` 的 await 点：零缓冲通道没有可用 reader 时，producer 协程挂起并把执行权交回 executor。它不需要循环检查条件，consumer `read` 到达后通道内部等待队列直接匹配双方并恢复 producer 或 consumer。

### Capstone4 RPC reference

带着工程问题读：一次 request 从 client 到 server 再回来，所有后台协程谁拥有？

读法：

- `frame/read_frame/parse_*`：确认协议边界。
- `queued_writer`：确认同一 socket 写入串行化。
- `client::call`：确认 pending、timer、retry、cancel frame。
- `client::read_loop`：确认 response 如何唤醒 call。
- `server::handle_connection`：确认 request handler、cancel map、writer。
- `rpc_reference_test.cpp`：确认 6 请求分布和 in-flight drain。

读完后回答：如果 client 超时后 response 晚到，代码如何避免完成一个已不存在的 pending？

**答案解析：** timeout 路径在 `client::call` 中先 `pending_.erase(req.id)`，再发送 cancel frame 并返回 timeout 或重试。晚到 response 进入 `client::read_loop` 后会执行 `pending_.find(resp->id)`；找不到 id 就 `continue` 丢弃，因此不会写已经释放的 pending state，也不会再次完成已返回的 call。

## 最终验收

读完这些源码后，拿任何一个协程库类型，都能在 5 分钟内画出：

- 返回对象和 promise 的关系。
  **答案解析：** 返回对象来自 `promise_type::get_return_object()`，通常持有或引用对应协程帧的 handle。promise 位于 frame 内，负责定义启动、完成、结果、异常和 await 转换；返回对象是外部拿到的所有权或消费入口。
- frame 创建、启动、完成、销毁路径。
  **答案解析：** 创建发生在调用协程函数时，启动由 `initial_suspend` 后的 resume、awaiter、`sync_wait` 或 operation `start` 触发。完成路径经过 `return_value/return_void/unhandled_exception` 和 `final_suspend`，销毁由 task、scope、operation state 或 runtime owner 调用 `destroy()`。
- value/error/stopped/cancel 的传播路径。
  **答案解析：** value 通常存入 promise/result storage 或走 receiver `set_value`；error 走 `exception_ptr`、`error_code`、`expected` 或 `set_error`；stopped 是 sender/receiver 独立通道；cancel 可能是 stop token、OS cancel、业务 cancel frame 或 pending 本地移除。读源码时要把“请求停止”和“已完成为 stopped”分开画。
- awaiter 或 operation state 的拥有者。
  **答案解析：** awaiter 常在协程帧中跨挂起存活；operation state 通常由等待方、组合器或 `connect` 结果拥有，并且必须活到 completion。任何 completion callback 保存的裸指针或 handle 都只是身份线索，不能替代 owner。
- scheduler/executor 切换点。
  **答案解析：** 切换点通常出现在 `schedule()`、`starts_on`、`continues_on`、`co_withExecutor`、Asio executor 绑定或 event loop 投递处。记录切换点时同时写出恢复线程和共享状态访问方式，才能判断是否还需要 strand、锁或消息化。
- shutdown 或 scope join 的收束证据。
  **答案解析：** 证据可以是 future 全部 `get()` 完成、scope `join()` 返回、in-flight 计数归零、pending map 清空、registry 为空或测试断言通过。只关闭 socket、发出 stop 请求或让函数返回，都不足以单独证明后台协程已经收束。

画不出来就回到对应练习。源码阅读的价值是建立坐标，文件名只是入口。
