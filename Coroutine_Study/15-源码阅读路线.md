# 15 源码阅读路线

## 这份文件怎么用

前面 14 个文件让你通过 30+ 道练习题、5 个结课项目，把协程从"会写 co_await"练到了"能独立实现 mini 协程库 + RPC 框架"。这份文件负责最后一步：带你走出去，看真正工业级的协程代码是什么样。

三阶段层层递进：
1. 第一阶段（模块 A-C）：用协程表达顺序异步和并发组合
2. 第二阶段（模块 D-G）：看见并亲手实现编译器变换、promise hooks、awaitable 三层、symmetric transfer、HALO
3. 第三阶段（模块 H-J）：对接 stdexec / asio / folly / cobalt，写 RPC 和 mini 库

这份源码阅读路线对应第三阶段尾声——你已经有了写库的能力，现在你要有能力读懂别人的库，并建立"库源码 <-> 你的练习"的对照坐标。

## 第一轮：只看形状，不抠细节

阅读顺序固定如下：

1. **cppcoro** `task.hpp` + `generator.hpp`
2. **libstdc++** generator 实现
3. **folly** `Task.h` + `SafeTask.h` + `AsyncScope.h`
4. **stdexec** `exec/task.hpp` + `__connect_awaitable.hpp`

第一轮只做三件事：

- 画出每个类型的 promise_type 有哪些 hook
- 标出 initial_suspend / final_suspend 的返回类型
- 标出协程帧的分配点（operator new / HALO 触发点）

不要一开始就陷进模板细节、SFINAE、或 executor 绑定逻辑。

## 第二轮：只补对象关系

第二轮再做下面这些事：

- 找出 `await_transform` 拦截了什么类型
- 找出 `final_suspend` 的 symmetric transfer 是怎么接起来的
- 找出 `unhandled_exception` 如何处理异常并传给等待者
- 找出 `get_return_object_on_allocation_failure` 的兜底策略
- 找出 allocated frame 的 `operator delete` 与 promise destructor 的调用顺序
- 找出 shared_task 的引用计数在什么时候 +1 / -1
- 找出 async_scope 如何管理 operation_state 的拥有关系

## 第三轮：对照论文，不对照语法糖

当你去看提案论文时，不要试图把每个 API 签名都逐条映射到当前编译器实现。第三轮只做：

- 对照对象角色（promise / handle / awaiter / frame / continuation）
- 对照调用阶段（创建 -> initial_suspend -> co_await -> yield -> final_suspend -> destroy）
- 对照 completion 传播思路（从内部 co_await 到外部 sync_wait）
- 对照 allocator 的设计意图（P0912R5 的 promise operator new 机制）
- 对照可观察效果（HALO / symmetric transfer / 取消传播）

## 推荐阅读问题清单（每文件统一 5 问）

每打开一个源码文件，都先回答：

1. 这个文件实现了几种协程类型？它们的 lazy/eager 策略分别是什么？
2. `final_suspend` 返回什么？为什么选择这个返回类型？
3. `await_transform` 拦截了什么？不拦截的默认行为是什么？
4. 协程帧的分配/释放由谁控制？有没有 HALO 的可能？
5. 如果在这个实现上叠加 cancellation，最自然的插入点在哪里？

## 学完之后下一步该练什么

如果你已经完成了全部三个阶段，推荐按这个顺序继续扩展：

1. **Coroutine frame pool allocator**：基于 P0912R5，实现一个针对协程帧优化的大小-类内存池。测量池化前后 100 万次 task 创建/销毁的分配次数和时间。
2. **awaitable I/O 框架**：把模块 I-2（io_uring/IOCP）扩展为一个通用异步 I/O 库。核心挑战：I/O 完成事件如何高效分发到等待者协程。
3. **Coroutine-friendly mutex（async_mutex）**：实现一个可跨 co_await 安全持有的互斥锁。关键设计：等待队列不是阻塞线程而是挂起协程。
4. **Channel（协程间通信）**：参考 Boost.Cobalt channel，实现 MPSC（多生产者单消费者）协程 channel，支持 backpressure。
5. **coroutine_handle 类型擦除**：设计一个无虚函数、无堆分配的类型擦除 wrapper，使不同类型的协程可以被统一管理（类似 `std::any` 但有 coroutine 语义）。
6. **编译期协程诊断工具**：基于 clang-tidy 或 clang AST plugin，实现一个检测"lock_guard 跨越 co_await"等协程陷阱的编译期检查器。
7. **对比其他语言**：如果你还写 Rust 或 C#，用 Rust async/await 和 C# async/await 分别实现相同的 RPC client/server，对比语言级别的协程设计差异。

不要反过来。先把三个阶段的全部练习做完、把源码读懂，再去加框架复杂度。

## 最后一句提醒

真正理解 C++ 协程，不是你会写多少 `co_await`，而是你能不能在一段协程代码里立刻指出：

- 帧在哪里
- 挂起点在哪里
- 谁在等谁
- 异常会怎么走
- 取消会怎么传
- 内存由谁分配由谁释放

如果这六件事都能快速指出来，这套练习就已经达到了目的。
