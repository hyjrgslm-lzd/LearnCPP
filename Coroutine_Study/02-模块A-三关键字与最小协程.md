# 02 模块 A：三关键字与最小协程

## 模块目标

这个模块只做一件事：把 C++20 协程的三个关键字——`co_yield`、`co_return`、`co_await`——从"只见过语法"变成"能亲手写出对应的最小协程"。

你会先写一个最简单的 `std::generator<int>`（C++23），感受 `co_yield` 的惰性语义；然后使用仓库共享的 `coroutine_study::lazy_task<T>`，感受 `co_return` 如何让协程产生一个可以稍后取走的值；最后给 `std::future<T>` 写一个最小 awaiter，亲手体验 `await_ready / await_suspend / await_resume` 三方法。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- `co_yield` 为什么是惰性的——generator 在迭代器推进时才 resume。
- `co_return` 的值是通过 promise_type 的 `return_value` / `return_void` 传递给返回对象的。
- `co_await` 的挂起和恢复不是魔法，而是 awaiter 三方法（`await_ready`、`await_suspend`、`await_resume`）的协作结果。
- 协程的 `coroutine_handle` 是一个轻量句柄，它不是协程本身，但它控制着协程的生杀大权。

## 使用约定

- 本模块仅使用 C++23 标准库 `<generator>`。不需要安装任何第三方库。
- 练习题 A-2 需要的 `lazy_task<T>` 已放在 `Coroutine_Study/exercises/include/coroutine_study/lazy_task.hpp`，练习中直接包含并使用共享实现。
- 每道题先写最小可观察版本，再做"进阶任务"。
- 所有日志都建议打印：阶段名、协程标识、执行线程 ID。

## 练习 A-1：第一个 generator

### 目标

用 `std::generator<int>` 写一个斐波那契数列生成器和一个按行 yield 文本的生成器，配合 `std::views::take` 消费，亲手感受 `co_yield` 的惰性语义。

### 前置理解

- 你知道 `std::generator<T>` 是 C++23 标准库提供的协程 generator 类型，包含在 `<generator>` 头文件中。
- 你知道 `co_yield expr` 会挂起当前协程，把 `expr` 的值传递给 generator 的调用方（即迭代器的 `operator*`）。
- 你理解 generator 的每次 `++it` 都会恢复协程并执行到下一个 `co_yield`。
- 你接受本题的重点是验证惰性，不是实现高性能数列算法。

### 必做任务

1. 写一个 `fibonacci()` 函数，返回 `std::generator<int>`。协程体内用 `co_yield` 依次产出斐波那契数列的前 N 项（N 由函数参数指定）。
2. 在 `main()` 中用 `std::views::take` 消费这个 generator 的前 10 项。注意不要把 generator 构造成临时对象然后立即让临时析构（generator 的析构会销毁协程帧）。
3. 在协程体内，每次 `co_yield` 前后各加一行日志（打印当前数列值和协程阶段的序号），观察执行顺序。
4. 在 `main()` 的迭代循环中，每次取下一个值之前和之后也各加一行日志。把两边的日志对比，确认：迭代器不推进，协程体就不继续执行。
5. 再写一个 `read_lines()` 函数，返回 `std::generator<std::string>`。协程体模拟"逐行读取"——用 `co_yield` 逐行产出 5 到 8 条模拟的文本行。
6. 用 range-based for 循环消费这个 generator，打印每行内容和行号。
7. 画一张生成器执行时序图：标注协程创建点、每次 `co_yield` 挂起点、每次迭代器 `++` 恢复点、协程 final_suspend 销毁点。

### 进阶任务

- 让 `fibonacci()` 变成一个无限生成器（去掉了 N 的限制），然后用 `std::views::take` 截取前 15 项。观察：generator 允许无限惰性序列，只要迭代器不越过边界。
- 写一个 `filter_even()` 辅助函数，接收一个 `std::generator<int>` 的右值引用，用 `co_yield` 只产出其中的偶数。观察：协程 generator 可以被另一个协程 generator 包装（coroutine composition）。
- 把 `read_lines()` 改造成按"段" yield——每个段是 3 行文本拼在一起。观察 `co_yield` 可以产出任意类型和大小，不限于基本类型。

### 验收点

- 你能在日志里看到：main 的循环打印在前，协程体的 co_yield 前打印在后；迭代器不推进，协程体不运行。
- 你能解释为什么 generator 对象（含有协程帧）不能作为临时对象立即析构。
- 你能画出从 `auto gen = fibonacci(10)` 到 `for (auto v : gen)` 这条链上，协程帧什么时候创建、什么时候第一次 resume、每次 co_yield 后谁在等谁。

### 观察点

- `co_yield` 的本质是把"生产者"和"消费者"的执行交织在一起：每次消费者请求下一个值，生产者才执行到下一个 `co_yield`。
- generator 的迭代器 `begin()` 是触发第一次 resume 的时刻。如果你从来不调用 `begin()`，协程体一行都不会执行。
- 如果没有 `views::take`，无限 generator 会在 range-based for 循环中永远跑下去（直到你按 Ctrl+C）。

### 常见坑

- 把 `fibonacci(N)` 直接写在 range-based for 的表达式里：`for (auto v : fibonacci(10))` 没问题，但 `for (auto v : some_transform(fibonacci(10)))` 要注意 generator 临时对象的生命周期——如果临时 generator 在外层表达式结束前析构，迭代器就会引用已销毁的协程帧。
- 在 `co_yield` 前后加了 `std::cout` 但在 main 端没对应加日志，导致看不出交替执行的时间线。
- 把 `co_yield` 理解成 `return` 的变体，以为协程就此结束。实际上 `co_yield` 之后协程还在，下次 resume 就从 `co_yield` 下一行继续。

### 提示

- 斐波那契数列的前两项可以用 `co_yield a; co_yield b;` 手动写，然后用循环 `co_yield a + b`。
- 日志的内容可以把"线程 ID + 协程内/外标记 + 步骤序号"组合起来，一眼能看出上下文切换。
- 如果你想让日志更清楚，可以写一个小工具函数 `log(const char* tag, int val)` 统一格式。
- generator 的惰性最适合用断点观察：在协程内部的 `co_yield` 和 main 循环的 `for` 行各设一个断点，单步执行直观感受交替。

### 复盘问题

- `co_yield expr` 在语义上等价于哪两步的组合？（提示：想想 `co_await promise.yield_value(expr)`）
- 为什么 generator 的迭代器被设计成 input_iterator（只能单遍遍历），而不是 forward_iterator？
- 如果你需要把 generator 的结果存起来多次遍历，你会怎么做？
- 这题中，协程帧在什么时候被销毁？谁负责销毁？

### 对应官方参考

- cppreference：`std::generator<T>`
- P2502R2：`std::generator` 标准提案
- Lewis Baker 协程系列第 2 篇：Generator 的实现原理

## 练习 A-2：co_return 与 lazy task

### 目标

使用仓库共享的 `coroutine_study::lazy_task<T>`，写一段三步值变换的协程，用 `co_return` 产出最终结果，并在 main 中通过 sync 方式取走值。体会 lazy task 的"创建时不执行，被 await 或 sync_wait 时才执行"与普通函数的区别。

### 前置理解

- 你理解 `co_return expr` 会调用 `promise.return_value(expr)`。
- 你知道 lazy task 的核心特征是 `initial_suspend` 返回 `suspend_always`，使得协程在创建后立即挂起，由调用方决定何时第一次 resume。
- 你接受本题的 `lazy_task<T>` 是一个教学用共享实现：它足够支撑 A-C 与第一阶段结课，但仍不是生产 task（没有通用调度器、完整取消传播、allocator 策略等）。

### 共享 lazy_task<T> 运行时契约

本题不要复制旧版短代码。直接使用仓库头文件：

```cpp
#include <coroutine_study/lazy_task.hpp>

coroutine_study::lazy_task<int> compute_async(int x);
auto result = coroutine_study::sync_wait(compute_async(5));
```

共享实现有几条必须理解的契约：

- `initial_suspend()` 返回 `std::suspend_always`，所以创建 task 时协程体不执行。
- `final_suspend()` 负责通知等待者，协程帧不会在结果被消费前自动消失。
- `lazy_task<T>` 是 move-only、single-consumer；`sync_wait` 和 `co_await` 都通过右值消费 task。
- `coroutine_study::sync_wait(std::move(task))` 拥有 root task，只启动一次，然后等待 `final_suspend` 或等价完成通知。不要把“循环 resume 任意协程”当成通用 `sync_wait` 设计；只有专门的 manual coroutine 练习才手动逐步 resume。

### 必做任务

1. 包含 `coroutine_study/lazy_task.hpp`，写一个协程函数 `compute_async(int x)`，返回 `coroutine_study::lazy_task<int>`。
2. 协程体内做三步值变换：
   - 第一步：`int step1 = x + 10;`
   - 第二步：`int step2 = step1 * 2;`
   - 第三步：`int step3 = step2 - 5;`
   - 最后 `co_return step3;`
3. 在每一步前后都加日志（打印步骤名和当前值）。
4. 在 `main()` 中调用 `compute_async(5)`，拿到一个 `lazy_task<int>` 对象。在这一行前后加日志，确认 task 创建后协程体是否立即执行。
5. 然后调用 `coroutine_study::sync_wait(std::move(task))` 取走结果，打印最终值。
6. 再写一个普通函数 `int compute_sync(int x)` 做完全相同的三步计算。对比两种写法的日志输出顺序。
7. 画一张协程帧状态图：标注 initial_suspend 挂起点、协程体三步、final_suspend 挂起点、sync_wait 的 resume 入口。

### 进阶任务

- 在协程体三步之间（比如第一步后）插入一个能自行完成并恢复的 awaiter。观察 root task 只由 `sync_wait(std::move(task))` 启动一次，后续恢复由 awaiter、事件循环或 final-suspend 通知链负责。
- 把 `compute_async` 的输入从 `int` 换成结构体 `Request{int id; double payload;}`，`co_return` 也换成结构体 `Response{int id; double result;}`。验证 lazy_task 对非平凡类型的支持。

### 验收点

- 你能用日志证明：`auto task = compute_async(5)` 这一行不触发协程体的执行。协程体的所有日志都出现在 `sync_wait(std::move(task))` 调用之后。
- 你能解释 lazy_task 的哪个设计点（`initial_suspend` 返回 `suspend_always`）导致了惰性启动。
- 你能说明 `co_return step3` 这个值是怎么通过 `promise.return_value` 最终到达 `sync_wait` 的返回值的。
- 你能解释为什么 lazy_task 必须禁止拷贝构造（协程帧所有权的唯一性）。

### 观察点

- lazy task 的"创建时挂起"与普通函数的"调用即执行"形成了最根本的差异。这个差异是后续所有协程设计的起点。
- `sync_wait` 在这里扮演的角色是"外部非协程世界中驱动协程执行并取走结果的入口"。在第一阶段，你要习惯"协程链的末端总有一个 sync_wait 或等价消费函数"。
- co_return 之后的 final_suspend 协程没有自动销毁帧——因为 `final_suspend` 返回了 `suspend_always`。帧需要被外部显式销毁（本代码中由 `sync_wait` 的 `handle_.destroy()` 负责）。

### 常见坑

- 把 `sync_wait` 写成 blind-resume 循环。它只适用于完全手动驱动的玩具 awaiter；真实异步 awaiter 可能由回调线程、事件循环或 symmetric transfer 恢复，外层循环再次 `.resume()` 会破坏状态机。
- 拷贝了 `lazy_task` 对象，导致两个 task 持有同一个 coroutine_handle，析构时 double-free。这就是为什么 task 必须禁止拷贝。
- 忘记在 `sync_wait` 中检查 `exception_`，结果协程体抛异常后消费者拿到的是空 `optional` 的 UB。
- 把 `co_return` 和普通函数的 `return` 语义混为一谈——在普通函数中 `return` 直接返回到调用方；在协程中 `co_return` 先走 `promise.return_value`，再走 `final_suspend`，执行流比普通 return 多两层。

### 提示

- 三步变换的计算本身不要太复杂，重点是观察执行时机的差异。
- 日志里打印 `__LINE__` 或阶段名，比打印值本身更能揭示执行顺序。
- 如果你的编译器对 C++23 `<generator>` 以外的协程特性支持有问题（比如 MSVC 17.10 之前的版本），先确保 `/std:c++latest` 和适当的协程支持 flag 已开启。
- 建议把 `lazy_task` 放在独立的 `.hpp` 文件中，A-3 和之后的练习都会用到。

### 复盘问题

- 如果把 `initial_suspend` 从 `suspend_always` 改成 `suspend_never`，协程体会在什么时候执行？这和普通函数的区别是什么？
- 如果把 `final_suspend` 从 `suspend_always` 改成 `suspend_never`，帧会在什么时候被销毁？`sync_wait` 中还能安全访问 `promise().result_` 吗？
- 为什么 `promise_type` 中的 `result_` 用了 `std::optional<T>` 而不是裸 `T`？这解决什么问题？
- `lazy_task` 的析构函数中调用 `handle_.destroy()` 的前提是什么？如果 `handle_` 已经被 `sync_wait` 中的 `destroy()` 置为 null 呢？

### 对应官方参考

- cppreference：`std::coroutine_handle`、`std::suspend_always`、`std::suspend_never`
- Lewis Baker 协程系列第 3 篇：`co_return` 与 promise_type 的交互
- cppcoro：`task.hpp` 中 `promise_type` 的定义

## 练习 A-3：co_await 一个 std::future

### 目标

给 `std::future<T>` 写一个最小包装 awaiter（`await_ready`、`await_suspend`、`await_resume` 三方法），让 `co_await as_awaitable(std::move(fut))` 可以消费 future 结果。这是你第一次亲手实现 awaiter 协议。不要给 `std::future` 本身添加成员，也不要向 `namespace std` 塞 `operator co_await`。

### 前置理解

- 你知道 awaiter 必须提供三个方法：`await_ready()`、`await_suspend(coroutine_handle)`、`await_resume()`。
- 你知道 `co_await expr` 不是直接调用这三个方法，而是经过了 awaitable 到 awaiter 的变换（三步查找或隐式转换）。
- 你了解 `std::future<T>` 可以通过 `std::async` 创建，它代表一个可能在另一个线程上运行的计算结果。
- 你接受本题的重点是 awaiter 三方法的行为，不是跨线程调度的性能优化。

### 必做任务

1. 写一个 `future_awaiter<T>` 模板类，接收一个 `std::future<T>`，实现 awaiter 三方法：
   - `await_ready()`：返回 `future.wait_for(0s) == std::future_status::ready`。如果 future 已经完成（通常不会，因为 async 要在另一个线程池跑），直接跳过挂起。
   - `await_suspend(coroutine_handle h)`：把等待工作提交给一个可 join 的 worker（例如 `std::jthread` 或本题 main 中持有的 worker_group）。worker 中调用 `future.wait()` 阻塞等待结果，然后调用 `h.resume()` 恢复协程。注意：此处 `h.resume()` 是从另一个线程调用的，这意味着协程的恢复点可能发生在不同于挂起点的线程上。
   - `await_resume()`：返回 `future.get()`——此时 future 已经 ready，`get()` 不会阻塞。
2. 写一个你自己命名空间内的包装函数或包装类型，例如 `future_awaitable<T> as_awaitable(std::future<T>&&)`，让调用点写成 `co_await as_awaitable(std::move(fut))`。`std::future` 的关联命名空间是 `std`，用户代码不能向 `std` 添加这种重载，因此不要追求裸写 `co_await some_future`。
3. 写一个测试协程 `test_future_await()`（返回 `lazy_task<int>`，使用 A-2 的头文件）：
   - 先 `auto fut = std::async(std::launch::async, []{ std::this_thread::sleep_for(100ms); return 42; });`
   - 再 `int result = co_await as_awaitable(std::move(fut));`（通过你写的 awaiter）。
   - 最后 `co_return result * 2;`。
4. 在 main 中使用 `sync_wait` 取走最终结果并打印。
5. 在 `await_suspend` 和协程体内分别打印当前线程 ID，确认跨线程 resume 确实发生了。
6. 画一张 awaiter 三方法的调用时序图：标注挂起点、`await_suspend` 中启动线程、新线程中 `wait()` 阻塞、新线程中 `h.resume()` 恢复协程、`await_resume` 取走值。

### 进阶任务

- 给 `future_awaiter` 加上 `std::stop_token` 版本（C++20 中 `std::future` 本身不直接支持，但你可以模拟一个包装），当 `stop_requested` 时提前从 `await_suspend` 返回而不等待 future 完成，协程走 exception 路径通过 `unhandled_exception` 通知调用方。
- 不要写裸 `future_awaiter` 类型，而是写一个轻量包装类型 `future_awaitable<T>`，由 `as_awaitable(std::future<T>&&)` 构造。思考：为什么 `std::future` 不能靠用户代码直接获得成员 `operator co_await` 或 `std` 命名空间自由重载？这揭示了 C++ 协程扩展点的边界。
- 把 `std::future<T>` 换成 `std::shared_future<T>`。两个问题需要注意：（1）`shared_future::get()` 返回的是 `const T&` 还是 `T`？（2）多个 `co_await` 同一个 shared_future 会发生什么？

### 验收点

- 你能在日志中看到 `await_suspend` 和协程体的恢复发生在不同线程上。
- 你能解释 awaiter 三方法各自在什么时候被谁调用。
- 你能说明为什么 `await_suspend` 中调用 `h.resume()` 是合法的——编译器保证此时协程已经暂停，帧是稳定的。
- 你能画出一张从 `co_await as_awaitable(std::move(fut))` 出发、经过 awaiter 三方法、最终到 `result` 获得值的完整数据流图。

### 观察点

- `await_suspend` 的语义不是"暂停协程"，而是"协程已经暂停了，现在你要告诉我接下来做什么"。你可以选择保存 handle 稍后 resume（本练习的做法），也可以选择返回另一个 handle 做 symmetric transfer，还可以返回 void/bool 让编译器决定。
- 跨线程 resume 意味着你的协程恢复点可能跑在与创建时不同的线程上。这对协程体内的 thread_local 变量、锁、以及任何依赖线程亲和性的代码都有深远影响。
- `await_resume` 的返回值就是 `co_await` 表达式的值。这是协程中"异步结果回到同步代码"的唯一通道。

### 常见坑

- 在 `await_suspend` 中启动裸 `std::thread` 后没有把它交给可 join 的所有者，导致 `std::thread` 析构时 `std::terminate`。本题不要使用 `detach()` 规避生命周期问题。
- 在等待线程还没确认 future ready 前就调用 `h.resume()`，导致协程恢复后 `await_resume` 中的 `future.get()` 可能阻塞，甚至与外层生命周期设计产生竞态。
- `future.wait()` 和 `future.get()` 的语义差异没分清：`wait()` 只等待，不取走值；`get()` 取走值（move），只能调用一次。所以等待线程里只做 `wait()` 并恢复协程，`await_resume` 才用 `get()`。
- 忘记处理 `await_ready` 返回 `true` 的短路情况——此时 `await_suspend` 不会被调用，协程不会挂起。如果 future 在 `co_await` 时就已经 ready（例如 `std::async` 以 `deferred` 模式启动但恰好在当前线程算完了），你的 awaiter 必须能处理这种路径。
- 使用 `std::async` 时未指定 `std::launch::async`，结果 library 选择了 `deferred` 策略，future 的 `wait()` 不会启动新线程，整个 await 变成了同步等待，观察不到跨线程效果。

### 提示

- 用来等待的线程可以用 `std::jthread`（C++20）或 main 中持有的 worker_group 管理；关键是拥有者退出前必须 join。
- 日志中打印 `std::this_thread::get_id()` 即可区分不同线程。
- 如果你发现 `future.wait_for(0s)` 总返回 ready（因为计算太快），可以把 `sleep_for` 加长（比如 500ms）或把计算换成更重的模拟工作。
- 本题的核心收获是 awaiter 三方法的真实体感，不要花太多时间在"跨线程细节做得多优雅"上。第二阶段你会写更规整的实现。

### 复盘问题

- 为什么 `await_suspend` 的参数是 `coroutine_handle` 而不是协程帧的裸指针？这个 handle 的价值在哪里？
- 如果在 `await_suspend` 中没有调用 `h.resume()` 而是把 `h` 保存在全局变量里，协程会怎样？这个全局 handle 的生命周期谁负责？
- 为什么说"awaiter 决定了协程的调度策略"？从本题看，如果 `await_suspend` 在新线程上 resume，那协程恢复就发生在那个线程上——这意味着什么？
- 如果 `future` 里的任务抛了异常，`future.get()` 会重新抛出。这个异常在协程体内 `co_await` 这行被抛出时，协程的 `unhandled_exception` 是否会被触发？请跟踪异常路径。

## 做完模块 A 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- `co_yield` 是惰性的——generator 在迭代器推进时才 resume 协程，执行到下一个 `co_yield` 又挂起。
- `co_return` 的值经过 `promise.return_value` 存储，再通过 `coroutine_handle` 交给外部消费者。
- `co_await` 不是魔法——它展开为 awaiter 的 `await_ready/await_suspend/await_resume` 三次调用。
- `initial_suspend` 选择 `suspend_always` 决定了 lazy 语义；`final_suspend` 选择 `suspend_always` 决定了帧不会自动销毁，由外部控制。
- `coroutine_handle` 是一个轻量句柄，`.resume()` 让它继续执行，`.destroy()` 释放帧内存。谁持有 handle 谁就对协程帧的生死负责。
- awaiter 的 `await_suspend` 是协程调度决策的枢纽——它可以保存 handle 稍后 resume（本模块），也可以返回 bool 或返回 coroutine_handle 做 symmetric transfer（后续模块）。
