# 05 第一阶段结课：异步小爬虫

## 这份文件怎么用

前面 9 道题（模块 A/B/C 各 3 道）把协程的局部能力拆开练了：三关键字、generator、lazy_task、stop_token 取消、when_all/when_any 组合、async_scope 收束。这份文件负责把这些能力重新拼成一个完整项目。

这个结课项目的重点不是业务真实度，而是让你同时管理：

- 串行异步阶段（co_await 链）
- 惰性数据生成（generator 按行解析）
- 并发组合（when_all 汇合多个 URL 结果）
- 取消传播（stop_token 超时控制）
- 结构化并发收束（async_scope 管理所有 flying task）

建议顺序：先把项目中涉及的所有协程对象画成一张调用图，再写代码。

## 结课项目：异步小爬虫

### 项目目标

实现一个"并发抓取 N 个 URL + 解析 + 汇总报告"的异步小爬虫。使用 `sleep_for` 模拟网络延迟，使用 `std::generator` 按行产出解析结果，使用 `when_all` 汇合所有 URL 的结果，使用 `stop_token` 实现整体超时，使用 `async_scope` 收束所有并发协程。

### 固定题面

输入是 N 个"URL"（用字符串模拟，实际不需要网络 I/O），输出是一份汇总报告。

每个 URL 的处理流程最少包含以下阶段：

1. **fetch**：模拟网络请求（用 `co_await async_sleep(delay)` 模拟不同延迟），返回原始响应字符串。
2. **parse**：用 `std::generator` 将原始响应按行 yield，惰性产出每行解析结果。
3. **aggregate**：将所有 URL 的解析结果汇总为一份报告。

### 必须包含的设计约束

1. **至少 3 类异步阶段**：fetch（co_await 延迟）、parse（generator 惰性 yield）、aggregate（when_all 合流）。三类阶段必须清晰地出现在代码中。
2. **至少 1 次 stop_token 检查**：在 fetch 阶段或整体协调器中，通过 `stop_token` 实现超时控制。当整体耗时超过阈值时，未完成的 fetch 应该被取消。
3. **至少 1 次 when_all 或 when_any**：并发发起所有 URL 的 fetch，用 `when_all` 汇合结果。
4. **必须用 async_scope**：所有并发 fetch 协程必须被 scope 管理。scope 析构前必须等齐所有 spawning task。禁止使用 `detach`、裸 `std::thread` 或全局可变状态来绕过生命周期管理。

### 推荐输入模型

为了把注意力留给协程结构，建议输入固定得非常小：

- 3~5 个 URL（用字符串常量模拟，例如 `"https://example.com/data/1"`...）
- 每个 URL 的内容是一个固定的小型 CSV 或日志行集合，内嵌在测试数据中，而非从真实文件或网络读取。
- 每个 URL 设定不同的模拟延迟（50ms / 150ms / 300ms 等），以观察并发效果。

例如：

```
URL: "data/1.csv"  -> 内容: "name,score\nAlice,85\nBob,92\n"  延迟: 150ms
URL: "data/2.csv"  -> 内容: "name,score\nCarol,78\nDave,88\n"  延迟: 100ms
URL: "data/3.csv"  -> 内容: "name,score\nEve,95\nFrank,82\n"   延迟: 300ms
```

### 推荐输出模型

最终报告至少包含：

- 成功 fetch 的 URL 数
- 超时/失败的 URL 数
- 总解析行数
- 每个 URL 的汇总统计（行数、解析耗时、状态）
- 整体耗时

示例输出格式：

```
=== 异步小爬虫报告 ===
请求 URL 总数: 3
成功: 2 | 超时: 1
总解析行数: 4
整体耗时: 165ms

URL: data/1.csv | 状态: 成功 | 行数: 2 | 耗时: 150ms
URL: data/2.csv | 状态: 成功 | 行数: 2 | 耗时: 100ms
URL: data/3.csv | 状态: 超时 | 行数: 0 | 耗时: -
```

### 必做任务

1. **画全局协程调用图**：在写代码之前，先画出所有协程对象之间的调用关系、co_await 链、when_all 合流点、scope 管理边界。
2. **实现 fetch 协程**：
   - 接收 URL（字符串）和 `stop_token`
   - 用 `co_await async_sleep(delay)` 模拟网络延迟
   - 在 await 之后检查 `stop_token`，如果被取消则提前返回部分结果或 stopped 标记
   - 返回一个包含 URL、原始内容、状态码的结构体
3. **实现 parse generator**：
   - 用 `std::generator` 接收原始响应字符串
   - 按行 `co_yield` 结构化记录（例如 `struct Record { std::string name; int score; };`）
   - 跳过空行，对格式错误的行产出错误标记但继续 yield
4. **实现 aggregate 协程**：
   - 用 `when_all` 汇合所有 fetch 结果
   - 对每个成功 fetch 的结果，用 generator 遍历解析行
   - 汇总统计信息
   - 用 `co_return` 返回最终报告结构体
5. **实现超时控制**：
   - 使用 `in_place_stop_source` + `stop_token`
   - 在整体协调器中设置超时阈值（例如 200ms）
   - 用另一个协程在超时后调用 `stop_source.request_stop()`
   - fetch 协程在下一个 `co_await` 点检查 token 并响应
6. **使用 async_scope 管理所有并发 fetch**：
   - 所有 fetch 协程通过 `scope.spawn()` 或等效方式启动
   - scope 析构前确保所有 spawn 的协程已结束
7. **输出最终报告**，并附上你在第 1 步画的协程调用图。

### 进阶任务

- 实现**优雅降级**：如果部分 URL 超时，仍然汇总已完成 URL 的结果，而不是整个报告失败。
- 增加**重试逻辑**：对于被取消的 URL，如果是因为超时而非内容错误，自动重试一次（使用更短的超时）。
- 用 `when_any` 替代超时协程：将 `when_all(all_fetches)` 和 `timeout_after(200ms)` 放入 `when_any`，竞速决定是全部完成还是超时。
- 将 parse generator 改为**递归 generator**：如果响应内容有层级结构（如 JSON 数组嵌套），用递归 generator 展开。
- 写一份 1 页小结：如果以后把这个项目接到真实 HTTP client（如 libcurl 或 asio），哪些协程结构可以直接复用，哪些需要重构。

### 验收点

- 你能在协程调用图上指出所有并发点、合流点、取消传播路径、scope 收束边界。
- 你能让超时的 URL 走 stopped 路径，而非抛异常覆盖整个报告。
- 所有协程帧的生命周期都有明确的拥有者（scope 或 task 的调用者）。
- 你没有使用全局可变状态来在协程之间共享数据。
- 你的 generator 正确惰性产出解析结果，没有一次性加载全部行到内存。
- 你能在不看代码的情况下，口头描述整个项目的协程拓扑。
