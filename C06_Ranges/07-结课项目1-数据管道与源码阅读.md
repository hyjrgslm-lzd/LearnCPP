## 结课项目 1：CPU 数据流水线

### 项目目标

把模块 A-D 的主要能力串起来，做一个完整但不复杂的 ranges 小系统。这个项目的重点不是业务真实度，而是让你同时管理：

- view 依赖图（多层嵌套 view 的对象关系）
- iterator_concept 分布（每层 view 的迭代器概念降级链）
- borrowed_range 判定（哪些层是借用，哪些层持有生命周期）
- projection 投影（用成员指针替换 lambda 的场合）
- 结构适配（join / split / chunk_by 改变 range 形状）
- `ranges::to` 收束（把惰性管道实体化为具体容器）
- 协程源（可选：用 `std::generator` 写惰性行产生器）

### 固定题面

实现"批量导入并汇总日志记录"的小型流水线。

**输入格式**（固定，每条记录是一行文本）：

```
timestamp,level,user_id,message
```

- `level` ∈ `{INFO, WARN, ERROR}`
- 允许少量非法行（字段数不足、level 不识别等）
- 不涉及文件 I/O，直接用 `std::string_view` 数组或 `std::istringstream` 模拟

**推荐输入示例**：

```cpp
// 可以放在 main 里，也可以用 std::generator（进阶）生成
std::vector<std::string_view> raw_lines = {
    "2024-01-01T00:00:01,INFO,alice,login ok",
    "2024-01-01T00:00:02,WARN,bob,disk usage 80%",
    "2024-01-01T00:00:03,ERROR,alice,connection refused",
    "2024-01-01T00:00:04,ERROR,carol,timeout",
    "INVALID_LINE_NO_COMMAS",
    "2024-01-01T00:00:05,INFO,bob,task complete",
    "2024-01-01T00:00:06,ERROR,alice,segfault detected",
    "2024-01-01T00:00:07,BADLEVEL,dave,unknown",
    "2024-01-01T00:00:08,WARN,carol,retry 2",
};
```

**输出格式**（最终汇总报告，至少包含）：

- 总条数 / 按 level 计数（INFO / WARN / ERROR）
- 按 user_id 分组计数
- 前 N 条（N=3）ERROR 记录的完整内容

### 必须包含的设计约束

每条约束对应一个模块的核心训练点，缺一不可：

1. **模块 A**：至少使用 3 个 view 工厂的组合。可选范围：
   `iota` / `istream_view` / `single_view` / `repeat_view` / `cartesian_product_view`。
   例如：用 `views::iota` 生成行号，用 `views::single` 包装分隔符，用 `views::repeat` 生成填充行。

2. **模块 B**：至少使用 `filter` / `transform` / `take` 三个基础 adaptor。

3. **模块 C1**：至少使用 `join` 或 `split` 或 `chunk_by`（C++23）中的一个结构适配器。

4. **模块 C2**：至少使用一次带 `projection` 的 `ranges::sort` 或 `ranges::max_element` 或 `ranges::count_if`。

5. **模块 C2**：至少使用一次 `ranges::to<container>` 把惰性管道收束为具体容器。

6. **模块 D**：至少一处使用 C++23 视图（`zip` / `chunk` / `stride` / `as_const` / `join_with` 等之一）。

7. **borrowed_range 显式标注**：至少一处显式写出 view 是否 borrowed，例如：
   ```cpp
   // iota_view 是 borrowed_range，迭代器有效性不依赖 view 对象本身
   static_assert(std::ranges::borrowed_range<decltype(std::views::iota(0, 10))>);
   // 含 filter_view 的管道不是 borrowed_range
   static_assert(!std::ranges::borrowed_range<decltype(raw_lines | std::views::filter(is_valid))>);
   ```

8. **（可选进阶）协程源**：用 `std::generator<std::string_view>` 写一个"每行一条记录"的惰性生产者，替换 `raw_lines` 数组作为输入。

### 推荐结构设计

在写代码之前，先画 view 依赖图。下面是一个参考结构（不要求完全照搬，但层次关系要清楚）：

```
输入源
  └─ raw_lines (vector<string_view> 或 std::generator)
       │  [contiguous_range / input_range]
       ├─ 解析阶段
       │    views::transform(parse_line)    → optional<LogRecord>
       │    views::filter(has_value)        → [iterator_concept 按底层裁顶到 bidirectional；普通 vector 底层 const filter 仍不可迭代]
       │    views::transform(*_)            → LogRecord
       │    // 底层是 vector（random_access）→ filter 裁顶到 bidirectional；
       │    // 底层若是 forward_list → filter 保持 forward；input 底层 → 保持 input。
       │
       ├─ 按 level 分组 / 计数
       │    ranges::count_if(is_error, &LogRecord::level)   ← projection
       │
       ├─ 按 user_id 分组
       │    views::transform(&LogRecord::user_id)
       │    ranges::to<std::unordered_map<...>>              ← 收束
       │
       ├─ 前 N 条 ERROR
       │    views::filter(is_error)
       │    views::take(N)
       │    ranges::to<std::vector<LogRecord>>               ← 收束
       │
       └─ 行号配对（C++23 zip）
            views::zip(views::iota(1), parsed_records)
```

**必须在图旁边标注每层的 iterator_concept 和 borrowed 状态。**

### 必做任务（7 项）

#### 任务 1：阅读 libstdc++ `filter_view`

文件路径（GCC 13）：`libstdc++-v3/include/std/ranges`，搜索 `class filter_view`。

阅读并标注以下六个要素：

- **模板参数**：`_Vp`（底层 view 类型）和 `_Pred`（谓词类型）
- **构造函数**：接受 viewable_range + pred，内部调用 `views::all` 规范化底层 range
- **`__non_propagating_cache` 缓存**：用于缓存第一个满足条件的 iterator 位置；
  之所以叫"non-propagating"，是因为拷贝构造 / 赋值时缓存不传播（重置为 nullopt）——
  这保证了 O(1) copy 的 view 语义公理（拷贝不触发 O(n) 扫描）
- **`begin()` 为何非 const**：内部需要向缓存写入，写入 = 非 const 操作
- **iterator 嵌套类**：定义在 `filter_view` 内部，持有对 `filter_view` 的指针和当前 iterator；
  `operator++` 实现为"找到下一个满足 pred 的位置"，即每次 `++` 都可能是 O(n) 扫描
- **sentinel 嵌套类**：持有底层 view 的 end sentinel；
  与 iterator 的比较通过 `it._M_current == _M_end` 实现

#### 任务 2：阅读 MSVC STL `filter_view`

文件：`_Ranges_v3.h` 或 `<ranges>` 实现部分（MSVC 把大部分 ranges 实现放在 `<yvals_core.h>` / `<ranges>` 内联实现文件中）。

对照 libstdc++ 标注同样六个要素，特别关注差异：

- 缓存结构：MSVC 使用 `_Optional_cache<_It>` 或 `optional<_It>` 的等价内部类型（命名不同但语义相同）
- 成员命名规范：MSVC 习惯用 `_Pred` / `_Range` 等前缀下划线命名，与 libstdc++ 的 `__` 双下划线不同
- iterator 的 `iterator_concept` 推导：两者规则相同，结果应一致——底层 bidirectional → bidirectional，底层 forward → forward，底层 input → input

#### 任务 3：阅读 range-v3 `filter.hpp`

文件：`include/range/v3/view/filter.hpp`

range-v3 早于 C++20 标准，记录它与标准库的以下差异：

- **缓存结构**：range-v3 使用 `cache1` 辅助类（不是 `__non_propagating_cache`），缓存语义类似但实现不同
- **基类**：range-v3 的 `filter_view` 继承自 `view_adaptor<filter_view<Rng,Pred>, Rng>`，而非 `std::ranges::view_interface<D>`——这是两套不同的 CRTP 注入机制
- **`const` 可迭代性**：range-v3 在某些情况下提供了 const begin()，通过额外的 const overload 和 mutable 缓存实现；标准库 C++20 原规范选择非 const begin；C++26 草案通过 P3725R3 增加了很窄的 const-input 分支，但普通 vector 底层 filter 仍不能 const 迭代
- **filter_view 继承链**：range-v3 不使用 view_interface，注入的默认成员来自 view_adaptor 和 range_facade；标准库的 view_interface 通过 CRTP 注入 `empty()` / `front()` / `back()` / `size()` 等便利成员

### 第一轮：只看形状

**阅读顺序**（固定）：

```
filter_view → transform_view → take_view → join_view
```

**第一轮只做三件事**：

1. 画 view 依赖图（模板参数里包哪个底层 view，iterator 嵌套在哪里）
2. 标注每层的 iterator_concept（底层 view 的 concept 如何影响本层）
3. 标注 borrowed 状态（本 view 是否有 `enable_borrowed_range` 特化）

**不要在第一轮做的事**：

- 不要追 `__non_propagating_cache` 的完整实现
- 不要追 `view_interface` 注入的每个成员
- 不要追 `operator|` 的 CRTP 基类

这四个 view 的关系：

- `filter_view`：最典型的缓存案例；C++20 主路径 begin 非 const，C++26/P3725R3 仅放开 const input range 特例；iterator_concept 有上界
- `transform_view`：最典型的透传案例，iterator_concept 随底层透传，const 可迭代性依赖函数对象
- `take_view`：最典型的"截断不降级"案例，对 sized + random_access 底层有特殊路径
- `join_view`：最典型的"两层状态"案例，外层/内层迭代器组合，上界 bidirectional

### 第二轮：只补对象关系

第二轮在第一轮基础上，逐一补充以下对象关系：

- **`__non_propagating_cache`**（libstdc++）或等价类型：找到它在 `filter_view` / `drop_while_view` 中的具体使用。理解为何拷贝时不传播缓存——拷贝传播缓存意味着"复制的 view 和原 view 指向同一个缓存位置"，但拷贝后的 view 可能基于不同的底层数据，缓存失效。
- **`view_interface` 注入的默认成员**：找到 `view_interface<Derived>` 的 CRTP 实现，标出它注入了哪些成员（`empty()` / `front()` / `back()` / `size()` / `operator[]`），以及每个成员依赖的底层 concept（`size()` 要求 `sized_range`，`back()` 要求 `bidirectional_range` 且 `common_range`）。
- **iterator 嵌套类的 friend 关系**：观察 `filter_view::_Iterator` 如何用 `friend class filter_view` 访问外层 view 的私有成员（谓词和缓存）。
- **sentinel 如何派生类型**：找到 `filter_view` 的 sentinel 类型，观察它如何只持有底层 view 的 end 位置，并通过 `operator==` 与 iterator 比较。
- **`operator|` 如何被 `range_adaptor_closure` 基类注入**（P2387R3）：找到 `range_adaptor_closure<Derived>` 的实现，找到 `operator|` 的定义位置。在 libstdc++ 里，这通常在 `<ranges>` 中的 `__adaptor` 命名空间。观察它如何把 `range | adaptor_closure` 转换为 `adaptor_closure(range)` 的调用。

### 第三轮：对照论文，不对照语法糖

第三轮的目的是把你读到的代码结构，映射回设计提案里的动机描述。对照以下提案（只看动机段，不通读）：

| 提案 | 你要找的段落 | 与你读到的代码的对应关系 |
|------|-------------|------------------------|
| P0896R4 / P3725R3 | §4.1 Views, §5.2 filter_view / const-iterable input branch | begin() 缓存决策；iterator_concept 上界；普通 vector 底层 const filter 仍受限 |
| P2415R2 | §Introduction, §Design | owning_view 引入动机；view 语义边界澄清 |
| P2210R2 | §Motivation, §Design | split 作为 C++20 DR 的修订：原始代理子范围语义由 lazy_split 承接，修订后 split 使用真实子范围 |
| P2387R3 | §Background, §Design | range_adaptor_closure 正式化：operator\| 的合法机制 |

**第三轮只做四件事**：

1. 对照对象角色（提案里的抽象描述 vs 代码里的具体类型）

## 全套练习最终验收清单（阶段一）

完成第一阶段所有模块 + 两个结课项目后，对照以下条件自查：

1. 至少画过 **8 张 view 依赖图**（模块 A 每题 1 张 + 模块 B 每题 1 张 + 结课项目 1 张，共至少 8 张）。

2. 至少读懂 **1 份标准库 filter_view 源码**（libstdc++ 或 MSVC STL），能指出缓存结构、C++20 主路径 begin 为何非 const、P3725R3 const-input 特例为何不覆盖普通 vector 底层，以及 iterator 嵌套类的 friend 关系。

3. 能在不查资料的情况下，说出 **6 个核心对象的职责**：
   - `range`：提供 begin + end 接口的最宽泛抽象
   - `view`：满足三条 O(1) 语义公理的 range
   - `iterator + sentinel`：begin 与 end 分离，end 只需可比较
   - `range_adaptor_closure`：绑定非 range 参数后等待 `|` 应用的部分应用对象
   - `CPO / niebloid`：函数对象形式的定制化入口，ADL 隔离
   - `projection`：算法的第三/四参数，先于谓词应用于每个元素

4. 能对任一给定管道，回答：
   - 每层的 `iterator_concept` 是什么
   - 是否 `borrowed_range`，dangling 可能出现在哪里
   - 真正触发迭代的代码行在哪里
   - `filter_view` 在哪里可能导致 const 存储编译错误

5. 能手工用 **projection 替换至少 3 处 lambda**，并说明替换是否等价（当 lambda 只访问成员时，成员指针 projection 与 lambda 等价；当 lambda 含计算时，projection 不能直接替换）。

6. 能用一句话解释：**为什么 `filter_view` 的 begin() 缓存拷贝时不传播**（保证 O(1) copy 公理）。

7. 能用一句话解释：**为什么修订后 split 的子范围可以直接构造 string_view，而 lazy_split 不行**（子范围迭代器类型不同：新 split 使用底层的真实迭代器，lazy_split 使用代理迭代器）。

8. 能解释 **`owning_view` 的引入动机**（P2415R2 之前，右值临时容器无法合法进入管道）。

9. 能指出 **iterator_concept vs iterator_category 双轨的实践意义**：对于产出 proxy reference 的 view（如 `zip_view`），`iterator_concept = random_access_iterator_tag`，但 `iterator_category = input_iterator_tag`，使得 C++17 算法拒绝，而 C++20 算法接受。

10. 完成结课项目 1 的必做任务 8 项，且 view 依赖图注释已附在代码中。

## 学完之后下一步该练什么

如果完成阶段一，推荐进入**阶段二（模块 E-H）**，那里将从使用者变成实现者：实现自定义 view、实现 range_adaptor_closure、实现 sentinel、实现 borrowed_range 标记，以及实现简化版 `ranges::to`。

如果想横向扩展而不是纵向深入实现层，按以下顺序考虑（难度递增）：

1. **`basic_const_iterator` 细节**（C++23，P2278R4）：理解 `views::as_const` 和 `basic_const_iterator` 的组合如何让可变视图包装成不可变元素视图，以及它与 `filter_view` 的缓存/const begin 边界不是同一个问题。

2. **`any_view` 类型擦除**（非标，range-v3）：把不同具体类型的 view 统一存入一个 `any_view<int>` 容器。理解类型擦除对 iterator_concept 的代价（通常降为 input 或 forward）。

3. **`views::concat`**（C++26，P2542）：把多个异构 range 拼接成单一 range。理解它如何处理底层类型不同的 range，以及 `common_reference` 机制在此的作用。

4. **`views::enumerate`**（C++23，P2164R9）：把任意 range 转换为（index, element）pair 的序列，是 `zip(iota, r)` 的语义糖，但有更清晰的 iterator_concept 保证。

5. **Unicode 视图**：P2728R7 走到 C++26 工作草案边界，但本机标准库能力需要 capability probe；不要在练习里模拟缺失标准 API。

6. **从 ranges 到 `std::execution` 的桥接**（可选）：`std::generator`（P2502R2，模块 D 的协程桥）是 ranges 与 execution 的接触点。generator 作为惰性生产者与 ranges 管道兼容，但 generator 的执行调度（何时恢复协程）属于 execution 的问题域。如果两套都练透，这条桥接路径是最自然的融合点。

## 最后一句提醒

真正理解 ranges，不是你能写出多少管道，而是你能不能看着一段代码立刻指出：view 链在哪、iterator_concept 是谁、borrowed 在哪、真正触发迭代在哪、projection 在哪。

如果这五件事都能快速指出来，这套练习就已经达到目的了。
