# 11 模块 H：高级实现模式

## 模块目标

前面的模块 E、F、G 让你掌握了 CPO / niebloid 的 ADL 隔离、`view_interface` 的 CRTP 注入、以及 range adaptor closure 的完整实现套路。模块 H 要把你带到整个练习包的最深处——这是最后一套"坑 + 模式"集合，帮你在读标准库源码和自写 ranges 库时不再被卡住。

你会遇到：

- `filter_view` 的 **`__non_propagating_cache<T>`** 机制：为什么拷贝一个 `filter_view` 时缓存不能随之传播，以及这与 view 的 O(1) copy 公理之间的精确关系
- **`common_iterator<I, S>`** 的 variant-based 实现：如何把 begin/end 类型不同的 view 对接 C++17 遗留算法
- **proxy reference、`iter_move`、`iter_swap` CPO** 的必要性：zip/as_rvalue 这类迭代器为何必须定制这两个 CPO，否则 `ranges::sort` 等算法行为错误
- **`basic_const_iterator<I>`**（P2278R4，C++23）：如何用它包装任意迭代器让其产出只读引用，以及它与"在迭代器类型上加 const"的根本区别
- **模板膨胀与 `any_view` 类型擦除**：每加一层 view adaptor 产生新模板实例化的代价，以及 range-v3 的非标准 `any_view` 如何用类型擦除换取编译边界
- **`std::generator` 的 promise_type 骨架**（P2502R2）：`yield_value`、`elements_of`、symmetric transfer 尾递归的内部结构

**反向引用**：

- `01-心智模型.md` 的"三条 view 语义公理"与"iterator_concept 双轨"是本模块所有坑的根因追溯入口。
- 模块 F（`09-模块F-概念精化与迭代器分类.md`）的 proxy iterator 练习 F-3 是练习 H-2 的直接前置；iterator_concept / iterator_category 双轨概念在那里建立。
- 模块 G（`10-模块G-自行实现视图.md`）的 `view_interface` 经验是练习 H-1 的直接前置；`my_filter_view` 骨架在那里已经建立。
- 模块 D（`06-模块D-C++23高阶视图与协程桥.md`）的 `std::generator` 概览是练习 H-3 的前置；那里介绍了 `generator` 作为 `input_range` 的基本形态，本模块深入 promise_type 内部结构。

**前向引用**：结课项目 2（`12-结课项目2-实现级源码阅读.md`）把本模块所有能力综合起来，做"实现级源码对照 + mini-ranges 子集实现"。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- `__non_propagating_cache<T>` 的语义：拷贝时缓存不传播，因为 view 的 O(1) copy 语义要求新 view 必须重新计算 `begin()`，缓存若传播就破坏"不同 view 对象有独立迭代状态"的值语义。
- `common_iterator<I, S>` 内部是 `std::variant<I, S>` 的变体，解决"begin/end 类型不同"的 view 传给 C++17 算法（要求 begin/end 同类型）的问题。
- `iter_move(it)` CPO 对 proxy iterator（zip/as_rvalue）的必要性：没有它，`std::move(*it)` 对 proxy reference 不会触发正确的 move 语义。
- `iter_swap(a, b)` CPO 对 proxy iterator 的必要性：`std::swap(*a, *b)` 对 proxy reference 要么不合法，要么语义错误（只交换了代理对象，没有交换底层元素）。
- `basic_const_iterator<I>` 是"让任何 iterator 产出 const 引用"的包装器，不是 `I const` 的别名——`const I` 根本不是合法的 iterator typedef，对其解引用拿到的仍是可变引用。
- 模板膨胀：每加一层 view adaptor 产生新的模板实例化，深管道在 TU 间传递时的编译时间与二进制大小代价。`any_view` 是 range-v3 的非标准工具，用类型擦除换取稳定的 ABI 边界。
- `std::generator` 的 promise 结构：`get_return_object` / `initial_suspend=suspend_always`（惰性启动）/ `final_suspend=suspend_always`（保留 done 状态）/ `yield_value` 暂存值地址后返回 `suspend_always`；`elements_of(sub)` 通过 symmetric transfer 实现尾递归，使嵌套 generator 的 resume 栈深不增长。

## 背景速查段

在开始写代码之前，给出本模块关键实现细节的最小速查表。不需要背，编译出错或遇到坑时回来对照。

### `__non_propagating_cache<T>` 语义速查

```cpp
// C++20
// libstdc++ 实现命名（来自 P1251 设计，libstdc++ / MSVC STL 均有类似实现，
// 但并非 ISO 标准规定的名字，不同实现可能用不同名字）
template<class T>
struct non_propagating_cache {
    std::optional<T> slot_;

    non_propagating_cache() = default;

    // 拷贝构造：slot_ 不传播（新 view 需要重新计算 begin）
    non_propagating_cache(const non_propagating_cache&) : slot_() {}

    // 移动构造：同样不传播（避免两个 view 共享缓存状态）
    non_propagating_cache(non_propagating_cache&&) : slot_() {}

    // 拷贝赋值：清空目标的缓存
    non_propagating_cache& operator=(const non_propagating_cache&) {
        slot_.reset();
        return *this;
    }

    // 移动赋值：清空目标的缓存
    non_propagating_cache& operator=(non_propagating_cache&&) {
        slot_.reset();
        return *this;
    }
};
// 关键：这不是普通 optional 的包装——它刻意打破了值语义的"拷贝保留值"直觉，
// 目的是满足"拷贝后的新 view 迭代状态独立"这条 view 语义公理。
```

### `common_iterator<I, S>` 结构速查

```cpp
// C++20
// std::common_iterator<I, S> 内部持有 variant<I, S>
// begin() 时存 I；end() 时存 S；到达末尾后切换为 S
// 目的：把"begin/end 类型不同"的 range 暴露为"begin/end 类型相同"的 common_range
// 供 C++17 算法（std::accumulate, std::copy 等）使用

template<std::input_or_output_iterator I, std::sentinel_for<I> S>
    requires (!std::same_as<I, S> && std::copyable<I>)
class common_iterator {
    std::variant<I, S> var_;  // 简化示意；实际实现更复杂
public:
    // 当持有 I 时，*it 解引用；当持有 S 时，行为未定义（表示已到末尾）
    decltype(auto) operator*() const { return *std::get<I>(var_); }
    common_iterator& operator++() {
        ++std::get<I>(var_);
        return *this;
    }
    friend bool operator==(const common_iterator& a, const common_iterator& b) {
        // 两种情况均相等：两者都是 S（哨兵），或 I == S 的逻辑相等
        if (a.var_.index() == 1 && b.var_.index() == 1) return true;
        if (a.var_.index() == 0 && b.var_.index() == 1)
            return std::get<I>(a.var_) == std::get<S>(b.var_);
        if (a.var_.index() == 1 && b.var_.index() == 0)
            return std::get<I>(b.var_) == std::get<S>(a.var_);
        return false;  // 两者都是 I：一般不直接比较
    }
};
```

### `iter_move` / `iter_swap` CPO 速查

```cpp
// C++20
// iter_move(it) 的默认行为：std::move(*it)
// 对 proxy iterator（zip_view 等），*it 返回 tuple<T&, T&>（prvalue），
// std::move(*it) 得到 tuple<T&, T&>&&（对 tuple 本身取右值引用）——
// 但 tuple 内部的 T&/T& 并不会因此变成 T&&，元素级 move 不会发生。
// 因此必须定制 iter_move 显式返回 tuple<T&&, T&&>，让下游真正 move 到元素。

// 定制方式：在迭代器类内部或同命名空间定义 hidden friend
struct MyZipIt {
    // ...
    friend auto iter_move(const MyZipIt& it) {
        // 返回 tuple<T&&, T&&>，真正触发 move 语义
        return std::tuple<T&&, T&&>(
            std::ranges::iter_move(it.it1_),
            std::ranges::iter_move(it.it2_)
        );
    }
    friend void iter_swap(const MyZipIt& a, const MyZipIt& b) {
        // 分别 swap 每一维的底层元素
        std::ranges::iter_swap(a.it1_, b.it1_);
        std::ranges::iter_swap(a.it2_, b.it2_);
    }
};
// 必须 hidden friend 或同命名空间非成员函数（ADL 找到）
// 不能写成普通成员函数（ranges::iter_move CPO 不走成员查找路径）
```

### `basic_const_iterator<I>` 结构速查（C++23）

```cpp
// C++23: -std=c++23
// basic_const_iterator<I> 让任何 iterator 产出 const 引用
// 错误思路：const I 或 I const
//   const vector<int>::iterator it; // it 本身不能 ++，但 *it 仍是 int&（可变！）
// 正确做法：包装 I，重写 operator* 返回 iter_const_reference_t<I>

template<std::input_iterator I>
class basic_const_iterator {
    I current_;
public:
    using value_type = std::iter_value_t<I>;
    using difference_type = std::iter_difference_t<I>;
    // iterator_concept 继承底层 I 的 concept
    using iterator_concept = /* 从 I 推导 */;

    // 关键：operator* 返回 const 引用，而不是 I::reference
    constexpr std::iter_const_reference_t<I> operator*() const noexcept(/*...*/) {
        return static_cast<std::iter_const_reference_t<I>>(*current_);
    }
    // 其余 operator++ / -- / + / - 等委托给 current_
};
// views::as_const(vec) 内部：返回 basic_const_iterator 包装后的视图
```

## 练习 H-1：实现 `non_propagating_cache` 并接入 `my_filter_view`

### 目标

把模块 G 的 `my_filter_view` 升级，让它模拟标准 `filter_view` 的缓存行为。核心目标是亲手实现 `non_propagating_cache<T>`，并用它缓存 `begin()` 扫描结果，同时通过 `static_assert` 验证拷贝后的新 view 缓存为空——这是 view O(1) copy 公理的实现级保障。

### 前置理解

- 你已完成模块 G 的 `view_interface` CRTP 练习，能写出基本的 `my_filter_view` 骨架。
- 你理解 `01-心智模型.md` 中的 view O(1) copy 公理：若 view 允许拷贝，拷贝代价必须是 O(1)。
- 你接受 `filter_view::begin()` 在 C++20 里是非 const 成员（它需要写入缓存），因此无法对 `const filter_view` 调用。

### 预计练习方向

```cpp
// C++20
#include <ranges>
#include <optional>
#include <functional>
#include <iterator>
#include <iostream>
#include <cassert>

// ---- Step 1: non_propagating_cache ----

template<class T>
struct non_propagating_cache {
    std::optional<T> slot_;

    non_propagating_cache() = default;

    // 拷贝：缓存不传播——新 view 必须重新计算 begin
    non_propagating_cache(const non_propagating_cache&) noexcept : slot_() {}

    // 移动：缓存不传播——移动源被置为"未缓存"状态同样合理
    non_propagating_cache(non_propagating_cache&&) noexcept : slot_() {}

    non_propagating_cache& operator=(const non_propagating_cache&) noexcept {
        slot_.reset();
        return *this;
    }

    non_propagating_cache& operator=(non_propagating_cache&&) noexcept {
        slot_.reset();
        return *this;
    }

    // 工具：是否已缓存
    bool has_value() const noexcept { return slot_.has_value(); }

    // 工具：访问缓存值
    T& operator*() noexcept { return *slot_; }
    const T& operator*() const noexcept { return *slot_; }

    // 工具：设置缓存
    template<class... Args>
    T& emplace(Args&&... args) {
        slot_.emplace(std::forward<Args>(args)...);
        return *slot_;
    }

    void reset() noexcept { slot_.reset(); }
};

// ---- Step 2: my_filter_view ----

template<std::ranges::forward_range V,
         std::indirect_unary_predicate<std::ranges::iterator_t<V>> Pred>
    requires std::ranges::view<V> && std::is_object_v<Pred>
class my_filter_view : public std::ranges::view_interface<my_filter_view<V, Pred>> {
    V base_;
    Pred pred_;

    // 缓存 begin() 的结果（非传播：拷贝时不继承）
    non_propagating_cache<std::ranges::iterator_t<V>> cached_begin_;

public:
    my_filter_view() = default;

    constexpr my_filter_view(V base, Pred pred)
        : base_(std::move(base)), pred_(std::move(pred)) {}

    // begin() 是非 const：需要写缓存
    constexpr auto begin() {
        if (!cached_begin_.has_value()) {
            // O(n) 扫描，只在第一次调用时发生
            auto it = std::ranges::begin(base_);
            auto end = std::ranges::end(base_);
            while (it != end && !std::invoke(pred_, *it)) {
                ++it;
            }
            cached_begin_.emplace(it);
        }
        return *cached_begin_;
    }

    // end() 是 const：不写缓存
    constexpr auto end() const {
        return std::ranges::end(base_);
    }

    // 返回底层 range（标准 filter_view 接口）
    constexpr V& base() noexcept { return base_; }
    constexpr const V& base() const noexcept { return base_; }

    // ---- 内部迭代器 ----
    class iterator {
        my_filter_view* parent_ = nullptr;
        std::ranges::iterator_t<V> current_{};

        // 推进到下一个满足谓词的位置
        void skip_bad() {
            auto end = std::ranges::end(parent_->base_);
            while (current_ != end && !std::invoke(parent_->pred_, *current_)) {
                ++current_;
            }
        }

    public:
        // iterator_concept 上界 bidirectional，但实际值取 min(底层, bidirectional)：
        // 若底层只是 forward，本迭代器仍应为 forward（operator-- 需要加概念保护）。
        using iterator_concept  = std::conditional_t<
            std::ranges::bidirectional_range<V>,
            std::bidirectional_iterator_tag,
            std::forward_iterator_tag>;
        using iterator_category = iterator_concept;
        using value_type        = std::ranges::range_value_t<V>;
        using difference_type   = std::ranges::range_difference_t<V>;

        iterator() = default;

        constexpr iterator(my_filter_view* parent, std::ranges::iterator_t<V> it)
            : parent_(parent), current_(std::move(it)) {}

        constexpr decltype(auto) operator*() const { return *current_; }

        constexpr iterator& operator++() {
            ++current_;
            skip_bad();
            return *this;
        }
        constexpr iterator operator++(int) {
            auto tmp = *this;
            ++*this;
            return tmp;
        }

        // operator-- 只在底层迭代器支持反向推进时才参与重载解析；
        // 底层只到 forward 时本类退化为 forward_iterator，不再有反向接口。
        constexpr iterator& operator--()
            requires std::ranges::bidirectional_range<V>
        {
            auto begin = std::ranges::begin(parent_->base_);
            do { --current_; }
            while (current_ != begin && !std::invoke(parent_->pred_, *current_));
            return *this;
        }
        constexpr iterator operator--(int)
            requires std::ranges::bidirectional_range<V>
        {
            auto tmp = *this;
            --*this;
            return tmp;
        }

        friend bool operator==(const iterator& a, const iterator& b) {
            return a.current_ == b.current_;
        }
        friend bool operator==(const iterator& a,
                               const std::ranges::sentinel_t<V>& s) {
            return a.current_ == s;
        }
    };

    // begin() 返回 iterator，end() 返回底层 sentinel
};

// ---- Step 3: 验证 O(1) copy 公理与缓存不传播 ----

int main() {
    std::vector<int> v = {1, 3, 4, 6, 7, 9, 10};

    auto fv = my_filter_view(std::views::all(v), [](int x) { return x % 2 == 0; });

    // 第一次调用 begin()：触发 O(n) 扫描，缓存结果
    auto it1 = fv.begin();
    std::cout << "first even: " << *it1 << '\n';  // 4

    // 第二次调用 begin()：直接返回缓存，O(1)
    auto it2 = fv.begin();
    std::cout << "second begin (cached): " << *it2 << '\n';  // 4
    assert(it1 == it2);

    // 拷贝 fv：新 view 缓存为空
    auto fv_copy = fv;
    // fv_copy 的 cached_begin_ 已被 non_propagating_cache 的拷贝构造清空
    // 再次调用 begin() 会重新扫描——这是正确的值语义
    auto it3 = fv_copy.begin();
    std::cout << "copy's begin (re-scanned): " << *it3 << '\n';  // 4

    // static_assert：my_filter_view 满足 copyable（O(1) copy 公理要求）
    static_assert(std::copyable<decltype(fv)>);

    // 演示：const 版本无法调用 begin()（因为 begin() 是非 const 成员）
    // const auto cfv = fv;
    // cfv.begin();  // 编译错误：'begin' is not a const member function
    //               // 这是预期行为，与标准 filter_view 一致

    // 对比：mutable optional<It> 版本的语义错误
    // 如果用 mutable optional<It> cached_begin_，拷贝时 optional 会随 value 一起复制，
    // 导致两个 view 对象共享同一个"缓存位置"的假象（实际 copy of It），
    // 但更危险的是：如果 It 是指向底层数据的迭代器，而底层被修改，
    // 缓存值就变成了悬垂迭代器——non_propagating_cache 的"拷贝清空"直接规避了这个坑。

    // range-based for 验证完整迭代
    std::cout << "all evens: ";
    for (int x : fv) {
        std::cout << x << ' ';  // 4 6 10
    }
    std::cout << '\n';

    return 0;
}
```

### 进阶任务

- 把 `begin()` 改为用 `std::ranges::find_if` 实现（内部等价），对比手写 while 循环，确认行为一致。
- 演示 `mutable optional<It>` 版本：把缓存改为 `mutable std::optional<...> cached_begin_`，使 `begin()` 变为 `const` 成员，然后解释它破坏了哪条语义：(a) 两个独立 view 对象共享缓存状态；(b) 对 `const` 对象写入是 `mutable` 的语义，但 O(1) copy 公理仍然要求拷贝时缓存被清空，所以 `mutable optional` 依然需要在拷贝构造中手写清空逻辑——你漏掉这一步才是真正的坑。
- 为 `my_filter_view` 的迭代器实现完整的 bidirectional 支持（含 `operator--`），并用 `std::ranges::bidirectional_range` concept 验证。
- 把 `non_propagating_cache` 的 `T` 约束为可默认构造，然后观察：如果 iterator 类型不可默认构造，缓存要怎么处理（答案：用 `optional<T>` 而非裸 `T` 正是这个原因）。

### 验收点

- `non_propagating_cache` 的拷贝构造和移动构造均不传播缓存值。
- 拷贝 `my_filter_view` 后，新 view 的第一次 `begin()` 会重新扫描底层序列（可通过日志计数器验证）。
- `static_assert(std::copyable<my_filter_view<...>>)` 通过。
- `const my_filter_view` 无法调用 `begin()`（编译期阻止）。
- 你能解释为什么这是"标准 `filter_view` const 迭代受限"的根因，而不只是一个实现选择。

### 观察点

- `non_propagating_cache` 的拷贝清空不是偶然：它是 view O(1) copy 公理的实现级保障。O(1) copy 要求拷贝代价与"覆盖序列的长度"无关；如果缓存里存的是"扫描到第一个满足元素的结果"，传播它不代价，但"新 view 的迭代状态应该是独立的"这条值语义要求它必须重新扫描。
- 这就是为什么标准不用 `mutable optional`（那样 begin() 可以是 const，但缓存传播问题依然存在）。
- `filter_view::begin()` 的非 const 性是 **有意为之的设计约束**，不是实现缺陷——它正确表达了"begin() 会修改 view 的可观察状态"这个事实。
- C++23 不会修复这一点：即使加了 `views::as_const`，`const filter_view` 依然无法迭代。`as_const` 解决的是"元素只读"，不解决"begin() 需要写缓存"。

### 常见坑

- 把 cache 直接写成 `mutable optional<It>`，忘记在拷贝构造中显式清空，导致两个 view 对象共享缓存状态，违反值语义。
- `non_propagating_cache` 的移动构造没有清空缓存（移动后旧对象应保持"未缓存"状态，否则移动后析构旧对象可能触发悬垂访问）。
- `begin()` 的实现中没有用缓存，每次都重新扫描，退化成 O(n) 的重复代价——这不会编译失败，但会让性能悄悄崩塌。
- 忘记 `begin()` 是非 const，导致某些场景（如 `const auto& fv = ...`）下调用失败。这是正确的，但如果你不理解原因会以为是 bug。
- 把 `non_propagating_cache` 里的 `T` 设为 iterator 类型，但忘记了某些 iterator 类型不可默认构造——`optional<T>` 的 slot 设计正是为此。

### 复盘问题

## 练习 H-2：`common_iterator` 与 proxy reference / `iter_move` / `iter_swap`

### 目标

### 前置理解

- 你已完成模块 F 的 proxy iterator 练习 F-3，理解了 `iterator_concept` / `iterator_category` 双轨。
- 你知道 C++17 算法（`std::accumulate`、`std::copy` 等）要求 begin/end 是相同类型。
- 你理解 `iter_move` CPO 的默认行为是 `std::move(*it)`，对 proxy reference 这不够。

### 预计练习方向

```cpp
// C++20
#include <ranges>
#include <numeric>
#include <algorithm>
#include <iterator>
#include <tuple>
#include <iostream>

// ---- Part A: common_iterator 对接 C++17 算法 ----

int main() {

    // 展示 variant-based 内部结构

// ---- Part C: proxy reference + iter_move / iter_swap 的必要性 ----

// 手工构造 zip-like proxy iterator
template<class It1, class It2>
struct ZipIterator {
    It1 it1_;
    It2 it2_;

    using value_type      = std::tuple<std::iter_value_t<It1>,
                                       std::iter_value_t<It2>>;
    using difference_type = std::common_type_t<std::iter_difference_t<It1>,
                                               std::iter_difference_t<It2>>;
    // proxy reference：*it 返回 tuple of refs，不是真实左值引用
    using reference       = std::tuple<std::iter_reference_t<It1>,
                                       std::iter_reference_t<It2>>;

    // iterator_concept = random_access（若底层都是）
    // iterator_category = input（因为是 proxy reference，见模块 F 双轨说明）
    using iterator_concept  = std::random_access_iterator_tag;
    using iterator_category = std::input_iterator_tag;

    reference operator*() const {
        return reference(*it1_, *it2_);  // 返回 tuple<T1&, T2&>
    }

    ZipIterator& operator++() { ++it1_; ++it2_; return *this; }
    ZipIterator  operator++(int) { auto t = *this; ++*this; return t; }
    ZipIterator& operator--() { --it1_; --it2_; return *this; }
    ZipIterator  operator--(int) { auto t = *this; --*this; return t; }

    ZipIterator& operator+=(difference_type n) { it1_ += n; it2_ += n; return *this; }
    ZipIterator& operator-=(difference_type n) { it1_ -= n; it2_ -= n; return *this; }
    ZipIterator  operator+(difference_type n) const { auto t = *this; t += n; return t; }
    ZipIterator  operator-(difference_type n) const { auto t = *this; t -= n; return t; }
    difference_type operator-(const ZipIterator& o) const { return it1_ - o.it1_; }
    reference operator[](difference_type n) const { return *(*this + n); }

    auto operator<=>(const ZipIterator&) const = default;
    bool operator==(const ZipIterator&) const = default;

    // ---- 关键 1：定制 iter_move ----
    // 没有这个定制，std::ranges::iter_move(it) 调用默认的 std::move(*it)
    // std::move(tuple<T1&, T2&>) -> tuple<T1&, T2&>（引用被 move 了，但值没有 move）
    // 有了这个定制，iter_move 正确返回 tuple<T1&&, T2&&>
    friend auto iter_move(const ZipIterator& it) {
        return std::tuple<std::iter_rvalue_reference_t<It1>,
                          std::iter_rvalue_reference_t<It2>>(
            std::ranges::iter_move(it.it1_),
            std::ranges::iter_move(it.it2_)
        );
    }

    // ---- 关键 2：定制 iter_swap ----
    // 没有这个定制，std::ranges::iter_swap(a, b) 调用：
    //   std::ranges::swap(*a, *b)
    //   即 swap(tuple<T1&, T2&>, tuple<T1&, T2&>)
    // 问题：tuple 的 swap 是 swap(get<0>(a_proxy), get<0>(b_proxy))
    //        这只交换了代理对象的"引用绑定"（不可能，引用不可重绑），
    //        或者产生编译错误
    // 有了这个定制，直接 swap 底层每一维的真实元素
    friend void iter_swap(const ZipIterator& a, const ZipIterator& b) {
        std::ranges::iter_swap(a.it1_, b.it1_);
        std::ranges::iter_swap(a.it2_, b.it2_);
    }
};

void demo_proxy_sort() {
    std::vector<int>    keys   = {3, 1, 4, 1, 5, 9, 2, 6};
    std::vector<double> values = {3.3, 1.1, 4.4, 1.2, 5.5, 9.9, 2.2, 6.6};

    ZipIterator<std::vector<int>::iterator,
                std::vector<double>::iterator> begin{keys.begin(),   values.begin()};
    ZipIterator<std::vector<int>::iterator,
                std::vector<double>::iterator> end  {keys.end(),     values.end()};

    // ranges::sort 要求 sortable<I>，其中 sortable 依赖 iter_move 和 iter_swap
    std::ranges::sort(begin, end, {}, [](auto&& pair) { return std::get<0>(pair); });

    std::cout << "sorted by key:\n";
    for (auto i = begin; i != end; ++i) {
        auto [k, v] = *i;
        std::cout << "  " << k << " -> " << v << '\n';
    }
    // 如果移除 iter_move / iter_swap，ranges::sort 要么编译失败，要么只排序了 keys
    // 而 values 没有跟着动——这是静默的语义错误，比编译失败更危险

    // 对比：std::sort 用 std::swap(*a, *b)，对 proxy reference 不工作
    // std::sort(begin, end);  // 可能编译，但 swap 语义错误或不合法
}

int main() {
    demo_proxy_sort();
    return 0;
}
```

### 进阶任务

### 验收点

- `views::iota(1) | views::take(10) | views::common` 能成功传给 `std::accumulate`，结果为 55。
- 不加 `views::common` 时，直接传给 `std::accumulate` 编译失败（类型不匹配）。
- `ZipIterator` 的 `iter_move` 返回 `tuple<T1&&, T2&&>`（可用 `decltype` / `static_assert` 验证）。
- `ranges::sort` 通过 `ZipIterator` 排序后，keys 和 values 同时被正确排列。
- 你能解释为什么 `iter_move` / `iter_swap` 必须是 hidden friend（ADL 可找到）而不是普通成员函数。

### 观察点

- `iter_move(it)` 和 `iter_swap(a, b)` 是 ranges 算法（`ranges::sort`、`ranges::rotate` 等）与 iterator 交互的两个最底层 CPO。标准库的 `sortable` concept 内部约束了这两个 CPO，因此不正确定制它们会直接导致 `sortable` 不满足，进而 `ranges::sort` 无法编译——这是一个设计上的编译期安全保障。
- `std::sort`（老式算法）用 `std::swap(*a, *b)` 和直接赋值，对 proxy reference 的行为依赖实现，不可靠。这正是"ranges 算法 vs C++17 算法"在 proxy iterator 场景下的关键差异。
- `common_iterator` 是"让现代 ranges 与 C++17 遗留代码共存"的桥梁。它的代价是：每次 `operator==` 需要检查 variant 状态，比原生 iterator 稍慢；但这个代价只出现在需要传给 C++17 算法的场合，不影响 ranges 管道内部的性能。

### 常见坑

- 把 `iter_move` 写成普通成员函数：`std::ranges::iter_move` CPO 通过 ADL 找到同命名空间（或 hidden friend）的 `iter_move`，不走成员函数路径。写成成员函数后，CPO 会退回默认行为 `std::move(*it)`，你的定制完全无效。
- `iter_swap` 只 swap 了底层迭代器之一：`tuple` 里每一维的引用都必须被 swap，漏掉任何一维会导致"部分排序"的静默错误。
- 忘记 `common_iterator` 在构造为 end 时存储 S（哨兵）而不是 I：如果你把 end 也构造为持有 I 的状态，`operator==` 永远不会在正确位置停止。
- 把 `views::common` 与 `views::as_const` 混淆：前者解决"begin/end 类型不同"，后者解决"元素可变/不可变"——两个完全正交的问题。

### 复盘问题

1. `common_iterator` 的 `operator==` 需要比较 `variant<I, S>` 的两种状态，为什么"两个 I 相等"这种情况通常不需要处理？（提示：common_range 的 end iterator 存的是 S，begin iterator 存的是 I）
2. 如果 `iter_move(it)` 没有被定制，`ranges::sort` 在排序 `ZipIterator` 范围时最可能出现什么现象？（提示：sort 内部需要把元素 move 到临时位置，move 一个 proxy reference 意味着什么）

## 练习 H-3：`std::generator` 的 promise_type 骨架 + `basic_const_iterator`

### 目标

### 前置理解

- 你已完成模块 D 的 `std::generator` 概览（`06-模块D-C++23高阶视图与协程桥.md`）。
- 你理解 C++20 coroutine 的基本机制：`promise_type`、`coroutine_handle`、`co_yield`、`co_return`、`initial_suspend`、`final_suspend`。
- 你接受本练习的骨架是简化版（不含 allocator 支持、不含完整 exception propagation），重点是理解设计决策的"为什么"。

### 预计练习方向

```cpp
// C++23: -std=c++23
#include <coroutine>
#include <optional>
#include <exception>
#include <type_traits>
#include <iostream>

// ---- Part A: std::generator promise_type 骨架（简化版） ----
// 这不是完整实现，只到关键成员。目的是理解每个决策的根因。

template<class Ref, class Val = std::remove_cvref_t<Ref>>
class my_generator {
public:
    struct promise_type {
        // 当前 yield 值的地址（指针而非值，避免拷贝）
        // yield_value 只存地址，值本身仍在调用方的临时量或 co_yield 表达式里
        const Val* current_value_ = nullptr;
        std::exception_ptr exception_;

        // ---- 为什么 initial_suspend 必须是 suspend_always ----
        // 惰性启动：generator 被构造时，协程体尚未开始执行。
        // 只有调用方第一次调用 begin()（即第一次 resume）时，
        // 协程才开始运行直到第一个 co_yield。
        // 如果是 suspend_never，协程在构造时立刻运行，
        // 产出第一个值之前调用方根本没有机会安装迭代器。
        std::suspend_always initial_suspend() noexcept { return {}; }

        // ---- 为什么 final_suspend 必须是 suspend_always ----
        // 保留 done 状态可读：协程执行完毕后，我们需要能够检测到"协程已结束"
        // （即 handle.done() == true），以便迭代器知道停止。
        // 如果是 suspend_never，协程帧在最后自动销毁（resume + destroy），
        // 之后再检查 handle.done() 是 UB；且 iterator 析构时
        // 也无法安全调用 handle.destroy()（已被自动销毁会 double-free）。
        std::suspend_always final_suspend() noexcept { return {}; }

        my_generator get_return_object() noexcept {
            return my_generator{
                std::coroutine_handle<promise_type>::from_promise(*this)
            };
        }

        // ---- yield_value：暂存值地址后 suspend_always ----
        // 不拷贝值，只存地址；调用方在协程挂起后通过指针读取。
        // 返回 suspend_always：确保值被消费前协程不继续执行。
        // 如果返回 suspend_never，值还没被读取就继续执行，
        // current_value_ 指向的临时量已失效——悬垂指针。
        template<class T>
            requires std::convertible_to<T, Val>
        std::suspend_always yield_value(T&& val) noexcept {
            current_value_ = std::addressof(val);  // 存地址，不 move/copy
            return {};
        }

        void return_void() noexcept {}  // generator 不 co_return 值

        void unhandled_exception() {
            exception_ = std::current_exception();
        }
    };

    // ---- iterator（简化版） ----
    class iterator {
        std::coroutine_handle<promise_type> handle_;
    public:
        using value_type        = Val;
        using difference_type   = std::ptrdiff_t;
        using iterator_concept  = std::input_iterator_tag;
        // generator 只是 input_range：单遍，不能重置，不能多个独立迭代器

        explicit iterator(std::coroutine_handle<promise_type> h) : handle_(h) {}

        // operator++ 恢复协程，直到下一个 co_yield 或协程结束
        iterator& operator++() {
            handle_.resume();
            if (handle_.promise().exception_)
                std::rethrow_exception(handle_.promise().exception_);
            return *this;
        }

        // 解引用：通过存储的地址访问 yield 的值
        const Val& operator*() const noexcept {
            return *handle_.promise().current_value_;
        }

        bool operator==(std::default_sentinel_t) const noexcept {
            return handle_.done();
        }
    };

    // begin()：resume 一次（跳过 initial_suspend），得到第一个值
    iterator begin() {
        handle_.resume();
        if (handle_.promise().exception_)
            std::rethrow_exception(handle_.promise().exception_);
        return iterator{handle_};
    }

    std::default_sentinel_t end() const noexcept { return {}; }

    // generator 是 move-only（不可拷贝：协程句柄是唯一所有权）
    my_generator(my_generator&&) = default;
    my_generator& operator=(my_generator&&) = default;
    my_generator(const my_generator&) = delete;
    my_generator& operator=(const my_generator&) = delete;

    ~my_generator() {
        if (handle_) handle_.destroy();
    }

private:
    explicit my_generator(std::coroutine_handle<promise_type> h) : handle_(h) {}
    std::coroutine_handle<promise_type> handle_;
};

// ---- Part B: elements_of 的 symmetric transfer 语义说明 ----
// elements_of(sub_generator) 是 C++23 std::generator 支持的特殊 yield 形式：
//
//   co_yield std::ranges::elements_of(nested_gen());
//
// 它的作用：把嵌套 generator 的每个值逐一 yield 给外层。
// 关键：通过 symmetric transfer（协程的 await_suspend 返回另一个 coroutine_handle）
//       直接跳转到嵌套 generator 的协程帧，而不是在外层协程里循环 resume。
//
// 为什么重要：
// - 普通的"在外层 for 循环里 yield 嵌套 gen 的每个值"需要 O(depth) 次恢复步骤，
//   且每次都经过外层协程的栈帧，导致递归深度随嵌套层数线性增长。
// - symmetric transfer 通过尾调用优化，使嵌套 generator 的 resume
//   直接跳转到最深层协程，不增加外层协程的活跃栈帧——O(1) 栈深。
//
// 简化演示（不完整实现，只展示语义）：
struct elements_of_sentinel {
    // 在完整实现中，这里持有嵌套 generator 的 handle，
    // yield_value(elements_of_sentinel) 的实现会设置当前协程的"active child"
    // 并在 await_suspend 里返回 child.handle，实现 symmetric transfer
};

// ---- Part C: 使用 my_generator ----

my_generator<int> fibonacci() {
    int a = 0, b = 1;
    while (true) {
        co_yield a;
        auto next = a + b;
        a = b;
        b = next;
    }
}

my_generator<int> range_gen(int n) {
    for (int i = 0; i < n; ++i) {
        co_yield i;
    }
}

void demo_generator() {
    std::cout << "first 8 fibonacci: ";
    for (int x : fibonacci() | std::views::take(8)) {
        std::cout << x << ' ';  // 0 1 1 2 3 5 8 13
    }
    std::cout << '\n';

    std::cout << "range(5): ";
    for (int x : range_gen(5)) {
        std::cout << x << ' ';  // 0 1 2 3 4
    }
    std::cout << '\n';
}

// ---- Part D: basic_const_iterator<I> 最小骨架（C++23） ----
// 目标：让任何 iterator 产出 const 引用，而不是"const 化 iterator 本身"

// 错误思路：const vector<int>::iterator
//   const std::vector<int>::iterator it = v.begin();
//   // it 本身不能被 ++ 赋值，但 *it 仍是 int&（可写！）
//   // 这只是让 it 变量不可修改，不是让解引用变成只读

// 正确思路：basic_const_iterator<I>
template<std::input_iterator I>
class my_basic_const_iterator {
    I current_;

public:
    // iter_const_reference_t<I> = const range_value_t<I>&（通常情况）
    using value_type      = std::iter_value_t<I>;
    using difference_type = std::iter_difference_t<I>;

    // iterator_concept 继承底层 I 的能力（random_access 仍然 random_access）
    using iterator_concept = /* 从 I 的 iterator_concept 推导 */
        std::conditional_t<
            std::random_access_iterator<I>,
            std::random_access_iterator_tag,
            std::conditional_t<
                std::bidirectional_iterator<I>,
                std::bidirectional_iterator_tag,
                std::conditional_t<
                    std::forward_iterator<I>,
                    std::forward_iterator_tag,
                    std::input_iterator_tag
                >
            >
        >;

    explicit constexpr my_basic_const_iterator(I it) : current_(std::move(it)) {}

    // ---- 核心：operator* 返回 const 引用 ----
    constexpr const value_type& operator*() const noexcept(
            noexcept(static_cast<const value_type&>(*current_))) {
        return static_cast<const value_type&>(*current_);
    }

    constexpr const value_type* operator->() const noexcept {
        return std::to_address(current_);
    }

    constexpr my_basic_const_iterator& operator++() {
        ++current_;
        return *this;
    }
    constexpr my_basic_const_iterator operator++(int) {
        auto tmp = *this;
        ++*this;
        return tmp;
    }

    // bidirectional 支持（仅当 I 满足时才启用）
    constexpr my_basic_const_iterator& operator--()
        requires std::bidirectional_iterator<I>
    {
        --current_;
        return *this;
    }

    // random access 支持（仅当 I 满足时才启用）
    constexpr my_basic_const_iterator& operator+=(difference_type n)
        requires std::random_access_iterator<I>
    {
        current_ += n;
        return *this;
    }

    friend bool operator==(const my_basic_const_iterator& a,
                           const my_basic_const_iterator& b) {
        return a.current_ == b.current_;
    }

    // 允许与原始 iterator 比较（兼容 as_const 视图的 begin/end 类型匹配）
    friend bool operator==(const my_basic_const_iterator& a, const I& b) {
        return a.current_ == b;
    }
};

void demo_const_iterator() {
    std::vector<int> v = {1, 2, 3, 4, 5};

    my_basic_const_iterator<std::vector<int>::iterator> cit(v.begin());
    my_basic_const_iterator<std::vector<int>::iterator> cend(v.end());

    // *cit 是 const int&：只读
    std::cout << "const-iterated: ";
    for (auto it = cit; it != cend; ++it) {
        std::cout << *it << ' ';  // 1 2 3 4 5
        // *it = 99;  // 编译错误：*it 是 const int&，不可写
    }
    std::cout << '\n';

    // views::as_const（C++23 标准版）内部就是用 basic_const_iterator 包装
    // auto cv = std::views::as_const(v);
    // static_assert(std::same_as<decltype(*cv.begin()), const int&>);
}

// ---- Part E: 模板膨胀警示 ----
//
// 每加一层 view adaptor，产生一个新的模板实例化：
//   iota_view<int, unreachable_sentinel_t>
//   take_view<iota_view<int, unreachable_sentinel_t>>
//   filter_view<take_view<...>, Pred1>
//   transform_view<filter_view<...>, Proj1>
//   take_view<transform_view<...>>
//
// 五层管道 = 五个不同类型，每个都会在头文件被 include 的每个 TU 里各自实例化。
// 当管道作为函数参数或返回值在 TU 边界传递时，链接器需要消除重复实例化，
// 但在调试符号里，这些类型名会展开成超过终端宽度的字符串——
// 编译器报错时看到的类型名可能有 300-500 个字符。
//
// 应对策略：
// 1. 及早物化（ranges::to<vector>）：把管道结果存进容器，截断类型链
// 2. any_view（range-v3，非标准）：用类型擦除代替深模板嵌套，
//    代价是虚函数调用开销，好处是 ABI 稳定、编译时间减少
// 3. auto 不穿越 TU 边界：不要把管道类型作为公开函数签名的参数/返回类型，
//    改用 ranges::to 后的容器，或用 concept 约束的模板函数

int main() {
    demo_generator();
    demo_const_iterator();
    return 0;
}
```

### 进阶任务

- 为 `my_generator` 添加异常传播：在 `iterator::operator++` 里检查 `promise().exception_`，若非空则 rethrow，验证 `co_yield` 之后协程体抛出的异常能传播到调用方。
- 实现真正的 `elements_of` 最小语义（不含 symmetric transfer）：在 `yield_value` 重载里接受一个 `range`，然后 for 循环 yield 每个元素——先理解语义，再理解 symmetric transfer 为什么更优。
- 扩展 `my_basic_const_iterator` 以支持完整的 C++23 `basic_const_iterator` 要求：包括 `common_reference_t`、`iter_const_reference_t` 的正确推导，以及与 `views::as_const` 的配合。
- 测量模板膨胀：写一个五层 view 管道，用 `nm` 或 `dumpbin /SYMBOLS` 统计编译后目标文件中因为该管道产生的符号数量，对比 `ranges::to<vector>` 物化后的符号数量，记录差异。

### 验收点

- `my_generator<int>` 能产出 fibonacci 数列，通过 `views::take(8)` 正确停止，迭代器不 double-resume。
- `initial_suspend = suspend_always` 和 `final_suspend = suspend_always` 的原因能用一句话说清楚，不与 `suspend_never` 混淆。
- `yield_value` 存的是值的地址（不拷贝），且返回 `suspend_always`——你能解释为什么这两个选择缺一不可。
- `my_basic_const_iterator<I>` 的 `operator*` 返回 `const value_type&`，`static_assert` 验证类型正确。
- 你能用一句话区分"basic_const_iterator<I>"和"const I"这两个东西各自意味着什么。

### 观察点

- `std::generator` 是 C++23 里把协程结果接入 ranges 管道的标准桥梁（P2502R2），它本身满足 `input_range` + `view`，但只是 `input_range`——不满足 `forward_range`（你不能有两个独立的迭代器同时遍历同一 generator，因为协程状态是唯一的）。
- `final_suspend = suspend_always` 使 generator 的"协程已结束"状态可被稳定读取（`handle.done()`），这与 `std::generator::iterator::operator==` 的实现直接相关——operator== 检查的就是 `handle.done()`。
- `basic_const_iterator` 不是 C++20 里就有的：它是 P2278R4 在 C++23 引入的。在 C++20 里，要实现"只读视图"，你只能用 `const T&` 约束或手写只读迭代器。
- 模板膨胀不只是编译时间问题：在 debug 构建下，每个模板实例会产生独立的调试信息（DWARF / PDB），链接时 debug info 体积可能比 release 二进制本身大 10 倍以上。

### 常见坑

- 把 `final_suspend` 写成 `suspend_never`：协程帧被自动销毁，iterator 再检查 `handle.done()` 是 UB；析构 generator 时再 `handle.destroy()` 是 double-free。
- `yield_value` 返回 `suspend_never`：值还没被消费，协程继续执行到下一个 `co_yield` 或结束，`current_value_` 指针悬垂——最终读取到垃圾值，没有编译错误，只有运行时 UB。
- 把 `basic_const_iterator<I>` 当作"在 I 上加 const"的别名：`const std::vector<int>::iterator` 的 `operator*` 仍然返回 `int&`（可写），这与 `basic_const_iterator` 的 `const int&` 完全不同。
- 模板膨胀提醒：管道类型名里的每一层 view 都会在编译器错误信息里完整展开，调试一个五层管道的类型错误时，终端可能被一行几百字符的类型名淹没——遇到这种情况，及时用 `auto` + 类型打印辅助工具缩短诊断。
- `elements_of` 的语义是"递归 yield 嵌套 generator 的每个值"，不是"yield 一个 range 对象本身"——如果你以为 `co_yield sub_gen` 就能嵌套产出，会直接编译失败（generator 的 yield_value 不接受 generator 类型，除非走 elements_of 重载）。

### 复盘问题

1. 如果 `initial_suspend` 返回 `suspend_never`，generator 的构造行为会发生什么变化？（提示：协程体在 `my_generator` 构造完成之前就开始执行）
2. `yield_value` 为什么存地址而不存值的拷贝？（提示：generator 的 yield 语义是"暂停并让调用方读取值"，不是"把值交给调用方拥有"）
3. `std::generator` 是 move-only 的（不可拷贝），这与 `filter_view` 的可拷贝性形成对比——根本原因是什么？（提示：协程句柄的唯一所有权 vs view 的借用语义）
4. `basic_const_iterator<I>` 的 `iterator_concept` 应该等于 I 的 `iterator_concept`，还是降级？（提示：const 化只影响解引用的可变性，不影响随机访问能力）
5. 模板膨胀在什么场合会真正成为工程问题，而在什么场合可以忽略？（提示：TU 边界、头文件 include 范围、是否有公开 API 暴露管道类型）

## 做完模块 H 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- `__non_propagating_cache` 的拷贝清空不是为了性能，而是 view 值语义的守护者：两个独立的 view 对象必须有独立的迭代状态，缓存不能传播。
- `filter_view::begin()` 是非 const 成员，这是正确的，不是缺陷。C++23 的 `views::as_const` 无法修复这一点，它们解决的是两个正交的问题。
- `common_iterator<I, S>` 是"C++20 ranges 与 C++17 算法"之间的 adapter 层。它的代价是每次 `operator==` 需要检查 variant 状态，但只在需要传给 C++17 算法时使用。
- `iter_move` 和 `iter_swap` 是 proxy iterator 必须定制的两个 CPO。没有它们，`ranges::sort` 这类依赖正确 move/swap 语义的算法对 proxy iterator 要么编译失败，要么产生静默的语义错误。
- `basic_const_iterator<I>` 是包装器，让 `operator*` 返回 `const T&`。`const I`（在 iterator 变量上加 const）根本不解决这个问题——`const vector<int>::iterator` 的解引用仍然是 `int&`。
- `std::generator` 的 `initial_suspend = suspend_always` 让它惰性启动；`final_suspend = suspend_always` 让"协程已结束"状态可被安全读取；`yield_value` 存地址返回 `suspend_always` 保证值在被读取前不被销毁。这三条规则缺一不可，任意一条改错都是 UB。
- 模板膨胀是深管道的隐性代价：每层 view adaptor 产生新类型，五层管道 = 五个不同模板实例。在 TU 边界传递时，及早用 `ranges::to` 物化或考虑 `any_view` 类型擦除。

到这里，你已经覆盖了标准库 ranges 源码里几乎所有"为什么要这样写而不是那样写"的微观决策。读懂这三道题，你就能在 libstdc++ / libc++ / MSVC STL 的 view 实现里认出每一种模式，并知道它背后守护的是哪条语义约束。
