# 02 顺序容器：连续、分段、节点和适配器

顺序容器解决同一个基础问题：按顺序保存一组元素。但它们给调用者的承诺不同。`array` 固定容量，`vector` 连续且可增长，`deque` 分段连续，`list` 和 `forward_list` 用节点保存元素，`stack` 和 `queue` 则把底层容器裁剪成受限接口。容器选择不是偏好题，而是把访问方式、插入位置、借用稳定性、内存局部性和异常边界放在一起取舍。

本章只讲顺序容器和两个简单适配器。关联容器、无序容器、堆和算法会在后续基础章继续展开。

## `std::array`：容量是类型的一部分

`std::array<T, N>` 是固定大小对象。它不分配堆内存，元素直接在 `array` 对象内部。`N` 是类型参数，所以 `std::array<int, 3>` 和 `std::array<int, 4>` 是不同类型。

这带来两个直接后果：

- `size()` 是常数，且编译期已知。
- 不能 `push_back`，因为容量不会变化。

`array` 适合“数量本来就是契约”的场景：三维坐标、固定颜色通道、小型查找表、协议头里的固定字段。它不适合“先不知道会有多少条记录”的输入。

## `std::vector`：连续存储和增长成本

`vector<T>` 的核心价值是连续存储。`data()` 返回首元素地址，`operator[]` 可以用地址加偏移访问任意元素。排序、二分、批量复制、传给 C API、构造 `std::span`，都直接受益于连续性。

代价也来自连续性。中间插入或删除会移动后面的元素；容量不足时，增长必须申请新连续块，再把旧元素搬过去。增长之后，旧的指针、引用、迭代器可能全部失效。

这就是 `reserve` 的意义。它不是让元素变多，而是提前买够存储位置：

```cpp
std::vector<int> v;
v.reserve(1000);   // capacity 至少 1000，size 仍是 0
v.push_back(1);    // 在已获得的存储里构造第一个元素
```

如果你知道最多会插入多少元素，`reserve` 是最小的正确工具。它比自写缓存层简单，也比事后解释扩容抖动可靠。

## `std::deque`：两端增长更稳，整体不连续

`deque<T>` 支持两端高效插入删除。常见实现是分段存储：内部维护若干固定大小块，再用一个控制结构定位块。它不像 `vector` 那样保证所有元素在一整段连续内存里，所以没有 `data()`。

这换来一个不同的成本结构：

- `operator[]` 仍是常数时间，但比 `vector` 多一层块定位。
- 两端 `push_front` / `push_back` 不需要搬迁所有旧元素。
- 中间插入仍然可能移动较多元素。

如果你需要频繁从两端进出，`deque` 是 `queue` 默认底层容器的合理选择。如果你需要把元素作为一段连续内存交给系统调用、图形 API 或 SIMD 批处理，`deque` 就不合适。

## `std::list` 与 `std::forward_list`：节点稳定性换局部性

`list<T>` 是双向链表。每个节点独立保存元素和前后指针。给定位置迭代器时，插入和删除节点是常数时间，并且不会移动其他元素。已有元素的引用和迭代器通常保持有效，只有被删掉的那个元素失效。

`forward_list<T>` 是单向链表，只能向前走。它少一个反向指针，节点更小，但很多操作要用“前一个位置”表达，比如 `insert_after`、`erase_after`。

链表的代价同样明确：

- 不能随机访问第 i 个元素。
- 每个元素有额外指针开销。
- 遍历时跳来跳去，局部性通常差。

所以“链表插入 O(1)”不是万能理由。如果你为了找到插入位置先线性搜索，再插入一个节点，完整操作仍是 O(n)。只有调用者已经持有位置迭代器，节点插入的 O(1) 才真正有意义。

## `std::span` 与 `std::string_view`：借用，不拥有

`span<T>` 和 `string_view` 不是容器。它们不拥有元素，只保存指针和长度一类的视图状态。它们的拷贝、移动和析构都是 O(1)，但它们不能让底层对象多活一秒。

```cpp
std::vector<int> v{1, 2, 3};
std::span<int> s = v;
```

`s` 指向 `v` 的连续存储。只要 `v` 不销毁、不重分配，`s` 就能观察这段元素。若 `v.push_back` 触发重分配，`s.data()` 保存的旧地址就不再可用。正确教学反例应只比较重分配前后的地址，不解引用旧 span；解引用已经失效的借用就是未定义行为。

`string_view` 对字符串也一样。它适合参数传递和只读切片，不适合存进长期结果对象，除非你能证明底层字符缓冲比结果对象活得更久。

## `stack` 与 `queue`：容器适配器

`std::stack<T>` 和 `std::queue<T>` 不是新的存储结构，它们是容器适配器。默认底层通常是 `deque<T>`，但公开接口只暴露栈或队列允许的操作。

`stack` 只让你看顶部、压入、弹出；`queue` 只让你看队头/队尾、入队、出队。它们的价值是限制使用者，不让调用者依赖底层容器的随机访问或遍历细节。

如果你的算法需要“取最大元素”，别把 `queue` 硬改成每次线性扫描；后续堆和 `priority_queue` 会给出对应模型。如果你的算法需要遍历全部元素，`stack`/`queue` 的受限接口反而碍事，直接选择底层容器更清楚。

## 反例：为了稳定引用而默认用链表

很多人听到“vector 扩容会让引用失效”，就直接换 `list`。这通常是过度反应。先问：

- 元素数量是否能预估？能就 `reserve`。
- 是否真的长期保存元素引用？如果只是循环内部临时引用，不受扩容影响。
- 热路径是否主要遍历和排序？如果是，`vector` 的连续性通常更重要。
- 插入位置是否已经由迭代器给出？如果不是，链表仍要搜索。

只有当节点稳定性是硬契约，且插入删除位置已经可得，链表才常常胜出。否则它只是把扩容问题换成局部性和额外分配问题。

## 实验

`L02_sequence_containers` 会构造小输入并观察：

- `array` 的大小固定。
- `vector` 预留容量后 push 不改变 `data()`，超过容量后可能改变 `data()`。
- `deque` 可以两端 push，且不是连续容器。
- `list` 在插入其他节点后，旧元素地址保持不变。
- `forward_list` 使用 `insert_after`/`erase_after` 表达位置。
- `stack`/`queue` 隐藏遍历和随机访问，只保留受限接口。

这些观察是行为入口，不是性能排名。真正的大输入成本要在后续实验里分开计数、计时和解释。

## 解析

顺序容器的第一选择常常是 `vector`，因为连续存储给访问、遍历、排序和跨接口传递提供了最简单的契约。偏离 `vector` 时要能说出硬理由：固定容量用 `array`；两端增长用 `deque`；节点稳定和给定位置插入删除用 `list`；只需向前链式结构用 `forward_list`；只想暴露后进先出或先进先出时用 `stack`/`queue`。

容器不是孤立 API。它们和复杂度、失效、异常安全、ranges 借用语义绑定在一起。下一章会把“哪些操作会让指针、引用和迭代器失效”单独拿出来，因为这是使用容器时最容易写错、也最难靠小样例撞出来的问题。
