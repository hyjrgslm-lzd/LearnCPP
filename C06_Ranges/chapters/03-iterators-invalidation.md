# 03 迭代器与失效：能走到哪里，何时不再有效

迭代器是“当前位置”的对象。它可以像指针一样解引用和前进，但它不是单纯指针；它的能力、比较方式和失效规则都由所属 range 或容器决定。容器修改以后，旧迭代器、指针、引用是否还能用，是容器契约的一部分。

本章只建立顺序容器和借用视图的失效矩阵。关联容器和无序容器后续再补。重点不是背表，而是理解失效来自哪里：连续存储会搬迁，节点结构会删除节点，分段结构会重排控制块，view 借用底层对象而不延长它的生命期。

## 三种东西要分开

同一个元素可以被三种句柄指向：

- 指针：例如 `int* p = v.data();`
- 引用：例如 `int& r = v[0];`
- 迭代器：例如 `auto it = v.begin();`

它们经常一起失效，但不是永远一起。`deque` 两端插入会让迭代器失效，但对已有元素的引用通常仍可用。`list` 插入新节点不会让旧节点迭代器失效，删除某个节点只让被删节点失效。`vector` 一旦重分配，旧指针、引用、迭代器全部指向旧存储，不能再用。

教学代码必须避免“用 UB 证明失效”。正确做法是比较操作前后 `data()`、地址或返回的合法新迭代器；不要解引用已经失效的旧句柄。

## 能力：iterator concept 与算法前提

ranges 算法通过 concept 表达迭代器能力。大致可以从弱到强理解：

- `input_iterator`：能读一次，适合单遍消费。
- `forward_iterator`：能多遍走同一序列。
- `bidirectional_iterator`：能前进也能后退。
- `random_access_iterator`：能跳转 `it + n`。
- `contiguous_iterator`：元素在连续内存里，能形成指针级连续视图。

能力越强，算法能做的事越多。二分查找只要求有序 forward range 也能工作，但在 random access 上才能直接跳中点；排序需要 random access，因为它要频繁交换和跳转。`list` 有双向迭代器，但没有随机访问，所以不能直接 `std::ranges::sort(list)`；它有自己的成员 `sort()`，利用节点重接完成排序。

## 顺序容器失效矩阵

下面是本阶段需要掌握的基础矩阵，省略 allocator 传播和实现扩展细节：

| 容器 | 操作 | 指针/引用 | 迭代器 |
|---|---|---|---|
| `array` | 元素赋值 | 仍指向同一元素 | 仍有效 |
| `vector` | 不扩容的尾插 | 旧元素引用通常有效，`end()` 变 | `end()` 失效 |
| `vector` | 扩容 | 全部失效 | 全部失效 |
| `vector` | 中间插入/删除 | 位置及之后失效 | 位置及之后失效 |
| `deque` | 两端插入 | 旧元素引用通常有效 | 迭代器失效 |
| `deque` | 中间插入/删除 | 多数句柄可能失效 | 多数句柄可能失效 |
| `list` | 插入其他节点 | 旧节点引用有效 | 旧节点迭代器有效 |
| `list` | 删除节点 | 被删节点失效 | 被删节点失效 |
| `forward_list` | `insert_after` 其他节点 | 旧节点引用有效 | 旧节点迭代器有效 |
| `forward_list` | `erase_after` | 被删节点失效 | 被删节点失效 |

“通常有效”在课程实现里要写成当前容器契约能支持的范围。对于 `vector`，只要不重分配，旧元素地址保持；但中间插入会移动位置及之后元素，所以那些位置的引用不能继续表示原来的元素。对于 `deque`，分段结构让迭代器更脆弱，哪怕引用仍指向同一对象，也不要假设旧迭代器能继续走。

## 借用：`span` 和 `string_view` 的边界

`std::span<T>`、`std::string_view`、`std::ranges::subrange` 这类对象经常被称为借用视图。它们的迭代器有效性依赖底层存储，不依赖 view 对象本身。销毁一个 `span` 不会销毁元素；但销毁底层 `vector`、让 `vector` 扩容，或让字符串缓冲离开作用域，都会让借用失效。

这和 ranges 的 `borrowed_range` 直接相关。`std::span<int>` 是 borrowed range，因为从右值 span 取出的迭代器仍指向外部数组；`std::vector<int>` 不是 borrowed range，因为右值 vector 表达式结束时会销毁自己的元素。

```cpp
std::span<int> make_span(std::vector<int>& v) { return v; }
```

这个函数只在调用者保证 `v` 继续存在且不重分配时安全。`span` 不是所有权转移，也不是生命周期延长器。

## 反例：缓存 `begin()` 后修改容器

下面写法看起来很自然：

```cpp
auto it = v.begin();
v.push_back(42);
use(*it);
```

如果 `push_back` 触发扩容，`it` 已经失效，`*it` 是未定义行为。如果容量足够，`it` 可能仍有效。问题在于这段代码没有把“容量足够”写成前提，也没有在修改后重新获取迭代器。

最小修复通常不是加一层封装，而是把顺序写清楚：

```cpp
v.reserve(v.size() + 1);
auto it = v.begin();
v.push_back(42);
use(*it); // 这里依赖 reserve 后本次尾插不扩容
```

或者更简单：修改容器后重新取迭代器。

## 实验

`L02_sequence_containers` 的失效部分只做安全观察：

- 对 `vector`，记录扩容前 `data()`，扩容后只比较地址是否改变，不读旧地址。
- 对不扩容尾插，比较第一个元素地址仍相同。
- 对 `list`，保存旧节点地址，插入新节点后比较旧地址仍相同。
- 对 `forward_list`，使用 `erase_after` 返回后的合法结构验证删除结果。
- 对 `span`，记录它借用 `vector` 的 `data()`，再用 `reserve` 说明重分配会让旧 span 的地址过期；不解引用旧 span。

## 解析

失效规则是容器选择的一部分。你保存的是元素值，就让容器自由移动；你保存的是迭代器或指针，就必须约束后续修改；你传出的是 `span` 或 `string_view`，就必须说明底层 owner 活多久、期间是否允许重分配。

ranges 管道会放大这个问题，因为 view 往往只保存底层 range 的引用、迭代器、谓词和缓存。底层容器一变，view 不会替你修复旧状态。后续讲 `borrowed_range`、`dangling`、`filter_view` 缓存和自定义 view 时，这一章的规则就是基础。
