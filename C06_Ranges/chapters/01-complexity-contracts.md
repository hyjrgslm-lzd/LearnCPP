# 01 复杂度契约：不是跑得快，而是承诺成本上界

标准库容器和算法的复杂度不是一句性能建议，而是接口契约的一部分。调用者选择 `vector`、`list`、`sort` 或 `find` 时，依赖的不只是函数名和返回值，还依赖“输入扩大后成本怎样增长”。如果一个接口说随机访问是常数时间，调用者才敢在二分查找、堆调整和索引表里反复下标访问；如果一次插入可能移动后面所有元素，调用者就不能把它写进内层热点循环后再期待链表式成本。

本章先建立三种最常用的复杂度词汇：最坏、平均、摊还。它们回答的是不同问题。

最坏复杂度问：“任意一次调用，最多要付多少成本？” `std::vector::operator[]` 是 O(1) 最坏复杂度，因为取第 0 个和第 100000 个元素都只做一次地址计算。`std::vector::insert(begin(), x)` 是 O(n) 最坏复杂度，因为它必须给新元素腾出首位，后面的所有元素都要移动或复制。

平均复杂度问：“在声明的输入分布或数据结构状态下，期望成本是多少？” 哈希表查找常说平均 O(1)，前提是哈希函数把 key 分散得足够均匀，桶数量与元素数量保持合理比例。这个平均不是“我这次测得很快”，而是绑定到哈希、相等比较和装载因子的模型。

摊还复杂度问：“一串操作合起来平均到每次是多少？” `std::vector::push_back` 在容量够时是 O(1)，容量满时要重新分配并搬迁全部旧元素，是 O(n)。但如果容量按倍数增长，连续 push N 次总搬迁次数仍是 O(N)，所以每次摊还 O(1)。

## 从一次慢调用到一串便宜调用

看一个只记录操作次数的简化动态数组。容量从 0 开始，每次满了就翻倍：

```cpp
capacity: 0 -> 1 -> 2 -> 4 -> 8 -> 16
push #1  搬 0 个旧元素
push #2  搬 1 个旧元素
push #3  搬 2 个旧元素
push #5  搬 4 个旧元素
push #9  搬 8 个旧元素
```

到第 16 次 push 为止，真正插入新元素做了 16 次，旧元素搬迁只发生在容量增长点，总数是 `1 + 2 + 4 + 8 = 15`。总成本小于 `2N`，所以每次摊还是常数。

这不表示每一次 `push_back` 都是常数时间。第 9 次 push 仍然会搬 8 个旧元素。摊还只允许你对一串操作做预算，不能保证单次延迟稳定。如果你的系统在实时音频回调、游戏帧预算或交易撮合热路径中不能接受某次突然搬迁，就要提前 `reserve`、使用固定容量容器，或换成不会搬迁整段连续存储的结构。

## 复杂度由公开操作定义

复杂度要按调用者看到的完整操作计算，不能只挑底层一步。比如“数组下标是 O(1)”不等于“向数组头部插入是 O(1)”。头插包含腾位置、移动旧元素和构造新元素。完整公开操作是 O(n)。

类似地，“链表插入节点是 O(1)”也不等于“按第 i 个位置插入是 O(1)”。如果接口只给你 `i`，它必须先从头走到第 i 个节点，这一步是 O(n)。只有在调用者已经持有目标位置迭代器时，链表插入才是 O(1)。

这也是容器章节反复强调接口前提的原因。同一个 `insert`，当输入是位置迭代器和当输入是整数下标，复杂度不是同一个问题。

## 平均复杂度要写出假设

`std::unordered_map` 的查找通常按平均 O(1) 理解，但这个说法有条件：

- `hash(key)` 本身不能太贵。
- 哈希值要让 key 分布到不同桶。
- `key_equal` 必须能正确判断等价 key。
- 容器需要在装载因子过高时 rehash。

如果所有 key 都落到同一个桶，查找就会退化成在桶链里线性搜索，最坏 O(n)。这不是实现“偷懒”，而是哈希表契约本来就有平均与最坏两条边界。生产代码如果处理外部输入 key，还要额外考虑攻击者构造冲突的情况；课程这里只建立容器成本模型，不展开安全哈希策略。

## 反例：把摊还当最坏

下面这段逻辑在吞吐型批处理里通常没问题：

```cpp
std::vector<int> ids;
for (int id : input) {
    ids.push_back(id);
}
```

如果 `input` 有 N 个元素，且 `vector` 按倍数增长，总体插入成本摊还是 O(N)。但如果这段代码每处理一个网络包就执行一次，并且包处理延迟有硬上限，某一次扩容就可能越过时限。正确改法不是换个更复杂的数据结构，而是先说明约束：能否预知上限？能就 `reserve(max_packets)`；不能就选择允许分段增长、引用稳定性更好的结构，并接受遍历局部性下降。

## 实验：计数比计时更先行

性能实验常犯的错误是先跑总耗时，再把原因猜成“缓存更好”“分配更少”。本课程的基础练习先做操作计数：比较线性查找、二分查找、尾部 push 摊还和头部插入搬迁。计数不能代表真实 CPU 时间，但它能先回答“算法层级有没有搞错”。如果 O(n) 和 O(log n) 的比较次数都没数清，直接看毫秒数只会把编译器、缓存、分支和系统噪声混在一起。

本章练习 `L01_complexity` 使用固定输入，检查：

- 线性查找最坏要检查全部元素。
- 二分查找比较次数随 N 缓慢增长。
- 翻倍增长的动态数组连续 push N 次，总搬迁次数小于 N。
- 头部插入 N 次移动次数是 `0 + 1 + ... + N-1`，不是摊还常数。

## 解析

读复杂度表时先问四件事：

1. 这是最坏、平均还是摊还？
2. 输入规模 n 指什么，是元素数、桶数、字符数，还是要插入的区间长度？
3. 操作前提是什么，调用者是否已经有迭代器、是否已排序、容量是否足够？
4. 这个复杂度是否包含元素构造、移动、比较、哈希和分配？

`vector::push_back` 的摊还 O(1) 与 `vector::insert(begin())` 的 O(n) 不冲突；它们不是同一个公开操作。`unordered_map::find` 的平均 O(1) 与最坏 O(n) 也不冲突；它们绑定到不同分布假设。把这些边界说清，后面讨论容器选择、迭代器失效和 ranges 惰性求值时，才不会把局部现象误读成通用保证。
