# 04 模块 C1：结构适配器

## 模块目标

前两个模块（模块 A 视图工厂与惰性、模块 B 基础适配器与管道）建立了"单层线性管道"的直觉：数据源进来，经过一排变换，从另一端流出。这个模块开始进入另一层：**改变 range 的形状本身**。

你会遇到把多层嵌套压平的 `views::join`，会遇到把序列按分隔符切分成子范围的 `views::split`（以及它在 C++20 和 C++23 之间令人困惑的语义演变），还会遇到把 iter/sentinel 类型不同的 view 整理成 begin/end 同类型的 `views::common`，以及反转、元素投影这一组"结构整理"适配器。

这些适配器的共同特点是：它们不只是对每个元素做映射或过滤，而是**重新组织迭代器的推进方式**，因此对 iterator_concept 的影响比 `transform` 或 `filter` 更复杂。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- `views::join` 把 range-of-ranges 拍平时，外层迭代器和内层迭代器如何合成出 `join_view` 的迭代器，以及为什么 `join` 之后通常无法保留 random access。
- 修订后 `views::split` 与 `views::lazy_split` 的差异：P2210R2 已作为 C++20 DR 采纳，旧惰性设计由 `lazy_split` 承接，修订后的 `split` 在连续底层上保留真实迭代器。
- `views::common` 的必要场景：当 iter 类型与 sentinel 类型不同的 view 需要传给 C++17 风格算法时，如何用它统一 begin/end 类型。
- `views::reverse` 为什么要求 `bidirectional_range`，以及它对 iterator_concept 的影响。
- `views::elements<N>` / `views::keys` / `views::values` 对 tuple-like 元素的投影语义，以及对右值 map 取 `views::values` 时的 borrowed 状态与悬垂风险。

## 练习 C1-1：join 与嵌套 range 的拍平

### 目标

观察 `views::join` 对 range-of-ranges 的拍平行为，并理解外层 / 内层迭代器概念如何合成出 `join_view` 的最终迭代器概念。

### 前置理解

- 你已经理解 01 心智模型中 iterator / sentinel 分离的设计意图：`begin()` 和 `end()` 可以是不同类型，view 只承诺能用 `!=` 比较它们。
- 你知道 view 的三条语义公理（O(1) move / O(1) copy / O(1) destroy），以及 `views::filter` 的迭代器概念由底层决定、最高裁顶到 `bidirectional_iterator`。
- 你接受这题的重点是"迭代器概念合成规则"，而不是数据处理性能。

### 预计练习方向

**基础任务**

1. 构造一个 `std::vector<std::vector<int>>`，内容可以是 `{{1,2,3},{4,5},{6}}`。
2. 用 `views::join` 拍平，用 for-range 循环消费，确认输出为 `1 2 3 4 5 6`。
3. 在代码注释里标注：`join_view` 的 `begin()` 类型和 `end()` 类型是否相同？

```cpp
// C++20
#include <ranges>
#include <vector>
#include <iostream>

int main() {
    std::vector<std::vector<int>> nested = {{1,2,3},{4,5},{6}};

    auto flat = nested | std::views::join;

    for (int x : flat) {
        std::cout << x << ' ';  // 1 2 3 4 5 6
    }
    std::cout << '\n';

    // join_view 的迭代器概念：
    // 外层 vector<vector<int>> 是 random_access_range
    // 内层 vector<int> 也是 random_access_range
    // 但 join_view 的迭代器只能是 bidirectional_iterator
    // 原因见"观察点"
}
```

4. 换一个更有意思的嵌套结构：用 `views::iota` 生成嵌套范围，再 `join`：

```cpp
// C++20
#include <ranges>
#include <iostream>

int main() {
    // iota(1,4) 产生 1, 2, 3
    // transform 把每个 n 变成 views::iota(0,n)：
    //   1 -> [0]
    //   2 -> [0,1]
    //   3 -> [0,1,2]
    // join 拍平：0, 0,1, 0,1,2
    auto nested = std::views::iota(1, 4)
                | std::views::transform([](int n) {
                      return std::views::iota(0, n);
                  });

    auto flat = nested | std::views::join;

    for (int x : flat) {
        std::cout << x << ' ';  // 0 0 1 0 1 2
    }
    std::cout << '\n';
}
```

5. 用 `static_assert` 或类型打印验证 `join_view` 的迭代器概念：

```cpp
// C++20
#include <ranges>
#include <vector>

int main() {
    std::vector<std::vector<int>> nested = {{1,2},{3,4}};
    auto flat = nested | std::views::join;

    using It = decltype(flat.begin());

    // join_view 迭代器：外层 random_access + 内层 random_access -> bidirectional
    static_assert(std::bidirectional_iterator<It>);
    static_assert(!std::random_access_iterator<It>);

    // stored vector<vector<int>> 的内外层都是 common_range，
    // 所以这个 join_view 也是 common_range，begin/end 同型。
    static_assert(std::same_as<decltype(flat.begin()), decltype(flat.end())>);
    static_assert(std::ranges::common_range<decltype(flat)>);
}
```

如果要观察非 common 的边界，不要用上面的 stored-inner-range 例子。单列一个 iter/sentinel 异型的 range 更直接：

```cpp
// C++20
#include <ranges>

int main() {
    auto r = std::views::iota(0)
           | std::views::filter([](int x) { return x % 2 == 0; })
           | std::views::take(4);

    static_assert(!std::same_as<decltype(r.begin()), decltype(r.end())>);
    static_assert(!std::ranges::common_range<decltype(r)>);
}
```

### 进阶任务

**join_with（C++23）**

`views::join_with(delim)` 在 C++23 中由 P2441R2 引入。它在拍平的同时，在每个内层范围之间插入分隔符。

```cpp
// C++23: -std=c++23
#include <ranges>
#include <vector>
#include <iostream>
#include <string>

int main() {
    std::vector<std::string> words = {"hello", "world", "ranges"};

    // join_with 在每个子范围之间插入 '-'
    auto with_sep = words | std::views::join_with('-');

    for (char c : with_sep) {
        std::cout << c;   // hello-world-ranges
    }
    std::cout << '\n';

    // 对比：纯 join 直接拼接，无分隔符
    auto no_sep = words | std::views::join;
    for (char c : no_sep) {
        std::cout << c;   // helloworldranges
    }
    std::cout << '\n';
}
```

对比 `join_with` 和手工拼接的区别：`join_with(delim)` 是一个惰性适配器，分隔符在迭代过程中按需"插入"，不产生中间字符串。如果用 `join | transform(prepend-delim) | join` 的方式模拟，则需要多层嵌套且语义容易出错（第一个元素前也会有分隔符）。`join_with` 的语义是"内层范围之间"而非"每个内层范围之前"，两者有本质差异。

### 验收点

- 你能输出两段代码的正确结果，并指出真正触发迭代的是哪一行。
- 你能用 `static_assert` 证明 `join_view` 的迭代器最高是 `bidirectional_iterator`。
- 你能解释为什么即使内外层都是 `random_access_range`，`join_view` 也无法保留 random access。
- 你能说出 `join_with` 的分隔符插入时机（在相邻内层范围之间，而非每层之前/之后）。

### 观察点

- `join_view` 迭代器推进时，需要同时维护外层迭代器和内层迭代器的状态。推进一步时，先推进内层迭代器；当内层到达末尾时，推进外层迭代器并重置内层。这个"两层状态"的结构决定了迭代器只能双向，无法随机跳跃：要跳到第 k 个元素，没有 O(1) 的方法，必须逐步推进。
- `join_view` 迭代器概念合成规则（完整版）：要达到 `bidirectional_iterator`，必须同时满足——外层是 `bidirectional_range`、外层 `reference` 是**左值引用**（即内层 range 存在于外层之外，不是 prvalue）、内层是 `common_range` 且 `bidirectional_range`；否则只有 `forward_iterator`；外层是 `input_range` 则只有 `input_iterator`。注意"外层 reference 必须是 lvalue reference" 这一条——如果外层是 `transform` 返回 prvalue view，join 必须内部缓存当前内层，迭代器会被进一步降级。random access 在任何情况下都无法达到。
- `join_view` 是否是 `common_range` 取决于底层条件：stored `vector<vector<int>>` 这类内外层都是 common 的例子通常仍是 common，`begin()` / `end()` 同型；外层或内层引入独立 sentinel 时才会变成非 common。如果需要传给 C++17 风格算法，先实测 `common_range`，不满足时再用 `views::common` 包装（见练习 C1-3）。
- 当内层 range 是 xvalue（右值 view，例如 `transform` 返回的临时 `iota_view`）时，`join_view` 内部需要缓存当前内层 range 的副本（因为不能对同一个右值调用两次 `begin()`）。这个缓存是 join_view 内部状态的一部分，与模块 A 中 `filter_view::begin()` 缓存第一个元素位置的机制类似——都是为了保证迭代行为的正确性。cppreference 把这类情况描述为"inner references"问题：被缓存的内层 view 本身的生命周期需要你格外注意。

### 常见坑

- 期望 `join` 后能随机访问（`flat[5]`）：`join_view` 不是 `random_access_range`，不支持下标访问。
- 没有实测就把 `join` 后的 view 当成非 common：stored `vector<vector<int>> | views::join` 是 common；真正需要 `views::common` 的是 begin/end 异型的 range。
- 当内层 range 是 `transform` 返回的临时 view（xvalue）时，不理解为何 `join_view` 需要内部缓存，误以为这是 bug。
- 混淆 `join_with(sep)` 与"在每个元素前加分隔符"：`join_with` 是在相邻内层范围之间插入，第一个内层范围之前没有分隔符。

### 提示

- 用 `typeid(...).name()` 或 `__PRETTY_FUNCTION__` 打印迭代器类型，可以直观看到 `join_view` 内部的迭代器结构。
- 先不要纠结 join_with 的分隔符类型：它可以是单个字符，也可以是 range。先用单字符版本，跑通后再尝试 range 版本。
- 如果你的编译器 C++23 支持不全，可以先跳过 join_with，只做基础任务和 `static_assert` 验证。
- 迭代器概念合成规则不需要死记：只需记住"join 之后最高只有 bidirectional"，原因是两层状态无法 O(1) 随机跳跃。

### 复盘问题

- `join_view` 迭代器的"两层状态"（外层迭代器 + 内层迭代器）为什么决定了不能随机访问？
- 如果内层 range 是 `forward_range` 而非 `bidirectional_range`，`join_view` 的迭代器概念会是什么？
- 为什么不能说 `join_view` 一定不是 `common_range`？哪些底层条件会让 begin/end 保持同型，哪些条件会让它变成 iter/sentinel 异型？
- `join_with` 与手工 `for` 循环插入分隔符相比，惰性体现在哪里？什么时候才真正访问字符数据？

## 练习 C1-2：split 与 lazy_split 的历史差异

### 目标

直面标准演化和 DR 带来的实现差异：P2210R2 已作为 C++20 缺陷修正采纳，修订后的 `views::split` 会为连续底层产生连续 subrange；旧设计保留为 `views::lazy_split`。本题验证的是 `split` 与 `lazy_split` 的设计差异，不是简单按 `-std=c++20` / `-std=c++23` 切换。

### 前置理解

- 你已经读过 `references/standards.md` 的 split/lazy_split 边界：N4893 LWG poll 20 将 P2210R2 作为 C++20 DR 采纳，不能假定切换 `-std=c++20` 就恢复旧 split 行为。
- 你理解 P2210R2 的处理方式不是"删掉旧 split"，而是"改名保留"：旧设计目标通过 `views::lazy_split` 保留，修订后的 `views::split` 更贴近字符串切分直觉。
- 你接受这题的目的不是"选哪个更好"，而是"亲眼看到差异"。

### 预计练习方向

**第一步：lazy_split（旧 split 设计目标）行为**

在当前编译器下用 `views::lazy_split`，观察子范围的类型。不要把 `-std=c++20` 当作旧行为开关；标准库可能已经应用 DR。

```cpp
// lazy_split：保留旧 split 设计目标
#include <ranges>
#include <string_view>
#include <iostream>

int main() {
    std::string_view sv = "hello,world,ranges";

    // lazy_split 子范围不是 string_view，是一个特殊的 forward range
    auto parts = sv | std::views::lazy_split(',');

    for (auto subr : parts) {
        // subr 不是 string_view，不能直接用 std::string(subr)
        // 必须手动收集字符：
        for (char c : subr) {
            std::cout << c;
        }
        std::cout << '|';
    }
    std::cout << '\n';
    // 输出：hello|world|ranges|

    // 验证子范围的迭代器概念：
    auto first_part = *parts.begin();
    using SubIt = decltype(first_part.begin());
    static_assert(std::forward_iterator<SubIt>);
    // lazy_split 的子范围是 forward_range，不是 contiguous_range
}
```

**第二步：修订后的 split 行为**

```cpp
// 修订后的 views::split：连续底层产生连续 subrange，可直接构造 string_view
#include <ranges>
#include <string_view>
#include <iostream>
#include <string>

int main() {
    std::string_view sv = "hello,world,ranges";

    // views::split：子范围支持 string_view 构造
    auto parts = sv | std::views::split(',');

    for (auto subr : parts) {
        // 修订后 split 的子范围是 subrange<iterator_t<V>, iterator_t<V>>，
        // 继承底层 view 的迭代器类别——对 string_view 底层，子范围迭代器就是 const char*。
        // 因此可以直接构造 string_view：
        std::string_view word(subr.begin(), subr.end());
        std::cout << word << '|';
    }
    std::cout << '\n';
    // 输出：hello|world|ranges|

    // 验证：子范围迭代器继承底层迭代器类别。
    // 仅当底层是 contiguous_range 时，这一断言才成立。
    auto first_part = *parts.begin();
    using SubIt = decltype(first_part.begin());
    static_assert(std::contiguous_iterator<SubIt>);  // 来自底层 string_view 的 const char*
}
```

**第三步：对比子范围的类型差异**

```cpp
// C++23: -std=c++23
#include <ranges>
#include <string_view>
#include <type_traits>

int main() {
    std::string_view sv = "a,b,c";

    // lazy_split（旧设计目标）：子范围是特殊 forward range
    auto lazy_parts = sv | std::views::lazy_split(',');
    auto lazy_first = *lazy_parts.begin();
    // lazy_split 子范围不是 contiguous_range
    static_assert(!std::ranges::contiguous_range<decltype(lazy_first)>);
    static_assert(std::ranges::forward_range<decltype(lazy_first)>);

    // 修订后 split：子范围是 subrange，保留 contiguous 性质
    auto split_parts = sv | std::views::split(',');
    auto split_first = *split_parts.begin();
    static_assert(std::ranges::contiguous_range<decltype(split_first)>);
    // 可以无痛构造 string_view：
    std::string_view word{split_first};  // 直接用 range 构造 string_view（C++23）
    (void)word;
}
```

### 进阶任务

**手动把 lazy_split_view 子范围转为 string_view**

理解为什么 C++20/lazy_split 的子范围无法直接转成 `string_view`，以及如何绕过：

```cpp
// C++20
#include <ranges>
#include <string_view>
#include <iostream>

// 把 lazy_split 子范围转为 string_view 的辅助函数
// 要求：底层是 contiguous_range（string_view 满足）
template<std::ranges::contiguous_range R>
auto subrange_to_sv(R&& r) -> std::string_view {
    return {std::ranges::data(r), std::ranges::size(r)};
}

int main() {
    std::string_view sv = "foo,bar,baz";

    // lazy_split 子范围不能直接用 string_view 构造，
    // 因为子范围的 begin() 不是 contiguous_iterator
    // 但底层 string_view 是 contiguous，
    // 可以通过 ranges::data + ranges::size 重建：
    auto parts = sv | std::views::lazy_split(',')
                    | std::views::transform([](auto subr) {
                          // subr 是 lazy_split 的子范围
                          // 注意：这里需要 ranges::data/size，而非直接构造
                          // 以下写法在 C++20 下可能编译失败，
                          // 因为 subr 不满足 contiguous_range
                          // 改用 common 化后再收集：
                          std::string result;
                          for (char c : subr) result += c;
                          return result;
                      });

    for (auto s : parts) {
        std::cout << s << '|';
    }
    std::cout << '\n';
    // 输出：foo|bar|baz|
}
```

**对比为何修订后 split 能自然支持**

修订后 `views::split` 的子范围是 `std::ranges::subrange<I, S>` 其中 `I` 继承了底层 range 的 iterator 类型。当底层是 `contiguous_range`（如 `string_view`），子范围的迭代器就是 `contiguous_iterator`，可直接构造 `string_view`。`lazy_split` 的子范围则是一个内部类型，其迭代器是独立实现的"代理迭代器"，只满足 `forward_iterator`，不传递底层的 contiguous 性质。

**用 split 切分 forward-only range**

```cpp
// C++23: -std=c++23
#include <ranges>
#include <forward_list>
#include <iostream>

int main() {
    // forward_list 是 forward_range，不是 contiguous_range
    std::forward_list<int> fl = {1, 0, 2, 3, 0, 4};

    // 修订后 split 可以处理 forward_range；子范围迭代器继承底层 forward_iterator
    auto parts = fl | std::views::split(0);
    for (auto subr : parts) {
        for (int x : subr) std::cout << x << ' ';
        std::cout << '|';
    }
    std::cout << '\n';
    // 输出：1 |2 3 |4 |

    // 子范围的迭代器概念取决于输入：forward_list -> forward_iterator
    auto first = *parts.begin();
    static_assert(std::ranges::forward_range<decltype(first)>);
    static_assert(!std::ranges::bidirectional_range<decltype(first)>);
}
```

### 验收点

- 你能分别写出 `lazy_split` 和修订后 `split` 的代码，并观察子范围类型的差异。
- 你能解释为什么 lazy_split 的子范围不能直接构造 `std::string_view`，而修订后 split 在连续底层上可以。
- 你能指出 P2210R2 选择"改名保留旧语义"而非"删除旧语义"的实际效果：两者在 C++23 下都可用，只是名字不同。
- 你能说出修订后 `split` 对输入 range 的概念要求：底层必须是 `forward_range`；子范围是 `subrange<iterator_t<V>, iterator_t<V>>`，所以它的迭代器类别由底层继承——底层是 `contiguous_range` 时子范围迭代器才是 `contiguous_iterator`，这不是 split 的独立保证，而是 `subrange` 透传的结果。

### 观察点

- `views::lazy_split` 的子范围是一个惰性代理：它的迭代器本质是"在原 range 上以分隔符为边界按需推进的游标"，因此迭代器概念只能是 `forward_iterator`，无法向上传递底层的 contiguous 性质。
- 修订后 `views::split` 的子范围是 `subrange<iterator_t<V>, iterator_t<V>>`，其中 `V` 是底层 view，迭代器类型直接取自底层。因此当底层是 `string_view`（`contiguous_range`），子范围的 `begin()` 就是 `const char*`，`string_view(subr)` 或 `string_view(subr.begin(), subr.end())` 可以构造——这两种构造法分别来自 `string_view` 的 range 构造器（要求 `contiguous_range + sized_range`）与 (iter, iter) 构造器，能成立都是因为子范围继承了底层的 contiguous 性质，不是 split 的独立保证。
- P2210R2 的改动方式不是破坏性重做：它保留了所有旧的语义，只是给它换了名字（`lazy_split`）。这对于正确理解现有代码库的迁移路径非常重要——如果你维护的旧代码依赖原始惰性 split 设计，迁移到应用 P2210R2 DR 的标准库时应显式改用 `lazy_split`；不能靠 `-std=c++20` 假定保留旧行为。
- 跨编译器行为不一致：MSVC 和 GCC 对 P2210R2 DR 与 lazy_split 的实现进度可能不同。如果某个特性无法编译，先用简单手写替代验证语义，不要把编译失败误判为"标准说错了"。

### 常见坑

- 把 `views::split` 当旧 split 设计用，误以为连续底层的子范围仍是 forward-only 代理；实现若应用 P2210R2 DR，子范围会保留 contiguous 性质。
- 在 C++20 环境下误判能否用迭代器对构造字符串：事实方向是——`std::string(It, It)` 的构造器只要求 `InputIterator`，`lazy_split` 子范围迭代器是 forward（也就满足 input），因此 `std::string(subr.begin(), subr.end())` 能编过；真正不行的是 `std::string_view(subr.begin(), subr.end())` 或 `std::string_view(subr)`，它们要求 `contiguous_iterator` / `contiguous_range + sized_range`，lazy_split 子范围两者都不满足。
- 混淆 `lazy_split` 和 `split` 的适用场景：如果需要对子范围做 `string_view` 化处理，修订后 `split` 更自然；如果只是简单迭代子范围内的元素，两者都可以。
- 期待 `split` 的分隔符可以是复杂谓词：`split` 的分隔符是一个 value 或一个 range（作为模式），不是任意谓词。如果需要按谓词分割，C++23 有 `views::chunk_by`（模块 D 会覆盖）。

### 提示

- 如果你的编译器缺少 `views::lazy_split` 或修订后 `views::split`，记录为实现能力限制；不要用标准年份推断行为。
- 当子范围需要转换为 `string` 或 `string_view` 时，先打印子范围迭代器的类型，这样你能直观看到 lazy_split vs split 的差异。
- `static_assert(!std::ranges::contiguous_range<decltype(lazy_first)>)` 是一个很直接的验证手段，不需要运行就能看出概念差异。

### 复盘问题

- P2210R2 为什么选择“旧语义由 lazy_split 承接、split 名字给修订语义”而不是另起一个新名字？这个 DR 决定对现有代码的迁移有什么影响？
- `lazy_split` 子范围的迭代器是"代理迭代器"（forward-only），而修订后 `split` 子范围的迭代器是底层 range 的真实迭代器。这两种设计在"迭代器传递 contiguous 性质"上的核心差异是什么？
- 为什么 `split` 分隔符用的是"值"或"range 模式"，而不是"谓词"？如果你想要谓词切分，应该用什么适配器？
- 如果你维护一个已依赖旧 split 设计的代码库，升级到应用 P2210R2 DR 的标准库后需要做什么改动？

## 练习 C1-3：common / reverse / elements / keys / values

### 目标

一次性把"结构投影"这一组适配器过完：`views::common`、`views::reverse`、`views::elements<N>`、`views::keys`、`views::values`。建立心智词汇，知道每个适配器的适用场景、对 iterator_concept 的影响，以及可能触发悬垂的右值 borrowed 问题。

### 前置理解

- 你已经在 01 心智模型中理解了 `common_range` 的概念：begin/end 类型相同的 range 才能直接传给 C++17 风格算法。
- 你已经在模块 B 中练习过 `views::reverse`（或即将练习），知道反转需要双向迭代器。
- 你理解 `borrowed_range`：对右值非 borrowed_range 调用返回迭代器的算法，会得到 `ranges::dangling`。

### 预计练习方向

**common：让 iter/sentinel 不同类型的 view 兼容 C++17 算法**

```cpp
// C++20
#include <ranges>
#include <algorithm>  // std::accumulate（C++17 风格）
#include <numeric>
#include <iostream>

int main() {
    // views::iota(1) 是无界序列：end() 是 unreachable_sentinel_t，类型与 begin() 不同
    // views::take(10) 截断后：end() 是 take_view 的 sentinel，仍与 begin() 不同
    auto r = std::views::iota(1) | std::views::take(10);

    // 不是 common_range，不能直接传给 C++17 的 std::accumulate
    static_assert(!std::ranges::common_range<decltype(r)>);

    // views::common 把 iter/sentinel 统一为同一类型
    auto cr = r | std::views::common;
    static_assert(std::ranges::common_range<decltype(cr)>);

    // 现在可以传给 C++17 风格算法：
    int sum = std::accumulate(cr.begin(), cr.end(), 0);
    std::cout << "sum 1..10 = " << sum << '\n';  // 55

    // 注意：C++20 ranges 算法不需要 common_range，可以直接接受 iter/sentinel 不同类型
    int sum2 = std::ranges::fold_left(r, 0, std::plus{});  // C++23
    // 或用 ranges::accumulate 等价物（注意标准没有 ranges::accumulate，
    // 用 ranges::fold_left 替代，C++23 加入）
    (void)sum2;
}
```

`views::common` 的内部机制：对于原本 iter/sentinel 同类型的 range，`common_view` 是个 no-op（直接返回原 range）；对于 iter/sentinel 不同类型的 range，它把 sentinel 包装成与 iterator 同类型的对象，使 begin/end 可以比较。包装的代价是：`common_view::end()` 返回的对象内部持有原 sentinel，每次比较时做类型转换。

**reverse：反转需要 bidirectional_range**

```cpp
// C++20
#include <ranges>
#include <vector>
#include <list>
#include <forward_list>
#include <iostream>

int main() {
    // vector 是 random_access_range -> reverse_view 的迭代器是 random_access_iterator
    std::vector<int> v = {1, 2, 3, 4, 5};
    auto rv = v | std::views::reverse;
    for (int x : rv) std::cout << x << ' ';  // 5 4 3 2 1
    std::cout << '\n';

    // list 是 bidirectional_range -> reverse_view 的迭代器是 bidirectional_iterator
    std::list<int> l = {1, 2, 3};
    auto rl = l | std::views::reverse;
    static_assert(std::ranges::bidirectional_range<decltype(rl)>);
    static_assert(!std::ranges::random_access_range<decltype(rl)>);

    // forward_list 是 forward_range -> 不能 reverse，编译错误
    // std::forward_list<int> fl = {1, 2, 3};
    // auto rfl = fl | std::views::reverse;  // 编译错误：不满足 bidirectional_range

    // reverse_view 的 iterator_concept：
    // 底层是 random_access_range -> reverse 的迭代器也是 random_access_iterator
    using RIt = decltype(rv.begin());
    static_assert(std::random_access_iterator<RIt>);

    // reverse_view 是 common_range（begin/end 同类型）：
    static_assert(std::ranges::common_range<decltype(rv)>);
}
```

`views::reverse` 的 iterator_concept 规则：`reverse_view` 的迭代器是对底层迭代器的包装（`std::reverse_iterator<I>`），其 iterator_concept 与底层 `I` 相同——如果底层是 `random_access_iterator`，反转后也是 `random_access_iterator`；如果底层是 `bidirectional_iterator`，反转后也是 `bidirectional_iterator`。

**elements / keys / values：对 tuple-like 元素的投影**

```cpp
// C++20
#include <ranges>
#include <map>
#include <vector>
#include <tuple>
#include <string>
#include <iostream>

int main() {
    // 1. views::keys / views::values 作用于 map
    std::map<std::string, int> scores = {
        {"Alice", 95}, {"Bob", 87}, {"Carol", 91}
    };

    // views::keys 取每个 pair<const string, int> 的 first
    std::cout << "Keys: ";
    for (const auto& k : scores | std::views::keys) {
        std::cout << k << ' ';
    }
    std::cout << '\n';  // Alice Bob Carol

    // views::values 取每个 pair 的 second
    std::cout << "Values: ";
    for (int v : scores | std::views::values) {
        std::cout << v << ' ';
    }
    std::cout << '\n';  // 95 87 91

    // 2. views::elements<N> 作用于 tuple range
    std::vector<std::tuple<int, std::string, double>> data = {
        {1, "foo", 1.5},
        {2, "bar", 2.5},
        {3, "baz", 3.5}
    };

    // elements<0>：取第一个元素（int）
    for (int id : data | std::views::elements<0>) {
        std::cout << id << ' ';  // 1 2 3
    }
    std::cout << '\n';

    // elements<1>：取第二个元素（string）
    for (const auto& s : data | std::views::elements<1>) {
        std::cout << s << ' ';  // foo bar baz
    }
    std::cout << '\n';

    // views::keys 等价于 views::elements<0>
    // views::values 等价于 views::elements<1>
    // 标准将 views::keys 定义为 views::elements<0> 的别名（keys_view = elements_view<V, 0>），
    // 因此 same_as 成立，不只是"语义等价"。values / elements<1> 同理。
    static_assert(std::same_as<
        decltype(scores | std::views::keys),
        decltype(scores | std::views::elements<0>)
    >);
}
```

**进阶：观察 values 对右值 map 的 borrowed 状态与悬垂风险**

```cpp
// C++20
#include <ranges>
#include <map>
#include <string>
#include <iostream>

std::map<std::string, int> get_map() {
    return {{"x", 1}, {"y", 2}};
}

int main() {
    // 危险写法：对右值 map 取 values，然后试图保留迭代器
    // std::map 不是 borrowed_range（map 拥有元素生命周期）
    static_assert(!std::ranges::borrowed_range<std::map<std::string,int>>);

    // ranges::find 对右值非 borrowed_range 返回 ranges::dangling：
    auto it = std::ranges::find(get_map() | std::views::values, 2);
    // it 的类型是 std::ranges::dangling
    static_assert(std::same_as<decltype(it), std::ranges::dangling>);
    // 编译器会阻止你解引用 it（dangling 没有 operator*）

    // 安全写法：先把 map 存下来，再取 values
    auto m = get_map();
    for (int v : m | std::views::values) {
        std::cout << v << ' ';  // 1 2
    }
    std::cout << '\n';

    // values_view 本身也不是 borrowed_range（因为底层 map 不是）：
    auto vv = m | std::views::values;
    static_assert(!std::ranges::borrowed_range<decltype(vv)>);
}
```

### 验收点

- 你能用 `views::common` 把一个非 common_range（如 `iota | take`）包装成 C++17 算法可用的形式，并证明 `begin/end` 类型现在相同。
- 你能用 `static_assert` 证明 `forward_list` 不能被 `views::reverse`（不满足 `bidirectional_range`）。
- 你能写出 `views::keys` / `views::values` / `views::elements<N>` 的基本用法，并说出它们的等价关系。
- 你能解释对右值 `map` 取 `views::values` 后，算法返回 `ranges::dangling` 的原因。
- 你能说出 `reverse_view` 的 iterator_concept 如何从底层 range 的 iterator_concept 继承。

### 观察点

- `views::common` 的典型使用场景是"桥接 C++20 view 管道和 C++17 算法接口"。C++20 的 ranges 算法（`ranges::sort`、`ranges::find` 等）直接接受 iter/sentinel 不同类型的 range，不需要 common；但如果你在调用 `std::accumulate`、`std::copy` 等 C++17 接口，就必须先用 `views::common`。这是模块 A 中"两个世界"差异的直接体现。
- `views::reverse` 的约束是设计上的必然：双向迭代器才能从尾部向头部推进。`forward_iterator` 只能单向，无法实现"从末尾开始前推"的语义。强行对单向 range 调用 reverse 会在 concept 层面就被拦截，这正是 01 心智模型所强调的"concept 约束在编译期阻拦不合法使用"。
- `views::elements<N>` 依赖 `get<N>` 的 ADL 查找，这是 C++ tuple-like 协议的一部分。只要类型满足 `tuple_size`、`tuple_element`、`get<N>`，就可以被 `elements` 投影——不仅仅是 `std::tuple`，`std::pair`、`std::array`，以及用户自定义满足 tuple 协议的类型都可以。
- `views::values` 应用到右值 `map` 上的悬垂风险，与 01 心智模型中讲的"右值非 borrowed_range 传给返回迭代器算法"是同一个问题。`values_view` 不改变底层 range 的 borrowed 属性：底层是 borrowed 的，views_view 也是；底层不是 borrowed 的（如 `map`），values_view 也不是。这是"视图不改变底层借用语义"的一般规律。

### 常见坑

- 对单向迭代器（`forward_list`、`iota` 无界序列、`filter_view` 等）用 `views::reverse`，期待编译通过：concept 会在调用 `views::reverse` 时就报错，不会等到运行时。
- 对非 tuple-like 的元素类型用 `views::elements` / `views::keys` / `views::values`：如果元素类型不满足 tuple 协议（没有 `get<N>`），编译错误会比较冗长，要认出"没找到 get<N>"这类信息。
- 期待 `views::values` 对右值 `map` 返回的迭代器在 `map` 销毁后仍有效：`map` 不是 `borrowed_range`，对右值 `map` 做任何返回迭代器的操作都会触发 `ranges::dangling` 保护。
- 在已经是 `common_range` 的 view 上再套 `views::common`，以为会有额外开销：标准规定 `common_view` 对 `common_range` 是 no-op，直接透传。
- 把 `views::keys` 当成返回所有 key 的一个新 `vector`：它是惰性 view，不会提前分配内存，消费时才按需读取 key。

### 提示

- 测试 `views::common` 时，先用 `typeid` 或类型打印工具打出 `r.begin()` 和 `r.end()` 的类型，然后包装一层 `views::common` 再打印，直观看到类型变化。
- 测试 `views::reverse` 的迭代器概念时，优先用 `static_assert`，而不是运行时断言。把 `static_assert(std::random_access_iterator<decltype(rv.begin())>)` 写出来，比看文档更直接。
- `views::elements<N>` 的 N 必须是编译期常量，不能是运行时变量。这是 tuple 协议的基本约束，不是 ranges 的限制。
- 对于 `borrowed_range` 的验证，先用 `static_assert(!std::ranges::borrowed_range<std::map<std::string,int>>)` 确认底层类型，再验证 `values_view` 是否继承了这个属性。

### 复盘问题

- `views::common` 解决的问题本质上是"C++17 接口要求 begin/end 同类型"，而 C++20 ranges 算法已经解除了这个限制。在未来的代码里，你会在什么情况下仍然需要 `views::common`？

## 做完模块 C1 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- `views::join` 把 range-of-ranges 拍平时，迭代器最高只能到 `bidirectional_iterator`，因为两层状态（外层迭代器 + 内层迭代器）无法在 O(1) 内随机跳跃。
- 原始惰性 split 设计由 `views::lazy_split` 承接，产出的子范围是 forward-only 的代理，无法直接构造 `string_view`；修订后 `views::split` 的子范围保留底层 contiguous 性质，可以直接构造 `string_view`。P2210R2 是 C++20 DR，旧语义通过 `lazy_split` 继续可用。
- `views::common` 的必要场景是：把 iter/sentinel 类型不同的 view 包装成 begin/end 同类型的 `common_range`，为 C++17 风格算法服务。C++20 的 ranges 算法不需要它。
- `views::reverse` 要求底层是 `bidirectional_range`；`reverse_view` 的 `iterator_concept` 与底层迭代器相同（底层是 random access，反转后也是 random access）。
- `views::elements<N>` / `views::keys` / `views::values` 依赖 tuple-like 协议（`get<N>`），不改变底层的 borrowed 属性：底层 `map` 不是 `borrowed_range`，所以 `values_view` of `map` 也不是，对右值 `map` 的操作会触发 `ranges::dangling`。
- 结构适配器让管道从"一路走到底"变成"会折叠、会拍平、会重新形状"：这一层的复杂度不在于值变换，而在于迭代器的行进方式本身发生了结构性改变。

## 前向引用：下一模块（C2）预告

模块 C1 的关注点是"view 的形状"——拍平、切分、翻转、按元素位置取值。

**模块 C2 把关注点从 view 管道移到算法本身**：`std::ranges::` 算法的 projection 参数（已在 01 心智模型中做了概念铺垫）、富返回类型（`ranges::dangling` / `borrowed_iterator_t` / `subrange`）、borrowed_range 的判定规则，以及 C++23 的 `ranges::to`——把任意 range 消费成容器的统一接口。

如果你在模块 C1 的练习里已经注意到"右值 map 的 values_view 触发 dangling"这个问题，模块 C2 会系统解释这背后的 borrowed_range 判定机制，以及算法如何在类型系统层面编码安全保障。
