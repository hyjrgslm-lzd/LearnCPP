# 12 缓存、分支与分配：用对照缩小原因

先修：[测量边界](01-measurement.md)、AoS/SoA、矩阵分块和 C07 allocator/虚拟内存基础。本章处理三个最容易被性能报告误判的词：cache、branch、allocator。它们都可能真实影响程序，但总时间变了不等于原因就是它们。

## 1. cache 结论要先固定访问集合

缓存不是“数据结构名字”的属性，而是访问地址、步长、工作集、写入方式和多核一致性共同形成的行为。AoS/SoA 改变字段排列；矩阵分块改变重复使用的时机；false sharing 改变多个 core 对同一 cache line 的所有权流动。这些都需要对照。

最小对照应只改变一个主要因素。例如比较 AoS 与 SoA 时，先保证：

- 输入元素相同，输出逐元素相同。
- 计时窗口都只包含更新内核，或都包含转换加更新。
- 元素数覆盖小于 L1、接近 LLC、大于 LLC 的规模。
- 若声明自动向量化参与，保存报告或反汇编。

这样仍不能直接得到“DRAM 流量减少”。逻辑流量 `2 input + 1 output` 只是估算；缓存命中、写分配、写回和预取都会改变硬件总线流量。没有计数器时，应写成访问模式假设，而不是硬件事件结论。

## 2. branch 结论要区分数据分布和算术变化

分支预测成本依赖输入分布。全部正数、正负交替、随机正负，可能得到完全不同的行为。把 `if` 改成 `std::max` 或 SIMD select 时，也可能改变 NaN、-0、异常和执行全部候选表达式的语义。

正确对照先给独立 oracle：

```cpp
float relu(float x) {
    return x > 0.0f ? x : 0.0f;
}
```

然后准备多组输入：全正、全负、规律交替、固定种子随机、含 NaN 和 -0 的特殊值。若只在全正输入上比较，分支预测几乎没有压力；若只在随机输入上比较，也不能推广到真实业务分布。

SIMD `select(mask, yes, no)` 表达的是选择，不是短路。`select(x != 0, 1/x, 0)` 仍可能先计算 `1/x`。因此分支替换不是纯性能改动，必须先核对语义。

## 3. allocator 结论要把分配从计算里拆出来

分配成本常被混进热循环。`push_back` 可能触发扩容、移动、构造和释放；`vector(n)` 会初始化元素；`pmr` 可能减少系统分配次数，也可能因为同步或上游资源变慢。要证明 allocator 是主要成本，至少要输出分配次数、容量变化或分阶段时间。

一个可运行对照可以分三段：

| 阶段 | 问题 |
|---|---|
| reserve/fill | 容量策略本身花了多少 |
| compute | 预分配后计算循环花了多少 |
| teardown | 释放是否在用户关心路径内 |

如果只执行一次短任务，预留容量的收益可能被额外初始化抵消。若长生命周期对象复用缓冲，分配阶段应从每帧计时中移出。两者是不同场景，不能用同一个加速比。

## 4. 正确报告长这样

对应的实际入口是 [L05/costs.cpp](../exercises/L05_measurement_observation/costs.cpp)。`allocation_counter` 将请求转发到 `new_delete_resource`，仅在成功后计数；容器先于资源销毁。两种填充都核对同一个整数和，reserve 路径同时检查本实现只需一次分配。计数直接支持“分配调用数量不同”，总耗时仍包含填充和插桩，不能只凭时间把 allocator 认定为唯一瓶颈。

同一程序还对有符号零/NaN 和尾部做分支替换语义检查，并用同一矩阵的行/列遍历展示步长实验。程序输出没有预设排名。要研究分支预测，应再按本章输入分布设计多组对照并采集定位信息；本例的特殊值检查不冒充预测器性能测量。

可以写：

> 在 `n=262147`、Release、同一输入、计时窗口只含 `add` 调用时，SSE2 和 scalar 均通过解析 oracle。当前单次观察显示二者耗时不同；是否因为内存带宽或自动向量化，需要汇编报告和多进程样本确认。

不要写：

> SSE2 更快，因为 cache 命中更好。

前者把已验证、已观察和未验证分开。后者把一个可能机制冒充成根因。

## 5. 和 C08/C13 练习的关系

C08 的 false sharing、SIMD、NUMA 程序提供底层入口；C13 的 L02/L05/L07/L08 从数值和数据布局侧消费它们。共同规则是：

- 正确性检查独立于计时。
- 总时间不能单独证明 root cause。
- 缺少硬件、权限或实现能力时保留 SKIP。
- 优化无收益也是有效结果，不改故事。

## 自测与解析

**SoA 内核快，能说 cache 更好吗？** 不能。需要访问集合、规模变化、向量化形态或硬件计数器。只能先说该窗口观察到更低耗时。

**把 branch 改成 select 总是等价吗？** 不总是。select 不短路，特殊浮点值和候选表达式副作用都要检查。

**预分配让总时间下降，allocator 就是唯一瓶颈吗？** 不能。它说明分配相关阶段可能重要；还要看容量变化、分配次数和计算阶段是否不变。

**为什么不追求一个万能 benchmark？** 因为不同问题的窗口不同。端到端、内核、分配、线程池稳态是不同契约，混成一个数字只会让结论失真。
