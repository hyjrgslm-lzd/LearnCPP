# 01 测量边界：秒表先回答窗口，不回答原因

先修：C01 的 Release 构建和命令行运行，C02 的对象与存储，C06 的复杂度，C08 的线程基础。目标是学会把“做了同一件事”“测了哪个窗口”“能否归因”分开。性能课不是从“换一种更快写法”开始，而是从一个可反驳的问题开始。

一个计时数字只表示两个时刻之间经过了多少时间。初始化、分配、随机数、线程创建、输入拷贝、校验、日志输出、异常路径和析构都可能落在这两个时刻之间。它们不一定是噪声；如果用户关心端到端时延，它们就是工作的一部分。如果问题只研究内核循环，就必须把它们移出计时窗口，并在报告里说清楚。

## 1. 先写实验问题

把问题写成能被失败结果推翻的一句话：

> 在相同粒子输入、相同步数、相同数值容差下，SoA 位置更新内核是否比 AoS 内核耗时更低？

这句话固定了输入、步数、语义和比较对象。它还没有包含“原因”。若结果显示 SoA 较快，仍不能直接写“因为 cache miss 少”或“因为 SIMD”。要证明原因，需要额外证据：地址和访问集合、向量化报告、反汇编、profile、硬件计数器，或只替换一个因素的受控对照。

同样，`std::execution::par` 的结果不能只按 `hardware_concurrency()` 解释。标准执行策略允许实现并行，但不承诺创建固定线程数。若没有记录实际参与线程，只能把 `threads=0` 写成“实现管理，未观测线程数”，不能填入机器线程数。

## 2. 正确性检查不属于性能结论的装饰

性能比较必须先证明候选完成同一件事。C13 的练习用独立解析真值、逐元素检查、shape 拒绝和误差预算来保护这个前提。跳过尾部、放宽容差、把异常输入当空输入、少做一次归约，都能制造好看的耗时。

计时窗口通常不包含完整校验，因为校验本身可能比内核更贵。但校验必须实际执行，并且失败时整个样本不能进入性能排名。L05 的阶段观察就是这个结构：

```cpp
const double update_ms = cs::bench::measure_ms([&] {
    for (std::size_t i = 0; i < steps; ++i)
        c13::update_soa(particles, 0.016f);
});
for (std::size_t i = 0; i < particles.x.size(); ++i)
    c13::check(c13::near(particles.x[i], oracle_x(i)), "x update oracle");
```

计时区间只包更新循环；后面的 oracle 检查证明这次更新没有漏元素。这个程序仍不是完整 benchmark。它只有一轮进程内观察，没有随机版本顺序、五次独立样本、中位数和干扰记录。

## 3. 阶段计时回答“成本在哪个阶段出现”

粒子管线可以拆成：

| 阶段 | 计时内包含 | 不包含 |
|---|---|---|
| `generate` | 固定种子的随机数与 SoA 构造 | 后续更新、归约、完整性能采样 |
| `update` | `steps` 次位置更新 | 输入生成、结果校验、日志 |
| `reduce` | 动能归约 | 更新、校验、输出解释 |

如果 `generate` 比 `update` 大，只能说明当前窗口内生成成本较高。不能从这条结果推出“随机数是系统瓶颈”，因为真实应用可能复用输入，也可能把输入从文件或网络读入。窗口改变，问题就改变。

如果总耗时变化明显，先追阶段。若只有 `update` 变，继续看内核：是否处理相同元素、是否自动向量化、是否对齐、是否有尾部、是否受内存带宽限制。若 `generate` 或转换阶段变，优化内核可能对端到端无帮助。

## 4. 汇编与自动向量化怎么读

源码逐元素不代表机器码逐元素。编译器可能把标量循环自动向量化，也可能因为别名、异常、未知对齐、浮点合同或控制流放弃。读汇编和向量化报告的目的不是寻找炫技指令，而是确认被测代码实际做了什么。

MSVC 的最小观察方式是给目标加优化并输出报告。本任务不修改公共 CMake；可在临时构建或单文件命令中使用同等选项：

```powershell
cl /std:c++23 /O2 /EHsc /W4 /I C13_Performance_Numerics_Data_Layout\exercises\include /I C08_Concurrency\exercises\include /FAcs /Qvec-report:2 source.cpp
```

看三件事：

1. 报告是否说循环被向量化，或说明阻断原因。
2. `.asm` 中是否出现预期宽度的 packed 指令，例如 SSE 的 `addps`，以及尾部如何处理。
3. 生成代码是否仍包含完整循环、校验之外的输出使用和必要的边界处理。

报告没有提到某循环，不等于它一定没优化；汇编出现 packed 指令，也不等于性能瓶颈已经解决。它们只证明“生成代码形态”。要把形态连接到耗时，需要同口径测量。

## 5. 样本和结论的边界

正式性能结论至少需要外部重复采样：默认一轮预热、五个独立进程样本、固定随机种子、随机版本顺序、中位数和范围。一次运行可以用来检查程序接线和阶段边界，不能作为排名。

报告时使用这种句式：

- 已验证：`update` 阶段处理全部元素，计时窗口不含生成和校验。
- 已观察：当前 Release 构建在本机输出某组阶段耗时。
- 未证明：cache miss、分支预测、allocator、SIMD 或调度线程数是主要原因。

这个边界有点啰嗦，但能防止最常见的性能误判：拿一个总时间给一个喜欢的解释。

## 自测与解析

**为什么不能把校验放进计时里再比较？** 可以，但那研究的是“计算加校验”的端到端任务。若只研究内核，应把校验移出窗口，并说明失败样本无效。

**标量源码比显式 SSE2 慢，能说显式 SIMD 更好吗？** 只能在同输入、同构建、同样本规则下说该实现较快。还要看标量是否已自动向量化、尾部和对齐是否相同、瓶颈是否已经转到带宽。

**`threads=0` 是什么意思？** 表示线程数由实现管理且本程序没有观测实际线程数。它不是零线程，也不是硬件线程数。

**看到 `generate` 很慢，能优化随机数吗？** 先问真实场景是否每次都生成输入。若生产路径读文件或复用缓冲，优化随机数不解决目标问题。
