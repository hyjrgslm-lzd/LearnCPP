# 10 综合：从正确的局部内核到完整处理成本

先修：L01 稳定归约、L02 布局、L03 矩阵视图，以及单位边界和计时口径。这里把它们接成一个真实可运行的任务：输入三维位置与速度，推进一个小时间步，将更新后位置变换到输出坐标系，再返回稳定统计。[综合练习](../exercises/L04_particle_pipeline/README.md) 必须返回全部坐标，不能只用一个标量摘要证明处理正确。

## 先声明输入、输出与所有权

输入是 `std::span<const particle>`，只借用调用者存储。每个粒子有三轴位置和三轴速度。课程生成器固定 mt19937 种子及整数到 float 的映射，生成有界有限值。接口拒绝超过一百万粒子、非有限字段以及超出 `[0,1000] ms` 的时间参数。

输出 `pipeline_result` 拥有行优先 `N×3` 的 `std::vector<double>` 和其中所有元素的稳定和。源输入保持不变，输出与临时 SoA 是不同所有者。`std::mdspan` 只负责在输出分配存活期间索引，不拥有内存，也不会延长局部临时量的寿命。

```text
输入 AoS（调用者拥有）
    │  const span 借用
    ▼
局部 SoA ── 一次位置更新 ── 3×3 坐标变换
                              │
                              ▼
                   输出 vector<double> + mdspan 视图
                              │
                              ▼
                        稳定求和 → 返回所有权
```

## 四个阶段各做一件事

**单位入口。** `milliseconds{16}` 先经过有限值及应用上限检查，转成 `0.016f` 秒。转换一次，不在每个元素内部重新解释单位。真实量纲类型的使用由 L10 展开；核心接口不会因为关闭第三方而改变输入单位。

**布局与更新。** AoS 转成六个等长数组。更新按 float 内核执行，容许符合本实验预算的浮点舍入；速度保持输入定义。转换、更新都发生在函数拥有的临时存储里，外部输入没有半更新状态。

**矩阵变换。** 固定矩阵 `R=[0,-1,0;1,0,0;0,0,1]` 把更新后坐标映射成 `(-y,x,z)`。Reference 实际用 `std::mdspan` 访问矩阵和输出，通过三个乘加计算每个结果。独立 good 可以按解析关系直接写出答案，用不同结构核对同一个契约。

**归约。** 对已经写好的全部输出调用 Neumaier 求和。它比“只看第一粒子是否在合理范围”多覆盖了所有元素，却仍不能替代逐坐标检查：有些不同数组有相同和。因此短检查同时验证数组与和，算法层误差单独在 L01 分析。

这是一次从状态到输出坐标的处理，不把输出坐标再与原始坐标系速度直接重复积分。若要做持续物理模拟，必须另外声明速度所在坐标系、时间积分方案、力和稳定性；这里的矩阵变换不是完整仿真模型。

## 先修不是只挂一个链接

运行本项目之前，读者应该已经能解释三个细节：为什么 SoA 的长度要一致；为什么 `N*3` 必须在分配前检查溢出；为什么 naive、Kahan 和 Neumaier 不保证同样的结果。如果只能抄 Reference 才能完成对应阶段，应回到主讲单元，而不是在综合层继续堆代码。

本项目使用固定 3×3 变换，所以直接循环足够。L03 的通用分块 GEMM 解决另外一种尺寸问题，不把通用 GEMM 生搬进三个坐标的更新来体现“复用”。两者共享 mdspan 的布局知识与形状契约，承担不同工作。

## 计时口径决定能回答的问题

`c13_pipeline` 的计时区间包围完整 `c13::run_pipeline` 调用，包含参数检查、局部分配、AoS/SoA 转换、更新、坐标变换、求和以及函数退出前临时存储的释放。输入已经准备好，输出在区间结束时仍存活；随机生成、输出销毁、打印和独立检查在区间外。

所以它回答“已有一批输入，产生可消费结果要多久”，不回答进程启动多久、读取文件多久或回收全部结果多久。如果真实应用还要求输出序列化、GPU 传输或转换回 AoS，必须把这些阶段接进自己的端到端计时；不能用内核耗时估算代替。

[L05](../exercises/L05_measurement_observation/README.md) 是独立的二维阶段观察分支，保留质量字段与动能统计，帮助定位准备、更新和归约的时间。它与本项目的三维输出契约不同，不能直接计算两者的加速比。两个例子的作用是展示阶段与任务边界，而不是不同题目之间的性能竞赛。

## 正确性检查为什么这样设计

参考样本用相同的输入生成器保证数据一致，预期值则用独立的标量表达式计算。检查所有坐标能发现漏粒子、漏轴、错单位、遗漏矩阵变换；稳定和检查能发现归约漏算或错误摘要。输入生成与算法验证是两条责任：随机数引擎的结果不作为自己的算法答案。

bad 实现把 duration 丢弃，仍生成输入、变换坐标并返回合法形状。旧式“结果有限、第一项在范围内、总和大于零”的检查可能被这种实现骗过。这里的逐坐标 oracle 会明确拒绝它，证明检查器在消费真实变换结果。

## 如何提出下一轮优化

如果阶段测量显示转换占主要部分，可以提出“长期保留 SoA”的接口方案，但它改变了输入契约与上游责任，必须作为新场景重建基线。若矩阵阶段占主要部分，可以调查自动向量化；若分配占比大，可以考虑调用者复用输出，但这又引入缓冲大小、借用和并发使用规则。

所有这些都先是候选，不是已经证实的性能改进。先确定热点和同口径对照，再改一个主要因素。局部无收益、基线胜出或新增生命周期负担都是需要保留的结果。本次交付只做短自检与样章对照，不给综合项目预设加速比。

## 自测与解析

1. **为什么不只比较 sum？** 不同数组可以有相同和，漏写、交换坐标或抵消误差可能逃过摘要检查；要核对实际业务输出。
2. **返回 mdspan 能代替返回 vector 吗？** 若它引用本函数的局部 vector，函数返回即悬空。这里返回拥有者，视图只在拥有者存活时使用。
3. **同一个输入种子能证明两个版本可比吗？** 还要核对尺寸、单位、时间步、输出坐标系、误差预算和计时责任。
4. **三维管线和 L05 二维动能观察能算加速比吗？** 不能。维度、输出、阶段和工作量都不同，必须先建立同契约版本。
