# 11 从真实调用读源码，再看前沿接口

先修：C04 的模板与重载、C06 的算法契约、本课 mdspan/数值/SIMD 章节。阅读目标是解释当前 consumer 为什么能得到正确结果、有哪些前置条件、实际走到哪个执行路径，而不是收集一串库名字。

## 先固定调用表达式和版本

从 [L11](../exercises/L11_stdblas/main.cpp) 的 `matrix_product(A,B,C)` 出发：A 是 2×3，B 是 3×2，C 是 2×2，存储不重叠，输出先填哨兵。我们使用的是固定 stdBLAS 源码快照。规范上的 `std::linalg`、参考实现的 `std::experimental::linalg`、CMake target 名字不是同一类标识，不能见到一个名为 `std::linalg` 的构建目标就宣布标准库已经实现了它。

所有规范、依赖提交与真实入口集中在 [标准与实现索引](../references/standards-and-implementations.md)。阅读时打开对应固定提交；如果跟随上游 main，应重新核对接口，而不是沿用旧讲义中的行号和结论。

## stdBLAS：从入口到实际循环

打开 `include/experimental/linalg`，它按算法族包含具体头文件。`blas1_dot.hpp` 负责点积，`blas3_matrix_product.hpp` 负责矩阵乘。先看函数模板的元素类型、extents、layout 和 accessor 参数：算法操作的是逻辑索引，不把所有矩阵都假设为一块连续行优先数组。

然后找到没有显式执行策略的重载，观察它怎样进入带执行策略的重载；策略映射再选择可用的定制路径或 serial `inline_exec_t`。本课没有开启 BLAS、TBB、Kokkos，所以应沿 serial 路径读实际乘加，而不是把未启用后端的文档性能描述套到这个二进制。

最后看写输出的循环：输出初始化与累加发生在哪里，内外循环各对应哪个矩阵维度，有没有临时值或更宽的累加类型。对照 L03 自己写的朴素与分块版本，区分“表达一样的线性代数运算”与“使用同样的循环顺序”。改变分组可能改变舍入结果，所以输出核对应先满足数值契约，再讨论速度。

退出阅读的最低成果是能画出：调用表达式 → 形状和类型 → 策略映射 → 当前 serial 算法 → 输出。若不能指出实际走到哪一段循环，只知道库支持 GPU，不算已经解释了当前程序。

## mdspan：为什么同一个视图可以有不同成本

mdspan 分离 extents、layout mapping 与 accessor。extents 描述逻辑空间；mapping 把多维索引变成偏移；accessor 解释如何从数据句柄和偏移取得元素。向量拥有的容量、视图的逻辑元素数、mapping 的 required span size 不能混用。

读取参考实现时，从 `include/experimental/mdspan` 进入兼容入口，再沿它实际包含的 `include/mdspan/mdspan.hpp` 观察布局和访问器的组织。不要把兼容命名空间误当作本机标准库实现证据。本课因此将参考 mdspan 与原生 mdspan 放在不同目标，课程核心依然直接使用 C++23 `<mdspan>`。

## C++26 的多维扩展分别解决什么

`submdspan` 从已有视图切出逻辑子区域。选一列时，元素在物理存储中往往有行跨度；子视图依然借用原存储，不是复制列。F01 的主体修改子视图并检查原矩阵对应元素，直接验证这个关系。

padded layout 用额外间隔表达对齐后的行距。2×3 矩阵按 4 元素行距存储，逻辑上仍有 6 个元素，物理偏移可能到第 6 号元素。F01 检查逻辑尺寸、实际行距和未改动的填充；不能把所有已分配字节都当作矩阵元素遍历。

`aligned_accessor` 表达访问所依赖的对齐前提，不会替一块未对齐的内存施法。本课使用真实 `alignas(64)` 存储再构造该视图。传入随意偏移的指针来“测试它会不会自动修复”违反前置条件，不能放进默认正常实验。

## 原生 SIMD 与已有 SIMD 后端

本课固定草案路径的原生接口是 `<simd>` 中的 `std::simd::vec` 及相应 load/store 操作。它与 Parallelism TS、xsimd 和直接 SSE2 intrinsic 各自有独立接口。主体用五个元素检查完整四 lane 与尾部 partial load/store，而不是只构造一个向量类型就宣布完整运算验证通过。

L07 仍可在没有原生 `<simd>` 时消费现有 scalar/SSE2/xsimd 路径。这里是明确选择已有后端，配置和输出都标出名字；不会把 xsimd 的成功汇总成原生标准库通过。

## C++29 的 mdspan copy/fill

P3242R4 的调用形式是 `std::copy(src_view,dst_view)` 和 `std::fill(dst_view,value)`，不是带迭代器的三参数算法。它按逻辑索引复制；行优先的源与列优先的目的可以保存同一个逻辑矩阵，但底层数组排列不同。

F01 给出这样的真实主体：源数组 `[0,1,2,3,4,5]` 表示行优先 2×3，复制到列优先目标后底层应为 `[0,3,1,4,2,5]`。尺寸必须匹配，copy 的源和目的元素不能重叠，目的映射还必须满足规范要求；不能拿普通 `memcpy` 的结果冒充逻辑复制。

纳入草案不等于本机可执行。原生探针在缺接口时明确记录不可用，正文与主体仍保留。不得为了得到绿色状态而用自写同名函数补进 `std`；教学实现和规范接口必须保持真实身份。

## 自测与解析

- **stdBLAS consumer 通过能证明本机 `<linalg>` 可用吗？** 不能。头文件、实现来源和命名空间均不同，原生路径单独探测。
- **所有输出正确是否表示后端采用了最佳算法？** 不表示。它只支持该输入的正确性观察；需要定位当前执行路径及成本后才能谈优化。
- **为什么 probe 和主体不是同一个源文件？** 最小 probe 判断是否存在所需能力；能力具备后的完整主体错误应真实阻断，避免把代码 bug 吞成缺能力。
- **为什么不在核心代码静默切换到参考 mdspan？** 两个路径会有不同类型、扩展和兼容边界；显式目标让读者知道验证的到底是哪一种实现。
