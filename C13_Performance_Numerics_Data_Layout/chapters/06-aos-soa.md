# 06 从 AoS 到 SoA：改变的是访问集合

先修：C02 的对象与连续存储、`std::vector` 的容量与借用失效；本课的误差预算与计时边界。还没学 SIMD 也能完成本章。目标不是记住“SoA 更快”，而是能决定自己处理的数据是否值得转换，并知道该怎样验证。配套 [L02 练习](../exercises/L02_layout/README.md) 和 [完整内核](../exercises/include/c13/layout.hpp) 是同一套接口。

## 一个粒子的六个字段

粒子有位置 `(x,y,z)` 和速度 `(vx,vy,vz)`。一步更新规定 `x += vx*dt`，另两个轴相同，速度不变。`dt` 必须有限且非负。课程生成器只生成有界有限数据；本章不处理碰撞、力或真实物理积分的稳定性。有限输入仍可能在极大步长下溢出到无穷，因此正常数值比较限定在本实验的小步长与有限步数范围。

AoS（array of structures）将一个对象的字段放在一起：

```text
particle 0           particle 1           particle 2
x y z vx vy vz | x y z vx vy vz | x y z vx vy vz
```

SoA（structure of arrays）将同一个字段放在一起：

```text
x:  x0  x1  x2 ...       vx: vx0 vx1 vx2 ...
y:  y0  y1  y2 ...       vy: vy0 vy1 vy2 ...
z:  z0  z1  z2 ...       vz: vz0 vz1 vz2 ...
```

六个 `vector<float>` 分别拥有自己的存储。不能把整个 `particles_soa` 当作一块连续浮点数组；也不能假设 AoS 没有填充。实际地址间隔应由 `sizeof(particle)`、成员地址和编译器布局判断。对象合法性、生命周期与别名规则由 C02 主讲，这里不通过 `reinterpret_cast<float*>` 穿越不同成员来冒充数组。

## 先建立正确基线

AoS 基线逐粒子读取速度、更新位置。它很直接：一轮处理一个完整对象，无需重新组织输入。SoA 版本做相同算术，但访问六条数组。

```cpp
for (auto& v : particles) {
    v.x += v.vx * dt;
    v.y += v.vy * dt;
    v.z += v.vz * dt;
}
```

转换是按字段复制，既不推进时间，也不改变元素顺序。转换后必须满足六个数组长度相同，否则同一个索引不再表示完整粒子。`advance_soa` 在任何写入前验证全部长度与 `dt`。空集合是合法输入，更新为空操作；最后不足四个的元素也必须更新，因为四只是某些向量指令的宽度，并非业务契约。

参考实现预留六个数组的容量，避免填充过程中的反复扩容。练习的独立 good 实现不使用这项优化，仍应通过相同正确性检查。这说明“算法正确”与“特定分配策略”不是一个判据。

## 哪个成本可能变化

如果算法只读取所有粒子的 `x`，AoS 跨过其余字段，SoA 的逻辑访问则连续。能否减少实际内存流量，还取决于缓存行、预取器、工作集大小和处理器。当前更新会读取六个字段中的全部内容，因此不能仅凭图中更整齐的访问就宣布 SoA 更省带宽。SoA 还可能方便编译器形成向量加载；这需要向量化报告或生成代码支持，不能由类型名称推导。

SoA 同时带来六个所有者、额外转换、不同的逐对象访问成本。对于只执行一次、最终还要恢复 AoS 的任务，转换和回转可能超过内核收益。对于长时间保持 SoA 的计算，转换则可能被后续多轮摊薄。两者是不同使用场景。

先写可检验问题：**相同输入与相同步数下，SoA 内核是否更快？加上一次转换后，这个结论是否仍成立？** 在得到结果前，两个版本都是同契约候选，不是一条已证明的升级路线。

## 分阶段对照

[benchmark.cpp](../exercises/L02_layout/benchmark.cpp) 把运行分成四行：

| 行 | 包含 | 不包含 |
|---|---|---|
| `aos_kernel` | 多轮位置更新及参数检查 | 初始输入、AoS 副本创建 |
| `aos_to_soa` | 六组分配与字段复制 | 位置更新 |
| `soa_kernel` | 同样多轮更新及形状检查 | 转换 |
| `soa_convert_plus_kernel` | 上面相邻两个阶段耗时之和 | 输入生成、最终销毁、回转、整个进程启动 |

最后一行不是完整端到端时延。若下游需要 AoS，还需新增“回转＋消费”独立场景，不能给它沿用当前行的结论。粒子综合项目进一步区分整条处理管线与内核。

```powershell
cmake -S exercises/L02_layout -B build/layout -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build/layout
ctest --test-dir build/layout --output-on-failure
./build/layout/c13_layout_bench.exe --size 100000 --steps 10
```

从 C13 目录、已经初始化的 MSVC 开发终端执行。输入规模最多一百万、步数最多一千，默认执行有限。计时之后逐元素核对位置；结果失败就退出，不能把失败行用于性能比较。速度不变和转换字段正确另由短检查验证。

默认短对照用于核实程序和阶段边界，不作为性能排名。完整性能研究应按 [C08 测量方法](../../C08_Concurrency/chapters/12-measurement.md) 增加独立进程样本、随机版本次序、规模变化和编译报告。单次顺序运行仍有预热、温度、调频、后台负载等干扰。阶段计时能够直接显示转换耗时，不能独自证明 cache miss 或 SIMD 是内核差异的根因。

## 读出结果之后怎么办

记 `A` 为 AoS 每轮耗时，`S` 为 SoA 每轮耗时，`C` 为一次转换成本。若它们在所研究规模下近似稳定，保持 SoA 的 `k` 轮任务可比较 `k*A` 与 `C+k*S`。只有 `A>S` 时才有候选摊薄点 `k>C/(A-S)`。这个代数关系不是测量结论；实际多轮缓存状态、舍入误差和消费者成本可能改变估算。

若只看到总时间变化，先检查是否漏算尾部、工作量是否相同、是否把转换放到了计时外。若内核差异稳定，再读取编译报告和访问模式。若没收益，保留简单 AoS 是该输入下的合理选择；不能推广为 SoA 无价值，也不应为了让故事“越来越快”选择性删掉样本。

## 自测与解析

1. **为什么不能只比较前四个粒子？** 错误实现可能只处理完整向量组。17 元素和单元素输入会检查尾部，业务契约与 SIMD 宽度无关。
2. **good 没有 reserve，为什么仍算正确？** 容量增长影响分配成本，但只要返回字段和顺序相同，就满足转换契约。性能与正确性分别判断。
3. **SoA 数组长度不一致后先更新 x 再报错，可以吗？** 本接口要求验证失败前无写入，部分更新会留下难以恢复的状态；必须在循环之前检查全部长度。
4. **内核快 10%，整体就快 10% 吗？** 不成立。必须加上转换、输入准备、消费者和清理。当前四行只支持所列边界，不能冒充全进程收益。
5. **`float` 与 `double` 基准为什么不要求逐位相同？** `float` 的乘法与加法可能分别舍入；检查器用独立 double 表达式与明确容差验证本题的小值域，不以两个共享实现相等代替参考真值。
