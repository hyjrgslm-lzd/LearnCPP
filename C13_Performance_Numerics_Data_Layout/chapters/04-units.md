# 04 数值的单位、量纲与语义

先修：C03 的类型不变量与接口、C04 的 Concepts、本课的浮点误差。目标是把“16”变成可以安全参与计算的量，并理解类型检查能拦住什么、还必须在运行时检查什么。[L10](../exercises/L10_units/README.md) 使用真实 mp-units 2.5.0；综合项目的输入则采用固定毫秒接口，方便隔离第三方与核心构建。

## 同一个 double 可以错一千倍

位置更新写成 `position += velocity * dt` 并不足以定义计算。如果速度用米每秒、位置用米、时间参数却传入毫秒，表达式合法但位移放大一千倍。变量名 `dt_ms` 可以提醒人，却不影响 C++ 的乘法规则。数值误差和单位错误也不同：前者可能是舍入后的几个 ulp，后者是整个物理尺度错了。

核心管线接受 `milliseconds{16}`，先检查有限且在本题的 `[0,1000] ms` 范围，再统一换成秒。这样单位转换有单一入口，循环不用每个粒子都除以一千。它是固定接口的最小类型边界，不是一个完整量纲库：若要组合任意单位，应使用成熟库而不是继续往这个结构塞转换规则。

## 从数值到 quantity

一个物理量可以理解为“数值表示＋参考单位＋所描述的量”。mp-units 的单位参与类型系统，表示类型仍可选 `int`、`double` 等。以 [实际 consumer](../exercises/L10_units/main.cpp) 为例：

```cpp
using namespace mp_units;
using namespace mp_units::si::unit_symbols;
constexpr auto dt = 16.0 * ms;
constexpr auto elapsed = dt.in(s);
constexpr auto velocity = (120.0 * m) / (10.0 * s);
constexpr auto displacement = velocity * elapsed;
```

前三个表达式分别建立时间、换算时间、推导速度；最后一个表达式的量纲是长度。`elapsed.numerical_value_in(s)` 得到 `0.016`，`displacement.numerical_value_in(m)` 得到 `0.192`。只有在进入明确要求裸数值的内核边界时才提取数值，不能把 quantity 提早全部脱成 `double` 后继续期待编译器保护单位。

这里使用浮点表示，避免把 16 ms 转成整秒时失去小数。把表示改成整数不是无害的性能优化：可表示集合变了，某些转换需要显式选择截断或其他策略。`in`、显式 value cast 的适用条件，应从固定版本的接口阅读，不要假设所有 unit conversion 都是隐式且无损。

## 量纲相同不一定可互换

距离与某个位置坐标都可能以米表示，但一个描述差值，另一个还涉及原点。能量和转矩具有相同的基础量纲组合，业务含义和允许操作却不同。仅做“长度指数、质量指数、时间指数”的模板运算不足以编码全部语义。

mp-units 用 quantity specification 表达量的语义，并提供对应约束。L10 的 `speed` 将参数限制为长度和时间，而不只是两个支持除法的对象：

```cpp
template<QuantityOf<isq::length> Distance, QuantityOf<isq::time> Time>
constexpr auto speed(Distance d, Time t) { return d / t; }
```

`speed(120.0*m, 10.0*s)` 满足约束；将第二个参数写成长度则不满足。Concepts 解释编译期可接受的操作域，不保证运行期分母非零，也不会替你判断测量数据是否可信。本例使用确定的正常常量；面向外部输入的速度接口仍必须先拒绝零或非法持续时间。

## 点、差值与仿射原点

摄氏温度的某个读数与“温度增加多少”是两种操作对象。带偏移的点不能简单按单位比例相乘；点减点得到差值，点加差值得到另一个点，两个点直接相加通常没有所需语义。坐标原点与时间历元也是同类问题。

源码中的 `quantity_point` 与 `quantity` 分开处理这种区别。读者应先写清楚“这是位置还是位移、时间点还是持续时间”，再选择表示。不要为了让某个表达式编译，直接取裸数值绕过语义检查。综合管线只处理持续时间和一次坐标输出变换，并没有声称建立完整的物理仿真模型。

## 与高性能内核的边界

单位约束通常能在编译期检查，但不能仅凭“零成本抽象”这个描述认定所有程序无额外工作。运行期单位换算、格式化、复杂表示类型和数据打包仍可能有成本。合理的路径是：边界接受语义类型 → 验证值域 → 一次转换到内核固定单位 → 用明确布局批量计算 → 给结果重新附上语义。

不要在每个 SIMD lane 上重复单位解释，也不要为提速删除边界验证。若声称某个量纲包装没有运行成本，先对比同契约函数的生成代码；若声称整个管线更快，还要把输入转换、分配与输出转换一起计入。本课只编译实际 consumer 并检查转换结果，没有给出量纲库的性能排名。

## 源码阅读路线

固定版本入口在 [标准与实现索引](../references/standards-and-implementations.md)：

1. 从 `src/systems/include/mp-units/systems/si.h` 进入具体单位定义，再看 `isq.h` 中数量语义的组织。
2. 看 `src/core/include/mp-units/framework/reference.h`：单位与 quantity specification 怎样形成引用关系。
3. 看 `framework/quantity.h` 与 `quantity_cast.h`：算术如何选择结果表示，单位转换受哪些条件限制。
4. 对照 `quantity_point.h`，解释为什么带原点的点不能直接套用所有 quantity 运算。

阅读结束条件是能说明 L10 三个计算表达式的单位、表示和约束来源，而不是读完整个库。所有入口都来自固定源码；库的行为不等同未来标准接口。

## 自测与解析

- **把所有 quantity 立即转换成 double 能保持安全性吗？** 不能。跨过转换点之后，类型系统已不再携带单位；要让转换点与稳定的内核单位约定对应。
- **编译期单位正确，就不需要检查 duration 吗？** 仍需检查值域、非有限值、零分母和应用上限。单位不编码所有运行期不变量。
- **相同量纲就是相同业务类型吗？** 不是。点/差值、能量/转矩说明需要数量语义与操作契约。
- **能否把 mp-units 写成 C++29 标准库？** 不能。本课消费的是明确版本的第三方库；标准化活动与已发布接口分开登记。
