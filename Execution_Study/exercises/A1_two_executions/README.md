# 练习 1：两种 execution 的第一印象

## 目标

用同一个问题分别写出"并行算法执行策略版"和"sender 图版"，强制自己看见它们在抽象层次上的差异。

## 前置理解

- 你知道 `std::transform_reduce` 或 `std::for_each` 的基本用法。
- 你能把一组连续数据拆成固定数量的区间。
- 你接受这题的重点不是跑分，而是比较两种抽象方式。

## 必做任务

1. 构造一个整数数组，范围建议为 `1..1'000'000`。
2. 写版本 A：使用 `std::transform_reduce(std::execution::par, ...)` 或等价并行算法，计算"所有偶数平方和"。
3. 写版本 B：把数据手工切成 4 段，每一段对应一个 sender 分支。
4. 每个 sender 分支只负责本段局部求和，建议写成 `just(range) -> then(local_reduce)`。
5. 用 `when_all` 汇合 4 个局部和，再在最后一个 `then` 里把 4 个结果加起来。
6. 用 `sync_wait` 得到最终结果。
7. 在代码旁边或单独笔记里写下：版本 A 与版本 B 分别是在什么位置进入执行阶段的。

## 进阶任务

- 把每段返回值从单个整数升级为结构体，例如 `{ partial_sum, even_count }`。
- 在最终汇合阶段同时产出总和与总计数。
- 尝试把 sender 版本拆成"构图函数"和"消费函数"两层，进一步体会"描述工作"和"触发工作"的分离。

## 验收点

- 两个版本的最终结果一致。
- 你能指出 sender 版本里真正开始执行的边界，而不是笼统地说"定义变量时就开始了"。
- 你能说明 sender 版本为什么需要你手动拆分数据，而并行算法版本不需要。
- 你能说明这题里 sender 图的价值不是"更短"，而是"组合关系更显式"。

## 观察点

- 并行算法版本的中心是"把策略喂给算法"。
- sender 版本的中心是"先构造几条分支，再显式合流"。
- 在 sender 版本里，`when_all` 让多个结果在类型层面汇合，而不是把它们塞进共享可变对象。
- sender 版本里，你会明显感觉到：局部工作、汇合工作、消费工作是三个不同层次。

## 常见坑

- 把 sender 版本写成 `just(vector) -> then(一次性全量求和)`，这样就失去了"显式分支和组合"的练习意义。
- 试图让 sender 版本完全复刻并行算法库的内部调度行为。这题不需要，也不现实。
- 在 `par_unseq` 场景里乱打日志，导致观察结果被 I/O 干扰。
- 把共享累加器放到 4 个分支里并发写，结果练成了并发同步题，而不是 sender 组合题。

## 提示

- 区间可以用迭代器对、索引对，或轻量的 `span` 表示。
- sender 版本里，每个分支内部可以先只做普通顺序累加，这不影响你学习框架结构。
- 如果你发现 sender 版本代码更长，这是正常现象；你买到的是"结构显式"，不是"短代码"。
- 先不要纠结性能曲线，重点是比较抽象边界。

## 复盘问题

- 版本 A 的"执行策略"与版本 B 的"sender 图"分别附着在什么对象上？
- sender 版本为什么更容易插入新的阶段，例如统计、记录、合并多种结果？
- 如果你删掉 sender 版本里的 `sync_wait`，还有哪些代码会真正执行？
- 如果把 4 个分支改成 8 个分支，这更像是在改"算法参数"，还是在改"执行图形状"？
