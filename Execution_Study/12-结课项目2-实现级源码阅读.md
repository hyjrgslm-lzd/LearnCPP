# 12 结课项目（第二阶段）：实现级源码阅读与 mini execution

## 这份文件怎么用

第一阶段的结课项目训练的是"会用框架"。这份文件训练的是"懂框架的实现"。

本文件包含 2 个结课项目：

1. `实现级源码对照项目`：带着实现层的知识重新阅读 stdexec 源码
2. `mini std::execution 子集实现项目`：从零实现一个最小但完整的 sender-receiver 子系统

建议顺序是：先做项目 1，再做项目 2。项目 1 帮你建立"源码结构地图"，项目 2 帮你在自己的代码中验证理解。

## 结课项目 3：实现级源码对照

### 项目目标

带着你在模块 E-H 中学到的实现技术，重新阅读 stdexec 源码。这次不是看"这段代码在干什么"，而是看"它用了哪种实现模式，为什么选择这种模式"。

### 固定交付物

这个项目最终必须产出四份东西：

1. 一张实现层对象关系图
2. 一份技术模式对照表
3. 一份 tag_invoke / CPO 使用清单
4. 一页实现层读书笔记

### 必做任务

1. 重新阅读下面四个示例和它们对应的库实现：
   - `just` 的实现：找到 `just_sender` 类型，标注 completion_signatures 定义方式、connect 实现、operation_state 结构
   - `then` 的实现：找到 inner receiver 模式、签名变换逻辑、value channel 拦截与转发
   - `when_all` 的实现：找到 atomic 计数、结果存储结构、取消传播机制
   - `sync_wait` 的实现：找到内部 receiver、run_loop 或类似等待机制、结果提取
2. 对每个实现，回答：
   - 它用了 tag_invoke 还是 member-function dispatch？
   - completion_signatures 是如何计算/传播的？
   - inner receiver 的 get_env 是否转发？是否覆盖了某些 query？
   - operation_state 是栈分配还是堆分配？是否 non-movable？
   - 有没有用到 intrusive data structure？
3. 填写技术模式对照表（格式见下）。
4. 列出 stdexec 中至少 8 个使用 tag_invoke 的 CPO，标注每个的定制意图。
5. 写一页读书笔记，题目固定为："我现在如何向别人解释 stdexec 的实现架构"。

### 推荐对照表格式

| 库算法 | 核心实现模式 | 签名计算方式 | 你在哪个练习中实现过类似的 | 最大收获 | 你之前的理解误差 |
| --- | --- | --- | --- | --- | --- |
| just | 直接 sender | 静态声明 | 模块 D / Ex12 |  |  |
| then | inner receiver + 签名变换 | make_completion_signatures | 模块 G / Ex G-1 |  |  |
| when_all | atomic 计数 + 取消传播 | 值类型合并 | 模块 A / Ex3 (使用层) |  |  |
| sync_wait | 内部 receiver + run_loop | 不对外暴露签名 | 模块 D / Ex11 |  |  |

### 进阶任务

- 阅读 `let_value` 的实现，找到 variant<operation_state...> 模式，理解运行时动态 sender 类型如何被处理。
- 阅读 `async_scope::spawn` 的实现，找到堆分配 operation_state 和引用计数模式。
- 如果 retry 实现可读，对照你在模块 G 中的 retry 实现，标注差异。

### 验收点

- 你不再只是"看懂代码在干嘛"，而是能指出它用了哪种实现模式。
- 你能把库实现和自己的练习实现一一映射。
- 你能说出至少 3 种在 stdexec 中广泛使用的 C++ 实现技术。
- 你能指出至少两个你在做第一阶段时的误解，以及现在的正确理解。

## 结课项目 4：mini std::execution 子集实现

### 项目目标

从零实现一个最小但功能完整的 sender-receiver 子系统。这个项目是对你在模块 D-H 中学到的所有实现技术的综合考试。

### 必须包含的组件

你的 mini execution 库至少要包含：

1. **核心协议**
   - `connect` CPO（通过 tag_invoke 或 member dispatch）
   - `start` CPO
   - `set_value` / `set_error` / `set_stopped` CPO
   - `get_env` CPO

2. **类型基础设施**
   - `completion_signatures<...>` 类型
   - `value_types_of` / `error_types_of` 元函数
   - 至少一个 concept：`sender` 或 `receiver`

3. **基础 sender**
   - `just(values...)` — 产出固定值
   - `just_error(err)` — 产出错误
   - `just_stopped()` — 产出停止

4. **至少一个 sender adaptor**
   - `then(sender, f)` — 值变换

5. **至少一个消费端**
   - `sync_wait(sender)` — 同步等待结果

6. **至少一个 scheduler**
   - `run_loop` — 手动驱动的单线程 scheduler

### 设计约束

- 不需要工业级泛型，但对象关系必须正确。
- completion_signatures 必须在编译期可查询。
- `then` 的签名变换必须在编译期完成。
- `sync_wait` 必须能消费 `just` 和 `then` 的结果。
- `run_loop::schedule()` 必须返回合法 sender。
- 所有 operation_state 必须是 non-movable 的。

### 必做任务

1. 先画出整个系统的架构图：CPO 层、类型层、sender 层、消费层、scheduler 层。
2. 按从底层到上层的顺序实现：
   - 先实现 CPO 基础设施（tag_invoke 或 member dispatch）
   - 再实现 completion_signatures 和 concepts
   - 再实现 just / just_error / just_stopped
   - 再实现 then
   - 再实现 sync_wait
   - 最后实现 run_loop
3. 每完成一层，用 static_assert 或简单测试验证。
4. 最终验证：以下代码必须能编译运行：
   ```cpp
   auto result = mini::sync_wait(
       mini::then(mini::just(42), [](int x) { return x * 2; })
   );
   // result == 84
   ```
5. 最终验证：以下代码必须能编译运行：
   ```cpp
   mini::run_loop loop;
   auto sch = loop.get_scheduler();
   auto work = mini::then(
       mini::schedule(sch),
       [] { return 100; }
   );
   // 在另一个线程或之后调用 loop.run()
   ```
6. 写一份不超过两页的设计文档，解释你的每层选择。

### 进阶任务

- 增加 `when_all(s1, s2)` 支持（至少两个 sender 版本）。
- 增加 pipe 语法 `sender | then(f)`。
- 增加一个自定义 query（如 `get_allocator`）。
- 让你的 mini 库能和 stdexec 的某个组件互操作（例如用你的 sender 配 stdexec 的 sync_wait，或反过来）。

### 验收点

- 核心协议（connect/start/set_value/set_error/set_stopped）正确实现。
- completion_signatures 在编译期可查询。
- `just | then | sync_wait` 能端到端运行。
- run_loop 能手动驱动 sender 执行。
- operation_state 是 non-movable 的。
- 你能拿着架构图解释整个系统，而不是只展示代码。

### 项目复盘问题

- 实现过程中，哪一层最出乎你意料地复杂？
- completion_signatures 的编译期计算在实现中造成了什么困难？
- 如果要增加 `let_value`，你预期主要的实现挑战是什么？
- 你的 mini 库和 stdexec 相比，最大的简化在哪里？这些简化会在什么场景下出问题？
- 完成这个项目后，你对 P2300 提案的设计选择有了什么新的理解？

## 最后一句提醒

真正理解 `std::execution`，不仅是你能用它的 API 写出异步程序，更是你能解释它为什么这样设计、它的每一层抽象解决了什么问题、如果让你重写一个子集你会怎么做。

如果你做完了这两个阶段的全部练习，你对 C++ 异步框架的理解将不再停留在"会用"，而是到达"能设计"的层面。这正是这套练习的终极目标。
