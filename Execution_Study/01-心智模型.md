# 01 心智模型

## 为什么先讲心智模型

如果你一上来就找 `std::execution` 的 API 名字，你很容易陷入两个误区：

- 误把并行算法执行策略当成 sender-receiver 模型本身。
- 误把 sender 图理解成“另一种线程池 API”。

这两个误区都会让后面的练习变成“抄例子”，而不是“理解框架设计”。

所以在开始写任何代码之前，先把这套模型里的对象关系钉牢。

## 先分清两件不同的事

## 1. C++17 并行算法执行策略

你会在当前 MSVC `<execution>` 中看到：

- `std::execution::seq`
- `std::execution::par`
- `std::execution::par_unseq`

它们的典型用法是把一个策略对象传给算法，比如 `for_each`、`sort`、`transform_reduce`。这种设计的关注点是：

- 算法本身仍然是中心
- 执行方式通过策略参数修饰
- 调度资源通常隐藏在实现里
- 调用算法时就进入执行逻辑

## 2. P2300 sender-receiver 执行模型

你真正要练的 `std::execution` 则是另一层抽象。它的关注点是：

- 先把工作描述成一个 sender 图
- 再把 sender 与 receiver 连接起来
- 生成一次执行实例 `operation_state`
- 最后再显式启动

这层设计不是“给现有算法再加一个策略参数”，而是在描述一套通用异步执行框架。

## 两个世界的核心差异

| 维度 | 并行算法执行策略 | sender-receiver 模型 |
| --- | --- | --- |
| 中心对象 | 算法 | 异步工作图 |
| 何时开始执行 | 通常在算法调用点 | 在连接并启动后，或被消费时 |
| 调度资源 | 多数时候隐藏 | 可以显式进入图 |
| 组合能力 | 主要围绕算法接口 | 天然面向组合 |
| 错误/停止表达 | 依赖算法语义 | completion channel |
| 生命周期归属 | 由算法实现隐藏处理 | 由 operation_state、scope 等对象承接 |

后面的全部练习，都是围绕右边这一列展开。

## 五个最重要的对象

## 1. sender

sender 不是线程，不是 future，也不是已经在跑的任务。

你可以把 sender 理解成“对一段异步工作的描述”。它回答的是：

- 这段工作完成时可能产生哪些 completion？
- 正常完成时会产出什么值？
- 它需要什么环境？
- 它如何与其他工作组合？

最容易犯的错是：把 `just(42)`、`schedule(sch)`、`when_all(...)` 的返回对象当成“已经启动的任务”。

练习里你要不断验证一件事：sender 大多数时候只是在描述工作，还没有真正执行。

## 2. receiver

receiver 是这次执行的消费端。它关心的不是“怎么做工作”，而是“工作完成时怎么接收结果”。

receiver 至少要面对三条 completion channel：

- `set_value(...)`
- `set_error(...)`
- `set_stopped()`

同时，receiver 还是 environment 的入口，因为很多查询值就是从 receiver 的环境里被读取出来的。

## 3. operation_state

这是整套模型最值得你刻意练的对象。

sender 只是蓝图，receiver 只是消费端。真正代表“一次具体执行”的，是 `connect(sender, receiver)` 之后得到的 `operation_state`。

所以你应该反复问自己：

- 谁拥有这次执行实例？
- 它什么时候被销毁？
- 销毁时是否还有未完成工作？
- 如果需要结构化并发，谁来收束这批 operation_state？

模块 C 的 `async_scope` 和模块 D 的自定义 sender，都会强迫你正面回答这些问题。

## 4. scheduler

scheduler 不是线程对象，而是“可把工作安排到某种执行资源上”的能力对象。

你应该把它理解成：

- 线程池可能拥有多个线程
- scheduler 是线程池暴露出来的调度接口
- sender 可以显式依赖 scheduler
- 环境里也可以携带当前 scheduler

所以当你在代码里写 `pool.get_scheduler()` 时，不要把它脑补成“拿到一个线程”，而是“拿到一个调度入口”。

## 5. environment

environment 是这套模型里最容易被低估的设计。

它解决的问题不是“少传几个参数”这么简单，而是：

- 如何让执行上下文沿异步图传播
- 如何让算法不依赖某个固定全局对象
- 如何让 stop token、scheduler 等查询值在不同层之间解耦传递

在练习里你会直接用到：

- `get_scheduler()`
- `get_stop_token()`

记住一个核心判断：如果某个信息本质上属于“执行上下文”，那它更像应该进入 environment，而不是变成层层穿透的普通函数参数。

## 6. completion_signatures

这是你在做练习时最容易忽略的一层。

sender 不仅要能描述工作、能与 receiver 连接。它还需要在编译期声明：

- 如果正常完成，它会产出什么类型的值？
- 如果错误完成，它会传递什么类型的异常或错误？
- 它是否可能走 stopped 通道？

这种声明就是 `completion_signatures`。它本质上是 sender 的"类型级接口"。

为什么这一层是必需的？因为 sender 组合器（比如 `then`、`when_all`、`let_value`）在编译期就需要知道上游可能产出什么，才能推导出自己的输出签名，才能检查下游 receiver 是否能接住这些输出。

你可以把它类比成：`completion_signatures` 之于 sender，就像函数签名之于函数。没有签名，编译器就无法帮你做类型安全检查，组合器也无法自动推导图的类型流。

在练习的前半部分（模块 A 到 C），你大多数时候不需要手动定义 completion_signatures，因为 `just`、`then`、`when_all` 这些现成组合器已经帮你算好了。但到了模块 D 手写 sender 时，你就必须自己声明它，否则你的 sender 无法被 `sync_wait` 或任何标准组合器消费。

在第二阶段（模块 F），你还会学到如何变换、传播、计算 completion_signatures，那是实现层面的核心技术之一。

## 三条 completion channel

很多人刚开始会只盯着 `set_value`，然后把其它情况都笼统叫“失败”。这不够准确。

### 1. value

正常完成，产出值。

### 2. error

异常或错误完成，沿 error 通道传播，通常会被 `upon_error` 或上层 receiver 处理。

### 3. stopped

停止不是普通错误。它更像“这条执行路径没有继续产出值，但这是被框架允许且有意义的一种终止方式”。

如果你把 `stopped` 和 `error` 混在一起，后面理解取消、结构化并发、作用域收束时就会一直模糊。

## 一次执行到底发生了什么

你可以把一次 sender-receiver 执行想成下面四步：

1. 构造 sender 图：此时主要是在描述工作。
2. 提供 receiver：定义结果要如何被接收。
3. `connect(sender, receiver)`：生成 `operation_state`。
4. `start(op)`：真正启动这次执行。

很多高级算法会把这套过程封起来，例如 `sync_wait`。但你做题时不能因为看不见就忘了它存在。

模块 D 的目的之一，就是把这层从“黑盒”里挖出来。

## 惰性：这套模型的第一个核心感觉

sender 图最重要的第一感觉是惰性。

你在写：

```cpp
auto work = ex::just(1)
          | ex::then([](int x) { return x + 1; })
          | ex::then([](int x) { return x * 2; });
```

时，重点不是“我已经排好了三个函数调用”，而是“我已经描述好一条值流转路径”。

大多数情况下，在消费它之前，它并不会真的跑起来。

模块 A 会用最朴素的日志和断点，让你亲眼看到这一点。

## 显式调度：这套模型的第二个核心感觉

并行库经常把调度隐藏在内部实现里。但 sender-receiver 设计里，一个重要目标就是让调度决策能够显式出现在组合图里。

这意味着：

- 你能明确看见某段工作在哪个 scheduler 上开始
- 你能明确看见何时切换执行上下文
- 你能把“工作内容”和“放到哪里执行”区分开

模块 B 练的就是这个。

## 结构化并发：这套模型的第三个核心感觉

当你开始管理多条并发工作时，最危险的问题不是“如何启动”，而是“谁负责收尾”。

`async_scope` 这类对象存在的价值在于：

- 让你显式拥有一组异步工作
- 让你等待它们全部完成
- 防止任务悄悄越过拥有者生命周期

如果你只会启动工作，不会回答“谁拥有它们”，那你还没有真正掌握框架设计层面的要点。

## 每做一题都画这五样东西

从现在开始，你每做完一题，都至少画或写出下面五项：

1. sender graph
2. 谁是最终 receiver
3. 谁拥有 operation_state
4. 哪些阶段可能走 value / error / stopped
5. scheduler 或 environment 在哪里进入图

这五项会把你的注意力从“语法像不像例子”拉回到“对象关系是否清楚”。

## 做题时的四个固定提问

每题都问自己：

1. 这段代码里，真正开始执行的是哪一行？
2. 这次执行的生命周期被哪个对象拥有？
3. 如果这里失败或停止，会走哪条 completion channel？
4. 这里出现的 scheduler / stop token 是普通参数，还是 environment 查询结果？

如果这四个问题里有任意一个回答不清，这题就不算真正做完。
