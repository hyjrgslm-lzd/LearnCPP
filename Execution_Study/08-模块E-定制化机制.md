# 08 模块 E：定制化机制

## 模块目标

前面的模块 D 让你手写了 sender、receiver、operation_state，并接触了 `tag_invoke` 作为"框架要求的接入方式"。这个模块要把定制化机制本身拆开看清楚：

- 为什么 `std::execution` 选择编译期多态而不是虚函数
- ADL 自由函数方案的致命缺陷是什么
- CPO（Customization Point Object）和 Niebloid 是怎么解决 ADL 劫持的
- `tag_invoke` 为什么要用单一 ADL 入口 + 标签类型代替多个独立 ADL 函数
- C++26 方向的 member-first dispatch 为什么又在回到成员函数
- 整条演进线索：ADL (C++98) → CPO/Niebloid (C++20) → tag_invoke (P1895) → member-first (P2855/C++26)

如果你跳过这一层，就很容易在阅读 `stdexec` 源码时对那些 `tag_invoke` 友元声明感到困惑，也无法理解 P2300 为什么选择了这样的定制化架构。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- 为什么裸 ADL 自由函数作为定制点会被第三方命名空间劫持。
- 为什么 CPO 是对象而不是函数模板，以及这一点如何阻止非预期 ADL。
- 为什么 `tag_invoke` 只暴露一个 ADL 名字，所有定制都通过 tag 区分。
- 为什么 member-first dispatch 可以降低样板代码，但无法完全替代 `tag_invoke`。
- 为什么 `std::execution` 中的 `connect`、`start`、`set_value` 等都是 CPO。
- 四种机制各自适合什么场景，各自的权衡是什么。

## 使用建议

- 本模块不依赖线程池或调度器，全部练习都可以在单线程 + 编译期完成。
- 建议每道练习都保留多个版本（ADL 版、CPO 版、tag_invoke 版、member 版），方便最终做对照表。
- 如果你本地的 `stdexec` 版本同时支持 `tag_invoke` 和成员函数两种接入方式，优先两种都试一遍。

## 练习 E-1：CPO 与 Niebloid

### 目标

实现一个最小 CPO（Customization Point Object）和 Niebloid，与裸 ADL 自由函数方案做对照，亲手触发并修复 ADL 劫持问题。

### 前置理解

- **ADL（Argument-Dependent Lookup）**：C++ 在调用一个未限定函数名时，会根据实参类型所在的命名空间去查找候选函数。这意味着只要你在某个命名空间里定义了一个同名函数，编译器就可能在你不知情的情况下把它选中。
- **ADL 劫持问题**：假设你定义了一个协议 `greet(x)`，期望由类型作者在自己的命名空间里提供重载。但如果某个无关的第三方库恰好也定义了 `greet(x)` 并且参数类型能匹配，编译器就可能选中那个无关的重载，导致你的协议被劫持。这在大型项目和跨库组合时是一个现实风险。
- **CPO（Customization Point Object）**：把定制点做成一个全局 `constexpr` 对象（通常是一个带 `operator()` 的函数对象），而不是一个函数模板。因为对象不参与 ADL，所以用户通过 `cpo_name(args...)` 调用时不会触发非预期的 ADL 查找。CPO 内部再按优先级尝试成员函数、受控的 ADL 调用、默认实现。
- **Niebloid**：C++20 Ranges 库中对 CPO 的一种叫法。`std::ranges::sort` 就是一个 Niebloid——它是对象不是函数，因此 `using std::ranges::sort;` 不会让它参与 ADL。
- **为什么 `std::execution` 的定制点是对象**：`stdexec::connect`、`stdexec::start`、`stdexec::set_value` 等全部是 CPO。这保证了无论用户代码在哪个命名空间里调用它们，都不会被意外的同名函数抢走。

### 必做任务

1. **裸 ADL 版本**：在两个独立命名空间 `lib_a` 和 `lib_b` 中，各定义一个类型（例如 `lib_a::Cat` 和 `lib_b::Dog`），并各自提供一个 ADL 自由函数 `greet(Cat)` 和 `greet(Dog)`。在 `main` 中用未限定调用 `greet(cat)` 和 `greet(dog)`，确认 ADL 能正确找到对应实现。
2. **触发 ADL 劫持**：新增一个第三方命名空间 `third_party`，在其中定义一个类型 `third_party::Widget`（它可能继承自 `lib_a::Cat` 或包含一个 `lib_a::Cat` 成员），同时"不小心"定义了一个 `greet(Widget)` 函数。演示：当你用一个 `Widget` 对象调用 `greet(w)` 时，编译器可能选中 `third_party::greet` 而非你预期的定制。分析为什么会这样。
3. **CPO 版本**：在一个专用命名空间（例如 `cpo_ns`）中定义一个 `constexpr` 函数对象 `greet_cpo`。它的 `operator()` 应按以下优先级尝试：
   - 首先：尝试调用 `x.greet()`（成员函数优先）
   - 然后：尝试受控的 ADL 调用 `greet_impl(x)`（注意：用不同于 CPO 自身的名字，避免递归）
   - 最后：提供一个默认实现（例如打印 "unknown"）
4. **验证 CPO 防劫持**：让 `lib_a::Cat` 和 `lib_b::Dog` 通过成员函数或 `greet_impl` 接入 CPO。再用 `third_party::Widget` 测试，确认 CPO 版本不会被 `third_party` 中的意外 `greet` 劫持。
5. **解释为什么 CPO 必须是对象**：在笔记中写出——如果 `greet` 是函数模板而不是对象，`using` 声明加上 ADL 会发生什么？为什么对象不参与 ADL 重载集？

### 进阶任务

- 让 CPO 的检测逻辑使用 C++20 concepts 或 `requires` 表达式来做 SFINAE，而不是靠 `decltype` 尾置返回值。
- 实现一个返回值类型不同的 CPO：例如 `name_of` CPO，对于有 `.name()` 成员的类型返回 `std::string_view`，否则返回 `"<unnamed>"`。观察 CPO 如何做多层 fallback。
- 尝试在 CPO 中加入 `static_assert` 或 `concept` 约束，让"用户类型既没有成员函数也没有 ADL 重载"的情况给出清晰编译错误而不是选中默认实现。

### 验收点

- 你能用编译器输出或运行结果证明裸 ADL 版本存在劫持风险。
- 你能用同样的测试场景证明 CPO 版本不受劫持。
- 你能说出 CPO 内部的优先级链（member → ADL → default）。
- 你能解释为什么 `std::execution` 中 `connect`、`start` 等都是对象而不是函数。
- 你能说明 `using cpo_ns::greet_cpo;` 与 `using std::swap;` 在 ADL 行为上的差异。

### 观察点

- 裸 ADL 方案在小项目里看起来很简洁，但在大型多库项目里非常脆弱。
- CPO 的核心思路是"把入口收窄为一个对象调用，由对象内部控制查找策略"。
- `std::ranges` 里的算法和 `std::execution` 里的定制点走的是同一条路。
- CPO 不是在消灭 ADL，而是在控制 ADL 的边界。

### 常见坑

- 在 CPO 的 `operator()` 内部用和 CPO 同名的函数做 ADL 调用，导致无限递归。
- 以为 CPO 就是"给函数加个 namespace 前缀"——那只是限定调用，不是 CPO。
- 忘记给 CPO 加 `constexpr`，导致某些编译器在模板上下文中报错。
- 把 CPO 定义成 `inline constexpr` 但放在头文件里忘记 `inline`，导致 ODR 违规。
- 在对照测试时忘记用完全相同的类型和场景，导致对比不公平。

### 提示

- 可以用 `if constexpr` + `requires` 表达式来实现 CPO 内部的多层检测。
- ADL 劫持的最小复现不需要复杂继承，只要第三方命名空间里有同名函数 + 参数类型能匹配就行。
- 先把裸 ADL 版本跑通，看见问题，再写 CPO 版本修复，这样印象最深。
- 建议给每个版本的文件或代码段标上 `// v1: raw ADL`、`// v2: CPO` 前缀。

### 复盘问题

- 为什么 C++ 标准库在 C++20 之前的定制点（如 `std::swap`、`std::begin`）容易被劫持？
- CPO 把"函数"变成"对象"这一步，到底切断了 ADL 链条的哪一环？
- 如果一个 CPO 的 fallback 默认实现永远可用，会不会掩盖用户忘了写定制的 bug？怎么权衡？
- 为什么 `std::execution` 不直接用虚函数做多态，而要走 CPO 这条编译期路线？

### 对应官方参考

- N4381: Suggested Design for Customization Points
- Eric Niebler 的博文 "Customization Point Design in C++11 and Beyond"
- `std::ranges` 中 niebloid 的设计

## 练习 E-2：tag_invoke 基础设施

### 目标

实现 `tag_invoke` 基础设施，并用它来定制 `connect` 协议，理解为什么"单一 ADL 入口 + 标签类型"比"每个协议一个 ADL 函数名"更好。

### 前置理解

- **从 CPO 到 tag_invoke 的动机**：练习 E-1 中你看到 CPO 可以防止 ADL 劫持。但如果框架有几十个定制点（`connect`、`start`、`set_value`、`get_env`、`get_scheduler`...），每个定制点都需要一个独立的 ADL 函数名（`connect_impl`、`start_impl`...），用户仍然面临名字冲突问题——你无法保证所有库都不会恰好定义某个 `xxx_impl`。
- **tag_invoke 的核心思想**：只暴露一个 ADL 函数名 `tag_invoke`，所有定制都通过第一个参数（tag 类型）来区分。这样 ADL 命名空间里只有 `tag_invoke` 一个名字，冲突概率从 N 降到 1。
- **dispatch 链条**：`cpo(args...)` → CPO 的 `operator()` → `tag_invoke(cpo_tag, args...)` → 用户在自己类型的命名空间里通过 `friend tag_invoke(tag, ...)` 提供实现。
- **tag_invoke 的签名约定**：`tag_invoke(Tag, Args...)` 中，`Tag` 是 CPO 的标签类型实例，后续参数是原始 CPO 的参数。框架通过 `Tag` 的类型来区分不同的定制点。
- **为什么用 friend 函数**：用户通常以 `friend` 的方式在自己的类型内部定义 `tag_invoke` 重载，这样 ADL 能找到它（因为参数之一是用户类型），同时不污染外层命名空间。

### 必做任务

1. **实现最小 tag_invoke 函数**：定义一个 `tag_invoke` 函数模板作为唯一 ADL 入口点。最简形式：
   ```cpp
   namespace _tag_invoke {
       void tag_invoke(); // poison pill，阻止非受控查找
   }
   using _tag_invoke::tag_invoke; // 引入作为 fallback
   ```
   这样，当没有用户定制时，调用 `tag_invoke(tag, args...)` 会因为 poison pill 而编译失败，而不是静默选中某个无关重载。

2. **定义 connect_t 标签类型**：创建一个空的标签类型 `struct connect_t {};`，并定义 `inline constexpr connect_t connect_tag{};`。

3. **构建 connect CPO**：实现一个 `connect` CPO 对象，它的 `operator()` 接受 `(sender, receiver)` 并内部调用 `tag_invoke(connect_t{}, sender, receiver)`。

4. **自定义 sender**：写一个 `my_sender` 类型，通过 `friend` 函数提供定制：
   ```cpp
   struct my_sender {
       int value;
       template <typename Receiver>
       friend auto tag_invoke(connect_t, my_sender s, Receiver r) {
           // 返回 operation_state
       }
   };
   ```

5. **自定义 query**：写一个 `get_scheduler_t` 标签和对应 CPO，再写一个 `my_context` 类型通过 `friend tag_invoke(get_scheduler_t, const my_context&)` 提供调度器查询。

6. **验证全链路**：在 `main` 中调用 `my_connect(my_sender{42}, my_receiver{})`，确认 dispatch 链条完整：CPO → `tag_invoke` → 用户 `friend` 实现。同样验证 `get_scheduler` 的 query 链路。

7. **在笔记中解释**：为什么一个 `tag_invoke` 名字 + N 个 tag 类型，比 N 个独立 ADL 函数名更安全？从 ADL 查找规则的角度说明。

### 进阶任务

- 为 `tag_invoke` 添加 concept 约束：定义 `tag_invocable<Tag, Args...>` concept，检测 `tag_invoke(tag, args...)` 是否是合法表达式。在 CPO 的 `operator()` 中用这个 concept 做约束。
- 为 `connect` CPO 添加返回类型约束：要求 `tag_invoke` 的返回类型满足 `operation_state` concept。
- 实现第三个定制点 `start_t`，让你的 `operation_state` 也通过 `tag_invoke` 来定制 `start`。把完整的 sender-receiver 三步走（connect → operation_state → start）全部通过 tag_invoke 串起来。

### 验收点

- 你能手动走通 `connect(sender, receiver)` 的完整 dispatch 链。
- 你能说明 `tag_invoke` 的 poison pill 为什么重要。
- 你能说明 friend 函数为什么能被 ADL 发现。
- 你能对比 E-1 的 CPO 内部直接做 ADL 和 E-2 的 CPO 通过 `tag_invoke` 做 ADL 的差异。
- 你能解释为什么 `stdexec` 的每个 CPO（`connect_t`、`start_t`、`set_value_t`...）都是 tag 类型。

### 观察点

- `tag_invoke` 把 N 个 ADL 函数名合并成一个，这是一次命名空间级别的收窄。
- 用户只需要学一个模式：`friend tag_invoke(SomeTag, MyType, ...)`，所有定制点的接入方式统一。
- 这种设计让框架可以在 CPO 内部做统一的约束检查、日志、计数等横切逻辑。
- `stdexec` 源码中大量的 `friend tag_invoke(...)` 就是这个模式的实际应用。

### 常见坑

- 忘记定义 poison pill，导致在没有用户定制时编译器选中了某个意外的候选。
- `friend` 函数的参数类型写错，导致 ADL 找不到它。
- CPO 的 `operator()` 直接调用用户类型的成员函数而不经过 `tag_invoke`，绕过了整个机制。
- 以为 `tag_invoke` 本身需要很复杂的实现——实际上它只是一个名字，真正的逻辑在用户的 `friend` 重载里。
- 在 CPO 里写死了某个具体类型，失去了泛型能力。

### 提示

- poison pill 的作用是确保在无匹配时给出编译错误而不是静默通过。
- 先实现 `connect` 一个 CPO 把全链路走通，再加 `get_scheduler` 等其它定制点。
- `friend` 函数定义在类体内部时，它的命名空间是类所在的命名空间，这正好让 ADL 能找到它。
- 可以回到模块 D 的类型骨架，对照看 `tag_invoke(stdexec::connect_t, ...)` 的实际用法。

### 复盘问题

- 如果没有 `tag_invoke`，每个定制点都用独立 ADL 名字，维护成本会怎么增长？
- `tag_invoke` 的 tag 类型在运行时有开销吗？为什么？
- 你现在回头看模块 D 中的 sender/receiver 骨架，能否识别出哪些 `friend` 声明就是 `tag_invoke` 模式？
- 如果你要给框架新增一个定制点（比如 `get_allocator`），在 `tag_invoke` 体系下需要做哪几步？

### 对应官方参考

- P1895R0: tag_invoke: A general pattern for supporting customisable functions
- `stdexec` 源码中 `tag_invoke` 的使用
- `libunifex` 中 tag_invoke 的早期实现

## 练习 E-3：演进对比与 Member-first Dispatch

### 目标

把 E-2 中基于 `tag_invoke` 的 sender 重构为 member-function dispatch（C++26 方向），然后横向比较四种定制机制，形成完整的演进认知。

### 前置理解

- **tag_invoke 的样板代码问题**：你在 E-2 中已经体会到，每个定制都需要写 `friend tag_invoke(SomeTag, MyType, Args...)`，tag 类型作为第一个参数出现在每个签名里，可读性不算好，样板代码也不少。对于"你自己拥有的类型"，直接写成员函数会自然得多。
- **Member-first dispatch（P2855 方向）**：C++26 的 `std::execution` 提案倾向于让 CPO 优先检测成员函数。例如 `connect(sender, receiver)` 会先尝试 `sender.connect(receiver)`，找不到时再 fallback 到 `tag_invoke(connect_t{}, sender, receiver)`。这样，对于你自己写的类型，只需要定义成员函数就行；`tag_invoke` 退化为"定制你不拥有的第三方类型"的后备机制。
- **两种场景的区分**：
  - 你拥有类型的源码 → 成员函数最自然、最简洁
  - 你不拥有类型的源码（第三方库类型）→ 必须用 `tag_invoke` 或其他外部注入方式
- **stdexec 的实际现状**：截至目前，`stdexec` 的较新版本已经同时支持两种接入方式（member 和 `tag_invoke`），CPO 内部按 member-first 优先级做 dispatch。

### 必做任务

1. **重构为成员函数版本**：把 E-2 中的 `my_sender` 从 `friend tag_invoke(connect_t, my_sender, Receiver)` 重构为直接提供 `connect(Receiver)` 成员函数。同样把 `operation_state` 的 `start` 从 `friend tag_invoke(start_t, ...)` 改为成员函数。

2. **更新 CPO**：修改 `connect` CPO 的 `operator()`，让它优先检测 `sender.connect(receiver)`。如果有，直接调用成员函数；如果没有，fallback 到 `tag_invoke(connect_t{}, sender, receiver)`。用 `if constexpr` + `requires` 表达式实现。

3. **保留两种类型做对照**：保留 E-2 的 `tag_invoke` 版本 sender（例如命名为 `ti_sender`），同时保留 E-3 的 member 版本 sender（例如命名为 `member_sender`）。用同一个 CPO 分别调用两种 sender，证明 CPO 能透明地处理两种定制方式。

4. **写对照表**：列出以下维度的比较（建议用注释或笔记形式）：

   | 维度 | 裸 ADL | CPO (E-1) | tag_invoke (E-2) | member-first (E-3) |
   |------|--------|-----------|-------------------|---------------------|
   | 用户代码行数 | | | | |
   | 可读性 | | | | |
   | 定制自己拥有的类型 | | | | |
   | 定制第三方类型 | | | | |
   | ADL 劫持风险 | | | | |
   | 框架横切逻辑能力 | | | | |

5. **讨论适用场景**：在笔记中明确写出——什么时候 member-first 就够了？什么时候必须用 `tag_invoke`？给出至少两个具体例子：
   - 例子 1：你自己写的 sender 类型 → member 函数足够
   - 例子 2：你想让一个第三方库的类型（你无法修改其源码）支持某个 query → 必须用 `tag_invoke`

6. **写演进总结**：用一段连贯的文字写出完整的演进路线：
   - **ADL (C++98)**：未限定调用 + ADL 查找，简单但脆弱，`swap` / `begin` 就是这个时代的产物
   - **CPO / Niebloid (C++20)**：把定制点做成对象，收窄 ADL 入口，`std::ranges` 开始大规模使用
   - **tag_invoke (P1895)**：进一步收窄到单一 ADL 函数名，所有定制通过 tag 区分，`stdexec` / `libunifex` 采用
   - **Member-first dispatch (P2855 / C++26)**：CPO 优先检测成员函数，`tag_invoke` 退为后备，兼顾简洁性和扩展性

### 进阶任务

- 实现一个更完整的 member-first CPO：让 `set_value` CPO 先检测 `receiver.set_value(values...)`，再 fallback 到 `tag_invoke(set_value_t{}, receiver, values...)`。把完整的 sender-receiver connect-start-complete 链路全部走一遍 member-first 版本。
- 研究 `stdexec` 源码中实际的 CPO 实现（例如 `stdexec::connect` 的定义），看它是否已经实现了 member-first dispatch。在笔记中记录你找到的代码位置和 dispatch 策略。
- 设计一个混合场景：你的 `my_sender` 用 member 方式提供 `connect`，但它的 `get_env` 用 `tag_invoke` 方式提供。验证两种定制方式可以在同一个类型上混合使用。

### 验收点

- 你的 member 版本 sender 能通过同一个 CPO 正常工作。
- 你的 CPO 能同时处理 member 版本和 tag_invoke 版本的 sender。
- 你的对照表覆盖了至少 6 个维度。
- 你能清楚说出 member-first 无法覆盖的场景（第三方类型定制）。
- 你能完整复述四阶段演进线索，并给出每个阶段的代表性技术。

### 观察点

- member-first dispatch 让"最常见的定制场景"（定制自己的类型）变得最简洁。
- `tag_invoke` 没有被废弃，它退化为处理边界场景的后备机制。
- 这种"常见路径简洁 + 边界路径灵活"的分层设计是 C++ 标准库演进的常见思路。
- 如果你只看 C++26 的最终形态，会觉得成员函数理所当然；但只有理解了 ADL → CPO → tag_invoke 的历史，才能理解为什么 CPO 内部要做多层 fallback。

### 常见坑

- 重构时只改了 `connect` 忘了改 `start`，导致一半走 member 一半走 tag_invoke，行为不一致。
- CPO 内部的优先级顺序写反了（先查 tag_invoke 再查 member），导致 member 版本永远不被选中。
- 对照表只比较语法长短，忽略了"能否定制第三方类型"这个关键维度。
- 误以为 member-first 可以完全替代 tag_invoke，在笔记中没有讨论第三方类型场景。
- 把 `tag_invoke` 版本和 member 版本放在同一个类型里，导致两者同时存在时 CPO 选了哪个不清楚。

### 提示

- `if constexpr` + `requires` 表达式是实现多层 fallback 的最清晰方式。
- 对照表可以先手工填，不需要写成代码自动生成。
- 重构时保留旧版本的完整副本，方便一行行对照。
- 写演进总结时，每个阶段给出一个"代表性 API"会帮助记忆：ADL → `swap`，CPO → `std::ranges::sort`，tag_invoke → `stdexec::connect`，member-first → C++26 `std::execution::connect`。

### 复盘问题

- 如果 C++ 从一开始就有 concepts 和 `constexpr` 对象，ADL 定制点这条弯路还会走吗？
- member-first dispatch 在什么意义上是"回到了最朴素的面向对象"，又在什么意义上不是？
- 为什么 `std::execution` 不直接用虚函数 + 类型擦除，而要走编译期多态这条路？性能之外还有什么原因？
- 如果你要从零设计一个新的 C++ 框架，你会选择哪种定制化机制？为什么？
- 回顾模块 D 中你手写的 sender/receiver，现在你能否识别出哪些 `friend` 声明本质上就是 tag_invoke dispatch 的一环？

## 做完模块 E 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- 裸 ADL 定制点在大型项目中会被第三方命名空间劫持，这是 CPO 出现的根本原因。
- CPO 是对象不是函数模板，因此它不参与非预期的 ADL 重载集构建。
- `tag_invoke` 用单一 ADL 函数名 + tag 类型来区分所有定制点，把命名空间污染降到最低。
- member-first dispatch 让最常见的定制场景（定制自己的类型）写法最简洁，但无法取代 `tag_invoke` 对第三方类型的外部定制能力。
- `std::execution` 中的 `connect`、`start`、`set_value` 等全部是 CPO，这是整个框架可扩展性的基石。
- 四种机制不是互相替代，而是演进关系：每一步都在解决上一步暴露出来的问题，最终形成一个分层的 dispatch 策略。
