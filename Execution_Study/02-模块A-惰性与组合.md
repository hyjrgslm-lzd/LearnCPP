# 02 模块 A：惰性与组合

## 模块目标

这个模块只做一件事：把 sender 当成“工作描述对象”的感觉练出来。

你会先从最接近现有 MSVC `<execution>` 的热身题开始，再进入 `just`、`then`、`when_all`、`sync_wait` 这组最基础但最关键的组合。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- 为什么 sender 通常是惰性的。
- 为什么 `sync_wait` 之类的消费端会成为执行边界。
- 为什么 `when_all` 倾向于让值汇合，而不是让多个阶段去共享写同一块状态。
- 为什么 sender-receiver 更像“图组合”，而不是“线程 API 包装”。

## 练习 1：两种 execution 的第一印象

### 目标

用同一个问题分别写出“并行算法执行策略版”和“sender 图版”，强制自己看见它们在抽象层次上的差异。

### 前置理解

- 你知道 `std::transform_reduce` 或 `std::for_each` 的基本用法。
- 你能把一组连续数据拆成固定数量的区间。
- 你接受这题的重点不是跑分，而是比较两种抽象方式。

### 必做任务

1. 构造一个整数数组，范围建议为 `1..1'000'000`。
2. 写版本 A：使用 `std::transform_reduce(std::execution::par, ...)` 或等价并行算法，计算“所有偶数平方和”。
3. 写版本 B：把数据手工切成 4 段，每一段对应一个 sender 分支。
4. 每个 sender 分支只负责本段局部求和，建议写成 `just(range) -> then(local_reduce)`。
5. 用 `when_all` 汇合 4 个局部和，再在最后一个 `then` 里把 4 个结果加起来。
6. 用 `sync_wait` 得到最终结果。
7. 在代码旁边或单独笔记里写下：版本 A 与版本 B 分别是在什么位置进入执行阶段的。

### 进阶任务

- 把每段返回值从单个整数升级为结构体，例如 `{ partial_sum, even_count }`。
- 在最终汇合阶段同时产出总和与总计数。
- 尝试把 sender 版本拆成“构图函数”和“消费函数”两层，进一步体会“描述工作”和“触发工作”的分离。

### 验收点

- 两个版本的最终结果一致。
- 你能指出 sender 版本里真正开始执行的边界，而不是笼统地说“定义变量时就开始了”。
- 你能说明 sender 版本为什么需要你手动拆分数据，而并行算法版本不需要。
- 你能说明这题里 sender 图的价值不是“更短”，而是“组合关系更显式”。

### 观察点

- 并行算法版本的中心是“把策略喂给算法”。
- sender 版本的中心是“先构造几条分支，再显式合流”。
- 在 sender 版本里，`when_all` 让多个结果在类型层面汇合，而不是把它们塞进共享可变对象。
- sender 版本里，你会明显感觉到：局部工作、汇合工作、消费工作是三个不同层次。

### 常见坑

- 把 sender 版本写成 `just(vector) -> then(一次性全量求和)`，这样就失去了“显式分支和组合”的练习意义。
- 试图让 sender 版本完全复刻并行算法库的内部调度行为。这题不需要，也不现实。
- 在 `par_unseq` 场景里乱打日志，导致观察结果被 I/O 干扰。
- 把共享累加器放到 4 个分支里并发写，结果练成了并发同步题，而不是 sender 组合题。

### 提示

- 区间可以用迭代器对、索引对，或轻量的 `span` 表示。
- sender 版本里，每个分支内部可以先只做普通顺序累加，这不影响你学习框架结构。
- 如果你发现 sender 版本代码更长，这是正常现象；你买到的是“结构显式”，不是“短代码”。
- 先不要纠结性能曲线，重点是比较抽象边界。

### 复盘问题

- 版本 A 的“执行策略”与版本 B 的“sender 图”分别附着在什么对象上？
- sender 版本为什么更容易插入新的阶段，例如统计、记录、合并多种结果？
- 如果你删掉 sender 版本里的 `sync_wait`，还有哪些代码会真正执行？
- 如果把 4 个分支改成 8 个分支，这更像是在改“算法参数”，还是在改“执行图形状”？

### 对应官方参考

- Microsoft Learn: `<execution>`
- `NVIDIA/stdexec` README 的基础示例

## 练习 2：值通道与惰性

### 目标

用最小 sender 链条观察“值是如何沿图流动的”，并用日志或断点证明：在被消费之前，图只是图。

### 前置理解

- 你知道 `just` 可以构造一个最简单的 sender。
- 你理解 `then` 表示“在 value completion 上继续做转换”。
- 你知道 `sync_wait` 会把 sender 消费掉并同步等待结果。

### 必做任务

1. 构造一条最小链路：`just(5) -> then(+1) -> then(*2) -> sync_wait`。
2. 在每个 `then` 的 lambda 里打印阶段名和输入值。
3. 在 `sync_wait` 前后分别打印一条主线程日志。
4. 运行程序并记录日志顺序，证明各阶段不是在定义 sender 时立刻执行。
5. 把输入值从 `int` 换成一个自定义结构体，例如 `TaskInput { int base; std::string label; }`。
6. 再做一次日志观察，确认值仍然是沿 value channel 流动，而不是靠外部共享状态传播。

### 进阶任务

- 插入一个返回 `void` 的 `then` 阶段，再在后续阶段重新生成新值，观察 value channel 形状如何变化。
- 额外做一个版本：让其中一个阶段只记录日志但不修改值，再比较“有副作用的透传”和“真正变换值”的区别。
- 在断点模式下逐步观察 `sync_wait` 前后的调用栈变化。

### 验收点

- 你能用一段清晰的日志证明惰性。
- 你能解释 value channel 里每一阶段的输入输出分别是什么。
- 你没有依赖外部全局变量来传递中间结果。
- 你知道把一个阶段改成 `void` 返回后，下游签名会发生什么变化。

### 观察点

- `then` 的重点不是“又调了一个函数”，而是“把上游 value completion 接到下游变换上”。
- 只要没有显式调度切换，这些阶段更像是一条纯数据流，而不是线程跳来跳去的并发图。
- `sync_wait` 在这里同时扮演了“最终 receiver”与“同步边界”的角色。

### 常见坑

- 在构造 sender 时就调用了某个带副作用的普通函数，导致误以为 sender 本身不惰性。
- 日志打得过粗，只看到“开始/结束”，却看不到每个阶段的真实顺序。
- 结构体值通过引用在多个地方被改写，结果看不清 value flow。
- 对 `void` 阶段的下游参数个数没有预期，编译错误后以为是库不稳定。

### 提示

- 给每个阶段一个固定名字，比如 `stage_1_prepare`、`stage_2_transform`、`stage_3_finalize`。
- 你可以给每条日志加一个递增序号，避免多行输出时顺序感不清。
- 如果你引入了结构体，优先让每个阶段返回新值，而不是原地修改共享对象。
- 观察“谁在打印日志”比“日志写了什么”更重要。

### 复盘问题

- 如果把 `sync_wait` 换成别的 receiver，sender 图本身需要变吗？
- 为什么说 sender 更像“描述工作”，而不是“包装一个立即执行的函数对象”？
- 当某个阶段返回 `void` 时，下游为什么会感觉像进入了一条新的 value channel 形状？
- 为什么这题里几乎不需要谈线程，但仍然能学到异步框架的核心设计？

### 对应官方参考

- `NVIDIA/stdexec` README 中 `just / then / sync_wait` 的基本形状

## 练习 3：扇出与合流

### 目标

用 `when_all` 把三种不同类型的结果汇合成一个最终对象，彻底建立“组合优先于共享状态”的习惯。

### 前置理解

- 你已经做完练习 2，知道值是如何沿 sender 图传播的。
- 你知道 `when_all` 可以并列组合多个 sender。
- 你接受本题的重点是值的组织方式，而不是模拟真实网络或 I/O。

### 必做任务

1. 设计三个轻量类型，例如：`UserProfile`、`QuotaState`、`FeatureFlags`。
2. 以同一个 `user_id` 为输入，写三条独立分支。
3. 每条分支都从 `just(user_id)` 起步，并在自己的 `then` 中构造对应结果对象。
4. 用 `when_all` 汇合三条分支。
5. 在最后一个 `then` 中把三种结果拼成一个 `UserDashboard` 或 `UserViewModel`。
6. 用 `sync_wait` 拿到最终对象，并打印其中关键字段。

### 进阶任务

- 把其中一条分支改为返回 `std::optional` 或带状态字段的结果，练习在合流点做决策。
- 尝试把三条分支分别封装成三个返回 sender 的函数，再在主流程里组合。
- 再做一个版本：人为增加第四个分支 `AuditInfo`，观察合流点的形状如何变化。
- 用 `split` 把某一条分支的 sender 结果同时供给两个不同的下游消费者。例如：`UserProfile` 既要给 `UserDashboard` 用，也要给一个单独的 `AuditLog` 用。观察：如果不用 `split`，同一个 sender 能否被连接两次？编译结果是什么？这里的核心设计意图是什么？

### 验收点

- 三条分支之间没有通过共享可变对象互相写数据。
- 最终对象的组装发生在显式的合流点，而不是分支内部偷偷完成。
- 你能画出一张很清楚的三叉树形 sender graph。
- 你能说明如果未来新增一个分支，代码应该改在“图结构”哪里。

### 观察点

- `when_all` 让”并列工作”在图结构上变得一眼可见。
- 每个分支只负责自己的产物，合流点才负责跨分支的综合判断。
- 这类写法比”先创建一个大对象，再让三个异步阶段往里填字段”更容易推理。
- sender 默认是”单次消费”对象——一个 sender 只能被 `connect` 一次。`split` 通过共享结果打破这个限制，是理解 sender 值语义的关键观察点。

### 常见坑

- 三条分支共享一个 `UserDashboard` 并分别写字段，结果把组合题写成并发共享状态题。
- 在分支内部偷偷依赖其它分支的中间结果，破坏独立性。
- 误以为 `when_all` 必须搭配真实并发才有价值；其实它首先是组合器。
- 最终对象过于庞大，导致你看不出 `when_all` 汇合的价值。

### 提示

- 让三个结果类型足够小，字段只保留能体现差异的那几个。
- 先让每条分支都纯计算，不碰 I/O，不碰外部状态。
- 如果想让日志更有辨识度，可以给每条分支固定前缀。
- `UserDashboard` 这种合流产物最好是不可变或只在最终阶段构造一次。

### 复盘问题

- 为什么 `when_all` 的心理模型更接近“结果汇合”，而不是“任务都跑完就行”？
- 如果你把三条分支改成顺序执行，再逐步合并结果，会损失什么表达力？
- 为什么“每条分支只生产自己的结果”有助于后面处理错误和生命周期？
- 这题中，sender 图最像一张什么样的结构图？

### 对应官方参考

- `NVIDIA/stdexec` README 的 `when_all` 示例
- `stdexec/examples/then.cpp` 一类基础组合示例

## 做完模块 A 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- sender 主要是在描述工作，而不是立刻启动工作。
- `sync_wait` 之类的消费端是执行边界。
- `then` 关注的是 value completion 的转换。
- `when_all` 让“并列工作”和“显式合流”成为图上的一等公民。
- sender-receiver 的价值不在于代码一定更短，而在于结构更清楚、组合点更显式。
