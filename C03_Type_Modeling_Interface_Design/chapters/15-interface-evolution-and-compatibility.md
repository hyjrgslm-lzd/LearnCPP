# 15：接口演进、源兼容、行为兼容与 ABI 边界

接口设计完成后，真实项目还会继续演进。演进风险至少有三条轴：源兼容、行为兼容、ABI 兼容。源兼容问“旧源码能否重新编译”；行为兼容问“旧调用重新编译后语义是否保持”；ABI 兼容问“旧二进制不重新编译能否加载新实现并正确运行”。三者不能互相推出。一个改动可能源码能编译但行为变了，也可能源码不用改但 ABI 已破坏。

默认实参是行为兼容常见陷阱。默认值绑定在调用点，旧客户端编译时看到 `timeout = 1000`，新头文件改成 `timeout = 250` 后，新编译客户会用 250，旧二进制仍可能带着 1000。若这代表协议超时，行为就分裂。演进时更安全的做法是新增显式 overload 或 options 对象，让旧入口继续显式传旧默认值；新入口使用新默认值，并在文档里标出行为变化。

新增 overload 也会改变解析。旧代码 `send(0)` 原来匹配 `send(bool)`，新增 `send(int)` 后会改走新 overload；旧代码 `send({1,2})` 可能因 initializer-list overload 改变优先级。源兼容并不等于同一 overload 被选中。正反实验应让 v1 客户端代码分别包含 v1/v2 头并观察解析结果，而不是只看编译是否成功。

虚接口演进更危险。给已有基类新增纯虚函数会让旧派生类无法重新编译；给虚函数改参数或 noexcept 会改变 override 关系；在二进制边界上，虚表布局变化还可能破坏旧插件。兼容做法通常是新增非虚自由函数、适配器、能力查询接口，或新增 V2 接口并通过 `dynamic_cast`/查询函数发现。不要在旧稳定基类上随意追加纯虚槽位。

Pimpl 能降低头文件暴露，减少重编译，也能把私有数据布局藏到 `.cpp`。但 Pimpl 不自动提供跨编译器 ABI 稳定：调用约定、标准库类型、异常模型、分配器、RTTI、编译器版本和链接边界都仍可能破坏二进制兼容。跨 ABI 边界时更稳的是 C API、固定大小句柄、显式创建/销毁函数和版本查询；C++ Pimpl 只是减少公开布局，不是 ABI 魔法。

本章把 C01 的编译/链接/ABI 模型接回接口设计：头文件决定调用点能看到什么，默认实参在调用点展开，inline 函数和模板在使用方实例化，虚函数表和对象布局属于二进制协议。C03 的类型模型若不考虑这些边界，写出来的接口会在升级时把客户锁死。

练习 L15 是实现型，并带一个 ABI 风险观察模型。给定 v2 引擎 `Engine::fetch(name, timeout_ms = 250, Format = compact)`，学生要写 `CompatClient` 暴露 v1 语义：`fetch(name)` 必须继续使用 v1 默认超时 `1000` 和 legacy 格式；`fetch(name, timeout)` 使用显式 timeout 但仍保持 legacy 格式；新行为通过 `fetch_compact(name)` 显式进入。Reference 与 validation_good 独立实现同一契约，validation_bad 只犯一个错误：直接使用 v2 默认实参，导致 v1 默认超时从 1000 变成 250。checker 精确拒绝这个触发面。另有 `abi_model` 对比 v1/v2 公开 options 布局，运行时确认公开布局已经变化；这只证明 ABI 风险模型，不证明真实旧二进制加载新库的结果。

完整解析：适配器不是为了隐藏所有变化，而是把演进分成旧入口和新入口。旧入口承诺旧行为，所以它不能依赖 v2 头里的默认实参；它要把旧默认值作为实现细节显式传入。新入口可以选择新默认值，但名称或参数应让调用者意识到行为变化。这个实验只证明源级和行为级兼容模型，不声称 ABI 稳定；ABI 需要单独的二进制 v1 客户 + v2 实现实验和平台约束。
