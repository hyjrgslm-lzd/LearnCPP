# 03 模块 B：核心容器与字符串

## 模块目标

反向引用 `01-心智模型.md` 的 §1 Module-first：在真正进入 UObject/反射层（模块 D）之前，你必须先把 UE 的底层词汇钉牢。`TArray`、`TMap`、`TSet`、`FString`、`FName`、`FText` 这六个类型是 UE 代码库里出现频率最高的基础积木。它们表面上对应 STL 的 `std::vector`、`std::unordered_map`、`std::unordered_set`、`std::string`，但每一个都有足以让经验丰富的 C++ 工程师踩坑的语义差异。

本模块的阶梯定位是 **use + inspect**：你先正确使用这些类型（use），再通过读 UE5.7 源码理解它们的设计决策（inspect）。你不需要重新实现这些容器，但你需要知道：为什么 `RemoveAtSwap` 比 `RemoveAt` 快、`TInlineAllocator` 对 cache 局部性的影响在哪里量化、`FString` 的 `operator*` 做了什么（以及什么时候不安全用它的返回值）、`FName::ToString()` 为什么有成本、`FText` 的惰性求值为什么和 `FString` 的立即字符串不是同一层抽象。

本模块不涉及 UObject、UPROPERTY、GC——这些是模块 C/D 的主题。本模块里所有代码都是纯 C++ 层面操作，只依赖 `Core` 模块。

## 模块完成标准

做完本模块，你至少要能稳定说清楚以下四条：

- **TArray growth policy 与 reserve 语义**：TArray 的默认 allocator 用几何增长策略（slack），`Reserve(N)` 保证后续 N 次 `Add` 不触发重分配，但 `Shrink()` 是显式调用的，不会自动发生。`RemoveAt` 保序但 O(N) 移位；`RemoveAtSwap` 破坏顺序但 O(1)。这两者在不同场景下的选择完全不同。
- **FString 与 std::string 在内存、编码、API 上的三条差异**：FString 内部是 `TArray<TCHAR>`（Windows 上 `TCHAR = wchar_t`，UTF-16LE 内部编码），而 `std::string` 是 `char`（通常 UTF-8）；`FString::GetData()` 返回内部指针（可能 null 指针当数组为空），`operator*` 保证返回有效 null-terminated 指针（空串返回 `TEXT("")`），两者不等价；`FString` 没有 SSO（small string optimization），所有字符串都在堆上分配。
- **FName 为何不可修改（池化 ID 本质）**：`FName` 内部存的是 `FNameEntryId`（一个 `uint32` 偏移量），指向全局 `FNamePool` 里的 `FNameEntry`。一旦入池，字符串内容就不能改，你持有的只是 ID，不是字符串本身。`FName::ToString()` 需要从池里查条目再构造 `FString`，不是 O(1) 读字段。
- **FText 惰性求值与 FString 立即求值的差异**：`FText` 持有一个 `TSharedRef<ITextData>` 以及一条 `FTextHistory`（描述"这段文字是怎么来的"）。调用 `FText::Format(...)` 时，结果 FText 不是立即把格式化字符串算出来放进去，而是存下了"格式化 pattern + 参数"的 history；只有在 `ToString()`（或本地化系统刷新）时才真正求值。`FString::Printf` 是立即求值，调用时就完成了字符串拼接。

## 练习 B1：TArray / TMap / TSet 语义与迭代器失效

### 目标

通过一系列可测量的实验，把 UE 三大容器在增删改过程中的内存语义和迭代器失效规律刻进直觉，并对比它们与对应 STL 容器的差异。重点不是"会用 API"，而是"能预测一次操作后容器内存状态和已持有指针/迭代器的有效性"。

### 前置理解

- 你熟悉 `std::vector` 的迭代器失效规则（`push_back` 触发重分配使所有迭代器失效，`erase` 使被删元素之后的迭代器失效）。
- 你熟悉 `std::unordered_map` 在 rehash 后指针失效的行为。
- 你理解 cache 局部性的基本概念（连续内存访问比随机内存访问快）。
- 你已完成模块 A（理解 `.Build.cs` 依赖声明，本题只需依赖 `"Core"`）。

### 必做任务

1. **TArray 基础语义对比**

   创建一个 `TArray<int32>`，填入 100 个元素。记录 `GetData()` 返回的指针地址 P1。

   - 调用 `Add(101)`，再记录 `GetData()` 地址 P2。观察 P1 == P2 还是 P2 != P1，解释触发重分配的条件（capacity 是否足够）。
   - 提前调用 `Reserve(200)` 后再重复上述实验，观察 P2 是否等于 Reserve 后的指针。
   - 写下结论：`Reserve` 在哪个条件下保证不触发重分配。

2. **RemoveAt vs RemoveAtSwap 对比**

   创建 `TArray<FString>`，依次填入 `"A"`, `"B"`, `"C"`, `"D"`, `"E"`（共 5 个）。

   - 用 `RemoveAt(1)` 删除索引 1（即 `"B"`），打印删除后数组内容。验证顺序：`["A", "C", "D", "E"]`。
   - 重新创建同样内容的数组，用 `RemoveAtSwap(1)` 删除索引 1，打印删除后数组内容。验证顺序：最后一个元素被移到索引 1 的位置，即 `["A", "E", "C", "D"]`。
   - 对比两次操作：哪个保序，哪个不保序？对 N 个元素，`RemoveAt` 最坏情况移动几个元素，`RemoveAtSwap` 移动几个？记录结论。

3. **TArray 迭代器失效实验**

   用 ranged-for 遍历 `TArray<int32>` 时，在循环体内调用 `Array.Add(999)`（注意 UE 调试构建下有 `TCheckedPointerIterator` 守卫）。

   - 在 Debug/Development 构建中观察是否触发 `ensureMsgf`（"Array has changed during ranged-for iteration!"）。
   - 改为用索引循环 `for (int32 i = 0; i < Array.Num(); ++i)` 来安全地边遍历边修改，记录两种写法的差异。

4. **TMap 基础操作与 FindOrAdd**

   创建 `TMap<FString, int32>` 代表"单词频率表"。

   - 向 Map 里插入 100 条不同的 key。记录此时 `Num()` 返回值。
   - 用 `FindOrAdd(SomeKey)` 取到一个引用 `int32& Ref`，自增 1。然后再向 Map 插入超过当前 bucket 数量的新条目（触发 rehash）。在 rehash 后解引用 Ref，观察结果。
   - 写下结论：`TMap` 在 rehash 后，之前通过 `Find()` 或 `FindOrAdd()` 取到的引用是否仍然有效。与 `std::unordered_map` 的行为对比（`std::unordered_map` 保证 rehash 不使引用失效，TMap 不提供此保证）。

5. **TSet 基础操作与包含测试**

   创建 `TSet<int32>`，插入 1000 个随机整数。

   - 测量 `Contains(X)` 的调用（任意 X），体会哈希查找的 O(1) 平均复杂度。
   - 对同一组数据用 `TArray<int32>` 线性查找（`Array.Contains(X)` 逐元素比较）做对比，用 `SCOPE_CYCLE_COUNTER` 或 `FPlatformTime::Cycles()` 记录两者的 tick 差。
   - 记录观察：集合大小为 N 时，TSet 查找与 TArray 查找的耗时比约为多少。

### 进阶任务

- **TInlineAllocator 对 cache 局部性的影响**：

  准备两个版本的数组：
  ```cpp
  TArray<int32>                               HeapArr;   // 默认堆分配
  TArray<int32, TInlineAllocator<16>>         InlineArr; // 前 16 个元素在栈/对象内
  ```
  各填入 16 个随机 int32。用 `FPlatformTime::Cycles()` 测量对全部元素求和的时间，重复 1 000 000 次，取平均。观察：当元素数量不超过 inline 上限时，InlineArr 的求和是否显著快于 HeapArr，为什么（指针追踪次数差异）。再把元素数量增到 32（超过 inline 上限），重复实验，观察性能差异是否消失。

- **TSparseArray 结构 inspect**：

  阅读 `Engine/Source/Runtime/Core/Public/Containers/SparseArray.h` 的类定义。回答：TSparseArray 的"稀疏"体现在哪里（删除元素后位置被标记为空洞而非移动后续元素）？它为什么能保证元素的指针在删除后仍然有效（对未被删除的元素）？TMap 内部用 `TSparseArray` 存储键值对，这和 TArray 直接存储有什么本质区别？

- **TChunkedArray 适用场景 inspect**：

  阅读 `Engine/Source/Runtime/Core/Public/Containers/ChunkedArray.h`（如果存在于 UE5.7 源码中），或在 UE 源码里搜索 `TChunkedArray` 的使用场景（Glob 一下 `**/*.h` 中的使用处）。理解：分块数组为什么能保证"指针稳定性"（每块独立分配，不整体 realloc），以及什么场景下选分块数组而非 TArray。

### 验收点

- 你能在不查文档的情况下口述：`RemoveAt` 和 `RemoveAtSwap` 的时间复杂度差异，以及各自适用场景。
- 你能解释为什么 `TArray` 在 `Add` 触发重分配后，所有已持有的 `ElementType*` 指针都失效。
- 你能解释 TMap 的 `FindOrAdd` 返回引用在 rehash 后失效的根本原因（underlying storage 重分配）。
- 你做过 TSet vs TArray `Contains` 的耗时对比，并能用数字说明哈希查找在 N=1000 时的优势。
- 你读过 `TCheckedPointerIterator` 的定义（`Array.h` 第 204 行附近），能解释它在 Debug 构建里为什么能检测到"边遍历边修改"。

### 观察点

- `TArray::RemoveAt` 在 `Array.h:2083` 附近实现，它通过 `DestructItems` + `FMemory::Memmove` 完成移位。`RemoveAtSwap` 在 `Array.h:2185` 附近，用最后一个元素覆盖被删元素，再缩短 ArrayNum。两者都接受 `EAllowShrinking` 参数控制是否调用 `ReallocShrink`——默认值因 allocator 类型而异（`TInlineAllocator` 默认 `EAllowShrinking::No`，避免把 inline 存储切换回堆）。

- `TArray` 的增长策略是"几何 slack"：`CalculateSlackReserve` 函数在 `ContainerAllocationPolicies.h` 里，实际增长量大于请求量，减少 realloc 频率。这和 `std::vector` 的行为类似，但具体增长系数在不同平台/allocator 下不同。

- `TMap` 在 `Map.h` 里用 `TSet<TPair<KeyType, ValueType>>` 作为内部存储，而 `TSet` 内部用 `TSparseArray` + 哈希桶。这意味着每次 rehash，`TSparseArray` 的底层 storage 会重分配，之前通过 `Find()` 取到的指针/引用失效——这和 `std::unordered_map` 标准保证的节点稳定性相反，是 UE 设计的一个已知 trade-off（UE 优先考虑 cache 局部性，而不是指针稳定性）。

- `TInlineAllocator<N>` 在对象内部嵌入 N 个元素的存储，只有当元素数量超过 N 时才回退到堆分配。这在 UE 的 `TSet` 内部哈希桶、`FTextFormat` 内部、许多短命的临时数组中大量使用。关键是：inline 部分和对象共同分配，访问时无额外指针追踪，cache 友好；但对象本身变大了，不适合存在大量实例里。

### 常见坑

- **在 ranged-for 中修改 TArray 大小**：UE Debug 构建下 `TCheckedPointerIterator` 会通过 `ensureMsgf` 报警，但 Shipping 构建没有这层保护，会静默地产生未定义行为（迭代器指向已释放或移位后的内存）。安全做法是收集待删除的索引或用倒序删除。

- **误以为 TMap 的 FindOrAdd 返回的引用在任何操作后都有效**：引用仅在没有触发 rehash 的操作期间有效。一旦在取得引用后继续向 Map 插入元素，rehash 随时可能使引用悬空。正确模式：操作完成后立刻让引用出作用域，不要跨越可能改变 Map 大小的操作持有它。

- **用 TArray 做频繁随机删除**：`RemoveAt` 的 O(N) 移位在元素数量大时是性能杀手。如果不需要保序，用 `RemoveAtSwap`；如果需要稳定指针，用 `TSparseArray`（但要接受随机访问变慢）。

- **混淆 TArray 的 Num() 和 Max()**：`Num()` 是已有元素数，`Max()` 是已分配容量（包括 slack）。`Reserve(N)` 确保 `Max() >= N`，但不改变 `Num()`。`SetNum(N)` 才会改变 `Num()`，对于新增的元素调用默认构造器。

### 提示

- 测量 cycle 时，包括 `FPlatformTime::Cycles()` 的调用和打印，都可能干扰结果。建议把测量体放在一个大循环里，只取循环总耗时再除以次数。
- `TInlineAllocator` 的 micro-benchmark 结果受 CPU cache 状态影响很大。建议在每次测量前清空 cache（或者用足够大的"噪声数据"填充 L1，让两次测量处于相同的 warm/cold 状态）。
- 阅读 UE 源码里迭代器相关部分时，注意 `TARRAY_RANGED_FOR_CHECKS` 宏：在非 Shipping/Test 构建时为 1，开启 `TCheckedPointerIterator`；在 Shipping 中为 0，退化为裸指针迭代器。这是 UE 的调试辅助，不是 C++ 标准迭代器。

### 复盘问题

- **Q1：执行真正开始时刻？** `TArray::Add` 触发的重分配在 GameThread 的 calling context 里同步发生，没有延迟执行。本题不涉及 RenderThread。

- **Q2：生命周期拥有者？** 所有容器对象本题以栈变量或局部对象形式存在。`TArray` 持有 heap storage 的所有权，析构时调用 `DestructItems` + 释放内存。`TInlineAllocator` 的 inline 部分与对象共同析构（栈上对象直接消亡）。不涉及 UObject/GC。

- **Q3：涉及哪些 Named Thread？** 本题全部在 GameThread（或 TaskGraph worker，取决于你如何驱动代码）。不涉及 RenderThread/RHIThread。

- **Q4：涉及 UObject 时怎么对 GC 可见？** 本题不涉及 UObject。`TArray<int32>`、`TMap<FString, int32>` 都是纯 C++ 值类型，GC 不感知它们。如果容器存在于非 UObject 类里，整个对象用 `TSharedPtr` 或栈管理；如果存在于 UObject 成员里，必须加 `UPROPERTY`（模块 D 再讲）。

- **题目特异问题**：为什么 `RemoveAtSwap` 的常见替代不是就地 "swap with dummy element + shrink"，而是直接"覆盖 + 缩短 ArrayNum"？读 `Array.h:2185` 附近的实现，回答：覆盖用的是 `MoveOrCopy`，为什么需要正确处理 destructor，不能直接 memcpy？

## 练习 B2：FString / FStringView 三件套

### 目标

把 `FString` 与 `std::string` 的三大差异刻成直觉，搞清楚 `operator*` 和 `GetData()` 的使用边界，掌握 `FStringView` 作为非拥有视图的正确用法，以及 `FString::Printf` 的格式约定。通过 inspect 阅读 `FString` 内部 `TArray<TCHAR>` 的实现，理解宽字符编码在跨平台边界处的转换需求。

### 前置理解

- 你知道 `std::string` 内部存 `char`（通常 8-bit，UTF-8 或 Latin-1），而 UE 的 `TCHAR` 在 Windows 上是 `wchar_t`（16-bit，UTF-16LE），在 Linux/Mac 上是 4-byte `wchar_t`（UTF-32）。
- 你理解悬垂引用（dangling reference）的产生条件：一个临时对象的生命周期比持有其地址的指针短。
- 你已做完练习 B1，理解 `TArray` 重分配后指针失效的原因。

### 必做任务

1. **TCHAR 编码验证**

   打印 `sizeof(TCHAR)` 在当前平台的值。在 Windows 上应该是 2（`wchar_t` = UTF-16LE code unit）。

   创建 `FString Str = TEXT("Hello, 世界");`，打印 `Str.Len()`。观察：`Len()` 返回的是 `TCHAR` code unit 数量，不是 Unicode codepoint 数量（对于 BMP 内的字符，两者相等；对于 Surrogate Pair 字符，UTF-16 里一个 codepoint 占两个 code unit）。

   和 `std::wstring` 做类比：`FString` 内部本质上就是一个带 null terminator 的 `TArray<wchar_t>`（在 Windows 上）。这是第一条差异：**编码与单元大小**。

2. **GetData() vs operator* 的语义差异**

   场景一：
   ```cpp
   FString Str = TEXT("test");
   const TCHAR* PtrA = *Str;          // operator* — 保证非 null，空串返回 TEXT("")
   const TCHAR* PtrB = Str.GetData(); // GetData() — 返回内部指针，可能指向 null（若内部 TArray 为空）
   FString Empty;
   const TCHAR* PtrC = *Empty;        // 保证返回 TEXT("") 指针
   const TCHAR* PtrD = Empty.GetData(); // 可能返回 nullptr（内部 TArray 未分配时）
   ```

   打印 `PtrC == nullptr` 和 `PtrD == nullptr`，观察两者的差异。

   场景二：
   ```cpp
   const TCHAR* GetDangling()
   {
       FString Temp = TEXT("temporary");
       return *Temp;   // 错误：返回了栈上 Temp 内部 TArray 分配的堆块的指针
                       // Temp 析构后指针悬空
   }
   ```
   在注释里解释为什么这段代码是未定义行为，以及这和 `std::string::c_str()` 相同模式下犯的错完全一样，但在 UE 里更容易犯（UE 代码大量用函数返回 `FString` 并链式操作）。

3. **FString 没有 SSO（small string optimization）**

   `std::string` 在 GCC/Clang/MSVC 实现里通常有 SSO，短字符串（通常 15 个字节以内）不进行堆分配。

   验证 `FString` 没有 SSO：
   - 创建一个空 `FString`，`sizeof(FString)` 是多少？（应等于 `sizeof(TArray<TCHAR>)`，即 三个指针/大小的组合，没有额外的 inline 字符缓冲区）。
   - 创建 `FString Str = TEXT("hi")`，打印 `Str.GetData()` 地址，它应该指向堆上分配的内存，而不是对象内部。
   - 这是第二条差异：**没有 SSO，所有非空 FString 都在堆上分配**。

4. **FString::Printf 格式约定**

   `FString::Printf` 使用 `TCHAR*` 格式串，格式符与 C 的 `printf` 基本一致，但有两处重要区别：
   - 字符串参数用 `%s`，接受的是 `const TCHAR*`，不是 `const char*`。要打印 `FString`，必须用 `*MyString`（`operator*` 转换到 `const TCHAR*`），不能直接传 `FString` 对象。
   - 整数类型用 `%d`、`%lld` 等，和 C printf 一致。`int64` 建议用 `%lld` 或 `%" INT64_FMT "` 宏（`Core/Public/HAL/PlatformMisc.h` 里有 UE 专属 printf 格式宏）。

   练习：
   ```cpp
   FString Name = TEXT("Player");
   int32 Score = 9999;
   FString Msg = FString::Printf(TEXT("Name=%s, Score=%d"), *Name, Score);
   UE_LOG(LogTemp, Log, TEXT("%s"), *Msg);
   ```
   运行并确认输出正确。然后故意漏掉 `*Name`，直接传 `Name`，观察编译器警告或运行时输出（未定义行为，可能打印乱码）。

5. **FStringView 非拥有视图**

   `FStringView`（`Containers/StringView.h`）是对 `const TCHAR*` + length 的封装，不拥有内存，不做拷贝。

   ```cpp
   FString LongStr = TEXT("Hello World");
   FStringView View = LongStr;                 // 构造视图，零拷贝
   FStringView Sub  = View.Left(5);            // "Hello" 的视图，零拷贝
   bool bStarts = View.StartsWith(TEXT("Hello")); // 比较操作，不分配
   ```

   对比 `FString` 的 `Left(5)`（返回新 `FString`，有堆分配）和 `FStringView::Left(5)`（返回新的 `FStringView`，无分配）。

   重要限制：`FStringView` 的有效性完全依赖底层 `FString` 的生命周期。如果底层 `FString` 发生重分配（`Append` 触发内存增长）或析构，视图悬空。演示这个失效场景：取 `FStringView`，然后对底层 `FString` 调用 `Append` 使其重分配，再通过视图访问——结果是悬空读取。

### 进阶任务

- **阅读 FString 内部 TArray<TCHAR> 实现**：

- **性能对比：多次 FString 拼接 vs TStringBuilder**：

### 观察点

- **为什么 UE 选择 UTF-16 而不是 UTF-8 内部编码**？历史原因：UE 的 Windows 路径追求与 Win32 API（宽字符版本）的直接兼容，`wchar_t` 传给 Win32 API 无需转换。现代引擎新增了 `FUtf8String` 和 `UTF8CHAR` 用于需要 UTF-8 的场景（如网络协议、JSON），但 `FString` 本体未改变编码。

- **`TArray<TCHAR>` 的 null terminator 管理**：`FString` 保证内部 `Data` 的末尾始终有一个 `'\0'`（`Data.Num() == Len() + 1`）。这样 `operator*` 直接返回 `Data.GetData()` 就是合法的 C 字符串。但如果你直接操作内部 `Data`（不通过 `FString` 的公开 API），可能破坏这个不变式。

- **`FStringView` 的 length-range 视图语义**：不同于 C 的 null-terminated 字符串，`FStringView` 存 `(pointer, length)` 对，可以视图化一个更长字符串的子串（无需 null terminator 在子串末尾）。这意味着 `FStringView` 子视图操作不能直接传给接受 `const TCHAR*` 的 C 风格 API——需要先 `ToString()` 到 `FString`，或用 `TStringBuilder` 做缓冲。

- **FString 与 std::string 的第三条差异（API 安全性）**：`std::string::c_str()` 和 `std::string::data()`（C++11）都保证在字符串非空时返回有效指针；C++11 后 `data()` 也保证 null-terminated。但两者在空串时的行为一样（返回指向 null terminator 的指针，不是 nullptr）。FString 的 `GetData()` 在内部 `TArray` 未分配时返回 `nullptr`，与 `std::string` 的行为不同，这是历史遗留问题，也是 `operator*` 被引入的原因。

### 常见坑

- **`*FString` 返回值不能持久持有**：`operator*` 返回指向内部 `TArray` 数据区的 `const TCHAR*`。任何后续使 `FString` 重分配的操作（`Append`、`+=`、`Insert`、赋值等）都会使该指针失效。常见错误模式：`const TCHAR* Ptr = *SomeFunc(); DoSomethingThatMayModify(OutStr);`，此时 `Ptr` 已悬空。

- **误把 `FString` 返回值的 `operator*` 结果直接传给异步回调或储存**：
  ```cpp
  // 错误：临时 FString 析构后 Ptr 悬空
  const TCHAR* Ptr = *FString::Printf(TEXT("Hello %d"), Value);
  SomeCallback(Ptr);  // Ptr 已经是悬空指针
  ```
  正确做法：先把 `FString` 赋给有足够生命周期的变量，再取 `operator*`。

- **在需要 `const char*` 的地方直接传 `const TCHAR*`**：`TCHAR` 是 `wchar_t`（Windows），不是 `char`。两者不兼容。必须用 `TCHAR_TO_UTF8(*Str)` 或 `TCHAR_TO_ANSI(*Str)` 做转换，且转换结果只在当前作用域（`TCHAR_TO_UTF8` 是栈变量宏）有效。

- **`FString::Printf` 格式串里用 `%s` 传 `FString` 而非 `*FString`**：`printf` 的 `%s` 期望 `const TCHAR*`，传 `FString` 对象是未定义行为（对象布局不是以字符指针开头的）。UE 的 `CheckVAArgs` 工具链在某些平台/编译选项下可以检测这类错误，但不保证所有平台都能检测。

### 提示

- 读 `UnrealString.h.inl` 时，注意文件顶部的 `#define UE_STRING_CLASS FString` 等宏：这套模板化字符串 `.inl` 文件被多次 include 以生成不同的字符串类（`FString`、`FAnsiString`、`FUtf8String`），靠宏替换 class 名和 char 类型。这是 UE 里一种"手动模板特化"的代码复用方式，第一次看到可能困惑。
- `FStringView` 的头文件是 `Containers/StringView.h`，和 `FString` 不同文件。
- 做悬空指针演示时，在 Debug 构建下 UE 的 `ensure/check` 可能捕获部分越界访问，但悬空指针本身通常无法被运行时检测，是静默的未定义行为。用 AddressSanitizer（`-fsanitize=address`）可以检测。

### 复盘问题

- **Q1：执行真正开始时刻？** `FString::Printf` 是同步立即执行（在调用处的线程，通常是 GameThread 上），结果 FString 立即构造完成。本题不涉及延迟执行或 RenderThread。

- **Q2：生命周期拥有者？** `FString` 拥有内部 `TArray<TCHAR>` 的唯一所有权（值语义，move 可以转移）。`FStringView` 不拥有任何内存，生命周期完全依赖底层 `FString` 或 `const TCHAR*`。不涉及 UObject/GC。

- **Q3：涉及哪些 Named Thread？** 字符串操作通常在 GameThread 上，但 `FString` 本身不是线程安全的（并发写同一个 `FString` 对象无保护）。如果要在多线程里处理字符串，应该每个线程持有独立的 `FString`，或使用互斥锁。

- **Q4：涉及 UObject 时怎么对 GC 可见？** `FString` 本身不是 UObject，不需要 UPROPERTY。如果 `FString` 是某个 UObject 的成员，需要声明 `UPROPERTY` 让 UHT 生成序列化/反射代码，但这是为了序列化，不是为了 GC（GC 不追踪 FString 内容，只追踪 UObject 指针）。

- **题目特异问题**：`std::string_view`（C++17）和 `FStringView` 的语义差异是什么？`std::string_view` 在 C++ 标准里允许视图化 null-terminated 字符串（不含 null）或任意字节序列（不含 null）；`FStringView` 是否保证视图内容 null-terminated？（答：不保证。`FStringView` 存 pointer+length，子视图不在末尾插入 null。这是和 `operator*` 不兼容的根本原因。）

## 练习 B3：FName 与 FText

### 目标

彻底理解 `FName` 和 `FText` 存在的理由——两者都不是"更好的 FString"，而是在不同语义维度上对 FString 的补充：FName 是不可变的、大小写不敏感的、全局池化的标识符，适合"引用一个已知字符串"；FText 是可本地化的、惰性格式化的显示字符串，不适合逻辑比较。

### 前置理解

- 你已做完练习 B2，理解 FString 是堆上分配的宽字符数组。
- 你理解全局哈希表/字符串驻留（string interning）的概念：把字符串存入全局表，返回一个整数 ID，之后用 ID 比较而不是逐字符比较。
- 你理解"惰性求值"的概念（`01-心智模型.md` 的 §5 RDG = lazy graph 里有类比）：`FText::Format` 不是立即把格式化结果算出来，而是存下"格式化描述"，在真正需要显示字符串时才触发求值。

### 必做任务

1. **FName 池化验证**

2. **FName::ToString 成本观察**

   ```cpp

   // 方式一：直接比较 FName
   bool bEqual1 = (MyName == FName(TEXT("TestName"))); // 比较 FNameEntryId（整数比较，O(1)）

   // 方式二：ToString 后比较字符串
   bool bEqual2 = (MyName.ToString() == TEXT("TestName")); // ToString 触发池查找+FString构造
   ```

   用 `FPlatformTime::Cycles()` 在循环里对两种方式各做 1 000 000 次，测量耗时。预期结论：直接 FName 比较应该比 `ToString()` 快 1-2 个数量级。

   解释原因：`FName` 比较内部是 `GetComparisonIndex() == Rhs.GetComparisonIndex()`（`uint32` 比较），而 `ToString()` 要在 `FNamePool` 里找到对应的 `FNameEntry`，再把 `ANSICHAR` 或 `WIDECHAR` 内容复制构造成 `FString`。

3. **NAME_None 的特殊性**

   ```cpp
   FName None1;                     // 默认构造 == NAME_None
   FName None2(NAME_None);          // 显式构造 NAME_None
   FName None3(TEXT("None"));       // 字符串 "None" 也是 NAME_None

   UE_LOG(LogTemp, Log, TEXT("None1.IsNone(): %d"), None1.IsNone());
   UE_LOG(LogTemp, Log, TEXT("None2.IsNone(): %d"), None2.IsNone());
   UE_LOG(LogTemp, Log, TEXT("None3.IsNone(): %d"), None3.IsNone());
   UE_LOG(LogTemp, Log, TEXT("NAME_None ToString: %s"), *None1.ToString());
   ```

   观察：`FNameEntryId` 的默认构造值是 0（`IsNone() == true`）。NAME_None 是 FName 池中 ID 为 0 的特殊条目，类似于空指针在指针类型里的含义。注意 FName 不能用于存储空字符串——空字符串 `FName(TEXT(""))` 等同于 NAME_None。

4. **FText 惰性求值观察**

   ```cpp
   // 立即格式化（FString 路径）
   FString ImmediateResult = FString::Printf(TEXT("Player: %s, Score: %d"), TEXT("Alice"), 100);

   // 惰性格式化（FText 路径）
   FText PlayerText   = FText::FromString(TEXT("Alice"));
   FText ScoreText    = FText::AsNumber(100);
   FText FormatPat    = LOCTEXT("ScoreFmt", "Player: {0}, Score: {1}");
   FText LazyResult   = FText::Format(FormatPat, PlayerText, ScoreText);
   // LazyResult 此时持有 FTextHistory_OrderedFormat（格式 pattern + 参数列表）
   // 显示字符串还没有被计算出来

   // ToString() 触发实际求值（或在当前 culture 已缓存则直接返回缓存）
   FString DisplayStr = LazyResult.ToString();
   UE_LOG(LogTemp, Log, TEXT("%s"), *DisplayStr);
   ```

   通过在 `FText::Format` 和 `ToString()` 之间插入日志，验证两次调用之间没有字符串分配发生（在 Editor 里很难直接测量，但可以在 `FTextHistory_OrderedFormat::BuildDisplayString` 上打断点来确认"求值发生在 ToString 时"）。

5. **FText 不可用于比较逻辑**

   ```cpp
   FText TextA = FText::FromString(TEXT("Hello"));
   FText TextB = FText::FromString(TEXT("Hello"));

   // FText 没有 operator==（有意为之）
   // 以下代码不能编译：
   // if (TextA == TextB) { ... }

   // 正确做法：若必须比较，用 ToString() 比较（成本高），或根本不要用 FText 做逻辑
   bool bSame = TextA.ToString() == TextB.ToString();
   // 更好：如果你需要逻辑比较，用 FName 或 FString，不要用 FText
   ```

   记录结论：`FText` 没有 `operator==` 是设计决策，不是遗漏。本地化文字不适合作逻辑标识符——两个 FText 的显示字符串相同，不代表它们的"来源"相同（一个可能来自 LOCTEXT，另一个来自 FromString）。使用 `IdenticalTo(Other, ETextIdenticalModeFlags::...)` 可以做深度比较，但这是序列化层用的，不是业务逻辑比较用的。

6. **三种类型的用途分类**

   根据以上实验，填写下表（在代码注释或笔记里）：

   | 场景 | 用哪个 |
   |---|---|
   | 日志打印，需要格式化数字 | `FString::Printf` 或 `UE_LOG` |
   | 作为 TMap 的 key 做快速查找 | `FName` |

- **阅读 FNamePool 分片结构（源码 inspect）**：

### 观察点

- **FName 的 comparison vs display 双 ID 体系**（Editor 构建）：`GetComparisonIndex()` 用于 `operator==`，永远按全小写匹配；`GetDisplayIndex()` 用于 `ToString()`，返回原始大小写字符串。这套双 ID 体系只在 `WITH_CASE_PRESERVING_NAME`（即 `WITH_EDITORONLY_DATA`）时存在。这解释了为什么 `FName("Foo") == FName("FOO")`，但 `FName("Foo").ToString() != FName("FOO").ToString()`（在 Editor 构建中）。

- **FName 池的"永不回收"特性**：FName 一旦入池就不会被移除（即使所有引用它的 FName 实例都析构了）。这是为了保证 ID 的永久有效性。在长时间运行的 Editor 进程里，FName 池会随时间增长。这就是为什么不应该用随机生成的字符串作 FName（会持续膨胀池）。

- **FText 与反射系统的不兼容**：`FText` 没有 `operator==`，这意味着它不能直接参与 `UPROPERTY` 的 dirty 检测（序列化系统用 `IdenticalTo` 而非 `operator==`）。这是 `FText` 在蓝图/反射层有特殊处理逻辑的原因。不要把两个 FText 对象的 `ToString()` 结果用于业务逻辑判断——本地化文字的意思相同，字符串却可能因为 culture 不同而不同。

- **FText::AsNumber 的文化敏感性**：`FText::AsNumber(1234567.89)` 在英语 culture 下输出 `"1,234,567.89"`，在德语 culture 下输出 `"1.234.567,89"`（小数点和千位分隔符互换）。`FString::Printf(TEXT("%.2f"), 1234567.89)` 则永远输出 `"1234567.89"`（C locale）。这是两者的根本差异：FText 跟随 culture，FString::Printf 不跟随 culture。

- **`LOCTEXT` 和 `NSLOCTEXT` 宏**：`LOCTEXT("Key", "Default String")` 把 namespace+key+默认字符串注册到本地化系统，翻译文件里可以覆盖对应 key 的值。`NSLOCTEXT("Namespace", "Key", "Default String")` 显式指定 namespace。这些宏在编译时只是 `FText::AsLocalizable_Advanced_LocText(...)` 的调用，运行时查本地化表。`INVTEXT("Literal")` 是 CultureInvariant 字面量，不参与翻译。

### 常见坑

- **用 FName 存储动态/随机生成的字符串**：FName 池只增不减，如果你每帧用随机数生成 FName，池会无限增长，最终 OOM。FName 适合"有限的已知名称集合"，不适合"任意动态字符串"。

- **在非 Editor 构建里依赖 FName::ToString() 的大小写**：Runtime 构建（`!WITH_CASE_PRESERVING_NAME`）下，FName 只存一个全小写的 comparison ID，`ToString()` 返回的字符串全小写。如果你的代码依赖 `FName("MyComponent").ToString() == "MyComponent"`，在 Shipping 里会失败。

- **FText 用于日志打印或调试字符串**：FText 的 `ToString()` 涉及 culture 查询和 history 求值，成本高于 `FString::Printf`。在 `UE_LOG` 里频繁调用 FText 的 `ToString()` 是不必要的开销。调试日志用 FString，玩家可见文字用 FText。

- **FText 不参与反射比较**：`UPROPERTY` 标注的 `FText` 成员在序列化 dirty 检测时用 `FText::IdenticalTo`，而不是 `operator==`（FText 没有此运算符）。如果你手写序列化代码，错用字符串 `==` 比较两个 FText 的 `ToString()` 来判断是否修改，可能在 culture 切换后误判"未修改"。

- **混用 FName 和 FString 作为 TMap key**：两种 key 类型的比较语义不同。`TMap<FName, Value>` 是大小写不敏感 map，`TMap<FString, Value>` 是大小写敏感 map（`FString` 的 `operator==` 按字符逐一比较，区分大小写）。这在做属性名查找时容易踩坑。

### 提示

- UE 源码里 `FNamePool` 的实现在 `.cpp` 文件（`UnrealNames.cpp`），不对外暴露完整的类定义。你能在头文件里看到 `FNamePoolShardBase` 的 `friend` 声明（`NameTypes.h:368-369`），但详细实现要去 `.cpp` 里找。
- 测量 FName 比较 vs ToString 比较的性能差异时，注意把 FName 构造（入池查找）排除在计时范围外——只计时"对已有 FName 实例做比较"的部分。
- `LOCTEXT` 宏必须在带有 `#define LOCTEXT_NAMESPACE "YourNamespace"` 的文件里使用，末尾用 `#undef LOCTEXT_NAMESPACE` 关闭。忘记这两个宏会导致 UHT 解析失败或本地化命名空间污染。

### 复盘问题

- **Q1：执行真正开始时刻？** `FName` 的构造（入池）在调用处同步执行（可能涉及哈希查找和 lock 分配）。`FText::Format` 的调用是同步的，但它只构造 `FTextHistory` 对象，不进行字符串格式化。实际字符串格式化（`BuildDisplayString`）发生在 `FText::ToString()` 被调用时，也是同步的。不涉及 RenderThread。

- **Q2：生命周期拥有者？** `FName` 本身是值类型（内部只有 `FNameEntryId`，即 `uint32`），拷贝开销极低。池里的 `FNameEntry` 由全局 `FNamePool` 拥有，生命周期与进程相同（永不回收）。`FText` 内部有 `TSharedRef<ITextData>`，通过引用计数管理 `FTextHistory` 的生命周期；`FText::Format` 产生的 FText 在所有引用者析构后才释放 history 数据。不涉及 UObject/GC。

- **Q3：涉及哪些 Named Thread？** `FName` 的入池操作是线程安全的（shard 级别锁），可以在任意线程调用。`FText::Format`/`ToString()` 可以在任意线程调用，但本地化 table 查找有内部线程安全保障（`FTextLocalizationManager` 用读写锁）。不涉及 RenderThread/RHIThread。

- **Q4：涉及 UObject 时怎么对 GC 可见？** `FName` 和 `FText` 都是非 UObject 的值类型，GC 不追踪它们的内容。如果 `FName` 或 `FText` 存在于 UObject 的成员里，需要 `UPROPERTY` 标注以便 UHT 生成序列化代码，但这是为了序列化/反射，不是为了 GC 可达性（GC 不追踪 FName/FText 内部的任何指针，因为它们内部没有 UObject 指针）。

- **题目特异问题**：`FText::AsCultureInvariant(MyString)` 和 `FText::FromString(MyString)` 产生的 FText 有什么区别？（提示：查看 `ETextFlag::CultureInvariant` 和 `ETextFlag::InitializedFromString` 的差异，以及两者在序列化时的行为差异。）

## 做完本模块后你现在应该能说清楚什么

至少把下面几句话说顺：

- `TArray::RemoveAt` 保序但 O(N) 移位，`RemoveAtSwap` 破序但 O(1)。`Reserve` 之后的增加操作不触发重分配。从 `TArray` 取到的指针或引用在任何触发重分配的操作后失效。

- `FString` 内部是 `TArray<TCHAR>`（Windows 上 UTF-16LE），没有 SSO，所有非空字符串都在堆上。`operator*` 保证返回非 null 的 `const TCHAR*`（空串返回静态 `""`），`GetData()` 可能返回 nullptr（内部 TArray 未分配时）。`FString::Printf` 的 `%s` 需要传 `*FString`（`const TCHAR*`），不能传 `FString` 对象本身。

- `FName` 内部存的是全局池的 `FNameEntryId`（一个 `uint32` 偏移量），不是字符串本身。`operator==` 默认大小写不敏感（比较 ComparisonIndex），`ToString()` 涉及池查找+FString构造（有成本）。FName 一旦入池不可修改、不可移除（不可变、永久存在）。在 Editor 构建（`WITH_CASE_PRESERVING_NAME`）里保留原始大小写，Runtime 构建里只存小写——不要依赖 `ToString()` 的大小写。

- `FText` 持有 `FTextHistory`（描述"这段文字怎么来的"），`Format` 调用是惰性的（不立即产出字符串），`ToString()` 才触发求值。`FText` 没有 `operator==`（设计决策），不适合做逻辑比较，只适合显示给玩家看的文字。
