## 读法说明

### 建议阅读顺序

按依赖层次从底到顶：文件 1（Module 启动）→ 文件 2（UObject 基础）→ 文件 3（Actor/World 生态）→ 文件 4（资产异步流入）→ 文件 5（RDG 惰性图）→ 文件 6（场景渲染骨架）。

### 每文件"带问题入场"三步法

1. 先读头部注释和类声明，建立"这个文件负责什么"的最高层认知。
2. 用 Grep/Find 跳到核心函数入口，只读主干调用链，跳过错误处理分支。
3. 在函数体里找能对应到你自己某道练习的代码段，把行为差异写下来。

### 必答五问（每文件独立回答）

每个源码文件都必须回答以下五个问题：

- **Q1 执行真正开始时刻**：这段代码在引擎启动序列或帧序列的哪个时机点被调用？哪条线程？
- **Q2 生命周期拥有者**：核心对象由谁创建、由谁销毁？是 GC、FModuleManager、UWorld，还是 RDG Transient Pool？
- **Q3 涉及哪些 Named Thread**：调用链跨越了哪些 `ENamedThreads`？哪里有显式的线程切换点（`ENQUEUE_RENDER_COMMAND`、TaskGraph、IoDispatcher 线程）？
- **Q4 涉及 UObject 时 GC 可见性**：相关 `UObject*` 是通过 `UPROPERTY`、`TObjectPtr`、Outer 链，还是 `AddToRoot` 来保持 GC 可见的？
- **Q5 最像我哪个自写练习**：能对照到你哪道具体的练习（例：A1、D3、K3）？差异最大的一点是什么？

## 每文件必答详解

### 文件 1：`Runtime/Core/Private/Modules/ModuleManager.cpp`

**对应模块 A — 构建系统与模块生命周期**

**入口路径**：

```
FModuleManager::LoadModule(InModuleName)            // 行 908 — 公开 API
  → GetOrLoadModule(...)                             // 行 914 — 检查是否已加载，非 GameThread 则拒绝
    → LoadModuleWithFailureReason(...)               // 行 965 — 真正执行加载的函数
      → InitializeModule lambda                      // 行 1061 — 创建模块实例并调 StartupModule
          ModuleInfo->Module->StartupModule()        // 行 1087 — 你的 IModuleInterface 实现被调用
          ModuleInfo->bIsReady = true                // 行 1093 — 其他线程可见的就绪标志
          ModulesChangedEvent.Broadcast(...)         // 行 1096 — 广播模块加载完成事件
```

`IMPLEMENT_MODULE(MyClass, MyModule)` 宏展开行为因构建模式不同而分两路：

- **动态链接（模块化构建，默认）**：宏在 DLL 内定义一个静态 `FModuleInitializerEntry` 实例（`ModuleManager.cpp` 行 98 声明其链表头 `GFirstModuleInitializerEntry`）。`FModuleInitializerEntry` 构造函数把自身插入该双向链表，持有工厂函数指针 `Function`。`LoadModuleWithFailureReason`（行 1206）在 DLL 加载后通过 `FModuleInitializerEntry::FindModule` 遍历链表查找工厂，调用后得到 `IModuleInterface*` 实例。

- **单体链接（Monolithic/Merged 构建）**：宏改为定义 `FStaticallyLinkedModuleRegistrant<ModuleImplClass>` 全局对象，其构造函数调用 `FModuleManager::RegisterStaticallyLinkedModule`（行 2084），把工厂函数存入 `PendingStaticallyLinkedModuleInitializers`，随后由 `ProcessPendingStaticallyLinkedModuleInitializers`（行 1954）转移到 `StaticallyLinkedModuleInitializers`（`TMap<FName, FInitializeStaticallyLinkedModule>`）。`LoadModuleWithFailureReason` 在行 1113 先查此 map，找到后调用工厂，调 `StartupModule`。

**两者关系**：`GFirstModuleInitializerEntry` 链表与 `StaticallyLinkedModuleInitializers` map 是两套并存的注册路径，分别对应动态和静态/单体链接场景。两套路径最终都在 `LoadModuleWithFailureReason` 汇聚，产出 `IModuleInterface*` 实例后立即调用 `StartupModule`（行 1087）。

**Q1 执行真正开始时刻**：GameThread 上，引擎启动序列中由主程序或其他 Module 的 `StartupModule` 链式触发。`LoadModule` 函数有保护：非 GameThread 调用时（`!IsInGameThread()`）会返回空，不会执行真正加载（行 921）。

**Q2 生命周期拥有者**：`FModuleManager` 单例。模块实例保存在 `ModuleInfo->Module`（`TUniquePtr<IModuleInterface>`）中，`FModuleManager` 拥有其生命周期。`ShutdownModule` 在引擎退出时被调用，之后 `TUniquePtr` 析构释放实例。

**Q3 Named Thread**：整个加载链均在 **GameThread** 上执行。源码在行 921 处对非 GameThread 调用做了显式排斥。加载过程不涉及 RenderThread 或 RHIThread，但 `StartupModule` 内部可以向 RenderThread 投递命令（由模块自己决定）。

**Q4 GC 可见性**：`FModuleManager` 本身不是 `UObject`，模块实例（`IModuleInterface`）也不是 `UObject`，因此 GC 不参与管理。若模块在 `StartupModule` 中持有 `UObject*`，必须自行用 `AddToRoot` 或挂在合适 Outer 上保证 GC 可达。

**Q5 最像哪个练习**：练习 **A1**（Hello Module + `StartupModule`/`ShutdownModule` 日志观察）。差异在于 A1 里你写的是 Module 实现端，`ModuleManager.cpp` 展示的是 Module 管理端——链表注册、工厂查找、`TUniquePtr` 拥有实例、`bIsReady` 就绪标志——这些在你的练习代码里完全看不到，是引擎隐藏的另一侧。

### 文件 2：`Runtime/CoreUObject/Public/UObject/Object.h` + `Private/UObject/Obj.cpp`

**对应模块 D — UObject / 反射 / GC**

**UObject 构造链关键节点**：

`Object.h` 中声明了两个构造函数（行 102、109）：无参版本和接受 `FObjectInitializer` 的版本。`GENERATED_BODY()` 展开后注入的代码最终会调用 `FObjectInitializer` 路径来完成子对象的递归构造。

`CreateDefaultSubobject` 路径（`Obj.cpp` 行 191）：

```cpp
UObject* UObject::CreateDefaultSubobject(...)
{
    FObjectInitializer* CurrentInitializer = FUObjectThreadContext::Get().TopInitializer();
    return CurrentInitializer->CreateDefaultSubobject(...);
}
```

`CreateDefaultSubobject` 不是直接创建对象，而是从线程局部栈顶的 `FObjectInitializer` 借力。这意味着只能在构造函数中调用它（此时 `FObjectInitializer` 在栈上存在），在 `PostInitProperties` 或之后调用会崩溃。

**析构链（GC 侧）**：

```
ConditionalBeginDestroy()  → BeginDestroy()      // Object.h 行 1183、Obj.cpp 行 1071
  IsReadyForFinishDestroy()                       // Object.h 行 373（轮询，等待异步操作）
ConditionalFinishDestroy() → FinishDestroy()      // Object.h 行 1186、Obj.cpp 行 1101
  RF_FinishDestroyed 标志置位
UObject 内存由 GUObjectArray 管理并最终释放
```

**Q1 执行真正开始时刻**：`NewObject<T>()` / `SpawnActor<T>()` / CDO 构造（引擎初始化时）分别对应不同时刻，均在 **GameThread**。`BeginDestroy` 由 GC 在帧与帧之间（GameThread 空闲时）调用；`FinishDestroy` 在 `IsReadyForFinishDestroy` 返回 `true` 后由 GC 轮询触发。

**Q2 生命周期拥有者**：GC（`FUObjectArray` / `GUObjectArray`）。GC 从根集出发沿 `UPROPERTY` 指针递归标记可达对象；未标记者在 GC 运行时被 `BeginDestroy`/`FinishDestroy` 两步析构后回收内存。`Outer` 链是 GC 可达性的主要路径之一。

**Q3 Named Thread**：构造在 **GameThread**。`BeginDestroy` / `FinishDestroy` 亦在 **GameThread**（GC 在帧间的 GameThread 空闲窗口运行）。`PostLoad`（异步加载包时）可能在 **异步加载线程**（`IoDispatcher` 相关工作线程）触发，这是少数非 GameThread 的 UObject 操作。

**Q4 GC 可见性**：成员变量加 `UPROPERTY` 或用 `TObjectPtr<T>` 包装（UE5 推荐）；对象挂在正确的 Outer 链上；调用 `AddToRoot()` 强制加入根集。三种方式任选其一可保证 GC 不回收。

**Q5 最像哪个练习**：析构侧最像 **D4**（mini mark-sweep GC），`BeginDestroy`/`FinishDestroy` 两阶段对应你手写的"标记"和"清除"两步。`CreateDefaultSubobject` 的"构造时借 `FObjectInitializer` 栈"模式最像 **D2**（CreateDefaultSubobject 与构造阶段）。差异：官方实现有 `IsReadyForFinishDestroy` 异步轮询机制，mini 练习里你的 GC 是同步单步清除，没有"等待渲染资源释放"这一步。

### 文件 3：`Runtime/Engine/Private/Actor.cpp`（§9.1 新增）

**对应模块 K — Actor / Component / World / Subsystem**

**`UWorld::SpawnActor` 完整路径**（实现在 `LevelActor.cpp` + `Actor.cpp`）：

```
UWorld::SpawnActor(Class, Transform, SpawnParameters)   // LevelActor.cpp 行 455
  → NewObject<AActor>(...)                              // 用 Class 和 Outer(Level) 创建实例
  → Actor->PostSpawnInitialize(...)                     // Actor.cpp 行 4249
      DispatchOnComponentsCreated(this)                 // 触发所有默认 Component 的 OnComponentCreated
      RegisterAllComponents()                           // 注册 Component 到 World/Physics/Renderer
      PostActorCreated()
      FinishSpawning(UserSpawnTransform, ...)            // Actor.cpp 行 4347
        ExecuteConstruction(...)                        // 蓝图 SCS 执行，原生 C++ 用户构造脚本
        PostActorConstruction()                         // Actor.cpp 行 4403
          PreInitializeComponents()                     // 钩子 1
          InitializeComponents()
          PostInitializeComponents()                    // 钩子 2（Actor.cpp 行 6544）
          DispatchBeginPlay()                           // 钩子 3（若 World 已经 HasBegunPlay，Actor.cpp 行 4690）
```

**五钩子顺序**（从 `Actor.cpp` PostSpawnInitialize 注释段，行 4249 起）：

```
1. PreInitializeComponents()    — 所有 Component 注册完毕，尚未初始化
2. PostInitializeComponents()   — 所有 Component 初始化完毕（InitializeComponent 后，行 6544）
3. BeginPlay()                  — World 已开始 Play 且 Actor 已完整构建（行 4753）
4. Tick()                       — 每帧 GameThread
5. EndPlay(EEndPlayReason)       — Actor 销毁或 World 卸载（行 3232）
   → Destroyed()                — 销毁回调（行 3284）
   → BeginDestroy()             — GC 侧（并非钩子，但是拆解的起点）
```

`DispatchBeginPlay`（行 4690）在 `PostActorConstruction`（行 4403）内被条件触发：若 `World->HasBegunPlay()` 且满足调用条件，才立即调用 `BeginPlay`（行 4753）；否则等 World 统一广播 `BeginPlay`。

**Q1 执行真正开始时刻**：`UWorld::SpawnActor` 由业务代码在 **GameThread** 调用，整个链在 GameThread 上同步完成（除非指定了 `bDeferConstruction`）。`BeginPlay` 的调用时机依赖 `World->HasBegunPlay()`——如果 World 尚未进入 Play 状态（例如在 Editor 中放置 Actor），则延迟到 World 启动时统一调用。

**Q2 生命周期拥有者**：`UWorld`（通过 `ULevel` 持有 Actor 列表）。Actor 是 `UObject`，GC 通过 `UWorld → ULevel → TArray<AActor*> Actors`（`UPROPERTY`）这条链路维持 GC 可达性。`AActor::Destroy()` 调用后 Actor 被标记为 `PendingKill`，在下一次 GC 中被回收。

**Q3 Named Thread**：整个生命周期（`SpawnActor` → `BeginPlay` → `Tick` → `EndPlay`）均在 **GameThread**。若 Actor 有渲染代理（`FPrimitiveSceneProxy`），`RegisterAllComponents` 会向 **RenderThread** 投递命令更新 `FScene`，但 Actor 自身逻辑始终留在 GameThread。

**Q4 GC 可见性**：Actor 的 `UActorComponent*` 成员均带 `UPROPERTY`（或 `TObjectPtr<UActorComponent>`）。`OwnedComponents`（`TSet<UActorComponent*>`，带 `UPROPERTY`）是 GC 可达性的主链路。Actor 自身以 `UWorld → ULevel → Actors` 链路可达，无需 `AddToRoot`。

**Q5 最像哪个练习**：最像 **K1**（Hello AActor + 五钩子日志观察）和 **K3**（UWorld/ULevel/UGameInstance 三层关系 + `SpawnActor` 路径阅读）。差异：K1/K3 你观察的是钩子被调用的顺序和日志输出，`Actor.cpp` 展示了条件控制逻辑——`bDeferConstruction`、碰撞检测分支、`bDeferBeginPlayAndUpdateOverlaps`——这些边界条件在练习里感知不到，真实引擎里却是钩子可能不被调用的原因。

### 文件 4：`Runtime/CoreUObject/Private/Serialization/AsyncLoading2.cpp`

**对应模块 E — 资产与加载**

**路径说明**：大纲原列路径（`Engine/Private/Streaming/`）不正确。`AsyncLoading2.cpp` 属于 `CoreUObject` 模块，实现的是基于 `IoDispatcher` 的新一代异步包加载系统（"Zen Loader" / Zenith）。旧的 `AsyncLoading.cpp`（同目录）是基于 `FLinkerLoad` 的经典路径，两者并存，由 `UE_ASYNCLOADING2` 编译开关控制。

**核心类层次**：

```
FAsyncLoadingThread2            // 行 4147 — 整个异步加载系统的主控对象
  FAsyncPackage2                // 行 3559 — 一个 "正在加载中的包" 的状态机
    FEventLoadNode2             // 行 2990 — 加载图中的一个节点（有 barrier 计数）
  FGlobalImportStore            // 行 1651 — 已导入对象的全局缓存
  IoDispatcher（外部）          // 底层 I/O 线程，异步读取包数据
```

**入口调用链**：

```
LoadPackageAsync(PackagePath, Delegate, ...)            // 公开 API（UObjectGlobals.cpp）
  → FAsyncLoadingThread2::LoadPackageInternal(...)      // 声明：行 4504；实现：行 11541 — 创建 FPackageRequest
    → FAsyncLoadingThread2::QueueUnresolvedPackage(...)
      或 FindOrInsertPackage(...)                        // 行 4462 — 在 ALT 线程创建 FAsyncPackage2
        FAsyncPackage2 进入事件驱动加载图
          IoDispatcher 异步读包数据
          反序列化 Exports → 创建 UObject 实例
          PostLoad 回调（可在加载线程或 GameThread）
          CompletionCallback 在 GameThread 端触发
```

`FAsyncLoadingThread2` 有自己的专属后台线程（ALT，Async Loading Thread），与 GameThread 分离。GameThread 通过 `TickAsyncLoadingFromGameThread`（声明：行 4482；实现：行 10157）在帧末轮询，把已完成的包 `PostLoad` 回调派发到 GameThread。

**Q1 执行真正开始时刻**：`LoadPackageAsync` 在 **GameThread** 上调用，立即返回（非阻塞）。实际加载由 **ALT**（AsyncLoadingThread）驱动，I/O 读取由 **IoDispatcher 线程**完成。`PostLoad` 根据 `IsPostLoadThreadSafe()` 结果决定在 ALT 还是 GameThread 执行。

**Q2 生命周期拥有者**：加载完成的 `UPackage`（及其 Export UObject）由 GC 管理，通过 `RF_RootSet` 或 Outer 链保持可达。加载过程中的中间状态（`FAsyncPackage2` 等辅助结构）由 `FAsyncLoadingThread2` 管理，加载完成后释放。

**Q3 Named Thread**：`LoadPackageAsync` 调用在 **GameThread**；实际加载在 **ALT**（专用后台线程，不是 TaskGraph worker）；I/O 在 **IoDispatcher 线程**；`PostLoad`/`CompletionCallback` 回调在 **GameThread**（通过 `ProcessLoadedPackagesFromGameThread`，声明：行 4826；实现：行 9897，在帧末由 GameThread 触发）。

**Q4 GC 可见性**：`FAsyncPackage2` 内部通过 `FPackageReferencer`（行 722 附近）持有对目标 `UPackage` 的引用，确保加载期间 GC 不回收正在构建的对象。加载完成后，`UPackage` 本身通过 `GUObjectArray` 中的对象注册表可达；调用方若用 `FStreamableHandle` / `TSoftObjectPtr` 则通过 `FStreamableManager` 持有引用。

**Q5 最像哪个练习**：最像 **E3**（`FStreamableManager` 异步加载）。差异：E3 你使用的是 `FStreamableManager::RequestAsyncLoad`，它在内部最终调用到 `LoadPackageAsync`，然后进入 `AsyncLoading2` 的事件驱动图。`AsyncLoading2.cpp` 展示的是这个调用链的最底层实现——IoDispatcher 驱动的事件节点状态机，完全不同于 E3 里你看到的面向用户的 Handle/回调 API。

### 文件 5：`Runtime/RenderCore/Public/RenderGraphBuilder.h` + `Private/RenderGraphBuilder.cpp`

**对应模块 H — RenderGraph 与场景渲染**

**三阶段架构**（与 stdexec 类比的核心）：

```
描述期（AddPass 调用时）：
  FRDGBuilder::AddPass(Name, ParameterStruct, Flags, ExecuteLambda)
    → AddPassInternal(...)
      Pass 节点加入 Passes 数组
      资源引用计数更新
      执行 Lambda 不被调用（仅存储）

编译期（Execute 内部）：
  FRDGBuilder::Compile()                   // RenderGraphBuilder.cpp 行 1316
    Pass 依赖分析（SetupPassDependencies）
    Pass Culling（深度优先搜索，行 1380 附近）
    Barrier 计算（CompilePassBarriers，行 3750 附近）
    资源生命周期分析（transient 起止 pass）

执行期（Execute 末段）：
  FRDGBuilder::Execute()                   // RenderGraphBuilder.cpp 行 1755
    WaitForParallelSetupTasks(...)         // 等待 AddSetupTask 异步任务完成
    Compile()                              // 行 1895 区域
    AllocateTransientResources(...)        // 行 1986 — 为 transient 资源分配显存
    ExecutePasses(...)                     // 行 2036 — 逐 pass 录制 RHI 命令
      ExecutePass → ExecutePassPrologue → 调用 pass Lambda → ExecutePassEpilogue
    BeginFlushResourcesRHI()              // 推送命令到 RHIThread
```

`FRDGTextureRef` / `FRDGBufferRef` 是描述期的句柄，不持有真实 GPU 资源。`Execute()` 中 `AllocateTransientResources` 才真正从 Transient Resource System 分配显存，`pass lambda` 执行时才拿到真实的 `FRHITexture*`。

**Q1 执行真正开始时刻**：`FRDGBuilder::Execute()` 在 **RenderThread** 上调用，由 `FSceneRenderer::Render` 或类似的渲染函数触发。`AddPass` 调用时 pass lambda 不执行；`Execute` 调用时整个图的 Compile + 资源分配 + pass 录制才真正开始。

**Q2 生命周期拥有者**：`FRDGBuilder` 本身是栈上对象（header 注释明确要求"created on the stack"，`RenderGraphBuilder.h` 行 44 注释）。Transient 资源由 `GRDGTransientResourceAllocator` 管理，pass 结束后由 epilogue pass 自动释放。`FRDGBuilder` 析构时若未调用 `Execute`，会触发断言。

**Q3 Named Thread**：`AddPass` 和 `Execute` 均在 **RenderThread**。`Execute` 内部的 `WaitForParallelSetupTasks`（行 1800 区域）等待通过 `AddSetupTask` 投递到 **TaskGraph worker pool** 的并行编译任务。最终 GPU 命令通过 `FRHICommandList` 提交到 **RHIThread**。

**Q4 GC 可见性**：RDG 中不涉及 `UObject`（资源句柄是 `FRDGTextureRef` 等非 UObject 类型）。若某个 pass 需要访问 `UTexture2D` 的底层数据，需在 GameThread 侧先读取好数据或 `FRHITexture*`（在 RenderThread 安全的访问路径），不能在 pass lambda 里持有 `UObject*`（GC 与 RenderThread 不同步）。

**Q5 最像哪个练习**：最像 **H3**（手写 RDG Pass + `FRDGBuilder::AddPass` 使用）和 **H1**（RDG 惰性图与 stdexec 类比）。差异：H3 练习里你写的是一个 pass 的参数结构和 lambda，`RenderGraphBuilder.cpp` 的 `Execute` 内部展示了图级别的操作——全图 Culling、barrier 自动插入、transient 资源生命周期计算——这些是 RDG 比传统 `FRHICommandList` 多出的核心价值，单个 pass 练习感知不到。

`FScene`（渲染侧的场景表示）在 `UWorld::Scene` 字段持有，是 `IRendererInterface*` 的实现。GameThread 修改 Scene 数据时通过 `ENQUEUE_RENDER_COMMAND` 把指令投递到 RenderThread；RenderThread 的 `FSceneRenderer::Render` 读取这些已同步的数据构建 RDG 图。

`FPrimitiveSceneProxy` 是每个可渲染 Actor Component 在 RenderThread 侧的镜像对象，由 `FPrimitiveSceneInfo` 包裹注册到 `FScene`。这就是心智模型中"双对象镜像"的实现：GameThread 的 `UPrimitiveComponent` ↔ RenderThread 的 `FPrimitiveSceneProxy`。

**Q1 执行真正开始时刻**：`BeginRenderingViewFamilies` 在 **GameThread** 的帧末（`UGameViewportClient::Draw` 调用时）执行。`ENQUEUE_RENDER_COMMAND` 将实际渲染工作（`SceneRenderer->Render`）投递到 **RenderThread**，通常滞后 GameThread 约一帧执行。

**Q2 生命周期拥有者**：`FScene` 由 `UWorld` 拥有（通过 `UWorld::Scene`，非 `UObject` 字段，生命周期与 `UWorld` 绑定）。`FSceneRenderer` 在 `ENQUEUE_RENDER_COMMAND` 的 lambda 值捕获中被创建，由 RenderThread 在完成后销毁（`delete SceneRenderer`）。`FPrimitiveSceneProxy` 由 `FScene` 的数组持有，在 `UPrimitiveComponent` 取消注册时被删除。

**Q3 Named Thread**：`BeginRenderingViewFamilies` 的前半段（`SendAllEndOfFrameUpdates`、帧号递增）在 **GameThread**；`ENQUEUE_RENDER_COMMAND` 之后的所有渲染工作（`Render` → `FRDGBuilder::AddPass` → `FRDGBuilder::Execute`）在 **RenderThread**；`FRDGBuilder::Execute` 末段把 RHI 命令推送到 **RHIThread**。这是 UE 三线程模型最完整的一条调用路径。

**Q4 GC 可见性**：`FScene`、`FSceneRenderer`、`FPrimitiveSceneProxy` 均是纯 C++ 对象（非 `UObject`），GC 不参与管理。渲染侧用智能指针（`TSharedPtr`）和手动生命周期（`delete`）管理这些对象。连接 GameThread UObject 与 RenderThread 的桥梁是 `ENQUEUE_RENDER_COMMAND` 的值捕获——复制 `FLinearColor`、`FMatrix` 等 POD 数据，不传 `UObject*`。

**Q5 最像哪个练习**：最像 **H2**（FScene 双对象镜像）和 **F4**（`ENQUEUE_RENDER_COMMAND` 值捕获实验）。差异：H2 练习里你观察 `FPrimitiveSceneProxy` 的创建时机，`SceneRendering.cpp` 展示的是"消费侧"——`FSceneRenderer::Render` 如何把 `FScene` 里的所有 Proxy 数据组装成 RDG 图。这是 Proxy 存在的目的，练习里只看到了创建，这里才看到了使用。

## 交付物 3：一页笔记

### 我现在如何向别人解释 UE 引擎内核的骨架

UE 引擎内核由四层正交机制叠加构成，每层解决一个独立问题，合起来支撑整个引擎运行。

**第一层：Module 组织。** 引擎所有代码被切分为独立的 Module（每个有 `.Build.cs` 声明依赖和 `LoadingPhase`）。`IMPLEMENT_MODULE` 宏把工厂函数注册进全局链表，`FModuleManager::LoadModule` 在 GameThread 按需加载、调 `StartupModule`、用 `TUniquePtr` 持有实例。Module 不是文件，而是有生命周期的可加载单元。Plugin 是 Module 的上一层容器（一个 `.uplugin` 包含多个 Module），但加载机制相同。

**第二层：UObject 反射与 GC。** UHT 在 C++ 编译器之前扫描带 `UCLASS`/`UPROPERTY`/`UFUNCTION` 的头文件，生成 `.generated.h` 注入反射元数据。`NewObject<T>()` 在 `FUObjectArray` 注册对象，GC 用标记-清除从根集（`RF_RootSet` + `AddToRoot` 对象）沿 `UPROPERTY` 指针链遍历，未可达对象经 `BeginDestroy` → `IsReadyForFinishDestroy` → `FinishDestroy` 两阶段回收。`TObjectPtr<T>` 在 Editor 构建时追踪不安全访问，Shipping 构建退化为裸指针。UObject 子类生态（`AActor`/`UActorComponent`/`UWorldSubsystem`）建立在此层之上，`SpawnActor` 链调用 `PreInitializeComponents` → `PostInitializeComponents` → `BeginPlay` 五钩子顺序固定。

**第三层：三线程分线。** GameThread 跑所有 Actor/Component 逻辑；RenderThread 构建并执行 RDG 图、维护 `FScene` 与 `FPrimitiveSceneProxy`；RHIThread 提交 GPU 命令。跨线程通信的唯一安全路径是 `ENQUEUE_RENDER_COMMAND`——值捕获（不能捕获 `UObject*` 引用），lambda 在 RenderThread 排到时执行。`BeginRenderingViewFamilies` 是 GameThread 帧末向 RenderThread 投递渲染工作的入口。异步加载有第四条路径：`FAsyncLoadingThread2` 专用后台线程 + IoDispatcher I/O 线程，完成后回调回 GameThread。

**第四层：RDG 延迟图 + Subsystem 层级单例。** `FRDGBuilder::AddPass` 只描述工作，`Execute()` 才触发 Compile（全图依赖分析 + Culling + barrier 计算）和资源分配（Transient 显存在 pass 首次写入时分配、最后读取后回收），最后录制 RHI 命令。这与 stdexec 的 sender 惰性、`start` 触发执行的结构同构。Subsystem 则解决"谁来管全局唯一对象的生命周期"问题：`UEngineSubsystem` 绑 `GEngine`、`UGameInstanceSubsystem` 绑 `UGameInstance`、`UWorldSubsystem` 绑 `UWorld`，由框架反射发现并自动 `Initialize`/`Deinitialize`，避免裸全局单例在 PIE 多次开启时的悬空引用。

这四层各司其职：Module 组织代码加载顺序；UObject + GC 管理可反射对象的生命周期；三线程分线分离逻辑/渲染/GPU 提交；RDG 延迟图和 Subsystem 体系分别是渲染和业务逻辑里的"描述后执行"模式的两个具体化。理解了这四层，任意一段 UE 源码都能找到它归属哪一层、与哪些边界发生交互。

**常见坑**：

- 看到 `AsyncLoading2.cpp` 里的 `FAsyncPackage2` 不要和旧版的 `FAsyncPackage`（`AsyncLoading.cpp`）混淆；两套系统并存，但现代 UE 5.x 默认走 AsyncLoading2 路径。
