# 02 模块 A：构建系统与模块生命周期

## 模块目标

反向引用 `01-心智模型` 的 §1 **Module-first，不是 File-first**。

在 UE 工程里，C++ 代码不能凭借"文件存在"就被引擎感知——它必须先归属某个 Module，该 Module 必须有 `.Build.cs` 声明依赖，必须有实现了 `IModuleInterface` 的入口类，必须用 `IMPLEMENT_MODULE` 宏注册到 UBT 生成的静态初始化链表，引擎在对应的 `ELoadingPhase` 才会调用其 `StartupModule()`。这个从"源文件"到"可被引擎加载的代码"的完整路径，是 UE 工程里与纯 C++ 经验差距最大的第一道墙。

本模块只做一件事：把这条路径从头到尾走一遍，走到你能闭眼复述它的程度。

**阶梯定位**：use + inspect。A1 做到 use（写出来、跑起来），A2/A3 做到 inspect（读懂 UBT/UHT 在背后做了什么）。

**Editor-only 统一约束**：全部三道练习均在 Editor 下运行，不涉及 Cook/Shipping。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- **C++ 代码如何变成可被 UE 加载的 Module**：`.Build.cs`（UBT C# 脚本）声明依赖 → `IMPLEMENT_MODULE` 宏把入口函数插入静态链表 `GFirstModuleInitializerEntry` → 引擎启动时 `FModuleManager::LoadModuleWithFailureReason` 调用 `ModuleInfo->Module->StartupModule()` 完成初始化。
- **LoadingPhase 各阶段差异**：`EarliestPossible`（pak 文件可读之后立刻）、`PostConfigInit`（配置文件读完后）、`Default`（引擎 init 主阶段，绝大多数 Module 在此）、`PostEngineInit`（引擎完全初始化后）；在 `Default` 之前 UObject 系统尚未完全就绪。
- **跨 Module 依赖与循环依赖打破**：`PublicDependencyModuleNames` vs `PrivateDependencyModuleNames` 的可见性语义差异；循环依赖用 interface class + 运行时动态加载（`FModuleManager::Get().LoadModuleChecked`）解耦。
- **UBT / UHT / `.Build.cs` 三件套角色**：UBT 读取 `.Build.cs` 生成 Makefile/解析依赖图；UHT 在 C++ 编译前跑生成 `.generated.h`；`.Build.cs` 是模块的"自述文件"，不是构建脚本全部。
- **Plugin vs Module 层级差异**：Plugin 是 Module 的容器；`.uplugin` 的 `Modules` 数组声明每个 Module 的 `LoadingPhase`；`IPluginManager::LoadModulesForEnabledPlugins()` 在引擎启动各阶段逐一触发。

## 练习 A1：Hello Module

### 目标

写出 UE 里最小可加载的 Module——不含任何 `UCLASS`，不含 UHT，只有三件事：`.Build.cs`、`IModuleInterface` 的两个虚函数、`IMPLEMENT_MODULE` 宏。跑起来之后，在引擎启动日志里找到 `StartupModule` 的打印，验证 Module 确实被加载了。

进阶部分：拆分 `Public/` 与 `Private/` 目录，感受 UBT 的 include path 管理；切换 `PCHUsage` 观察编译行为变化。

### 前置理解

- **UBT 的角色**：UnrealBuildTool 是一个 C# 程序，读取项目中所有的 `.Build.cs` 和 `.Target.cs` 文件，解析模块依赖图，生成平台相关的编译指令。它不是 Make/CMake 的包装，而是 UE 自己的构建系统前端。
- **`IMPLEMENT_MODULE` 宏的作用**：这个宏展开后会声明一个静态的 `FModuleInitializerEntry` 对象，其构造函数在静态初始化阶段把自己插入以 `GFirstModuleInitializerEntry` 为头节点的链表（见 `ModuleManager.cpp:100-119`）。引擎启动后，`FModuleManager` 遍历这个链表找到对应的模块入口函数，随后调用 `StartupModule()`。
- **`Public/` vs `Private/` 的语义**：放在 `Public/` 目录下的头文件，其路径会被加入依赖方的 include search path；`Private/` 下的头文件只对本 Module 可见。这是 UBT 在 include path 层面做的强制封装。
- **Editor-only 练习的 `bEditor` 约束**：在 `C15_Unreal_Engine.uproject` 里注册本 Module 时，`Type` 填 `"Editor"` 或在 `.Build.cs` 里通过 `Target.bBuildEditor` 判断，确保只在 Editor 构建中编译，避免 Shipping 路径的复杂性。

### 必做任务

1. 在 `exercises/A1_HelloModule/` 目录下新建以下文件结构：
   ```
   A1_HelloModule/
     A1_HelloModule.Build.cs
     Private/
       A1_HelloModule.cpp
     Public/
       (暂时为空)
   ```

2. 写 `A1_HelloModule.Build.cs`：继承 `ModuleRules`，在构造函数里至少声明 `PublicDependencyModuleNames.Add("Core")`。这是最小的合法 `.Build.cs`——没有 `Core` 依赖，连 `UE_LOG` 都用不了。

3. 写 `A1_HelloModule.cpp`：
   ```cpp
   #include "Modules/ModuleManager.h"

   class FA1HelloModule : public IModuleInterface
   {
   public:
       virtual void StartupModule() override
       {
           UE_LOG(LogTemp, Log, TEXT("[A1] StartupModule called"));
       }
       virtual void ShutdownModule() override
       {
           UE_LOG(LogTemp, Log, TEXT("[A1] ShutdownModule called"));
       }
   };

   IMPLEMENT_MODULE(FA1HelloModule, A1_HelloModule)
   ```

4. 在 `C15_Unreal_Engine.uproject` 的 `Modules` 数组中追加本 Module 的注册项（`Name`、`Type`、`LoadingPhase`）。

5. 用 UBT 重新生成项目文件（`GenerateProjectFiles`），在 IDE 中编译，确认无错误。

6. 启动 Editor，在输出日志（`Window > Output Log` 或 `Saved/Logs/*.log`）里搜索 `[A1] StartupModule`，记录它出现的时机（在哪些日志条目之前/之后）。

7. 记录观察：这条日志在 `GIsEditor = true` 设定之后出现，还是之前？在第一个 UObject 的 CDO 创建日志之前还是之后？（用 `LogInit` 或 `LogUObjectBase` 过滤辅助判断。）

### 进阶任务

- **Public/Private 拆分**：在 `Public/` 下新建 `IA1Service.h`，声明一个纯接口：
  ```cpp
  class IA1Service
  {
  public:
      virtual ~IA1Service() = default;
      virtual void DoWork() = 0;
  };
  ```
  在 `Private/` 下新建 `A1ServiceImpl.h`（实现类头文件）和 `A1ServiceImpl.cpp`（实现）。从另一个 Module（例如 `C15_Unreal_EngineCore`）试着 `#include "IA1Service.h"`（`Public/` 下，可以）和 `#include "A1ServiceImpl.h"`（`Private/` 下，UBT 应该报 include path 找不到）。观察两种 include 的编译结果差异。

- **PCHUsage 切换**：在 `.Build.cs` 里添加 `PCHUsage = ModuleRules.PCHUsageMode.UseExplicitOrSharedPCHs;`（UE5 推荐值），与默认值 `UseSharedPCHs` 对比，观察首次增量编译的文件数量变化。`UseExplicitOrSharedPCHs` 要求每个 `.cpp` 文件显式 `#include "CoreMinimal.h"` 或其他 PCH 源头，减少隐式 PCH 传播带来的不必要重编。

- **`WITH_EDITOR` 守卫观察**（UE 特有点）：在 `StartupModule()` 里加一段：
  ```cpp
  #if WITH_EDITOR
      UE_LOG(LogTemp, Log, TEXT("[A1] Running in Editor build"));
  #endif
  ```
  在 Editor 构建中观察这条日志是否打印；想想如果这段代码用于 Shipping 包会发生什么（该宏展开为 `0`，代码不编译）。这是 `README.md` §"UE 特有破坏纯模板剥皮点" 第 3 条"Editor-only 守卫"的第一次实际触碰。

- **`SupportsDynamicReloading()` 观察**：在 `FA1HelloModule` 中重写 `SupportsDynamicReloading()` 返回 `false`，尝试在 Editor 内热重载（Live Coding），观察 `FModuleManager::UnloadModule` 的行为变化（应该拒绝卸载）。

### 验收点

- `[A1] StartupModule called` 日志在 Editor 启动时出现，且只出现一次。
- `[A1] ShutdownModule called` 在 Editor 关闭时出现。
- 能正确说出 `IMPLEMENT_MODULE(FA1HelloModule, A1_HelloModule)` 中第二个参数（Module 名字符串）的含义：它必须与 `.Build.cs` 文件名（去掉扩展名）完全一致，且与 `.uproject` `Modules` 数组里的 `Name` 字段一致，三者构成一个命名三元组。
- 能从 `Private/` 的 cpp 文件里引用 `Public/` 的头文件，但无法从外部 Module 引用 `Private/` 的头文件（UBT include path 限制）。

### 观察点

- **`IMPLEMENT_MODULE` 不是魔法**，它只是在静态初始化阶段往 `GFirstModuleInitializerEntry` 链表里插了一个节点（`ModuleManager.cpp:100-119`）。引擎启动后 `FModuleManager::LoadModuleWithFailureReason`（`ModuleManager.cpp:965`）会查找这个链表，找到入口函数，调用它，再调用 `StartupModule()`（`ModuleManager.cpp:1087`）。整个流程是纯 C++ 静态初始化 + 单例模式的组合，和"插件机制"没有任何神秘之处。
- **`StartupModule` 调用时机**：从日志观察，`Default` phase 的 `StartupModule` 在 `FEngineLoop::Init()` 主干里被触发，此时配置文件已读完，但渲染线程尚未完全启动。这个顺序在 A2 会系统化地探索。
- **UBT 不是 Makefile 包装**：`Core.Build.cs`（`Engine/Source/Runtime/Core/Core.Build.cs:7`）里用的是 C# 的 `if / foreach`，可以根据平台、构建类型动态增减依赖。这是 UE 构建系统和 CMake 的本质区别——`.Build.cs` 是真正可执行的 C# 脚本，不是声明式配置。

### 常见坑

- **`IMPLEMENT_MODULE` 第二个参数拼写错误**：如果 `IMPLEMENT_MODULE(FA1HelloModule, A1HelloModule)`（漏掉下划线），而 `.uproject` 里的 `Name` 是 `"A1_HelloModule"`，引擎找不到初始化函数，报 `FileNotFound` 错误，难以定位。规则：Module 名字符串在 `.Build.cs` 文件名、`IMPLEMENT_MODULE` 第二参数、`.uproject Modules[].Name` 三处必须完全一致。
- **忘记在 `.uproject` 注册**：Module 文件编译通过，但引擎不知道要加载它，`StartupModule` 永远不会被调用。检查方法：`FModuleManager::Get().IsModuleLoaded(TEXT("A1_HelloModule"))` 返回 `true` 才算真正加载。
- **`WITH_EDITOR` 守卫漏写**（UE 特有点）：如果在 `StartupModule` 里调用了 Editor-only API（比如 `FEditorDelegates::XXX`），但没有 `#if WITH_EDITOR` 守卫，Shipping 构建会链接失败或产生未定义符号。本套练习虽统一 Editor-only，但养成守卫习惯在此题开始。
- **`.Build.cs` 写在错误目录**：`.Build.cs` 必须和 Module 的 `Public/` / `Private/` 目录处于同一层级（即 Module 根目录）。放到子目录下 UBT 找不到。

### 提示

- `Core.Build.cs`（`Engine/Source/Runtime/Core/Core.Build.cs`）是研究"真实 `.Build.cs` 长什么样"的最佳样本，它包含了 `PublicDependencyModuleNames`、`PrivateDependencyModuleNames`、平台条件分支等所有常见写法。
- 如果编译失败且错误信息含 `cannot open include file`，优先检查 `.Build.cs` 的依赖声明是否覆盖了 include 的 Module。
- `UE_LOG(LogTemp, ...)` 不需要额外的 `DEFINE_LOG_CATEGORY`，是快速调试的最简单方式。正式 Module 建议自己 `DEFINE_LOG_CATEGORY_STATIC(LogA1, Log, All)`。

### 复盘问题

- **Q1 执行真正开始时刻**：`StartupModule()` 在 `FModuleManager::LoadModuleWithFailureReason`（`ModuleManager.cpp:1087`）中被调用，时机取决于 Module 的 `LoadingPhase`。对于 `Default` phase，这发生在 `FEngineLoop::Init()` 的主阶段，在 GameThread 上同步执行。
- **Q2 生命周期拥有者**：Module 实例（`IModuleInterface` 子类）由 `FModuleManager` 持有，存储在 `TUniquePtr<IModuleInterface>` 中（`ModuleManager.cpp:1066` — `ModuleInfo->Module = TUniquePtr<IModuleInterface>(...)`）。`FModuleManager` 本身是静态单例（`UE::Core::Private::GetModuleManagerSingleton()`，`ModuleManager.cpp:186-191`），在引擎关闭时通过 `TearDown()` 销毁。
- **Q3 涉及哪些 Named Thread**：`StartupModule` 和 `ShutdownModule` 均在 **GameThread** 上同步调用（`ModuleManager.cpp:159` 里 `WarnIfItWasntSafeToLoadHere` 检查 `IsInGameThread()`）。Module 加载是引擎主线程的单线程操作，不涉及 RenderThread 或 RHIThread。
- **Q4 涉及 UObject 时怎么对 GC 可见**：A1 不涉及 UObject（Module 实例本身不是 `UObject`，由 `TUniquePtr` 管理，与 GC 无关）。这是本题的刻意设计——先把 Module 机制和 UObject/GC 机制分开理解。等 A3 和模块 D 才引入两者的交叉点。
- **题目特异问题**：`IMPLEMENT_MODULE` 宏做了哪两件事？（①声明 `FA1HelloModule` 的静态初始化入口函数 `Initialize___`；②通过 `FModuleInitializerEntry` 把这个函数注册到全局链表。）如果一个 Module 有多个 `.cpp` 文件，`IMPLEMENT_MODULE` 必须写在哪里？（恰好一个 `.cpp` 文件中，不能重复，否则链接期 `multiple definition` 错误。）

### 对应官方参考

- `Engine/Source/Runtime/Core/Public/Modules/ModuleInterface.h`：`IModuleInterface` 完整定义，含 `StartupModule`、`ShutdownModule`、`PreUnloadCallback`、`PostLoadCallback`、`SupportsDynamicReloading`、`SupportsAutomaticShutdown`。
- `Engine/Source/Runtime/Core/Private/Modules/ModuleManager.cpp:98-119`：`GFirstModuleInitializerEntry` 链表 + `FModuleInitializerEntry` 构造/析构，`IMPLEMENT_MODULE` 的实际底层。
- `Engine/Source/Runtime/Core/Private/Modules/ModuleManager.cpp:1060-1110`：`LoadModuleWithFailureReason` 内部找到 `StaticallyLinkedModuleInitializers` 后调用 `ModuleInfo->Module->StartupModule()` 的完整路径。
- `Engine/Source/Runtime/Core/Core.Build.cs`：真实引擎 Module 的 `.Build.cs` 样本，包含平台条件依赖、PCHUsage、`PrivateDependencyModuleNames`、`DynamicallyLoadedModuleNames` 等完整写法。

## 练习 A2：LoadingPhase 对照观察

### 目标

`ELoadingPhase` 是 UE 启动序列的分阶段控制机制，决定一个 Module 的 `StartupModule()` 在引擎初始化流程的哪个节点被调用。不同阶段有不同的"可用资源"——某些阶段 UObject 系统尚未就绪，某些阶段 `FCoreDelegates` 尚未开放订阅。

这道题通过亲手把同一个 Module 放到不同 LoadingPhase，用日志对照观察"在哪个阶段什么东西变得可用"，把 `ELoadingPhase` 的语义从"枚举值列表"变成"有真实感知的时间线"。

### 前置理解

- **`ELoadingPhase` 完整枚举**（`Engine/Source/Runtime/Projects/Public/ModuleDescriptor.h:24-60`）：
  ```
  EarliestPossible  → pak 文件可读之后立刻（用于文件系统/压缩格式 Module）
  PostConfigInit    → 配置文件读完后（用于非常底层的钩子）
  PostSplashScreen  → 第一帧 splash 渲染后
  PreEarlyLoadingScreen → CoreUObject 之前（用于 chunk 补丁系统）
  PreLoadingScreen  → Loading Screen 触发前（用于 UI 钩子）
  PreDefault        → Default 之前一步
  Default           → 引擎主初始化阶段（绝大多数 Module 在此）
  PostDefault       → Default 之后一步
  PostEngineInit    → 引擎完全初始化后（用于依赖完整引擎的后置系统）
  None              → 不自动加载
  ```
- **UObject 系统的就绪边界**：`GUObjectArray` 的初始化发生在 `PreLoadingScreen` 到 `Default` 之间的某个时刻。`Default` phase 的 `StartupModule` 调用时，UObject 系统已经可以处理 CDO，但 `GWorld` 可能还没建立（那是 `PostEngineInit` 之后的事）。
- **`FCoreDelegates` 的就绪边界**：`FCoreDelegates::OnPostEngineInit` 等在各自的 phase 触发，Module 在该 phase 的 `StartupModule` 里订阅，需要确保订阅时机早于广播时机。
- **两个 API 入口**：Project 侧由 `IProjectManager::Get().LoadModulesForProject(LoadingPhase)` 触发；Plugin 侧由 `IPluginManager::Get().LoadModulesForEnabledPlugins(LoadingPhase)` 触发（`IPluginManager.h:303`）。两者在引擎主循环的每个 phase 都会被依次调用。

### 必做任务

1. 新建一个专门用于观察的 Module `A2_PhaseObserver`，它的 `StartupModule` 做三件事（全部加 `UE_LOG` 打印）：
   - 打印当前阶段名（作为硬编码字符串，因为要在不同 phase 下观察，每次修改 phase 名打印同步修改）
   - 尝试调用 `UObject::StaticClass()`，用 `ensureAlways(UObject::StaticClass() != nullptr)` 检查 UObject 系统是否就绪，打印结果
   - 尝试订阅 `FCoreDelegates::OnPostEngineInit`，如果已过时机，该委托的广播已经发生，订阅进去的函数不会被再次调用；如果未过，会在 `PostEngineInit` 触发时被调用

2. 在 `C15_Unreal_Engine.uproject` 的 `Modules` 数组里，依次把 `A2_PhaseObserver` 的 `LoadingPhase` 改为以下值，分别启动 Editor，对照日志记录每种 phase 下三件事的结果：
   - `"PostConfigInit"`
   - `"PreLoadingScreen"`
   - `"Default"`
   - `"PostEngineInit"`

3. 制作一份对照表（至少 4 行 × 3 列）：`LoadingPhase | UObject::StaticClass() 是否非空 | FCoreDelegates::OnPostEngineInit 订阅是否有效`，用日志结果填写。

4. 特别观察 `Default` phase 下：`StartupModule` 被调用时，日志里前后最近的 `LogInit` 条目是什么？引擎处于哪个大阶段？

5. 修改 `LoadingPhase` 为 `"None"` 并重启 Editor：观察 `StartupModule` 是否被调用（应该不被调用，除非有其他 Module 显式 `LoadModuleChecked` 了它）。

### 进阶任务

- **`bCanProcessNewlyLoadedObjects` 观察**：在 `ModuleManager.cpp:1078` 处，`ProcessLoadedObjectsCallback.Broadcast(InModuleName, bCanProcessNewlyLoadedObjects)` 在 `StartupModule()` 之前被触发。`bCanProcessNewlyLoadedObjects` 只有在 `StartProcessingNewlyLoadedObjects()` 被调用后才为 `true`。阅读 `FModuleManager` 的 `StartProcessingNewlyLoadedObjects` 实现，找到它在引擎启动时被调用的时机，理解"UObject 注册处理"的就绪边界与 LoadingPhase 的关系。
- **`FModuleManager::StartProcessingNewlyLoadedObjects` 调用路径**：用 Grep 在源码中找到 `StartProcessingNewlyLoadedObjects` 的调用点（提示：在 `LaunchEngineLoop.cpp` 的 `FEngineLoop::PreInit` 里），标注它相对于哪个 LoadingPhase 被触发。
- **`FCoreDelegates::OnPostEngineInit` 订阅测试**：写一个辅助 lambda，在 `PostConfigInit` phase 的 `StartupModule` 里订阅 `FCoreDelegates::OnPostEngineInit`，验证该 lambda 在 `PostEngineInit` 阶段确实被回调。这是"在早期 phase 预订后期事件"的标准做法。

### 验收点

- 你有一张完整的对照表，至少包含 `PostConfigInit` / `Default` / `PostEngineInit` 三行，每行都有实测的 UObject 就绪状态和 `OnPostEngineInit` 订阅有效性。
- 你能说出为什么绝大多数游戏 Module 应该用 `Default`，而不是 `PostConfigInit`（答：`Default` 时引擎主体已基本就绪，过早加载会触碰尚未初始化的子系统）。
- 你能说出 `None` phase 和 `PostEngineInit` phase 的区别（答：`None` 是"永远不自动加载"，`PostEngineInit` 是"在引擎完全初始化后自动加载"）。
- `A2_PhaseObserver` 的 `StartupModule` 中，`UObject::StaticClass()` 在 `Default` phase 时非空，在 `PostConfigInit` phase 时行为不确定（可能 crash 或返回空，取决于 UObject 系统初始化是否已完成）。

### 观察点

- `ELoadingPhase` 本质上是引擎启动时间线的分段标记，不是"线程优先级"或"依赖权重"。两个 Module 若都是 `Default`，加载顺序由 `.uproject`/`.uplugin` 里声明的顺序和依赖图共同决定。
- `FModuleManager::bCanProcessNewlyLoadedObjects`（`ModuleManager.cpp:205`）是一个内部状态位，它分隔了"Module 里的 UObject 是否可以被 UObject 系统处理"的边界。在这个位为 `false` 时加载的 Module，其内部的 `UCLASS` 不会立即被 GC 处理系统扫描——这在 `PostConfigInit` 阶段是正常的。
- `StartupModule` 在 GameThread 上同步运行（`ModuleManager.cpp:159`）。如果你在 `StartupModule` 里做任何重度 IO 或阻塞操作，会直接卡住引擎启动。

### 常见坑

- **在过早的 phase 访问 UObject 系统**：在 `PostConfigInit` 的 `StartupModule` 里调用 `NewObject<T>()` 或 `GetDefault<T>()`，大概率崩溃，因为 `GUObjectArray` 还没初始化完成。正确做法是推迟到 `Default` 或 `PostEngineInit`，或用 `FCoreDelegates::OnPostEngineInit` 回调中执行。
- **把 `.uproject` 里的 `LoadingPhase` 和 `.Build.cs` 里的依赖声明混淆**：`LoadingPhase` 是运行时加载顺序，`PublicDependencyModuleNames` 是编译期符号可见性，两者解决完全不同的问题。改了 `LoadingPhase` 不需要重新跑 UBT；改了 `.Build.cs` 必须重新 UBT 并重新编译。
- **`None` phase 下期望 `StartupModule` 被调用**：声明为 `None` 的 Module 不会在任何阶段自动加载，必须有其他 Module 通过 `FModuleManager::Get().LoadModuleChecked(TEXT("MyModule"))` 显式加载才会触发 `StartupModule`。

### 提示

- 最可靠的"什么时候什么东西可用"的参考来源是 `Engine/Source/Runtime/Launch/Private/LaunchEngineLoop.cpp`（`FEngineLoop::PreInit` 和 `FEngineLoop::Init`）。找到 `LoadModulesForProject` 和 `LoadModulesForEnabledPlugins` 的调用点，就能精确知道每个 phase 在启动时间线上的位置。
- 输出日志里 `LogModuleManager Verbose` 类别会打印每个 Module 的加载过程，但默认不显示 Verbose 级别，需要在 `DefaultEngine.ini` 里加 `[Core.Log] LogModuleManager=Verbose`。

### 复盘问题

- **Q1 执行真正开始时刻**：`StartupModule()` 的调用时机由 `ELoadingPhase` 决定；对 `Default` phase，是 `FEngineLoop::Init()` 主阶段 GameThread 上的同步调用。引擎主循环每个 phase 都调用一次 `IProjectManager::LoadModulesForProject(phase)` 和 `IPluginManager::LoadModulesForEnabledPlugins(phase)`，后者调用 `FModuleDescriptor::LoadModulesForPhase`（`ModuleDescriptor.h:245`），最终落到 `FModuleManager::LoadModule`。
- **Q2 生命周期拥有者**：同 A1，Module 实例由 `FModuleManager` 的 `TUniquePtr<IModuleInterface>` 持有，生命周期由 `FModuleManager` 单例管理到引擎关闭。
- **Q3 涉及哪些 Named Thread**：`StartupModule` 全部在 **GameThread** 上。`FModuleManager::WarnIfItWasntSafeToLoadHere`（`ModuleManager.cpp:157-163`）明确检查 `IsInGameThread()`，非 GameThread 调用 `LoadModule` 会产生警告。
- **Q4 涉及 UObject 时怎么对 GC 可见**：本题 Module 实例不是 UObject，不涉及 GC。在 `StartupModule` 里测试 `UObject::StaticClass()` 只是为了探测 UObject 子系统的就绪状态，不代表 Module 本身与 GC 有关联。
- **题目特异问题**：在 `PostConfigInit` 的 `StartupModule` 里调用 `GetMutableDefault<UMySettings>()` 是否安全？（答：不安全，因为 `Default` phase 之前 CDO 不一定已创建；应等到 `Default` 或更晚。）

## 练习 A3：跨 Module 依赖与循环依赖打破

### 目标

在 UE 里，两个 Module 互相需要对方的接口是一个在大型项目里频繁出现的问题。本题通过亲手制造循环依赖、观察 UBT 的报错，再用"interface class + 运行时动态加载"解耦的标准方案解决它，把"依赖声明是强制的"这条规则从理论变成肌肉记忆。

进阶部分：探索从 `.Build.cs` 编译期依赖挪到运行期动态加载的完整路径。

这道题是本模块里与 UHT/UBT 接触最深的一道，在观察点里会第一次触碰 UHT 代码生成的入口条件（为什么本题可以不用 `UCLASS`，以及如果用了会发生什么）。

### 前置理解

- **`PublicDependencyModuleNames` vs `PrivateDependencyModuleNames`**：
  - `PublicDependencyModuleNames`：A 的 `Public/` 头文件里 include 了 B 的头文件 → 任何 include A 的 Module C，也需要能找到 B 的头文件 → B 必须在 A 的 Public 依赖里。如果不声明，C 在编译 A 的公开头时找不到 B 的类型，报 `undeclared identifier`。
  - `PrivateDependencyModuleNames`：A 的 `Private/` `.cpp` 文件里 include 了 B 的头文件，但 A 的 `Public/` 头文件里没有 → B 只需要对 A 的实现文件可见 → 放在 Private 依赖里，不会把 B 泄漏给 A 的消费方。
  - 原则：**最小可见性原则**。能放 Private 就不放 Public，避免传递性依赖膨胀。
- **循环依赖的 UBT 层面含义**：如果 Module A 在 `.Build.cs` 里依赖 B，B 也依赖 A，UBT 在解析依赖图时会检测到环，报 `Circular dependency`（链接层面更早体现为符号未定义）。这不是 C++ 语言本身的限制，而是 UBT 构建图的限制。
- **运行时动态加载**：`FModuleManager::Get().LoadModuleChecked<IMyModule>(TEXT("MyModule"))` 在运行时加载一个 Module 并返回其 `IModuleInterface` 子接口指针，不需要编译期依赖（不需要在 `.Build.cs` 里声明）。代价是：加载时机由你控制，必须在使用前确保该 Module 已加载或主动加载它。
- **UHT 的触发条件**（UE 特有点，观察点中详述）：只有头文件里含有 `UCLASS`、`USTRUCT`、`UENUM`、`UFUNCTION` 等宏时，UHT 才会为这个头文件生成 `.generated.h`。纯接口类（`class IFoo { ... }`）不含这些宏，UHT 不处理它，也不需要 `#include "IFoo.generated.h"`。这是本题故意不用 `UCLASS` 的原因：先把"Module 间解耦"和"UObject 反射"这两个概念分开理解。

### 必做任务

1. 新建两个 Module：`A3_ModuleAlpha` 和 `A3_ModuleBeta`。

2. **制造循环依赖（版本 1 — 错误做法，观察 UBT 报错）**：
   - 在 `A3_ModuleAlpha.Build.cs` 的 `PublicDependencyModuleNames` 里加 `"A3_ModuleBeta"`
   - 在 `A3_ModuleBeta.Build.cs` 的 `PublicDependencyModuleNames` 里加 `"A3_ModuleAlpha"`
   - 跑 UBT 生成项目文件，记录报错信息的完整文本。

3. **去掉循环，制造 Private 依赖可见性错误（版本 2 — 错误做法，观察编译失败）**：
   - 只在 `A3_ModuleAlpha.Build.cs` 的 `PrivateDependencyModuleNames` 里加 `"A3_ModuleBeta"`（单向依赖，无循环）
   - 在 `A3_ModuleAlpha/Public/A3AlphaPublicFoo.h` 里 `#include "SomeBetaPublicType.h"`（来自 `A3_ModuleBeta/Public/`）
   - 新建一个依赖 `A3_ModuleAlpha` 的第三 Module `A3_ModuleGamma`，在其 `.cpp` 里 `#include "A3AlphaPublicFoo.h"`
   - 观察编译错误：`A3_ModuleGamma` 在编译时找不到 Beta 的头，因为 Alpha 把 Beta 放在 Private 依赖，Beta 没有传递给 Gamma。
   - 修复：把 Alpha 对 Beta 的依赖从 `PrivateDependencyModuleNames` 移到 `PublicDependencyModuleNames`，观察编译通过。

4. **interface class + 运行时加载解耦（版本 3 — 正确做法）**：
   - 新建一个 Module `A3_ModuleInterfaces`（只含接口），在其 `Public/IA3BetaService.h` 里声明：
     ```cpp
     class IA3BetaService
     {
     public:
         virtual ~IA3BetaService() = default;
         virtual FString GetBetaGreeting() const = 0;
     };
     ```
   - `A3_ModuleBeta` 的 Module 类实现 `IA3BetaService`，并在 `StartupModule` 里把自己注册到某个全局可访问的位置（最简单：作为模块接口的一部分，通过 `FModuleManager::Get().GetModuleChecked<IA3BetaModule>` 获取）
   - `A3_ModuleAlpha` 在需要 Beta 服务时，用：
     ```cpp
     if (FModuleManager::Get().IsModuleLoaded(TEXT("A3_ModuleBeta")))
     {
         // 运行时获取，不需要编译期依赖 A3_ModuleBeta
         auto& BetaModule = FModuleManager::GetModuleChecked<IA3BetaModule>(TEXT("A3_ModuleBeta"));
         FString Greeting = BetaModule.GetBetaGreeting();
         UE_LOG(LogTemp, Log, TEXT("[A3] Beta says: %s"), *Greeting);
     }
     ```
   - `A3_ModuleAlpha.Build.cs` 里**不声明对 `A3_ModuleBeta` 的依赖**，只声明对 `A3_ModuleInterfaces` 的依赖（接口头在此）。
   - 编译通过，在 Editor 启动日志里看到 Beta 的问候语被 Alpha 打印出来。

5. 写出两个版本（`PublicDependencyModuleNames` vs `PrivateDependencyModuleNames` 的版本 1/2）编译失败时的错误信息关键字，以及运行时动态加载版本（版本 3）的编译/运行成功记录。

### 进阶任务

- **`DynamicallyLoadedModuleNames`**：在 `A3_ModuleAlpha.Build.cs` 里用 `DynamicallyLoadedModuleNames.Add("A3_ModuleBeta")` 替代依赖声明，观察 UBT 对这个字段的处理（它只是提示 UBT 这个 Module 会在运行时动态加载，不生成编译期依赖，但会确保它被打包进二进制）。
- **运行时加载时机控制**：把版本 3 里 `A3_ModuleAlpha` 的"获取 Beta 服务"代码，从 `StartupModule` 移到一个控制台命令回调（`FAutoConsoleCommand`）里，观察调用时序：Alpha 的 `StartupModule` 先跑，Beta 的 `StartupModule` 也先跑（取决于 `LoadingPhase` 和加载顺序），控制台命令在引擎完全就绪后才可用——这验证了"运行时加载解耦"的灵活性。
- **UHT 触发条件对照**（UE 特有点）：把 `IA3BetaService` 改成 `UINTERFACE` 形式：
  ```cpp
  UINTERFACE(MinimalAPI)
  class UA3BetaService : public UInterface { GENERATED_BODY() };
  class IA3BetaService : public IInterface
  {
  public:
      virtual FString GetBetaGreeting() const = 0;
  };
  ```
  观察 UHT 现在会为这个头文件生成 `.generated.h`，并且必须 `#include "IA3BetaService.generated.h"` 作为最后一个 include。与纯 C++ 接口版本对比，理解"只要有 UCLASS/UINTERFACE 宏，UHT 就必须处理这个头"。

### 验收点

- 你有三份编译/运行记录：版本 1（循环依赖 UBT 报错）、版本 2（Private 依赖传递性失败的编译错误）、版本 3（interface + 运行时加载，编译通过，运行时日志正确）。
- 你能用一句话解释"为什么版本 3 里 Alpha 的 `.Build.cs` 不需要声明对 Beta 的依赖"：因为 Alpha 的头文件和实现文件里没有任何 Beta 头的 include，只用了接口头（来自 `A3_ModuleInterfaces`），编译期不需要 Beta 的类型定义。
- 你能说出什么情况必须用 `PublicDependencyModuleNames` 而不是 `PrivateDependencyModuleNames`：当本 Module 的 **Public** 头文件里 include 了对方 Module 的头文件时，必须用 Public 依赖，因为你的消费方也需要能找到那个类型。

### 观察点

- **UHT 只处理含 UE 宏的头文件**（UE 特有点）：本题的 `IA3BetaService.h` 不含任何 `UCLASS`/`UINTERFACE` 宏，UHT 完全不处理它，不会生成 `.generated.h`，不需要特殊的 include 顺序。这是在模块 D 之前第一次触碰"UHT 触发条件"——通过对比纯 C++ 接口和 `UINTERFACE` 接口，理解"UHT 的存在对代码组织有什么实际影响"。
- **`FModuleManager::GetModuleChecked<T>` 的类型参数**：`T` 必须是 `IModuleInterface` 的子类，且 Module 的实现类必须能被 `static_cast` 转换为 `T`。这意味着你的 Module 类需要继承接口 `T`（`class FA3BetaModule : public IModuleInterface, public IA3BetaModule`）。这是 UE 里"Module 对外暴露服务"的标准做法：Module 类同时继承 `IModuleInterface`（生命周期钩子）和自定义接口（服务契约）。
- **`PrivateDependencyModuleNames` 的传递性规则**：私有依赖不传递给消费方。这是 UBT 依赖图的设计意图：避免"编译传染病"——A 私有依赖 B，B 私有依赖 C，但如果 A 的公开头不暴露 B/C 的类型，消费方 D 完全不需要知道 B 和 C 的存在。

### 常见坑

- **`#include` 路径和 `PublicDependencyModuleNames` 不匹配**：在 Private `.cpp` 里 include 了某 Module 的头，但 `.Build.cs` 里加的是 `PublicDependencyModuleNames`（本应用 `PrivateDependencyModuleNames`），不会报错但会不必要地把对方 Module 的 include 路径暴露给所有消费方。最终效果是消费方可以不声明依赖、直接 include 到对方的头，造成隐式依赖。
- **`FModuleManager::GetModuleChecked<T>` 在 Module 未加载时 crash**：如果不先用 `IsModuleLoaded` 检查，调用 `GetModuleChecked` 时 Module 尚未加载会直接 `check` 失败。安全做法：先 `IsModuleLoaded` 检查，或用 `LoadModuleChecked` 直接加载（如果允许主动加载）。
- **interface 头和实现头混放**：如果把 `IA3BetaService.h`（接口）放在 `A3_ModuleBeta/Public/` 而不是 `A3_ModuleInterfaces/Public/`，当 Alpha 想 include 这个接口时，仍然需要声明对 `A3_ModuleBeta` 的依赖，循环没有打破。接口必须放在一个中立的"只含接口"的 Module 里，才能真正解耦两端。
- **`UINTERFACE` + `.generated.h` 顺序错误**：进阶任务里改成 `UINTERFACE` 后，`#include "IA3BetaService.generated.h"` 必须是这个头文件里最后一个 `#include`，否则 UHT 报解析错误。这条规则来自 UHT 的 include 顺序假设，违反会产生 UHT 层面的报错，和 C++ 编译器的报错不在同一层次。

### 提示

- UBT 循环依赖报错通常出现在"生成项目文件"（`GenerateProjectFiles`）阶段，而不是 C++ 编译阶段。如果报错不在 IDE 的编译输出而在 UBT 日志里，去 `Saved/Logs/UnrealBuildTool-*.log` 找完整错误。
- `DynamicallyLoadedModuleNames` 是 `.Build.cs` 里的另一个字段，告诉 UBT "这个 Module 会被运行时动态加载，请确保它被打包"，但不建立编译期符号依赖。适合在 `Core.Build.cs` 里声明 `DirectoryWatcher` 这类 Editor-only 的运行时可选 Module。

### 复盘问题

- **Q1 执行真正开始时刻**：Alpha 在其 `StartupModule`（`Default` phase，GameThread）里通过 `FModuleManager::Get().IsModuleLoaded` + `GetModuleChecked` 动态获取 Beta 的服务。Beta 的 `StartupModule` 早于 Alpha（假设 Beta 也是 `Default` phase 且在 `.uproject` 中注册在 Alpha 之前），因此调用时 Beta 已加载。
- **Q2 生命周期拥有者**：Alpha、Beta、Interfaces 三个 Module 实例分别由 `FModuleManager` 的 `TUniquePtr<IModuleInterface>` 独占持有，互相不知道对方的存在（编译期）；运行期通过接口指针交互，接口指针指向 Beta 的 Module 实例，Beta Module 由 `FModuleManager` 保证在 `ShutdownModule` 前存活。
- **Q3 涉及哪些 Named Thread**：全部在 **GameThread**，同 A1/A2。`FModuleManager::LoadModuleChecked` 的注释明确：非 GameThread 调用会产生线程安全警告。
- **Q4 涉及 UObject 时怎么对 GC 可见**：本题不涉及 UObject。纯 C++ 接口 `IA3BetaService` 不继承 `UObject`，其实现类的生命周期由 `FModuleManager` 管理（Module 实例作为 `TUniquePtr` 持有），与 GC 完全无关。进阶任务里改成 `UINTERFACE` 后，`UA3BetaService`（继承 `UInterface`，后者继承 `UObject`）会进入 GC 系统，但 Module 实例本身仍不是 `UObject`。
- **题目特异问题**：`PublicDependencyModuleNames` 和 `PrivateDependencyModuleNames` 中，哪个会影响到消费方（依赖本 Module 的其他 Module）的 include path？（答：`PublicDependencyModuleNames` 的依赖 Module 的头路径会传递给消费方；`PrivateDependencyModuleNames` 不传递。）

## §Plugin 尾补：Module 与 Plugin 的层级关系

本节不增加练习，是对"UE 工程组织的第二层切分"的概览补充。

### Plugin 是 Module 的容器

在 UE 里，**Module 是代码单元，Plugin 是 Module 的打包和分发单位**。一个 Plugin 可以包含零个到多个 Module，也可以包含 Content（资产）、Shader、Config 等非代码资源。

层级关系：
```
.uproject（工程）
  └── Plugins（插件列表，也可以是引擎内置 Plugin）
        └── MyPlugin/
              └── MyPlugin.uplugin          ← Plugin 描述文件
              └── Source/
                    └── MyPluginModule/
                          └── MyPluginModule.Build.cs   ← Module 描述
                          └── Private/
                          └── Public/
```

### `.uplugin` 关键字段

`.uplugin` 是一个 JSON 文件，核心字段（来自 `PluginDescriptor.h:38-160`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `FriendlyName` | `FString` | 编辑器里显示的友好名称 |
| `Version` / `VersionName` | `int32` / `FString` | 内部版本号 / 显示版本名 |
| `Modules` | `TArray<FModuleDescriptor>` | **本 Plugin 包含的所有 Module 列表，每个 Module 声明自己的 `LoadingPhase` 和 `Type`（Runtime/Editor/等）** |
| `EnabledByDefault` | `EPluginEnabledByDefault` | `Enabled` / `Disabled` / `Unspecified`，控制是否默认启用 |
| `SupportedTargetPlatforms` | `TArray<FString>` | 控制哪些平台可以使用本 Plugin，用于平台条件裁剪 |
| `CanContainContent` | `bool` | Plugin 是否包含 Content 资产目录 |

一份最小 `.uplugin` 示例结构：
```json
{
    "FileVersion": 3,
    "Version": 1,
    "VersionName": "1.0",
    "FriendlyName": "My Learning Plugin",
    "Description": "C15_Unreal_Engine A 模块练习插件",
    "EnabledByDefault": false,
    "Modules": [
        {
            "Name": "A1_HelloModule",
            "Type": "Editor",
            "LoadingPhase": "Default"
        },
        {
            "Name": "A3_ModuleBeta",
            "Type": "Editor",
            "LoadingPhase": "Default"
        }
    ],
    "SupportedTargetPlatforms": ["Win64", "Mac", "Linux"]
}
```

### LoadingPhase 在 Plugin 与 Project 两侧的叠加顺序

引擎启动时，对每个 `ELoadingPhase::Type` 值，都依次执行：

1. `IProjectManager::Get().LoadModulesForProject(phase)` — 加载 `.uproject` 的 `Modules` 数组里该 phase 的 Module
2. `IPluginManager::Get().LoadModulesForEnabledPlugins(phase)` — 加载所有已启用 Plugin 的 `.uplugin` 的 `Modules` 数组里该 phase 的 Module（`IPluginManager.h:303`）

两者的关系是"Project Module 先，Plugin Module 后"（在同一 phase 内）。如果 Plugin Module 的 `StartupModule` 依赖 Project Module 提供的某个服务，需要确保 Project Module 的 `LoadingPhase` ≤ Plugin Module 的 `LoadingPhase`，或者 Plugin Module 在 `StartupModule` 里显式用 `FModuleManager::Get().LoadModuleChecked` 主动加载 Project Module（如果还没加载的话）。

### 与 `.uproject` `Modules` 数组的区别

- `.uproject` 的 `Modules` 数组：直接属于项目的 Module（非 Plugin 包装）。通常是项目游戏逻辑的 Module，比如 `GameName` Module 本身。
- `.uplugin` 的 `Modules` 数组：插件拥有的 Module。插件可以来自引擎（`Engine/Plugins/`）、项目（`Project/Plugins/`）或外部路径（`AdditionalPluginDirectories`）。

### `IPluginManager` 的主要入口

`IPluginManager::Get().LoadModulesForEnabledPlugins(ELoadingPhase::Type LoadingPhase)` 是 Plugin 侧的核心加载入口（`IPluginManager.h:303`）。它遍历所有已启用的 Plugin，对每个 Plugin 调用其 `Modules` 数组中 `LoadingPhase == LoadingPhase` 的 Module 的加载流程，最终也落到 `FModuleManager::LoadModule`。

`IPlugin`（定义在 `Engine/Source/Runtime/Projects/Public/Interfaces/IPluginManager.h:110`，实际 `IPlugin` 类内容通过 `IPluginManager.h` 和 `PluginDescriptor.h` 合并表达）提供了 `GetDescriptor()` 方法，可以在运行时获取 Plugin 的 `FPluginDescriptor`，从而知道它的 `Modules`、`SupportedTargetPlatforms` 等字段。

## 做完本模块后你现在应该能说清楚什么

至少把下面几句话说顺：

- `.Build.cs` 是 UBT 读取的 C# 脚本，不是 Makefile，可以用 `if/foreach` 按平台/构建类型动态声明依赖。`PublicDependencyModuleNames` 传递给消费方，`PrivateDependencyModuleNames` 不传递。
- `IMPLEMENT_MODULE(ModuleClass, ModuleName)` 把 Module 的初始化函数插入静态链表 `GFirstModuleInitializerEntry`，`FModuleManager` 在加载阶段遍历这个链表找到入口，调用 `StartupModule()`（`ModuleManager.cpp:1087`）。
- `ELoadingPhase` 决定 `StartupModule()` 在引擎启动时间线的哪个节点被调用；`Default` 是绝大多数游戏 Module 的选择；`PostConfigInit` 过早、`PostEngineInit` 过晚各有适用场景。
- 循环依赖由 UBT 在依赖图解析阶段拒绝；打破方法是把接口抽到中立 Module，用 `FModuleManager::GetModuleChecked<T>` 在运行时解耦。
- Plugin 是 Module 的容器，`.uplugin` 的 `Modules` 数组描述每个 Module 的类型和加载阶段，`IPluginManager::LoadModulesForEnabledPlugins` 在每个 phase 驱动 Plugin 侧的加载。
- `WITH_EDITOR` 守卫控制 Editor-only 代码的编译包含，是 UE 工程里区分 Editor 和 Shipping 路径的标准机制，A1 就开始养成守卫习惯。
