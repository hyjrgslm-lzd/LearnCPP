# 07 模块 E：资产与加载

## 模块目标

反向引用 `01-心智模型` 的 §4（GC ownership 与 C++ ownership 两套并存）与 §6（Subsystem 化，而非全局单例）。

资产系统是 UE 引擎中把"磁盘文件"与"内存 UObject"衔接起来的那一层管道。理解它需要同时看懂三件事：

1. **序列化层**——`FArchive` 是 UE 所有数据进出内存的统一接口，`UPackage` 是 UObject 在磁盘上的容器单位。
2. **元数据查询层**——`IAssetRegistry` 是一张在 Editor 启动时构建的"磁盘资产目录"，不加载资产本体，只维护它们的路径、类型、依赖关系。
3. **惰性加载层**——`FSoftObjectPath` 描述资产位置，`FStreamableManager::RequestAsyncLoad` 返回 `FStreamableHandle`，真正的磁盘 I/O 发生在引擎的 AsyncLoading 线程，不阻塞 GameThread。

这三层的递进关系——序列化是底，注册表是元，惰性流送是用——也对应了本模块三道练习的顺序。

阶梯定位：**use + inspect**。流水线过大（AsyncLoading2、LinkerLoad 核心路径），不要求 implement-own。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- `UPackage` 是什么，一个 `.uasset` 文件与内存中的 `UPackage` 对象之间是什么对应关系。
- `FArchive::IsSaving()` / `FArchive::IsLoading()` 为什么能让同一份序列化代码双向运行，这背后的设计思想是什么。
- `IAssetRegistry::GetDependencies` 与 `GetReferencers` 的区别，以及为什么在 Module 的 `StartupModule` 里直接调用它有崩溃风险。
- `FStreamableManager::RequestAsyncLoad` 返回 `FStreamableHandle` 的瞬间加载是否已经开始，`GetLoadedAsset()` 在什么条件下才能返回有效指针。
- 硬引用（`UObject*` / `TObjectPtr<T>` UPROPERTY）与软引用（`TSoftObjectPtr<T>` / `FSoftObjectPath`）的本质区别，以及后者如何配合 `FStreamableManager` 做到"按需加载"。
- `UAssetManager::LoadPrimaryAsset` 与直接调用 `FStreamableManager::RequestAsyncLoad` 的职责分界在哪里。

## 练习 E1：UPackage + FArchive 双向序列化

### 目标

通过手写一个简单的自定义 `UObject` 并用 `FMemoryWriter` / `FMemoryReader` 对它做往返序列化，直观体验 `FArchive` 的"单代码双向"设计，并通过 `UObject::GetOutermost()` 观察 `UPackage` 作为 UObject 容器的角色。

### 前置理解

- 你已完成模块 D，能定义 `UCLASS` + `UPROPERTY` 并用 `NewObject<T>` 创建实例。
- 你知道 `FArchive` 是 UE 序列化体系的基类，但还没有动手用过它。
- 你知道 `.uasset` 文件在内存中对应一个 `UPackage` 对象，UPackage 继承自 `UObject`。

**关键源码**（在阅读本节任务时同步翻看）：

- `Engine/Source/Runtime/CoreUObject/Public/UObject/Package.h`：`UPackage` 的类定义；注意 `UCLASS(MinimalAPI, Config=Engine)` 声明——Package 本身是一个受 UHT 管理的 UObject 子类。关键字段：`PackageFlagsPrivate`（`std::atomic<uint32>`）、`bHasBeenFullyLoaded`、`AdditionalInfo->LinkerLoad`；关键方法：`UPackage::Save`（静态）、`MarkAsFullyLoaded()`、`GetLinker()`。
- `Engine/Source/Runtime/CoreUObject/Public/Serialization/Archive.h`（`FArchive`）：基类，`IsSaving()` / `IsLoading()` 是返回内部 `ArIsSaving` / `ArIsLoading` bit 的 `inline` 方法，同一个 `Serialize(FArchive& Ar)` 函数对 `FMemoryWriter` 和 `FMemoryReader` 表现出写与读两个方向。
- `Engine/Source/Runtime/CoreUObject/Public/UObject/PackageFileSummary.h`：`FPackageFileSummary` 是 `.uasset` 文件头，包含版本号、导入表偏移、导出表偏移、依赖哈希等字段。（进阶时参考）

### 必做任务

1. 在你的练习 Module（例如 `E1_SerializeUObject`）里，新建一个 `UCLASS`，例如 `UMySerializable`，带若干 `UPROPERTY`（`int32 Health`、`FString Name`、`float Speed`）。

2. 在 `StartupModule` 或一个控制台命令回调里，用 `NewObject<UMySerializable>()` 创建实例并赋初值。

3. 用 `FMemoryWriter` 序列化该对象：
   ```cpp
   TArray<uint8> Buffer;
   FMemoryWriter Writer(Buffer, /*bIsPersistent=*/true);
   MyObj->Serialize(Writer);
   UE_LOG(LogTemp, Log, TEXT("Serialized %d bytes"), Buffer.Num());
   ```

4. 用 `FMemoryReader` 反序列化到一个新实例：
   ```cpp
   FMemoryReader Reader(Buffer, /*bIsPersistent=*/true);
   UMySerializable* Clone = NewObject<UMySerializable>();
   Clone->Serialize(Reader);
   // 此时 Clone 的字段应与 MyObj 一致
   ```

5. 加日志，打印序列化前后字段的值，验证往返一致性。

6. 调用 `MyObj->GetOutermost()`，观察返回的 `UPackage*` 是哪一个——它的 `GetName()` 是什么？这个 package 是怎么来的？

7. 在代码里同时检查：`Writer.IsSaving()` 与 `Reader.IsLoading()` 各返回什么，加注释说明为什么同一个 `Serialize` 函数能分别执行写/读逻辑。

### 进阶任务

- 在 `UMySerializable::Serialize(FArchive& Ar)` 里重写基类实现，手动调用 `Super::Serialize(Ar)`，然后额外序列化一个不用 `UPROPERTY` 修饰的 `int32 InternalCounter`（Tagged vs Untagged 差异）；观察 `FMemoryReader` 方向能否正确读回。
- 通过 `UPackage::Save` 把含有 `UMySerializable` 的 Package 存到一个临时路径的 `.uasset` 文件，再用 `LoadPackage` 加载回来，验证对象完整性。（观察 `UPackage::SavePackage` 的签名：`static bool SavePackage(UPackage*, UObject* InAsset, const TCHAR* Filename, const FSavePackageArgs&)`。）
- 用十六进制查看器打开生成的 `.uasset` 文件，对照 `FPackageFileSummary` 的字段找到文件头的魔数（`0x9E2A83C1`）、版本号字段偏移、导出表起始位置——理解"文件格式"与"内存对象"的对应。
- 了解 `FLinkerLoad` / `FLinkerSave` 的角色：它们是比 `FMemoryWriter/Reader` 更重的、专门处理 UAsset 文件格式（包含 ImportTable / ExportTable / DependsMap）的 FArchive 子类。观察 `UPackage.h` 中 `GetLinker()` 返回的是 `FLinkerLoad*`——只有真正从磁盘加载的 Package 才会有非 null 的 Linker。

### 验收点

- `FMemoryWriter` 方向 `Writer.IsSaving() == true`，`FMemoryReader` 方向 `Reader.IsLoading() == true`；能在控制台日志中打印证明。
- 往返序列化后，`Clone` 的 `Health`、`Name`、`Speed` 与原始值完全一致。
- 能用 `GetOutermost()` 取到 `UPackage*`，并说清楚：为什么 `NewObject<T>()` 不指定 Outer 时，对象会挂在一个临时 Transient Package 下。
- 能解释"Tagged Property Serialization"与"Untagged Raw Serialization"的区别：`UObject::Serialize` 调用 `SerializeTaggedProperties`，写入的是带 FName tag 的字段；手动写的字段则是按字节偏移读写，二者不可混搭。
- 四固定问题书面回答完整（见"复盘问题"节）。

### 观察点

**为什么 `FArchive` 用单接口双向设计**：在传统序列化框架（如 protobuf）中，序列化（encode）和反序列化（decode）是两套代码。UE 的设计让同一份 `Serialize(FArchive& Ar)` 代码靠 `Ar.IsSaving()` / `Ar.IsLoading()` 分支，在逻辑对称的结构上只写一遍——不容易出现"写了 3 个字段但只读了 2 个"导致偏移漂移的 bug。这与 stdexec 里 sender 图的"描述期与执行期分离"是精神类似的设计哲学：一个函数，两种上下文语义。

**UPackage 作为容器的角色**：UE 里每个 UObject 都有一个 Outer 链，最终汇聚到某个 `UPackage`（通过 `GetOutermost()` 可达）。Package 是"UObject 世界"与"磁盘文件"之间的桥梁：一个 `.uasset` 文件精确对应一个 `UPackage`，文件内存放的是该 Package 下所有顶层 UObject 的序列化数据。`NewObject<T>()` 不指定 Outer 时，UE 会把对象挂在 `GetTransientPackage()`（一个全局临时 Package），这就是为什么随意调用 `NewObject` 后必须关心 Outer——你的对象会不会在下次 GC 时因为 TransientPackage 没被引用而被踢掉？

**FArchive 的生命周期规则**：`FMemoryWriter` / `FMemoryReader` 是栈上对象，不拥有底层 `TArray<uint8>` 的所有权（只持有引用）。写完后 Buffer 由调用方管理——这是 UE 里 RAII 非 UObject 对象的典型模式（参考心智模型 §4：非 UObject 由 C++ 所有权管理）。

### 常见坑

- **`Serialize` 里忘调 `Super::Serialize(Ar)`**：`UObject::Serialize` 会处理 `UPROPERTY` 字段的 Tagged Serialization，漏调则所有反射字段都不会被序列化，但手动写的字段还在——结果是部分往返失败，日志也没有明显报错。
- **`FMemoryWriter` 构造时的 `bIsPersistent` 参数**：该参数控制 FArchive 是否在序列化后保留 Buffer 而不析构。对临时往返测试为 `true` 即可，但要确保 Buffer 生命周期长于 Writer。
- **`GetOutermost()` 返回的 Package 是 TransientPackage**：在 Editor 中用 `NewObject<T>()` 创建的临时对象，其 Package 是全局 Transient Package，不会被存盘。要创建"真正可存盘"的对象，必须用 `CreatePackage(TEXT("/Game/MyPackage"))` 先建包，再以该包为 Outer 创建对象。
- **在 Shipping 构建中 `FMemoryWriter/Reader` 不包含 `WITH_EDITOR` 守卫**，可以正常用于运行时数据流（例如网络序列化缓冲），但 `UPackage::Save` 是 Editor-only API，Shipping 中不可用。
- **`UObject::Serialize` 的线程安全**：默认不保证，必须在 GameThread 调用，或在对象确认不被 GC 访问的情况下操作。

### 提示

- 从最简单的 `FMemoryWriter`/`FMemoryReader` 开始，不要一上来就尝试 `LoadPackage`——后者涉及 AsyncLoading 路径，复杂度高一个量级。
- 观察 `Buffer.Num()` 的字节数：即使只有 3 个简单字段，Tagged Serialization 的开销（FName tag + 类型 tag）也会让输出比你预期大得多。
- `FArchive` 有数十个子类（`FMemoryWriter`、`FMemoryReader`、`FArchiveCountMem`、`FArchiveObjectPropertyMapper` 等），都遵守同一个接口。用 `<<` 运算符（它委托到 `Serialize` 重载）可以序列化基础类型：`Ar << MyInt32; Ar << MyFString;`。

### 复盘问题

- **Q1（执行真正开始时刻）**：`Clone->Serialize(Reader)` 被调用时，真正的反序列化在哪条线程的哪个调用栈上开始？是否存在异步路径？
- **Q2（生命周期拥有者）**：`UMySerializable* Clone` 这个指针，在 `NewObject<UMySerializable>()` 返回后，由谁负责它的生存？如果你把这个指针存在一个普通 C++ 局部变量里，GC 下次运行时会发生什么？怎么修复？
- **Q3（涉及哪些 Named Thread）**：`Obj->Serialize(Ar)` 完全在 GameThread 上同步完成。AsyncLoading2 路径（`LoadPackage`）则在哪些线程上运行？（反向引用大纲 §7 Cap2 第 3 项：`CoreUObject/Private/Serialization/AsyncLoading2.cpp`）
- **Q4（涉及 UObject 时怎么对 GC 可见）**：你创建的 `Clone` 对象，如果没有任何 `UPROPERTY` 指向它，也没有 `AddToRoot()`，GC 会在多少个 tick 内回收它？说出让 GC 保留它的三种方法。
- **补充问题**：`FArchive::IsSaving()` 和 `FArchive::IsLoading()` 能同时为 true 吗？为什么？看 `FArchive.h` 里的 `ArIsSaving`/`ArIsLoading` 字段定义来回答。

## 练习 E2：AssetRegistry 依赖查询

### 目标

在 Editor 环境中通过 `IAssetRegistry::Get()` 查询资产元数据，理解 `GetAssetsByClass`、`GetDependencies`、`GetReferencers` 三个查询接口的语义差异，并观察 `FAssetData` 的字段结构。

### 前置理解

- 你知道 `IAssetRegistry` 是一个全局接口，提供对磁盘上所有已扫描资产的元数据访问，**不**加载资产本体。
- 你知道在 Editor 启动时 AssetRegistry 会异步扫描 `/Game` 目录（通过 `IAssetRegistry::SearchAllAssets`），扫描完成前部分查询结果可能不完整。
- 你知道 AssetRegistry 在 cooked 游戏中的形态与 Editor 中完全不同（后详）。

**关键源码**（同步参考）：

- `Engine/Source/Runtime/AssetRegistry/Public/AssetRegistry/IAssetRegistry.h`：`IAssetRegistry` 是一个 `UINTERFACE`。主要查询方法：
  - `GetAssetsByClass(FTopLevelAssetPath ClassPathName, TArray<FAssetData>& OutAssetData, bool bSearchSubClasses)` — 按类查资产
  - `GetDependencies(FName PackageName, TArray<FName>& OutDependencies, EDependencyCategory Category)` — 查某 package 依赖了哪些其他 package
  - `GetReferencers(FName PackageName, TArray<FName>& OutReferencers)` — 查哪些 package 引用了某 package
  - 静态访问：`IAssetRegistry::Get()` 返回 `IAssetRegistry*`（可能为 null！）；`IAssetRegistry::GetChecked()` 则 check 后返回引用。
- `FAssetData`（头文件 `AssetRegistry/Public/AssetRegistry/AssetData.h`）：关键字段：
  - `FName PackageName`：包名，形如 `/Game/MyFolder/MyAsset`
  - `FTopLevelAssetPath AssetClassPath`：资产类的全路径，例如 `/Script/Engine.StaticMesh`
  - `FName AssetName`：资产名（不含路径）
  - `FAssetDataTagMapSharedView TagsAndValues`：由 `GetAssetRegistryTags()` 填入的键值对，例如材质球的 `NumTextures`

### 必做任务

1. 在你的练习 Module（例如 `E2_AssetRegistryQuery`）的 `StartupModule` 里，**不要直接查询**，而是注册一个回调到 `IAssetRegistry::OnFilesLoaded()`，在回调里做查询——这是处理"AssetRegistry 还没扫描完就查询"这个坑的正确做法。

2. 在回调里，用 `IAssetRegistry::GetChecked().GetAssetsByClass` 查询某个具体类型的资产（建议用你项目里已有的资产类型，例如 `UStaticMesh`，类路径为 `/Script/Engine.StaticMesh`）：
   ```cpp
   TArray<FAssetData> AssetList;
   IAssetRegistry::GetChecked().GetAssetsByClass(
       FTopLevelAssetPath(TEXT("/Script/Engine"), TEXT("StaticMesh")),
       AssetList,
       /*bSearchSubClasses=*/false
   );
   UE_LOG(LogTemp, Log, TEXT("Found %d StaticMesh assets"), AssetList.Num());
   ```

3. 对结果中的第一个 `FAssetData`，打印 `PackageName`、`AssetName`、`AssetClassPath`，以及所有 `TagsAndValues` 的键值对。

4. 用 `GetDependencies` 查询该资产所在 Package 的依赖：
   ```cpp
   TArray<FName> HardDeps, SoftDeps;
   IAssetRegistry::GetChecked().GetDependencies(
       AssetData.PackageName, HardDeps,
       UE::AssetRegistry::EDependencyCategory::Package,
       UE::AssetRegistry::FDependencyQuery(UE::AssetRegistry::EDependencyProperty::Hard)
   );
   IAssetRegistry::GetChecked().GetDependencies(
       AssetData.PackageName, SoftDeps,
       UE::AssetRegistry::EDependencyCategory::Package,
       UE::AssetRegistry::FDependencyQuery(UE::AssetRegistry::EDependencyProperty::Soft)
   );
   ```
   分别打印硬依赖（必须一起加载）和软依赖（可以延迟加载）的数量与路径。

5. 用 `GetReferencers` 查询该 Package 被哪些 Package 引用（反向依赖）。打印前 5 个结果。

6. 写 5–10 行观察记录：硬依赖通常是什么（材质、纹理、骨架？），软依赖通常是什么（蓝图类的 ClassDefaultObject？），引用者通常是什么？

### 进阶任务

- 递归查询：对硬依赖列表里的每一项，再次调用 `GetDependencies`，用递归或 BFS 把整个依赖树打印出来（深度限制为 2 层，避免无限扩展）。对比"一个 StaticMesh 的完整依赖树有多宽"。
- 了解 `FAssetData::TagsAndValues` 的来源：查看任意 `UObject` 子类（如 `UStaticMesh`）中的 `GetAssetRegistryTags` 虚函数实现——这就是在保存时写入 AssetRegistry 的元数据。
- **Editor vs Cooked 差异**：Editor 中 `IAssetRegistry` 是在启动时扫描全部磁盘文件构建的，是全量数据。Cooked 游戏中，AssetRegistry 是在 Cook 时写入的一个二进制文件（`AssetRegistry.bin`），只包含 Cook 时保留的数据子集，且大多数 tag 被剥除以节省空间。在 Cooked 运行时调用 `GetDependencies` 可能返回空结果。
- 观察 `IAssetRegistry::IsLoadingAssets()` / `IsGathering()`：在 Editor 启动序列的不同阶段调用会得到不同结果，理解为什么必须等 `OnFilesLoaded()` 再查询。

### 验收点

- 能打印出至少一个真实资产的 `PackageName`、`AssetClassPath`、`TagsAndValues`（至少 3 个 tag）。
- `GetDependencies` 的硬依赖列表非空，且结果路径格式正确（以 `/Game/` 或 `/Engine/` 开头）。
- `GetReferencers` 能找到至少一个引用者（或说明为什么返回为空——例如该资产没有被其他资产直接引用）。
- 能解释 `EDependencyCategory::Package` 中硬依赖（`EDependencyProperty::Hard`）与软依赖（`EDependencyProperty::Soft`）的语义差异。
- 四固定问题书面回答完整。

### 观察点

**AssetRegistry 不加载资产**：`IAssetRegistry` 的所有查询操作都不触发实际资产加载。它只维护一张"元数据表"——每个 Package 的类型、路径、Tag 字典、依赖链。这使得"查询项目里有多少种 SoundCue"这样的操作可以在毫秒内完成，而不需要把所有 SoundCue 加载进内存。

**依赖 vs 引用者（方向问题）**：`GetDependencies(A)` 返回"A 依赖了谁"（A → ?）；`GetReferencers(A)` 返回"谁依赖了 A"（? → A）。在资产迁移、内存分析、Cook 裁剪等工程场景中，这两个方向都重要：前者用于"加载 A 需要先加载哪些"，后者用于"删除 A 会影响哪些其他资产"。

**硬依赖 vs 软依赖**：硬依赖（`EDependencyProperty::Hard`）是 Linker 在加载包时自动一起加载的依赖——通常来自 `UObject*` 或 `TObjectPtr<T>` 类型的 `UPROPERTY` 直接引用另一个包的对象。软依赖（`EDependencyProperty::Soft`）来自 `FSoftObjectPath` / `TSoftObjectPtr` 引用——它只记录"存在这个引用关系"，但不触发加载，加载时机由调用方决定（正是 E3 的主题）。

**`OnFilesLoaded` 的重要性**：AssetRegistry 在 Editor 启动时是异步扫描的（`bIsSearchAsync == true`）。在 Module 的 `StartupModule`（LoadingPhase 为 Default）里直接调用 `GetAssetsByClass`，AssetRegistry 可能仍处于扫描中。正确做法是注册 `OnFilesLoaded` 委托，在回调里执行查询。

### 常见坑

- **在 `StartupModule` 里直接查询 AssetRegistry 导致崩溃或返回空结果**：原因是 AssetRegistry 模块的 LoadingPhase 是 `PreEngineInit`，但它的后台扫描是异步的，`StartupModule` 被调用时扫描还没完成。解决方案：用 `OnFilesLoaded` 委托，或先检查 `IsLoadingAssets()` 状态。
- **`IAssetRegistry::Get()` 返回 nullptr**：在非常早期的加载阶段（`PreDefault` Phase）AssetRegistry 模块尚未初始化。用 `GetChecked()` 会 check 失败。应先通过 `FModuleManager::IsModuleLoaded("AssetRegistry")` 确认模块已加载。
- **`FTopLevelAssetPath` 构造方式**：UE5 中类路径从旧的 `FName` 格式迁移到了 `FTopLevelAssetPath`（格式 `/Script/ModuleName.ClassName`），不能直接传旧式字符串，需要用 `FTopLevelAssetPath(TEXT("/Script/Engine"), TEXT("StaticMesh"))` 两参数构造。
- **`GetDependencies` 只返回磁盘记录的依赖**：如果资产刚在内存里被修改但还没保存，`GetDependencies` 返回的是磁盘上的旧版数据。Editor 里需要保存资产后才能看到最新依赖。
- **Cooked 包中 dependency data 可能被剥除**：`CookSettings` 中的 `bSerializeDependencies` 控制依赖数据是否写入 Cook 后的 AssetRegistry，默认在 Shipping 包中被剥除以节省空间。

### 提示

- 如果你的工程里没有合适的资产，可以在 Editor 里新建一个 Material 或 StaticMesh（哪怕是空的），保存一次，让 AssetRegistry 扫描到它，再做查询。

## 练习 E3：StreamableManager 异步加载（与 sender 惰性类比）

### 目标

用 `FSoftObjectPath` 描述资产的"地址"（不触发加载），通过 `FStreamableManager::RequestAsyncLoad` 发起异步加载请求并获得 `FStreamableHandle`，在 `CompleteDelegate` 里用 `GetLoadedAsset<T>()` 取到加载完毕的对象。通过这个练习，建立 `FStreamableHandle` ↔ stdexec `sender` 的精准类比。

### 前置理解

- 你已完成练习 E2，理解了 `FAssetData::PackageName` 与 `FSoftObjectPath` 的关系。
- 你了解 stdexec 的 sender-receiver 模型：sender 是"描述工作"的对象，`start(op)` 才真正启动，completion 时调用 receiver。（引自 `Execution_Study`）
- 你知道 UE 里有 `TSoftObjectPtr<T>` 和 `FSoftObjectPath` 两种软引用类型，前者是模板包装，后者是通用字符串路径。

**关键源码**（重点阅读）：

- `Engine/Source/Runtime/Engine/Classes/Engine/StreamableManager.h`：`FStreamableManager`（非 UObject，继承 `FGCObject` 以手动告知 GC 自己引用的对象）。核心方法：
  ```cpp
  // 主异步加载接口（模板重载，支持路径数组 + 回调 lambda）
  TSharedPtr<FStreamableHandle> RequestAsyncLoad(
      PathContainerType&& TargetsToStream,
      FuncType&& DelegateToCall = ...,
      TAsyncLoadPriority Priority = DefaultAsyncLoadPriority,
      bool bManageActiveHandle = false,
      bool bStartStalled = false,
      FString DebugName = FString(),
      UE::FSourceLocation Location = ...);
  
  // 同步加载接口（会阻塞 GameThread，慎用）
  UObject* LoadSynchronous(const FSoftObjectPath& Target, ...);
  ```
  优先级常量：`DefaultAsyncLoadPriority = 0`；`AsyncLoadHighPriority = 100`。

- `FStreamableHandle`（同文件）：关键状态查询：
  - `HasLoadCompleted()` — 所有资产已加载
  - `IsLoadingInProgress()` — 加载还在进行
  - `WasCanceled()` — 已被取消
  - `GetLoadedAsset<T>()` — 取回已加载的第一个资产（泛型重载）
  - `CancelHandle()` — 中止加载
  - `ReleaseHandle()` — 释放资产持有，允许 GC 回收

- `FSoftObjectPath`（`CoreUObject/Public/UObject/SoftObjectPath.h`）：本质是 `FTopLevelAssetPath AssetPath + FUtf8String SubPathString`，用字符串描述一个 UObject 的完整路径，不持有对象引用，GC 不感知它。`FSoftObjectPath::IsNull()` 检查是否为空。

- `Engine/Source/Runtime/Engine/Classes/Engine/AssetManager.h`：`UAssetManager::Get()` 是全局单例，包含了一个 `FStreamableManager StreamableManager`（可通过 `UAssetManager::GetStreamableManager()` 访问）。`LoadPrimaryAsset(FPrimaryAssetId, ...)` 是在 `FStreamableManager` 之上封装了 PrimaryAsset 类型注册语义的更高层接口。

### 必做任务

1. 在你的工程中找一个已存在的资产（例如一个 `UStaticMesh` 或 `UTexture2D`），记录它的完整软路径，例如 `/Game/StarterContent/Shapes/Shape_Cube`。

2. 在 Module 里声明一个 `FStreamableManager` 实例（或使用 `UAssetManager::GetStreamableManager()`），以及一个 `TSharedPtr<FStreamableHandle>` 成员，用 `UPROPERTY`-不可用 → 改用 `FGCObject` 或存在 `UCLASS` 成员里保活（见"常见坑"）。

3. 发起异步加载请求：
   ```cpp
   FSoftObjectPath AssetPath(TEXT("/Game/StarterContent/Shapes/Shape_Cube.Shape_Cube"));
   
   StreamableHandle = StreamableManager.RequestAsyncLoad(
       AssetPath,
       FStreamableDelegate::CreateLambda([this]()
       {
           // 此处在 GameThread 上，CompleteDelegate 被延迟触发
           UObject* LoadedObj = StreamableHandle->GetLoadedAsset();
           if (LoadedObj)
           {
               UE_LOG(LogTemp, Log, TEXT("Loaded: %s"), *LoadedObj->GetName());
           }
       }),
       FStreamableManager::DefaultAsyncLoadPriority,
       /*bManageActiveHandle=*/true,  // 让 manager 保活 handle
       /*bStartStalled=*/false,
       TEXT("E3_LoadShapeCube")
   );
   
   // 注意：此处 StreamableHandle 已返回，但加载尚未完成
   UE_LOG(LogTemp, Log, TEXT("Handle returned. HasLoadCompleted: %d"),
       StreamableHandle.IsValid() ? (int)StreamableHandle->HasLoadCompleted() : -1);
   ```

4. 在同一帧的下一 Tick（通过 `FTicker` 或 `TimerManager`），再次查询 `StreamableHandle->HasLoadCompleted()`，观察是否已经加载完毕。

5. 在 `CompleteDelegate` 里验证：
   - `StreamableHandle->HasLoadCompleted()` 返回 `true`
   - `GetLoadedAsset<UStaticMesh>()` 返回非 null（如果资产是 StaticMesh）
   - `GetLoadedAsset<UTexture2D>()` 返回 null（如果资产不是 Texture）

6. 试验 cancel：在 `RequestAsyncLoad` 调用后立即调用 `StreamableHandle->CancelHandle()`，观察 CompleteDelegate 是否还会被调用（答案：不会——cancel 会阻止 complete delegate）。

### 进阶任务

- 用 `FStreamableManager::AsyncLoadHighPriority` 加载同一资产，对比与 `DefaultAsyncLoadPriority` 的加载完成时间（在 Tick 里轮询 `HasLoadCompleted()` 并记录帧数）。
- 将 `bManageActiveHandle = false`，把返回的 `TSharedPtr<FStreamableHandle>` 存在一个会超出作用域的局部变量里——观察 handle 析构后再访问 `GetLoadedAsset()` 会发生什么，理解 handle 生命周期与资产内存保持的关系。
- 使用 `UAssetManager::Get().LoadPrimaryAsset(FPrimaryAssetId(...), {TEXT("UI")})` 加载一个已注册为 Primary Asset 的资产（需先在 `DefaultGame.ini` 的 `[/Script/Engine.AssetManagerSettings]` 里注册 `PrimaryAssetTypesToScan`），体会 AssetManager 在 bundle state 管理上对 StreamableManager 的封装。
- 理解 `bStartStalled = true` 的用途：创建 handle 但不立即发起 I/O 请求，直到手动调用 `StartStalledHandle()`——这允许你"预先描述"一批加载任务，在合适时机再批量启动。

### 验收点

- `RequestAsyncLoad` 返回有效的 `TSharedPtr<FStreamableHandle>`；请求返回后 `HasLoadCompleted()` 为 `false`（除非资产已在内存中）。
- CompleteDelegate 在若干帧后被调用，`GetLoadedAsset<T>()` 返回正确类型的非 null 指针。
- `CancelHandle()` 后 CompleteDelegate 不被调用；`WasCanceled()` 返回 `true`。
- 四固定问题书面回答完整，**必须包含 StreamableHandle ↔ sender 对照表**（见下节）。

### 核心观察：StreamableHandle ↔ sender 惰性对照表

这是本练习最重要的理论输出，要求在你的复盘记录里明确写出：

| FStreamableManager / FStreamableHandle | stdexec sender-receiver | 说明 |
|---|---|---|
| `RequestAsyncLoad(Paths, Delegate)` 返回 `FStreamableHandle` | `auto s = sender_factory(...)` — 构造 sender | 调用的瞬间**仅**创建了描述对象，AsyncLoading2 的 I/O 请求已被提交到内部队列，但资产尚未进内存。类比 sender 构造：描述了工作，scheduler 收到了 token，但 start 尚未被外部显式触发（内部已隐式触发）。|
| `StreamableHandle->GetLoadedAsset()` 在 CompleteDelegate 里调用 | `sync_wait(sender)` 或在 `then` 里取值 | 只有在"加载完成"这个 completion event 发生后，取值才有意义。在 CompleteDelegate 外提前调用 `GetLoadedAsset()` → 返回 null，类比在 sender 完成前 `sync_wait` 超时取空值。|
| `StreamableHandle->CancelHandle()` | `stop_token::request_stop()` | 中止正在进行的加载，阻止 CompleteDelegate 触发。类比 sender 的 stop request：已发出的 I/O 不一定能被回收，但 receiver 的 `set_value` 不会被调用。|
| `RequestAsyncLoad(..., Priority = AsyncLoadHighPriority)` | sender 绑定到高优先级 scheduler | 调度语义：priority 决定了底层 AsyncLoading 线程处理这批 package 的顺序，不改变接口形状，只改变执行顺序。类比把 sender 提交到 thread_pool_scheduler 的高优先级队列。|

**与模块 H 的 RDG ↔ sender 类比形成前后呼应**：RDG 的 `AddPass` 是"纯惰性"（GPU 命令在 `Execute()` 前完全不执行）；StreamableManager 的 `RequestAsyncLoad` 是"半惰性"（磁盘 I/O 已隐式启动，但结果尚未可用）。两者都是"描述工作的对象 + 完成时回调"的模式，但生命周期拥有者不同：RDG 由 `FRDGBuilder` 管理，StreamableManager handle 由调用方（或 manager 内部的 `ManagedActiveHandles`）管理。

### 观察点

**"请求返回后加载尚未完成"的含义**：`RequestAsyncLoad` 内部做的事情是：创建 `FStreamableHandle`，把请求加入 `FStreamableManager` 的 `StreamableItems` 映射，然后调用底层的 `LoadPackageAsync`（最终进入 `AsyncLoading2.cpp` 的队列）。这些都在 GameThread 上同步完成。真正的磁盘读取发生在 AsyncLoading 专用线程（`ALT Thread`，UE 内部称为 Async Loading Thread）。当加载完成时，`FStreamableHandle::CompleteLoad()` 被调用，触发 `CompleteDelegate`——此时已回到 GameThread（via `GameThreadCompletionEvent`）。

**`bManageActiveHandle` 的保活语义**：如果 `bManageActiveHandle = true`，`FStreamableManager` 内部会把 handle 加入 `ManagedActiveHandles` 数组，持有 `TSharedRef`，保证 handle 不会因为调用方忘了保留 `TSharedPtr` 而析构。如果 `false`，调用方必须自己保住 `TSharedPtr<FStreamableHandle>` 的生命，否则 handle 析构时会触发 `ReleaseHandle()`，允许 GC 回收已加载的资产。

**`FStreamableManager` 是 `FGCObject` 而非 `UObject`**：它通过重写 `AddReferencedObjects(FReferenceCollector&)` 手动告诉 GC"我持有这些 UObject，不要回收它们"——这是非 UObject 对象与 GC 系统交互的标准方式（对比 UObject 的 `UPROPERTY` 自动注册）。

**AsyncLoading2 的路径说明**：底层实际执行磁盘加载的代码位于 `Engine/Source/Runtime/CoreUObject/Private/Serialization/AsyncLoading2.cpp`（Cap2 阅读清单第 3 项）。大纲中曾误标为 `Engine/Private/Streaming/AsyncLoading2.cpp`，实际文件在 `CoreUObject` 模块的 Serialization 子目录——这体现了 UE 的架构决策：异步加载是序列化（CoreUObject 职责）而非引擎流送（Engine 职责）的一部分。

### 常见坑

- **`FStreamableHandle` 的 TSharedPtr 不能存在 `UPROPERTY` 里**：`TSharedPtr` 不是 UObject，GC 不管理它。但它内部持有对已加载 UObject 的引用——如果 handle 本身存活（未被 release），它通过 `FStreamableManager::AddReferencedObjects` 间接保活那些 UObject。如果你把 `TSharedPtr<FStreamableHandle>` 存在一个可能比 handle 活得更长的 UObject 的成员变量里，用普通 C++ 成员即可（不需要 `UPROPERTY`）；但如果你把它存在一个普通 `struct` 里，确保 struct 的生命周期覆盖加载完成时刻。
- **在 CompleteDelegate 里访问捕获的 `UObject*`**：CompleteDelegate 在 GameThread 上被调用，但如果你在 lambda 里捕获了一个裸 `UObject*`（比如 `this` 是一个 Actor），在多个 Tick 之后触发时该 Actor 可能已经被 `Destroy()` 或 GC 回收。解决方案：用 `TWeakObjectPtr` 捕获，在 delegate 里先 `IsValid()` 再访问。
- **`GetLoadedAsset()` 返回 null 不一定是加载失败**：如果指定的路径本身就是 null 或路径格式错误（缺少 `.AssetName` 后缀），加载会"成功完成"但资产不存在。`HasLoadCompleted() == true` 且 `GetLoadedAsset() == nullptr` 意味着加载路径有误，不是引擎 bug。
- **`FSoftObjectPath` 路径格式**：完整格式是 `/Package/Path.AssetName`（注意点号分隔包名与资产名）。仅传 `/Package/Path` 不含资产名时会加载整个 package 但 `GetLoadedAsset()` 仍可能为 null。用 `FAssetData::ToSoftObjectPath()` 从 AssetData 转换是最安全的方式。
- **`bStartStalled = true` 后必须手动 `StartStalledHandle()`**，否则资产永远不会开始加载——这是一个静默的"永不完成"陷阱，日志里没有任何报错。

### 提示

- `FStreamableManager` 是非 UObject，可以直接在你的 Module 类里作为成员变量声明：`FStreamableManager StreamableManager;`。也可以直接用 `UAssetManager::GetStreamableManager()`（如果你的工程里有 AssetManager 初始化）。
- `RequestAsyncLoad` 的 `DelegateToCall` 参数支持 lambda：`[this]() { ... }`，也支持 `FStreamableDelegate::CreateUObject(this, &UMyClass::OnLoaded)`。两者都在 GameThread 上被调用。
- 如果你想同步等待加载完成（在非生产代码的调试场景），可以调用 `StreamableHandle->WaitUntilComplete()`——但这会阻塞 GameThread，在真实游戏中不能用于主线程。
- 用 `FStreamableManager::AsyncLoadHighPriority` 做优先级测试时，注意高优先级只是"在 AsyncLoading 队列里排前面"，不保证在当前帧内完成，因为磁盘 I/O 的时间下限由硬件决定。

### 复盘问题

## 做完本模块后你现在应该能说清楚什么

至少把下面几句话说顺：

- **FArchive 双向设计**：`FMemoryWriter` 和 `FMemoryReader` 都是 `FArchive`，同一份 `Serialize(FArchive& Ar)` 代码通过 `Ar.IsSaving()` / `Ar.IsLoading()` 分支，在写方向写入字节，在读方向恢复值——UE 用这个设计避免了写/读代码不对称的 bug。
- **UPackage 的角色**：每个 `.uasset` 文件对应内存里一个 `UPackage` 对象。UObject 通过 Outer 链最终归属某个 Package（`GetOutermost()` 返回 `UPackage*`）。不指定 Outer 的 `NewObject<T>()` 会把对象挂在 `GetTransientPackage()`——这是内存资产与磁盘资产的关键区别。
- **AssetRegistry 是元数据层，不加载资产**：`GetAssetsByClass` / `GetDependencies` / `GetReferencers` 都只操作"目录"，不触发任何磁盘 I/O。AssetRegistry 在 Editor 中是全量异步扫描构建的，在 Cooked 游戏中是 Cook 时写入并在启动时加载的二进制文件。
- **硬引用 vs 软引用的本质**：`TObjectPtr<T>` UPROPERTY 是硬引用——加载持有它的对象时，被引用的对象会被自动一起加载（Linker 的 ImportTable 机制）。`TSoftObjectPtr<T>` / `FSoftObjectPath` 是软引用——只记录路径，不触发加载，需要手动用 `FStreamableManager` 发起异步加载。
- **StreamableHandle 的惰性语义**：`RequestAsyncLoad` 返回 handle 的瞬间，磁盘 I/O 已被提交到 AsyncLoading 队列，但资产不在内存中。`GetLoadedAsset()` 只有在 `HasLoadCompleted() == true` 后才返回有效指针。这与 RDG 的 `AddPass`（纯惰性，GPU 命令在 `Execute()` 前完全不发出）构成"半惰性 vs 全惰性"的有趣对比——两者都是"描述工作 + 完成时回调"的接口形状。
- **AsyncLoading2 的位置修正**：底层异步加载实现位于 `CoreUObject/Private/Serialization/AsyncLoading2.cpp`，不在 `Engine/Private/Streaming/`。这反映了 UE 的架构决策：异步包加载是序列化职责（CoreUObject 层），不是引擎流送职责（Engine 层）。
