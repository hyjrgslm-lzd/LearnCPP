# 04 模块 C：内存、智能指针、委托

## 模块目标

反向引用 `01-心智模型` 的 §4（GC ownership vs C++ ownership）。

模块 C 是本系列第一个包含 **implement-own** 练习的模块。你将从"用 TSharedPtr 管理非 UObject 的生命周期"出发，深入到 UE 内存分配器的分桶机制，最终手写一个能跑通的 multicast delegate 最小实现，并在对比表中读懂它与 `DECLARE_MULTICAST_DELEGATE*` 宏展开物的差距。

做完本模块，你能在任意 UE 代码现场快速回答：

- 这个对象用哪套所有权机制——`TSharedPtr` 路径还是 GC 路径？
- `MakeShared` 节省的那次分配发生在哪里、节省的是什么？
- `FMemory::Malloc` 调用链最终落在哪个分配器上？
- C++ delegate 与 `DYNAMIC_MULTICAST_DELEGATE` 在反射系统中处于完全不同的层，边界在哪里？

**阶梯定位**：use（C1/C2）→ implement-own（C3）。C3 是全套课程中第一道 implement-own 练习，做完后你对 UE delegate 宏展开物的理解会从"我在背宏名"升到"我知道这个宏展开成什么形状的类"。

## 模块完成标准

做完本模块，你至少要能稳定说清楚以下四条（这也是验收线）：

1. `ESPMode::ThreadSafe` 与 `ESPMode::NotThreadSafe` 的实现差异：控制块内的引用计数分别用 `std::atomic<int32>` 和裸 `int32`，前者每次 AddRef/Release 都走原子操作，代价在高并发下可见；后者仅在单线程场合安全。
2. `MakeShared<T>` 比 `MakeShareable(new T)` 少一次堆分配的原因：`MakeShared` 把对象与控制块合并在同一块连续内存里；`MakeShareable` 先分配对象，再分配控制块，控制块持有指向已有对象的指针。
3. C++ delegate（本模块）与 `DYNAMIC_MULTICAST_DELEGATE`（D 模块/蓝图层）的边界：前者是纯 C++ 类型擦除的回调容器，零反射；后者必须配合 `UFUNCTION` 标注、走 UHT 代码生成、可被蓝图绑定和序列化，属于 UObject 反射体系。
4. `FMemory::Malloc` 与 `MallocBinned2` 的关系：`FMemory::Malloc` 是全局入口，最终通过 `GMalloc` 指针派发到当前平台选择的分配器（大多数平台是 `FMallocBinned2`）；Binned2 对小于阈值（`UE_MB2_MAX_SMALL_POOL_SIZE`，默认 32768-16 字节）的分配走分桶池，否则直接走 OS 大页分配。

## 练习 C1：TSharedPtr / TWeakPtr / TUniquePtr 语义

### 目标

建立 UE 智能指针三件套的用法肌肉记忆，并在实际编码中钉死两条规则：不要把 `UObject*` 塞进 `TSharedPtr`，`TSharedPtr` 和 `TObjectPtr` 是两套完全不重叠的所有权空间。

### 前置理解

- 你理解 C++ `std::shared_ptr` 的引用计数语义；本练习的重点不是"能用"，而是"能说清 UE 实现与 STL 实现在线程安全和分配模型上的差异"。
- 已读 `01-心智模型.md` §4（GC ownership vs C++ ownership）：TSharedPtr 管理的是非 UObject 对象，GC 对其一无所知。
- 源码参考：
  - `Engine/Source/Runtime/Core/Public/Templates/SharedPointer.h`（用户侧 API 注释，含 Tips/Limitations）
  - `Engine/Source/Runtime/Core/Public/Templates/SharedPointerInternals.h`（控制块 `TReferenceControllerBase`，两种计数类型的 `if constexpr` 分支）
  - `Engine/Source/Runtime/Core/Public/Templates/UniquePtr.h`（`TUniquePtr<T>` + `TDefaultDelete<T>`）

### 必做任务

1. 创建一个非 UObject 结构体 `FMeshData`（成员：`int32 VertexCount`，`FString Name`），用 `MakeShared<FMeshData>(...)` 创建一个 `TSharedPtr<FMeshData>`。
2. 在控制块层面观察 `ESPMode` 差异：
   - 声明两份指针，一份 `TSharedPtr<FMeshData, ESPMode::ThreadSafe>`，一份 `TSharedPtr<FMeshData, ESPMode::NotThreadSafe>`（默认值即 `NotThreadSafe`）。
   - 打开 `SharedPointerInternals.h`，找到 `TReferenceControllerBase<Mode>` 中 `SharedReferenceCount` 的类型定义：`std::conditional_t<Mode == ESPMode::ThreadSafe, std::atomic<int32>, int32>`。在注释里写出：线程安全版本的每次 AddRef 对应 `++SharedReferenceCount`（MSVC 路径映射到 `_InterlockedIncrement`）；非线程安全版本的 AddRef 是裸 `++`，无 fence。
3. 观察 `MakeShared` vs `MakeShareable` 的分配次数差异：
   - 写一个自定义计数 allocator（或使用 `DECLARE_MEMORY_STAT` + `INC_MEMORY_STAT_BY` 宏观察），分别用 `MakeShared<FMeshData>()` 和 `MakeShareable(new FMeshData())` 构造，在日志里打印"分配发生几次"的自己的理解。
   - 定位 `SharedPointerInternals.h` 中 `TIntrusiveReferenceController` 与普通 `TReferenceController` 的区别：前者把对象和控制块内联在同一个结构体里（`MakeShared` 走此路径），后者只持有对象指针（`MakeShareable` 走此路径）。
4. 演示循环引用场景：
   - 创建 `FNode`（成员 `TSharedPtr<FNode> Next`），形成 A→B→A 的环，观察析构时的内存泄漏（在 UE Editor 下用 `checkf` 或打印计数）。
   - 将 `FNode::Next` 改为 `TWeakPtr<FNode> Next`，演示 `TWeakPtr::Pin()` 的正确用法以及 Pin 返回空时的判断路径。
5. `TUniquePtr<FMeshData>` 的 move 语义演示：
   - 构造 `TUniquePtr<FMeshData> Ptr1`，尝试复制（预期编译失败），改用 `MoveTemp(Ptr1)` 转移，观察转移后 `Ptr1 == nullptr`。

### 进阶任务

- 让 `FMeshData` 继承 `TSharedFromThis<FMeshData>`，在成员函数里调用 `AsShared()` 返回 `TSharedRef<FMeshData>`，观察与直接构造 `TSharedPtr` 的区别（`AsShared()` 不新增控制块，而是共享已有的那个）。
- 尝试把一个 `UObject*` 塞进 `TSharedPtr<UObject>` 并记录编译/链接时或运行时的行为。`SharedPointer.h` 的 Limitations 注释明确写道："Shared pointers are not compatible with Unreal objects (UObject classes)!"——触发这个限制后，理解为什么 UObject 的生命周期由 GC 管而不能交给引用计数。
- 对比 `TObjectPtr<T>` 与 `TSharedPtr<T>`：在 `UPROPERTY` 成员上分别使用两者，观察 Editor 构建中 `TObjectPtr` 的 access barrier 行为（需进入 D 模块时深入，此处只做形状对比）。

### 验收点

- 能用一句话解释 `ESPMode::ThreadSafe` 在控制块层的代价（原子操作 vs 非原子）。
- 能指出 `MakeShared` 节省的分配发生在哪个类型（`TIntrusiveReferenceController` vs `TReferenceController`）。
- 循环引用场景可复现，用 `TWeakPtr` 打破后析构顺序符合预期。
- 能给出"为什么 `TSharedPtr<UObject>` 是错误的"的书面解释（至少两个层面：GC 不可见此引用计数；UObject 由 `NewObject` + GC 管理，析构时机由 GC mark-sweep 决定，不受引用计数影响）。
- `TUniquePtr` 的 move 转移演示可运行。

### 观察点

- `TSharedRef` 与 `TSharedPtr` 的核心差别不在引用计数逻辑，而在"允不允许为 nullptr"：`TSharedRef` 构造时断言非空，所有解引用都无需空检查，是 UE 对"我保证这个对象存在"的类型表达。
- `TWeakPtr::Pin()` 在 `SharedReferenceCount == 0` 时返回空 `TSharedPtr`，这是循环引用安全的核心机制。背后实现：控制块的 `WeakReferenceCount` 在所有强引用归零后仍保持存活，直到最后一个 `TWeakPtr` 也销毁，控制块才真正释放。
- `TSharedFromThis` 的正确使用前提是对象必须已经被某个 `TSharedPtr`/`TSharedRef` 持有；在纯栈对象上调用 `AsShared()` 会触发断言失败。
- `TSharedPtr` 与 `TObjectPtr` 处于完全不重叠的所有权空间：前者管理堆上的非 UObject 对象，后者是 GC 路径上 `UPROPERTY` 成员的推荐包装。两者不需要也不应该互相转换。

### 常见坑

- **把 `UObject*` 塞进 `TSharedPtr`**：是 UE 最典型的内存安全误用。GC 不知道 `TSharedPtr` 控制块的存在；当 GC 决定回收该对象时，`TSharedPtr` 里的引用计数对 GC 不可见，不会阻止回收。回收后 `TSharedPtr` 持有悬空指针，解引用是 UB。
- **在多线程代码里忘记 `ESPMode::ThreadSafe`**：默认的 `NotThreadSafe` 模式下并发修改引用计数会发生 data race。在任何跨线程持有的共享指针上必须显式选择 `ThreadSafe` 模式。
- **循环引用导致的隐形内存泄漏**：UE 的 `TSharedPtr` 没有弱引用自动探测，程序员需要主动识别环并用 `TWeakPtr` 打破。在含有"父子互持"或"观察者反向引用"的数据结构中这是最常见的坑。
- **在栈对象上调用 `AsShared()`**：`TSharedFromThis` 的控制块在首次 `TSharedPtr` 指向该对象时设置；如果对象在栈上，`AsShared()` 会因找不到有效控制块而断言失败。

### 提示

- `SharedPointerInternals.h` 中的 `TReferenceControllerBase<Mode>` 是理解线程安全代价的最直接入口，重点看 `AddSharedReference()`/`ReleaseSharedReference()` 在两种 `constexpr if` 分支下的代码路径。
- `MakeShared` 走 `TIntrusiveReferenceController`，后者用 `TypeCompatibleBytes<ObjectType>` 内联存储对象内容，整个结构体只 `new` 一次。
- 在 Editor 构建中，UE 会在 `TSharedPtr` 的各种转换路径上插入检查宏（`checkf(IsValid(), ...)`），便于调试；在 Shipping 构建中这些检查被移除。

### 复盘问题

- **Q1：执行真正开始时刻？** 本题的对象创建（`MakeShared`/`new`）发生在调用点的当前线程（通常是 GameThread）；`TSharedPtr` 析构发生在最后一个持有者的析构点，没有特定线程约束（这正是 `ThreadSafe` 模式必要的原因）。
- **Q2：生命周期拥有者？** `TSharedPtr` 引用计数——最后一个持有者（强引用）归零时析构；控制块额外存活直到所有弱引用也归零。
- **Q3：涉及哪些 Named Thread？** 本题全在 GameThread；如果在多线程场合共享（例如传给 TaskGraph worker），需 `ESPMode::ThreadSafe`；GC 线程不参与 `TSharedPtr` 的引用计数（GC 与 `TSharedPtr` 体系完全正交）。
- **Q4：涉及 UObject 时怎么对 GC 可见？** 本练习中的 `FMeshData` 是普通 C++ 结构体，**不是 UObject**，不参与 GC 体系——这是 C++ 所有权路径的完整示例。如果要在 `FMeshData` 里存一个 `UObject*`，该指针 GC 不可见（进阶坑），需要改成 `TObjectPtr` 并加 `UPROPERTY`（那就要把 `FMeshData` 改成 `USTRUCT` 或 `UObject` 子类）。

## 练习 C2：FMemory / Allocator / LLM

### 目标

理解 `FMemory::Malloc` 这条调用链从全局入口到分桶策略的完整路径；掌握 `TInlineAllocator` 在 `TArray` 上的用法；用 `LLM_SCOPE` 和控制台命令观察内存分类统计。

### 前置理解

- 已理解 `std::allocator` 的基本机制；本题的重点是 UE 在此之上的分层结构。
- 源码参考：
  - `Engine/Source/Runtime/Core/Public/HAL/MemoryBase.h`（`FMalloc` 基类，`GMalloc` 全局指针声明；注意 UE5.6 起 `GMalloc` 在 `UE::Private` 命名空间下，裸 `GMalloc` 被 `UE_DEPRECATED(5.6, ...)` 标记，应通过 `FMemory::Malloc` 调用）
  - `Engine/Source/Runtime/Core/Public/HAL/MallocBinned.h`（Binned 初代；主要用于了解 Binned 概念，实际平台多用 Binned2）
  - `Engine/Source/Runtime/Core/Public/HAL/MallocBinned2.h`（主力分配器；`UE_MB2_MAX_SMALL_POOL_SIZE`、`UE_MB2_SMALL_POOL_COUNT`、`UE_MB2_LARGE_ALLOC` 三个宏是关键数字）
  - `Engine/Source/Runtime/Core/Public/HAL/LowLevelMemTracker.h`（`LLM_SCOPE`、`LLM_SCOPE_BYNAME`、`ENABLE_LOW_LEVEL_MEM_TRACKER` 宏定义结构）

### 必做任务

1. 追踪 `FMemory::Malloc` 调用链：
   - 在代码里写 `void* Ptr = FMemory::Malloc(64);` 然后 `FMemory::Free(Ptr)`，用 IDE 的"跳转到定义"追到 `UnrealMemory.h`，再追到 `GMalloc->Malloc(Size, Alignment)`，理解 `FMemory` 是 `GMalloc` 的薄包装（外加 LLM 追踪和 AutoRTFM 支持）。
2. 观察 `FMallocBinned2` 的分桶策略：
   - 打开 `MallocBinned2.h`，记录三个关键宏的值（默认非 `AGGRESSIVE_MEMORY_SAVING` 路径）：
     - `UE_MB2_MAX_SMALL_POOL_SIZE`：`32768 - 16 = 32752` 字节（小于此大小走分桶）
     - `UE_MB2_SMALL_POOL_COUNT`：51 个桶
     - `UE_MB2_LARGE_ALLOC`：65536 字节（OS 页分配的对齐单位）
   - 在注释里写出分桶逻辑的核心思路：小于 `UE_MB2_MAX_SMALL_POOL_SIZE` 的分配，按大小向上对齐到最近的桶边界，在预分配的内存池页中找空闲块；等于或大于阈值的分配直接走 OS 虚拟内存页（对齐到 `UE_MB2_LARGE_ALLOC`）。
   - 简述 Binned vs Binned2 的关键差异：Binned（初代）使用固定大小的全局自旋锁（`USE_COARSE_GRAIN_LOCKS` 路径），并发性较差；Binned2 引入每池细粒度锁（`USE_FINE_GRAIN_LOCKS`）和 per-thread cache，减少锁争用，是 UE4 末期到 UE5 的默认选择。Binned3（`MallocBinned3.h`）进一步为 64 位平台优化了内存布局，避免元数据/对象数据的 false sharing。
3. 在 `TArray` 上使用 `TInlineAllocator`：
   - 声明 `TArray<FVector, TInlineAllocator<8>> SmallVerts`，添加 8 个顶点，观察无堆分配发生；添加第 9 个时触发堆分配。
   - 对比 `TArray<FVector>` 的"总是堆分配"路径与 `TInlineAllocator<N>` 的"栈内联，溢出才堆分配"路径，写出各自适用场景（小而数量固定的容器首选 InlineAllocator）。
4. 使用 `INC_MEMORY_STAT_BY` 观察自定义统计：
   - 声明一个内存统计宏：`DECLARE_MEMORY_STAT(TEXT("MyPlugin Memory"), STAT_MyPluginMemory, STATGROUP_Memory)`
   - 在自定义分配点写 `INC_MEMORY_STAT_BY(STAT_MyPluginMemory, AllocSize)` / `DEC_MEMORY_STAT_BY(STAT_MyPluginMemory, AllocSize)`，在 Editor 的 `stat Memory` 视图里观察该项目的变化。

### 进阶任务

- 用 `LLM_SCOPE(ELLMTag::Meshes)` 包裹一段分配，然后在 Editor 控制台执行 `stat LLMFULL`，观察"Meshes"类目的内存占用变化。注意 `ENABLE_LOW_LEVEL_MEM_TRACKER` 在非 Shipping 构建下默认开启。
- 尝试 `LLM_SCOPE_BYNAME(TEXT("MyCustomTag"))` 定义自定义标签，观察它出现在 `stat LLMFULL` 的哪个类目下。
- 阅读 `LowLevelMemTracker.h` 顶部的宏守卫逻辑（`ENABLE_LOW_LEVEL_MEM_TRACKER = LLM_ENABLED_IN_CONFIG && PLATFORM_SUPPORTS_LLM`）——在 Shipping 构建中 LLM 通常被关闭（`LLM_ENABLED_IN_CONFIG=0`），理解这对内存分析工作流的含义。

### 验收点

- 能画出 `FMemory::Malloc(N)` → `GMalloc->Malloc(N, Alignment)` → `FMallocBinned2::Malloc(N, Alignment)` 的简短调用图。
- 能说出 Binned2 下小分配（< 32752 字节）走池，大分配（≥ 65536 字节）走 OS 的规则，以及 51 个桶的作用（减少内碎片：分配大小向上对齐到最近的桶边界）。
- `TInlineAllocator<8>` 示例跑通，8 个元素无堆分配、第 9 个触发分配的行为可通过注释或日志说明。
- `INC_MEMORY_STAT_BY` 宏在 `stat Memory` 面板可见。

### 观察点

- `FMemory` 并非一个类的实例，而是一组静态方法的命名空间（`struct FMemory` with `static` functions）。它的价值在于把 LLM 追踪、AutoRTFM 事务支持和 `GMalloc` 派发统一封装，调用方无需手动处理这三层。
- Binned 分配器的"桶"本质是大小类（size class）：同一个大小类的分配物共享一个内存页池，分配时只需从链表摘头，Free 时挂回链表——这是为何 Binned 分配器对小对象的 Malloc/Free 比 `malloc(3)` 更快的关键。
- `TInlineAllocator` 是 UE 容器分配器定制化机制的一部分。`TArray<T, Alloc>` 的第二个模板参数可以是任意满足 UE allocator 概念的类型；`TFixedAllocator<N>` 则是硬限容量版本（超出 N 个元素时断言失败而非扩容）。
- LLM 是运行时内存分类统计工具，不是调试用途的 sanitizer。它的代价是每次分配时维护一个"当前 scope 的 tag"，写入分配元数据。关闭 LLM（Shipping 默认）后这个元数据不存在，`stat LLMFULL` 命令也不产生输出。

### 常见坑

- **UE5.6+ 后直接用裸 `GMalloc`**：`MemoryBase.h` 中裸 `GMalloc` 被标记 `UE_DEPRECATED(5.6, ...)` 并移入 `UE::Private` 命名空间。新代码应始终用 `FMemory::Malloc/Free` 而非直接访问 `GMalloc`。
- **在 Shipping 构建中依赖 `INC_MEMORY_STAT_BY` 统计结果**：Stats 系统在 Shipping 构建中默认被剥离（`STATS=0`），相关宏展开为空操作，不要把统计结果用于 Shipping 逻辑。
- **TInlineAllocator 用于大元素**：`TInlineAllocator<N>` 的内联存储在栈上，`N * sizeof(T)` 字节会占用栈帧。对大型结构体（如包含大数组的类）滥用 `TInlineAllocator` 会导致栈溢出。
- **LLM_SCOPE 的范围不匹配**：`LLM_SCOPE` 是 RAII 对象，生命周期内的所有分配都被归入该标签。如果在异步任务或跨帧代码里错误使用，统计会归错类别。

### 提示

- `FMemory.h`（`Engine/Source/Runtime/Core/Public/HAL/UnrealMemory.h`）是 `FMemory` 所在头文件，用 Glob 搜索 `FMemory::Malloc` 的实现时应找 `UnrealMemory.h`，而不是 `MemoryBase.h`（后者只含 `FMalloc` 基类定义）。
- Binned2 的桶边界表在 `MallocBinned2.cpp` 中的 `SmallBinSizesInternal` 数组里，共 51 项，从 16 字节到 32752 字节，间隔非均匀（小区间密，大区间稀），这是减少碎片与内存开销的权衡。
- `stat LLMFULL` 要求启动参数加 `-llm`（或在 `DefaultEngine.ini` 里配置），否则 LLM 即使编译进去也不会追踪。

### 复盘问题

- **Q1：执行真正开始时刻？** `FMemory::Malloc` 在调用点的当前线程执行；分配器内部可能持锁（细粒度池锁），所以并发调用是安全的但存在竞争。
- **Q2：生命周期拥有者？** 原始内存的生命周期拥有者是调用 `FMemory::Free` 的代码——`FMemory::Malloc/Free` 是手动内存管理，没有 RAII 保证；`TUniquePtr`/`TSharedPtr` 在析构时调用 `delete`（最终走 `operator delete` → `FMemory::Free`），才把 RAII 层叠在分配之上。
- **Q3：涉及哪些 Named Thread？** 分配器本身线程安全（Binned2 有锁），可以在任意线程调用；LLM tag 的追踪是线程局部的（TLS 存储当前 scope），跨线程传递对象时 LLM 标签不跟随对象。
- **Q4：涉及 UObject 时怎么对 GC 可见？** 本题不涉及 UObject，是纯 C++ 分配路径。UObject 的分配通过 `NewObject<T>` 走 `UClass::CreateDefaultSubobject` → UObject 专属分配路径，底层也会经过 `FMemory::Malloc`，但对象注册到 GUObjectArray 这一步与 `FMemory` 层无关。

## 练习 C3：手写最小 multicast delegate（implement-own）

### 目标

这是本模块的 implement-own 练习，也是全套课程中**第一道 implement-own**。你将从零手写一个 `TMulticastDelegate<void(int)>` 的最小实现，支持 `AddLambda`/`Remove`/`Broadcast`，并通过与 UE 源码宏展开物的对比表，理解工业级实现在哪些维度比你的 mini 版本复杂。

做完之后你对"调用 `DECLARE_MULTICAST_DELEGATE_OneParam` 之后展开成什么"有基于源码的清晰图景，而不再只是背宏名。

### 前置理解

- 你理解 C++ 函数指针与 `std::function` 的类型擦除机制；UE delegate 的核心也是类型擦除，但以句柄（Handle）管理绑定，而非裸 `std::function`。
- 了解 `DECLARE_MULTICAST_DELEGATE_OneParam` 等宏的调用形态（不需要理解展开物，这是本题的学习目标）。
- 明确 C++ delegate（本题）与 `DYNAMIC_MULTICAST_DELEGATE`（反射层）的边界：
  - `DECLARE_MULTICAST_DELEGATE*`：纯 C++ 类型擦除，不依赖 UHT，不可被蓝图直接绑定，不可序列化，**不是 `UPROPERTY` 类型**。
  - `DECLARE_DYNAMIC_MULTICAST_DELEGATE*`：必须配合 `UFUNCTION` 标注，UHT 为其生成反射元数据，可被蓝图绑定、序列化到磁盘，作为 `UPROPERTY` 存在于 UObject 中。属于模块 D 的内容范围（反射/UObject 体系）。
- 源码参考：
  - `Engine/Source/Runtime/Core/Public/Delegates/DelegateCombinations.h`（宏的声明形状，`DECLARE_MULTICAST_DELEGATE_OneParam` 的形参结构）
  - `Engine/Source/Runtime/Core/Public/Delegates/Delegate.h`（C++ delegate 系统的完整文档注释，理解 payload 变量、binding 选项、动态委托区别）

### 必做任务

1. **定义句柄类型**：声明 `FDelegateHandle`（仅包含一个 `uint64 ID`，构造时从静态计数器递增生成唯一 ID；`ID == 0` 表示无效句柄）。

2. **定义绑定条目类型**：声明 `FBinding`：

   ```cpp
   struct FBinding {
       FDelegateHandle Handle;
       TFunction<void(int)> Func;  // UE 的 TFunction 类似 std::function
   };
   ```

3. **声明 `TMyMulticastDelegate<void(int)>`**（非线程安全，不支持 Remove-during-Broadcast）：

   ```cpp
   class FMyIntDelegate {
   public:
       FDelegateHandle AddLambda(TFunction<void(int)> Lambda);
       void Remove(FDelegateHandle Handle);
       void Broadcast(int Value);
   private:
       TArray<FBinding> Bindings;
   };
   ```

4. **实现 `AddLambda`**：生成新句柄，创建 `FBinding`，追加到 `Bindings`，返回句柄。

5. **实现 `Remove`**：用 `Bindings.RemoveAll(...)` 或线性查找，按 `Handle.ID` 删除对应条目。

6. **实现 `Broadcast`**：遍历 `Bindings`，对每个 `Func` 调用 `Func(Value)`。注意：不要在遍历中删除，防止迭代器失效（进阶才处理 Remove-during-Broadcast）。

7. **验证**：

   ```cpp
   FMyIntDelegate D;
   FDelegateHandle H1 = D.AddLambda([](int X){ UE_LOG(LogTemp, Log, TEXT("H1: %d"), X); });
   FDelegateHandle H2 = D.AddLambda([](int X){ UE_LOG(LogTemp, Log, TEXT("H2: %d"), X); });
   D.Broadcast(42);   // 期望：H1: 42, H2: 42
   D.Remove(H1);
   D.Broadcast(7);    // 期望：仅 H2: 7
   ```

8. **填写差异对比表**（见下文"UE 展开物对比表"，必须完成至少 4 行）。

### 进阶任务

- **添加单播 `TMyDelegate` 版本**：支持 `BindLambda`（覆盖之前的绑定）/`Execute(int)`/`IsBound()`，对应 UE 的 `DECLARE_DELEGATE_OneParam`。
- **支持 payload**：把 `FBinding` 的 `Func` 改为 `TFunction<void(int, float)>`，在 `AddLambda` 时传入捕获一个 `float Payload` 的 lambda，在 `Broadcast(int Value)` 内部调用时自动附加 payload（不修改 `Broadcast` 签名，使 payload 对调用方透明）。这是 UE delegate 的 payload 机制的最小复刻。
- **Remove-during-Broadcast 防护**：用"延迟删除"模式：Broadcast 期间把要删除的句柄记录进 `PendingRemove` 列表，Broadcast 结束后再真正移除。

### 验收点

- `AddLambda`/`Remove`/`Broadcast` 三个接口功能正确（可用 C3 验证代码跑通）。
- `FDelegateHandle` 的 ID 唯一性有保证（静态计数器，不能复用已删除的 ID）。
- 对比表至少 4 行，每行内容准确（见下文）。
- 能书面说明"为什么不能把 `DYNAMIC_MULTICAST_DELEGATE` 视为本题实现的扩展版"（原因：两者的绑定目标不同——C++ delegate 绑 `TFunction`，dynamic delegate 绑 `UFunction` 反射对象，依赖 UHT 代码生成，完全不同的机制层）。
- 单播进阶版的 `Execute()` 在未绑定时断言失败，`IsBound()` 能正确返回 `false`。

### mini delegate 与 UE 源码展开物对比表

这是本练习的必答内容。完成实现后，对照 `Delegate.h` 和 `DelegateCombinations.h` 填写下表（**至少 4 行**）：

| 维度 | 你的 mini 实现 | UE `DECLARE_MULTICAST_DELEGATE_OneParam` 展开物 |
|---|---|---|
| **类型擦除机制** | `TFunction<void(int)>`（内部用 `std::function`-like 堆分配） | 自定义 `IDelegateInstance` 虚接口 + per-binding 堆分配；避免 `std::function` 的双重间接 |
| **句柄管理** | `uint64` ID，线性扫描 `TArray<FBinding>` | `FDelegateHandle`（同为 uint64 ID），内部用侵入式双链表（`FDelegateBase`）；Remove 是 O(1) 而非 O(n) |
| **Remove-during-Broadcast** | 不支持（遍历中删除 = 迭代器失效） | 使用内部"压缩"机制：广播期间被 Remove 的条目标记无效，广播结束后 compaction；广播是可重入的 |
| **线程安全** | 完全不线程安全 | `DECLARE_TS_MULTICAST_DELEGATE*` 系列（Thread-Safe 版本）用细粒度锁保护绑定列表 |
| **payload 支持** | 需要手动在 lambda 捕获列表里塞 payload | 原生支持最多 4 个额外 payload 变量，在 `Bind*/Add*` 时传入，广播时自动附加到函数参数末尾，类型安全 |
| **与蓝图/反射的关系** | 零反射，`UHT` 不知道此类型存在 | `DECLARE_DYNAMIC_MULTICAST_DELEGATE*` 才是反射层；本表所指的 `DECLARE_MULTICAST_DELEGATE*` 同样是纯 C++，与你的 mini 版本在反射上处于同一层（**都不可被蓝图直接绑定**） |

**对比表的关键结论**：UE 的 `DECLARE_MULTICAST_DELEGATE*` 在接口语义上与你的 mini 版本相同（AddLambda/Remove/Broadcast），在实现上的主要差距是：侵入式链表 O(1) Remove、广播可重入的延迟删除、原生 payload 支持。这些差距都是为了工程可靠性，不是核心概念上的质变。把这条对比表背下来，你就能在看到任意 UE delegate 宏时立刻推理出它的内部行为。

### 观察点

- UE `TFunction`（`Engine/Source/Runtime/Core/Public/Templates/Function.h`）是 UE 版的 `std::function`，支持 small buffer optimization（小 functor 内联存储，避免堆分配）。你的 mini 实现如果直接用 `TFunction<void(int)>` 来存绑定，已经获得了这个优化。
- `IDelegateInstance` 是 UE delegate 系统的内部类型擦除接口，定义了 `Execute`/`ExecuteIfSafe`/`IsSafeToExecute`/`GetHandle` 等虚方法。每个绑定条目（member function、lambda、static function、shared pointer method 等）都是一个实现此接口的具体类。这套设计比 `TFunction` 更重，但支持了"绑定对象是否还活着"的弱引用检查（对 shared pointer 绑定和 UObject weak 绑定特别重要）。
- `DECLARE_MULTICAST_DELEGATE_OneParam(FMyDelegate, int32)` 展开后会生成一个继承自 `TMulticastDelegate<void(int32)>` 的类 `FMyDelegate`，其核心方法是 `AddLambda`/`AddUObject`/`AddStatic`/`AddWeakLambda`/`Remove`/`Broadcast`——你的 mini 版本只实现了 `AddLambda` + `Remove` + `Broadcast` 这个子集。
- 区分 `Broadcast()` 和 `ExecuteIfBound()`：`Broadcast` 用于 multicast（调用所有绑定），`Execute` 用于单播（调用唯一绑定，未绑定时断言失败），`ExecuteIfBound` 用于单播但允许未绑定（静默跳过）。

### 常见坑

- **在 `Broadcast` 中途 `Remove`**：你的 mini 版本用 `TArray` 线性遍历，在遍历中 `Remove` 会触发 `TArray` 的迭代器失效（元素移位），产生跳过或重复调用。进阶任务的延迟删除是修复此问题的标准模式。
- **误以为 `DECLARE_DYNAMIC_MULTICAST_DELEGATE` 是 `DECLARE_MULTICAST_DELEGATE` 的超集**：两者不是继承关系。Dynamic 版本绑定的目标是 `UFunction`（UHT 生成的反射函数对象），绑定语法（`AddDynamic` 宏）完全不同，序列化到磁盘的内容是函数名字符串而不是函数指针。在不需要蓝图可见性的场合，`DECLARE_DYNAMIC_MULTICAST_DELEGATE` 比 `DECLARE_MULTICAST_DELEGATE` 有额外开销，不应滥用。
- **句柄 ID 不保证唯一性（静态计数器溢出）**：生产代码里 UE 用 `uint64` 计数，在任何合理的程序运行周期内不会溢出；你的 mini 实现也应使用 `uint64` 而非 `int32`，避免理论上的 ID 复用问题。
- **共享同一 `FDelegateHandle` 给多处 Remove**：`Remove` 是幂等的（删除不存在的 Handle 静默成功），但如果你误把同一 Handle 同时存在两个容器里，第一次 Remove 删掉绑定，第二次 Remove 什么也不做（这通常是你想要的行为）。

### 提示

- 先把三个接口跑通，再考虑进阶的 payload 和 Remove-during-Broadcast 防护。implement-own 的价值不在于复刻工业级全功能，而在于亲手走一遍类型擦除 + 句柄管理的设计路径。
- `TFunction` 在 UE 中的声明在 `Engine/Source/Runtime/Core/Public/Templates/Function.h`，它的 small buffer size 默认是 32 字节（可查 `TFunction_OwnedObject` 的实现）；超过 32 字节的 functor 会堆分配。你的 lambda 如果捕获大量数据，记住这个边界。
- 做完 mini 实现后，在 IDE 中对 `DECLARE_MULTICAST_DELEGATE_OneParam(FMyRealDelegate, int32)` 手动展开（GCC/Clang 下用 `-E`，MSVC 下用 `/P`），与你的 mini 版本的类结构对照，这是理解 UE delegate 宏最直接的方式。

### 复盘问题

- **Q1：执行真正开始时刻？** `Broadcast(Value)` 调用时，在当前线程同步地遍历所有绑定并逐一调用。没有延迟、没有任务队列投递，这是 C++ delegate 的关键特征——"调用即执行"，与 `ENQUEUE_RENDER_COMMAND` 的延迟语义截然不同。
- **Q2：生命周期拥有者？** `FMyIntDelegate` 实例的生命周期由其宿主对象管理（通常是包含它的 C++ 对象或 UObject 成员）。每个 `FBinding` 的 `TFunction` 捕获的 lambda 闭包，其生命周期由引用计数（如果捕获了 `TSharedPtr`）或用户保证（如果捕获了裸引用）决定——**这是 C++ delegate 最大的生命周期陷阱来源**：绑定的 lambda 比 delegate 活得短，Broadcast 时出现悬空。
- **Q3：涉及哪些 Named Thread？** 本题全在 GameThread（或调用 `Broadcast` 的任意线程）；`DECLARE_TS_MULTICAST_DELEGATE*` 才是多线程安全版本，你的 mini 版本不线程安全。
- **Q4：涉及 UObject 时怎么对 GC 可见？** 本题不涉及 UObject。如果 lambda 捕获了 `UObject*`，GC **不可见**该引用，对象可能在 `Broadcast` 前被 GC 回收。正确做法是在 `AddWeakLambda` 风格中持有 `TWeakObjectPtr`，在 Broadcast 时先 `IsValid()` 检查再调用。这就是 UE 真正的 `AddUObject` / `AddWeakLambda` 存在的原因。

## 做完本模块后你应该能说清楚什么

至少把下面几句话说顺：

- `TSharedPtr<T, ESPMode::ThreadSafe>` 的控制块用 `std::atomic<int32>` 计数；`NotThreadSafe` 用裸 `int32`。跨线程持有共享指针必须选 `ThreadSafe`，但在单线程场合 `ThreadSafe` 有不必要的原子操作开销。
- `MakeShared<T>` 把对象和控制块合并成一次分配（`TIntrusiveReferenceController`）；`MakeShareable(new T)` 先分配对象再分配控制块，两次分配。优先使用 `MakeShared`。
- `TSharedPtr` 与 GC 完全正交：`TSharedPtr` 管理的对象不走 GC 路径；UObject 不走 `TSharedPtr` 路径。把两者混用是最典型的内存安全错误来源。
- `FMemory::Malloc` 是全局统一分配入口，最终派发到 `FMallocBinned2`（大多数平台）：小分配走分桶池，大分配走 OS 页。
- C++ delegate（`DECLARE_MULTICAST_DELEGATE*`）是类型擦除的 C++ 回调容器，零 UHT/GC 参与；`DECLARE_DYNAMIC_MULTICAST_DELEGATE*` 才是反射/蓝图层的委托，两者边界明确不可混淆。
