# 01 心智模型

## 为什么先讲心智模型

如果你一上来就找 `UCLASS`、`UPROPERTY`、`FRDGBuilder` 这些 API 的用法，你很容易陷入三个误区：

- 误把 UHT 宏当成普通 C++ attribute，不理解为什么编译器之前还要跑一遍"别的工具"。
- 误把 `UObject*` 当成普通裸指针，写出 GC 看不见的引用，然后迷惑地看着对象被踢掉。
- 误把 `ENQUEUE_RENDER_COMMAND` 当成"另一种线程池投递"，然后在 lambda 里捕获引用，在 RenderThread 侧读到垃圾。

这三个误区不是 API 没背熟，而是心智模型没建立。在开始写任何代码之前，先把 UE 引擎内核里和纯 C++ 经验差距最大的几个结构性转变钉牢。

本文件共 6 个 mindset shift，没有代码练习。做完后建议回答末尾的 10 道自测题，确认每一条心智转变都真正理解了，再进入模块 A。

## Mindset Shift 1：Module-first，不是 File-first

在纯 C++ 工程里，"一份代码"的最小单位是文件（`.cpp` / `.h`）。你可以随意 `#include`，只要链接器找得到符号就能编。

UE 不是这样工作的。**在 UE 里，代码的最小可部署单位是 Module**。

每个 Module 有一个 `.Build.cs` 文件（C# 脚本，由 UBT 解释），声明这个 Module 依赖哪些其他 Module、对外暴露哪些头文件目录、在哪个 LoadingPhase 被装载。`IModuleInterface` 的实现类（通过 `IMPLEMENT_MODULE` 宏注册）是这个 Module 的入口点，相当于一个带有生命周期钩子的 DLL 入口。

这产生了几个在纯 C++ 经验里没有类比的概念：

**LoadingPhase** 决定 Module 在引擎启动序列的哪个阶段被加载。`Default` 是最常见的，`PostConfigInit` 比 `Default` 早（在配置文件读取之后、其他大多数 Module 初始化之前），`PostEngineInit` 则在引擎完全初始化之后。如果你的 Module A 依赖 Module B 的初始化结果，必须确保 B 的 LoadingPhase 早于 A，否则 A 的 `StartupModule` 里去找 B 提供的对象时会扑空。

**依赖声明是强制的**。你的代码用了 `TArray`，你的 `.Build.cs` 里就必须有 `"Core"` 在 `PublicDependencyModuleNames` 或 `PrivateDependencyModuleNames` 里。UBT 不允许隐式的跨 Module 符号引用——如果你直接 `#include` 了另一个 Module 的头文件但没在 `.Build.cs` 里声明，UBT 要么报错，要么生成一个不可重现的链接依赖，在某些平台上悄悄失败。

**Public 与 Private 头文件的边界是真实的**。放在 `Public/` 的头文件可以被依赖方看见；放在 `Private/` 的只在本 Module 内可见。这是 C++ 里 `include path` 管理在引擎层面的强制化版本。

**对习惯纯 C++ 的人，最直接的影响是**：你在开新文件之前，先想的问题不是"我要建哪个类"，而是"这个类属于哪个 Module，这个 Module 依赖什么"。文件从属 Module，Module 从属工程。这个顺序不能倒。

源码参考：`Engine/Source/Runtime/Core/Public/Modules/ModuleInterface.h`（`IModuleInterface` 定义，`StartupModule`/`ShutdownModule` 两个虚函数），`Engine/Source/Runtime/Core/Private/Modules/ModuleManager.cpp`（`FModuleManager` 的加载流程）。

## Mindset Shift 2：Reflection before types——UHT 在编译器之前跑

C++ 模板给了你编译期类型计算的能力，但它没给你"在运行时枚举一个类有哪些字段，字段的名字、类型、默认值分别是什么"的能力。UE 需要这个能力，因为编辑器属性面板、蓝图、网络 replication、序列化都建立在运行时反射之上。

UE 的解决方案是 **UnrealHeaderTool（UHT）**：一个在 C++ 编译器之前运行的预处理器，读取你的头文件，解析 `UCLASS()`、`UPROPERTY()`、`UFUNCTION()` 等宏，然后为每个被标注的类生成 `.generated.h` 和 `<ClassName>.gen.cpp`。

这产生了一个在纯 C++ 经验里不存在的构建顺序：

```
你的 .h 文件（含宏）
    ↓ UHT 读取并解析宏标注
    ↓ 生成 <ClassName>.generated.h
    ↓ 生成 <ClassName>.gen.cpp（注册反射元数据）
    ↓ C++ 编译器处理你的 .h + .generated.h
    ↓ 链接
```

这意味着：

**`#include "MyClass.generated.h"` 必须是头文件的最后一个 `#include`**。这条规则来自 UHT 的 include 顺序要求，不是风格建议。

**`.generated.h` 里有什么**？它包含 `GENERATED_BODY()` 宏展开所需的内容——包括反射元数据的静态注册调用、`StaticClass()` 的声明、序列化函数的前向声明等。模块 D 的第一道练习要求你亲手打开并读懂 `.generated.h` 的内容，因为只有这样你才能真正理解"UHT 做了什么，以及为什么必须这么做"。

**UHT 的限制**：UHT 不是完整的 C++ 解析器，它只解析宏标注行和类声明的结构，不理解模板特化、运算符重载、`constexpr if` 等复杂 C++ 语法。这就是为什么 `UCLASS`/`UPROPERTY` 有一套有限的语法规则（例如 `UFUNCTION` 不能有默认参数的所有组合），违反这些规则会在 UHT 阶段报错，和 C++ 编译器的错误完全是两个层次的东西。

**从 stdexec 视角理解这一转变**：在 Execution_Study 里，你习惯了"类型在编译期完整存在"。UE 在此之上叠加了"类型在运行时也可以被枚举和查询"的能力——代价是引入了 UHT 这个编译期工具链额外步骤。这不是 C++ 标准的一部分，而是 UE 工程决策的结果。

源码参考：`Engine/Source/Runtime/CoreUObject/Public/UObject/Object.h`（`UObject` 基类，`StaticClass()` 声明），任意 `UCLASS` 标注的类头文件旁边的 `.generated.h`（IDE 生成目录下可找到）。

## Mindset Shift 3：Game/Render/RHI thread 分线是一等公民

纯 C++ 多线程编程里，线程通常是"资源"——你创建它，等它干活，销毁它。线程模型是你的业务逻辑之外的一层基础设施。

UE 不是这样。**GameThread、RenderThread、RHIThread 是引擎内核的一等公民，它们有严格的职责边界，数据不能随意跨线程共享。**

三条主干线程的职责划分：

- **GameThread**：所有游戏逻辑运行在这里。`BeginPlay`、`Tick`、`EndPlay`、输入处理、AI、物理结果查询——一切 Actor 和 Component 的逻辑代码，默认在 GameThread 上调用。`UObject` 的大多数成员函数都假设在 GameThread 上被调用。
- **RenderThread**：渲染命令的录制和场景更新在这里。`FSceneRenderer::Render`、RDG 的构建（`FRDGBuilder::AddPass`）、场景代理（`FPrimitiveSceneProxy`）的更新——这些都在 RenderThread 上执行。RenderThread 通常比 GameThread 滞后一帧。
- **RHIThread**：GPU 命令的实际提交在这里。`FRHICommandList` 的录制结果最终被 RHIThread 提交给 GPU 驱动层。在某些平台/配置上 RHIThread 可以被禁用（命令在 RenderThread 上直接提交），但代码应该按 RHIThread 存在的假设来写。

**跨线程通信的唯一安全方式**（对 GameThread→RenderThread）是 `ENQUEUE_RENDER_COMMAND`：

```cpp
// GameThread 侧
FMyData DataCopy = MyData;  // 按值复制，不捕获引用
ENQUEUE_RENDER_COMMAND(MyRenderCmd)(
    [DataCopy](FRHICommandListImmediate& RHICmdList)
    {
        // RenderThread 侧执行
        // DataCopy 是值，完全安全
    });
```

**为什么 lambda 必须按值捕获**？因为 lambda 在 GameThread 上构造，但在 RenderThread 上异步执行。构造时的 GameThread 栈已经销毁，任何捕获的引用或指针都已经悬空。如果你捕获了一个 `UObject*`，等到 RenderThread 执行时，GC 可能已经回收了那个对象——这是 UE 中最高频的线程安全 bug 之一。

**与 sender-receiver 的类比**：`ENQUEUE_RENDER_COMMAND` 的 lambda 和 stdexec 的 sender 有相似的"描述工作，稍后执行"结构，但有一个关键差别：stdexec 的 sender 在被 `start` 之前绝对不执行；`ENQUEUE_RENDER_COMMAND` 的 lambda 会在 RenderThread 的命令队列排到时自动执行，不需要你显式 `start`。生命周期拥有者是 UE 的 rendering command queue，不是你。

**TaskGraph worker pool** 是第四条并发路径，用于 CPU 密集型异步任务（不绑定到特定线程）。`UE::Tasks::Launch`（现代 API）或 `TGraphTask`（旧 API）投递的任务跑在 worker pool 上。与 RenderThread 不同，worker pool 任务没有"必须按值捕获"的硬约束，但依然需要遵守 UObject 的 GC 可见性规则（不能在 worker 里裸持有 `UObject*`）。

源码参考：`Engine/Source/Runtime/RenderCore/Public/RenderingThread.h`（`ENQUEUE_RENDER_COMMAND` 宏定义），`Engine/Source/Runtime/Core/Public/Async/TaskGraphInterfaces.h`（`FTaskGraphInterface`、`ENamedThreads`），`Engine/Source/Runtime/Core/Public/Tasks/Task.h`（`UE::Tasks::Launch`）。

## Mindset Shift 4：GC ownership 与 C++ ownership 两套并存

C++ 的所有权模型很清晰：谁拥有对象，谁负责销毁它；`TSharedPtr` / `TUniquePtr` 把所有权编码进类型里。

UE 里这套模型仍然存在，但它只管理**非 UObject 的对象**。凡是继承自 `UObject` 的类（包括 `AActor`、`UActorComponent`、所有资产类型），其生命周期由 **GC（Garbage Collector）** 管理，遵循一套完全不同的规则。

**GC 的工作方式**：UE 的 GC 是标记-清除（mark-sweep）式。它从一组"根集"出发（包括被 `AddToRoot()` 标记的对象、所有活跃的 `UWorld`、所有 `UGameInstance`），沿着 `UPROPERTY` 标注的指针递归遍历，标记所有可达的 `UObject`。未被标记的 `UObject` 在 GC 运行时被回收。

**对你的直接影响**：

第一，**裸 `UObject*` 成员变量如果不加 `UPROPERTY`，GC 看不见它**。这意味着 GC 在遍历时不会把它算作"可达引用"。即使你的代码仍然持有这个指针，GC 依然可能回收指向的对象，指针变成悬空指针，后续解引用是未定义行为。**解决方案**：凡是成员变量里存储 `UObject*`，必须加 `UPROPERTY`（或用 `TObjectPtr<T>`，在 UE5 里推荐替代裸指针）。

第二，**局部变量里的 `UObject*` 不需要 `UPROPERTY`**，因为 GC 只在 GameThread 空闲时运行（在帧与帧之间），不会在函数执行中途介入。但如果你把 `UObject*` 存在一个生命周期跨越 GC 运行时机的容器里（比如一个自定义的非 UObject 容器类），就需要显式告诉 GC。

第三，**`TSharedPtr` 管理的对象与 GC 完全分离**。`TSharedPtr<FMyStruct>` 里的 `FMyStruct` 不是 `UObject`，GC 对它一无所知，引用计数归零时自动析构，和 UE 无关。但如果 `FMyStruct` 里存了一个 `UObject*`，GC 依然看不见这个指针。

**两套体系的共存规则**，一句话总结：

> 非 UObject 的生命周期用 `TSharedPtr`/`TUniquePtr`/RAII 管理；UObject 的生命周期由 GC 管理，通过 `UPROPERTY` / `TObjectPtr` / Outer 链确保 GC 可见性。**绝对不要混用**：不要用 `TSharedPtr` 管理 `UObject`，不要用裸 `UObject*` 成员变量（不加 UPROPERTY）持有 UObject 引用。

**`TObjectPtr<T>` 的特殊之处**：在 UE5 中，用 `TObjectPtr<T>` 替代 `T*` 作为 `UPROPERTY` 成员的类型是推荐实践。在 Editor 构建中，`TObjectPtr` 会追踪访问行为（access barrier），帮助检测不安全的 UObject 访问模式。在 Shipping 构建中，`TObjectPtr` 退化为裸指针，零开销。

**与 Execution_Study 的类比**：`TSharedPtr` 的生命周期管理类似 `operation_state` 的引用计数——谁拥有引用，谁就是生命周期的参与者。`UPROPERTY` 则类似"把对象注册进 GC 的 environment 里"，让 GC 的遍历能够找到它。

源码参考：`Engine/Source/Runtime/CoreUObject/Public/UObject/Object.h`（`UObject` 基类），`Engine/Source/Runtime/CoreUObject/Public/UObject/UObjectGlobals.h`（`NewObject`、`AddToRoot`），`Engine/Source/Runtime/CoreUObject/Public/UObject/GarbageCollection.h`（GC 接口）。

## Mindset Shift 5：RDG = lazy graph，不是命令队列

如果你用过传统 RHI API（OpenGL、DX11 或 UE 的 `FRHICommandList`），你的直觉可能是：调用一个渲染 API 函数，命令就立刻进入命令缓冲区，最终被 GPU 执行。这是"命令录制"模式。

UE 的 RenderDependencyGraph（RDG）不是这样工作的。它是一个**惰性图**：在 `Execute()` 被调用之前，所有的 `AddPass()` 调用只是在描述图的节点和边，并不产生任何 GPU 命令。

这和 stdexec 的 sender 图有结构上的强类比：

| RDG 概念 | stdexec 类比 | 说明 |
|---|---|---|
| `FRDGBuilder::AddPass(...)` | `then(...)` / `when_all(...)` | 描述一个工作节点，建立依赖边，不立即执行 |
| `FRDGBuilder::Execute()` | `start(op)` | 触发整个图的编译和执行 |
| `FRDGTextureRef` / `FRDGBufferRef` | sender 图中的值槽 | 描述期的资源句柄，执行期才分配实际内存 |
| Transient resource pool | `operation_state` | RDG 管理资源的实际生命周期，pass 执行完毕即回收 |
| Pass 描述（`FRDGPassDesc`） | sender 的 `completion_signatures` | 声明这个 pass 读/写哪些资源（依赖关系） |
| RDG compile（`Execute` 内部）| `connect(sender, receiver)` | 分析依赖图，插入 barrier，安排执行顺序 |

**为什么要惰性**？因为 RDG 在 `Execute()` 时可以做全图优化：

- **自动 barrier 插入**：RDG 知道每个 pass 读写哪些资源，能自动在正确的位置插入 transition barrier，不需要手写。
- **Transient resource 分配**：RDG 知道每个资源的"第一次写入 pass"和"最后一次读取 pass"，可以在这个范围内分配临时显存，pass 结束后立即回收——类似 `operation_state` 在 `start` 后被分配、在 completion 后被销毁。
- **Pass culling**：如果某个 pass 的输出在后续 pass 中没有被用到，RDG 可以直接跳过它，不产生 GPU 开销。

**对习惯 stdexec 的人，最直接的感觉是**：你在 `AddPass` 里写的 lambda，和你在 `then` 里写的 lambda，都只是"描述"，不是"执行"。`FRDGTextureRef` 是资源的"描述符"，不是实际的 GPU 纹理句柄——就像 stdexec 里的 sender 不是已经运行的任务。真正的资源分配和 GPU 命令录制，发生在 `Execute()` 里。

**RDG 与传统 `FRHICommandList` 的关系**：`FRHICommandList` 是 RDG 的底层原语，RDG 在 `Execute()` 时内部使用 `FRHICommandList` 录制 GPU 命令。模块 G 先教 `FRHICommandList`（命令录制模式），模块 H 再教 RDG（惰性图模式），这个顺序让你能在理解底层的基础上理解上层的设计动机。

源码参考：`Engine/Source/Runtime/RenderCore/Public/RenderGraphBuilder.h`（`FRDGBuilder` 类定义，`AddPass`、`Execute` 方法），`Engine/Source/Runtime/RHI/Public/RHICommandList.h`（`FRHICommandList` 基础）。

## Mindset Shift 6：Subsystem 化，而非全局单例

C++ 工程里，"全局唯一对象"的常见实现是裸全局单例——一个 `static` 实例，或者 Meyer's singleton。这在小型工程里没什么问题，但在 UE 的 editor + runtime 环境里，裸全局单例有一个致命问题：**它的生命周期没有任何人管理**。

在 PIE（Play In Editor）模式下，你可以在同一个 Editor 进程里启动、停止、再启动游戏。每次 PIE 开始，`UWorld` 被创建；每次 PIE 停止，`UWorld` 被销毁。如果你的"单例"是一个裸全局，它会跨越 PIE 的生命周期存活——从第一次 PIE 一直活到 Editor 关闭。这意味着它在第二次 PIE 时持有第一次 PIE 的 `UWorld` 指针，指向已销毁的对象。

UE 的解决方案是 **Subsystem 体系**：把"单例"的实现换成一个 `UObject` 子类，由 UE 的框架层创建并挂在特定的生命周期容器上，随容器的创建/销毁自动初始化/反初始化。

**三层 Subsystem，对应三种生命周期**：

- **`UEngineSubsystem`**：生命周期绑定 `GEngine`（即整个 Editor/Game 进程）。PIE 开始/停止不会影响它的生命周期，只有引擎关闭时才销毁。适合存储跨 PIE 会话的状态，例如编辑器工具的全局注册表。
- **`UGameInstanceSubsystem`**：生命周期绑定 `UGameInstance`。`UGameInstance` 在关卡切换时存活，比 `UWorld` 更长，但只在一次完整的游戏会话（从"开始游戏"到"退出游戏"）内存活。在 PIE 中，每次 PIE 启动创建新的 `UGameInstance`，停止时销毁。适合存储跨关卡但不跨游戏会话的状态。
- **`UWorldSubsystem`**：生命周期绑定 `UWorld`。每个 `UWorld` 实例有一套自己的 `UWorldSubsystem` 集合，PIE 中的 Server World 和 Client World 各有独立实例。适合存储"与这个世界绑定"的系统状态，例如单个世界里的寻路缓存、光照查询系统等。

**Subsystem 的创建和销毁不需要你手动管**：UE 框架在合适的时机自动调用 `Initialize`（`UGameInstanceSubsystem`）或 `OnWorldBeginPlay`（`UWorldSubsystem`）。你只需要继承对应基类，声明 `UCLASS`，UE 的反射系统会自动发现并实例化它。

**与 Mindset Shift 4（GC ownership）的联系**：Subsystem 是 `UObject`，它的生命周期由 GC + 所属容器（`GEngine`/`UGameInstance`/`UWorld`）共同管理。Subsystem 实例挂在容器对象的 Outer 链上，只要容器活着，Subsystem 就不会被 GC 踢掉。这是 UE 里最规范的"单例等价物"实现方式。

**关键的实践结论**：当你在 UE 工程里想写一个"全局唯一的管理器"，先问自己：它的生命周期应该绑定到引擎、游戏会话，还是世界？然后选对应的 Subsystem 基类，而不是写裸全局。

源码参考：`Engine/Source/Runtime/Engine/Public/Subsystems/WorldSubsystem.h`（`UWorldSubsystem` 定义），`Engine/Source/Runtime/Engine/Public/Subsystems/GameInstanceSubsystem.h`（`UGameInstanceSubsystem` 定义），`Engine/Source/Runtime/Engine/Classes/Engine/World.h`（`UWorld` 及其 Subsystem 管理接口），`Engine/Source/Runtime/Engine/Classes/GameFramework/Actor.h`（`AActor` 作为 `UObject` 子类在 World 中的位置）。

## 四固定问题

以上 6 个 mindset shift 对应的核心提问，在每道练习里都会反复出现。现在先把这四个问题的完整含义理解透：

**Q1：执行真正开始时刻？**

不是"代码写在哪里"，而是"这段代码在引擎的哪个时机点、哪条线程上被调用"。可能的答案包括：`IModuleInterface::StartupModule`（模块加载时）、`CDO` 构造器（Class Default Object 创建时，早于任何实例化）、`PostInitializeComponents`（Actor 所有 Component 注册完毕后）、`BeginPlay`（World 开始运行时）、`Tick`（每帧 GameThread）、`ENQUEUE_RENDER_COMMAND` 的 lambda 体（RenderThread 排到该命令时）、`FRDGBuilder::Execute()`（RDG 执行期）、`FRHICommandList` 的 GPU 提交（RHIThread）。

**Q2：生命周期拥有者？**

谁负责这个对象的存在和销毁。UObject：GC（通过 `UPROPERTY`/Outer 链确保可达性）。非 UObject：`TSharedPtr` 引用计数或 `TUniquePtr` 独占所有权。Module：`FModuleManager`（`ShutdownModule` 后销毁）。Actor：`UWorld`（World 销毁时 Actor 被销毁，也可手动 `Destroy()`）。RDG 资源：RDG transient pool（pass 执行完毕即回收）。Subsystem：所属容器（`GEngine`/`UGameInstance`/`UWorld`）。

**Q3：涉及哪些 Named Thread？**

`ENamedThreads::GameThread`（游戏逻辑）、`ENamedThreads::RenderThread`（渲染命令录制）、`ENamedThreads::RHIThread`（GPU 提交）、TaskGraph worker pool（异步 CPU 任务）。如果题目涉及跨线程投递，写出投递点（哪条线程，用什么机制）和接收点（哪条线程，何时执行）。

**Q4：涉及 UObject 时怎么对 GC 可见？**

五种方式：①成员变量加 `UPROPERTY`（最常用）；②成员变量用 `TObjectPtr<T>` 包装（UE5 推荐）；③调用 `AddToRoot()` 强制加入根集（通常用于需要跨 World 存活的对象）；④对象挂在可达的 Outer 链上（例如 Actor 的 Component 以 Actor 为 Outer，World 持有 Actor，GC 从 World 出发可达）；⑤不涉及 UObject（纯 C++ 对象用 `TSharedPtr`/`TUniquePtr` 管理，与 GC 无关）。

## 五张图触发规则

不是每题都画全部五张图。以下规则决定哪个模块触发哪种图：

**模块依赖图**（触发模块：A 首题必画，Cap1）
内容：本 Module 的节点，`PublicDependencyModuleNames` 和 `PrivateDependencyModuleNames` 作为有向边，标出每个依赖 Module 的 LoadingPhase。目的：让你直观看到 UE 工程里"代码分层"的实际形态。

**线程时序图**（触发模块：F 全部题、G、H、Cap1）
内容：横轴时间，纵轴三条主干线程（GameThread / RenderThread / RHIThread）。标出每个操作在哪条线程发生，跨线程投递点（`ENQUEUE_RENDER_COMMAND`、`FlushRenderingCommands`、RDG pass barrier）用箭头标出。目的：让你看清"这段代码真正在哪里跑"。

**对象生命周期图**（触发模块：D、K、Cap1）
内容：从对象创建（`NewObject` / `SpawnActor` / Subsystem 自动创建）到 GC 回收的完整弧。标出 Outer 链（谁是谁的 Outer），标出 UPROPERTY 引用边（哪些引用让 GC 可达），标出生命周期关键事件（`BeginPlay`、`EndPlay`、`Destroyed`、`ConditionalBeginDestroy`）。目的：让你真正理解"这个对象什么时候会死，谁杀死它"。

**反射可见性图**（触发模块：D 反射遍历题、J replication 题）
内容：一个 `UCLASS` 的字段分类视图：哪些字段加了 `UPROPERTY`（对 UHT/GC/反射可见），哪些加了 `UPROPERTY(Replicated)`（对网络 replication 可见），哪些是普通 C++ 字段（对 GC 不可见）。目的：让你记住"UHT 的可见性"和"C++ 编译器的可见性"是两回事。

**RDG pass 图**（触发模块：H 全部题、Cap1）
内容：矩形节点是 pass（`AddPass` 调用），椭圆节点是资源（`FRDGTextureRef` / `FRDGBufferRef`）。有向边表示 pass 读取（虚线）或写入（实线）资源。标出每个资源的 transient lifetime（哪个 pass 首次写，哪个 pass 最后读）。目的：让你把 RDG 的惰性图模型视觉化，类比 stdexec 的 sender graph。

## 对后续模块的期待

- **模块 A（构建系统与模块生命周期）**：把"代码归属 Module，Module 有 LoadingPhase"刻进肌肉记忆。建出第一个可被 UE 加载的 Module，亲眼看到 UBT/UHT 的处理顺序。
- **模块 B（核心容器与字符串）**：把"UE 容器语义不等于 STL"刻进直觉。`FString` 不是 `std::string`，`FName` 是全局哈希池里的 ID，`FText` 是本地化懒求值对象——三件套各有用途，不可互换。
- **模块 C（内存、智能指针、委托）**：把"C++ 所有权（TSharedPtr 路径）与 GC 所有权（UPROPERTY 路径）的边界"钉死，在面对任意 UE 对象时都能快速判断"用哪套所有权机制"。
- **模块 D（UObject / 反射 / GC，枢纽）**：亲手直面代码生成——打开 `.generated.h`，读懂 UHT 生成的每一行。手写 mini mark-sweep GC，理解"为什么 UPROPERTY 缺失会导致悬空"的底层机制。这是整套课程难度最集中的节点。
- **模块 K（Actor / Component / World / Subsystem）**：从 UObject 机制层跨入 UE 可运行对象生态层。`AActor` 是世界里可定位的 `UObject`，`UActorComponent` 是 Actor 的能力插件，`UWorldSubsystem` 是由 World 托管的单例 `UObject`——三条主线在这里汇合。
- **模块 E（资产与加载）**：资产系统建立于 `UObject` + `UPackage` + `FArchive`。`FSoftObjectPath` 懒引用 + `FStreamableManager` 异步加载的组合，是 UE 里"描述资产，稍后加载"的惰性模式，与 stdexec 的 sender 有精神上的类似。
- **模块 F（并发与任务图）**：真正操作三线程分线。`ENQUEUE_RENDER_COMMAND` 是通往模块 G/H 的钥匙——只有在 F 模块把"按值捕获的必要性"做成直觉，G/H 的渲染代码才不会写出线程安全 bug。
- **模块 G（RHI 与着色器）**：传统 `FRHICommandList` 路径，理解 GPU 命令录制的底层形态。`SHADER_PARAMETER` 宏是 UHT 之外的第二处代码生成点，C++ struct 与 HLSL cbuffer 的字段对应关系是这一模块的核心教学内容。
- **模块 H（RenderGraph 与场景渲染，压轴）**：课程最重要的收束点。RDG 的描述期 vs 执行期，与 stdexec 的 sender 惰性 vs `start`，在这里形成最强的类比。做完模块 H，你应该能把整套课程的知识点串成一句话：UE 引擎内核是一个把 Module 系统、反射 GC、三线程模型、惰性渲染图整合在一起的工业级 C++ 框架。
- **模块 I（Slate / UMG，可选）**：正交于渲染主线，随时可插入。`SCompoundWidget` 的 DSL 式声明语法是 UE 里另一处"非纯 C++ 写法"，`SLATE_BEGIN_ARGS`/`SLATE_END_ARGS` 宏展开产生的代码值得一读。
- **模块 J（网络与 Replication）**：反射元数据驱动的 replication。`DOREPLIFETIME` 告诉 NetDriver 这个 `UPROPERTY` 需要同步，RPC 三向（Server/Client/NetMulticast）的触发条件与 Actor 的 `Role`/`RemoteRole` 直接相关——这是模块 D 能力在网络维度的完整投射。
