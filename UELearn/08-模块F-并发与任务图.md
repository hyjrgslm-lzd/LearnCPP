# 08 模块 F：并发与任务图

## 模块目标

反向引用 `01-心智模型` 的 §3 线程分线：GameThread、RenderThread、RHIThread 是 UE 内核的**一等公民**，数据不能随意跨线程共享。模块 F 把这一条心智模型变成你手上真正能拨动的旋钮——写出能在正确线程上运行的任务，并最终打通"游戏逻辑 → 渲染线程"这道最关键的跨线程通道。

模块 F 覆盖 UE 并发的三层 API：

1. **FRunnable / FRunnableThread**：手工管理线程生命周期，与 `FEvent` 配合做同步——UE 最底层、最接近 OS 的并发原语。
2. **TaskGraph（经典）**：通过 `FFunctionGraphTask::CreateAndDispatchWhenReady` 把工作挂到任意 Named Thread 或 worker pool；用 `FGraphEventRef` 建立显式依赖链。
3. **UE::Tasks（现代）**：`UE::Tasks::Launch` + `Then` + `FPipe`，UE5 引入的轻量级高层接口，底层走 LowLevelTasks + TaskGraph dispatch。
4. **ENQUEUE_RENDER_COMMAND**：GameThread 向 RenderThread 投递命令的**唯一安全方式**，通向模块 G 的钥匙。

阶梯定位：**use → implement-own**。F1/F2 在 use 层练习 API，F3 在 use + inspect 层理解 UE::Tasks 与 stdexec 的类比，F4 在 implement-own 层把 render command 的值捕获语义刻进肌肉记忆。

**四固定问题在本模块的具体含义**：

- **Q1（执行真正开始时刻）**：是 `FRunnableThread::Create` 后立即在新线程调用 `Init()/Run()`？还是 TaskGraph worker poll 到任务时？还是 RenderThread 排到命令队列里的命令时？
- **Q2（生命周期拥有者）**：FRunnable 由你自己管（RAII）；FRunnableThread 由你创建并调用 `Kill+delete` 或 `WaitForCompletion+delete`；TaskGraph 任务由 `TGraphTask` 内部的 ref count 管；UE::Tasks 的 `TTask<T>` 持有 `TRefCountPtr` 指向 `FTaskBase`；ENQUEUE_RENDER_COMMAND 的 lambda 由 UE 的 render command queue 持有，直到 RenderThread 执行完毕才销毁。
- **Q3（涉及哪些 Named Thread）**：F1 涉及 OS 原生线程（不挂在 TaskGraph Named Thread 体系）；F2/F3 全部 `ENamedThreads` 类型都要能答清（见各练习）；F4 涉及 GameThread（投递侧）和 RenderThread（执行侧）两条线程。
- **Q4（GC 可见性）**：F1-F3 通常不直接涉及 UObject，但若任务体捕获了 `UObject*`，裸指针对 GC 不可见，必须用 `TWeakObjectPtr`（在执行时重新 Pin）或在 GameThread 侧在任务执行前确保对象不会被 GC 踢掉。F4 的 render command lambda **绝对禁止**捕获裸 `UObject*`，详见 F4 常见坑节。

## 练习 F1：FRunnable 手动线程 + FEvent 同步

### 目标

派生 `FRunnable`，用 `FRunnableThread::Create` 启动一条手工管理的线程，用 `FEvent`（UE 的跨平台同步事件）实现主线程与子线程之间的双向握手，观察 `ThreadID` 与 GameThread 的差异。理解 UE 最底层并发原语的使用模式与 C++ `std::thread` + `std::atomic` 等价形态的对比。

### 前置理解

- 理解 `FRunnable` 的生命周期：`Init()` 在新线程上调用（不是在创建线程的那条线程），`Run()` 是主执行体，`Stop()` 由外部请求提前终止，`Exit()` 做清理。源码：`Engine/Source/Runtime/Core/Public/HAL/Runnable.h`。
- 理解 `FRunnableThread::Create(FRunnable*, const TCHAR* ThreadName, ...)` 是工厂方法，返回 `FRunnableThread*`，你负责 `Kill()` 和 `delete`。源码：`Engine/Source/Runtime/Core/Public/HAL/RunnableThread.h`（`Create` 静态工厂，第 44 行）。
- 理解 `FEvent` 是跨平台的 OS 同步事件（AutoReset / ManualReset 两种模式），通过 `FPlatformProcess::GetSynchEventFromPool(bool bIsManualReset)` 从池中获取，用完须 `FPlatformProcess::ReturnSynchEventToPool(FEvent*)` 归还。直接 `new FEvent` 在 UE5 已被标为 `UE_DEPRECATED(5.0, ...)`。源码：`Engine/Source/Runtime/Core/Public/HAL/Event.h`（`FEvent` 类，第 20 行）。
- 理解 `FThreadSafeBool` 和 `FThreadSafeCounter` 是不依赖锁的原子标志/计数器，适合跨线程的简单状态通信。

### 必做任务

1. 新建一个 `FMyWorker` 类，继承 `FRunnable`。重写 `Init()`、`Run()`、`Stop()`、`Exit()` 四个虚函数。`Run()` 里做一个简单循环（例如计数到 1000 万），并在循环的起始和结束各打印一次 `FPlatformTLS::GetCurrentThreadId()`。

2. 在 `Run()` 开始时 `Trigger()` 一个 `FEvent`（"就绪事件"），通知主线程"子线程已经开始运行"。主线程在 `Create` 之后立即 `Wait()` 这个事件，确认子线程已启动后再继续。

3. 在 `Run()` 结束时再 `Trigger()` 另一个 `FEvent`（"完成事件"），通知主线程"计算已完成"。主线程 `Wait()` 完成事件，取出计算结果，打印。

4. 在主线程侧，正确调用 `Thread->Kill(true)` 后 `delete Thread`（`Kill(true)` 表示等待线程退出后再返回）。观察若先 `delete` 再 `Kill` 会发生什么，并在观察记录中写出原因。

5. 在 `StartupModule` 里打印 GameThread 的 `FPlatformTLS::GetCurrentThreadId()`，与 worker 线程的 ID 做对比，确认它们不同。

6. 画一张**线程时序图**（F 模块全题必画）：横轴时间，纵轴 GameThread / WorkerThread，标出 `Create` 调用点、`Trigger/Wait` 握手点、`Kill` 调用点。

### 进阶任务

- 将计数循环的"是否应该继续"改为由 `FThreadSafeBool bShouldStop` 控制。在 `Stop()` 里把 `bShouldStop` 置为 `true`，`Run()` 循环体每轮检查它，实现提前退出。
- 在 `Run()` 里用 `FThreadSafeCounter` 记录已处理迭代数，让主线程在任意时刻（不加锁）查询当前进度。
- 写一个等价的 `std::thread` + `std::atomic<bool>` + `std::condition_variable` 版本，与 UE 版本做并排对比：`FRunnable` 对应哪个 C++ 概念？`FEvent` 对应 `std::condition_variable` 的哪一段语义？`FThreadSafeBool` 对应 `std::atomic<bool>` 的哪一段语义？把对比写进观察记录。
- 尝试给 `FRunnableThread::Create` 传入不同的 `EThreadPriority`（`TPri_AboveNormal`、`TPri_BelowNormal`），用 Windows Task Manager / Unreal Insights 观察优先级变化。

### 验收点

- 控制台输出能看到两个不同的 ThreadID（GameThread vs WorkerThread）。
- 两次 FEvent 握手都正确工作：主线程不会在子线程启动之前继续执行，也不会在子线程完成之前取结果。
- `Kill(true)` 后 `delete Thread` 无崩溃，内存无泄漏（Valgrind / AddressSanitizer 或 UE 内置的内存追踪器验证）。
- 进阶版的 `FThreadSafeBool` 提前退出能在预期的迭代次数内停止，而不是跑完全部 1000 万次。
- 线程时序图能正确展示两条线程的时间关系，握手点清晰标出。

### 观察点

- `FRunnable::Init()` 是在**新线程**的上下文里调用的，不是在调用 `FRunnableThread::Create` 的那条线程。这与 `std::thread` 的行为一致：传入的 callable 直接在新线程里执行，没有单独的 Init 阶段。
- `FEvent` 的 AutoReset 模式（`bIsManualReset = false`）在 `Trigger()` 并且一个等待线程被唤醒后，事件会自动回到未触发状态。ManualReset 模式（`bIsManualReset = true`）会持续保持触发状态，直到显式调用 `Reset()`。选错模式会导致多个等待线程行为不一致，或事件"永远不会再触发"。
- `FRunnableThread::GetThreadID()` 返回平台相关的 OS 线程 ID，与 `FPlatformTLS::GetCurrentThreadId()` 在新线程内部获取的值相同，可以用来确认"代码真的在那条线程上跑"。

### 常见坑

**坑 1：Kill 与 delete 顺序颠倒**

`Kill(true)` 会等待线程退出。如果你先 `delete Thread` 再 `Kill`（或者根本不 `Kill` 就 `delete`），对象已经释放但 OS 线程仍在运行，后续对 `FRunnable` 成员的访问是 UAF（Use After Free），结果不确定。正确顺序永远是：先 `Kill(true)`，再 `delete Thread`。

**坑 2：FEvent 泄漏——忘记 ReturnSynchEventToPool**

`FPlatformProcess::GetSynchEventFromPool` 从事件池中取事件。如果你没有配对调用 `ReturnSynchEventToPool`，事件对象永远不会归还，反复触发导致池被耗尽。建议用 RAII 包装：

```cpp
// 推荐做法：用 FEventRef（UE5 已有）
// Engine/Source/Runtime/Core/Public/HAL/Event.h 第 129 行
// FEventRef 在构造时 GetSynchEventFromPool，析构时 ReturnSynchEventToPool
FEventRef ReadyEvent { EEventMode::AutoReset };
FEventRef DoneEvent  { EEventMode::AutoReset };
// 不需要手动 Return，离开作用域自动归还
```

**坑 3：在 Run() 里裸持有 UObject 指针**

如果 `Run()` 的循环体需要访问某个 UObject，绝对不能把 `UObject*` 直接存在 `FRunnable` 成员里不加保护。GC 可能在 GameThread 的帧间隙运行，踢掉这个对象。正确做法：要么只在 GameThread 侧与线程通信（通过 FIFO 或 lock-free 队列传值拷贝），要么用 `TWeakObjectPtr`，在 worker 线程侧需要访问时 Pin 并立即检查是否有效。

**坑 4：Stop() 被调用时机的误解**

`Stop()` 由外部（另一条线程，通常是主线程）调用，目的是通知 `Run()` "你应该尽快退出了"。`Stop()` 本身不会强制终止线程——你的 `Run()` 循环必须主动检查"是否应该停止"的标志。如果 `Run()` 是一个死循环且从不检查任何退出条件，调用 `Stop()` 和 `Kill(true)` 会无限阻塞主线程。

### 复盘问题

- **Q1：执行真正开始时刻**：`FRunnable::Init()` 在哪条线程上调用？`Run()` 开始执行时，`FRunnableThread::Create` 是否已经返回了？两者有什么先后关系？
- **Q2：生命周期拥有者**：`FRunnable` 对象的生命周期由谁管理？`FRunnableThread` 对象呢？它们的析构顺序有什么约束？
- **Q3：涉及哪些 Named Thread**：F1 创建的线程是 `ENamedThreads` 体系里的 Named Thread 吗？它在 TaskGraph 里有 ID 吗？如果需要在 `Run()` 里向 GameThread 投递工作，用什么机制？
- **Q4：GC 可见性**：F1 的 `FRunnable` 本身不是 `UObject`，它的生命周期由谁管？如果 worker 线程需要引用一个 UObject，最安全的传递方式是什么（值拷贝、`TSharedPtr<非UObject>`，还是 `TWeakObjectPtr`）？
- `FEvent::Wait(uint32 WaitTime)` 参数是毫秒，`INFINITE` 值是 `MAX_uint32`。如果你给了一个有限超时，`Wait` 返回 `false` 表示超时而不是被 Trigger，你的代码如何区分这两种情况？
- `FThreadSafeCounter` 的 `Increment()` 和 `Decrement()` 返回操作后的值，而不是操作前的值。这一点在实现"恰好第 N 次调用时触发某行为"时有什么影响？

## 练习 F2：TaskGraph + Named Threads

### 目标

通过 `FFunctionGraphTask::CreateAndDispatchWhenReady` 把工作投递到 TaskGraph 的不同 Named Thread 和 worker pool；用 `FGraphEventRef` 建立 A → B → C 的显式依赖链；能说清 `ENamedThreads` 枚举里各个值的含义；读懂 TaskGraph 图执行的 hot path 片段。

### 前置理解

- `ENamedThreads::Type` 是一个位域枚举，低 8 位编码线程索引（`GameThread = 1`、`ActualRenderingThread = 2`、`RHIThread = 0`、`AnyThread = 0xff`），高位编码优先级和队列偏移。源码：`Engine/Source/Runtime/Core/Public/Async/TaskGraphInterfaces.h`，第 54–208 行。
- `FFunctionGraphTask::CreateAndDispatchWhenReady(TUniqueFunction<void()>, TStatId, const FGraphEventArray*, ENamedThreads::Type)` 是创建和投递 lambda 任务的最简洁方式。源码：`TaskGraphInterfaces.h` 第 1117 行。
- `FGraphEventRef`（即 `TRefCountPtr<FGraphEvent>`）是任务的"完成句柄"，可以作为后续任务的前置条件传入 `FGraphEventArray`。
- `TGraphTask<T>::CreateTask(Prerequisites).ConstructAndDispatchWhenReady(...)` 是完整的创建路径，`FFunctionGraphTask` 是对它的简化封装。
- `FTaskGraphInterface::Get().ProcessThreadUntilIdle(ENamedThreads::GameThread)` 可以让 GameThread "排空" 等待自己的本地队列，在 `StartupModule` 里测试时经常需要这一句。

### 必做任务

1. 在 `StartupModule` 里，用 `FFunctionGraphTask::CreateAndDispatchWhenReady` 创建三个任务 A、B、C，建立如下依赖：
   - A：无前置，投递到 `ENamedThreads::AnyNormalThreadNormalTask`（worker pool）
   - B：前置为 A，投递到 `ENamedThreads::AnyHiPriThreadNormalTask`（高优先级 worker pool）
   - C：前置为 B，投递到 `ENamedThreads::GameThread`
   
   每个任务 lambda 里打印：任务名称、`FPlatformTLS::GetCurrentThreadId()`、`FTaskGraphInterface::Get().GetCurrentThreadIfKnown()` 的值。

2. 等待链尾 C 完成：用 `FTaskGraphInterface::Get().WaitUntilTaskCompletes(EventC, ENamedThreads::GameThread)` 在 GameThread 上阻塞到 C 结束。观察等待期间 GameThread 是否执行了其他工作（观察控制台是否有其他 GameThread 任务的日志交错）。

3. 单独创建一个投递到 `ENamedThreads::ActualRenderingThread` 的任务，打印其 ThreadID，与 GameThread ThreadID 对比。注意：如果在 Editor 中 `GIsThreadedRendering = true`，RenderThread 的 ID 与 GameThread 不同；否则在单线程渲染模式下它们相同。

4. 写出下列 `ENamedThreads` 值在运行时对应哪条实际线程，并在观察记录里给出：
   - `GameThread`：游戏逻辑，BeginPlay/Tick/Input，UObject 的大多数操作
   - `ActualRenderingThread`：场景代理更新、RDG 构建、FSceneRenderer::Render
   - `RHIThread`：GPU 命令实际提交（若 `GRHIThread` 存在）
   - `AnyNormalThreadNormalTask`：普通优先级 worker pool（CPU 密集型后台工作）
   - `AnyHiPriThreadNormalTask`：高优先级 worker pool（对延迟更敏感的工作）
   - `AnyBackgroundThreadNormalTask`：后台低优先级 worker pool（I/O、预热等）

5. 画线程时序图：三条 Named Thread（GameThread / HighPriWorker / NormalWorker），横轴时间，标出 A/B/C 投递与执行的时间点和依赖箭头。

### 进阶任务

- 实验 `ESubsequentsMode::FireAndForget`（在 `TGraphTask<>` 模板参数位置）：创建一个不需要被其他任务依赖的任务，观察与 `TrackSubsequents` 模式的 overhead 差异（可通过 Unreal Insights 或 stat frame 对比）。
- 用 `TGraphTask<T>::CreateTask(Prerequisites).ConstructAndDispatchWhenReady(...)` 路径（而不是 `FFunctionGraphTask`）创建一个自定义任务类型，要求它实现 `GetDesiredThread()`、`DoTask(ENamedThreads::Type CurrentThread, const FGraphEventRef& MyCompletionGraphEvent)` 两个方法，读懂这对应 hot path 的哪个调用链。
- 阅读 `TaskGraphInterfaces.h` 第 264–350 行的 `FTaskGraphInterface` 接口，理解 `QueueTask` 的参数语义（`ThreadToExecuteOn` vs `CurrentThreadIfKnown`），以及为什么 `AnyThread` 和具名线程需要不同的调度路径。
- 用 `FGraphEventRef::DontCompleteUntil(EventOther)` 延长一个任务的完成时刻（任务体已经执行完，但 event 不触发直到 `EventOther` 也完成），理解这在"协调异步依赖"场景里的用途。

### 验收点

- A → B → C 的顺序依赖正确：控制台输出必须按 A、B、C 的顺序显示，不能看到 B 在 A 之前、C 在 B 之前完成。
- 各任务的 `GetCurrentThreadIfKnown()` 返回值与投递时指定的 `ENamedThreads` 值一致（AnyThread 的返回值不固定，但不应该是 GameThread）。
- 投递到 `ActualRenderingThread` 的任务，在 `GIsThreadedRendering = true` 时 ThreadID 与 GameThread 不同。
- 能口头解释 `ENamedThreads::AnyNormalThreadNormalTask` 与 `ENamedThreads::GameThread` 在调度行为上的根本区别：前者去 worker pool，后者必须等 GameThread 空闲时执行。

### 观察点

- TaskGraph 里 "Named Thread" 不是普通操作系统意义上的"named thread"，而是 TaskGraph 调度器专门为特定角色保留的线程槽位。GameThread 的任务只有在 GameThread 运行 `ProcessThreadUntilIdle` / `ProcessUntilQuit` 时才被消耗。
- `FGraphEventRef` 的引用计数决定 `FGraphEvent` 对象的生命周期。当所有持有者释放引用，且关联的任务也已完成，`FGraphEvent` 才被回收。把 `FGraphEventRef` 放进 `FGraphEventArray` 传给下一个任务，会暂时增加 ref count，保证依赖期间对象存活。
- 在模块 `StartupModule` 里（此时 UE 还没进入 main game loop），GameThread 的任务队列消耗频率较低。如果你在 `CreateAndDispatchWhenReady(..., ENamedThreads::GameThread)` 后直接 `check` 任务已完成，可能会发现任务根本没跑——因为 GameThread 还没进入 `ProcessThreadUntilIdle`。需要显式调用 `WaitUntilTaskCompletes` 或者在 `Tick` 里测试。

### 常见坑

**坑 1：向 GameThread 投递任务后忘记驱动 GameThread 排队**

`FFunctionGraphTask::CreateAndDispatchWhenReady([]{...}, {}, nullptr, ENamedThreads::GameThread)` 把任务放进 GameThread 的队列，但 GameThread 必须运行其自己的任务消耗循环（`ProcessThreadUntilIdle` 或 main game loop 的 `FTaskGraphInterface::ProcessThreadUntilIdle(GameThread)` 调用）才会执行它。在 `StartupModule` 里如果调用这行代码后立即 `WaitUntilTaskCompletes`，且当前线程**就是** GameThread，则会产生 GameThread 在等自己的队列排空这种"自我阻塞"场景，UE 的 `WaitUntilTaskCompletes` 内部会处理这个情况（它在等待时会处理本线程队列），但行为容易让人困惑。

**坑 2：混淆线程优先级和任务优先级**

`ENamedThreads::AnyHiPriThreadNormalTask` 中，`HighThreadPriority` 指的是线程的 OS 优先级等级（高优先级 worker pool），`NormalTaskPriority` 指的是任务在该池的队列里的排队优先级。这两个优先级维度是独立的，组合起来才决定"此任务具体什么时候被哪条线程拿走"。

**坑 3：FGraphEventArray 持有悬空引用**

如果你把 `FGraphEventRef` 存进局部变量、然后传指针到 `FGraphEventArray`，而局部变量已超出作用域，`FGraphEventArray` 里的指针指向已销毁对象。正确做法：确保 `FGraphEventRef`（持有 ref count）的生命周期覆盖调用 `CreateAndDispatchWhenReady` 的整个范围。

**坑 4：在 worker task 里访问 GameThread-only API**

大量 UE 对象的方法（尤其是 `AActor`、`UActorComponent`、`UWorld`）都断言在 GameThread 上调用（`check(IsInGameThread())`）。在 `AnyThread` 的 lambda 里直接调用这些方法会触发 `checkf(false)` 崩溃。如果需要"worker 计算完成后通知 GameThread 更新对象"，应该再投递一个到 `ENamedThreads::GameThread` 的后续任务。

### 复盘问题

- **Q1：执行真正开始时刻**：TaskGraph 的任务在 `CreateAndDispatchWhenReady` 时会立即进入可执行状态（若所有前置都已完成），但真正被 worker thread 拿走执行的时刻不确定。"投递完成"和"执行开始"是两个不同的时刻。这对你在 StartupModule 里的代码有什么影响？

## 练习 F3：UE::Tasks 现代 API

### 目标

用 UE5 引入的 `UE::Tasks` 高层 API 完成一组常见并发模式：用 `Launch` 投递独立任务；用 `Then` 链接依赖链；用 `UE::Tasks::All`/`UE::Tasks::Any` 做聚合等待；用 `FPipe` 实现"串行化访问共享资源"。最后对照 stdexec 的对等概念，写出一张 3–4 行的对照表。

### 前置理解

- `UE::Tasks::Launch(DebugName, lambda, ETaskPriority)` 返回 `TTask<T>`（T 为 lambda 返回类型，void 时为 `TTask<void>`）。源码：`Engine/Source/Runtime/Core/Public/Tasks/Task.h`（`FTaskHandle::Launch` 模板，第 111–126 行）。
- `TTask<T>::Then(lambda)` 在前置任务完成后调度后续 lambda，类似 `std::future::then`（P1054 风格）。
- `UE::Tasks::All(task1, task2, ...)` 或 `UE::Tasks::All(TArrayView<TTask<>>)` 等待所有任务完成，类似 `when_all`。
- `UE::Tasks::Any(...)` 等待任意一个完成（注意 UE5.7 里 `Any` 的实际 API 形状，以源码为准）。
- `FPipe` 保证同一 pipe 里的任务串行（FIFO，无并发），用于保护共享状态。源码：`Engine/Source/Runtime/Core/Public/Tasks/Pipe.h`（`FPipe` 类，第 29 行；`FPipe::Launch` 模板，第 62 行）。
- `UE::Tasks` 底层通过 `LowLevelTasks` scheduler + `FTaskGraphInterface::QueueTask` dispatch 实现，**不是独立于 TaskGraph 的第二套调度器**，而是在 TaskGraph 上层的现代 wrapper。这意味着 `TTask<T>` 里的任务最终也会被 TaskGraph 的 worker pool 执行。

### 验收点

- `UE::Tasks::All` 等待的 4 个素数任务，全部完成后汇总结果数值正确（可预先手算验证）。

- 对照表 4 行都能口头解释，尤其是"Launch 不是 just+schedule 的完整等价，因为 UE::Tasks 没有惰性描述期"这一差异点。

### 观察点

- `UE::Tasks::Launch` 是**立即投递**（eager），不同于 stdexec 的 `just() | then()`（惰性，直到 `start` 才真正执行）。这是 UE 并发和 stdexec sender 的最大语义差异：UE 里任务一经 `Launch` 就进入调度队列，没有"描述期"概念。
- `FPipe` 的串行化是通过任务间的隐式前置条件实现的：新任务被加入 pipe 时，自动把 pipe 里最后一个未完成任务设为自己的前置条件。这是纯 TaskGraph 实现的 FIFO 串行器，没有独立的"串行线程"——任务仍然跑在 worker pool 上，只是同一时刻只有一个在跑。
- `TTask<T>::Wait()` 在当前线程阻塞，**内部会尝试在当前线程上 retract and execute（就地执行）任务**，减少真正的线程切换。这与 stdexec `sync_wait` 的设计思路相似——等待时尽量有效利用调用线程。
- `FPipe` 析构时会 `check(!HasWork())`（`Pipe.h` 第 42 行），如果 pipe 里还有未完成的任务就 `delete` pipe，会触发 crash。必须在析构前调用 `WaitUntilEmpty()`。

### 常见坑

**坑 1：在 Then 里捕获 TTask 本身**

```cpp
TTask<int> TaskA = UE::Tasks::Launch(TEXT("A"), []{ return 42; });
// 错误：循环依赖——TaskA 的 Then 里捕获了 TaskA，TaskA 的析构被推迟
TTask<void> TaskB = TaskA.Then(TEXT("B"), [TaskA]{ TaskA.GetResult(); });
```

`TTask` 持有对底层 `FTaskBase` 的引用。在 `Then` 的 lambda 里捕获 `TTask` 会形成引用环，导致底层任务对象永远无法被释放。正确做法：不捕获 `TTask` 对象本身，只在 `Then` 的 lambda 里通过参数（若 API 提供）或闭包捕获计算结果（值拷贝）。

**坑 2：在 UE::Tasks worker 里访问 UObject 不安全**

与 F2 的坑 4 相同：`UE::Tasks::Launch` 的 lambda 跑在 worker pool，不是 GameThread。在 lambda 里调用 `GetWorld()`、`GetOwner()` 等需要 GameThread 保证的方法会触发 `IsInGameThread()` 断言。

**坑 3：FPipe 在 pipe 任务仍有工作时析构**

```cpp
{
    UE::Tasks::FPipe MyPipe(TEXT("MyPipe"));
    for (int i = 0; i < 100; ++i)
        MyPipe.Launch(TEXT("Work"), [i]{ /* ... */ });
    // 离开 scope：FPipe 析构，但任务还没完成！
    // check(!HasWork()) 触发，程序崩溃
}
```

正确做法：在 pipe 析构前调用 `MyPipe.WaitUntilEmpty()`。

## 练习 F4：ENQUEUE_RENDER_COMMAND 跨线程（通往 G 的钥匙）

### 目标

写出一段规范的 `ENQUEUE_RENDER_COMMAND` 代码，亲身体验**值捕获 + 延迟执行**的语义；理解 render command queue 的 SPSC（Single Producer Single Consumer）模型；明确"GameThread 写、RenderThread 读"的数据流向；把"render command 的 lambda 必须按值捕获"从知识点变成直觉。F4 是通往模块 G（RHI 与着色器）的直接前置——模块 G 里所有 RHI 操作都通过 `ENQUEUE_RENDER_COMMAND` 从 GameThread 发起。

### 前置理解

- `ENQUEUE_RENDER_COMMAND(TypeName)` 宏（`RenderingThread.h` 第 1167–1169 行）展开后等价于：
  ```cpp
  DECLARE_RENDER_COMMAND_TAG(FRenderCommandTag_TypeName##__LINE__, TypeName)
  FRenderCommandDispatcher::Enqueue<FRenderCommandTag_TypeName##__LINE__>
  ```
  然后跟一个 lambda，lambda 的签名为 `[captures](FRHICommandListImmediate& RHICmdList) { ... }`。
  
- `FRenderCommandDispatcher::Enqueue<Tag>` 把 lambda 包装成一个任务，放入 `UE::Tasks::FPipe`（render command pipe）或通过 `FTaskGraphInterface::QueueTask` 投递到 `ENamedThreads::ActualRenderingThread` 上执行。"投递"发生在 GameThread；"执行"发生在 RenderThread 的 tick 里。

- **RenderThread 通常比 GameThread 滞后 1 帧**（`GIsThreadedRendering = true` 时）。这意味着当你在 GameThread 的 Frame N 的 `Tick()` 里 `ENQUEUE_RENDER_COMMAND`，这个命令可能在 Frame N 的 RenderThread 里执行，也可能延迟到 Frame N+1——取决于帧同步点和命令队列的消耗速度。**绝对不能假设命令在 Enqueue 后"立刻"执行**。

- `FlushRenderingCommands()`（`RenderingThread.h` 第 110 行）会阻塞 GameThread 直到 RenderThread 排空所有待处理命令。**在 GameThread 的 Tick/BeginPlay 里调用 FlushRenderingCommands 是严重的性能反模式**，相当于把游戏帧率上限降低到 RenderThread 能处理命令的速度。只应该在关卡切换、Editor 工具、调试路径里调用。

- **SPSC 模型**：`ENQUEUE_RENDER_COMMAND` 背后的命令队列设计为 Single Producer（GameThread）Single Consumer（RenderThread）。GameThread 写入命令（生产者），RenderThread 消耗命令（消费者），两者无需加锁，通过无锁 FIFO 或 UE::Tasks pipe 实现高效跨线程通信。


### 常见坑（F4 核心坑——必须单独展开）

**坑 1：按引用捕获 GameThread 局部变量 = 悬空指针（最高频 bug）**

这是 UE 并发里最高频的线程安全 bug，必须在直觉层面杜绝。

```cpp
// !!!!! 错误示范 !!!!! —— 悬垂引用，未定义行为
void UMyComponent::TickComponent(float DeltaTime, ...)
{
    FVector CurrentLocation = GetActorLocation();  // GameThread 栈变量
    
    ENQUEUE_RENDER_COMMAND(BuggyCmd)(
        [&CurrentLocation](FRHICommandListImmediate& RHICmdList)
        //  ^^^^^^^^^^^^^^^^ 按引用捕获！
        {
            // RenderThread 执行此处时，Tick() 早已返回
            // CurrentLocation 已经在 GameThread 的栈上析构
            // 这里读到的是垃圾值或者触发访问违例
            UE_LOG(LogTemp, Log, TEXT("Location: %s"), *CurrentLocation.ToString());
        });
}
```

```cpp
// 正确写法 —— 按值捕获，lambda 持有独立副本
void UMyComponent::TickComponent(float DeltaTime, ...)
{
    FVector LocationCopy = GetActorLocation();  // 值拷贝到局部变量
    
    ENQUEUE_RENDER_COMMAND(SafeCmd)(
        [LocationCopy](FRHICommandListImmediate& RHICmdList)
        //  ^^^^^^^^^^^ 按值捕获，lambda 生命周期内副本始终有效
        {
            // 完全安全：LocationCopy 是 lambda 闭包的一部分
            // lambda 在 RenderThread 执行完毕前不会析构
            UE_LOG(LogTemp, Log, TEXT("Location: %s"), *LocationCopy.ToString());
        });
}
```

**坑 2：捕获裸 `UObject*` 进 render command lambda**

即使是按值捕获，裸 `UObject*` 也是危险的：

```cpp
// !!!!! 错误示范 !!!!! —— UObject* 在 RenderThread 执行时可能被 GC 回收
AActor* MyActor = GetOwner();  // UObject*

ENQUEUE_RENDER_COMMAND(UObjectBugCmd)(
    [MyActor](FRHICommandListImmediate& RHICmdList)
    //  ^^^^^^^ 按值捕获了 UObject*，但 GC 不知道 lambda 持有这个指针！
    {
        // GC 在 GameThread 帧间可能已经回收了 MyActor
        // 此处访问 MyActor 是 UAF（Use After Free）
        FVector Loc = MyActor->GetActorLocation();  // 崩溃
    });
```

```cpp
// 正确做法 A：只传递 POD 数据（不传对象指针），提前在 GameThread 侧提取所需数据
FVector LocationCopy = GetOwner()->GetActorLocation();

ENQUEUE_RENDER_COMMAND(SafeUObjectCmd)(
    [LocationCopy](FRHICommandListImmediate& RHICmdList)
    {
        // 只有数据，没有对象指针，GC 无法影响到这里
        UE_LOG(LogTemp, Log, TEXT("Loc: %s"), *LocationCopy.ToString());
    });

// 正确做法 B：如果必须传递"类似 UObject 的资源"，使用 RHI 资源句柄（FTextureRHIRef 等）
// 这些句柄有自己的引用计数，与 GC 无关
FTextureRHIRef TextureRef = MyTexture->GetResource()->TextureRHI;  // 引用计数句柄

ENQUEUE_RENDER_COMMAND(TextureCmd)(
    [TextureRef](FRHICommandListImmediate& RHICmdList)
    //  ^^^^^^^^^^^ TRefCountPtr 按值捕获，引用计数保证 RHI 对象存活
    {
        // 安全：TextureRef 的引用计数在 lambda 析构前不会降到 0
    });
```

**坑 3：在 render command lambda 里再次 ENQUEUE 嵌套命令**

`ENQUEUE_RENDER_COMMAND` 设计为从 **GameThread** 调用。在 RenderThread 侧（即 render command lambda 内部）再次调用 `ENQUEUE_RENDER_COMMAND` 的行为是未定义的（取决于 `GIsThreadedRendering` 的状态，可能导致死锁或命令排序错乱）。如果需要在 RenderThread 里继续录制工作，应该直接在 lambda 体内操作 `FRHICommandListImmediate& RHICmdList`，而不是再次 Enqueue。

**坑 4：错误地认为 FlushRenderingCommands 可以"等待 GPU 完成"**

`FlushRenderingCommands()` 只确保 **CPU 侧**的 RenderThread 排空了其命令队列。它不等待 GPU 执行完成。GPU 的命令可能仍在飞行中（in-flight）。等待 GPU 完成需要 `FRHICommandListImmediate::BlockUntilGPUIdle()` 或相应的 fence 机制，这属于模块 G 的内容。

## 做完模块 F 之后，你现在应该能说清楚什么

至少把下面几句话说顺，不需要查笔记：

- `FRunnable::Init()` 在新线程的上下文里调用，不是在创建线程的那条线程。`Kill(true)` 必须在 `delete Thread` 之前调用，顺序不可颠倒。
- `ENamedThreads::GameThread` 是 TaskGraph 里 GameThread 的槽位标识，投递到它的任务只有在 GameThread 自己消耗任务队列时才执行——这不等于"立刻在 GameThread 执行"。
- `ENamedThreads::AnyNormalThreadNormalTask`、`AnyHiPriThreadNormalTask`、`AnyBackgroundThreadNormalTask` 三类 worker pool 的区别在于 OS 线程优先级等级，不在于调度语义的根本差异。
- `UE::Tasks::Launch` 是 eager（立即投递），不是 stdexec 的惰性 sender 描述。`TTask<T>::Then` 是对 TaskGraph `FGraphEventRef` 依赖链的现代封装。`FPipe` 是无锁的串行化工具，底层通过隐式前置条件实现 FIFO 保证。
- `ENQUEUE_RENDER_COMMAND` 的 lambda **必须按值捕获**所有需要用到的数据。捕获引用 = 悬垂。捕获裸 `UObject*` = GC 盲点，随时 UAF。唯一安全的捕获方式：POD 值拷贝，或带引用计数的 RHI 资源句柄（`TRefCountPtr`）。
- `FlushRenderingCommands()` 阻塞 GameThread 直到 RenderThread CPU 侧排空，**不等于 GPU 完成**，**不应该在 Tick/BeginPlay 里调用**。
- UE 的三条主干线程（GameThread / RenderThread / RHIThread）的数据流向：GameThread 描述场景状态 → RenderThread 录制渲染命令 → RHIThread 提交 GPU 命令。`ENQUEUE_RENDER_COMMAND` 是 GameThread → RenderThread 的唯一标准通道；RenderThread → RHIThread 的通道是 `FRHICommandList` 的提交机制（模块 G 内容）。
