# 结课项目 1 — 集成项目

**题目**：自定义 Asset `UHeightField` 的"运行时生成 + 异步流入 + GPU 后处理显示"

---

## 一、项目目标

本项目是 UELearn Wave 2 的收束点。它不再训练单一机制，而是要求你把模块 A/B/C/D/K/E/F/G/H 已练会的每一块能力，拼接成一个从数据生成到屏幕显示的完整纵向管线，并在真实的 UE 多线程约束下跑通。

具体来说，这个项目要证明你能同时做好下面九件事：

1. 用正确的 Module 组织方式（A）声明工程依赖；
2. 用 TArray/FString（B）承载 CPU heightmap 数据与日志格式化；
3. 用 TSharedPtr（C）管理非 UObject 的跨线程预处理结果；
4. 用 UObject 机制（D）设计自定义 Asset 类型；
5. 用 Actor + Subsystem 生态（K）承载可视化和批处理管理；
6. 用 StreamableManager（E）异步加载这个 Asset；
7. 用 `UE::Tasks` + `ENQUEUE_RENDER_COMMAND`（F）跨三条主干线程传递数据；
8. 用 RHI API（G）把 CPU float 数组上传为 GPU 纹理；
9. 用 FRDGBuilder（H）把三个 pass 串成惰性渲染图，最终输出到屏幕。

**这是全套课程里唯一要求你同时看见"九条线"的题目。**

## 二、贯穿覆盖表

每一行对应一个前序模块字母，说明该模块的核心能力如何在本项目中被使用。做完项目后，你应当能对着这张表，在代码里逐行指出对应模块的知识点。

| 模块 | 在本项目中的用途 |
|---|---|
| **A** | 新建 `UELearnCap1` Module；`UELearnCap1.Build.cs` 声明五项依赖：`CoreUObject`（UObject 基类）、`Engine`（StreamableManager/Actor 生态）、`RenderCore`（RDG/ENQUEUE_RENDER_COMMAND）、`RHI`（FRHITexture/FRHICommandList）、`AssetRegistry`（PrimaryAssetType 注册）；理解每项依赖对应的 LoadingPhase 约束 |
| **B** | `TArray<float>` 作为 heightmap 的 CPU 数据容器；`FString` 用于日志前缀格式化（`[Cap1][Step N]`）；`FName` 标识 PrimaryAssetType |
| **C** | `TSharedPtr<FHeightFieldPreprocessResult>` 管理 CPU 预处理阶段的中间结果（该结构体非 UObject，不受 GC 管理，引用计数决定其生命周期）；在 `UE::Tasks` worker 与 RenderThread 之间传递时采用值捕获 |
| **D** | `UHeightField` 继承 `UObject`；`UPROPERTY(EditAnywhere) int32 Size` 与 `Resolution`；GC 可见性通过 Outer 链（挂在 UPackage 下）保证；CDO 机制体现在 Editor 侧的"新建 HeightField Asset"默认字段值；`AddToRoot` 用于运行时生成的临时实例保活 |

| **F** | `UE::Tasks::Launch` 在 TaskGraph worker 上执行 CPU 预处理（高度图归一化 + 法线预算）；任务完成后通过 `ENQUEUE_RENDER_COMMAND` 把结果投递给 RenderThread；三次显式线程跨越全部标注 |

## 三、固定约束

以下约束是验收的硬条件，缺一不可。

### 3.1 线程约束

**必须有 ≥3 次线程跨越，且每次跨越必须在代码注释中显式标注**，格式建议：

```
// [Thread Crossing 1] GameThread → UE::Tasks worker
// [Thread Crossing 2] UE::Tasks worker → GameThread (via AsyncTask) → RenderThread (via ENQUEUE_RENDER_COMMAND)
// [Thread Crossing 3] RenderThread → RHIThread (via FRHICommandList submission)
```

三次跨越的职责划分：

- **GameThread → UE::Tasks worker**：发起 CPU 预处理任务（高度图归一化、法线预算），GameThread 不阻塞等待（不允许 `FlushRenderingCommands`，也不允许阻塞 wait）；
- **UE::Tasks worker → RenderThread**：预处理完成后投递渲染命令。**注意**：若项目未启用 `FRenderCommandPipe`，在 worker lambda 内直接调用 `ENQUEUE_RENDER_COMMAND` 可能导致命令顺序不定；建议 worker 结束后先通过 `AsyncTask(ENamedThreads::GameThread, ...)` 跳回 GameThread，再在 GameThread 侧调用 `ENQUEUE_RENDER_COMMAND`，把 `TSharedPtr<FHeightFieldPreprocessResult>` 按值捕获传入。本项目默认采用后者（"worker → GameThread → RenderThread"两跳方式）。三次线程跨越因此等于：GameThread → worker（跨越 1）→ GameThread（跨越 2）→ RenderThread（跨越 3，由 ENQUEUE 触发）；
- **RenderThread → RHIThread**：`FRDGBuilder::Execute()` 内部把录制好的 `FRHICommandList` 提交给 RHIThread，这一步由 RDG 框架完成，你需要理解发生了什么并在日志/注释中标出。

### 3.2 GC 约束

- **≥1 `UPROPERTY` 包装 `UObject` 引用**：`AHeightFieldVisualizer` 的成员 `TObjectPtr<UHeightField> HeightFieldAsset` 必须加 `UPROPERTY`，否则 GC 在下一个 GC 周期就会踢掉它；
- **≥1 `TSharedPtr` 管理非 UObject**：`FHeightFieldPreprocessResult` 是普通 struct，用 `TSharedPtr<FHeightFieldPreprocessResult, ESPMode::ThreadSafe>` 管理，不得用 `NewObject` 创建，不得加 `UCLASS`；
- **禁止裸 `new UObject`**：所有 UObject 创建必须走 `NewObject<T>` 或 `CreateDefaultSubobject<T>`；
- **禁止裸 `UObject*` 成员变量**：UPROPERTY 内用 `TObjectPtr<T>`，UPROPERTY 外如需持有 UObject 引用必须用 `TWeakObjectPtr<T>` 并处理 stale 情况。

### 3.3 Actor + Subsystem 约束（§9.1 新增）

- **≥1 `AActor` 承载可视化**：`AHeightFieldVisualizer` 必须是 `AActor` 子类，具备 `BeginPlay`/`EndPlay` 两个钩子的实现；可视化的 RT 最终通过此 Actor 的 `UMaterialInstanceDynamic` 或 SceneCapture 机制展示（或直接 dump PNG，两者皆可）；
- **≥1 `UWorldSubsystem` 管理批处理**：`UHeightFieldSubsystem` 必须继承 `UWorldSubsystem`，在 `Initialize` 中注册队列，`Deinitialize` 中清理；批处理队列（`TArray<FSoftObjectPath>`）和提交逻辑（`SubmitBatch`）放在这里，而不是放全局变量。

### 3.4 渲染约束

- **禁止 `FlushRenderingCommands`**：不允许在 GameThread 侧调用 `FlushRenderingCommands` 来等待渲染结果，必须用异步回调或 delegate 通知；
- **RDG Pass 必须有 `SHADER_PARAMETER_STRUCT` 宏**：每个 pass 的参数结构体必须用 `BEGIN_SHADER_PARAMETER_STRUCT` / `END_SHADER_PARAMETER_STRUCT` 声明，并包含正确的 `RDG_TEXTURE_ACCESS` 或 `SHADER_PARAMETER_RDG_TEXTURE` 宏，否则 RDG validation 会报错。

## 四、运行形态

### 4.1 Console 命令触发

在 Editor 内打开 Output Log，输入：

```
UELearn.Cap1.Run <size> <resolution>
```

示例：`UELearn.Cap1.Run 512 256`

参数含义：
- `<size>`：HeightField 的世界空间边长（整数，单位 cm）；
- `<resolution>`：heightmap 的像素分辨率（整数，必须是 2 的幂次）。

命令由 `IConsoleManager::Get().RegisterConsoleCommand` 注册，注册时机在 `UHeightFieldSubsystem::Initialize` 内，以确保 World 已经存在。

### 4.2 日志时序

每个阶段必须打印带前缀的日志，顺序如下：

```
[Cap1][Step 1] GameThread: UHeightField asset created (size=512, res=256)
[Cap1][Step 2] GameThread: FStreamableManager async load requested
[Cap1][Step 3] GameThread: Load callback received, dispatching UE::Tasks worker
[Cap1][Step 4] Worker: CPU preprocess started (normalize + normal estimate)
[Cap1][Step 5] Worker: CPU preprocess done, enqueuing render command
[Cap1][Step 6] RenderThread: RHI texture upload started (R32_FLOAT, 256x256)
[Cap1][Step 7] RenderThread: RHI texture upload done
[Cap1][Step 8] RenderThread: FRDGBuilder pass 1/2/3 added
[Cap1][Step 9] RenderThread: FRDGBuilder::Execute() called
[Cap1][Step 10] RenderThread: PNG dump triggered (pass1.png / pass2.png / pass3.png)
```

`UE_LOG(LogTemp, Display, TEXT("[Cap1][Step %d] %s"), StepN, *Message)` 即可满足要求。注意 Step 4/5 在 worker 线程，Step 6-10 在 RenderThread——打印前加 `check(IsInRenderingThread())` 是好习惯。

### 4.3 PNG 截图

每个 RDG pass 执行完成后，把对应的 RT dump 到 `<ProjectDir>/Saved/Cap1/pass1_heightfield.png`、`pass2_normal.png`、`pass3_gamma.png`。推荐以下两条路径之一：

**路径 A（推荐）**：在 RenderThread 完成后，通过 `AsyncTask(ENamedThreads::GameThread, ...)` 跳回 GameThread，在 GameThread 侧使用 `FImageWrapperModule::GetImageWrapper(EImageFormat::PNG)` 将 readback 得到的像素数据压缩为 PNG，再用 `FFileHelper::SaveArrayToFile` 落盘。这条路径不依赖 `UTextureRenderTarget2D`，完全走 RHI readback + CPU 压缩路径。

**路径 B**：若项目已有 `UTextureRenderTarget2D` 作为 RDG 输出目标，可在 GameThread 调用 `FImageUtils::ExportRenderTargetAsPNG(UTextureRenderTarget2D* RenderTarget, ...)` 直接落盘。注意：此函数接受 `UTextureRenderTarget2D*`，而非 RDG/RHI 裸资源句柄——若 RDG 输出是裸 `FRDGTextureRef`，需先将其 copy 到 `UTextureRenderTarget2D`（`FRenderTarget` 接口）再调用。

无论哪条路径，PNG 压缩写盘均须在 GameThread（或独立线程）完成，这带来了第四次（可选）线程跨越：从 RenderThread 回到 GameThread 的 readback callback。

### 4.4 不要求可玩 demo map

不需要放置任何 Pawn、PlayerController 或 Camera Actor。Editor 里点 PIE 后执行 console 命令即可。`AHeightFieldVisualizer` 的坐标默认在世界原点，不需要玩家能"走到"它面前。

### 5.3 对象生命周期图

从 console 命令触发到 World 销毁，四个关键对象的完整弧：

```
UHeightFieldSubsystem
  创建: World::InitializeSubsystems()
  ↓
  持有: TArray<FSoftObjectPath> BatchQueue
  ↓

UHeightField (运行时生成)
  创建: NewObject<UHeightField>(GetTransientPackage())
  ↓ TransientPackage 作 Outer，Outer 链已保 GC 可见；

  ↓ BeginPlay → 注册渲染回调
```

### 5.5 四固定问题书面回答

按 01-心智模型 § 四固定问题的格式，逐一书面回答：

**Q1：执行真正开始时刻？**
Console 命令注册在 `UHeightFieldSubsystem::Initialize`（World 创建后立即可用）。执行从 GameThread 的 `IConsoleManager` 回调开始——此时 `UELearn.Cap1.Run` 被调用，触发 `NewObject<UHeightField>` + `RequestAsyncLoad`。CPU 预处理在 `UE::Tasks::Launch` 后真正开始（worker 线程排到时）。RHI 纹理上传在 `ENQUEUE_RENDER_COMMAND` 的 lambda 被 RenderThread 排到并执行时开始。RDG 的 GPU 命令录制在 `FRDGBuilder::Execute()` 内部，精确时刻为 RenderThread 调用 `Execute` 的那一行。

**Q2：生命周期拥有者？**
`UHeightField`（运行时生成）：`AddToRoot` 加入根集 → StreamableManager 加载完成 → 由 `AHeightFieldVisualizer` 的 `UPROPERTY TObjectPtr<UHeightField>` 接管 GC 可见性 → Actor 销毁时引用消失 → 下一次 GC 回收。`AHeightFieldVisualizer`：生命周期归 `UWorld`，World 调用 `SpawnActor` 创建，`DestroyActor` 或 World 销毁时回收。`UHeightFieldSubsystem`：生命周期绑定 `UWorld`，由 Subsystem 框架自动管理，不需要手动 `NewObject`。`TSharedPtr<FHeightFieldPreprocessResult>`：引用计数归零时自动析构，归零点在 RenderThread 的 `ENQUEUE_RENDER_COMMAND` lambda 执行完毕（lambda 本身持有最后一个 shared_ptr 拷贝）。RDG transient textures：`FRDGBuilder::Execute()` 完成后由 RDG transient pool 回收，最晚在 Execute 返回时。

**Q3：涉及哪些 Named Thread？**
`GameThread`：Asset 创建、RequestAsyncLoad、StreamableHandle 回调、console 命令、PNG dump。`TaskGraph worker pool`（UE::Tasks）：CPU 预处理（归一化、法线估算），由 `UE::Tasks::Launch(TEXT("HeightFieldPreprocess"), ...)` 投递。`RenderThread`：RHI 纹理上传、`FRDGBuilder::AddPass` × 3、`FRDGBuilder::Execute()`，在 `ENQUEUE_RENDER_COMMAND` lambda 内执行。`RHIThread`：`FRHICommandList` 录制完成后提交 GPU 命令（由 RDG 框架通过 `FRHICommandListImmediate::Submit` 或 Task 链完成，代码不需要手动触发）。

**Q4：涉及 UObject 时怎么对 GC 可见？**
`UHeightField`（运行时生成，无 Outer 链接时）：调用 `AddToRoot()` 强制加入根集，加载完成 callback 里 `RemoveFromRoot()` 并改用 `AHeightFieldVisualizer` 的 `UPROPERTY` 持有（方式 ①③ 组合）。`AHeightFieldVisualizer` 的 `TObjectPtr<UHeightField> HeightFieldAsset`：加 `UPROPERTY`，GC 遍历 Actor 时可见（方式 ①②）。`UHeightFieldSubsystem`：挂在 `UWorld::SubsystemCollection` 的 Outer 链上，World 可达则 Subsystem 可达（方式 ④）。`FHeightFieldPreprocessResult`：非 UObject，完全不涉及 GC，由 `TSharedPtr` 引用计数管理（方式 ⑤）。

## 六、验收点

以下 9 条全部满足，项目才算通过。

1. **代码编译通过**：`UELearnCap1.Build.cs` 声明全部 5 项依赖，无隐式跨 Module 符号引用（UBT 不报 "Missing module dependency" 警告）；
2. **Console 命令可触发**：在 PIE 内输入 `UELearn.Cap1.Run 256 128` 后，Output Log 出现 Step 1–10 的完整日志序列，无乱序；
3. **三次线程跨越有代码注释**：在对应行附近有 `// [Thread Crossing N]` 格式注释，并与时序图（交付物 5.1）对应；
4. **约束全满足**：`≥1 UPROPERTY 包装 UObject`，`≥1 TSharedPtr 非 UObject`，`≥1 AActor 承载可视化`，`≥1 UWorldSubsystem 管理批处理`，`禁 FlushRenderingCommands`，`禁裸 new UObject`，`禁裸 UObject* 成员`；
5. **RDG 三 pass 流水线完整**：三个 pass 各有独立的 `SHADER_PARAMETER_STRUCT`，资源依赖关系通过 RDG 的 `FRDGTextureRef` 传递，不手动插入 barrier；
6. **PNG 截图三张产出**：文件存在，非空，三张图视觉上有可区分差异；
7. **GC 无崩溃**：运行 5 次 console 命令（累积触发 GC 压力），程序无 `ObjectIsNull` 断言或 stale pointer crash；
8. **六件交付物齐备**：时序图、RDG 依赖图、对象生命周期图、模块依赖图、四固定问题书面回答、PNG 截图全部提交；

## 七、常见坑专节

以下坑均来自本项目涉及机制的典型误用，每一条都足以让项目卡在某个步骤上。建议在开发每个阶段前先读一遍对应的坑。

### 坑 1：`ENQUEUE_RENDER_COMMAND` lambda 按引用捕获 GameThread 变量

**现象**：RenderThread 执行时读到垃圾值，或 `check(IsInRenderingThread())` 之后解引用崩溃。

**原因**：`ENQUEUE_RENDER_COMMAND` 的 lambda 在 GameThread 构造，在 RenderThread 异步执行。构造时的 GameThread 栈帧（局部变量的地址）在执行时已经失效。如果捕获了 `UObject*` 裸指针，GC 可能已经回收了该对象。

**正确做法**：所有要传入 lambda 的数据必须**按值捕获**。对于 `UHeightField`，捕获 `TObjectPtr<UHeightField>`（会触发 access barrier，Editor 下更安全）或者提前把需要的数据（如纹理描述符）提取出来按值捕获。对于 `FHeightFieldPreprocessResult`，捕获 `TSharedPtr<FHeightFieldPreprocessResult>`（引用计数保证 RenderThread 执行期间对象仍活）。

**来源**：01-心智模型 §Mindset Shift 3、模块 F `ENQUEUE_RENDER_COMMAND` 常见坑。

### 坑 2：`UHeightField` 未挂 Outer 链且未 `AddToRoot` 导致 GC 提前回收

**现象**：`RequestAsyncLoad` 的 callback 里，`UHeightField*` 已经是 nullptr 或 `IsValid()` 返回 false，即使代码里看起来还持有指针。

**原因**：若用 `NewObject<UHeightField>(nullptr)` 或把 Outer 设为非根对象创建实例，且没有任何 `UPROPERTY` 指向它，也没有 `AddToRoot`，GC 在下一次 mark-sweep 时会把它标记为不可达并回收——这可能发生在 `RequestAsyncLoad` 的异步等待期间。相比之下，`NewObject<UHeightField>(GetTransientPackage())` 以 TransientPackage 为 Outer，Outer 链本身已保证 GC 可见，此时 `AddToRoot` 冗余但无害。

**正确做法（Outer 为 nullptr 或非根对象时）**：创建后立即 `HeightField->AddToRoot()`；在加载完成 callback 里将其赋给 `AHeightFieldVisualizer` 的 `UPROPERTY TObjectPtr<UHeightField> HeightFieldAsset`，然后 `HeightField->RemoveFromRoot()`，此后由 UPROPERTY 的 GC 可见性接管。

**来源**：模块 D §AddToRoot 与 RF_RootSet、01-心智模型 §Mindset Shift 4。

### 坑 3：RDG Pass 的 Shader Parameter Struct 遗漏 `RDG_TEXTURE` 宏

**现象**：Editor 启动时 Shader 编译通过，但 PIE 运行时 RDG validation（`-rdgvalidation`）报 `Missing resource` 或 `Pass reads resource that was not declared`。

**原因**：RDG 在 `Execute()` 前会遍历每个 pass 的 parameter struct，检查所有声明的资源是否已经正确设置读/写标志。如果你的 pass 读取一个纹理但 parameter struct 里没有用 `SHADER_PARAMETER_RDG_TEXTURE`（而是直接放了 `FRHITexture*`），RDG 不知道这个依赖，既不会插入 barrier，也不会在 validation 里验证，最终可能读到转换前的资源状态，导致 GPU 端错误或黑屏。

**正确做法**：每个 pass 的 parameter struct 必须用 `BEGIN_SHADER_PARAMETER_STRUCT` / `END_SHADER_PARAMETER_STRUCT`，读取纹理用 `SHADER_PARAMETER_RDG_TEXTURE`，写入 RT 用 `RENDER_TARGET_BINDING_SLOTS()`，不要混用 RHI 裸资源和 RDG 资源句柄。

**来源**：模块 H §RDG Pass 描述常见坑、`Engine/Source/Runtime/RenderCore/Public/RenderGraphResources.h`。

### 坑 4：PNG 截图全黑

**现象**：截图产生但全黑，三张图没有差异。

**两种常见原因**：

a) **RT 格式不匹配**：`FImageUtils::ExportRenderTarget2DAsPNG` 要求 RT 的 Pixel Format 为 `PF_B8G8R8A8`（或可转换的格式）。如果你的 final_rt 格式是 `PF_FloatRGBA`，直接 readback 会得到 0 或 clamp 到 0。解决：在 Pass3 输出时显式转换到 `PF_B8G8R8A8`，或用 `FReadSurfaceDataFlags` 指定 linear to sRGB 转换。

b) **Readback 时机错误**：在 `FRDGBuilder::Execute()` 返回之前就调用 readback，GPU 命令还没执行完。解决：readback 必须在 Execute 返回之后，或者用 `AddReadbackPass` 在 RDG 图内部安排 readback，确保在 RenderThread 完成序列中正确排队。

### 坑 5：Initialize 时 World 未 BeginPlay / Level 未就绪

**现象**：在 `Initialize` 里调用 `GetWorld()->SpawnActor<AHeightFieldVisualizer>()` 崩溃（nullptr dereference），或者 console 命令注册后 World 指针悬空。

**原因**：`UWorldSubsystem::Initialize` 在 World 的初始化序列早期调用，此时 `GetWorld()` 可能已经有效，但 World 的 BeginPlay 还没触发，Level 也可能还没 streaming 进来。在 Initialize 里 SpawnActor 是允许的，但不能假设 Level 已经准备好。

**正确做法**：`AHeightFieldVisualizer` 的 SpawnActor 放在 `UWorldSubsystem::OnWorldBeginPlay` 里（而不是 `Initialize`），这确保了 World 和 Level 都已经初始化完成，PersistentLevel 可用。console 命令的注册可以在 `Initialize` 里进行（此时 World 已存在），但对 World 状态有依赖的操作必须延迟到 `OnWorldBeginPlay`。

**来源**：模块 K §UWorldSubsystem 生命周期、01-心智模型 §Mindset Shift 6。

### 坑 5.1：`ExportRenderTarget2DAsPNG` 只接受 `UTextureRenderTarget2D*`；RDG/RHI 裸资源需先 copy

**现象**：调用 `FImageUtils::ExportRenderTarget2DAsPNG` 时编译报错"no matching function"，或传入 `FRHITexture*` / `FRDGTextureRef` 后崩溃。

**原因**：`FImageUtils::ExportRenderTarget2DAsPNG`（以及 `ExportRenderTargetAsPNG`）的参数类型是 `UTextureRenderTarget2D*`，是 UObject 层的 RT 包装。RDG 的 `FRDGTextureRef` 和 RHI 的裸 `FRHITexture*` 都不是 `UTextureRenderTarget2D`，不能直接传入。

**正确做法**：若想复用此接口，须先在 GameThread 创建 `UTextureRenderTarget2D`，并将 RDG/RHI 输出 copy 到该对象的 `FRenderTarget`；或改走 §4.3 路径 A（`FImageWrapperModule` + `FFileHelper::SaveArrayToFile`），完全绕开 `UTextureRenderTarget2D` 依赖。

**来源**：§4.3 PNG 截图路径说明。

### 坑 6：`FStreamableHandle` 生命周期过短

**现象**：`RequestAsyncLoad` 调用后 callback 从未被调用，或 callback 被调用但 Asset 已经被卸载。

**原因**：`FStreamableManager::RequestAsyncLoad` 返回一个 `TSharedPtr<FStreamableHandle>`。如果你不保存这个 handle（让它立即析构），StreamableManager 认为请求已经被取消，Asset 不会被加载或者加载到一半被中止。

**正确做法**：在 `UHeightFieldSubsystem`（或 `AHeightFieldVisualizer`）里声明成员变量 `TSharedPtr<FStreamableHandle> LoadHandle`，持有 handle 直到 callback 完成，然后在 callback 里 `LoadHandle.Reset()` 释放。

**来源**：模块 E §FStreamableManager 生命周期管理常见坑。

### 坑 7：`UE::Tasks::Launch` 捕获了 `this`（UObject）

**现象**：在 worker 线程里解引用 `this->HeightFieldAsset` 崩溃，或 sanitizer 报 data race。

**原因**：UObject 的大多数成员函数和成员变量只能在 GameThread 上安全访问。在 `UE::Tasks::Launch` 的 lambda 里捕获 `this`（一个 `UWorldSubsystem*` 或 `AActor*`）并在 worker 上解引用，是线程安全违规——GC 也可能在此期间回收对象。

**正确做法**：在 GameThread 侧（Launch 之前）把需要传给 worker 的数据提取为局部 POD 或 `TSharedPtr`，按值捕获进 lambda。对 `TSharedPtr<FHeightFieldPreprocessResult>` 这类非 UObject 容器，可以安全地在 worker 里访问（因为 `TSharedPtr<T, ESPMode::ThreadSafe>` 的引用计数是线程安全的）。

## 八、可选网络扩展（串 J）

本节内容**不纳入必做约束**，不影响正式验收。但如果你已完成模块 J，以下扩展是把 Cap1 与 J 完整串联的最优路径。

### 8.1 Dedicated Server/Client 两端触发

在 `UHeightFieldSubsystem` 的 console 命令处理里，用 `GetWorld()->GetNetMode()` 判断当前是 Server 还是 Client：

- Server 端：生成 HeightField 数据，走完整管线，通过 NetMulticast RPC 通知所有 Client；
- Client 端：收到 RPC 后，本地也执行一次异步加载 + GPU 显示（但用服务端发来的 `FSoftObjectPath`，而非自己生成）。

### 8.2 `UHeightField` 作为 Replicated UPROPERTY

把 `AHeightFieldVisualizer` 设置为 `bReplicates = true`，并在其中声明：

```cpp
UPROPERTY(ReplicatedUsing = OnRep_HeightFieldAsset)
TObjectPtr<UHeightField> HeightFieldAsset;
```

在 `GetLifetimeReplicatedProps` 里加 `DOREPLIFETIME(AHeightFieldVisualizer, HeightFieldAsset)`，实现 Server 向 Client 的 HeightField Asset 引用同步。

**注意**：`UHeightField` 必须是已正确序列化的 UAsset（有 `UPackage` 和真实的 `.uasset` 文件），才能被 replication 系统序列化为 `FNetworkGUID` 并在 Client 上重建引用。运行时 `NewObject<UHeightField>(GetTransientPackage())` 创建的临时对象没有持久 GUID，无法直接通过 replication 传递——这是网络扩展中最重要的设计约束，也是串联 E（资产序列化）和 J（网络）两个模块的关键接合点。

### 8.3 PIE 运行形态

使用 PIE + Number of Players = 2（一个 Server，一个 Client）。在 Server 端执行 console 命令，观察 Client 端是否收到 `OnRep_HeightFieldAsset` 回调并触发本地渲染管线。

## 九、建议开发节奏（3 天）

本项目预计需要 3 天完成，以下是分阶段的推进建议。建议严格按顺序，每个阶段都有独立的可验证结果，不要跳步合并。

### Day 1：基础设施 + 数据层（A/B/C/D/K/E）

### Day 2：并发层 + GPU 层（F/G）

4. Day 2 上午验收：Step 4/5 日志出现，且 Step 4 打印时 `IsInGameThread()` 为 false（在 worker 里），Step 5 打印时 `IsInGameThread()` 为 true（已跳回 GameThread 侧，ENQUEUE 调用前），Step 6 打印时 `IsInRenderingThread()` 为 true。

**下午（3–4 小时）**

5. 在 `ENQUEUE_RENDER_COMMAND` lambda 里：
   - 用 `FRHITextureCreateDesc::Create2D(...)` + `RHICreateTexture` 创建 R32_FLOAT 格式纹理，打印 Step 6；
