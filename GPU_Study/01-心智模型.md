# 01 心智模型：GPU 是什么样的一台机器

## 为什么需要一份心智模型

很多人第一次写 CUDA kernel 时，会不自觉地把 GPU 当作"有更多核心的 CPU"来思考。这个直觉既不完全错误，也不完全正确——它会让你写出能跑的代码，但写不出高效的代码。

CPU 的设计哲学是：用复杂逻辑和大缓存来让单条指令流跑得快。延迟优先，吞吐次之。

GPU 的设计哲学恰好相反：用成千上万个简单执行单元并行跑，忍受单条流的长延迟，以换取海量吞吐。吞吐优先，延迟次之。

这个差异在三个地方最明显：
- **SIMT vs SIMD**：CPU 多核是每个核独立执行（MIMD），GPU 是数十个线程绑在一个"warp scheduler"上同步执行（SIMT）。分歧代价巨大。
- **内存墙**：GPU 内存带宽是 CPU 的 10–100 倍，但延迟反而略长。你不能靠缓存逃脱，只能靠吞吐压过延迟。
- **延迟 vs 吞吐**：CPU 优化关键路径的时间。GPU 优化"有多少工作同时在飞"。

## GPU 的四层线程模型

一个 GPU kernel 启动时，你描述的是一个四层树状结构：

```
GPU 物理硬件
  ↓
SM₀ SM₁ ... SM_N（10–100 个流式多处理器）
  ↓ 每 SM 含
Warp Scheduler × 2–4（调度器）
  ↓ 每调度器调度
32 个 lane（0–31 号线程，在锁步中执行）
  ↓ 映射关系
grid → block → warp → lane
```

对应 CUDA 代码：
- `grid` = `<<<gridDim, blockDim>>>`：GPU 级，包含若干 block
- `block` = `blockIdx.x/y/z`：一个 SM 上的线程集合，共享 shared memory 和 `__syncthreads`
- `warp` = 32 个线程：SM 调度的最小单位，同步 SIMT 执行
- `lane` = 单个线程：threadIdx（绝对编号）

关键观察：warp 是不可再分的。一个 warp 的 32 个线程必须按 lockstep 同步。如果其中一个走 if，其余也必须等它，只是执行单元disable。这叫 **warp divergence**，代价昂贵。

## 内存层级的五层

GPU 内存读写不是"一个延迟"：

```
寄存器 register        延迟 ~1 ns    带宽 ~19 TB/s
  ↓
L1 缓存 + 共享内存     延迟 ~20 ns   带宽 ~6 TB/s
  ↓
L2 缓存              延迟 ~60 ns   带宽 ~4 TB/s
  ↓
HBM 全局内存         延迟 ~200 ns  带宽 ~900 GB/s (H100)
  ↓
常量内存（广播优化）  延迟 ~20 ns   带宽取决于 hit
  ↓
纹理内存（2D缓存+插值） 特化用途
```

L1 和 shared memory 是同一块物理存储（96 KB / SM），可配。寄存器是超标量（每线程最多 255 个 32-bit 寄存器）。

带宽瓶颈往往在全局内存——1000 个线程竞争 900 GB/s，每线程平均 900 KB/s。如果你的内存访问不合并（coalescing），会被分散成多次事务，带宽掉 10 倍。

## 执行模型的三大约束

### 1. Warp Lockstep / 分歧

32 个线程绑定在一起同步执行。只要有一个线程走 if 分支，其余 31 个也得停下等。这不是软件缓冲，是硬件无法直接调度两条不同路径。

结果：**分歧越少，利用率越高**。极端情况下（所有线程都分歧），吞吐掉到 1/32。

### 2. Bank Conflict / Shared Memory 访问模式

Shared memory 被分成 32 个 bank，每 bank 4 字节宽。同一 warp 的多个线程同时访问同一 bank 会被串行化（bank conflict）。

逃脱方式：
- 确保同一 warp 的线程访问不同 bank（stride-1 合并是最优的）
- 或者用 padding 填充，把某些线程的访问"错开"到不同 bank

### 3. 占用率 / 资源竞争

每个 SM 最多 2048 个线程（Hopper）。如果你的 kernel 每线程用 200 个寄存器 + 100 字节 shared memory，占用率会很低。低占用率 = SM 大量空闲周期，无法隐藏内存延迟。

## Hopper 之后的新维度

Ampere (sm_80) 和 Ada (sm_89) 是"之前"的时代。Hopper (sm_90a) 带来了三个新概念：

### 1. Cluster = 跨 Block 的 Shared Memory

一个 cluster 包含多个 block，它们可以互相访问彼此的 shared memory（分布式 smem）。这打破了"block 是隔离的"假设，支持新的数据移动模式。

### 2. TMA = 硬件 DMA 搬运张量

`cp.async.bulk.tensor`（Tensor Memory Accelerator）是一个硬件单元，可以异步搬运多维张量，而不需要 kernel 代码显式管理每个元素。大幅降低了数据移动的代码复杂度和延迟。

### 3. WGMMA = Warp-Group 矩阵乘法

从 wmma（单 warp）→ mma.sync（单 warp，更灵活）→ wgmma（64 线程协作），矩阵乘法操作变成了"一个 warp 组做一次"，而不是"一个 warp 做一次"。数据流量和流水效率都提升了。

### 4. MBarrier = 异步屏障

替代了 `__syncthreads`。`mbarrier` 支持"等待某个数量的字节被搬运完毕"，而不是"所有线程都到达"。非常适合 TMA + producer-consumer 模式。

## Amdahl / Gustafson 给你的警告

GPU 加速能提升多少？理论答案是 **(GPU 吞吐 / CPU 吞吐) × (可并行部分 / 总工作)**。

但实践中，瓶颈来自三个地方：

1. **串行部分**（Amdahl）：即使 GPU 快 100 倍，如果 10% 的工作必须在 CPU 上串行做，整体加速最多 10 倍。
2. **数据搬运开销**：Host ↔ Device 的 PCIe 带宽是 GPU 内存的 1/10。如果搬运时间 > 计算时间，加速反而是负的。
3. **同步点和碎片化**：多个小 kernel 依次执行，每次都要同步回 host，launch overhead 吃掉收益。

正确的思路是：**把尽可能多的工作合并进一个大 kernel，最小化搬运和同步开销**。

## 本练习包教你用哪种思维方式

这套教程的三个承诺：

1. **先 tile 再 kernel**：先在纸上画出数据分块（tile）和线程映射，再写代码。不要上来就试。
2. **先正确再优化**：写出能通过 assert 的 naive 版本，再用 Nsight 找瓶颈，再针对性优化。不要过早优化。
3. **先 Nsight 再调参**：看一次 Nsight Compute 的 roofline 图，比调 1000 遍 block size 管用。

## 四层线程映射简图

```
Grid (GPU 级别启动)
├─ Block (0,0)  [SM0 上执行]
│  ├─ Warp 0 [lane 0–31]  
│  │  ├─ thread 0 (lane 0)
│  │  ├─ thread 1 (lane 1)
│  │  ├─ ...
│  │  └─ thread 31 (lane 31)
│  ├─ Warp 1 [lane 0–31]
│  └─ ...
├─ Block (1,0)  [SM1 上执行]
│  ├─ Warp 0
│  └─ ...
└─ Block (N,M)  [可能在 SM0 或 SM1 或后续轮入]

硬件调度策略：
- 一个 SM 上同时可以有 2-4 个活跃 block（取决于占用率）
- 每个 warp scheduler 轮询 warp，选一个有指令的 warp 下发
- Warp 内 32 个 lane 锁步执行；分歧时，inactive lane disable
```
