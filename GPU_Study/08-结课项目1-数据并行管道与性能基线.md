# 08 结课项目 1：数据并行管道与性能基线

## 项目目标

这是 Stage 1 的出口。你会把模块 A–F 学过的所有技术串联起来，完成一条从"读取图像"到"输出统计结果"的端到端 GPU 管道，并用 Nsight 工具链深度剖析它的性能。

核心任务是：**写一个多步骤的数据处理管道，每步都是独立的 kernel，用多 stream 实现步骤间的并发与数据重叠，用 CUDA Graph 打包整个管道消除 launch 开销，最后用 Nsight Systems 和 Nsight Compute 完整剖析性能瓶颈，绘制 roofline 图，给出基准数据。**

## 前置知识

- **必读** 模块 A–F 全部完成且理解。
- 理解 kernel fusion 动机：多个小 kernel 可能被拆成独立步骤（便于维护），也可以合并（节省 launch 开销）。
- 能用 CMake 组织多文件项目（或单文件也可）。
- 有兴趣在 Nsight 中花时间搞懂性能数据。

## 硬件与工具链要求

- **最低 Compute Capability**：CC 8.0（Ampere）；CC 9.0a（Hopper）最佳。
- **CUDA Toolkit**：13.x。
- **GPU 显存**：至少 4 GB（便于 8K 分辨率测试）；2 GB 仍可运行，但限于较小分辨率。
- **Nsight 工具**：Nsight Systems（`nsys`）+ Nsight Compute（`ncu`）+ compute-sanitizer。
- **样例硬件**：Hopper sm_90a 为主；Ampere/Ada 回退对比。

## 综合任务：图像统计管道

### 任务概述

**场景**：从 host 端生成或加载一张大尺寸的 2D 图像（float32，分辨率 4K/8K/16K 可选），对其进行一系列数据处理操作，输出统计结果。

**关键约束**：
- 每个处理步骤用独立的 kernel。
- 用多 stream 并发执行相邻步骤。
- 用 CUDA Graph 打包整个管道，支持重放测峰值吞吐。
- 每步用 NVTX range 标注，便于 Nsight Systems 观察。
- 每步用 `cudaEvent` 计时。

### 管道步骤（共 5 大步）

**Step 1：归一化（Normalize）**
- 输入：原始浮点图像（H × W，shape 为 [height, width]）。
- 操作：按通道计算均值和方差，然后 `(pixel - mean) / sqrt(var + eps)`。
- 使用 Welford 在线算法计算均值方差，减少多 pass 的数据移动。
- 输出：归一化后的图像（同大小）。
- **Kernel 骨架**：`kernel_normalize(float* in, float* out, int H, int W, float* channel_mean, float* channel_var)`。

**Step 2：直方图统计（Histogram）**
- 输入：归一化后的图像。
- 操作：统计像素值的分布。实现两个版本对比：
  - **V1**：朴素版，用全局内存的 atomic increment 累加直方图（容易成为 bottleneck）。
  - **V2**：优化版，每个 block 维护本地直方图，最后 atomic merge 到全局。
- 输出：256 bin 的直方图（或按需选择 bin 数）。
- **Kernel 骨架**：`kernel_histogram_atomic(float* data, int H, int W, int* hist)` 和 `kernel_histogram_privatized(...)` 两版。

**Step 3：2D 卷积（Convolution）**
- 输入：前一步的输出。
- 操作：3×3 或 5×5 卷积滤波（例如高斯或 Sobel）。
- 使用 shared memory tile + halo 加载，避免 global memory 重复读取。
- 输出：卷积结果（边界处理：zero-padding）。
- **Kernel 骨架**：`kernel_conv2d_shared(float* in, float* out, int H, int W, float* kernel, int K_size)`。

**Step 4：Inclusive Scan（扫描）**
- 输入：卷积结果（可以看作 1D，逐行或逐列扫描）。
- 操作：计算前缀和（inclusive prefix sum）。实现两个版本对比：
  - **V1**：Hillis-Steele 算法（并行度高，但 work-efficient 差）。
  - **V2**：Blelloch 算法（更 work-efficient，但实现复杂）。
- 输出：前缀和数组（同大小）。
- **Kernel 骨架**：`kernel_scan_hillis_steele(...)` 和 `kernel_scan_blelloch(...)`。

**Step 5：排序（Radix Sort）**
- 输入：前缀和数组（视为 key-value 对，key 是值本身，value 是原始索引）。
- 操作：对 32-bit key 进行基数排序。可选：
  - 用 CUB（Cooperative Thread Blocks）库的原语 `cub::DeviceRadixSort`。
  - 或手工实现 digit histogram + scan + scatter 三步。
- 输出：排序后的 key-value 对。
- **Kernel 骨架**：如果用 CUB，则是 API 调用；如果手工实现，则 `kernel_radix_digit_hist`、`kernel_radix_scatter` 等。

### 聚合与性能测量

**多 stream 并发组织**：
```
stream 0: load_host_to_device(image) 
          -> kernel_normalize 
          -> kernel_histogram 
          -> kernel_conv2d
          -> kernel_scan
          -> kernel_radix_sort
          -> memcpy_device_to_host(results)

stream 1: (optional) 并行的验证 kernel（例如计算 checksum）

...可以用 event 和 cudaStreamWaitEvent 构造依赖。
```

**CUDA Graph 封装**：
- 用 stream capture 或 explicit graph API 把整个管道打包。
- 支持参数更新（例如不同分辨率的输入）。
- Replay 10-100 次测峰值吞吐。

**计时与 Nsight 标注**：
```
nvtx_scoped_range scope("Normalize");
// kernel_normalize launch

nvtx_scoped_range scope("Histogram");
// kernel_histogram launch

// 类似...
```

## 必做任务（共 6-8 步）

1. **搭建项目骨架**：
   - 创建 `exercises/capstone1/` 目录。
   - 写 `CMakeLists.txt`，确保能编译 CUDA 代码。
   - 包含 `common/cuda_check.cuh`, `common/timer.cuh`, `common/nvtx_range.cuh`。

2. **实现 Normalize kernel**：
   - 读入浮点数组，计算均值方差（用 Welford 或 reduce kernel）。
   - 输出归一化结果。
   - 验证正确性（比对 CPU 计算）。

3. **实现 Histogram kernel（两版）**：
   - atomic 版：直接写全局内存（baseline，可能很慢）。
   - privatized 版：shared memory 本地累加，最后 atomic merge。
   - 对比两版的性能（用 Nsight Compute 或计时）。

4. **实现 Conv2D kernel**：
   - 3×3 或 5×5 高斯卷积。
   - 用 shared memory tile + halo 减少 global memory 访问。
   - 验证输出（与 CPU 卷积对比）。

5. **实现 Scan kernel（两版）**：
   - Hillis-Steele：轻量实现，O(n log n) work。
   - Blelloch：更复杂但 O(n) work，尽力实现或参考 CUB。
   - 对比性能。

6. **实现 Radix Sort**：
   - 用 CUB 的 `cub::DeviceRadixSort::SortPairs` 封装（推荐），或手工实现基本三步。
   - 验证排序正确性。

7. **组织管道与并发**：
   - 用 1-2 条 stream 启动 5 个 kernel（某些可串行，某些可并发）。
   - 用 event 和 `cudaStreamWaitEvent` 建立依赖（或直接串行）。
   - 用 CUDA Graph capture 或 explicit API 打包。
   - 测 replay 100 次的总耗时，计算平均 throughput。

8. **Nsight 采样与分析**：
   - `nsys profile -o capstone1_trace --stats=true ./capstone1`，采集时间线。
   - 对每个 kernel 分别用 `ncu --set full -o report_k<i> ./capstone1`，采集详细指标。
   - 对至少 3 个 kernel 计算 roofline 位置，绘制到同一张图上。

## 进阶任务（3-4 分支，选做）

### 分支 A：FP16 重写与 TensorCore 利用

- 用 FP16 重写 normalize、conv2d 等步骤。
- 用 `__half` 类型或 `__half2` 向量化。
- 对比 FP32 vs FP16 的性能和精度差异（histogram 仍用 int，其它用 FP16）。
- 测量 Nsight Compute 中的 Tensor Core 吞吐利用率。

### 分支 B：多 GPU 版本

- 用 NCCL 或手工 peer-to-peer 显存拷贝，把图像分块在多 GPU 上处理。
- 每个 GPU 处理一部分，最后在 GPU-0 上汇总结果。
- 测量多 GPU 相比单 GPU 的加速比（受通信开销制约）。

### 分支 C：端到端 CUDA Graph + Explicit API + 动态参数

- 用 explicit graph API 手工构建完整的 DAG（不用 stream capture）。
- 用 `cudaGraphExecKernelNodeSetParams` 在不改 graph 拓扑的情况下测试不同分辨率。
- 测量参数更新的成本。

### 分支 D：与 Thrust/CUB 版本对比

- 用 Thrust 的 `transform`, `reduce` 或 CUB 的原语重写某些步骤（例如 normalize 用 CUB reduce，sort 用 CUB radix sort）。
- 对比手工 kernel 与库函数的性能差异（库通常有更多优化）。
- 分析差异原因（如果手工快，说明库可能还有优化空间；如果库快，说明优化做得好）。

## 验收点

以下条件**必须同时满足**，缺一则项目未通过：

1. **代码编译通过**（VS2026 Release 配置）。
2. **程序运行无错误**（无 CUDA 错误、无 segfault）。
3. **输出正确性**（normalize 结果与 CPU 对比 ≤ 1e-5 相对误差，histogram 计数精确，sort 结果有序）。
4. **性能数据可交付**：
   - 5 个 kernel 各自的执行时间（从 event 计时或 Nsight 采集）。
   - 实测 throughput（例如 GB/s 或 GFLOPS）。
5. **Roofline 图完整**：至少 3 个 kernel 的算术强度和吞吐落在图上，清晰显示 memory-bound vs compute-bound。
6. **带宽利用率达标**：**整个管道的实测带宽 ≥ 理论峰值的 65%**（或给出 roofline 上至少一个 kernel 接近顶线的证据）。
   - 例如：Hopper H100 的 FP32 理论峰值 ≈ 60 TFLOPS，内存带宽 ≈ 3.4 TB/s。
   - 一个内存绑定的 normalize kernel 应该达到 ≥ 2.2 TB/s（65% of 3.4）。
   - 一个计算绑定的 kernel 应该接近 60 TFLOPS 的某个百分比。
7. **文档完整**：README + ANALYSIS.md 清晰说明了各步的功能、性能数据、优化点。

## 观察点（需要在 ANALYSIS.md 中记录）

至少记录以下 6 项观察（每项 2-3 行）：

1. **多 stream 并发效果**：有无 MPS 或多 stream 时，整体耗时如何变化？pipeline 中哪些步骤能并发？

6. **瓶颈定位**：用 Nsight Compute 指标，明确整个管道最大的瓶颈是什么（某个 kernel 的计算/内存/延迟）？下一步优化应该针对哪里？

## 常见坑（≥10 项）

1. **分辨率选择不当**：太小（如 512×512）无法充分填满 GPU，太大（16K×16K）显存不足。建议从 4K 开始试。
2. **Welford 算法实现错误**：单 pass 计算均值方差容易导致数值不稳定；必须用 Welford 或两 pass reduce。
3. **Histogram bin 数与输入范围不匹配**：假设像素在 [0, 256) 但实际输入是 float [0, 1)，导致 bin 溢出或空 bin。
4. **Shared memory 不足**：conv2d halo tile 如果 block size 太大，shared memory 会溢出；需要平衡 block size。
5. **Scan 中 `__syncthreads` 位置错误**：在 block 内部多个 stage 的 scan 中，同步位置不对会导致数据混乱。
6. **Stream 依赖漏掉**：某个 stream 上的 kernel 需要另一条 stream 的结果，但没有 `cudaStreamWaitEvent`，导致数据竞争。
7. **Graph capture 期间有 host-sync**：在 `cudaStreamBeginCapture` 和 `cudaStreamEndCapture` 之间调用 `cudaStreamSynchronize`，导致 capture 失败。
8. **Nsight Compute 报告不准确**：没有让 kernel 运行足够长时间（< 1 ms），采样数据噪声太大；或者没有用 `--set full` 获取完整指标。
9. **Roofline 单位混淆**：算术强度单位是 FLOP/byte，不是 FLOP/bit；理论吞吐单位是 FLOP/s 或 GB/s；混淆会导致图位置错误。
10. **CUB 头文件缺失**：如果用 CUB radix sort，需要确保 CUTLASS (包含 CUB) FetchContent 已正确配置，或手工安装 CCCL。
11. **Event 计时包含 synchronize 开销**：计时窗口从 kernel 启动到 `cudaEventSynchronize` 结束，意外包含了同步延迟；需要用异步计时或后处理数据。
12. **忘记 CUDA_CHECK**：kernel 或显存拷贝失败时无报错，导致后续数据混乱而不知道原因。

## 提示

- **调试首先保证正确性**：先写各 kernel 的 naive 版本并对标 CPU，再做性能优化。
- **分阶段集成**：先单独测每个 kernel，再组织多 stream，再用 graph。不要一上来就全做。
- **Nsight 采样技巧**：
  - 小数据量先快速采样（`--set speedoflight`）。
  - 确认没问题后再采集完整报告（`--set full`），会比较慢。
  - 记录关键指标到 CSV 便于后续分析。
- **性能对标**：查 cuDNN/cuBLAS 的文档，看它们对应操作的带宽/吞吐，作为对标目标。
- **Roofline 绘制**：可以用 Python matplotlib、Excel 或在线工具（例如 Google Sheets）。关键是清晰标出每个点和边界线。

## 复盘问题（8-10 题）

1. 多 stream 并发相比单 stream 串行的加速比是多少？什么因素决定了能否达到理论上的并发？
2. CUDA Graph replay 消除了多少 launch 开销？用什么方法测量的？
3. Histogram atomic vs privatized 两版为什么性能不同？从内存访问的角度解释。
4. Conv2D 用 shared memory tile + halo 相比直接用 global memory 快了多少倍？为什么？
5. Scan 的 Hillis-Steele 和 Blelloch 算法分别的 work complexity 是多少？这如何影响性能？
6. 根据 roofline 分析，哪个 kernel 是最大瓶颈？下一步优化应该从哪个方向入手？
7. FP32 vs FP16 性能对比如果做了，性能提升是多少？精度变化如何？
8. 多 GPU 版本（如果做了）的通信开销占比是多少？加速比与 GPU 数量的关系是否线性？
9. 整个管道与单步 normalize + histogram + conv2d + scan + sort 各自的总耗时对比，差异来自哪里？
10. 如果要把这个管道部署到生产环境，还需要补充哪些功能（错误处理、batch 支持、内存管理等）？
