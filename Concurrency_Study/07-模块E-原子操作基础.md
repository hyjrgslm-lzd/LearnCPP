# 07 模块 E：原子操作基础

## 模块目标

模块 A 到 D 里，你保护共享数据靠的一直是“上锁”——`std::mutex`、`std::lock_guard`、条件变量、future。锁的心智模型很简单：进临界区前锁上，出来时解开，临界区里你独占。但锁有它的代价：阻塞、上下文切换、优先级反转，以及“锁本身也是共享状态”带来的复杂度。有没有一种更细粒度的工具，能让“对一个变量做一次读-改-写”这件小事**不必上锁**就保证正确？

这就是**原子操作（atomic operation）**：对 `std::atomic<T>`（原子类型，`<atomic>`，C++11 引入）的操作是**不可分割（indivisible）**的——要么完整发生、要么没发生，任何线程都不会看到一个“做了一半”的中间状态。本模块带你认识原子操作这套工具本身：`load` / `store` / `exchange`、读-改-写家族 `fetch_add/sub/and/or/xor`、自旋旗标 `atomic_flag`、C++20 给既有对象套原子访问的 `atomic_ref`，以及无锁编程的真正基石——**比较并交换（compare-and-swap，CAS）**与围绕它的 CAS 循环范式。

有一件事本模块**刻意不展开**：内存序（memory order）。每个原子操作其实都接受一个内存序参数，用来控制“这次原子访问与周围普通读写之间的可见性/重排约束”。它默认取最强的**顺序一致（sequential consistency，`seq_cst`）**——最直观、最容易推理，代价是可能略慢。为什么很多场景能换用更弱的 `acquire`/`release`/`relaxed` 来提速、它们各自保证什么，是模块 F 的主题。**本模块所有代码都用默认 `seq_cst`，你只需先把“原子操作本身做了什么”吃透。**

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- **原子 = 不可分割**：为什么普通 `int` 的 `++` 在多线程下会丢更新（lost update，本质是“读-改-写”三步被并发覆盖，且无同步的并发访问本身就是数据竞争 data race / 未定义行为 UB），而 `std::atomic<int>::fetch_add` 不会。
- `std::atomic<T>` 的核心操作：`load`（原子读）/ `store`（原子写）/ `exchange`（写新值并返回旧值），以及读-改-写家族 `fetch_add` / `fetch_sub` / `fetch_and` / `fetch_or` / `fetch_xor`（都返回**旧值**）。
- 无锁（lock-free）的两个查询：`is_lock_free()`（成员，**运行期**查询此实例是否无锁）与 `is_always_lock_free`（C++17 起的 `static constexpr` 常量，**编译期**就能 `static_assert`，表示该特化在本平台任意实例都无锁）。
- `std::atomic_flag`（C++11）：标准保证**永远无锁**的最简原子旗标，`test_and_set`（置位并返回旧状态）/ `clear`（清位）/（C++20）`test`（只读探测）；如何用它搭一个自旋锁（spinlock）雏形，以及它与 `std::mutex` 的适用边界。
- `std::atomic_ref<T>`（**C++20**）：给一个**既有的非原子对象**（数组元素、结构体字段）临时套上原子访问，而不必把其类型改成 `atomic`；它的两条硬要求（对齐 alignment、可平凡复制 trivially copyable）与生命周期约束。
- **CAS**：`compare_exchange_weak` / `compare_exchange_strong(expected, desired)` 的精确语义（相等则写、不等则把 `expected` 刷新为真实当前值）；**CAS 循环**范式如何实现标准库没有内置的任意读-改-写（如 `fetch_max`）；`weak`（可伪失败、适合循环）与 `strong`（不伪失败、适合单次）的取舍。
- 一句话边界：本模块只引入“原子操作本身”，全部使用默认 `seq_cst`；“为什么能更弱”留给模块 F。

## 练习 E-1：原子操作基础

> 代码目录：`exercises/E1_atomic_basics/`

### 目标

把“原子 = 不可分割”从一句口号变成你亲眼看到的现象。用 `std::atomic<int>` 做多线程自增，并和普通 `int` 的自增**对照**——后者会丢更新、结果对不上，前者精确无误。再走一遍 `atomic` 的核心操作面板：`load` / `store` / `exchange` 与位运算 RMW；区分运行期的 `is_lock_free()` 与编译期的 `is_always_lock_free`。最后用 `std::atomic_flag` 搭一个最朴素的自旋锁雏形，体会“原子旗标”如何成为同步原语的积木。

### 前置理解

- **原子操作来自 `<atomic>`（C++11）**。`std::atomic<T>` 是一个模板：对它的操作保证不可分割。它**没有隐式转换**——取值要 `.load()`，写值要 `.store(v)`，这逼着你显式表达“这是一次原子访问”。
- **为什么非原子 `++` 会丢更新**：`++x` 实际是“读 x → 加 1 → 写回 x”三条机器指令。两个线程可能都读到同一个旧值、各自加 1、各自写回——两次自增只生效了一次。这就是丢更新。更要命的是：**多线程无同步地读写同一个普通变量本身就是数据竞争（data race），是未定义行为（UB）**——它“通常对不上”只是 UB 的一种温和表现，不能依赖。
- **RMW（read-modify-write）家族**：`fetch_add` / `fetch_sub` / `fetch_and` / `fetch_or` / `fetch_xor` 把“读旧值 → 运算 → 写新值”合成一个不可分割的整体，并**返回旧值**。`++counter`、`counter += 1` 等运算符重载同样是原子的，是 `fetch_add(1)` 的便捷写法。
- **无锁查询的两个层级**：
  - `is_lock_free()`：**成员函数、运行期**调用，返回此实例是否以无锁方式实现（极少数怪异类型/平台可能退化成内部加锁）。
  - `is_always_lock_free`：**C++17 起的 `static constexpr bool`**，编译期常量，可直接 `static_assert`。表示“该特化在本平台的**任意**实例都无锁”——比 `is_lock_free()` 更强的承诺。
- **`std::atomic_flag`**：C++ 标准明文保证**永远无锁**的最简原子布尔旗标。接口刻意极简：`test_and_set()`（原子地置位，并返回**置位前**是否已被 set）、`clear()`（原子清位）；C++20 起补充 `test()`（只读看当前是否 set，不改）。它必须用 `ATOMIC_FLAG_INIT` 或（C++20）默认初始化为清状态。
- 默认内存序是 `seq_cst`，本题不碰内存序参数。

### 必做任务

1. **原子自增 vs 非原子自增**（对应 `// TODO [必做 1]`）：8 个线程各自对同一计数器自增 10 万次。
   - 先用普通 `int`：打印结果，几乎总是 `< 800000`，亲眼看到丢更新。
   - 再用 `std::atomic<int>` + `fetch_add(1)`：结果精确等于 `800000`。
   理解：差别不在“加法”，而在“读-改-写是不是一个不可分割的整体”。

2. **核心操作面板 + is_lock_free**（对应 `// TODO [必做 2]`）：演示 `load()`（原子读）、`store(v)`（原子写、丢旧值）、`exchange(v)`（写新值并**返回旧值**）；再用 `fetch_or` / `fetch_and` / `fetch_xor` 对一个整型原子做位运算（都返回旧值）。打印 `is_lock_free()` 与 `is_always_lock_free`，看到两者一致为真。

3. **atomic_flag 自旋锁雏形**（对应 `// TODO [必做 3]`）：实现一个 `SpinLock`：
   - `lock()`：`while (flag_.test_and_set()) { /* 自旋 */ }`——`test_and_set` 返回 `true` 说明锁被别人占着（之前已 set），继续忙等；返回 `false` 说明这一刻是我把它置上的，抢锁成功。
   - `unlock()`：`flag_.clear()`。
   用它保护一个普通计数器，多线程自增后验证结果精确。

4. 记录并回答：
   - 用自己的话说清“为什么普通 `++` 在多线程下会丢更新”，以及“为什么这本身就是 UB”。
   - `fetch_add` 返回的是加之前还是加之后的值？`exchange` 返回的是哪一个？
   - `is_lock_free()` 与 `is_always_lock_free` 的区别是什么？哪个能写进 `static_assert`？

### 进阶任务

- **自旋锁的写争用优化**（思考为主）：在 `lock()` 的自旋里先 `flag_.test()`（C++20，只读探测）确认“看起来空了”再去 `test_and_set`，能减少对同一缓存行的写争用（test-and-test-and-set 模式）。想一想这为什么有用——线索是模块 J 的伪共享（false sharing）。
- 思考：自旋锁 vs `std::mutex`（模块 B）。自旋锁在临界区**极短**、且你不愿付出线程让出/唤醒开销时才划算；临界区一长，忙等就是纯浪费 CPU。绝大多数业务代码应当用 `std::mutex`。

### 验收点

- 你能用数据证明非原子 `++` 丢更新、`atomic::fetch_add` 不丢，并解释根因是“读-改-写是否不可分割”。
- 你能正确使用 `load`/`store`/`exchange` 与 RMW 家族，并说出它们各自返回什么。
- 你能区分 `is_lock_free()`（运行期）与 `is_always_lock_free`（编译期常量）。
- 你能用 `atomic_flag` 写出正确的自旋锁，并解释 `test_and_set` 的返回语义。

### 观察点

- 非原子版的结果每次运行可能不同，且总体偏小——这正是“多个线程的中间结果互相覆盖”的直接证据。
- `atomic<int>` 没有隐式转换：你必须写 `counter.load()` 才能拿到值，编译器在替你强调“这是一次原子读”。
- 自旋锁里，`test_and_set` 的一次成功调用（返回 `false`）就是“临界区入场券”被原子地发出的那一刻。

### 常见坑

- **把“通常对不上”当成确定行为**：非原子并发写是 UB，别依赖它的任何具体数值；它甚至可能（在某些优化下）表现得像“对得上”，但代码依然是错的。
- **以为 `atomic<T> x; int v = x;` 能直接取值**：不行，没有隐式转换，要 `x.load()`。
- **忘了 RMW 返回旧值**：`int prev = a.fetch_add(1);` 里 `prev` 是加之前的值，不是加之后的。
- **`atomic_flag` 当普通 bool 用**：它没有 `load`/`store`，接口只有 `test_and_set`/`clear`/（C++20）`test`，且没有“读出再判断”的隐式转换。
- **自旋锁忘了 `unlock`（`clear`）**：旗标一直 set，其它线程永远自旋——死等。

### 提示

- 计数器期望值 = 线程数 × 每线程次数；用它和实际结果对比最直观。
- `static_assert(std::atomic<int>::is_always_lock_free);` 可直接写在文件作用域，编译期校验本平台 `atomic<int>` 无锁。
- `SpinLock` 用一个私有成员 `std::atomic_flag flag_ = ATOMIC_FLAG_INIT;`；`lock`/`unlock` 如上。
- 用本仓库的 `cs::logf(...)`（`concurrency_study/log.hpp`）打印带时间戳与线程 id 的日志。

### 复盘问题

- “原子 = 不可分割”具体指什么？它如何消除丢更新？
- `load`/`store`/`exchange` 三者的区别？哪些操作属于 RMW、它们返回什么？
- `is_lock_free()` 与 `is_always_lock_free` 各在什么时刻给出答案？为什么后者能进 `static_assert`？
- `atomic_flag` 的接口为什么这么“穷”？它和 `atomic<bool>` 有什么不同？

## 练习 E-2：atomic_ref 引用既有对象

> 代码目录：`exercises/E2_atomic_ref/`

### 目标

认识 `std::atomic_ref<T>`（原子引用，**C++20**）：它能给一个**本来就是普通非原子类型**的既有对象临时套上原子访问，而**不要求你把这个对象/类型本身声明成 `std::atomic`**。用它对一个普通 `int` 数组的某个元素做多线程并发累加，结果精确无丢更新；同时把它的两条硬性要求（对齐、可平凡复制）和生命周期约束讲清楚——这是 `atomic_ref` 区别于 `atomic<T>` 的关键所在。

### 前置理解

- **`atomic<T>` 拥有存储，`atomic_ref<T>` 只是引用**。`std::atomic<int> x;` 里 `x` 自己就是那块原子存储；而 `std::atomic_ref<int> r(obj);` 里 `obj` 是一个**别处定义的普通 `int`**，`r` 只是“在 `obj` 这块既有内存上提供原子操作的视图”。它是引用语义、不拥有数据。
- **它解决什么痛点**：你有一片大的、性能敏感的普通数组 `int[]`（别的非并发代码要把它当普通数组高效使用），只在某个并发阶段需要对个别元素做原子访问。把整片数组改成 `std::atomic<int>[]` 既改变了类型、又可能影响别处的使用方式；`atomic_ref` 让你“按需、就地”地把原子性叠加到目标元素上。
- **两条硬性要求**：
  - **可平凡复制（trivially copyable）**：`T` 必须满足（`int` 满足）。
  - **对齐（alignment）**：被引用对象至少要满足 `std::atomic_ref<T>::required_alignment` 规定的对齐；对齐不足是未定义行为。对“可能未对齐”的对象（如 `#pragma pack` 打包结构体的字段、从字节缓冲里强转出来的对象）要格外当心。`required_alignment` 是一个 `static constexpr`，可直接打印/断言。
- **生命周期约束**（最容易踩的点）：
  - `atomic_ref` **不延长**被引用对象的寿命：只要还有任何 `atomic_ref` 活着，被引用对象就必须保持存活，否则是悬垂访问。
  - 在 `atomic_ref` 存活期间，对该对象的**所有访问都必须经由某个 `atomic_ref`**——你不能一边用 `atomic_ref` 原子访问、一边又用普通 `obj++` 访问同一对象，那就退回数据竞争了。
- 也有 `is_always_lock_free` / `is_lock_free()`，含义与 E-1 相同。默认内存序仍是 `seq_cst`。

### 必做任务

1. **atomic_ref 并发累加数组元素**（对应 `// TODO [必做 1]`）：定义一个**普通** `int data[4]`（类型仍是 `int[]`）。8 个线程各自对 `data[2]` 这个元素，**就地构造** `std::atomic_ref<int>`，用 `fetch_add(1)` 累加 10 万次。验证：`data[2]` 精确等于 `800000`，其余元素仍为 0。体会：底层始终是普通数组，原子性是 `atomic_ref` 临时叠上去的。

2. **对齐与生命周期**（对应 `// TODO [必做 2]`）：打印 `std::atomic_ref<int>::required_alignment`、`alignof(int)`、`std::atomic_ref<int>::is_always_lock_free`；再演示一段“先经 `atomic_ref` 原子 `store`、待其在内层作用域 `{}` 结束析构后、再用普通方式读该对象”的**合法顺序**，把生命周期边界走一遍。

3. 记录并回答：
   - `atomic_ref<T>` 和 `atomic<T>` 在“谁拥有存储”上有何本质区别？各自适合什么场景？
   - `atomic_ref` 对被引用对象有哪两条硬性要求？不满足会怎样？
   - 在一个对象还有 `atomic_ref` 指向它时，你能不能用普通方式读写它？为什么？

### 进阶任务

- **vector 元素上的陷阱**（思考为主）：把 `atomic_ref` 用在 `std::vector<int>` 的元素上时，一旦 vector 触发重新分配（reallocation，如 `push_back` 扩容），原来的元素地址失效，指向它的 `atomic_ref` 立刻悬垂。想清楚：你必须保证 `atomic_ref` 的整个存活期内底层存储不被搬动。
- 思考：什么时候宁可用 `atomic<T>` 而不用 `atomic_ref`？（线索：当这个对象**自始至终**都要被原子访问、且你能控制它的声明时，直接声明成 `atomic<T>` 更省心、更不易误用。）

### 验收点

- 你能解释 `atomic_ref`（引用语义、套在既有对象上）与 `atomic<T>`（拥有存储）的区别。
- 你能用 `atomic_ref` 对普通数组元素做无丢更新的并发累加。
- 你能说出 `atomic_ref` 的对齐与可平凡复制要求，以及生命周期约束。

### 观察点

- `data` 的类型从头到尾是 `int[4]`——你没有改变它的类型，只是在并发阶段对某元素套了原子视图。
- 并发结束、所有 `atomic_ref` 析构后，`data[2]` 又是个普通 `int`，可以直接读——这正是“按需叠加原子性”的好处。
- `required_alignment` 对 `int` 通常等于 `alignof(int)`，对更大的类型（如 `long long`）可能更大——这是“原子访问需要的对齐”而非“类型天然的对齐”。

### 常见坑

- **对齐不足**：在打包结构体或手工字节缓冲上构造 `atomic_ref` 而不保证对齐——UB。先核对 `required_alignment`。
- **生命周期越界**：被引用对象先于 `atomic_ref` 销毁（如局部对象出作用域、vector 扩容搬走元素）——悬垂访问。
- **混合访问**：在 `atomic_ref` 还活着时又用普通方式读写同一对象——退回数据竞争。
- **以为 `atomic_ref` 拥有数据**：它不拥有、不初始化目标的值，只是个视图；目标的初值由你在别处给定。

### 提示

- 就地构造：`std::atomic_ref<int> ref(data[2]); ref.fetch_add(1);`，每个线程的每次循环各自构造一个指向同一元素的 `atomic_ref` 都是合法的。
- 用 `alignas(std::atomic_ref<int>::required_alignment)` 标注数组，显式表达对齐要求（对 `int` 通常已满足，但写出来更稳妥、也更有教学意味）。
- 生命周期演示：用内层 `{ std::atomic_ref<int> ref(value); ref.store(123); }` 让 `ref` 提前析构，之后再普通读 `value`。

### 复盘问题

- 一句话区分 `atomic<T>` 与 `atomic_ref<T>`。
- `atomic_ref` 的两条硬性要求是什么？`required_alignment` 告诉你什么？
- “`atomic_ref` 存活期间，目标对象的所有访问都必须经由 `atomic_ref`”这条规则保护的是什么？
- 为什么在 `std::vector` 元素上用 `atomic_ref` 要特别小心？

## 练习 E-3：CAS 循环

> 代码目录：`exercises/E3_cas_loop/`

### 目标

掌握无锁编程真正的基石——**比较并交换（compare-and-swap，CAS）**：`compare_exchange_weak` / `compare_exchange_strong`。理解它“相等才写、不等则把期望值刷新成真实当前值”的精确语义，并学会围绕它的 **CAS 循环（CAS loop）** 范式——用它实现标准库**没有内置**的任意读-改-写操作。本题用 CAS 循环实现 atomic `fetch_max`（原子取最大值）和一个 atomic 乘法，并把 `weak` 与 `strong` 的取舍讲透。

### 前置理解

- **CAS 的语义**：`a.compare_exchange_X(expected, desired)` 原子地做：
  - 比较 `a` 的当前值是否等于 `expected`；
  - **相等** → 把 `a` 写成 `desired`，返回 `true`；
  - **不等** → 不修改 `a`，但把 `expected` **就地刷新为 `a` 的真实当前值**，返回 `false`。
  注意 `expected` 是按引用传入的——失败时它被改写，这正是 CAS 循环能“拿着最新值重试”的关键。
- **CAS 循环范式**（本模块最重要的套路）：标准库给了 `fetch_add/sub/and/or/xor`，但你想做的“读-改-写”常常不在这张清单里（取最大值、乘法、条件更新……）。通用解法：
  1. `load` 出当前值 `cur` 当作 `expected`；
  2. 用 `cur` 算出想写入的 `desired`；
  3. `compare_exchange_weak(cur, desired)`：成功就完成；失败说明别人抢先改了值，此时 `cur` 已被刷新为最新值，回到第 2 步用新 `cur` 重算重试。
  这个“读—算—试，不行就拿最新值重来”的骨架，会在模块 G 的无锁栈/队列里反复出现。
- **weak vs strong**：
  - `compare_exchange_weak`：允许**伪失败（spurious failure）**——即使当前值确实等于 `expected`，也可能返回 `false`。听起来很怪，但在某些架构（如 ARM 的 LL/SC）上，避免“强保证”能少一条指令、更高效。因为它**几乎总写在循环里**，伪失败只是多转一圈、无伤大雅。
  - `compare_exchange_strong`：**不会伪失败**——只有当前值确实不等于 `expected` 时才失败。适合**不便重试的单次调用**（比如一次性的状态翻转判断）。
  - 经验法则：**放进循环重试 → 用 weak；单次、不便重试 → 用 strong**。
- 默认内存序仍是 `seq_cst`。CAS 其实还能给“成功”和“失败”各指定一个内存序，这个更细的控制留到模块 F。

### 进阶任务

- **ABA 预告**（思考为主，正式在模块 G 展开）：CAS 只比较“值是否等于 `expected`”，它无法区分“值一直没变”和“值从 A 变成 B 又变回 A”。在裸指针型无锁结构里这会引发著名的 **ABA 问题**。本题的整型 `fetch_max`/乘法不受其害（值即一切），但请先把这个隐患记在心里。
- 思考：如果 `fetch_max` 的候选值分布让“别人总是先抬高”，你的 CAS 循环会重试很多次吗？高争用（high contention）下 CAS 循环的代价是什么？（线索：每次失败都要重读重算，争用越高、白做的功越多。）

### 观察点

- `fetch_max` 多线程跑完，结果**必然**精确等于全局最大候选——CAS 循环保证了每次抬高都基于“当时真实的当前值”。
- `compare_exchange_strong` 失败那一行打印出来的 `expected`，正是被刷新成的真实当前值——这就是循环能正确重试的机制来源。
- 把 `weak` 换成 `strong` 放进循环，程序依然正确（只是少了伪失败的重转）——这说明循环对两者都安全，区别只在效率与意图表达。

### 常见坑

- **CAS 循环里没用刷新后的 `cur` 重算 `desired`**：失败后必须基于新 `cur` 重新计算 `desired`，否则你写回的是基于过期值的结果——逻辑就错了。
- **在循环里用 strong 还指望它“不重试”**：strong 不伪失败，但只要别人真改了值它照样失败、照样要循环重来；它不能省掉重试逻辑。
- **单次判断却用了 weak**：单次、不便重试的场合用 weak，伪失败会让你“明明该成功却失败”，得不偿失——这种地方用 strong。
- **忘了 `expected` 是按引用、会被改写**：在循环外复用一个没被刷新的 `expected` 变量，或在失败后没意识到它已变，都会出错。
- **以为 CAS 能识破 ABA**：它只看值相不相等，识不破“变走又变回”。整型无妨，裸指针要警惕（模块 G）。

### 提示

- `fetch_max` 骨架：
  ```cpp
  int cur = target.load();
  while (candidate > cur) {
      if (target.compare_exchange_weak(cur, candidate)) return; // 成功
      // 失败：cur 已被刷新为最新当前值，循环条件用新 cur 重判
  }
  ```
- 乘法骨架：`long long cur = target.load(); while (!target.compare_exchange_weak(cur, cur * factor)) {}`。
- 让线程 `i` 的候选范围是 `[i*N, (i+1)*N)`，全局最大候选就是 `kThreads*N - 1`，便于断言。
- 用 `cs::logf(...)` 打印每步结果，观察 strong 失败时 `expected` 被刷新的值。

## 做完模块 E 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- **原子 = 不可分割**：`std::atomic<T>`（`<atomic>`，C++11）的操作要么完整发生、要么没发生，中间状态对别的线程不可见；普通 `int` 的 `++` 是“读-改-写”三步、会丢更新，且无同步的并发访问本身就是数据竞争（UB）。
- `atomic<T>` 的操作面板：`load`（原子读）/ `store`（原子写）/ `exchange`（写新值返回旧值），RMW 家族 `fetch_add/sub/and/or/xor`（返回旧值）；取值必须 `.load()`（无隐式转换）。
- 无锁查询分两层：`is_lock_free()`（成员、运行期）与 `is_always_lock_free`（C++17 `static constexpr`、编译期、可 `static_assert`）。
- `std::atomic_flag`（C++11）是保证永远无锁的最简旗标，`test_and_set`/`clear`/（C++20）`test`，是自旋锁的积木；自旋锁只在临界区极短时才比 `std::mutex` 划算。
- `std::atomic_ref<T>`（**C++20**）给既有非原子对象临时套原子访问（引用语义、不拥有存储），要求对齐与可平凡复制，且存活期间对象只能经 `atomic_ref` 访问、不能更早销毁。
- **CAS** 是无锁编程的基石：`compare_exchange_weak/strong(expected, desired)` 相等则写、不等则刷新 `expected`；**CAS 循环**用“读—算—试，失败拿最新值重来”实现任意未内置的 RMW（如 `fetch_max`）；循环里用 `weak`（可伪失败、更高效）、单次用 `strong`（不伪失败）。
- 一个贯穿全模块的边界：这里所有原子操作都用默认的 `seq_cst`。**为什么很多场景能换更弱的内存序来提速、各自又保证什么——正是模块 F 的主题。**
