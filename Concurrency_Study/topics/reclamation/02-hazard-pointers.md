# HP：把“正在用哪个对象”变成可见证据

上篇的读者加载了裸指针，写者却不知道它是否还要使用对象。HP 分支让读者公布一个具体地址。难点不在写入地址那一行，而在证明“公布得足够早”以及“扫描的确覆盖这一保护”。本篇对应 [hazard_pointer.hpp](../../exercises/include/concurrency_study/hazard_pointer.hpp) 和 [I2 reference](../../exercises/I2_hazard_pointer/reference.hpp)。

## 1. 只登记还不够：先问窗口在哪里

设 R 先从 head 读到 A，还没登记就暂停。W 摘下并退休 A，回收器扫描时未看到 A，于是释放它。R 恢复，把 A 的地址写到 hazard 槽。此时槽里虽然确实写着 A，但它无法逆转已经结束的生命期。

因此，读者不能在第一次加载后立即解引用。它要先公布地址，再重新加载源。若源不再等于自己公布的地址，就撤销这次尝试，换新值重试。只有验证成功后的指针才授予访问资格。对应接口是：

```cpp
auto hp = cs::make_hazard_pointer();
Node* p = hp.protect(head);   // 内含加载、公布、重读验证、失败重试
if (p) use(p);              // 所有解引用都在成功保护之后
hp.reset_protection();      // 此后不再使用借用
```

这段形状在栈 reference 的 pop 中有完整实现。它与“先读 p->next，再 protect”有实质区别；后者早已在没有保护时访问对象，不能靠后续验证补救。失败的 try_protect 会回填 expected，但回填值也还没有取得访问资格，调用方必须再尝试保护。

## 2. 全 SC 基线如何排除漏保护

本版主动限制：head 的加载、发布、交换、CAS 成功与失败路径，以及槽的公布、清空、扫描全部使用默认 SC。证明依赖整个协议，不能只把槽 store 改成 seq_cst，然后把其他地方留在 relaxed/acquire。

对某个候选对象 A，记：

- H：读者把 A 公布到槽；
- V：读者验证源仍等于 A；
- U：写者从源摘除 A；
- S：收集者检查该读者的槽，决定是否回收已退休的 A；
- Q：读者结束全部使用并清空槽。

在“不重新发布 A，且本次没有结束/替换保护”的情况下，验证看到 A 意味着 V 在 SC 顺序中早于摘除 U。读者程序顺序要求 H 在 V 前。写者先 U，再登记退休；登记与取候选的短锁建立顺序，因此检查 S 在 U 后。于是 H < V < U < S。S 不可能把槽中 H 之前的空值当成它当前的 SC 值；如果 S 看到 Q 之后的空值，读者的访问已经结束。两种情形都不能在合法访问期间误释放 A。

反向考虑：若 S 在 H 前已经看到空槽，则 U < S < H < V，V 不会仍验证到被摘除的那个发布状态，读者必须重试。这里没有使用“原子 load 总能看到实时最新值”这种错误理由；用的是这些操作在同一 SC 顺序及相应同步关系中的约束。

这是本教学协议的推导，不是标准 HP 的通用内存序要求。成熟实现可以借助更精细的屏障与批处理，但必须提交另一份完整证明。N5050 的 `[saferecl.hp]` 用保护 epoch、退休与回收之间的关系规定标准设施；不会自动替用户手写的槽扫描代码提供保证。[规范基准](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/n5050.pdf)

## 3. 回收器也有顺序：候选必须先退休

新实现把退休记录保存在全局队列，记录包含对象地址和实际删除器。cleanup 先在 pending 锁下检查已经退休的记录，扫描所有槽，把不受保护的记录 splice 到本地 ready，再解锁执行回调。仍受保护的记录留在原队列。扫描不能早于取得候选的退休资格；“先拍槽快照，再把后来退休的对象也算进去”会借用不适用于它们的旧快照。

ready 拥有每条待执行记录，pending 已不再拥有它。两个 cleanup 由 collector 锁串行，因此不存在两个收集者同时调用同一记录的问题。pending 锁不跨用户回调，删除器可再次退休别的对象。cleanup 使用线程局部的重入标志，同线程回调再次调用 cleanup 返回 0；外层执行完 ready 后继续扫描全局队列，处理新退休的对象。它不会递归遍历正在修改的容器。

TLS 只保存这个瞬时重入标志，不保存退休对象。退休线程退出不会让小于扫描阈值的一批记录消失。runtime 的 `hp_handles_and_exit()` 就让退休线程退出后，主线程继续保护、解除保护并清理这批对象。

## 4. 句柄所有权与对象所有权不是同一件事

工厂最多提供 128 个 active 槽，申请失败抛 bad_alloc。默认构造的句柄没有槽；工厂返回的句柄有槽但可能尚未保护对象。`empty()` 问的是“有没有槽”，不是“槽中是不是 nullptr”。

reset 清空保护而保留 active 槽，以便后续重复使用。析构才先清空保护再释放 active。移动构造转移槽指针，原句柄变空；移动赋值还需先释放目标原来拥有的槽。若错把目标旧槽和转入槽混在一起，可能丢掉仍在进行的保护。自移动在本版是无操作，空/移动后句柄可以 reset，但不能 protect 或设置非空保护；后一类违反契约会 terminate。

`reset_protection(p)` 仅公布已有合法存活保证的对象。它适合从另一份仍有效的保护转交，不替任意裸地址追认生命期；原保护必须保持到本函数返回。本实现比较完整 T 对象的原始地址；不要用带地址偏移的基类子对象指针保护、却用派生对象地址退休。一个句柄任一时刻只有一个使用者；跨线程移动必须通过正常线程同步完成，不能并发操作同一 C++ 句柄。

转交还有一个容易忽略的扫描问题：已退休对象从旧槽 A 转到新槽 B，若扫描先读 B 的空值，随后读到清空后的 A，就可能错过始终存在但换了位置的保护。因此本版 reset_protection(p) 的非空指针重载获取 pending_mutex，与整轮扫描互斥。扫描若先获得锁，转交尚未完成，旧保护仍在；若转交先完成，扫描会看到新槽。清空重载不需要该锁。普通 protect 仍依赖源验证及全 SC 顺序，句柄 move 则直接转移同一个槽，不移动槽内的地址。

## 5. 栈 reference：结构正确性仍需单独证明

本题只存 int，支持多生产者、多消费者，无固定节点容量。push 私有分配节点，next 初始化后用 CAS 发布；发布后 next 不再修改。push 成功 CAS 是线性化点。pop 保护 head 后读取 next，再 CAS 摘除；成功 CAS 是成功 pop 的线性化点，验证所得的空源读取是空返回的线性化点。CAS 失败后回到 protect，不能直接使用失败回填值继续解引用。

成功 pop 读取 int，然后 retire。其他竞争者也许仍保护 old，因此摘除成功不等于能立即 delete。只读取自己的成功节点不会产生数据写竞争；限定 int 也避免了摘除后用户类型复制抛异常导致所有权悬空的问题。若扩展任意 T，必须增加相应异常/值访问契约，不能只把 int 换成模板参数。

这里的 CAS 算法核心有常见的 Treiber 结构形状，但完整 push/pop 包括 new、槽申请、退休短锁及可能执行的删除回调，不承诺 lock-free。析构要求全部使用者已经 join，它摘除剩余链并退休、最终 cleanup；析构与并发操作重叠属于违反对象生命期契约。

## 6. 积压、回调、退出与异常

退休数达到 256 时尝试自动扫描；若已有收集者在执行，当前退休者不会等 collector，而让正在执行的收集者处理。显式 cleanup 会等待其他外层 cleanup 完成，但不等待读者撤销保护。返回值是这次外层调用完成的删除回调数，不是剩余队列长度；0 可能表示还有被保护的对象。

一个停顿句柄只直接阻止它所登记的那个对象被本协议回收，但这不意味着进程内存有严格的 128 节点上限。源中尚未摘除的节点、尚未被扫描的记录、分配器缓存以及删除器拥有的资源都不在这个结论之内。持续生产可使队列增长，用户回调可以阻塞收集者，所有这些都会增加积压。I2 的普通实验总共只生产 4000 个节点，容量边界由实验给定，不把扫描阈值当硬上限。

最终清场必须停止生产、join 所有使用者、清除全部保护，然后调用一次 cleanup；本版外层循环也会排空有限的回调派生退休。前提是回调链有限且会结束；无限生产不能要求有限时排空。默认域在静态析构时若仍有 pending 会 terminate，故不能依靠进程退出替代协议，也不能在默认域已析构后从别的静态对象再次调用它。

retire 函数体内的分配、删除器移动或加锁失败，以及删除回调异常越过 noexcept 边界，都会终止程序。调用前构造实参本身的异常仍可能发生在进入函数之前；这时尚未登记退休，所有权仍在调用者。删除器允许有状态、只可移动；它引用的外部计数器或资源必须活到回调完成。回调不得等待另一个必须完成 cleanup 才能前进的线程，避免 collector 锁上的依赖环。

## 7. 实验、自测与答案

先独立运行 I2 的 solution，阅读只读的 reference；作业只在 [student.hpp](../../exercises/I2_hazard_pointer/student.hpp) 补全 protect、retire、pop 和 cleanup。main 使用独立检查器实际调用学生操作，空 TODO 在线程启动前返回 1，不调用 reference::run。补全后检查 4000 个 ID 恰好各出现一次、所有节点析构，另用小历史检查 LIFO。总 push==总 pop 不能排除“丢一个又重复一个”，因此必须保留逐 ID 检查。再运行 runtime 检查，观察保护期间 0 次删除，移动解除 a 后只删除 a，最后解除 b 后才删除 b；删除器重入测试的累计状态为 7+11=18。不要通过改写 reference.hpp 完成作业。

**为什么没有崩溃不等于没有 UAF？** 释放后内存可能暂未覆盖，错误访问可能读取到貌似正确的旧值。需要协议推导、定向调度检查与动态工具共同提供证据。

**为什么只把 hazard store 设成 SC 不足？** 上述 H、V、U、S 的论证要求源与扫描也进入该顺序。移除任何一端后必须重新证明，不能继续引用这份推导。

**为什么一次 cleanup 返回 0 仍不能直接结束程序？** 可能还有活动保护，或本次是被抑制的回调重入。只有完成停止、join、解除保护的前置条件，才能把最终清场视为排空动作。

**如何复现？** 按 [验证说明](06-validation.md) 分别编译学生 main 和答案 solution。未完成的 main 返回 1，solution 应独立通过；检查断言使用 cs::check，Release 仍执行。专题 verify.ps1 默认只检查 Reference；Starter 模式接受并验证空作业返回 1，Student 模式要求补全后的实际检查通过。
