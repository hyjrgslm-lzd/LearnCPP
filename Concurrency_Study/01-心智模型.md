# 01 心智模型

> 这份文件不含练习。它是整套材料的概念地基——把并发世界里那些**容易混为一谈的东西先分清楚**，
> 并交给你一套贯穿全程的「画图 + 提问」方法。后面每个模块都默认你已经建立了这里的直觉。

并发编程之所以难，不是因为 API 多，而是因为**你的直觉是为单线程世界训练的**。
单线程里「写完一个值，下一行就能读到」「代码按书写顺序执行」这些天经地义的事，
在多线程 + 现代 CPU + 优化编译器面前，**全部失效**。这一章先把失效的地方标出来。

---

## 1. 先分清四组容易混淆的概念

### 1.1 并发（concurrency） vs 并行（parallelism）

- **并发**是一种**结构**：程序被组织成多个可以独立推进的任务，逻辑上「同时存在」。
  单核 CPU 上靠时间片轮转也能并发。并发关心的是**正确地管理交错（interleaving）**。
- **并行**是一种**执行**：多个任务在多个硬件执行单元上**真的同时跑**。并行关心的是**加速**。

一句话：**并发是关于「怎么写对」，并行是关于「怎么跑快」。** 本套阶段一、二主攻并发正确性，阶段三主攻并行性能。

### 1.2 任务（task） vs 线程（thread）

- **线程**是操作系统的调度单位，是**重的**资源（栈、内核对象、上下文切换成本）。
- **任务**是一段「要被执行的工作」的抽象，**轻**。一个线程池可以用少量线程跑成千上万个任务。

初学者常把「我要并发做 1000 件事」翻译成「我要开 1000 个线程」——这通常是错的。
正确姿势是「1000 个任务，交给 N 个线程的池子去跑」（阶段一结课、模块 M 会做这件事）。

### 1.3 共享内存（shared memory） vs 消息传递（message passing）

- **共享内存**：多个线程读写同一块内存，靠锁/原子/内存序来协调。**本套的主线**，因为它是 C++ 标准库的核心模型，也是 bug 的主要来源。
- **消息传递**：线程之间不共享可变状态，只传递消息/值（channel、actor、sender/receiver）。
  `std::execution`（`Execution_Study\`）走的就是这条「值在流动、不共享可变状态」的路。

记住一个价值排序：**能不共享就不共享；必须共享就用最简单的同步；锁能解决就别急着上无锁。**

### 1.4 阻塞（blocking） vs 非阻塞（non-blocking）

- **阻塞**：线程等不到条件就睡过去，让出 CPU（`mutex::lock`、`condition_variable::wait`、`future::get`）。
- **非阻塞 / 无锁（lock-free）**：线程不睡，靠原子操作和重试推进，保证「总有某个线程在前进」。

无锁不等于「更快」，也不等于「更好」——它换来的是**进展保证**（避免某线程持锁挂死拖垮全局），代价是**极难写对**。模块 G/I 会让你亲身体会。

## 2. 共享内存并发的根本难题：数据竞争 = 未定义行为

这是整套材料最重要的一句话，先记死：

> **如果两个（或多个）线程对同一个非原子对象有两次相冲突的并发访问（conflicting evaluations），
> 其中至少一个是写，且这两个访问之间没有 happens-before 关系，那么这就是一个数据竞争
> （data race），程序行为未定义（UB）。**

注意每个限定词：
- **非原子**：`std::atomic` 的访问不算数据竞争（它就是为并发访问设计的）。
- **至少一个写**：两个线程都只读，永远安全。
- **没有 happens-before 关系**：这是关键——光是「用了原子」或「时间上错开」都不够，必须建立**正式的顺序关系**（见第 4 节）。

「未定义行为」意味着：编译器有权假设它不发生，于是可能把你的代码优化成任何样子。
**数据竞争不是「读到旧值」这么温柔，而是「整个程序失去意义」。** 这也是为什么并发 bug 经常表现为诡异崩溃而非简单的数值错误。

---

## 3. 为什么直觉会失效：三层重排

你写下的 `a = 1; b = 2;`，在另一个线程眼里**未必是这个顺序生效**。原因有三层，从上到下：

1. **编译器重排**：优化器只要保证「单线程语义不变」，就可以自由调整无依赖语句的顺序、把变量缓存进寄存器。它对「别的线程在看」一无所知。
2. **CPU 乱序执行**：现代处理器会乱序发射指令、推测执行。
3. **缓存与写缓冲**：每个核心有自己的缓存。一个核心写了内存，另一个核心**不保证立刻看到**——写要经过 store buffer，读可能命中旧的缓存行。

`std::atomic` + `memory_order` 的全部意义，就是**在这三层之上建立一套可移植的规则**，
让你能精确表达「这个写必须对那个读可见」。这套规则就是 **C++ 内存模型**，模块 F 是它的主场。

> 关键转变：在并发世界里，**「顺序」不是默认存在的，而是你用同步原语显式建立出来的。**

---

## 4. 贯穿全套的核心偏序：happens-before（直觉版预告）

整套材料反复出现的一个词是 **happens-before**。这里给直觉，精确定义留到模块 F。

- **sequenced-before（单线程内）**：同一个线程里的求值顺序，大致遵循书写顺序——前面的语句 sequenced-before 后面的。（严格说它是按「求值」而非「语句」定义的：同一个表达式内的子求值可能没有固定顺序，例如 `f() + g()` 里 `f()` 与 `g()` 之间无序；细节留到模块 F。）
- **synchronizes-with（跨线程）**：当线程 A 对原子变量做 **release 写**，线程 B 对同一变量做 **acquire 读**并读到了 A 写的值，则 A 的 release **synchronizes-with** B 的 acquire。
- **happens-before**：把上面两种关系传递地连起来，就得到跨线程的偏序。

它的威力在于：**一旦 A happens-before B，那么 A 之前（sequenced-before）的所有写，对 B 之后的读都可见。**
这就是「一个 release 写 + 一个 acquire 读」能安全发布一整块数据的原理（模块 F 的「发布模式」）。

锁也是用同样的机制工作的：**解锁 synchronizes-with 之后对同一把锁的加锁**。所以临界区里的修改，
下一个拿到锁的线程一定能看到。你之所以平时用 `mutex` 不需要懂内存序，是因为锁替你建立好了 happens-before。

## 5. 三个核心感觉

学到后面，这三种「感觉」会内化成本能：

### 5.1 同步的本质是建立「可见性 + 顺序」，不只是「互斥」
新手以为锁是为了「不让两个线程同时进」。其实互斥只是表象，**锁更深的作用是建立 happens-before，
保证临界区里的写对后续持锁者可见**。原子操作没有互斥，但同样能建立可见性——这就是为什么能有无锁结构。

### 5.2 正确性 = 不变量在「每一个可能的交错」下都成立
单线程里你只需检查一条执行路径。并发里，调度器可以在**任意两条指令之间**切换线程。
证明正确，意味着证明**所有交错**下你的数据结构不变量都不被破坏。这就是为什么「跑过了」不等于「对了」。

### 5.3 性能来自「减少同步」和「数据局部性」，而非「多开线程」
阶段三你会反复看到：同步是有成本的（缓存行弹跳、内存屏障、上下文切换）。
真正的高性能并发，是**尽量让线程各干各的、少碰共享状态、让数据贴着 cache 走**（伪共享、SIMD、工作窃取都是这个主题）。盲目加线程往往更慢。

## 6. 每做一题都画这五样东西

做任何一道并发题之前/之中，在纸上或注释里画出这五样：

1. **有哪些线程/任务**（圈出来，标明谁是生产者、谁是消费者、主线程做什么）。
2. **共享了哪些状态**（方框标出，注明类型：普通变量？原子？受哪把锁保护？）。
3. **同步点在哪**（锁的获取/释放、原子的 release/acquire、condvar 的 wait/notify、barrier）。
4. **值 / 信号怎么流动**（用箭头画出数据从谁流向谁、通知从谁发给谁）。
5. **哪些交错是危险的**（标出「如果这里切到那个线程会怎样」的关键点）。

画不出来，就说明你还没想清楚——**别急着写代码**。

## 7. 做题时的四个固定提问

每道题做完，强迫自己回答这四问（阶段二、三再加两问）：

1. **这块共享状态由谁拥有、谁并发访问、用什么同步？**
2. **正确性靠哪条 happens-before 边保证？**（锁？某个 release-acquire 配对？）
3. **如果调度器在最坏的时刻切换线程，不变量还成立吗？**
4. **有没有数据竞争？**（每个非原子的共享访问，都能指出保护它的同步。）

阶段二额外两问：
5. **每个原子操作为什么用那一级 `memory_order`？换成更弱的会错吗？换成更强的有何代价？**
6. **如果是无锁结构：进展保证是哪一级（lock-free / wait-free）？回收安全吗？**

阶段三额外两问：
7. **热点数据的内存布局如何？有没有伪共享？局部性好吗？**
8. **这个并行/向量化真的比串行快吗？我用什么测的？开销在哪？**

## 8. 进入阶段一前的自测

合上文档，用自己的话回答（答不清的，回到对应小节）：

1. 并发与并行的区别是什么？哪个关心正确性，哪个关心速度？
2. 数据竞争的精确定义里，四个限定词分别是什么？为什么结果是 UB 而不是「读到旧值」？
3. 为什么 `a = 1; b = 2;` 在另一个线程看来可能不是这个顺序？列出三层原因。
4. happens-before 是怎么跨线程建立的？锁是如何利用它的？
5. 「能不共享就不共享」这条原则，对应到设计选择上意味着什么？
6. 为什么「跑过了一万次」不能证明并发代码正确？

> 6 道里有 2 道以上答不顺，别往下走——这章的直觉是后面所有模块的地基。

## 9. 对后续模块的期待

- **模块 A–D**：把「安全地管理线程、保护共享状态、取异步结果」刻进肌肉记忆，先用锁建立 happens-before。
- **模块 E–F**：掀开锁的盖子，直面原子与 `memory_order`，学会**自己建立** happens-before。
- **模块 G–I**：在没有锁的世界里维持正确性——无锁结构、ABA、安全回收。
- **模块 H**：用标准提供的成熟同步基建（latch/barrier/semaphore/atomic-wait）替代手写轮子。
- **模块 J–M**：从「对」转向「快」——消除伪共享、向量化、并行算法、工作窃取，最后桥接到结构化并发。

并发的终点不是「会调 API」，而是**能对着一段并发代码，画出它的同步结构，并论证它在所有交错下都正确且高效**。
