# 13 模块 J：缓存与伪共享

## 模块目标

前面的模块（E~I）让你写出了正确的原子、内存序与无锁结构。但“正确”不等于“快”。本模块把视角从**正确性**切到**性能**，聚焦一个最常见、最隐蔽、也最容易“写对了却慢得离谱”的并发性能陷阱——**伪共享（false sharing）**，以及它背后的硬件机制：**缓存行（cache line）** 与**缓存一致性（cache coherence）**。

核心事实（务必刻进脑子）：CPU 在核心之间搬运数据，从来不是“按变量”或“按字节”，而是**以整条缓存行为单位**（典型 **64 字节**）。于是会出现这样的怪事：两个线程各写各自的变量、逻辑上毫无关系，却因为这两个变量**恰好落在同一条缓存行**，硬件被迫把整条行在两个核心间反复搬来搬去（**缓存行弹跳，cache line bouncing**），吞吐暴跌好几倍。这就是伪共享——“共享”是假的（变量并不共享），但缓存行的争用是真的。

本模块给你三件武器与一个视野：

1. **测出来**（J-1）：亲手用计时把伪共享的代价量化，再用 `alignas` 把变量分到不同缓存行，对比加速比。
2. **标准化的尺子**（J-2）：用 C++17 的 `std::hardware_destructive_interference_size` / `std::hardware_constructive_interference_size` 替代硬编码的魔法数 64，并理解“隔开（destructive）”与“聚拢（constructive）”这对相反策略。
3. **更大的尺度**（J-3）：从单机缓存行，放大到多路服务器的 **NUMA（Non-Uniform Memory Access，非一致内存访问）**——访问代价随“数据在哪个节点”而不同，配套 **first-touch（首次接触）** 与**线程亲和性（thread affinity）** 两个调优抓手。

> 本模块纯标准库、零第三方依赖。J-1/J-2 的现象在任意多核机器上都可复现；J-3 的 NUMA 收益只有在**真多 NUMA 节点服务器**上才可量化，故 J-3 以概念 + 绑核小实验为主。

## 模块完成标准

做完本模块，你至少要能稳定说清楚（can-do）：

- 你能用一句话说清**伪共享**：不同线程频繁写**各自**的变量，但它们落在**同一条缓存行**，引发缓存行在核心间弹跳，造成本不该有的竞争与性能下降。
- 你能写出一个**实测伪共享**的小程序：相邻计数器版 vs `alignas(缓存行)` 分行版，打印两者耗时与加速比，并解释为什么差距来自缓存行争用而非算法。
- 你能正确使用 `alignas(std::hardware_destructive_interference_size)`（或保守的 64）做对齐 + 填充（padding），把被不同线程写的对象**隔开**到独立缓存行。
- 你能说清 `hardware_destructive_interference_size`（隔开，避免伪共享）与 `hardware_constructive_interference_size`（聚拢，促进真共享/局部性）这对常量的**语义对立**，知道它们是 **C++17**、`<new>`、**实现定义值**、且 `>= alignof(std::max_align_t)`，并知道 GCC 有 `-Winterference-size` 告警而 **MSVC 没有**。
- 你能讲清 **NUMA** 的本地/远端访问代价，**first-touch** 的“谁先写、分给谁的本地节点”，以及**线程亲和性**为何是 NUMA 局部性优化的前提。

> 本模块建立在你对“多核、多线程、原子写”的基本认知之上（模块 E/F）。若对原子自增、`memory_order_relaxed` 还不熟，建议先回头确认。

## 练习 J-1：伪共享实测

> 代码目录：`exercises/J1_false_sharing/`

### 目标

亲手把**伪共享的性能代价**量化出来：两个线程各自高频写一个计数器，逻辑上互不相干。先让两个计数器**相邻**（极可能同处一条缓存行）跑一遍计时；再用 `alignas(std::hardware_destructive_interference_size)`（或 64）把它们**分到不同缓存行**跑一遍；打印两者耗时与加速比（speedup），用数字证明伪共享真实存在。

### 前置理解

- **缓存行（cache line）**：CPU 缓存与缓存一致性协议（cache coherence，如 MESI）的**最小搬运单位**，x86-64 上典型为 **64 字节**。CPU 在核心间传输数据时，永远以整条缓存行为粒度，而非单个变量或字节。
- **伪共享（false sharing）**：不同线程频繁写**各自的**变量，但这些变量恰好落在**同一条**缓存行。当核心 A 写它的变量时，MESI 协议要求它独占（Modified 态）整条缓存行，于是核心 B 持有的该行副本被**失效（invalidate）**；B 接着写它自己的变量时又把行抢回去……整条缓存行就在两个核心间反复**弹跳（cache line bouncing）**。两个线程明明没有共享任何变量，却像在争一把锁——“共享”是假的，争用是真的。
- **对策**：用 `alignas(缓存行大小)` 给“被不同线程写”的对象做**对齐 + 填充（padding）**，强制它们各自起始于、并独占一条缓存行。这样核心 A 写自己的行不再波及核心 B 的行，弹跳消失。
- **与原子无关**：伪共享是缓存一致性层面的现象，普通的 `int` 写同样会触发。本题用 `atomic<int64_t>` 只是为了让“写竞争”更纯粹、计时更稳定。

### 必做任务

1. **测伪共享版**（对应 `// TODO [必做 1]`）：构造相邻计数器结构 `CountersShared{ atomic<int64_t> a, b; }`（`sizeof` 仅 16 字节，同一缓存行）。开两个线程，线程 0 反复 `a.fetch_add`，线程 1 反复 `b.fetch_add`（各 `kIters` 次，用 `memory_order_relaxed`），join，用 `steady_clock` 计时记 `ms_shared`。
2. **测对齐版**（对应 `// TODO [必做 2]`）：构造 `alignas(kCacheLine)` 的 `PaddedCounter`，组成 `CountersPadded{ PaddedCounter a, b; }`（a、b 各占一条缓存行）。同样两线程各锤一个，计时记 `ms_padded`，打印两者耗时与 `speedup = ms_shared / ms_padded`。

### 进阶任务

- **裸 int 验证**（`// TODO [进阶 1]`）：把 `atomic<int64_t>` 换成普通 `int64_t`（注意防优化器把循环优化掉，可累加打印或用 `volatile`），确认伪共享对“普通写”同样成立，与原子无关。
- **分片计数器**（`// TODO [进阶 2]`）：把线程数加到机器核数，用一个 `PaddedCounter` 数组（每核一个），对比“数组元素相邻打包”与“每元素 `alignas` 缓存行”的总吞吐——这正是并发计数器/分片统计（sharded counter）的标准做法。

### 验收点

- 伪共享版明显慢于对齐版，`speedup` 常见 **2~8 倍**（随 CPU、核数、调度而异；参考实现在某 32 核机上实测约 **7.9 倍**）。
- 你能解释这个差距**不是**算法差异（两版做的加法次数完全相同），而是缓存行争用。
- 从 `sizeof` 输出能看出布局差异：`CountersShared`=16 字节（挤在一起），`PaddedCounter`=64 字节、`alignof`=64（被填充到一条缓存行），`CountersPadded`=128 字节（各占一行）。

### 观察点

- `alignas(64)` 让 `sizeof(PaddedCounter)` 从 8 涨到 64：多出来的 56 字节是**故意浪费**的填充——用空间换“独占缓存行”。
- 加速比随机器变化很大：核数越多、缓存一致性流量越贵的平台，伪共享越致命。
- 计时若不稳定，适当加大 `kIters`，并确保 Release 构建。

### 常见坑

- **用 Debug 构建测**：Debug 下原子操作和循环开销很大，会**掩盖**伪共享差距（甚至看不出差别）。务必 Release。
- **以为只有原子才会伪共享**：错。普通变量同样会。伪共享是缓存层面的，不挑数据类型。
- **对齐写错粒度**：`alignas` 要按**缓存行**（64）对齐，而不是按变量大小（8）。后者根本没把变量推到不同行。
- **以为“变量不同名/不同对象”就安全**：安全与否只看**物理地址是否落在同一缓存行**，与是不是同一个变量无关。

### 提示

- 用 `memory_order_relaxed`：本题只关心“写同一缓存行的竞争代价”，不需要任何跨线程顺序保证，避免内存序开销污染对比。
- 读一下计数结果（或打印）以防整段循环被优化器消除。
- 用本仓库 `cs::logf(...)`（`concurrency_study/log.hpp`）打印结果。

### 复盘问题

- 伪共享用一句话怎么说？它和“真共享”（多个线程真的访问同一变量）有什么区别？
- 为什么两个线程“各写各的”还会互相拖慢？缓存一致性协议在其中扮演什么角色？
- `alignas(64)` 是怎么消除伪共享的？多出来的填充字节换来了什么？
- 如果换成 8 字节对齐（变量自身大小），还能消除伪共享吗？为什么？

- cppreference [`hardware_destructive_interference_size`](https://en.cppreference.com/w/cpp/thread/hardware_destructive_interference_size)

## 练习 J-2：硬件干扰尺寸常量

> 代码目录：`exercises/J2_interference_size/`

### 目标

把 J-1 里硬编码的“魔法数 64”升级为标准、可移植的编译期常量：认识 **C++17**（`<new>`）引入的一对实现定义常量 `std::hardware_destructive_interference_size`（破坏性干扰尺寸）与 `std::hardware_constructive_interference_size`（建设性干扰尺寸）。打印它们的值，用 destructive 常量做对齐结构体并用 `static_assert` 验证 `alignof`，并讲清两者**语义上的对立**。

### 前置理解

- **为什么需要这对常量**：J-1 里我们写死了 64。但缓存行大小是平台相关的（有的架构 128，有的 32），写死不可移植。C++17 给了标准常量，让“缓存行级对齐”这件事可移植地表达。
- **`hardware_destructive_interference_size`（破坏性，"离我远点"）**：两个被**不同线程**频繁访问的对象，至少应相距这么多字节，才能保证落在**不同缓存行**、互不干扰。它是 J-1 中“隔开计数器”的标准尺子——用它做 `alignas`/padding 来**避免伪共享**。
- **`hardware_constructive_interference_size`（建设性，"凑过来"）**：两个对象若想**促进真共享 / 提升局部性**（希望被同一线程一起访问时同处一条缓存行、一次缓存载入就全部命中），它们的合并大小**不应超过**这么多字节。用它把相关的热字段**聚拢**在一起。
- **标准保证与取值**：二者都是**实现定义值**，标准只保证 `>= alignof(std::max_align_t)`，且通常 `destructive >= constructive`。x86-64 上常见实现里**二者都等于 64**（一条缓存行）。判定实现是否提供它们用特性测试宏 `__cpp_lib_hardware_interference_size`。
- **GCC 的 `-Winterference-size` 告警**：GCC 对“在 ABI 边界（如导出到库的结构体布局）上直接使用该常量”会告警，因为该值随编译目标变化、可能破坏二进制布局兼容性，建议库 ABI 写死常量。**MSVC（含 VS2026）没有这个告警**。本练习只在单个可执行内使用、不跨 ABI 边界，任一实现都安全。

### 必做任务

1. **打印两个常量**（对应 `// TODO [必做 1]`）：打印 `destructive`、`constructive` 的值与 `alignof(std::max_align_t)`，并用注释/输出说清各自用途与“都 `>= alignof(max_align_t)`”这条标准保证。
2. **两个对齐策略结构体**（对应 `// TODO [必做 2]`）：
   - `DestructiveLayout`：两个 `alignas(destructive)` 的计数器（模拟被不同线程写），`static_assert(alignof == destructive)`，`sizeof >= 2*destructive`（各占独立行）；
   - `ConstructiveLayout`：`alignas(constructive)`，内含一簇“总是一起访问”的热字段，`static_assert(alignof == constructive)` 且字段裸大小 `<= constructive`（聚拢在一行内）；
   - 再对照一个紧凑打包版 `PackedLayout`，打印三者 `alignof/sizeof` 看差异。

### 进阶任务

- **分片计数器实测**（`// TODO [进阶 1]`）：用 `atomic` 数组做分片计数器，分别按“紧凑打包”与 `alignas(destructive)` 两种布局压测，量化对齐带来的吞吐提升（与 J-1 呼应）。
- **真实库对照**（`// TODO [进阶 2]`）：读 folly 的 `CachelineAligned` / Boost.Align 如何封装缓存行对齐，对照标准常量的可移植性，并解释 GCC `-Winterference-size` 在“跨 ABI 复用对齐结构体”时为何有意义（MSVC 无此告警，注明）。

### 验收点

- 能打印出两个常量的实际值（本机实测均为 **64**）。
- `static_assert` 通过：`DestructiveLayout` 的 `alignof == destructive`（两计数器各占独立缓存行）；`ConstructiveLayout` 的 `alignof == constructive` 且热字段簇装得进一条缓存行。
- 能用一句话区分二者：**destructive=隔开（防伪共享）**，**constructive=聚拢（提局部性）**。

### 观察点

- `sizeof(DestructiveLayout)` 通常是 `2*64=128`：每个 `alignas` 成员都被推到独立行。
- `ConstructiveLayout` 把 `int32+int32+int64` 这 16 字节裸数据聚在一条 64 字节行内，远未越界。
- `PackedLayout` 的 `alignof` 只有 8、`sizeof` 只有 16——正是伪共享温床。

### 常见坑

- **混淆两个常量的用途**：destructive 是“别人写的东西离我远点”，constructive 是“我自己要一起读的东西凑过来”。用反了，要么没消除伪共享，要么把数据切到两行损失局部性。
- **以为常量一定是 64**：是实现定义。不要在跨平台代码里假设具体数值，用常量本身。
- **跨 ABI 边界直接用常量（GCC）**：会触发 `-Winterference-size`。库的公开布局应写死一个约定值。MSVC 不告警，但移植到 GCC 时要注意。
- **constructive 簇过大**：若一起访问的字段总和超过 constructive，它会被切到两条缓存行，聚拢失去意义。

### 提示

- 用 `__cpp_lib_hardware_interference_size` 做特性检测，缺失时回退 64，保证任意实现可编译。
- `static_assert` 是验证对齐契约的零成本手段，比运行期打印更早暴露错误。

### 复盘问题

- 这两个常量分别在什么场景下用？各举一个例子。
- 为什么标准把它们定为“实现定义值”而不是固定 64？
- GCC 的 `-Winterference-size` 在担心什么？为什么 MSVC 不需要这个告警也没关系？
- constructive 尺寸如果用错（簇超过它），会发生什么？

## 练习 J-3：NUMA 概念与亲和性

> 代码目录：`exercises/J3_numa_concept/`

### 目标

把视野从“单机一条缓存行”放大到“多路服务器的内存拓扑”：说清 **NUMA（Non-Uniform Memory Access，非一致内存访问）** 的访问代价、**first-touch（首次接触）** 内存放置策略，以及**线程亲和性（thread affinity）**。用 Windows 的 `SetThreadAffinityMask`（`#ifdef _WIN32` 包裹）演示把线程绑定到指定核。本题以**概念 + 绑核小实验**为主，不强求真 NUMA 硬件。

### 前置理解

- **NUMA**：在多路（多 socket）服务器上，内存被分成若干 **NUMA 节点（node）**，每个节点“贴着”一组 CPU 核。核心访问**本地节点**内存快；访问**远端节点**内存要穿过处理器互联（Intel QPI/UPI、AMD Infinity Fabric），延迟更高、带宽更低。访问代价随“数据在哪个节点 + 谁在访问”而**不一致**——这就是 NUMA 的字面含义。对照模块 J 前两题：伪共享是“核间缓存行争用”，NUMA 是“跨节点内存访问代价”，都是“数据放哪、谁访问”决定性能。
- **first-touch（首次接触）**：Linux 等系统默认在某物理页被**第一次写入**时，把它分配到**写入线程当时所在 CPU 的本地节点**。推论极其重要：**谁先写，就分给谁的本地节点**。所以并行程序应让“将来读写某块数据的线程”去**亲手初始化**那块数据，数据才会落在它的本地节点；若全由主线程初始化，所有页都落在主线程的节点，其余 worker 全程远端访问，慢。
- **线程亲和性（thread affinity）**：把线程**绑定**到指定 CPU 核。两重价值：(1) 减少线程在核间迁移导致的 L1/L2 缓存损失；(2) 让线程**稳定待在某 NUMA 节点**，是配合 first-touch 拿到本地内存的前提。
  - Windows：`SetThreadAffinityMask(thread, mask)`，mask 是位图，第 k 位为 1 表示允许在第 k 号逻辑核运行；只置一位即“钉死单核”。查询 NUMA 拓扑用 `GetLogicalProcessorInformationEx`、`GetNumaHighestNodeNumber`，按节点分配内存用 `VirtualAllocExNuma`。
  - Linux：`pthread_setaffinity_np` + `cpu_set_t`；libnuma 的 `numa_alloc_onnode` 显式按节点分配。
  - macOS：仅有建议性的 thread affinity policy，不保证。

### 必做任务

1. **绑核 + first-touch 微缩演示**（对应 `// TODO [必做 1]`）：开 N 个线程（`N = min(hardware_concurrency, 4)`），第 i 个线程：(a) 调 `pin_current_thread_to_cpu(i)` 把自己绑到第 i 号核；(b) **亲手初始化**一块本地数据（first-touch 思想的微缩体现）；(c) 跑一段热负载；(d) 打印绑核成功与否。主线程 join 后汇总成功绑核数。非 Windows 平台 `pin_*` 返回 false，打印“跳过”。

### 进阶任务

- **first-touch 收益量化**（`// TODO [进阶 1]`）：在真 NUMA 机上实现“反例（主线程统一初始化整个大数组）vs 正解（各 worker 自己初始化其分片）”，用 `steady_clock` 计时对比，量化 first-touch 的收益。
- **显式节点放置**（`// TODO [进阶 2]`）：用 `VirtualAllocExNuma`（Windows）或 `numa_alloc_onnode`（Linux, libnuma）显式把内存分配到指定节点，结合 `SetThreadAffinityMask` 绑核，构造“本地访问 vs 强制远端访问”的对照实验。

### 验收点

- 在 Windows 上能成功把多个线程分别绑到不同核（参考实现在某 32 核机上实测 **4/4 成功**）。
- 能讲清 NUMA 的本地/远端访问代价，以及 first-touch“谁先写、分给谁的本地节点”。
- 能说清亲和性为何是 NUMA 局部性优化的前提；并理解**单 NUMA 节点的台式机/笔记本上 first-touch 无可测差异**（没有远端节点可言），收益只在真多节点服务器上出现。

### 观察点

- 运行时打开任务管理器/资源监视器，可看到各被绑核线程分别压在不同核上。
- `hardware_concurrency()` 给出逻辑核总数；NUMA 拓扑（哪些核属哪个节点）需另用平台 API 查询。
- 在单节点机器上本题“反例 vs 正解”两种写法跑出来一样快——这本身就是个要理解的结论，而非 bug。

### 常见坑

- **以为绑核就一定更快**：绑核减少迁移，但若把多个重负载线程绑到同一核会争用、反而更慢。绑核是为“稳定的局部性”，不是越绑越好。
- **忽视 first-touch，全由主线程初始化**：这是 NUMA 程序最常见的性能 bug——数据全堆在一个节点，其余核全程远端访问。
- **在单节点机上找 NUMA 收益**：找不到。先用 `GetNumaHighestNodeNumber`/`numactl --hardware` 确认机器真有多个节点。
- **跨亲和性组（Windows >64 逻辑核）**：`SetThreadAffinityMask` 只覆盖单个处理器组（最多 64 核），更大规模要用 `SetThreadGroupAffinity`。本题已限制 `cpu_index < 位宽`。

### 提示

- 用 `#ifdef _WIN32` 隔离平台相关 API，非 Windows 路径返回 false 并打印说明，保证跨平台可编译。
- 亲和性掩码 `1u << cpu_index` 只置一位 = 绑单核；要绑一组核就置多位。
- 真要做 NUMA 实验，先确认硬件确实是多节点（否则一切现象都不会出现）。

### 复盘问题

- NUMA 的“非一致”指的是什么不一致？哪种访问快、哪种慢？
- first-touch 是“谁分配”决定页的归属节点，还是“谁先写”？这对并行初始化代码意味着什么？
- 线程亲和性和 NUMA 局部性是什么关系？为什么说亲和性是前提？
- 为什么在你自己的笔记本上跑 J-3 看不出 first-touch 的性能差异？

## 做完模块 J 之后，你现在应该能说清楚什么

- **缓存行与伪共享**：CPU 以整条缓存行（典型 64 字节）为单位在核间搬数据；不同线程写各自变量但同处一行，会引发缓存行弹跳（cache line bouncing），让“逻辑无冲突”的写互相拖慢。你能写程序把这个代价测出来（参考实现约 7.9 倍差距）。
- **`hardware_destructive/constructive_interference_size`**：C++17、`<new>`、实现定义值、`>= alignof(max_align_t)`。destructive 用来**隔开**被不同线程写的对象避免伪共享；constructive 用来把一起访问的对象**聚拢**提升局部性。你知道 GCC 有 `-Winterference-size` 告警而 MSVC 没有。
- **`alignas` 对策**：用 `alignas(缓存行)` 做对齐 + 填充，把变量推到独立缓存行，是消除伪共享的标准手段；代价是空间（padding）。
- **NUMA**：多路服务器内存按节点划分，本地访问快、跨节点慢；**first-touch** 让物理页归属“首次写入它的线程所在节点”，所以应让使用数据的线程亲手初始化数据；**线程亲和性**把线程绑到固定核，是稳定 NUMA 局部性的前提。
