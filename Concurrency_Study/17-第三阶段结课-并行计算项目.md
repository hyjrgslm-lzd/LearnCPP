# 17 第三阶段结课 · 并行计算项目

## 这份文件怎么用

阶段三的四个模块（J/K/L/M）把"数据并行"这件事拆成了四块零件单独练：

- **模块 J（缓存与伪共享）**：缓存行（cache line，典型 64 字节）是缓存一致性协议的最小搬运单位；多线程各写各的计数器若落在同一缓存行就会发生伪共享（false sharing），用 `alignas(std::hardware_destructive_interference_size)` 把它们推到不同缓存行消除之；以及"缓存局部性（cache locality）/ 分块（cache blocking / tiling）"对带宽受限计算的决定性影响。
- **模块 K（数据并行与 std::simd）**：单指令多数据（Single Instruction Multiple Data，SIMD）——一条指令同时算 4/8/16 个 `float`；编译器自动向量化（auto-vectorization）的触发条件、SIMD-friendly 的循环写法、以及 `std::simd`/xsimd 的显式向量化（本结课项目把显式 SIMD 列为进阶，指回模块 K）。
- **模块 L（并行算法与执行策略）**：并行标准模板库（Standard Template Library，STL）——`std::execution::par` / `par_unseq`、`std::transform_reduce` 的并行归约、以及"并行不是免费午餐"的加速比测量方法学（预热、取最小值、Release、防优化）。
- **模块 M（工作窃取与结构化并发桥接）**：把任务拆给线程池、工作窃取（work stealing）的思路，以及与 `std::async` 的桥接。

这份文件负责把上面的零件**重新拼成一个"端到端的并行计算项目"**：拿一个真实的、计算量可观的核心算法，先写出**朴素串行版**作为正确性基线与计时基线，再**逐层加速**——缓存分块 → 并行 STL → SIMD-friendly 循环——每加一层都**重新测耗时、重新校验结果**，最后画一张"版本 × 耗时 × 加速比 × GFLOPS"的表。它几乎用到了阶段三的每一个概念，是检验你是否真正掌握"把并行优化按层叠加、并用实测证据说话"的试金石。

> **本项目刻意自包含、零外部依赖**：只用标准库（MSVC 把并行算法内置，无需链接 TBB）+ 模块 J 的伪共享规避技巧。SIMD 部分用**编译器自动向量化 + 手写 SIMD-friendly 循环**实现（不依赖 xsimd / `std::simd`）；把 xsimd / `std::simd` 的**显式向量化**列为进阶方向，指回**模块 K**。这样你只需 `cl` 或 VS2026 一键就能跑，不必配置任何第三方库。

建议顺序：先在纸上把三种核心算法的**数据布局与访存模式**画清楚（尤其矩阵乘里"为什么朴素三重循环对 `B` 的访问是跨行跳的、为什么分块能把工作集塞进缓存"），再动手把 `main.cpp` 里的 `// TODO` 占位替换成真正的分块 / 并行 / 向量化实现。

> 直接复用的前置题：练习 J-1（伪共享实测）、练习 J-2（`hardware_*_interference_size`）、练习 L-1（并行算法）、练习 L-2（`transform_reduce` 并行归约/扫描）、练习 L-3（并行 vs 串行基准方法学）、练习 K-1/K-2（SIMD 点积，进阶显式向量化的起点）。

## 项目目标

实现一组**计算密集型核心算法的多版本优化**，并用统一的基准框架量化每一层优化的收益。建议以**矩阵乘（GEMM）为主线**（最能体现"分块 + 并行 + 向量化"三层叠加），另两项作为对照：

1. **矩阵乘（GEMM，General Matrix Multiply）—— 主线**：
   `C = A × B`（方阵，`float`，行主序 row-major）。
   - **v0 朴素三重循环**：`i-j-k` 顺序，对 `B` 的访问跨行跳（stride-N），缓存极不友好 —— 正确性与计时基线。
   - **v1 缓存分块（tiling / cache blocking）**：把矩阵切成 `BS×BS` 的小块，让每个小块的工作集驻留在 L1/L2 缓存里，大幅减少缓存缺失（cache miss）。
   - **v2 并行分块**：用 `std::execution::par` 把外层（按行块或行）并行化，多核同时算不同的行块。
   - 对比三版的耗时、加速比、GFLOPS，并校验三版结果**逐元素一致**（容差内）。

2. **大规模并行归约（parallel reduction）—— 对照**：
   对一个大数组求和 / 求 L2 范数。
   - **标准版**：`std::transform_reduce(std::execution::par, ...)`。
   - **手写版**：每线程**局部累加**到一个 `alignas(hardware_destructive_interference_size)` 的槽位（避免伪共享），最后合并 —— 与标准并行版对照，亲手体会"为什么归约要避免伪共享、为什么浮点归约要在意结合律"。

3. **并行排序（parallel sort）—— 对照**：
   `std::sort` vs `std::sort(std::execution::par, ...)`，在不同规模下测加速比，体会"排序的并行收益与规模强相关"。

这个项目的重点**不是**"写出史上最快的 GEMM"（那需要汇编级调优、寄存器分块、预取，超出学习范围），而是让你把四件事同时做对：

- **按层叠加优化，每层都测**：朴素 → 分块 → 并行 →（进阶）显式 SIMD，每加一层都重新计时 + 重新校验，用一张表说清"每层各贡献了多少加速"。
- **把访存模式当一等公民**：能解释为什么朴素 GEMM 慢在"对 `B` 跨行跳"，为什么分块能把工作集塞进缓存，为什么这是**带宽受限（memory-bound）**而非纯算力受限的问题。
- **并行归约要避免伪共享、要尊重结合律**：能说清手写归约里"每线程局部累加 + 缓存行对齐"的两个理由，以及浮点加法不满足结合律对并行求和结果的影响。
- **用方法学严谨地测加速比**：预热、多跑取最小值、Release/优化、`volatile` sink 防优化 —— 否则测出来的"加速比"全是噪声。

## 固定题面

对外接口固定为下面这组（签名是验收的一部分，请勿改动语义）：

```cpp
// ---- 矩阵乘：方阵，行主序，C = A * B（函数内先把 C 清零）----
// 三个版本签名一致，便于在基准框架里统一调用与对照。
void gemm_naive(const float* A, const float* B, float* C, int N);             // v0 朴素 i-j-k
void gemm_tiled(const float* A, const float* B, float* C, int N, int BS);     // v1 分块
void gemm_par  (const float* A, const float* B, float* C, int N, int BS);     // v2 并行分块

// ---- 并行归约：求和 ----
double reduce_par_std   (const float* data, std::size_t n); // std::transform_reduce(par)
double reduce_par_manual(const float* data, std::size_t n); // 每线程局部累加 + alignas 防伪共享

// ---- 并行排序：原地排序 ----
void sort_seq(std::vector<int>& v); // std::sort
void sort_par(std::vector<int>& v); // std::sort(par)
```

## 必须包含的设计约束

1. **必须综合阶段三的核心**：并行 STL（`std::execution::par`，MSVC 内置，模块 L）、伪共享规避（`alignas(std::hardware_destructive_interference_size)`，模块 J）、缓存局部性 / 分块（cache blocking，模块 J）、并行归约需结合律（模块 L）。
2. **逐层叠加、每层都测**：v0/v1/v2 必须**独立成函数**且签名统一，基准框架对三者一视同仁地计时、校验、算 GFLOPS。**不允许**把分块和并行揉成一坨无法单独计时的代码。
3. **正确性校验先于性能**：每个加速版本（v1/v2/手写归约/并行排序）都必须**先与基线版逐元素比对通过**（浮点用相对/绝对容差），再谈耗时。校验失败时基准结果一律作废。
4. **加速比测量方法学逐条落实**：
   - **预热（warm-up）**：正式计时前先跑一次不计入，让线程池 / 页缓存就绪；
   - **多跑取最小值（min）**：每个配置跑多次取最小耗时 —— 最小值最接近"无被抢占干扰"的真实耗时，比平均值稳定；
   - **Release / 优化**：Debug 下并行往往更慢、向量化被关闭，必须在 Release（`/O2`）下观察趋势；
   - **防优化（anti-DCE）**：用 `volatile` sink 吸收结果，防止编译器把"结果没人用"的计算整段删掉（dead code elimination，DCE）。
5. **GFLOPS 口径统一**：GEMM 的浮点运算次数固定按 `2 * N^3`（每个输出元素 `N` 次乘 + `N` 次加，共 `N^2` 个输出）计；GFLOPS = `2 * N^3 / (耗时秒 * 1e9)`。三版用同一口径才可比。
6. **手写归约必须避免伪共享**：每线程的局部累加器必须落在**独立缓存行**（`alignas(std::hardware_destructive_interference_size)` 或保守的 64 字节），否则伪共享会让"手写并行版反而比标准版慢"——这恰是模块 J 的核心教学点，必须在代码里体现并能解释。

## 推荐输入输出模型

- **输入**：程序内部用固定随机种子（`std::mt19937`）生成测试数据（矩阵元素、归约数组、待排序数组），保证**可复现**；规模写成常量便于调整（GEMM 建议 `N=512`，归约/排序建议 `n=2^24` 量级，按机器内存酌情调整）。
- **输出**：纯 `stdout` 文本表格。每个任务打印一张表：

  ```
  ==== GEMM (N=512, BS=64) ====
  版本           耗时(ms)     加速比      GFLOPS    校验
  v0 naive       1234.5       1.00x       0.22      基线
  v1 tiled        456.7       2.70x       0.59      OK
  v2 par           98.3      12.55x       2.73      OK
  ```

- **校验列**：基线版标"基线"，其余版本与基线逐元素比对，通过标 `OK`、失败标 `FAIL(差值)`。
- 无需读写文件、无需命令行参数、无需任何第三方库 —— 一个 `.exe` 跑完打印全部结果。

## 必做任务

> 骨架已把基准框架（计时、GFLOPS、校验、表格）写好；下面 8 条对应 `main.cpp` 里的 `// TODO [必做 N]:`。未填处给了"最小占位实现"（多为串行/朴素版）保证可编译运行且结果正确，你的任务是把占位替换为真正的优化实现。

1. **GEMM v0 朴素三重循环**（基线）：实现 `gemm_naive`，标准 `i-j-k` 顺序，`C[i*N+j] += A[i*N+k] * B[k*N+j]`。这是正确性与计时的基线，**先把它写对**（占位已给，建议遮住重写一遍并解释"对 `B` 的访问为什么跨行跳"）。
2. **GEMM v1 缓存分块**：实现 `gemm_tiled`，六重循环 `(ii,jj,kk)` 外层按 `BS` 步进分块、`(i,j,k)` 内层在块内遍历，使每个 `BS×BS` 块的工作集驻留缓存。校验须与 v0 逐元素一致。
3. **GEMM v2 并行分块**：实现 `gemm_par`，在 v1 基础上把**最外层行块**用 `std::execution::par` 并行（推荐：构造一个行块起始索引数组，`std::for_each(par, ...)` 每个任务算一条行块）。注意**不同任务写 `C` 的不相交行区间**，天然无数据竞争、无需锁。
4. **并行归约·标准版**：实现 `reduce_par_std`，用 `std::transform_reduce(std::execution::par, data, data+n, 0.0, std::plus<>{}, [](float x){ return (double)x; })`（或等价形式）求和。注意累加器用 `double` 以减小浮点误差。
5. **并行归约·手写版**：实现 `reduce_par_manual`，把数组分块给 `T` 个线程，每线程把局部和写进一个 `alignas(std::hardware_destructive_interference_size)` 的槽位（**避免伪共享**），主线程最后把所有槽位相加。校验须与标准版在浮点容差内一致。
6. **并行排序对照**：实现 `sort_seq` / `sort_par`（`std::sort` vs `std::sort(std::execution::par, ...)`），在基准框架里对不同规模各测一次加速比。
7. **接入基准框架**：把上述函数挂到 `bench_min_ms`（预热 + 多跑取最小）上，正确填充每张表的耗时、加速比、GFLOPS 列，并调用校验函数填"校验"列。
8. **写正确性校验**：实现 `verify_equal`（矩阵逐元素相对/绝对容差比较）与归约/排序的校验，**确保任何加速版本先过校验再报耗时**。

## 进阶任务

- **显式 SIMD 向量化（指回模块 K）**：把 GEMM 内核或归约用 `std::simd`（C++26，模块 K）或 xsimd 显式向量化（一条指令算 8 个 `float`），与编译器自动向量化对比 GFLOPS。这是本结课项目刻意留给模块 K 的延伸——本题主体只靠自动向量化 + SIMD-friendly 循环。
- **分块大小扫描**：对 `BS ∈ {16,32,64,128}` 扫一遍，找出本机最佳分块（与 L1/L2 容量的关系），画出"BS × GFLOPS"曲线，解释为什么太小/太大都不好。
- **transpose-B 优化**：先把 `B` 转置成列主序再做 GEMM，让内层 `k` 循环对 `A`、`B^T` 都顺序访问，与分块版对比，体会"换布局 vs 换循环结构"两条路。
- **归约的结合律实验**：把手写归约的"每线程局部和"用**不同的分块数 / 不同合并顺序**各算一遍，观察浮点求和结果的**末位差异**，量化"并行归约不满足结合律"的实际影响。
- **`par` vs `par_unseq` 对照**：GEMM/归约分别用 `par` 与 `par_unseq` 各测一遍，看向量化约束放开后是否更快（结合 L-3 的方法学）。
- **NUMA 与线程亲和（概念，指回 J-3）**：在多路机器上讨论"先触碰（first-touch）"页分配与线程绑核对 GEMM 带宽的影响（仅概念，不要求实现）。
- **缓存缺失计数（工具）**：用 VTune / `perf` 量一量 v0 与 v1 的 L1/L2 缺失率差异，把"分块为什么快"从"猜"变成"测"。

## 验收点

- 你能跑出 GEMM 三版（v0/v1/v2）的耗时、加速比、GFLOPS 表，且三版结果**逐元素一致**（校验全 `OK`），多次运行趋势稳定。
- 你能解释**为什么朴素 GEMM 慢**——指出对 `B` 的访问是 stride-N 跨行跳、缓存命中率低；并解释**分块为什么快**——工作集驻留缓存、复用 `A`/`B` 块。
- 你能解释 v2 的并行**为什么无需锁**——不同任务写 `C` 的不相交行区间，没有数据竞争。
- 你能跑出并行归约标准版与手写版的耗时，且手写版**确实避免了伪共享**（局部累加器缓存行对齐），并能解释"若不对齐会怎样"。
- 你能说清**浮点归约为什么受结合律影响**——并行分块改变了加法结合顺序，结果可能与串行逐元素相加有末位差异。
- 你的基准框架**正确落实了方法学**：预热、多跑取最小、Release、`volatile` sink 防优化，你能逐条说出每项的理由。
- 你能解释 GFLOPS 的 `2*N^3` 口径，并据此判断本机 GEMM 离峰值算力还差多远（以及为什么差这么多）。

## 项目复盘问题

- 朴素 GEMM 的三重循环里，`i-j-k`、`i-k-j`、`k-i-j` 三种顺序的访存模式各是什么样？哪种对自动向量化最友好？为什么 `i-k-j` 常比 `i-j-k` 快很多（提示：内层对 `C` 与 `B` 都顺序）？
- 分块大小 `BS` 怎么选？它和 L1/L2 缓存容量、缓存行大小是什么关系？为什么 `BS` 太大反而会变慢？
- v2 把"行块"分给多线程，为什么不需要任何锁或原子操作？如果改成"每个任务算一列块"，写 `C` 还安全吗？
- 手写并行归约里，如果**去掉** `alignas`，让 `T` 个线程的局部累加器紧挨着，会发生什么？吞吐会怎样变化？这和模块 J 的伪共享实验是同一回事吗？
- 为什么并行求和的结果可能和串行求和**不完全相等**？这是 bug 还是浮点的固有性质？什么情况下这个差异会被放大到不可接受？
- `std::transform_reduce` 的第三个参数（init 值）和"二元归约操作必须满足结合律"之间是什么关系？如果传一个**非结合**的操作（如减法）给它，结果为什么不确定？
- 你测加速比时，如果**忘了预热**、或用**平均值**而非最小值、或在 **Debug** 下测，分别会让结论错在哪？
- `volatile` sink 是怎么阻止编译器删掉计算的？如果不用它，朴素 GEMM 的计时可能会出现什么诡异现象？
- 为什么本题"自动向量化 + SIMD-friendly 循环"就够，而把显式 `std::simd`/xsimd 列为进阶？显式 SIMD 相比自动向量化，多拿到的收益和多付出的代价分别是什么（指回模块 K）？
- 并行排序的加速比为什么和数据规模强相关？小数组用 `par` 排序为什么可能更慢（结合 L-3 的"并行不是免费午餐"）？
