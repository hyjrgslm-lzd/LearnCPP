# 04 模块 C：条件变量

## 模块目标

前面两个模块里，你学会了用线程把工作切开（模块 A），用互斥量（mutex）把共享数据保护起来（模块 B）。但还有一个反复出现的需求一直没被正面解决：**一个线程需要等另一个线程把某个条件准备好，再继续往下走**。

到目前为止你只有两种笨办法：要么忙等（busy-wait，`while (!ready) {}` 空转烧 CPU），要么定时轮询（`sleep` 一下再查一次，既慢又浪费）。这个模块给你正确的工具——**条件变量（condition variable，CV）**：让线程在条件不满足时主动睡去、不占 CPU，等另一个线程改变条件并发出通知（notify）时再被精确唤醒。

但条件变量是 C++ 并发里最容易写错的原语之一。它的两个经典坑——**虚假唤醒（spurious wakeup）**和**丢失唤醒（lost wakeup）**——会让“看起来能跑”的代码在压力下偶发死锁或提前推进。本模块的核心就是把“为什么 wait 必须配谓词（predicate）”这件事彻底讲透，让你以后写任何 CV 代码都条件反射地带上谓词。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- `std::condition_variable` 的 wait / notify 协议：谁持锁、wait 时锁如何被释放又重新获取、notify 唤醒了谁。
- 为什么 `wait` 必须配谓词，谓词版 `wait(lk, pred)` 与 `while (!pred()) wait(lk);` 的等价关系，以及它如何同时防住虚假唤醒和丢失唤醒。
- `notify_one` 与 `notify_all` 的语义差异，以及“一次状态变化只放行一个等待者”这条经验法则的边界。
- 如何用一把 mutex + 两个 CV 实现有界阻塞队列，以及为什么这里要用两个 CV、为什么 push/pop 里选 `notify_one`。
- `std::condition_variable_any` 配 `std::stop_token` 的可中断等待（C++20）是什么，它与“在谓词里塞一个关闭标志”这套做法相比，差异和取舍在哪里。

## 练习 C-1：条件变量与谓词等待

> 代码目录：`exercises/C1_condvar_predicate/`

### 目标

用 `std::condition_variable` + `std::mutex` + 谓词，实现一次“主线程置位 `ready` 后通知 worker 开工”的交接（handoff）。在做对它的同时，**亲手写出不带谓词的错误版本**，观察它如何丢失唤醒，建立“CV 的 wait 永远要配谓词”的肌肉记忆。

### 前置理解

- 你已经会用 `std::mutex` / `std::unique_lock`（模块 B）。条件变量从不单独存在：它**总是**与一把 mutex 和一个“共享谓词状态”绑定成三件套。
- 条件变量（condition variable，CV）来自 `<condition_variable>`，是 C++11 引入的。`std::condition_variable` 只能配 `std::unique_lock<std::mutex>`。
- 你知道 `wait` 会做三件事：**原子地**释放锁并让当前线程睡去；被唤醒后重新获取锁；返回。这意味着 wait 期间锁是放开的，别的线程才有机会去改谓词、发通知。
- 关键概念：
  - **虚假唤醒（spurious wakeup）**：`wait` 可能在没有任何 `notify` 的情况下自行返回。这是底层实现允许的行为，不是 bug。因此醒来后**必须重新检查条件**。
  - **丢失唤醒（lost wakeup）**：如果 `notify` 发生在 `wait` 真正进入睡眠之前，这一发通知就打在空气上、永久丢失，等待者可能永远醒不来。
  - **谓词版 wait**：`cv.wait(lk, pred)` 在语义上**完全等价于** `while (!pred()) cv.wait(lk);`。它在睡前先查一次谓词（若已满足则根本不睡 → 防丢失唤醒），每次醒来再查一次（不满足就继续睡 → 防虚假唤醒）。这两个坑被同一行代码一并解决。

### 必做任务

1. **正确的谓词等待**（对应 `// TODO [必做 1]`）：用 `condition_variable` + `mutex` + 一个 `bool ready` 谓词实现 handoff。worker 用 `cv.wait(lk, [&]{ return ready; })` 等待；主线程持锁置 `ready = true`，解锁后 `notify_one()`。观察 worker 被精确唤醒后开工。

2. **演示丢失唤醒**（对应 `// TODO [必做 2]`）：写一个反面版本——主线程**抢先**置位并 `notify_one`，此刻 worker 还没进入 wait；随后 worker 才启动、执行**不带谓词的裸 `wait`**。那一发 notify 已经丢失，裸 wait 会永久挂起。为了让程序仍能结束（而不是真的卡死整个测试），用带超时的 `wait_for` 把“丢失唤醒”显式暴露成一次超时返回。对照写出：若改成谓词版 wait，它会先检查到 `ready == true` 而立即返回，**根本不会丢**。

3. 记录并回答：
   - 谓词版 wait 为什么能同时免疫虚假唤醒和丢失唤醒？分别是谓词检查的哪一次起了作用？
   - `notify` 之前到底要不要持有那把锁？（见“常见坑”。）
   - 如果 worker 不在持锁状态下读 `ready`，会有什么问题？

### 进阶任务

- **notify_one vs notify_all**（对应 `// TODO [进阶 1]`）：让 3 个 worker 同时等待同一个 `ready` 谓词。主线程置位后用 `notify_all` 广播，观察三个都被唤醒。思考：若这里误用 `notify_one`，会发生什么？（答案：只有一个 worker 醒来，另外两个永远卡住——因为 `ready` 这个“广播型”事件只触发了一次唤醒。）
- 把谓词从 `bool` 换成一个计数器（例如“至少攒够 N 个信号才开工”），体会谓词可以是任意可调用对象。
- 测量：在循环里反复做 handoff，对比“谓词版 wait”与“轮询 + sleep(1ms)”两种方案的延迟与 CPU 占用，亲身感受 CV 为什么存在。

### 验收点

- 你能跑通正确的 handoff，并解释 wait 在睡眠期间释放了锁。
- 你能让反面版本观测到“丢失唤醒”（这里表现为超时），并说清谓词版为什么不会丢。
- 你能正确区分 `notify_one` 与 `notify_all` 的适用场景。
- 你能脱口而出：`wait(lk, pred)` 等价于 `while (!pred()) wait(lk);`。

### 观察点

- wait 期间锁是放开的——这是别的线程能修改谓词的前提，也是“wait 必须传一把 `unique_lock`”的原因（它需要可解锁/重锁）。
- 谓词检查发生在“睡前”和“每次醒来后”两个时刻；正是“睡前那一次”挡住了丢失唤醒。
- `notify_one` 唤醒至多一个等待者，`notify_all` 唤醒全部；被唤醒不等于“条件满足”，醒来后仍要靠谓词把关。
- 通知本身不携带数据：CV 只负责“叫醒”，真正的状态由你保护的共享变量承载。

### 常见坑

- **裸 wait（不传谓词）**：几乎总是错的。一旦 notify 早于 wait，就丢失唤醒；一旦虚假唤醒，就在条件不满足时往下跑。
- **在没持锁时修改谓词**：与读取方构成数据竞争（data race），即使后面补一个 notify 也救不回来。修改谓词必须在持锁状态下。
- **以为 notify 必须持锁**：标准允许在解锁后再 notify。持锁 notify 是安全的、但被唤醒者会立刻因抢不到锁而再次阻塞（“伤后又痛”/hurry-up-and-wait）；先解锁再 notify 通常更高效。关键约束是：**改谓词必须持锁，notify 可在解锁后**。
- **该 notify_all 时用了 notify_one**：广播型条件（一次事件应放行所有等待者）误用 notify_one 会导致部分等待者永久饿死。

### 提示

- 用本仓库的 `cs::logf(...)`（`concurrency_study/log.hpp`）打印带时间戳和线程 id 的日志，便于观察唤醒时序。
- 想稳定复现“丢失唤醒”，就刻意制造时序：让主线程 `notify` 跑在 worker 启动之前。
- 谓词写成捕获引用的 lambda 最方便：`[&]{ return ready; }`。

### 复盘问题

- 谓词版 wait 的“睡前检查”和“醒后检查”分别防住了哪个坑？去掉任意一次会怎样？
- 为什么说“通知不携带数据，只负责叫醒”？这对你设计共享状态有什么要求？
- `notify_one` 在什么场景下是正确且更优的？什么场景下必须 `notify_all`？
- 如果一个等待者醒来发现谓词不满足又继续睡，这是 bug 还是设计如此？

## 练习 C-2：用条件变量实现有界队列

> 代码目录：`exercises/C2_bounded_queue_condvar/`

### 目标

用一把 `std::mutex` + 两个 `std::condition_variable`（`not_full` / `not_empty`）实现一个**有界阻塞队列（bounded blocking queue）**：`push` 在队列满时阻塞等待，`pop` 在队列空时阻塞等待。多生产者多消费者（multiple-producer multiple-consumer，MPMC）下跑通，并正确选择 `notify_one`。进阶加上 `close()` 让消费者在队列耗尽后优雅退出。

### 前置理解

- 这是 C-1 的自然延伸：现在有**两个**条件需要等待——生产者等“队列非满”，消费者等“队列非空”。
- 你知道“有界”意味着一个固定容量 `cap`；不变式（invariant）是任何时刻 `size() <= cap`。
- 关键概念：
  - **为什么两个 CV**：生产者和消费者等待的是两个不同的谓词。若只用一个 CV，`notify_one` 可能把通知发给“等错谓词”的那一侧（例如本想唤醒一个消费者，却叫醒了一个生产者），造成无谓唤醒甚至活性问题。两个 CV 让“通知非满”和“通知非空”精确分流。
  - **为什么 notify_one**：一次 `push` 只新增 1 个可消费元素，只需放行一个消费者；一次 `pop` 只空出 1 个位置，只需放行一个生产者。用 `notify_all` 会引发惊群（thundering herd）——N 个被唤醒，N-1 个发现状态又被别人改没了，重新睡，纯属浪费。

### 必做任务

1. **实现 push / pop**（对应 `// TODO [必做 1]`）：
   - `push`：`not_full_.wait(lk, [&]{ return q_.size() < cap_ || closed_; })` → 入队 → `not_empty_.notify_one()`。
   - `pop`：`not_empty_.wait(lk, [&]{ return !q_.empty() || closed_; })` → 出队 → `not_full_.notify_one()`。
   - 谓词里就把 `closed_` 一并纳入（为进阶做准备），否则 `close()` 无法唤醒卡在满/空上的线程。

2. **MPMC 跑通**（对应 `// TODO [必做 2]`）：起 3 个生产者、2 个消费者，每个生产者投递 10 个元素，统计消费总数应等于 30。容量设小（如 4）以确保 push 真的会因满而阻塞、pop 真的会因空而阻塞，逼出阻塞路径。

### 进阶任务

- **close() 优雅退出**（对应 `// TODO [进阶 1]`）：实现 `close()`——置 `closed_ = true`，然后对**两个** CV 都 `notify_all`（关闭是广播型事件）。语义为：不再接受新元素，但已入队的元素仍可被取走（drain），队列排空后 `pop` 返回 `std::nullopt`，消费者据此跳出循环退出。`push` 在已关闭时返回 `false`。
- 给 `pop` 加超时版本 `pop_for(duration)`，返回 `std::optional`；区分“取到了”“超时了”“队列关了”。
- 思考无界队列与有界队列的差异：无界队列的 `push` 永不阻塞，那它还需要 `not_full` 这个 CV 吗？

### 验收点

- 你的队列在容量很小时仍能让 MPMC 正确跑通，消费总数 == 生产总数。
- 你能解释为什么用两个 CV、为什么 push/pop 各自选 `notify_one`。
- 你的 `close()` 能让所有消费者在排空后优雅退出，没有死锁、没有漏取。
- 你能说清 `pop` 返回 `nullopt` 的唯一含义是“已关闭且已排空”。

### 观察点

- 容量调小，你会在日志里看到生产者被“满”挡住、消费者被“空”挡住的交替节奏。
- `close()` 必须 `notify_all` 而非 `notify_one`：关闭要唤醒**所有**等待者去重新检查谓词，漏掉任何一个都会让它永久卡住。
- 谓词里 `|| closed_` 这一项是“关闭能穿透阻塞”的关键——它把“关闭”变成了一个能让 wait 返回的合法条件。

### 常见坑

- **只用一个 CV**：在 MPMC 下可能把唤醒发错对象，导致偶发卡顿或活性问题。
- **close() 用 notify_one**：只唤醒一个等待者，其余永久阻塞。
- **谓词漏掉 closed_**：`close()` 后，仍卡在“满/空”上的线程收不到能让谓词成立的条件，永远醒不来。
- **关闭后丢数据**：`close()` 语义应允许 drain（取完已入队元素），而不是立刻丢弃；`pop` 要先看队列是否还有货，再判断是否该返回 nullopt。
- **在持锁时做重活**：入队/出队要快进快出，不要在持锁区间里做耗时计算或 I/O。

### 提示

- 用 `std::queue<T>` 作底层容器，`std::optional<T>` 作 `pop` 返回类型表达“可能没有”。
- 谓词统一写成捕获 `this` 或引用的 lambda：`[&]{ return q_.size() < cap_ || closed_; }`。
- 先不实现 `close()`，用固定总数让主线程 `join` 完生产者后再触发关闭，跑通后再加超时版本。

### 复盘问题

- 为什么是两个条件变量而不是一个？把它合并成一个会带来什么具体问题？
- `push` 里为什么是 `not_empty_.notify_one()` 而不是 `not_full_`？方向搞反会怎样？
- `close()` 为什么必须 `notify_all`？它和 C-1 里“广播型”条件是同一个道理吗？
- 如果改成无界队列，哪个 CV 和哪段等待逻辑可以删掉？

## 练习 C-3：可中断的条件等待

> 代码目录：`exercises/C3_interruptible_wait/`

### 目标

用 `std::condition_variable_any` + `std::stop_token` 实现**可中断的等待（interruptible wait，C++20）**：worker 用 `cv.wait(lk, stoken, pred)` 阻塞，主线程 `request_stop()` 即可把它唤醒并让它优雅退出。然后把这套“stop_token 取消”与 C-2 里“关闭队列标志”两种唤醒退出方式正面对照。

### 前置理解

- 你在模块 A 见过 `std::stop_token` / `std::stop_source` / `std::jthread`（C++20 协作式取消）。这里把它接到条件变量上。
- **关键事实（务必记牢）**：
  - `std::condition_variable`（配 `std::mutex`，C++11）**没有** `stop_token` 重载。
  - 带 `stop_token` 的可中断 `wait` 是 `std::condition_variable_any` 的能力，且该重载是 **C++20 新增**。`condition_variable_any` 能配任意满足 `BasicLockable` 的锁，本题用 `std::mutex` + `std::unique_lock` 即可。
- 关键概念：
  - `cv.wait(lk, stoken, pred)` 的**行为意图**是：进入睡眠前检查 `pred()` 与 `stop_requested()`；睡眠中若被 `request_stop()` 唤醒（靠内部注册的 `stop_callback` 自动 notify）或被正常 notify，则醒来重新检查；如此循环直到 `pred()` 为真或 stop 被请求。返回时给出 `pred()` 的值：`true` 表示谓词满足（有数据），`false` 表示因 stop 被请求而醒来。
  - ⚠ 注意它**不能**简单写成 `while (!stoken.stop_requested() && !pred()) wait(lk);`——裸 `wait(lk)` 不响应 `stop_token`，线程一旦睡下，`request_stop()` 无法把它唤醒，会永久阻塞。可中断的关键正是那个内部 `stop_callback`（见下条）。
  - `request_stop()` 会通过内部注册的 `stop_callback` **自动 notify**，把卡在 wait 上的线程唤醒——你不需要再手动 `notify`。这正是它比“手动维护一个关闭标志 + 手动 notify_all”优雅的地方。

### 必做任务

1. **可中断等待**（对应 `// TODO [必做 1]`）：实现一个“信箱（mailbox）”，消费者用 `cv.wait(lk, stoken, [&]{ return slot_.has_value(); })` 等待信箱非空。用 `std::jthread` 起 worker（它自动把 `stop_token` 作为首参传入，析构时自动 `request_stop` + `join`）。主线程先正常投递两条消息（观察“正常唤醒”路径），再在 worker 空等时 `request_stop()`（观察“取消唤醒”路径）。worker 的 `take` 在收到 stop 时返回 `std::nullopt`，据此跳出循环、优雅退出。

### 进阶任务

- **两种退出方式对照**（对应 `// TODO [进阶 1]`）：用 C-2 风格复刻一个最小可关闭队列 `ClosableQueue`（普通 `condition_variable` + `closed_` 标志 + `notify_all`），与上面的 stop_token 版并列运行。在复盘笔记里写清两者取舍：
  - **方式 A（close 标志）**：退出原因与“业务状态/数据流结束”耦合，谓词里塞 `closed_`；适合“数据真的没有了”这种语义。
  - **方式 B（stop_token）**：退出原因独立于业务谓词，由上层统一发起取消；`jthread` 析构即自动触发，且同一个 `stop_source` 能跨多个等待点、多个原语复用。
- 让一个 worker 同时受“业务关闭”和“stop_token 取消”两路影响，谓词写成 `[&]{ return !q.empty() || closed_; }` 配合可中断 wait，观察两条退出路径如何并存。
- 思考：如果用的是 `std::condition_variable`（非 `_any`）却想支持取消，你只能退回方式 A（标志 + notify_all）——这就是为什么可中断 wait 要选 `condition_variable_any`。

### 验收点

- 你能让 worker 在 `request_stop()` 后被**自动唤醒**并优雅退出，无需手动 notify。
- 你能解释 `cv.wait(lk, stoken, pred)` 的返回值含义（true=谓词满足，false=被取消）。
- 你能讲清为什么可中断 wait 用的是 `condition_variable_any` 而不是 `condition_variable`，且这是 C++20 能力。
- 你能对比“close 标志”与“stop_token 取消”两种退出方式各自的适用场景。

### 观察点

- `request_stop()` → 内部 stop_callback → 自动 notify → wait 返回。整条链路你不用写 notify，标准库替你接好了。
- `jthread` 的析构语义（自动 request_stop + join）与“可中断等待”是天作之合：作用域一退出，等待中的 worker 自动收到取消并退出。
- 方式 A 把退出原因编码进“业务谓词”，方式 B 把退出原因放进“正交的取消通道”——两者不是谁取代谁，而是语义不同。

### 常见坑

- **用错原语**：在 `std::condition_variable`（非 `_any`）上找 `stop_token` 重载——它没有。
- **以为 request_stop 需要配合手动 notify**：可中断 wait 已经通过 stop_callback 自动唤醒，重复手动 notify 多余（但无害）。
- **取消后还去读“数据”**：可中断 wait 返回 `false` 时谓词并不满足（信箱仍空），此时必须走取消分支，不能假设有数据。
- **谓词与取消混淆**：把“被取消”当成一种“业务数据”处理，会让调用侧逻辑变拧巴；取消是独立通道。

### 提示

- 优先用 `std::jthread`：它自动给可调用对象传 `stop_token`，析构自动取消并 join，省去手动管理 `stop_source`。
- `cv.wait(lk, stoken, pred)` 的 `lk` 仍是 `std::unique_lock<std::mutex>`；`condition_variable_any` 不挑锁，但本题用 mutex 足够。
- 想让“取消唤醒”发生在可观察的时刻，就在 worker 进入空等待后再显式 `request_stop()`（而不是只靠 jthread 析构）。

### 复盘问题

- `cv.wait(lk, stoken, pred)` 内部是如何在“没有手动 notify”的情况下被 `request_stop()` 唤醒的？
- 为什么带 stop_token 的 wait 只在 `condition_variable_any` 上提供？`condition_variable` 的限制是什么？
- “close 标志”和“stop_token 取消”能否共存于同一个等待点？它们在谓词里如何并列？
- 如果你要给 C-2 的有界队列加“可被上层统一取消”的能力，你会把它改成 `condition_variable_any` + stop_token，还是保留 `closed_` 标志？为什么？

## 做完模块 C 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- 条件变量解决的是“线程等待某个条件成立”的问题，替代忙等和轮询；它只负责“叫醒”，数据由你保护的共享状态承载。
- `wait` 必须配谓词。`wait(lk, pred)` 等价于 `while (!pred()) wait(lk);`，靠“睡前检查”防丢失唤醒、靠“醒后检查”防虚假唤醒。
- 改谓词必须持锁；notify 可在解锁后发出。`notify_one` 放行一个等待者，`notify_all` 广播给全部——广播型条件（如“关闭”）必须 notify_all。
- 有界阻塞队列用一把 mutex + 两个 CV（not_full / not_empty），push/pop 各自 `notify_one`，因为一次状态变化只放行一个对侧等待者。
- `std::condition_variable_any` + `std::stop_token` 提供 C++20 的可中断等待：`request_stop()` 自动唤醒等待者；它与“在谓词里塞关闭标志”是两种正交的退出语义，各有适用场景。
