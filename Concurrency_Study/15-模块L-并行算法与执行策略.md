# 15 模块 L：并行算法与执行策略

## 模块目标

模块 J/K 让你在**单核内部**榨性能（缓存友好、SIMD 向量化）；本模块把你带到**多核之间**——但不是回去手搓线程池，而是用 C++17 起标准库给 STL 算法加的**执行策略（execution policy）**：给 `std::transform` / `std::for_each` / `std::sort` / `std::reduce` 多传一个 `std::execution::par`，标准库就替你把工作切块、分发到线程并行、再合并。一行之差，串行变并行。

本模块带你过三件事：①给常见算法**加执行策略**并验证并行结果与串行一致（练习 L-1）；②并行**归约（reduce）与扫描（scan）**，以及它们背后“为什么必须满足结合律”的硬约束（练习 L-2）；③用**基准（benchmark）**实测“何时并行才真正加速”，亲眼看到「小数据并行更慢」（练习 L-3）。

贯穿全模块的一句话是：**并行算法很好用，但不是免费午餐**。它把“怎么并行”交给标准库，却把“**该不该并行**”留给你——这正是本模块要教会你判断的。

> 工具链前提（务必先记）：**MSVC（本仓库 VS2026）的并行算法内置完整支持，无需链接任何额外库**。而 GCC/libstdc++ 历史上把并行后端委托给 Intel TBB，必须 `-ltbb` 才能真正并行（否则静默退化为串行）。本仓库 CMake 已用 `TbbSetup` 守卫非 MSVC 平台，你在 MSVC 上零依赖即可跑。

## 模块完成标准

做完本模块，你至少要能稳定说清楚（can-do）：

- 你能说出 `<execution>` 里四种执行策略的语义与版本：`seq`（C++17，串行不向量化）、`par`（C++17，多线程并行）、`par_unseq`（C++17，多线程并行 + 向量化）、`unseq`（**C++20**，单线程但向量化）。
- 你能把任意一个串行算法（`for_each`/`transform`/`sort`）通过“多传一个第一实参”升级为并行，并验证结果与串行**一致**。
- 你能说清 `par_unseq` / `unseq` 的**交错执行（interleaving）约束**：元素函数体内**禁止加锁、禁止分配内存、禁止相邻元素调用相互依赖**，否则未定义行为；而 `par` 不向量化、约束较松（单个调用完整，但仍不能有数据竞争）。
- 你能解释**为什么并行归约要求结合律（associativity）**（常还需交换律），并由此说清 `std::reduce` 与 `std::accumulate` 的区别。
- 你能记住**浮点求和的非确定性**：浮点加法不满足结合律，并行 `reduce` 的分组顺序变化会让结果产生微小差异，所以浮点对照串行**必须用容差**。
- 你能用 `std::transform_reduce` 做点积、用 `inclusive_scan` / `exclusive_scan` 做前缀和，并说清两个 scan 的区别。
- 你能用基准实测说清**何时并行才真正加速**（数据量、每元素工作量、内存带宽瓶颈、并行开销），并复现「小数据并行更慢」。
- 你能说出 **MSVC 内置 vs GCC 需 TBB** 的工具链差异。

## 练习 L-1：并行算法与执行策略

> 代码目录：`exercises/L1_par_algorithms/`

### 目标

把串行的 `std::for_each` / `std::transform` / `std::sort` 加上执行策略 `std::execution::par` 升级为并行，验证并行结果与串行**完全一致**，并做计时对比。讲清四种执行策略的语义与约束（重点：`par_unseq` 下为什么不能加锁）。

### 前置理解

- **执行策略（execution policy）**在头文件 `<execution>`，作为算法的**第一个实参**传入。四种标准策略：
  - `std::execution::seq`（C++17）：**串行**执行，且**不向量化**。等价于不带策略的老重载（但更明确）。
  - `std::execution::par`（C++17）：**多线程并行**。标准库把区间切块、分发到线程池，每块内部仍是普通（标量）执行。不同元素可能落在不同线程上。
  - `std::execution::par_unseq`（C++17）：**多线程并行 + 允许向量化（SIMD）**。除了跨线程并行，还允许在单个线程内把相邻元素的调用**交错（interleave）/ 向量化**。
  - `std::execution::unseq`（**C++20**）：**单线程，但允许向量化**。不开多线程，只在本线程内向量化交错。适合“数据量不大、想吃 SIMD 但不想付线程开销”的场景。
- **交错执行（interleaving）约束 —— 本练习最关键的一条**：在 `par_unseq` / `unseq` 下，元素函数体内**禁止**：
  - **加锁 / 任何同步原语**（mutex、atomic 的阻塞等待等）——因为同一线程上多个元素的调用可能交错执行，一个调用拿了锁还没放、另一个调用又来拿同一把锁 → **自死锁**；
  - **分配 / 释放内存**（`new`/`delete`、可能加锁的容器操作）——分配器内部常加锁，同样会被交错破坏；
  - **相邻元素调用之间相互依赖**的任何操作。
  
  违反即**未定义行为（UB）**。而 `par`（不带 unseq）**不向量化**，单个元素的调用是“从头跑到尾”的完整调用，因此**可以加锁/分配**（但当然仍不能有跨元素的数据竞争）。一句话：**要在元素函数里用锁/分配，最多用到 `par`，绝不能上 `par_unseq`/`unseq`。**
- **结果一致性**：`transform` 是逐元素的确定性映射、`sort` 的有序结果唯一——所以它们的并行结果与串行**逐元素完全相等**，可用 `==` 严格校验（这点与 L-2 的浮点归约不同）。
- **工具链差异**：MSVC 并行算法**内置、无需链接**；GCC/libstdc++ 把并行后端委托 Intel TBB，需 `-ltbb`，否则**静默退化为串行**（编译能过、跑起来不并行）。

### 必做任务

1. **并行 `transform`**（对应 `// TODO [必做 1]`）：把串行 `std::transform(seq, ...)` 改成 `std::execution::par` 版本，对大数组（百万级）做一个较重的逐元素映射，验证 `out_seq == out_par`（逐元素相等），并打印 seq/par 耗时与加速比。
2. **并行 `sort`**（对应 `// TODO [必做 2]`）：把 `std::sort(seq, ...)` 改成 `std::execution::par`，对大数组排序，验证 `v_seq == v_par`（排序结果唯一），并计时对比。
3. （已给出）**并行 `for_each` 就地修改**：每元素只改自己那一格、彼此不依赖 → 无数据竞争、无需加锁，验证结果一致。

### 进阶任务

- **试 `par_unseq`**：把映射函数确认为纯函数（无锁、无分配）后，换成 `par_unseq`，对比 `par`，看是否再快一点（取决于映射能否向量化）。
- **故意违规演示（思想实验，别真跑 UB）**：想清楚“若在 `par_unseq` 的元素函数里加一把 mutex 会怎样”——同线程交错调用导致自死锁。理解为什么这是 UB 而非偶发 bug。
- **`unseq`（C++20）单线程向量化**：对中等规模数据用 `unseq`，对比 `seq`，体会“不开线程、只吃 SIMD”的收益与边界。
- **空/极小区间**：传一个 0 或几个元素的区间给 `par`，观察并行版本是否反而更慢（线程开销，呼应 L-3）。

### 验收点

- 并行 `transform` / `sort` / `for_each` 结果与串行**逐元素一致**（`==` 通过）。
- 程序打印出 seq vs par 的耗时与加速比（大数组上 par 通常更快）。
- 你能口述四种策略的语义与版本号，并解释 `par_unseq`/`unseq` 为何**禁止加锁/分配**、`par` 为何可以。
- 你能说出 MSVC 内置 vs GCC 需 `-ltbb` 的差异。

### 观察点

- 加执行策略对调用方代码的改动**极小**（只多一个第一实参），但语义从串行变并行——这是并行算法最大的卖点。
- `transform`/`sort` 的并行结果与串行**完全相同**（确定性）；这与 L-2 浮点 `reduce` 的“可能微变”形成对照。
- 大数组上 `par` 明显快于 `seq`；但小数组未必（留到 L-3 系统验证）。

### 常见坑

- **在 `par_unseq`/`unseq` 的元素函数里加锁或分配内存** → UB（最常见的自死锁）。要用锁/分配，最多用 `par`。
- **以为 `par` 自动消除数据竞争**：`par` 只是“可能多线程跑”，若你的元素函数写了同一个共享变量，照样是数据竞争。这种“多个元素往一个累加器写”的需求应改用 `std::reduce`（见 L-2），而不是手动加锁。
- **GCC 上忘了 `-ltbb`**：编译通过但**没真并行**（静默串行），还以为“并行没用”。MSVC 无此坑。
- **Debug 构建测性能**：并行算法在 Debug/未优化下往往更慢，必须 Release 看趋势。
- **小数组也无脑上 `par`**：线程开销可能让它更慢（见 L-3）。

### 提示

- 执行策略实参就是 `std::execution::seq / par / par_unseq / unseq`，记得 `#include <execution>`。
- 让逐元素映射“有点分量”（几次三角/开方），才容易看出并行收益；纯赋值太轻，会被内存带宽卡住。
- 校验一致性：`transform`/`sort` 用 `==` 直接比两个 vector。
- 用本仓库 `cs::logf(...)`（`concurrency_study/log.hpp`）打印耗时与一致性结论。

### 复盘问题

- `seq` / `par` / `par_unseq` / `unseq` 各自的语义与引入版本是什么？
- `par_unseq` / `unseq` 为什么禁止在元素函数里加锁或分配内存？`par` 为什么可以？
- 给算法加执行策略，调用方代码要改多少？
- 为什么 `transform`/`sort` 的并行结果能用 `==` 严格校验，而浮点 `reduce` 不能？

## 练习 L-2：并行归约与扫描

> 代码目录：`exercises/L2_parallel_reduce_scan/`

### 目标

掌握并行**归约（reduction）**——`std::reduce`（求和/聚合）、`std::transform_reduce`（map+reduce，做点积/范数）——与并行**扫描（scan）/前缀和（prefix sum）**——`std::inclusive_scan` / `std::exclusive_scan`。并行求和、点积、前缀和，结果对照串行（整型精确相等、浮点用容差）。讲清为何 `reduce` 要求结合律、与 `accumulate` 的区别。

### 前置理解

- **`std::reduce`（`<numeric>`，C++17）**：并行求和/聚合。实现把区间**切块、各块各算、再两两合并**，因此**不保证求值顺序、也不保证分组（括号化）方式**。这换来了可并行性，但代价是：**二元运算必须满足结合律（associativity）**，常常**还要求交换律（commutativity）**——否则不同的分组/顺序会给出不同结果。
  - 默认运算是 `+`、默认 `init` 你要显式给（建议给定类型明确的 init，如 `0LL`，避免类型收窄/溢出）。
- **为什么必须结合律（核心直觉）**：串行 `accumulate` 算的是 `((a0+a1)+a2)+a3`（固定从左到右）；并行 `reduce` 可能算成 `(a0+a1)+(a2+a3)`（两块分别算再合并）。只有当 `+` 满足结合律，这两种括号化结果才相等。若并行实现还会打乱块的合并顺序，则**额外要求交换律**。
- **`std::reduce` vs `std::accumulate`**：
  - `accumulate`：严格**从左到右**顺序累加，顺序**确定**，但**天然串行**（不接受执行策略）。
  - `reduce`：不保证顺序/分组，**可并行**；要求运算结合（+交换）。
  - 一句话：要**确定的求值顺序** → `accumulate`（串行）；要**可并行** → `reduce`（运算须结合）。
- **`std::transform_reduce`（C++17）**：先对每个（或每对）元素做 `transform`，再 `reduce`，一趟完成、可并行。做**点积**（`Σ a[i]*b[i]`）、**范数**最顺手：双区间版默认“先乘后加”。
- **`std::inclusive_scan` / `std::exclusive_scan`（C++17）**：并行**前缀和**。
  - `inclusive_scan`：`out[i] = a[0] + ... + a[i]`（**含**当前元素）。
  - `exclusive_scan`：`out[i] = init + a[0] + ... + a[i-1]`（**不含**当前元素，`out[0] = init`）。
  - 二者相差恰好“是否含当前元素”：`inclusive[i] - exclusive[i] == a[i]`。并行扫描内部用两遍扫描/Blelloch 等算法，同样要求**结合律**。
- **浮点的非确定性（务必牢记）**：**浮点加法不满足结合律**（每步都有舍入误差，`(a+b)+c` 与 `a+(b+c)` 可能不同）。并行 `reduce`/`scan` 改变了分组顺序，于是浮点结果会**产生微小差异**——这是**正常现象，不是 bug**。因此浮点对照串行**必须用容差（tolerance）比较**，绝不能要求逐位 `==`。整型加法满足结合律，则可精确相等。

### 必做任务

1. **并行求和 `reduce`**（对应 `// TODO [必做 1]`）：用 `std::reduce(par, v.begin(), v.end(), 0LL)` 并行求 `1..N` 之和，与串行 `std::accumulate` 对照——整型加法满足结合律，二者**精确相等**且等于理论值 `N(N+1)/2`。
2. **并行点积 `transform_reduce`**（对应 `// TODO [必做 2]`）：用 `std::transform_reduce(par, a.begin(), a.end(), b.begin(), 0.0)` 做浮点点积，与串行 `std::inner_product` 对照——浮点用**容差**比较（差值 ≤ `1e-6 *(|期望|+1)` 即通过）。
3. （已给出）**并行前缀和 scan**：`inclusive_scan` 与串行 `partial_sum` 逐元素相等；`exclusive_scan` 满足 `inclusive[i] - exclusive[i] == a[i]`。

### 进阶任务

- **自定义结合运算**：用 `reduce` 求**最大值**（`std::max`，满足结合+交换）。再想一个**不满足结合律**的运算（如减法 `a-b`），论证为什么它不能用并行 `reduce`。
- **量化浮点漂移**：对同一组浮点数据，多次跑 `reduce(par)`，看结果是否每次都一模一样、与串行差多少（量级），体会“微小但真实”的漂移。
- **`transform_reduce` 算范数 / 方差**：用单区间版 `transform_reduce`（先平方再求和）算 L2 范数平方，体会 map+reduce 的通用性。
- **`exclusive_scan` 的用途**：用前缀和把“各段长度”变成“各段起始偏移”（经典的并行分桶/打包场景）。

### 验收点

- 整型 `reduce(par)` == `accumulate`（且等于理论值）。
- 浮点 `transform_reduce(par)` 与串行 `inner_product` 在**容差内**一致。
- `inclusive_scan(par)` 与 `partial_sum` 逐元素相等；`inclusive - exclusive == a[i]` 处处成立。
- 你能解释 `reduce` 为何要求结合律（+交换律）、与 `accumulate` 的区别、浮点为何必须用容差。

### 观察点

- 整型并行求和**精确**等于串行——结合律成立时并行无损。
- 浮点点积并行与串行有**微小**差异（最低有效位级别）——这是浮点非结合律的直接后果。
- `inclusive_scan` 的末元素 = 全体之和（= `reduce` 的结果），两者在数值上自洽。

### 常见坑

- **浮点 `reduce` 要求逐位相等**：必然“失败”，因为浮点不结合。必须用容差。
- **`init` 类型给错**：`std::reduce(v.begin(), v.end())`（不给 init）默认 init 是 `value_type{}`；对整型 `int` 大数组求和会**溢出**。给 `0LL`/合适类型的 init。
- **用非结合运算做 `reduce`**：如减法、浮点“强行要求确定顺序”的场景——结果不可预测。这种需求请退回 `accumulate`（串行、顺序确定）。
- **`exclusive_scan` 忘了给 `init`**：它**必须**有 init 实参（`out[0] = init`），签名与 `inclusive_scan` 不同。
- **把 `reduce` 当 `accumulate` 用来求“带顺序依赖的结果”**：`reduce` 不保证顺序，任何依赖“从左到右”的逻辑都会错。

### 提示

- `reduce`/`transform_reduce`/`inclusive_scan`/`exclusive_scan` 都在 `<numeric>`；执行策略在 `<execution>`。
- 整型对照用 `==`，浮点对照用 `|a-b| <= tol`（相对容差 `tol = eps*(|expected|+1)`）。
- 点积首选 `transform_reduce` 的双区间版（默认先乘后加），比手写循环更短更并行。
- 串行基线：求和用 `accumulate`、点积用 `inner_product`、前缀和用 `partial_sum`——都在 `<numeric>`。
- 用 `cs::logf(...)` 打印结果、差值、容差与“是否通过”。

## 练习 L-3：并行 vs 串行基准

> 代码目录：`exercises/L3_par_vs_seq_bench/`

### 目标

系统对比 `seq` vs `par` vs `par_unseq` 在**不同数据规模**下的耗时，打印一张「规模 × 策略 × 加速比」表，并用实测证据讲清**何时并行才真正加速**（数据量、每元素工作量、内存带宽瓶颈、并行开销），特别给出「小数据并行更慢」的实测证据。

### 前置理解

- **并行不是免费午餐**——它带来固定开销：**线程创建/唤醒、任务切块与分发、负载均衡、归约/合并的同步**。这些开销与数据规模基本无关（近似常数），但收益（并行计算省下的时间）随规模增长。于是存在一个**盈亏平衡点**：规模小于它，并行**更慢**。
- **何时并行才真加速**（三条判据）：
  1. **数据量足够大**：大到能摊薄上面的固定开销。小数组上并行几乎注定更慢（本练习专门复现）。
  2. **每元素工作量足够重（compute-bound）**：若每元素只是“加一下/拷一下”，瓶颈是**内存带宽（memory bandwidth）**而非 CPU——多核去抢同一条内存总线，再多核也喂不饱，并行收益有限甚至为负（这叫**memory-bound**）。只有每元素有实打实的算术（如本练习的多次三角/开方），多核才用得上。
  3. **能并行的结构**：元素间无顺序依赖（尴尬并行最理想）。
- **基准方法学（为什么这样测，否则数字不可信）**：
  - **多跑取最小值（min）**：最小值最接近“无被抢占/无系统抖动”的真实耗时，比平均值稳定（平均会被偶发抖动拉高）。
  - **预热（warm-up）**：跑正式计时前先空跑一次，让线程池就绪、页缓存（page cache）/TLB 预热，避免冷启动污染首次测量。
  - **防优化（`volatile` sink）**：把结果喂给一个 `volatile` 变量，否则“结果没人用”的整段计算会被编译器优化掉，测出 0ms 的假象。
  - **Release/优化下测**：Debug 下并行算法常更慢，趋势失真。
- **结果高度依赖机器**：核数、缓存大小、内存带宽都会改变盈亏平衡点。所以重点看**趋势（加速比随规模如何变化）**，而非某个绝对数字。

### 必做任务

1. **补全 par / par_unseq 测量**（对应 `// TODO [必做 1]`）：在 `run_scale` 里用 `std::execution::par` 与 `par_unseq` 各跑一遍 `transform(heavy)`，用 `bench_min_ms` 取最小耗时，与 `seq` 比得加速比。（`heavy()` 是纯函数，满足 `par_unseq` 的交错约束。）
2. **规模扫描出表**（已给出框架）：从 `1e3` 扫到 `8e6`，每行打印 seq/par/par_unseq 耗时与加速比；在**小规模行**复现加速比 < 1（并行更慢）。

### 进阶任务

- **加一组 memory-bound 对照**：把 `heavy()` 换成极轻的“乘个常数”，重跑规模扫描，观察即使大数据并行加速也很有限——这就是**内存带宽瓶颈**的实测证据。对比 compute-bound 那组。
- **找盈亏平衡点**：在小规模附近细化扫描（如 1e3、2e3、5e3、1e4……），找到 `par` 的加速比**首次 > 1** 的规模，记下你机器的“并行起步线”。
- **`par` vs `par_unseq` 谁更快**：在能向量化的轻计算上 `par_unseq` 可能更快；在不易向量化的重计算上二者接近。解释为什么。
- **核数关系**：查本机逻辑核数（`std::thread::hardware_concurrency()`），看大规模下 `par` 的加速比是否接近核数（理想线性）以及为何通常达不到。

### 验收点

- 输出表里：**小规模行**的 `par`/`par_unseq` 加速比通常 **< 1**（并行更慢），**大规模行**通常 **> 1**（并行明显加速）。
- 你能指着表说清「小数据并行更慢」的根因：固定开销 > 这点计算量的收益。
- 你能说清并行真加速的条件：**数据量足够大 + 每元素工作量足够重（compute-bound）**，并避开内存带宽瓶颈。
- 你能说出基准方法学的三件事：取最小值、预热、防优化，以及为何必须 Release 下测。

### 观察点

- 小规模（如 N=1000）：`seq` 往往最快，`par` 因线程开销反而最慢——加速比 < 1。
- 大规模（如 N=8e6，compute-bound）：`par` 显著快于 `seq`，加速比随核数上升但通常 < 核数（开销 + 非完美负载均衡）。
- 若把计算换成极轻操作，大规模下加速比也上不去——撞上内存带宽天花板。

### 常见坑

- **Debug 下测性能**：并行更慢、趋势失真。必须 Release/优化。
- **不预热**：首次测量被线程池冷启动/页错误污染，数字虚高。
- **不防优化**：结果没人用 → 编译器删光计算 → 测出 0ms 假象。`volatile` sink 兜住。
- **只测一个规模就下结论**：并行的好坏强依赖规模，必须扫一条曲线看趋势。
- **拿平均值当指标**：偶发系统抖动会污染平均；用最小值更稳。
- **无视内存带宽**：以为“加 par 就该线性加速”，却在 memory-bound 任务上失望——根因是带宽不是核数。

## 做完模块 L 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- **执行策略（`<execution>`）**：`seq`（C++17，串行不向量化）、`par`（C++17，多线程并行）、`par_unseq`（C++17，多线程 + 向量化）、`unseq`（**C++20**，单线程但向量化）。给算法“多传一个第一实参”即升级为并行。
- **`par_unseq` / `unseq` 的交错约束**：元素函数体内**禁止加锁、禁止分配内存、禁止相邻调用相互依赖**（否则 UB，典型是自死锁）；要用锁/分配最多上 `par`。
- **工具链差异**：**MSVC 并行算法内置、零依赖**；GCC/libstdc++ 历史上需 **`-ltbb`** 才真并行（否则静默退化串行）。
- **并行归约要结合律**：`reduce` 切块再合并 → 括号化/顺序不保证 → 二元运算须满足**结合律**（常还需**交换律**）。`reduce`（可并行、顺序不定）vs `accumulate`（串行、从左到右确定）。
- **浮点非确定性**：浮点加法**不结合**，并行 `reduce`/`scan` 结果会**微变** → 浮点对照串行**必须用容差**，整型才可精确相等。
- **并行 map+reduce 与 scan**：`transform_reduce` 做点积/范数；`inclusive_scan`（含当前元素）/`exclusive_scan`（不含，首元素 = init）做前缀和。
- **何时并行才真加速（本模块灵魂）**：**数据量足够大 + 每元素工作量足够重（compute-bound）**，且避开**内存带宽瓶颈**；小数据 / 轻计算下并行因**固定开销**反而**更慢**。默认串行，profiling 证明值得再上 `par`。这一判断力，配合模块 K 的 SIMD（单核向量化）与后续模块 M 的工作窃取/结构化并发，构成你“先单核压榨、再多核扩展、且只在划算时扩展”的完整数据并行工具箱。
