# 11 模块 I：安全内存回收

## 模块目标

模块 G 教你写出了第一批无锁（lock-free）数据结构，但留下一个刻意没填的坑：Treiber 栈 `pop` 摘下节点后**故意泄漏、永不 `delete`**。这个模块就是来填这个坑的——它要解决无锁编程里最难、也最本质的一个问题：**安全内存回收（safe memory reclamation，SMR）**，即“一个节点什么时候才能被真正释放而不引发 use-after-free”。

核心难题（务必刻进脑子）：在无锁结构里，线程 A 读到一个指向节点 N 的指针、但**还没解引用**；与此同时线程 B 把 N 从结构里摘下并 `delete`。等 A 回来解引用时，N 已是悬垂指针——这就是 **use-after-free**。它和模块 G-2 的 ABA 是同一枚硬币的两面：都源于“节点被释放/复用”，而朴素无锁代码无从知道“此刻还有没有人正握着这个指针”。

本模块给你三把解决回收难题的钥匙，难度与开销各不相同：

1. **`atomic<shared_ptr>`（引用计数）**——最简单：让 `shared_ptr` 的引用计数替你记账，读者手里有副本，对象就不释放。安全好写，但多数实现**不是 lock-free**，有同步代价。
2. **hazard pointer（风险指针）**——读者精确登记“我正在用这个指针”，回收方扫描后只释放“没人保护”的节点。读侧开销小、可扩展，但要维护 per-thread 的保护槽。
3. **RCU（read-copy-update，读-复制-更新）**——读者侧几乎零开销（只标记进出读临界区），写者发布新版本、retire 旧版本，等宽限期（grace period，老读者全离开）后回收。读多写少场景的王者。

> ⚠️ **标准现状**：`std::hazard_pointer`（`<hazard_pointer>`，提案 `P2530R3`）与 `std::rcu_*`（`<rcu>`，提案 `P2545R4`）都进入了 **C++26**，但**主流编译器（含 MSVC VS2026）尚未实现**。因此本套练习 I-2/I-3 使用本仓库自带的 **`cs::` 教学版**（`concurrency_study/hazard_pointer.hpp`、`concurrency_study/rcu.hpp`），API 命名刻意贴近 `std::` 的 C++26 版本。教学版是简化实现、**非标准、非生产级**，仅用于建立直觉；生产请用 folly 的 Hazptr/RCU 或等待编译器实现。`cs::` ↔ `std::` 的差异映射见本文末的对照表。

## 模块完成标准

做完本模块，你至少要能稳定说清楚（can-do）：

- 你能用一句话说清无锁结构的**回收难题**：A 读到指向 N 的指针、未解引用时 B `delete` 了 N → A 解引用悬垂指针（use-after-free），并指出它就是 G 模块 Treiber 栈“pop 故意泄漏”的真正病根。
- 你能用 `std::atomic<std::shared_ptr<T>>` 写出可并发安全读写的共享单元，解释引用计数如何撑住读者手里的旧对象、根除 use-after-free，并说出它的代价（多数实现非 lock-free）。
- 你能讲清 hazard pointer 的**保护-回收协议**：`protect`（登记+重读校验）→ 安全访问 → `retire`（延迟回收）→ 回收方扫描“无人保护”的节点才 `delete`，并能用它给 Treiber 栈的 `pop` 做到安全回收。
- 你能讲清 RCU 的思想：读者侧几乎零开销（只标记读临界区）、写者 publish 新版本 + retire 旧版本 + 等宽限期回收，并说出它和 hazard pointer 的取舍（读侧开销 vs 回收延迟）。
- 你能比较三种方案的开销与适用场景，并说出 hazard pointer / RCU 为什么也能顺带解决 ABA（从“安全回收”而非“值比较”的角度）。

> 本模块建立在模块 F（内存序）与模块 G（无锁结构、CAS、ABA）之上。如果你对 release/acquire 配对、Treiber 栈、ABA 还不熟，请先回头补齐。

## 练习 I-1：atomic&lt;shared_ptr&gt;

> 代码目录：`exercises/I1_atomic_shared_ptr/`

### 目标

用 C++20 的 `std::atomic<std::shared_ptr<T>>`（`<memory>`）实现一个可并发安全读写的共享配置单元，把回收难题交给**引用计数（reference counting）**解决；多线程压测验证全程不崩、无 use-after-free，并讨论它的性能代价。

### 前置理解

- **回收难题（reclamation problem）**：无锁结构中，线程 A 读到指向节点 N 的指针、尚未解引用时，线程 B 把 N 摘下并 `delete N` → A 解引用悬垂指针，即 **use-after-free**。这正是模块 G Treiber 栈“pop 故意泄漏”的真正病根：泄漏只是“不释放就不会悬垂”的鸵鸟策略，本模块要给出真解。
- **引用计数解法**：`std::shared_ptr` 用引用计数管理生命周期——只要还有一个 `shared_ptr` 指向对象，对象就不析构。读者 `load` 出一份 `shared_ptr` **副本**（计数 +1），从此哪怕写者 `store` 了新值、丢掉了对旧对象的最后一个外部引用，旧对象也被读者手里这份副本撑着，不会被提前释放；读者读完、副本析构、计数归零，才真正 `delete`。use-after-free 被根除。
- **`std::atomic<std::shared_ptr<T>>`（C++20，`<memory>`）**：它把“拷贝控制块指针 + 调整引用计数”这组**复合操作**做成原子的（否则裸 `shared_ptr` 的并发读写是数据竞争）。
- **关键代价**：`atomic<shared_ptr>` 在**多数标准库实现里并非 lock-free**——`is_lock_free()` 通常返回 `false`，内部往往用一把（或分片的）锁来原子地操作“指针 + 计数”这两样东西。所以它**安全、易写，但有同步开销**，热路径上的吞吐显著不如 hazard pointer / RCU。这一点本题会让你亲手打印 `is_lock_free()` 来确认。

### 必做任务

1. **实现 read / write**（对应 `// TODO [必做 1]`）：
   - `read()`：`cell_.load(std::memory_order_acquire)` 返回当前 `shared_ptr` 副本；
   - `write(new_cfg)`：`cell_.store(std::move(new_cfg), std::memory_order_release)` 发布新值；
   - release/acquire 配对保证读者看到的 `Config` 内容是写者完整写好的。
2. **并发读写压测**（验收）：N 个读者反复 `read()` 出副本并解引用、校验不变量 `payload == version*2`；M 个写者反复用新版本替换。验收：**全程不崩、无 use-after-free**，一致读取次数严格等于总读取次数。
3. **打印并讨论 `is_lock_free()`**：确认多数实现为 `false`，并能解释这一代价从何而来。

### 进阶任务

- **吞吐对比**：把读者数量逐步加大，观察 `atomic<shared_ptr>` 的吞吐随竞争增加而下降（内部锁争用）。把这条曲线记在心里，和 I-2/I-3 的无锁/低开销读侧对照。
- **`compare_exchange` 版本**：用 `atomic<shared_ptr>::compare_exchange_strong` 实现一个“基于旧版本做 CAS 更新”的写者（read-modify-write），体会它如何把无锁结构的“摘节点”安全地表达出来。
- **思考边界**：`atomic<shared_ptr>` 解决了回收，但每次 `load` 都要原子地动引用计数（典型实现还要加锁）。为什么这在高频读场景下不划算？这正是 hazard pointer / RCU 要改进的地方。

### 验收点

- 并发读写不崩、不撕裂：一致读取次数严格等于总读取次数。
- 你能说清引用计数如何撑住读者手里的旧对象、根除 use-after-free。
- 你能解释为什么 `atomic<shared_ptr>` 多数实现非 lock-free，以及它相对 hazard pointer / RCU 的取舍。

### 观察点

- `load` 返回的是**独立副本**——它增加的引用计数就是“旧对象不被提前释放”的保证。
- `is_lock_free()` 多半为 `false`：这台机器上 `atomic<shared_ptr>` 内部加了锁。
- 读者越多、写者越频繁，内部锁争用越明显——安全是有价的。

### 常见坑

- **以为 `atomic<shared_ptr>` 是 lock-free**：多数实现不是。需要极致读吞吐时它不是最优解。
- **把 `load` 出来的裸 `.get()` 指针存起来跨临界区用**：那等于绕过了引用计数的保护，又回到 use-after-free。要持有的是 `shared_ptr` **副本**本身。
- **对裸 `shared_ptr` 做并发读写**：是数据竞争（UB）。并发场景必须用 `std::atomic<std::shared_ptr<T>>`（或已废弃的自由函数 `std::atomic_load/store(shared_ptr*)`）。

### 提示

- 校验不变量（如 `payload == version*2`）是检测“撕裂/悬垂”的廉价手段：一旦读到不自洽的对象，立刻可观测。
- 写者每次 `make_shared<Config>()` 造全新对象再 `store`，不要原地改老对象（那会让正在读它的读者看到撕裂值）。
- 用本仓库 `cs::logf(...)`（`concurrency_study/log.hpp`）打印结果。

### 复盘问题

- 回收难题用一句话怎么说？它和 G 模块“pop 故意泄漏”是什么关系？
- 引用计数是如何保证“读者手里的旧对象不被提前释放”的？
- `atomic<shared_ptr>` 为什么多数实现不是 lock-free？这对高频读场景意味着什么？
- 如果换成 hazard pointer / RCU，读侧开销会怎么变？回收时机又会怎么变？

- cppreference [`std::shared_ptr`](https://en.cppreference.com/w/cpp/memory/shared_ptr)

## 练习 I-2：hazard pointer 安全回收

> 代码目录：`exercises/I2_hazard_pointer/`

### 目标

给模块 G 的 Treiber 无锁栈的 `pop` 加上**安全的节点回收**，用风险指针（hazard pointer）彻底消除“pop 后 `delete` 节点”导致的 use-after-free——做到既无锁、又能真正释放内存（不再像 G-1 那样故意泄漏）。多线程 push/pop 混合压测，验证无崩溃、收支平衡。

本题使用本仓库自带的**教学版** `cs::hazard_pointer`（`concurrency_study/hazard_pointer.hpp`）。

### 前置理解

- **风险指针（hazard pointer）的核心思想**：读者在解引用一个指针前，先把它**公开登记**到一个全局可见的“hazard 槽”里，等于宣告“我正在用这个指针，谁都别释放它”。回收方在真正 `delete` 一个退休对象前，**扫描所有 hazard 槽**：只要有人登记了它，就跳过不删，等下次再试；没人登记才安全释放。
- **保护-回收协议（三步）**：
  1. **protect（读者）**：`hp.protect(head_)` 把 `head_` 的当前值写进 hazard 槽，并**重读校验**——若登记期间 `head_` 没被换走，保护成立；否则用新值重试。这个“登记 → 重读”是协议的精髓：它堵死了“登记前指针已被换走并回收”的时间窗。
  2. **safe access（读者）**：保护成立后，被保护的对象在本 `hazard_pointer` 释放前**保证不被回收**，于是可以放心读它的 `next`、`data`，CAS 把它摘下。
  3. **retire（写者/摘除者）**：摘下的旧节点**不直接 `delete`**，而是 `retire()` 登记到回收系统。回收系统扫描 hazard 槽，只 `delete` 没人保护的退休节点。
- **为什么这修好了 G-1**：G-1 的 `pop` 不敢 `delete`（怕别的线程正握着同一节点），只能泄漏。hazard pointer 让“别的线程正握着”这件事**变得可观测**（它会登记到 hazard 槽），于是回收方能安全地区分“能删”与“还不能删”，泄漏被消除。
- **它也解决 ABA**：若受害者在读节点前先把它登记为 hazard，捣乱者就无法真正复用/释放该地址，ABA 从源头消失（对照 G-2）。
- **标准对照**：C++26 在 `std` 命名空间 `<hazard_pointer>` 标准化了等价设施（提案 `P2530R3`：`std::hazard_pointer`、`std::hazard_pointer_obj_base<T,D>`、`std::make_hazard_pointer`、`protect`/`try_protect`/`reset_protection`）。MSVC VS2026 尚未实现，故本题用 `cs::` 教学版。差异映射见文末对照表。

### 必做任务

1. **protect 读出的 head + retire 旧节点**（对应 `// TODO [必做 1]`）：
   - `cs::hazard_pointer hp = cs::make_hazard_pointer();` 申请保护槽；
   - 循环：`old = hp.protect(head_);` 保护当前 head（空则返回 false）；读 `old->next`；CAS `head_: old -> next`，失败则重读重 protect；
   - 成功摘下后取走 `old->data`，调用 `old->retire()` **延迟回收**（不直接 `delete`）。
2. **多线程压测**（验收）：N 个线程交替 push/pop 混合压测，全程**无崩溃**（无 use-after-free）、**收支平衡**（总 push == 总 pop，不丢不重）。

### 进阶任务

- **量化回收效果**：在教学头 `scan_and_reclaim` 里加计数，统计“成功回收”与“仍被保护而跳过”的节点数，直观看到延迟回收的节奏。
- **对照 G-1 的泄漏**：把本题的 `retire()` 临时改成“直接 `delete old`”，在高并发下大概率触发崩溃/ASan 报错（use-after-free）——这反向证明了 protect/retire 协议的必要性。（验证完务必改回 `retire()`。）
- **保护槽耗尽**：把 `kMaxHazardPointers` 调到很小（如 2），加大线程数，观察 `make_hazard_pointer()` 抛 `bad_alloc`——理解 hazard pointer 的“每线程保护数”是一种需要规划的资源。
- **try_protect**：把 `protect` 的内部循环用 `try_protect` 手动展开重写一遍，体会“登记-校验-重试”被拆开后的控制流。

### 验收点

- 多线程 push/pop 压测无崩溃、收支平衡（不丢不重）。
- 你能逐步说出 `protect head -> 安全读 next/data -> CAS 摘下 -> retire 旧节点` 的协议，并解释 protect 里“重读校验”堵住了哪个时间窗。
- 你能解释 `retire` 为何不立即 `delete`（可能仍有读者保护着它），以及它相对 G-1“泄漏”的根本改进。
- 你能说出 hazard pointer 也能解决 ABA，且着力点在“安全回收”而非“值比较”。

### 观察点

- protect 返回后，被保护的节点在 `hp` 释放前**不会被回收**——这是“安全读 next/data”的全部依据。
- `retire` 之后的节点不会马上消失：它要等到“没有任何 hazard 槽登记它”那一刻。回收是**延迟**且**批量**的。
- 多个线程可能同时保护同一个 `old`（它们在某线程 CAS 摘下前都读到了它）——这正是不能直接 `delete` 的原因。

### 常见坑

- **先解引用再 protect**：顺序反了就失去保护意义。必须**先 protect + 重读校验成立，再解引用**。
- **protect 后忘了校验/重试**：只 `store` 到 hazard 槽却不重读 `head_`，无法排除“登记前已被换走”的窗口，保护是假的。本题用 `hp.protect()` 已内置该循环。
- **retire 后还访问该对象**：`retire` 意味着交出所有权，之后再碰 `*old` 是 use-after-free（即便回收被延迟）。
- **直接 `delete` 摘下的节点**：等于退回 G-1 之前的危险做法，必崩。
- **hazard 槽泄漏**：`hazard_pointer` 是 RAII，离开作用域自动释放槽；别把它的生命周期拉得过长，否则白白占用稀缺槽位。

### 提示

- `cs::hazard_pointer` 只移动不拷贝（独占一个全局槽），用完即弃（RAII）。
- `protect` 内部已实现“登记 → 重读校验 → 重试”循环，直接用它的返回值即可。
- 压测时让每线程的操作数足够大（数万），并让 push/pop 交替，更容易撞出“多个线程同时握着同一节点”的危险时序。
- 用本仓库 `cs::logf(...)` 打印阶段性结果。

### 复盘问题

- hazard pointer 的保护-回收协议三步分别是什么？protect 里的“重读校验”堵住了哪个时间窗？
- 为什么摘下的节点必须 `retire` 而不能直接 `delete`？回收发生在什么时刻？
- hazard pointer 是怎么顺带解决 ABA 的？它和 G-2 的版本号方案在“着力点”上有何不同？

## 练习 I-3：RCU 读-拷贝-更新

> 代码目录：`exercises/I3_rcu/`

### 目标

用 RCU（read-copy-update，读-复制-更新）实现一个**读多写少**的共享配置：读者侧几乎零开销（不加锁，只标记“我在读临界区”），写者侧 publish 新版本 + retire 旧版本，等宽限期（grace period，所有当前读者都离开）后才安全回收旧版本。

本题使用本仓库自带的**教学版** `cs::rcu_*`（`concurrency_study/rcu.hpp`）。

### 前置理解

- **RCU 的灵魂——读侧几乎零开销**：读者进入“读临界区（read-side critical section）”不加锁、不参与任何会引发跨线程争用的写，只是**标记一下**“我现在在读”（本教学实现用 per-thread 计数 +1，离开时 -1）。在临界区内读到的指针，**保证在临界区结束前不会被回收**。所以无数读者可以同时高速读，彼此零干扰——这是 RCU 在读多写少场景碾压锁与 `atomic<shared_ptr>` 的根本原因。
- **写侧协议（read-COPY-update 的由来）**：
  1. **copy**：写者**复制**出一个全新的版本，在副本上改（绝不原地改正在被读的版本）；
  2. **publish**：用一次原子操作把全局指针换成新版本（release，与读者 acquire 配对），自此**新读者**都看到新版本；
  3. **retire**：把旧版本 `rcu_retire`（或 `obj.retire()`）登记延迟回收——**不能立即 `delete`**，因为可能还有**老读者**正握着它在自己的读临界区里用；
  4. **grace period**：`rcu_synchronize` / `rcu_barrier` 阻塞等待，直到**所有“拿到旧版本的老读者”都离开了读临界区**（宽限期结束）——此后旧版本不可能再被任何人触碰，安全回收。
- **宽限期（grace period）**：从“publish 新版本”到“所有当时在读的老读者都离开过读临界区”之间的这段时间。RCU 不追踪“谁在用哪个具体指针”（那是 hazard pointer 干的），它只确保“老读者全走光了”——这是更**粗粒度**但读侧更便宜的安全保证。
- **与 hazard pointer（I-2）对比**：
  - hazard pointer：读侧要往 hazard 槽 `store`（一次原子写），精确登记“我在用这个指针”；回收快（无人保护即可删）。
  - RCU：读侧更便宜（只动 per-thread 计数，无共享争用）；但回收要**等最慢的读者离开宽限期**，延迟更不可控。
  - 选型：读极多、写很少、能容忍回收延迟 → RCU；读多但要尽快回收、保护对象数可控 → hazard pointer。
- **标准对照**：C++26 在 `std` 命名空间 `<rcu>` 标准化了等价设施（提案 `P2545R4`：`std::rcu_obj_base<T,D>`、`std::rcu_domain`、`std::rcu_default_domain()`、`std::rcu_synchronize()`、`std::rcu_barrier()`、`std::rcu_retire()`）。MSVC VS2026 尚未实现，故本题用 `cs::` 教学版。差异映射见文末对照表。

### 必做任务

1. **rcu 读侧**（对应 `// TODO [必做 1]` 读侧）：用 `cs::rcu_default_domain().lock()/unlock()` 包住 `g_config.load()` + 解引用，并校验不变量 `checksum == a + b`；临界区内读到的指针受保护，不会被提前回收。
2. **写者 publish + retire**（对应 `// TODO [必做 1]` 写侧）：复制新版本 → `g_config.exchange(fresh)` publish → 旧版本 `retire()`（或 `cs::rcu_retire(old)`）→ 周期性 `cs::rcu_barrier()` 等宽限期后回收。
3. **验收**：读者全程读到自洽版本（不变量 `checksum == a + b` 始终成立），无 use-after-free。

### 进阶任务

- **RCU 保护的链表**：把单个配置指针换成一条 RCU 保护的单向链表，写者“插入/删除”节点时复制受影响部分、publish、retire 旧节点，读者无锁遍历。体会 RCU 在“读多写少的容器”上的威力。
- **宽限期可视化**：在 `rcu_synchronize` 前后打时间戳，制造一个“故意慢的读者”（在临界区里 sleep），观察写者的回收被这个慢读者拖住——直观理解“回收延迟取决于最慢的读者”。
- **对比 I-1**：把同一个读多写少负载分别用 `atomic<shared_ptr>`（I-1）和 RCU（本题）跑，比较读侧吞吐。理解 RCU 为什么在读多写少时更快（读侧不动共享引用计数、不加锁）。
- **`rcu_synchronize` vs `rcu_barrier`**：说清两者区别——`synchronize` 只等一个宽限期（不一定回收），`barrier` 等到“已 retire 的对象都被回收”。本题为简化把回收放在 `barrier` 里统一做。

### 验收点

- 读者无锁读、写者 publish + retire，全程无崩溃、不变量始终成立（无 use-after-free / 无撕裂）。
- 你能说清读临界区为何能保证“区内读到的指针不被回收”。
- 你能说清写者为何不能直接 `delete` 旧版本、必须 retire 等宽限期。
- 你能对比 RCU 与 hazard pointer 的读侧开销与回收延迟取舍，并说出各自适用场景。

### 观察点

- 读侧 `lock/unlock` 不涉及任何跨线程争用的共享写——这是“读侧几乎零开销”的来源。
- 写者 `retire` 的旧版本不会立刻消失：它要等宽限期结束（老读者全离开）。一个慢读者会拖慢回收。
- 新读者在 publish 之后进入，看到的必然是新版本，因此宽限期只需等“拿到旧版本的老读者”，不必等新读者。

### 常见坑

- **在读临界区外解引用**：`lock` 之前或 `unlock` 之后再解引用从全局读到的指针，就失去 RCU 保护，可能 use-after-free。解引用必须在 `lock`/`unlock` 之间。
- **原地修改正在被读的版本**：RCU 是“**复制**-更新”，必须造新版本再 publish；原地改会让正在读的读者看到撕裂值。
- **publish 后直接 `delete` 旧版本**：必崩。必须 `retire` + 等宽限期。
- **读临界区里做阻塞/长耗时操作**：会拖长宽限期、拖慢所有回收。RCU 读临界区应短小。
- **把 RCU 当“免费午餐”**：读侧便宜的代价是回收延迟与写侧复杂度（要复制、要等宽限期）。写多的场景 RCU 不划算。

### 提示

- 读临界区用 `cs::rcu_domain::lock()/unlock()`（或本仓库提供的 RAII 包装 `cs::rcu_reader`，对应标准里 `std::scoped_lock lk(std::rcu_default_domain())`）。
- publish 用 `g_config.exchange(fresh, acq_rel)` 一步换出旧指针，顺手拿到 `old` 去 retire。
- 维持一个易校验的不变量（如 `checksum == a + b`）来检测撕裂/悬垂。
- 程序退出前 `rcu_barrier()` 清场，确保所有退休对象的析构都跑完。

### 复盘问题

- RCU 读侧为什么“几乎零开销”？它和加锁、和 `atomic<shared_ptr>` 的读侧分别差在哪？

- RCU 和 hazard pointer 在“追踪粒度”上有何本质区别？这如何导致它们在读侧开销与回收延迟上的取舍？

## 附：`cs::` 教学 API ↔ `std::` C++26 标准 API 差异映射表

> ⚠️ **再次强调**：`cs::hazard_pointer` / `cs::rcu_*` 是本套练习的**简化教学实现**（位于 `exercises/include/concurrency_study/`），**不是标准、不是生产级**。它们存在只是因为 C++26 的 `std::hazard_pointer`（`P2530R3`）和 `std::rcu_*`（`P2545R4`）虽已入标准，但 MSVC VS2026 等主流编译器**尚未实现**。下表帮你把教学 API 一一对应到将来的标准 API，便于迁移。

### Hazard Pointer（`<hazard_pointer>`，C++26）

| 概念 / 操作 | 本套 `cs::`（教学版，`concurrency_study/hazard_pointer.hpp`） | C++26 标准 `std::`（`<hazard_pointer>`，`P2530R3`） | 差异 / 教学简化说明 |
|---|---|---|---|
| 命名空间 / 头 | `cs::`，`"concurrency_study/hazard_pointer.hpp"` | `std::`，`<hazard_pointer>` | 标准头/命名空间不同 |
| 句柄类型 | `cs::hazard_pointer` | `std::hazard_pointer` | 同名，行为类似 |
| 工厂 | `cs::make_hazard_pointer()` | `std::make_hazard_pointer()` | 同名；失败均抛 `std::bad_alloc` |
| 被保护对象基类 | `cs::hazard_pointer_obj_base<T, D>` | `std::hazard_pointer_obj_base<T, D>` | 同名 |
| 退休对象 | `obj.retire()`（教学版要求 `D` 无状态） | `obj.retire(D = D{})` | 标准支持有状态删除器；教学版忽略传入实例、用默认构造的 `D` |
| 保护并读 | `hp.protect(const std::atomic<T*>&)` | `hp.protect(const std::atomic<T*>&)` | 同名同义（登记 + 重读校验） |
| 试保护 | `hp.try_protect(T*&, const std::atomic<T*>&)` | `hp.try_protect(T*&, const std::atomic<T*>&)` | 同名同义 |
| 设/清保护 | `hp.reset_protection(p)` / `hp.reset_protection(nullptr)` | `hp.reset_protection(p)` / `reset_protection(nullptr)` | 同名同义 |
| 空句柄判定 | `hp.empty()` | `hp.empty()` | 同名 |
| 槽数量 | 编译期固定 `cs::kMaxHazardPointers`，耗尽抛 `bad_alloc` | 实现可动态扩容 | **教学简化**：固定上限 |
| 回收策略 | per-thread retire 列表 + 线性扫描，攒够阈值才扫 | 实现自定（通常更优、分代/批量） | **教学简化**：朴素 O(槽×退休数) 扫描 |

### RCU（`<rcu>`，C++26）

| 概念 / 操作 | 本套 `cs::`（教学版，`concurrency_study/rcu.hpp`） | C++26 标准 `std::`（`<rcu>`，`P2545R4`） | 差异 / 教学简化说明 |
|---|---|---|---|
| 命名空间 / 头 | `cs::`，`"concurrency_study/rcu.hpp"` | `std::`，`<rcu>` | 标准头/命名空间不同 |
| 域类型 | `cs::rcu_domain` | `std::rcu_domain` | 同名 |
| 默认域 | `cs::rcu_default_domain()` | `std::rcu_default_domain()` | 同名 |
| 读临界区 | `dom.lock()` / `dom.unlock()`（满足 BasicLockable） | `dom.lock()` / `dom.unlock()` | 同名；均可配 `std::scoped_lock` |
| 读临界区 RAII | `cs::rcu_reader`（**非标准糖**） | 用 `std::scoped_lock lk(std::rcu_default_domain())` | 教学加糖；标准用 `scoped_lock` |
| 被回收对象基类 | `cs::rcu_obj_base<T, D>` | `std::rcu_obj_base<T, D>` | 同名 |
| 侵入式退休 | `obj.retire()`（要求 `D` 无状态） | `obj.retire(D = D{})` | 标准支持有状态删除器；教学版用默认构造 `D` |
| 非侵入式退休 | `cs::rcu_retire<T,D>(p)` | `std::rcu_retire<T,D>(p, d)` | 同名；教学版 `D` 须无状态 |
| 等宽限期 | `cs::rcu_synchronize()`（朴素轮询自旋） | `std::rcu_synchronize()` | **教学简化**：自旋等读者计数归零，非工业级 epoch 推进 |
| 等回收完成 | `cs::rcu_barrier()`（等宽限期 + 实际删除 pending） | `std::rcu_barrier()` | 语义对齐；教学版回收集中在此发生 |
| 多域语义 | 仅一个全局默认域 | 支持多个独立域 | **教学简化**：不实现多域全部语义 |

> 迁移要点：当 MSVC 等实现了 C++26 的 `<hazard_pointer>`/`<rcu>` 后，绝大多数代码只需把 `cs::` 改成 `std::`、把头从 `"concurrency_study/..."` 改成 `<hazard_pointer>`/`<rcu>`、把 `cs::rcu_reader` 换成 `std::scoped_lock` 即可。语义已刻意对齐。

## 做完模块 I 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- **回收难题（use-after-free）**：无锁结构里，A 读到指向 N 的指针、未解引用时 B `delete` 了 N → A 解引用悬垂指针。这就是 G 模块 Treiber 栈“pop 故意泄漏”的真正病根，也和 ABA 同源（都怪“节点被释放/复用”）。
- **`atomic<shared_ptr>`（引用计数）**：读者 `load` 出副本撑住旧对象，根除 use-after-free；安全好写，但多数实现**非 lock-free**（内部加锁），高频读吞吐受限。
- **hazard pointer（风险指针）**：读者 `protect`（登记 + 重读校验）→ 安全访问 → `retire`（延迟回收）→ 回收方扫描“无人保护”的节点才 `delete`；读侧开销小、可扩展，要管 per-thread 保护槽；也能从“安全回收”角度解决 ABA。
- **RCU（读-复制-更新）**：读者侧几乎零开销（只标记读临界区），写者复制新版本 + publish + retire 旧版本 + 等宽限期回收；读多写少的王者，代价是回收延迟取决于最慢的读者、写侧更复杂。
- **三者取舍**：`atomic<shared_ptr>`（最简单、有锁代价）→ hazard pointer（读侧便宜、回收快、管保护槽）→ RCU（读侧最便宜、回收延迟大、适合读极多写极少）。
- **标准现状**：`std::hazard_pointer`（`P2530R3`）/`std::rcu_*`（`P2545R4`）已入 **C++26**，但 MSVC VS2026 等尚未实现；本套用 `cs::` 教学版建立直觉，迁移到标准只需换命名空间/头（见对照表）。
