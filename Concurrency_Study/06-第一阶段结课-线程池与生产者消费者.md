# 06 第一阶段结课 · 线程池与生产者-消费者

## 这份文件怎么用

前面阶段一的 12 道题（模块 A/B/C/D 各 3 道）把并发原语拆开单独练了：

- **模块 A**：`std::jthread`（C++20）的生命周期、`std::stop_token`（C++20）协作式取消、线程内异常处理；
- **模块 B**：`std::mutex` 家族、`std::scoped_lock` 防死锁、`std::call_once` 一次性初始化；
- **模块 C**：`std::condition_variable` 谓词等待、有界阻塞队列（练习 C-2）、`condition_variable_any` + `stop_token` 可中断等待（练习 C-3）；
- **模块 D**：`std::promise` / `std::future`、`std::async` 启动策略、`std::packaged_task` 打包任务。

这份文件负责把上面所有原语**重新拼成一个完整项目**——一个固定大小线程池（fixed-size thread pool）。它几乎用到了阶段一的每一个原语，是检验你是否真正掌握"组合"而非"会用单个 API"的试金石。

建议顺序：先把线程池的数据流画一张图（提交端 → 任务队列 → worker 端 → future 回传），标出**哪把锁保护什么状态**、**哪个条件变量等待什么谓词**、**停机信号如何传播到每个 worker**，再动手写代码。

> 直接复用的前置题：练习 C-2（有界阻塞队列）、练习 C-3（`stop_token` 可中断等待）、练习 D-3（`packaged_task`）。本项目本质上是把这三题缝合成一个可复用组件。

## 项目目标

实现一个**固定大小线程池** `ThreadPool`：构造时启动 N 个常驻 worker 线程，对外暴露一个 `submit(callable, args...)` 接口，把任意可调用对象打包成任务投递进去，由空闲 worker 取出执行，并通过 `std::future<R>` 把返回值（或异常）回传给提交方。析构时**优雅停机**：先停止接收新任务，把在途任务处理完，再让所有 worker 退出。

这个项目的重点不是"高性能调度器"，而是让你同时管理好三件容易出错的事：

- **共享可变状态的保护**：任务队列被多个提交者和多个 worker 同时读写，必须用一把 `mutex` 保护，且持锁范围要最小。
- **线程间的阻塞唤醒**：worker 在队列空时必须睡眠（而非忙等），靠 `condition_variable` 在新任务到来或停机请求时被唤醒。
- **生命周期与停机**：N 个 worker 的启动、停止、join 必须有明确的拥有者；停机信号要能唤醒正卡在 `wait` 上的 worker。

## 固定题面

对外接口固定为下面这组（签名是验收的一部分，请勿改动语义）：

```cpp
class ThreadPool {
public:
    explicit ThreadPool(std::size_t worker_count, std::size_t queue_capacity);
    ~ThreadPool();                          // 优雅停机：排空在途任务后退出

    ThreadPool(const ThreadPool&)            = delete;  // 不可拷贝
    ThreadPool& operator=(const ThreadPool&) = delete;

    // 提交任意可调用对象 + 参数，返回 future 承载其结果。
    template <class F, class... A>
    auto submit(F&& f, A&&... args)
        -> std::future<std::invoke_result_t<F, A...>>;
};
```

内部结构固定为：

1. 一个由 `std::mutex` + `std::condition_variable` 保护的**任务队列**，元素类型是"可调用的无参 void 任务"。首选 `std::move_only_function<void()>`（C++23）；若用 `std::function<void()>`（C++11），注意 **`std::packaged_task` 是 move-only、不可拷贝，不能直接塞进 `std::function`**——需把 `packaged_task` 用 `std::shared_ptr` 持有再包进可拷贝的 lambda，或自定义 move-only 的类型擦除包装。建议队列**有界**（`queue_capacity`），用以练习背压（back-pressure）。
2. `submit` 内部用 `std::packaged_task` 把 `f(args...)` 打包，取出其 `future` 后再把 task 包成无参 `void()` 入队。
3. N 个 worker 用 `std::jthread` 持有，每个 worker 在循环里取任务执行；停机用 `std::stop_token` + 排空策略驱动。

## 必须包含的设计约束

1. **必须综合阶段一的全部核心原语**：`std::jthread`（worker 持有者）、`std::mutex`（保护队列）、`std::condition_variable`（队列空/满的等待）、`std::packaged_task`（打包任务）、`std::future`（回传结果）、`std::stop_token`（优雅停机）。允许额外用 `std::call_once` 等，但上面六个是底线。
2. **任务队列的每一次访问都必须持锁**。持锁期间**绝不执行任务本体**——取出任务后先解锁，再调用，否则一个慢任务会阻塞整个池的提交与调度。
3. **优雅停机（graceful shutdown）语义**：析构时先标记"不再接收新任务"，唤醒所有 worker；已入队的在途任务必须被执行完，**不允许丢弃**；待队列排空后 worker 才退出。析构必须 `join` 所有 worker（`jthread` 析构自动 join，但停机信号要先发）。
4. **异常必须经 future 传播**，不允许逃逸到 worker 线程顶层。`packaged_task` 天然满足：被包裹的可调用对象抛出时，异常被存进共享状态，由 `future::get()` 重新抛出。worker 调用 task 时**不要**自己 try-catch 吞掉。
5. **禁止忙等（busy-wait）**：worker 在队列空且未停机时必须真正睡眠在 `condition_variable` 上，不允许 `while(queue.empty()) {}` 轮询。
6. **禁止数据竞争**：所有跨线程共享的可变状态（队列、停机标志、计数器）要么受同一把锁保护，要么用 `std::atomic`。

## 推荐输入输出模型

为了把注意力留给线程池结构，建议测试驱动写得很小、可预测：

- worker 数量：取 `std::jthread::hardware_concurrency()` 或固定 4。
- 队列容量：固定一个小值（如 64），方便观察背压。
- 一批"计算型"任务：提交 N 个返回 `int` 的任务（如第 i 个返回 `i*i`），收集所有 `future`，求和后与解析公式比对验证。
- 一个"会抛异常"的任务：提交一个 `throw std::runtime_error(...)` 的任务，对其 `future.get()` 用 try-catch 接住，验证异常确实经 future 传播出来。

示例输出（用 `cs::logf` / `cs::println` 打印，带线程 id 与时间戳）：

```
==== Capstone1：固定大小线程池 ====
[main] 启动线程池：worker=4, capacity=64
[ +1ms | tid 234 ] [worker] 启动
... (各 worker 取任务执行)
[main] 提交 100 个平方任务，收集 future 求和。
[main] sum(i*i, i=0..99) 期望 328350，实际 328350 -- 一致 OK
[main] 提交一个会抛异常的任务，验证异常经 future 传播。
[main] future.get() 捕获到异常：boom from task -- OK
[main] 线程池析构：优雅停机（排空在途任务后退出）。
... (各 worker 检测到 stop 且队列排空，退出)
==== 演示结束。请对照"验收点/复盘问题"自检。 ====
```

## 必做任务

1. **画数据流图**：动手写代码前，画出"提交端 → 队列 → worker 端 → future 回传"四段，标注：哪把锁保护队列、哪个条件变量等待哪个谓词、`stop_token` 如何从析构传播到每个 worker 的 `wait`。
2. **定义任务类型与队列**：选定无参 `void()` 任务的承载类型（`std::move_only_function<void()>` 优先，因为 `packaged_task` 只能移动不能拷贝）。复用练习 C-2 的有界阻塞队列骨架，元素换成任务类型。
3. **实现 `submit`**：用 `std::packaged_task<R()>` 打包 `std::bind`/lambda 捕获后的 `f(args...)`；先取出 `future`，再把 task `std::move` 进一个 `void()` 包装入队；返回 `future`。注意 `packaged_task` 不可拷贝，捕获时要 `std::move`。
4. **实现 worker 循环**：每个 worker 在 `while` 循环里，用条件变量等待"队列非空 或 已停机"谓词；取出一个任务后**先解锁再执行**；执行完继续循环。停机且队列排空时退出循环。
5. **实现入队/出队的加锁与通知**：入队后 `notify_one` 唤醒一个 worker；若队列有界，满时提交方等待"非满"谓词（背压）。出队后若用了"非满"条件变量，记得通知提交方。
6. **实现优雅停机**：析构（或显式 `shutdown()`）时置停机标志并 `notify_all`，唤醒所有卡在 `wait` 上的 worker；worker 谓词里把停机标志纳入唤醒条件，但**只有在队列也排空后才退出**（即"先排空再退出"）。`jthread` 析构会自动 join，但停机标志/通知要在 join 发生前发出。
7. **写测试驱动（返回值路径）**：在 `main()` 提交一批返回 `int` 的任务，收集 `future`，`get()` 求和并与期望值比对，打印 `一致 OK` / `不一致 MISMATCH`。
8. **写测试驱动（异常路径）**：提交一个会抛异常的任务，对其 `future.get()` 用 try-catch 接住并打印异常信息，验证异常经 future 正确传播。

## 进阶任务

- **用 `stop_token` 取代自定义停机布尔**：让每个 worker 接收 `jthread` 传入的 `std::stop_token`，用 `std::condition_variable_any` 的可中断 `wait(lk, stoken, pred)`（C++20，练习 C-3 的技法）等待任务；`jthread` 析构自动 `request_stop` 即触发停机。对比"业务布尔标志"与"stop_token 通道"两种停机方式的取舍。
- **两种停机策略可选**：增加一个参数区分"排空后退出（drain）"与"立即退出、丢弃未执行任务（cancel）"。思考各自的适用场景。
- **背压策略**：把有界队列的"满则阻塞提交方"改为"满则返回 `false` / 抛 `std::runtime_error`"，对比阻塞式背压与拒绝式背压。
- **`submit` 支持成员函数与有状态可调用对象**：验证 `submit(&Obj::method, &obj, args...)` 与移动捕获的 lambda 都能正确打包。
- **统计与观测**：加入"已提交 / 已完成 / 峰值队列长度"的原子计数器，停机时打印一份小报告。
- **写一页小结**：如果把这个池接到真实工作负载（如并行下载、并行编译），哪些部分可直接复用，哪些需要换成工作窃取（work-stealing，见阶段三模块 M）。

## 验收点

- 你能在数据流图上指出：哪把锁保护队列、临界区的最小边界在哪、为什么"执行任务"必须在锁外。
- 提交 N 个返回值任务，`future` 求和结果与期望值**完全一致**，多次运行稳定可复现。
- 会抛异常的任务，其异常确实经 `future.get()` 重新抛出并被你接住，而**没有**让 worker 线程崩溃或异常逃逸到顶层。
- 析构时**没有任务被丢弃**（排空策略下）：你能证明所有已入队任务都执行了（如用计数器核对提交数 == 完成数）。
- worker 在空闲时是**睡眠**而非忙等（你能解释为什么 `wait` 配谓词不会丢唤醒、不会惊群）。
- 用 ThreadSanitizer（GCC/Clang `-fsanitize=thread`）跑一遍**无数据竞争报告**（MSVC 下可用逻辑审查替代）。
- 你能不看代码、口头描述整个线程池的并发拓扑与停机时序。

## 项目复盘问题

- `submit` 里为什么要"先取出 `future` 再把 `packaged_task` 移进队列"？如果顺序反了会怎样？
- worker 取出任务后为什么必须**先解锁再执行**？如果在持锁状态下执行任务会发生什么？
- 优雅停机的谓词为什么是"队列非空 **或** 已停机"，而退出条件却是"已停机 **且** 队列已排空"？这两个布尔表达式的差异决定了什么行为？
- 入队用 `notify_one` 还是 `notify_all`？停机用哪个？为什么？（回顾练习 C-2 的"惊群"讨论。）
- 用"业务布尔标志 + `condition_variable`"和用"`stop_token` + `condition_variable_any`"实现停机，各自的优劣是什么？什么场景下后者明显更好？
- `packaged_task` 为什么不可拷贝、只能移动？这对你选择任务队列元素类型（`std::function` vs `std::move_only_function`）有什么影响？
- 异常是如何从 worker 线程"穿越"回提交线程的？`future` 的共享状态在这中间承担了什么角色？
- 如果一个任务本身又向同一个池 `submit` 新任务（任务嵌套提交），会不会死锁？在什么条件下会？

### 完成后能说什么

做完这个结课项目，你应该能稳定说出：

- "我能用一把 `mutex` + 一个 `condition_variable` 实现线程安全的任务队列，并解释临界区为什么要最小化、任务为什么要在锁外执行。"
- "我能用 `std::packaged_task` 把任意可调用对象与其 `future` 解耦，让结果和异常都经共享状态回传。"
- "我能用 `std::jthread` + `std::stop_token` 实现优雅停机，让停机信号自动唤醒卡在 `wait` 上的 worker，并保证在途任务不被丢弃。"
- "我理解线程池不是魔法——它就是'生产者-消费者'模式的一个产品化封装：提交方是生产者，worker 是消费者，中间隔着一个受锁保护的有界队列。"
