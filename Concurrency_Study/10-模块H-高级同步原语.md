# 10 模块 H：高级同步原语

## 模块目标

模块 A–D 给了你线程、互斥锁（mutex）、条件变量（condition variable）、future 这套“经典”同步工具；模块 E–G 把原子（atomic）与无锁（lock-free）打通。但这中间还缺一层：C++20 在 `<latch>`、`<barrier>`、`<semaphore>` 里补齐了一组**高级同步原语**，外加给 `std::atomic` 加上了 `wait`/`notify`。它们既比“裸 mutex + condition_variable 手搓”更省事、更不易写错，又比无锁结构更易懂——是你日常并发编排（多阶段任务、限流、起跑线、轻量信号）的首选工具。

本模块带你过四件套：用 **`std::latch`** 做“一次性栅栏”（等 N 件事都完成 / 全部就绪后同时开跑）；用 **`std::barrier`** 做“可重用的多阶段汇合点”（多轮迭代的相位同步，每轮末由某线程跑一次 completion function 收尾）；用 **`std::counting_semaphore` / `std::binary_semaphore`** 做计数限流与线程间信号；用 **`std::atomic<T>::wait`/`notify`** 把忙等自旋换成真正的睡眠等待（平台上常以 futex 类原语实现）。

贯穿全模块的一条主线是：**“选对原语，比手搓更短、更对”**。这些工具大多能用 mutex + condition_variable 拼出来，但标准库的实现往往更高效、语义更清晰、更难写错——学会识别“这个场景该用哪一个”，就是本模块的核心收获。

## 模块完成标准

做完本模块，你至少要能稳定说清楚（can-do）：

- 你能区分 `std::latch`（一次性、计数到 0 后不可重用）与 `std::barrier`（可重用、维护“代/阶段”、带 completion function），并各自举出一个典型场景。
- 你能用 latch 实现“全部就绪后同时开跑”（起跑线模型），并说清 `count_down`/`wait`/`arrive_and_wait`/`try_wait` 各自做什么。
- 你能用 barrier 实现多轮迭代的相位同步，解释 completion function“在每阶段末由某一个线程执行恰好一次、然后才唤醒全部”的语义，以及 `arrive_and_drop` 的用途。
- 你能用 `std::counting_semaphore<K>` 实现资源池限流（同时最多 K 个），并说清它与 mutex 的本质区别：**信号量无所有权**（acquire 与 release 可由不同线程执行，计数可 > 1）。
- 你能用 `std::binary_semaphore` 做线程间一次性信号 / 唤醒，并知道它就是 `counting_semaphore<1>`。
- 你能用 `std::atomic<T>::wait/notify` 写出高效等待，说清它相对忙等自旋的优势（不烧 CPU、省功耗、平台多用 futex 实现），并牢记两条铁律：等待方在 `while` 谓词里复查（防伪唤醒）、通知方先改值再 notify。

> 本模块的内存序判断仍建立在模块 F 之上：latch/barrier/semaphore 的 `wait`/`acquire` 与 `count_down`/`release`/`store+notify` 之间也建立 happens-before。若对 release/acquire 配对不熟，请先回顾模块 F。

## 练习 H-1：latch 与 barrier

> 代码目录：`exercises/H1_latch_barrier/`

### 目标

对比 C++20 两个新栅栏原语：`std::latch`（闩，一次性向下计数栅栏）与 `std::barrier`（屏障，可重用的多阶段汇合点）。用 latch 实现“全部就绪后同时开跑”；用 barrier 实现多轮迭代的相位同步，并用 completion function（完成函数）在每轮末做收尾汇总。

### 前置理解

- **`std::latch`（`<latch>`，C++20）**：内部维护一个计数，初值在构造时给定。
  - `count_down(n = 1)`：把计数减 `n`（不阻塞）。
  - `wait()`：阻塞到计数归零。
  - `arrive_and_wait(n = 1)`：等价 `count_down(n)` 后 `wait()`。
  - `try_wait()`：非阻塞查询计数是否已为 0。
  - **一次性**：计数到 0 后**不可重用**（没有“重置回初值”的操作）。要重复使用请改 barrier。
- **`std::barrier`（`<barrier>`，C++20）**：可**重用**的同步点，维护“代 / 阶段（generation / phase）”概念。
  - 构造 `barrier(expected, completion)`：`expected` 是每阶段需要到齐的参与者数；`completion` 是**完成函数**。
  - `arrive_and_wait()`：本线程“到达 + 等待”（= `wait(arrive())`）。当本阶段最后一个参与者到达时，**先**由实现选定的**某一个线程**执行 completion function **恰好一次**，**再**唤醒本阶段所有等待线程，barrier 自动进入下一代。
  - `arrive()`：到达但不等待，返回 `arrival_token`，可稍后 `wait(token)`。
  - `arrive_and_drop()`：本线程到达本阶段后**永久退出**后续参与，之后每阶段的“到齐人数”自动减 1。用于“某 worker 提前完工但不想拖累其余线程继续多轮”。
  - completion function 要求：可无参调用、且 **`noexcept`**（不能抛异常）。
- **本质区别**：latch 是“等 N 件事都完成”的**一次性闸门**；barrier 是“反复汇合 N 个参与者、每轮跑一次收尾”的**循环节拍器**。

### 必做任务

1. **用 latch 实现“全部就绪后同时开跑”**（对应 `// TODO [必做 1]`）：起跑线模型。
   - 一个 `latch ready(N)`：每个 worker 完成准备后 `ready.count_down()` 报到；主线程 `ready.wait()` 阻塞到全部就绪。
   - 一个 `latch go(1)` 当发令枪：worker 准备完后 `go.wait()` 等枪；主线程见全部就绪后 `go.count_down()` 一次性放行——所有 worker 几乎同时被唤醒、同时起跑。

2. **用 barrier 做多轮相位同步 + completion 收尾**（对应 `// TODO [必做 2]`）：
   - `barrier sync_point(N, on_phase_done)`，N 个 worker 跑 R 轮。
   - 每轮：各 worker 算一块、把贡献累加到共享累加器，然后 `sync_point.arrive_and_wait()`。
   - completion function 在每轮末（全部到齐后、唤醒前）由某一个线程执行一次：打印本轮汇总、清零累加器，为下一轮做准备。barrier 自动重用，循环 R 轮。

### 进阶任务

- **观察 completion 的“某一个线程”语义**：在 completion 里打印执行它的线程 id，多跑几轮，你会看到不同轮可能由不同线程执行——标准只保证“某一个、恰好一次”，不保证是哪一个。
- **用 `arrive_and_drop()` 让某 worker 提前退场**：让 0 号 worker 在第 2 轮后 `arrive_and_drop()`，观察后续轮次到齐人数自动减 1、其余 worker 仍能正常多轮汇合。
- **用 latch 串多个阶段**：体会“latch 只能用一次”的痛——要 3 个阶段就得 3 个 latch；这正是 barrier 存在的理由。
- **拆开 `arrive()` 与 `wait(token)`**：先 `arrive()` 拿到 token、做点不依赖同步的本地收尾，再 `wait(token)`，体会“到达”与“等待”可以分离。

### 验收点

- latch 演示：所有 worker 在发令枪后几乎同时起跑（程序统计起跑数 == N）。
- barrier 演示：completion function **每轮恰好执行一次**，barrier 跨多轮**重用**成功；本轮汇总值正确、轮末被清零。
- 你能说清 latch（一次性）与 barrier（可重用 + completion）的本质区别与适用场景。
- 你能说出 completion function 为什么必须 `noexcept`、在什么时机、由谁执行。

### 观察点

- 发令枪 latch `go.count_down()` 一次，所有 `go.wait()` 的 worker 几乎同步醒来——这就是“同时开跑”。
- completion function 在“全部 arrive 之后、唤醒之前”单线程执行，因此它与 worker 的下一轮计算之间天然有 happens-before，访问共享累加器无需额外加锁。
- 不同轮的 completion 可能由不同线程执行（实现自由）。

### 常见坑

- **拿 latch 当 barrier 重复用**：latch 没有重置，第二次 `wait()` 立即返回（计数早是 0），达不到“再次汇合”的效果。多轮请用 barrier。
- **completion function 抛异常**：它要求 `noexcept`，抛异常会 `std::terminate`。把可能抛的逻辑挡在外面。
- **在 completion 里做重活/阻塞**：所有其他线程都在等它跑完才被唤醒，completion 里阻塞会卡住整轮。只放轻量收尾。
- **忘了发令枪、只用一个 ready latch**：worker `count_down` 后若不等枪就直接跑，就退化成“各跑各的”，没有“同时开跑”。
- **barrier 的 expected 数与实际参与线程数不一致**：少一个线程永远到不齐，全体死等；多一个线程会提前触发。`arrive_and_drop` 是**唯一**正规的减员方式。

### 提示

- latch 的两段式（`ready` 报到 + `go` 发令）是“同时开跑”的标准写法，记住它。
- completion function 用 lambda 时记得标 `noexcept`；捕获共享累加器按引用。
- 让各 worker 准备耗时**故意错开**（sleep 不同毫秒），更能看出“latch 把先后到达的线程拉齐到同一起跑线”。
- 用本仓库 `cs::logf(...)`（`concurrency_study/log.hpp`）打印带时间戳/线程 id 的日志，方便看汇合时刻。

### 复盘问题

- latch 和 barrier 最关键的一句话区别是什么？各自典型场景？
- barrier 的 completion function 在什么时机、由谁、执行几次？为什么它和 worker 的下一轮之间无需额外加锁？
- 为什么 completion function 必须 `noexcept`？里面能做阻塞操作吗？
- 如果要做 5 个阶段的相位同步，用 latch 要几个对象、用 barrier 要几个？这说明了什么？
- `arrive_and_drop()` 解决什么问题？不用它而直接让某线程不再 `arrive` 会怎样？

### 对应官方参考

- cppreference [`std::latch`](https://en.cppreference.com/w/cpp/thread/latch)
- cppreference [`std::barrier`](https://en.cppreference.com/w/cpp/thread/barrier)

## 练习 H-2：counting / binary semaphore

> 代码目录：`exercises/H2_semaphore/`

### 目标

掌握 C++20 信号量（semaphore，`<semaphore>`）：用 `std::counting_semaphore<K>`（计数信号量）做**限流**——任意时刻最多 K 个线程持有资源 / 进临界区；用 `std::binary_semaphore`（= `counting_semaphore<1>`，二值信号量）做线程间**一次性信号 / 唤醒**。并理解信号量与互斥锁的本质差异。

### 前置理解

- **`std::counting_semaphore<LeastMaxValue>`（`<semaphore>`，C++20）**：内部一个**非负计数**。
  - `acquire()`：计数 -1；若计数已为 0 则**阻塞**，直到别人 `release`。
  - `release(n = 1)`：计数 +`n`，并唤醒等待者。
  - `try_acquire()`：非阻塞尝试 -1，拿不到立即返回 `false`。
  - `try_acquire_for(d)` / `try_acquire_until(t)`：限时尝试，超时返回 `false`。
  - 模板参数 `LeastMaxValue` 是**计数上限**（实现保证至少能到这个值）；构造参数是**初始计数**。
- **`std::binary_semaphore`** = `std::counting_semaphore<1>`：计数只在 0/1 之间，做轻量信号 / 唤醒。
- **信号量 vs 互斥锁（关键直觉）**：
  - **mutex 有所有权（ownership）**：谁 `lock` 就得谁 `unlock`，且天生只有“1 份”（要么锁住要么没锁）。它的语义是“**互斥保护一段代码**”。
  - **semaphore 无所有权**：A 线程 `acquire`、B 线程 `release` 完全合法；计数可以 > 1。它的语义是“**对一种可计数资源的许可管理 / 跨线程发信号**”。
  - 一句话选择：**保护临界区** → mutex；**限制并发份数 / 跨线程发信号** → semaphore。

### 必做任务

1. **用 `counting_semaphore<K>` 实现资源池信号量（限流）**（对应 `// TODO [必做 1]`）：
   - `counting_semaphore<K> pool(K)`：初始 K 份资源。
   - N 个线程（N > K）：进资源区前 `pool.acquire()`（用尽则阻塞），用完 `pool.release()` 归还。
   - 用一个原子计数器实时统计“当前在区内的线程数”，并维护峰值；断言峰值**从不超过 K**（程序打印峰值与限额比对）。

2. **用 `binary_semaphore` 做一次性 ping-pong 通知**（对应 `// TODO [必做 2]`）：
   - `binary_semaphore signal_ready(0)`：初值 0 表示“信号未就绪”。
   - ping 线程准备好数据后 `signal_ready.release()` 通知；pong 线程一直 `signal_ready.acquire()` 等信号，收到后读数据。
   - 再用第二个 `binary_semaphore signal_ack(0)` 让 pong 收到后**回告** ping，演示双向交棒——突出“release 与 acquire 由不同线程执行”这一无所有权特性。

### 进阶任务

- **`try_acquire_for` 做带超时的限流**：把资源区改成“限时等位”——拿不到许可就等最多 T 毫秒，超时则放弃本次（打印“限流拒绝”）。体会非阻塞 / 限时获取的用途。
- **semaphore 重做 H-1 的起跑线**：用 `counting_semaphore` 的 `release(N)` 一次性放行 N 个等待线程，对比 latch 发令枪写法，体会“同一个编排能用不同原语表达”。
- **semaphore 实现一个有界缓冲的“空位 / 满位”计数**（呼应模块 C 的条件变量版本）：用两个信号量分别计“空槽数”和“满槽数”，对比 condition_variable 写法的繁简。
- **故意用 mutex 模拟信号量**会遇到什么困难？想清楚“mutex 的所有权”为什么让它**做不了**“A acquire、B release”这种跨线程交棒。

### 验收点

- counting_semaphore 演示中**峰值同时占用 ≤ K**（无越界），且 N > K 时确有线程被挡在 `acquire` 上等待。
- binary_semaphore 演示中 ping/pong 一次性握手 + 回告成功。
- 你能说清信号量**无所有权**：`acquire` 与 `release` 可由不同线程执行、计数可 > 1。
- 你能在“保护临界区”与“限制并发份数 / 发信号”之间正确选用 mutex 还是 semaphore。

### 观察点

- 当 N > K 时，多出来的线程会卡在 `acquire`，直到有线程 `release` 才轮到——这就是限流。
- 峰值占用恰好顶到 K（而非超过），说明信号量的计数语义把并发数严格压在许可数内。
- ping 的 `release` 与 pong 的 `acquire`（以及反向的 ack）由不同线程执行却完全正常——这是 mutex 做不到的。

### 常见坑

- **把信号量当 mutex 来“保护代码”**：能用，但丢了信号量的长处、也容易误用（比如忘了 `release` 配对）。互斥首选 mutex（还能配 RAII 的 `lock_guard`）。
- **`acquire`/`release` 不配对**：少 release 会让计数只减不增，最终所有人卡死；多 release 会让并发数突破预期上限。
- **模板上限 K 写小了**：`counting_semaphore<2>` 却 `release` 到 3，超过 `LeastMaxValue` 是未定义行为。模板参数要 ≥ 你会用到的最大计数。
- **二值信号量初值搞反**：做“等信号”时初值应为 0（先 acquire 会阻塞），写成 1 会让等待方直接穿过、错过同步。
- **以为 semaphore 能解决 ABA / 数据竞争**：它只是计数许可，临界区内部的数据竞争仍要靠正确的同步（mutex / atomic）处理。

### 提示

- 资源池限流的标准骨架：`acquire()` → 用资源 → `release()`；可用 RAII 包一层确保异常路径也 release（进阶可自己写个 scope guard）。
- 验证“不越界”最简单：进区 `fetch_add` 抬高占用计数并 CAS 维护峰值，出区 `fetch_sub`；最后比对峰值 ≤ K。
- ping-pong 用两个 `binary_semaphore`（一个去、一个回）最清晰。
- 元素 / 线程数设得让 N 明显大于 K（如 N=8、K=3），才容易观察到“被挡住等待”。

### 复盘问题

- 信号量和互斥锁最本质的区别是什么（提示：所有权 + 计数）？各自的典型场景？
- `counting_semaphore<K>` 怎么做到“同时最多 K 个”？计数到 0 后再 `acquire` 会怎样？
- 为什么 `acquire` 和 `release` 可以由不同线程执行？这一点 mutex 为什么做不到？
- `binary_semaphore` 和一个初值为 0/1 的 `counting_semaphore<1>` 是同一个东西吗？
- 什么时候该用 `try_acquire_for` 而不是 `acquire`？

### 对应官方参考

- cppreference [`std::counting_semaphore`](https://en.cppreference.com/w/cpp/thread/counting_semaphore)
- 《C++ Concurrency in Action, 2nd ed.》(Anthony Williams) 第 4 章（信号量）

## 练习 H-3：atomic wait / notify

> 代码目录：`exercises/H3_atomic_wait_notify/`

### 目标

掌握 C++20 给 `std::atomic` 加的 `wait(old)` / `notify_one()` / `notify_all()`：用它把**忙等自旋（busy-wait / spin）**换成真正的睡眠等待，实现一个高效的“一次性事件 / flag”，并讲清相对自旋的优势。

### 前置理解

- **`atomic<T>::wait(old, mo)`**：若当前原子值**等于** `old`，则**阻塞**本线程（睡眠）；被 `notify` 唤醒且值发生改变后返回再加载比较。若调用时已经**不等于** `old`，**立即返回**（不阻塞）。
- **`atomic<T>::notify_one()` / `notify_all()`**：唤醒一个 / 全部正在 `wait` 的线程。`notify` 本身不改值——改值是你 `store` 的事。
- **相对忙等自旋的优势**：
  - 忙等自旋是 `while (flag.load() == old) { /* 空转，可能 yield */ }`——线程一直占着 CPU 反复复查，等待期间纯空耗、烧功耗、与别人抢核。
  - `wait` 让线程**真正睡眠**，由内核 / 运行时择机唤醒；平台上常借 **futex（Linux）/ `WaitOnAddress`（Windows）** 这类“按地址等待（wait-on-address）”原语实现，等待期间几乎不占 CPU。
  - 取舍：**极短**等待（几十纳秒级）下 spin 可能更快（省一次睡眠/唤醒的开销）；等待时间不可忽略时，`wait/notify` 才是正解。
- **两条铁律**：
  1. **等待方在 `while` 谓词里复查**：`wait` 允许伪唤醒（spurious wakeup）以及“值变了又变回”——醒来必须复查谓词，不满足就接着 `wait`。范式：`while (flag.load(mo) == old) flag.wait(old, mo);`
  2. **通知方先改值、再 notify**：`flag.store(new, mo); flag.notify_one();`。顺序反了，等待方可能在你 notify 之后、改值之前复查谓词，错过这次唤醒。
- 与模块 F 的联系：`store(new, release)` + `wait(..., acquire)` 之间建立 happens-before，所以唤醒后能看到通知方在 store 之前写好的其他数据（payload）。

### 必做任务

1. **用 atomic flag + wait/notify 实现高效等待**（对应 `// TODO [必做 1]`）：waiter 线程在 `while (flag.load(acquire) == 0) flag.wait(0, acquire);` 里睡眠等待，几乎不占 CPU。

2. **通知方拉起事件**（对应 `// TODO [必做 2]`）：signaler 先写好 payload，再 `flag.store(1, release)`（顺带发布 payload），最后 `flag.notify_one()` 唤醒 waiter。waiter 醒来后能读到完整 payload。

3. **对比忙等自旋（反面教材）**：第二部分用朴素 `while (flag.load()==0) yield();` 自旋，加一个自旋计数器，把“事件来临前白白转了多少圈”打印出来，直观感受 spin 烧 CPU 的浪费；并说清相对 `wait/notify` 的劣势。

### 进阶任务

- **多个 waiter + `notify_all()`**：起多个 waiter 都 `wait(0)`，signaler 用 `notify_all()` 一次唤醒全部，对比 `notify_one()`（只唤醒一个）。
- **量化 spin 的浪费**：把事件到来的延迟拉长（如 200ms），对比 spin 版本的空转圈数 / CPU 占用与 wait 版本（几乎 0）。讨论“短等待用 spin、长等待用 wait”的工程权衡，以及混合策略（先 spin 几圈再转 wait）。
- **用 wait/notify 手搓一个简化版“事件（event）”或“一次性 latch”**，对照 H-1 的 `std::latch`、模块 C 的 `condition_variable`，体会三者的层次：atomic wait/notify 是更底层的积木，latch/condvar 是更高层的封装。
- **思考 ABA 式漏唤醒**：如果 flag 在你 `load` 和 `wait` 之间被改了又改回 `old`，`wait` 会怎样？为什么“在 `while` 里复查”能兜住这种情况？

### 验收点

- wait/notify 版本中 waiter 被正确唤醒，并读到 signaler 通过 release 发布的 payload（release/acquire 配对建立可见性）。
- 自旋版本能打印出可观的空转圈数，与 wait 版本形成对比。
- 你能说清 `atomic::wait` 相对自旋的优势（不烧 CPU、省功耗、平台多用 futex 实现）与适用边界（极短等待 spin 可能更优）。
- 你能解释两条铁律：为何在 `while` 里复查、为何通知方要先改值再 notify。

### 观察点

- waiter 在 `wait` 上几乎不占 CPU；spinner 在同样等待时间内空转了成千上万圈——这就是 spin 的代价。
- signaler 的 `store(release)` 与 waiter 的 `wait(acquire)` 配对，唤醒后 payload 一定可见。
- `notify` 不改值；真正让 `wait` 返回的是“值变了”这件事，所以 `store` 必须在 `notify` 之前。

### 常见坑

- **用 `if` 而不是 `while`**：遇到伪唤醒或“值变回原样”，`if` 版本会误以为事件到了。必须 `while` 复查谓词。
- **先 notify 再改值**：等待方可能在你改值之前复查谓词、错过唤醒，然后睡死。**永远先改值、再 notify**。
- **`wait` 的 `old` 取错**：`wait(old)` 是“值还等于 old 就睡”。传成“期望的新值”会语义颠倒（值已是新值则立即返回、达不到等待效果）。
- **拿 spin 当默认**：等待时间不短时 spin 白烧 CPU、抢核拖慢整机。默认用 `wait/notify`，只有 profiling 证明“极短等待 + spin 更快”时才上 spin。
- **忘了内存序**：发布数据 + flag 用 `release`，等待方用 `acquire`；全写 relaxed 则唤醒后可能看不到 payload。

### 提示

- 等待范式背下来：`while (a.load(acquire) == old) a.wait(old, acquire);`；通知范式：`a.store(new, release); a.notify_one();`。
- 自旋版本里用 `std::this_thread::yield()` 稍微缓解占用，但它仍是忙等（不会真正睡眠）——正好用来对比。
- 把自旋圈数用线程局部变量累加，结束时一次性打印，避免打印本身干扰计数。
- 用本仓库 `cs::logf(...)` 打印唤醒时刻与读到的 payload，验证可见性。

## 做完模块 H 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- **`std::latch`**：一次性向下计数栅栏，`count_down`/`wait`/`arrive_and_wait`/`try_wait`；归零后**不可重用**。典型用法：“等 N 件事都完成 / 全部就绪后同时开跑”（起跑线模型，ready 报到 + go 发令）。
- **`std::barrier`**：**可重用**的多阶段汇合点，维护“代 / 阶段”；每阶段到齐后由某一个线程执行 completion function **恰好一次**（必须 `noexcept`）再唤醒全部，自动进入下一代；`arrive_and_drop` 用于正规减员。典型用法：多轮迭代的相位同步。
- **`std::counting_semaphore<K>` / `std::binary_semaphore`**：非负计数许可，`acquire(-1)`/`release(+1)`/`try_acquire[_for]`。做资源池**限流**（同时最多 K 个）与线程间**信号**；与 mutex 的本质区别是**无所有权**——acquire 与 release 可由不同线程执行、计数可 > 1。
- **`std::atomic<T>::wait/notify`**：把忙等自旋换成真正的**睡眠等待**（平台常以 futex / WaitOnAddress 实现），不烧 CPU、省功耗。两条铁律：等待方在 `while` 谓词里复查（防伪唤醒），通知方**先改值、再 notify**；配 release/acquire 还能发布等待期外的数据。
- **选型直觉（本模块的灵魂）**：保护临界区 → mutex；等若干事完成 / 同时开跑 → latch；多轮汇合 + 收尾 → barrier；限并发份数 / 跨线程发信号 → semaphore；底层高效等待单个原子条件 → atomic wait/notify。选对原语，比手搓 mutex + condition_variable 更短、更对、更高效。
