# 03 模块 B：互斥与锁

## 模块目标

模块 A 让你学会了怎样安全地**创建、汇合（join）、取消**线程。但只要两个线程同时碰同一块可变数据，你的程序就立刻进入未定义行为（undefined behavior，UB）的雷区——这就是数据竞争（data race）。模块 B 解决的核心问题只有一个：**当多个线程需要访问共享可变状态时，如何用互斥量（mutex）把它们串行化（serialize），从而消除数据竞争，同时又不引入死锁（deadlock）。**

具体来说，本模块带你建立三层能力：

- **选对工具**：标准库的互斥量不止 `std::mutex` 一个。`std::recursive_mutex`、`std::timed_mutex`、`std::shared_mutex` 各自解决不同问题。你要知道默认用哪个，以及什么时候才该升级到别的。
- **用对 RAII 锁包装器**：`std::lock_guard`、`std::unique_lock`、`std::scoped_lock`、`std::shared_lock` 是四种「在构造时上锁、析构时解锁」的资源获取即初始化（Resource Acquisition Is Initialization，RAII）包装器。它们解决的是「异常或提前返回时忘记解锁」这一类几乎必然会犯的错误。你要能在任意场景下，凭直觉选出最朴素够用的那一个。
- **躲开死锁**：一旦同时需要多把锁，加锁顺序就成了正确性问题。你要理解死锁的四个必要条件，并掌握标准库提供的「一次性原子获取多把锁」机制（`std::scoped_lock` / `std::lock`），它从算法层面消除了循环等待。

## 模块完成标准

做完本模块，你至少要能稳定说清楚（can-do 验收）：

- 你能说出 `std::mutex`、`std::recursive_mutex`、`std::timed_mutex`、`std::shared_mutex` 各自的语义差异，并能举出一个「只能用它、不能用 `std::mutex`」的场景。
- 你能解释为什么默认应该用 `std::lock_guard`，以及在哪三类场景下你必须升级到 `std::unique_lock`（延迟上锁、所有权转移、配合条件变量）。
- 你能用 `std::shared_mutex` + `std::shared_lock` / `std::unique_lock` 写出一个读多写少（reader-writer）的并发结构，并解释「多个读者可并发、写者独占」是如何成立的。
- 你能默写死锁的四个必要条件，能现场制造一个两锁反序死锁，并能用 `std::scoped_lock` 把它修掉，且解释清楚修复的原理不是「加超时」而是「破坏循环等待」。
- 你能说清楚 `std::call_once` + `std::once_flag` 与「函数内 static 局部变量（magic statics）」在线程安全惰性初始化上的异同与取舍。

## 前置理解（整个模块共用）

- 你已经接受：**没有任何同步手段时，一个线程写、另一个线程读（或两个都写）同一个非原子对象，就是数据竞争，是 UB**，编译器有权做出任何行为。不要靠「跑起来好像没问题」来判断正确性。
- 你知道互斥量的本质是「同一时刻最多一个线程持有锁」，未拿到锁的线程会**阻塞（block）**等待。
- 你知道「锁保护的是数据，不是代码」——是你在心里建立「这把锁守护这些变量」的约定，编译器不会替你检查。
- 你已经会用 `cs::log` / `cs::logf`（见 `exercises/include/concurrency_study/log.hpp`）做线程安全打印，本模块所有观察都靠它。

- 本模块三道题纯标准库、零外部依赖、可离线构建，MSVC（VS2026，C++20）为主路径。
- 所有日志都建议打印：阶段名、线程标识、关键变量值。
- 「常见坑」一节里的反例代码请务必亲手跑一遍——只有亲眼看到错误，纠正才会留下记忆。

## 练习 B-1：互斥量家族与 RAII 锁包装器

### 目标

把标准库互斥量家族（`std::mutex` / `std::recursive_mutex` / `std::timed_mutex` / `std::shared_mutex`）和四种 RAII 锁包装器（`std::lock_guard` / `std::unique_lock` / `std::scoped_lock` / `std::shared_lock`）一次性建立起选型直觉。亲手用 `std::mutex` + `std::lock_guard` 保护一个计数器消除数据竞争，再用 `std::shared_mutex` 写一个「读多写少」结构，最后体会 `std::unique_lock` 相对 `std::lock_guard` 多出来的灵活性。

### 前置理解

- **互斥量（mutex）** 是 `<mutex>`（C++11）/ `<shared_mutex>`（C++17）里的同步原语，本身只提供 `lock()` / `try_lock()` / `unlock()`，但你几乎永远不该手写这三个调用——要用 RAII 包装器。
- 四种互斥量的差异：
  - `std::mutex`（C++11）：最朴素的独占互斥量。同一线程**不可**重复上锁（重入即 UB / 死锁）。**默认就用它。**
  - `std::recursive_mutex`（C++11）：允许**同一线程**多次上锁（每次 `lock` 要配一次 `unlock`）。用于递归函数 / 互相调用的成员函数都需要持锁的场景。能不用就不用——通常需要它说明你的锁边界设计得不够清晰。
  - `std::timed_mutex`（C++11）：在 `std::mutex` 基础上增加 `try_lock_for()`（等一段时间）/ `try_lock_until()`（等到某时刻）。用于「拿不到锁就别死等，去干别的」。
  - `std::shared_mutex`（C++17）：读写锁（reader-writer lock）。支持两种上锁模式——**共享（shared）**：多个读者可同时持有；**独占（exclusive）**：写者独占，与所有读者和写者互斥。专为「读远多于写」设计。
- 四种 RAII 锁包装器的差异：
  - `std::lock_guard`（C++11）：最朴素。构造即 `lock`，析构即 `unlock`，**不可移动、不可提前解锁、无任何额外接口**。默认就用它。
  - `std::unique_lock`（C++11）：功能最全的独占锁包装器。支持**延迟上锁**（`std::defer_lock`）、**提前手动 `unlock()` / 再 `lock()`**、**可移动（转移锁所有权）**、并且是**条件变量 `wait()` 唯一接受的类型**。代价是比 `lock_guard` 多一个「是否持锁」的状态位，略重。
  - `std::scoped_lock`（C++17）：可一次性锁住**多把**互斥量，内部用死锁避免算法（deadlock-avoidance algorithm，等价于 `std::lock`）保证不会因加锁顺序不同而死锁。锁单把时等价于 `lock_guard`。**多锁场景的首选**（B-2 详讲）。
  - `std::shared_lock`（C++14）：以**共享模式**持有 `std::shared_mutex` 的 RAII 包装器（对应「读者」）。写者则用 `std::lock_guard<std::shared_mutex>` 或 `std::unique_lock<std::shared_mutex>` 以独占模式持有。
- 一句话选型口诀：**单锁默认 `lock_guard`；要延迟/移动/配 condvar 用 `unique_lock`；多锁用 `scoped_lock`；读写锁的读端用 `shared_lock`、写端用 `lock_guard<shared_mutex>`。**

### 必做任务

1. **数据竞争对照组**：先写一个**故意不加锁**的版本——开 N（如 8）个线程，每个线程对一个全局 `int counter` 自增 100000 次。运行多次，打印最终值，观察它**几乎从不等于** `N*100000`。这一步是为了让你亲眼看到数据竞争，**不要跳过**。（骨架里这部分已实现，看注释理解为什么结果错。）
2. **mutex + lock_guard 修复**：用 `std::mutex` + `std::lock_guard` 保护 `counter` 的自增。重新运行，验证结果**每次都精确等于** `N*100000`。体会 `lock_guard` 如何让「上锁—临界区—解锁」三件事缩成一行、且异常安全。
3. **shared_mutex 读多写少场景**：实现一个线程安全的 `Config`（或简单的 `std::map<std::string,int>` 缓存）：
   - 读操作 `get(key)`：用 `std::shared_lock<std::shared_mutex>` 上**共享锁**，允许多个读线程并发进入。
   - 写操作 `set(key, val)`：用 `std::lock_guard<std::shared_mutex>`（或 `std::unique_lock`）上**独占锁**，与所有读写互斥。
   - 起多个读线程 + 少量写线程并发跑，打印读到的值，验证没有崩溃 / 没有读到撕裂（torn）的数据。
4. **unique_lock 灵活性演示**：写一个小函数，展示 `std::unique_lock` 至少一项 `lock_guard` 做不到的能力——推荐演示「**临界区内提前 `unlock()`**，把耗时的非共享工作移出锁外」：先持锁读出需要的数据，`lk.unlock()` 后做耗时计算，避免长时间占着锁阻塞别人。日志打印锁的持有/释放时刻。

### 进阶任务

1. **timed_mutex 限时获取**：把某个资源换成 `std::timed_mutex`，一个线程长时间持锁，另一个线程用 `try_lock_for(50ms)` 尝试获取——拿到就干活，超时就打印「放弃，稍后重试」并去做别的事。体会「限时锁」相对「死等」在响应性上的价值。
2. **recursive_mutex 重入**：写一对互相调用、且都需要持有同一把锁的成员函数，先用 `std::mutex` 触发自死锁（自己等自己，观察程序卡死），再换成 `std::recursive_mutex` 修复。然后**反思**：这个设计能不能通过「提取一个不加锁的私有 helper」来避免 recursive_mutex？（提示：几乎总能。）
3. **shared_lock 不保证写者优先**：在读多写少结构里持续打高频读负载，观察写线程是否会被「读者洪流」长时间饿死（writer starvation）。记录现象，思考标准库为何不强制写者优先（答案：标准未规定调度策略，取决于实现）。

### 验收点

- 你能展示「无锁版结果错乱、`lock_guard` 版结果恒正确」的对照运行输出。
- 你能解释 `std::shared_mutex` 下「N 个读者并发 + 写者独占」为什么不构成数据竞争。
- 你能现场说出：给定一个临界区，什么时候用 `lock_guard` 就够、什么时候**必须**换 `unique_lock`，并各举一例。
- 你能说出 `std::shared_lock` 对应读者、`std::lock_guard<std::shared_mutex>` 对应写者，并解释为什么写者不能用 `shared_lock`。

### 观察点

- 无锁自增的最终值每次运行都不同，且总是 ≤ 理论值——因为 `counter++` 是「读—改—写」三步，可被另一线程插入覆盖（丢失更新，lost update）。
- 加了 `lock_guard` 后，吞吐明显下降（所有自增被串行化）——这是正确性的代价，你应当**感受到**它，而不是无视它。
- `shared_mutex` 下，多个读线程的日志时间戳会高度重叠（它们真的在并发），而写线程的日志区间内没有任何读者活动。
- `unique_lock` 提前 `unlock()` 后，其他线程立即能进入临界区——日志能看到锁的「空窗期」被别人填满。

### 常见坑

- **手写 `lock()` / `unlock()` 配对**：一旦临界区里有 `return`、`throw` 或 `break`，就会漏掉 `unlock()`，造成死锁。永远用 RAII 包装器。
- **声明了 RAII 锁却没命名**：`std::lock_guard<std::mutex>(m);` 创建的是一个**立即析构的临时对象**，锁在这一行结束就放了，等于没锁！必须 `std::lock_guard<std::mutex> lk(m);` 给它一个名字。这是 C++ 并发头号低级错误。
- **读者误用独占锁**：在 `shared_mutex` 的读路径上用了 `unique_lock` / `lock_guard`，读者之间也互斥了，读写锁退化成普通互斥锁，白白损失并发。读者**必须**用 `shared_lock`。
- **持锁做耗时工作**：在锁内 sleep、做 I/O、调用可能阻塞的函数，会把临界区拉长、严重伤害并发。能移出锁外的就移出去（必做任务 4 的训练点）。
- **对 `std::mutex` 重入**：同一线程对已持有的 `std::mutex` 再次 `lock`，是 UB（多数实现表现为死锁）。需要重入用 `recursive_mutex`，但先想想能不能重构掉。

### 提示

- `std::shared_lock` 在 `<shared_mutex>` 里，`std::shared_mutex` 也在那里；别忘了 `#include <shared_mutex>`。
- 写者用 `std::lock_guard<std::shared_mutex> lk(m);` 即可拿独占锁——`lock_guard` 调用的是 `m.lock()`（独占版），而 `shared_lock` 调用 `m.lock_shared()`。区别全在「调哪个成员」。
- 演示 `unique_lock` 提前解锁时，可以在 `unlock()` 前后各打一条日志，并让别的线程在那段时间抢锁，对照时间戳。
- 想确认数据竞争客观存在，可在支持的编译器上用 ThreadSanitizer（GCC/Clang 的 `-fsanitize=thread`）跑无锁版，它会直接报 data race。

### 复盘问题

- `counter++` 在汇编层面是几条指令？为什么它不是原子的？（这正是模块 E 原子操作要解决的问题——这里先用锁。）
- 如果读多写少结构里 99% 是读，用 `shared_mutex` 比用 `std::mutex` 能快多少？什么情况下 `shared_mutex` 反而更慢？（提示：`shared_mutex` 内部簿记更重，临界区极短 + 写比例不低时可能得不偿失。）
- `std::unique_lock` 比 `std::lock_guard` 多了哪个状态、多了多大开销？为什么标准库要同时保留这两个而不是只留功能更全的那个？
- 为什么 `std::shared_lock` 是 C++14 引入，而 `std::shared_mutex` 要等到 C++17？（历史：C++14 先有了 `shared_timed_mutex` 与 `shared_lock`，C++17 才补上更轻的 `shared_mutex`。）

## 练习 B-2：死锁与 scoped_lock 多锁原子获取

### 目标

亲手用两把互斥量、以**相反顺序**加锁，制造一个真实的死锁，理解它为什么会卡死；再用 `std::scoped_lock`（底层等价于 `std::lock`）一次性**原子地**获取多把锁，从根本上消除死锁。把「死锁四个必要条件」与「破坏循环等待」这一修复原理钉进肌肉记忆。

### 前置理解

- **死锁（deadlock）**：两个或更多线程各自持有一部分资源、又互相等待对方手里的资源，谁都无法前进，永久卡死。
- **死锁的四个必要条件**（Coffman 条件，四个**同时**满足才可能死锁，破坏任意一个即可避免）：
  1. **互斥（mutual exclusion）**：资源同一时刻只能被一个线程持有。
  2. **持有并等待（hold and wait）**：线程持有至少一个资源的同时，又在等待获取别的资源。
  3. **不可抢占（no preemption）**：资源只能由持有者主动释放，不能被强行夺走。
  4. **循环等待（circular wait）**：存在一个线程等待环（T1 等 T2 持有的锁，T2 等 T1 持有的锁）。
- **本题主攻「破坏循环等待」**：最经典的两种工程手段——
  - **固定全局加锁顺序（lock ordering）**：所有线程永远按同一个约定顺序（如按地址、按 id）获取多把锁，环就不可能形成。
  - **死锁避免式获取**：`std::scoped_lock` / `std::lock` 用死锁避免算法（`try_lock` 尝试 + 失败则释放已持有的所有锁 + 回退重试）获取多把锁。它的关键不是「事务般的原子瞬间」，而是**绝不在持锁状态下阻塞等待**另一把锁——一旦某把拿不到就立刻松手重来，从而破坏「持有并等待」这一必要条件。
- **层级锁（lock hierarchy）** 是「固定加锁顺序」的工程化：给每把锁一个层级编号，规定只能从高层级往低层级加锁，运行期断言违规即报错。本题作为思路讲解，不要求实现完整层级锁类。

### 必做任务

1. **制造死锁（反例）**：定义两把锁 `mA`、`mB` 和两份资源。
   - 线程 1：先锁 `mA`，（人为 `sleep_for` 一小段制造时间窗）再锁 `mB`。
   - 线程 2：先锁 `mB`，再锁 `mA`。
   - 运行，观察程序**卡死**（两个线程各持一把、互等另一把）。在注释里写清楚：**为什么会死锁、如何观察到它死锁了**（提示：程序不退出、日志停在「锁了第一把、正在等第二把」）。
   - ⚠️ 这一版会真的挂起。骨架里默认**用开关把它关掉**（不真正运行死锁版），你手动打开后亲眼观察，再关掉，以免阻塞后续测试。
2. **scoped_lock 修复版**：把两个线程获取双锁的地方都改成**一行** `std::scoped_lock lk(mA, mB);`（C++17 类模板实参推导，CTAD，可省略模板参数）。两个线程哪怕参数书写顺序相反，`scoped_lock` 内部也会用统一的死锁避免算法获取，**永不死锁**。运行验证：程序每次都能正常跑完。
3. **解释修复原理**：在注释 / README 里写清楚——`scoped_lock` 不是靠「加超时」或「重试」修的，而是**一次性原子获取多锁**，破坏了循环等待这个必要条件。

### 进阶任务

1. **std::lock + adopt_lock 写法**：不用 `scoped_lock`，改用底层的 `std::lock(mA, mB)` 先原子锁两把，再用两个 `std::lock_guard(mX, std::adopt_lock)` 接管所有权（adopt：领养已持有的锁，析构时负责解锁）。体会 `scoped_lock` 其实就是这套写法的语法糖。
2. **固定加锁顺序版**：不用 `scoped_lock`，改为「永远先锁地址较小的那把」（`if (&mA < &mB) ... else ...`），同样能避免死锁。对比两种方案的优缺点（`scoped_lock` 更简洁不易错；固定顺序在你无法一次性拿全部锁、需要分散获取时仍适用）。
3. **最小层级锁原型**：写一个 `hierarchical_mutex`，带一个层级值，`lock()` 时断言「当前线程已持有的最低层级 > 本锁层级」，违规则抛异常。用它去跑反序加锁，观察它在**运行期**就把潜在死锁暴露成异常（而不是等到真死锁）。（参考《C++ Concurrency in Action》3.2.5。）

### 验收点

- 你能现场写出一个两锁反序死锁，并解释它命中了四个必要条件中的哪几个。
- 你能用 `std::scoped_lock` 把它改成一行，并解释修复原理是「破坏循环等待 / 持有并等待」，而非超时重试。
- 你能说出至少两种避免多锁死锁的工程手段（一次性原子获取、固定加锁顺序、层级锁），并知道各自适用边界。

### 观察点

- 死锁版运行时，两个线程的日志都会停在「已获取第一把锁，正在请求第二把」，之后**再无任何输出**，进程不退出——这就是死锁的典型现场。
- `scoped_lock` 版无论运行多少次都能正常结束；即使你把两个线程里 `scoped_lock(mA, mB)` 和 `scoped_lock(mB, mA)` 写成相反顺序，它依然不死锁（因为内部按统一策略获取，与你书写的顺序无关）。
- 用进阶任务的 `std::lock` 版，你会看到它和 `scoped_lock` 行为完全一致——印证了语法糖关系。

### 常见坑

- **观察死锁后忘了关掉**：死锁版会永久挂起，会卡住整个测试驱动。务必用开关默认关闭，只在单独观察时打开。
- **以为「加 sleep」能避免死锁**：sleep 只是改变了时间窗口、降低复现概率，**死锁条件仍然成立**，随时会复发。这是初学者最危险的错觉。
- **以为 `try_lock` + 重试是好方案**：盲目 `try_lock` 失败就重试可能导致**活锁（livelock）**——大家都在「拿一把、发现另一把没拿到、全放掉、重来」里空转。要重试也得加随机退避，但远不如 `scoped_lock` 干净。
- **`scoped_lock` 锁单把时误以为有特殊行为**：锁一把时 `scoped_lock` 就等价于 `lock_guard`，死锁避免算法只在 ≥2 把时起作用。
- **混用「固定顺序」和「scoped_lock」却仍出错**：如果代码里有些地方用 `scoped_lock` 一次拿全、另一些地方又分散单独拿同一批锁且顺序不一，照样能死锁。一致性才是关键。

### 提示

- C++17 起 `std::scoped_lock lk(mA, mB);` 可省略模板参数（CTAD 自动推导）。早期写法是 `std::scoped_lock<std::mutex, std::mutex> lk(mA, mB);`。
- 制造死锁时，两个线程之间加一个 `std::this_thread::sleep_for(几十毫秒)` 在「锁第一把」和「锁第二把」之间，能让死锁**几乎必然复现**，便于观察。
- `std::lock(a, b)` 锁定后，记得用 `std::lock_guard l1(a, std::adopt_lock);` 而不是 `std::lock_guard l1(a);`——后者会再次尝试上锁导致 UB。`adopt_lock` 的含义是「锁已经被我持有了，你只管负责析构时解锁」。
- 想验证「修复不是靠运气」，把 `scoped_lock` 版在循环里跑上千次，全部正常结束即可佐证。

### 复盘问题

- 死锁的四个必要条件里，`std::scoped_lock` 同时破坏了哪几个？为什么说它破坏的是「循环等待」而 `try_lock` 重试破坏的是「不可抢占 / 持有并等待」？
- 如果你有三把锁、且不同代码路径需要其中不同的子集，「固定全局顺序」和「scoped_lock 一次拿全」哪个更合适？为什么？
- 活锁和死锁的区别是什么？为什么 `try_lock` 重试容易诱发活锁？
- 层级锁是在编译期还是运行期发现死锁风险的？相比 `scoped_lock`，它的优势和代价分别是什么？

## 练习 B-3：call_once 一次性初始化

### 目标

用 `std::call_once` + `std::once_flag` 实现线程安全的惰性初始化（lazy initialization）：多个线程并发触发同一段初始化代码，验证它**恰好只执行一次**。再把它与「函数内 static 局部变量（magic statics，C++11 起线程安全的局部静态初始化）」对比，建立两者的取舍直觉。

### 前置理解

- **惰性初始化**：资源在「第一次真正被用到时」才初始化，而不是程序启动时。难点在于：多个线程可能**同时**第一次用到它，必须保证初始化只发生一次、且其他线程能看到初始化完成的结果。
- **`std::once_flag`**（C++11）：一个标记对象，记录「某段初始化是否已经跑过」。不可拷贝、不可移动，通常做成 `static` 或类成员。
- **`std::call_once(flag, callable, args...)`**（C++11）：保证传入的可调用对象，对同一个 `once_flag`，在所有线程中**总共只成功执行一次**。如果初始化函数抛异常，本次视为「未成功」，`once_flag` 不翻转，下一个调用者会再次尝试（这点是 `call_once` 的重要保证）。
- **magic statics**（C++11 起的「魔法静态变量」）：函数内的 `static` 局部变量，标准保证其初始化是**线程安全**的——首个进入的线程负责初始化，其余线程阻塞等待其完成。语法上最简洁：`static T& instance = ...; return instance;`。
- 两者关系：magic statics 能覆盖**大多数**单例 / 惰性初始化场景且写法最短；`call_once` 更通用——当初始化目标不是「一个函数局部静态对象」（比如要初始化一个已存在的成员、要带复杂参数、要在非函数作用域控制时机）时，`call_once` 更合适。

### 必做任务

1. **call_once 惰性初始化**：定义一个全局 `std::once_flag flag;` 和一个待初始化资源（如 `std::unique_ptr<Widget>` 或一个 `int`）。写一个 `get_resource()`，内部 `std::call_once(flag, []{ /* 初始化，并打印一条「正在初始化」日志 */ });` 然后返回资源。
2. **并发触发验证只初始化一次**：起 N（如 8）个线程，几乎同时调用 `get_resource()`。用一个 `std::atomic<int> init_count` 在初始化函数里自增，最后断言 / 打印 `init_count == 1`。日志里你应当只看到**一条**「正在初始化」，其余线程直接拿到结果。
3. **magic statics 对照实现**：把同样的惰性初始化用「函数内 static 局部变量」再写一遍：`Widget& get_resource2() { static Widget w{...}; return w; }`。同样起 N 个线程并发调用，用计数器验证 `Widget` 的构造函数也**只被调用一次**。对比两种写法的代码量与适用性。

### 进阶任务

1. **初始化抛异常的语义**：让 `call_once` 的初始化函数**第一次故意抛异常**，捕获后再调用 `get_resource()`，观察第二次会**重新尝试**初始化（因为首次未成功，`once_flag` 没翻转）。这是 `call_once` 相对「自己用一个 bool 标记」最容易被忽视、也最重要的正确性保证。
2. **手写错误的 double-checked locking 反例**：用一个裸 `bool initialized` + `if (!initialized) { lock; if(!initialized){ init; initialized=true; } }` 实现「双重检查锁定（double-checked locking）」，并解释为什么在没有原子 / 内存序保证下它是**坏的**（第一个 `if` 读 `initialized` 与初始化写之间存在数据竞争，可能读到「已置位但对象尚未构造完」的中间态）。这正是 `call_once` 和 magic statics 替你正确处理的部分。（内存序细节在模块 F 展开，这里先建立「别手写 DCLP」的戒律。）
3. **call_once 配合带参数初始化**：演示 `std::call_once(flag, init_fn, arg1, arg2)` 传参，体会它比 magic statics 在「初始化需要运行期参数」时的灵活性。

### 验收点

- 你能展示「N 个线程并发触发，初始化函数 / 构造函数恰好执行一次」的运行输出（计数器 == 1）。
- 你能说清楚 `std::call_once` 与 magic statics 各自的适用场景，并能各举一例「这个用 X 更自然」。
- 你能解释 `call_once` 在初始化抛异常时为什么不翻转 `once_flag`，以及这个语义有什么实用价值。
- 你能说出为什么不该手写 double-checked locking，以及 `call_once` / magic statics 替你解决了什么。

### 观察点

- 无论起多少线程，「正在初始化」日志只出现一次；其余线程的日志显示它们「直接拿到了已初始化的资源」。
- magic statics 版的 `Widget` 构造函数也只触发一次——多个线程同时第一次进入时，只有一个执行构造，其余阻塞等待。
- 进阶任务里，初始化第一次抛异常后，`init_count` 在第二次调用时会再次自增——证明 `once_flag` 没被「失败的初始化」翻转。

### 常见坑

- **`once_flag` 用错粒度**：每次调用 `get_resource` 都新建一个局部 `once_flag`，等于每次都「第一次」，完全失效。`once_flag` 必须是 `static` / 全局 / 成员，跨调用持久存活。
- **把 `call_once` 当普通互斥**：`call_once` 只保证「该 callable 总共执行一次」，不是给一段临界区反复加锁。别拿它当 mutex 用。
- **magic statics 的析构顺序陷阱**：函数局部 static 对象在程序退出时按「构造的逆序」析构，若它依赖另一个已被析构的全局对象，会出问题（static destruction order）。长生命周期单例有时故意用 `new` 不析构来规避。
- **以为旧编译器的 magic statics 也线程安全**：C++11 才标准化线程安全的局部静态初始化。非常老的编译器（或显式关闭该特性的编译选项，如 MSVC 的 `/Zc:threadSafeInit-`）下不成立。现代 MSVC/GCC/Clang 默认开启。
- **手写 DCLP 以为「加了锁就对」**：双重检查里的第一个无锁读，与初始化写之间仍是数据竞争——这是经典的、曾误导整个行业多年的 bug。用 `call_once` / magic statics / 原子（模块 F）才正确。

### 提示

- `std::call_once` 与 `std::once_flag` 都在 `<mutex>` 里，不用单独 include 别的头。
- 让多个线程「几乎同时」触发，可以先创建线程并让它们在一个起跑栅栏（可以简单用一个 `std::atomic<bool> go` 自旋，或模块 H 的 `std::latch`）上等待，再统一放行——这样更容易暴露竞争。
- 验证「只初始化一次」最稳的办法是在初始化体里 `init_count.fetch_add(1)`，最后查它等于 1。
- magic statics 写单例：`static Singleton& inst() { static Singleton s; return s; }`——记住返回**引用**，别返回值（拷贝）或裸指针。

### 复盘问题

- `std::call_once` 和函数内 `static` 局部变量，底层大概率都依赖什么机制实现「只执行一次 + 其余线程等待」？（提示：内部也是某种 once flag + 同步。）
- 如果初始化函数可能失败并抛异常，你更倾向 `call_once` 还是 magic statics？为什么？（magic statics 抛异常时下次进入也会重试，行为类似，但 `call_once` 的语义更显式可控。）
- 为什么 double-checked locking 在 C++11 之前是「著名的错」？C++11 的内存模型 + 原子 / `call_once` 是怎么让它不再必要的？
- 单例模式用 magic statics 实现有什么隐藏风险（提示：析构顺序、跨翻译单元初始化顺序）？什么时候你会故意「泄漏」一个单例？

## 做完模块 B 之后，你现在应该能说清楚什么

- **互斥量家族选型**：默认 `std::mutex`；需要同线程重入用 `std::recursive_mutex`（但优先重构掉）；需要限时获取用 `std::timed_mutex`；读多写少用 `std::shared_mutex`。
- **RAII 锁包装器选型**：默认 `std::lock_guard`；要延迟上锁 / 转移所有权 / 配合条件变量，升级 `std::unique_lock`；一次锁多把用 `std::scoped_lock`；读写锁的读端用 `std::shared_lock`、写端用 `std::lock_guard<std::shared_mutex>`。
- **死锁四条件与多锁原子获取**：能默写互斥、持有并等待、不可抢占、循环等待四条件；知道破坏任一即可避免；能用 `std::scoped_lock` / `std::lock` 一次性原子获取多锁来破坏循环等待，也理解固定加锁顺序 / 层级锁的思路。
- **一次性初始化**：能用 `std::call_once` + `std::once_flag` 做线程安全惰性初始化，能与 magic statics 对比取舍，并知道为什么不能手写 double-checked locking。
