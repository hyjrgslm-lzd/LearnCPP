# 09 模块 G：无锁数据结构

## 模块目标

模块 E 教会你单个原子变量怎么用、模块 F 把内存序（memory order）讲透。但真实世界的并发数据结构（栈、队列、缓冲区）需要**协调多个原子操作**，让多个线程在**不加锁**的前提下安全地读写共享结构。这个模块就是把前两个模块的零件拼成第一批真正的无锁（lock-free）数据结构。

核心范式只有一个：**CAS 循环（compare-and-swap loop）**——读旧值、基于旧值算新值、用 `compare_exchange` 提交；失败就说明别人抢先动了，旧值被刷新，重试。围绕它，你会亲手实现 Treiber 无锁栈、踩中并破解臭名昭著的 **ABA 问题**、再写一个无需 CAS 的**单生产者单消费者（SPSC）环形缓冲**。

本模块还要让你建立两组关键直觉：其一，**进展保证（progress guarantee）**——lock-free / wait-free / obstruction-free 各自承诺什么；其二，**无锁回收难题**——pop 下来的节点什么时候才能安全 `delete`。后者本模块只点到（并刻意泄漏），完整解法（hazard pointer / RCU）留到模块 I。

## 模块完成标准

做完本模块，你至少要能稳定说清楚（can-do）：

- 你能写出标准的 CAS 循环，并解释 `compare_exchange_weak` 的引用参数在失败时如何被刷新、为什么循环体常常可以是空的。
- 你能实现 Treiber 无锁栈的 `push`/`pop`，并逐行说出每个原子操作用什么内存序、为什么（push 发布用 release、pop 消费用 acquire）。
- 你能讲清 ABA 问题的成因（CAS 只比较值、不比较历史），亲手构造一个会被 ABA 击穿的场景，并用带版本号的标签指针（tagged pointer）把它修好。
- 你能说出为什么 SPSC 环形缓冲**不需要 CAS**——`head` 与 `tail` 各由一方独占写入，两个写者之间没有竞争——以及 release/acquire 如何在它们之间传递槽位数据的可见性。
- 你能区分 lock-free（总有线程前进）、wait-free（每线程有界步数完成）、obstruction-free（无争用时单线程能完成）三种进展保证。
- 你能说清无锁数据结构的“回收难题”是什么（pop 释放节点的 use-after-free），并知道它的解法属于模块 I。

> 本模块所有内存序的判断都建立在模块 F 之上。如果你对 release/acquire 配对、happens-before、relaxed 的边界还不熟，请先回头把模块 F 过一遍。

## 练习 G-1：Treiber 无锁栈

> 代码目录：`exercises/G1_treiber_stack/`

### 目标

用单个原子指针 `head` + CAS 循环实现一个无锁的后进先出（LIFO）栈。`push`：new 一个节点，CAS 把它接到 `head`；`pop`：CAS 把 `head` 摘成 `head->next`，取走原栈顶的值。多线程压测验证不丢不重，并逐步讲清每个原子操作的内存序。

### 前置理解

- **Treiber 栈**（R. K. Treiber, 1986）是最经典的无锁数据结构：栈就是一条单向链表，`head`（一个 `std::atomic<Node*>`）指向栈顶；所有并发安全性都压在对 `head` 的 CAS 上。
- **CAS 循环范式**：
  1. 读当前 `head` 到 `old`；
  2. 基于 `old` 算出想要写入的新值；
  3. `head.compare_exchange_weak(old, new, ...)` 尝试提交；
  4. 失败 → CAS 已把 `head` 的**最新值写回 `old`**（第一个参数是引用！），据此重算、重试。
- 因为失败时 `old` 被自动刷新，`push` 的循环体往往可以是**空的**——`new_node->next` 就是那个被刷新的引用。
- 关键概念：
  - **`compare_exchange_weak` vs `_strong`**：weak 允许“伪失败”（spurious failure，即使值相等也可能返回 false），但在循环里更高效（某些平台上 strong 要靠额外循环模拟）。**在 CAS 循环里优先用 weak**；只有当“不在循环里、一次失败代价很大”时才用 strong。
  - **进展保证（progress guarantee）**：
    - **lock-free（无锁）**：系统整体总有线程能前进（某线程 CAS 失败，必然是因为另一个线程 CAS 成功了）。没有任何线程持锁，因此某线程被挂起不会卡死其他线程。
    - **wait-free（无等待）**：更强——**每个**线程都能在**有界步数**内完成，谁都不会被无限重试拖住。
    - **obstruction-free（无障碍）**：最弱——只保证“无争用时单个线程能在有界步数内完成”，有争用时可能互相回退。
    - Treiber 栈是 **lock-free 但非 wait-free**：高争用下某个线程可能反复 CAS 失败、一直重试。

### 必做任务

1. **实现 push**（对应 `// TODO [必做 1]`）：`new Node`，让 `new_node->next = head_.load(relaxed)`，然后
   ```cpp
   while (!head_.compare_exchange_weak(new_node->next, new_node,
                                       std::memory_order_release,   // 成功：发布新节点
                                       std::memory_order_relaxed))  // 失败：仅取回最新 head
   { /* 失败时 next 已被刷新为最新 head，重试 */ }
   ```
   - **为什么成功用 release**：CAS 成功意味着把 `new_node` 发布给了别的线程。`release` 保证“写好 `new_node->next`、`data` 等内容”这件事 happens-before 任何随后 `acquire` 读到这个 `head` 的线程，于是对方看到的节点是完整的。
   - **为什么失败用 relaxed**：失败只是把最新 `head` 取回来准备重试，没有要同步的数据。

2. **实现 pop**（对应 `// TODO [必做 1]`）：
   ```cpp
   Node* old = head_.load(std::memory_order_acquire);
   while (old && !head_.compare_exchange_weak(old, old->next,
                                              std::memory_order_acquire,
                                              std::memory_order_acquire))
   { /* 失败时 old 被刷新为最新 head，重试 */ }
   ```
   - **为什么用 acquire**：要与 push 的 release 配对，才能看到 push 端写好的节点内容（含 `next`）。
   - `old == nullptr` 表示空栈，返回失败。

3. **多线程压测**（对应 `// TODO [必做 2]`）：N 个线程并发 push 各 M 个元素，全部 join 后再起 N 个线程并发 pop 到空，统计弹出总数应严格等于压入总数（不丢、不重）。

4. **注明节点释放问题**：pop 成功摘下节点后，本应 `delete`。但无锁下这是危险的——可能另一个线程此刻正握着同一个指针准备读它的 `next`，直接 `delete` 会 use-after-free。**本题刻意泄漏（不 delete）**，把注意力集中在 CAS 与内存序上。安全回收留模块 I。

### 进阶任务

- **观察 ABA 的伏笔**：在“无回收（永不 delete）”的简化前提下，pop 里“CAS 成功前读 `old->next`”是安全的（节点恒有效）。一旦你试着加上 `delete old`，就会暴露 use-after-free 与 ABA——这正是 G-2 的主题。先把这个隐患记在心里。
- **改用 `compare_exchange_strong` 跑一遍**，对比高争用下两者的重试次数差异，体会 weak 在循环里为何更合适。
- **统计 CAS 重试次数**：给 push/pop 各加一个线程局部计数器，把高争用下的重试次数打出来，直观感受 lock-free ≠ wait-free。

### 验收点

- 多线程压测下弹出总数严格等于压入总数（不丢不重）。
- 你能逐行说出 push 的 release、pop 的 acquire 各自的作用，以及失败分支为何可用 relaxed。
- 你能解释 `compare_exchange_weak` 第一个参数为何是引用、失败时它被刷新成什么。
- 你能说清本题为什么必须泄漏节点，以及它和模块 I 的关系。

### 观察点

- CAS 失败时，`old`（或 `new_node->next`）被自动写回**最新的 head**——这是“循环体可为空”的原因。
- lock-free 的含义是“系统整体总有线程前进”，不是“每个线程都不阻塞”。高争用下个别线程可能反复失败。
- pop 与 push 之间的同步，靠的就是同一个 `head_` 上 release/acquire 的配对。

### 常见坑

- **在 CAS 之前没把 `new_node->next` 设好**：必须先让新节点的 `next` 指向当前 `head`，否则提交后链表断裂。
- **用 `compare_exchange_strong` 写 CAS 循环**：能跑，但在循环里通常不如 weak 高效。
- **以为可以直接 `delete` pop 下来的节点**：无锁下会 use-after-free。本模块一律泄漏。
- **内存序全写 seq_cst**：能对，但过度保守、损失性能。本题精确用 release/acquire/relaxed 即可。
- **失败分支误用 release**：失败时没有数据要发布，relaxed 足够；写 release 是多余的强约束。

### 提示

- 用 `std::atomic<Node*>` 存 `head`；节点是裸指针链表（本题不回收，所以裸指针够用）。
- 压测时把每线程的 push 数量调大（如上万），更容易在多核上撞出 CAS 失败重试。
- 用本仓库 `cs::logf(...)`（`concurrency_study/log.hpp`）打印阶段性结果。

### 复盘问题

- `compare_exchange_weak` 失败时，它对第一个参数做了什么？这如何让 push 的循环体为空？
- push 成功为什么要 release、pop 为什么要 acquire？把它们都换成 relaxed 会出什么问题？
- lock-free 和 wait-free 的区别是什么？Treiber 栈属于哪种？
- 如果现在就给 pop 加 `delete old`，会发生什么？为什么这把我们引向了 ABA 和模块 I？

## 练习 G-2：ABA 问题

> 代码目录：`exercises/G2_aba_problem/`

### 目标

亲手构造一个 **ABA** 场景，看着朴素指针 CAS 在“值变回原样”时被骗得**错误地成功**、把链表改坏；然后用带版本号的标签指针（tagged pointer / version counter）把它修好，并理解 hazard pointer / RCU 是另一类（基于安全回收的）解法。

### 前置理解

- **ABA 问题**：一个线程读到某原子的值是 `A`，随后被挂起；其间别的线程把它从 `A` 改成 `B`、又改回 `A`。原线程恢复后做 `compare_exchange`，发现“还是 `A`”，便误判“期间没人动过”而成功提交——可这个 `A` 的**含义/上下文已经变了**。
- 落到栈上的经典剧本（栈自底向上 `C -> B -> A(top)`）：
  1. 线程 1（受害者）读 `old_head = A`，缓存 `A->next == B`，准备 `CAS(head: A -> B)` 完成一次 pop，此刻被挂起。
  2. 线程 2（捣乱者）：pop A（head→B）、pop B（head→C）、再**复用同一个 A 节点**重新 push（head→A），但现在 `A->next` 已是 `C` 而非 `B`。
  3. 线程 1 恢复：CAS 期望 `head == A`——确实还是 `A`（值相同！）——成功，把 `head` 设成它**缓存的旧 `next == B`**。可 `B` 早被弹出、不在栈里了！`head` 指向一个悬空节点，`C` 丢失，栈彻底坏掉。
- **根因**：CAS 只比较**值（这里是指针）**，不比较**值的历史**。指针被复用（同一地址被释放后重新分配）时，“看起来没变”不等于“真的没变”。
- 关键概念：
  - **标签指针 / 版本号（tagged pointer / version counter）**：把 `(指针, version)` 打包成一个原子整体做 CAS，每次成功改动让 `version += 1`。于是“A 变 B 又变回 A”这条路径上 `version` 一定被推进过，受害者拿着旧 `version` 的 CAS **必然失败**、被迫重读看到真实状态。CAS 比较的是 `(指针, 版本)` 的**整体**，ABA 被根除。
  - **安全回收（safe reclamation）**：另一类思路是从“别让被释放的同址节点出现”入手——**hazard pointer**（线程发布“我正在用这个指针”，回收方看到就不释放）、**RCU（read-copy-update，读-复制-更新）**（等所有读者离开宽限期后再释放）。它们是模块 I 的主题，本题只点到。

### 必做任务

1. **复现 ABA**（对应第一部分 `// TODO`）：搭建 `C -> B -> A` 栈，用两个 `std::atomic<bool>` 信号把两个线程的步骤**严格编排**成上面的剧本（不靠运气撞时序）。让受害者的朴素 `compare_exchange_strong(head: A -> 缓存的旧 next)` 在捣乱者把 head 折腾回 `A` 后执行——观察它**错误地成功**，最终 `head` 指向已被弹出的 `B`。打印检查证明链表已损坏。

2. **用版本号修好**（对应第二部分 `// TODO`）：用一个 64 位整数打包 `(32 位下标, 32 位版本号)`，存进 `std::atomic<uint64_t>`（避免依赖平台双字 CAS）。每次成功改动 `version += 1`。在同样的交错下，受害者用**旧的 `(下标, 版本)`** 做 CAS——这次**正确地失败**了，因为 `version` 已被推进。说明 hazard pointer / RCU 是从回收角度解决的另一条路。

### 进阶任务

- **把第一部分改成 `compare_exchange_weak` 并放进真实 CAS 循环**，确认 ABA 与“weak/strong”无关——它是值比较的本质缺陷，换哪个 CAS 都救不了。
- **量化版本号位宽的风险**：32 位 `version` 在极高频改动下理论上会回绕（wrap around）重新撞上同一个 `(指针, version)`。讨论：为什么实践中 48/64 位计数器基本免疫？这和“ABA 只是被降到极低概率、而非数学上不可能”有什么关系？
- **对照 hazard pointer 的思路**（仅口头/笔记，实现留模块 I）：如果受害者在读 `A` 前先把 `A` 登记为 hazard，捣乱者就不会真正复用/释放 `A`，ABA 从源头消失。写清它与版本号方案的取舍：版本号简单但需要双字/打包，hazard pointer 通用但要维护 per-thread 的保护列表。

### 验收点

- 你能**确定性复现** ABA：受害者朴素 CAS“错误地成功”，head 被改成已弹出节点。
- 你能说清 ABA 的根因是“CAS 只比较值、不比较历史”。
- 你能用版本号让同样交错下的 CAS **正确失败**，并解释为什么 `(指针, 版本)` 整体比较能根除 ABA。
- 你能说出 hazard pointer / RCU 是另一类解法，着力点在“安全回收”而非“值比较”。

### 观察点

- 第一部分里，受害者 CAS 的“成功”恰恰是**灾难**——这反直觉的点正是 ABA 的精髓。
- 第二部分里，受害者 CAS 失败后，第一个引用参数被刷新成**最新的 `(下标, 版本)`**，据此就能重新决策。
- 指针复用（同地址再分配）是 ABA 在真实无锁结构里最常见的触发方式，而这又和“何时能安全 delete 节点”直接挂钩——把 G-1 的泄漏伏笔和 ABA 串起来看。

### 常见坑

- **以为换 `compare_exchange_strong` 能避免 ABA**：不能。strong 只是消除伪失败，与“值变回原样”无关。
- **以为加内存序能避免 ABA**：不能。ABA 是**值语义**问题，不是可见性/重排问题；任何内存序都挡不住它。
- **版本号忘了 `+1`**：标签指针方案的全部威力就在“每次改动都推进版本号”，漏掉它就退化回朴素 CAS。
- **把 ABA 和数据竞争（data race）混为一谈**：ABA 里每一步访问都是良好同步的原子操作，没有 UB；它是**逻辑**错误，不是 UB。

### 提示

- 用两个 `std::atomic<bool>`（`victim_loaded` / `attacker_done`）当编排信号，配 `std::this_thread::yield()` 自旋等待，把交错钉死成想要的顺序。
- 打包/解包用位运算：`pack(idx, ver) = (uint64_t(ver) << 32) | idx`。
- 想让“坏掉”可观测，就在最后打印 `head` 指向节点的值，对照它本不该是的那个值。

### 复盘问题

- ABA 的根因用一句话怎么说？为什么换 CAS 种类或加内存序都解决不了？
- 版本号方案为什么有效？它把 CAS 的比较对象从“什么”换成了“什么”？
- 32 位版本号会回绕，这是否意味着 ABA 没被真正解决？“概率降到极低”和“数学上不可能”差在哪？
- hazard pointer / RCU 和版本号分别从哪个角度解决 ABA？各自的代价是什么？

## 练习 G-3：SPSC 环形缓冲

> 代码目录：`exercises/G3_spsc_ringbuffer/`

### 目标

实现单生产者单消费者（single-producer single-consumer，SPSC）的无锁环形缓冲（ring buffer）：定长数组 + 两个原子下标 `head` / `tail`。生产者**只写** `tail`、消费者**只写** `head`，用 release/acquire 配对传递槽位数据的可见性。单生产者单消费者跑通并验证 FIFO（先进先出）顺序与不丢数据。

### 前置理解

- **SPSC 的灵魂假设**：限定**恰好一个**生产者和**恰好一个**消费者。于是可以让 `tail` 只被生产者写（消费者只读它）、`head` 只被消费者写（生产者只读它）。这样**两个写者各自独占一个原子下标，彼此之间没有写-写竞争**——所以 SPSC **不需要 CAS**，普通的 `load`/`store` 就够，只要内存序选对。
- 这与 G-1/G-2 形成鲜明对比：栈的 `head` 有多个写者抢，必须 CAS；SPSC 的每个下标只有一个写者，只需 release/acquire。**“谁来写”决定了你需不需要 CAS**——这是本题最该带走的直觉。
- **release/acquire 配对**（建立在模块 F 上）：
  - 生产者：先把数据写进槽位 `buf[tail]`，**再**用 `release` 提交新的 `tail`。`release` 保证“写槽位”这件事 happens-before 消费者 `acquire` 读到这个 `tail`，于是消费者读到新 `tail` 时，槽位数据**一定可见**。
  - 消费者：用 `acquire` 读 `tail`（与上面的 release 配对），从槽位取数据，再用 `release` 提交新的 `head`，告诉生产者“这一格腾空了”。
  - 读**自己写**的那个下标用 `relaxed` 即可（单写者，读自己的写无需同步）。
- 满/空判定（**留一格法**，最常见）：
  - 空：`head == tail`；
  - 满：`(tail + 1) % N == head`；
  - 代价是浪费一格，实际可用容量为 `N - 1`。好处是用“head 是否等于 tail”就能无歧义区分满与空（否则 `head == tail` 既可能是满也可能是空）。

### 必做任务

1. **实现 push / pop**（对应 `// TODO [必做 1]`）：
   - `push`（仅生产者）：`relaxed` 读自己的 `tail` → `acquire` 读 `head` 做满判定 → 满则返回 false → 写 `buf[tail]` → `release` 提交新 `tail`。
   - `pop`（仅消费者）：`relaxed` 读自己的 `head` → `acquire` 读 `tail` 做空判定 → 空则返回 false → 读 `buf[head]` → `release` 提交新 `head`。
   - 顺序铁律：**先写数据再发布下标**（生产者）、**先读数据再推进下标**（消费者），顺序反了就会读到/覆盖未就绪的数据。

2. **跑通并验证 FIFO 与不丢**（对应 `// TODO [必做 2]`）：生产者按 `0,1,2,…,N-1` 顺序 push（满则自旋让出），消费者按收到顺序检查值是否**严格等于**期望的递增序列，并统计消费总数。结束时断言：消费总数 == 生产总数（不丢），序列严格递增（FIFO 正确）。

### 进阶任务

- **缓存友好化**：把 `head_` 与 `tail_` 用 `alignas(64)` 放到不同缓存行，避免**伪共享（false sharing）**——两个本无关联的下标若落在同一缓存行，一方的写会让另一方的缓存行失效，拖慢吞吐。伪共享是模块 J 的主题，这里先体会“为什么要隔开”。（示例代码已用 `alignas` 演示。）
- **容量取 2 的幂用位运算取模**：把 `% Capacity` 换成 `& (Capacity - 1)`（要求 `Capacity` 是 2 的幂），对比性能。说明为什么取模在热路径上值得优化掉。
- **本地缓存对方下标**：生产者把上次读到的 `head` 缓存起来，只有当“按缓存判满”时才真正 `acquire` 重读一次 `head`，减少跨线程原子读。体会工业级 SPSC（如 folly、moodycamel）为何这么做。
- **思考边界**：如果放宽成多生产者或多消费者，这套“无 CAS”的方案为什么立刻失效？（答案：某个下标出现多个写者 → 写-写竞争 → 必须回到 CAS，甚至要处理 ABA。）

### 验收点

- 单生产者单消费者跑通：消费总数 == 生产总数（不丢），消费序列严格递增（FIFO 正确）。
- 你能说清为什么 SPSC **不需要 CAS**——每个原子下标只有一个写者。
- 你能指出哪一对 release/acquire 在传递槽位数据的可见性，以及“先写数据再发布下标”为什么不能反。
- 你能解释留一格法如何无歧义区分满与空。

### 观察点

- `tail` 的 release 与 `pop` 里 `tail` 的 acquire 配成一对：这是数据从生产者流向消费者的“可见性通道”。
- 读自己写的下标用 relaxed 不会出错——因为同一个线程内的读写本就有序（sequenced-before）。
- 把容量调小、再加点打印，你能看到生产者被“满”挡住自旋、消费者被“空”挡住自旋的交替节奏。

### 常见坑

- **顺序反了**：生产者先发布 `tail` 再写数据（或消费者先推进 `head` 再读数据），消费者就可能读到尚未写入的槽位——经典的发布-订阅顺序错误。
- **用错内存序**：发布下标用了 relaxed，消费者可能看到新下标却看不到新数据（数据竞争/读到旧值）。发布必须 release，读对方下标必须 acquire。
- **满/空判定写错**：不留一格时 `head == tail` 满空不分；或把 `(tail+1)%N == head` 写成 `tail % N == head` 之类的差一错误。
- **拿去做 MPMC**：这套方案**只在 SPSC 下正确**。多生产者/多消费者会让下标出现多个写者，必须改用 CAS（且要防 ABA）。把它误用于 MPMC 会偶发丢数据/重复。
- **在槽位里放需要析构的对象却不管理生命周期**：本题用 `int` 规避了；放复杂对象时要想清楚覆盖旧槽位时的析构/移动语义。

### 提示

- 用 `alignas(64)` 隔开 `head_`/`tail_`（MSVC 会就此给 C4324 填充警告，那正是你要的对齐，可局部 `#pragma warning(disable:4324)`）。
- 生产者满时、消费者空时用 `std::this_thread::yield()` 自旋让出，别忙等烧满 CPU。
- 验证 FIFO 最简单：生产者发严格递增序列，消费者断言“收到的值 == 期望计数器”。
- 元素总数设大（如二十万）才容易在多核上让满/空两条阻塞路径都被走到。

## 做完模块 G 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- **CAS 循环范式**：读旧值 → 基于旧值算新值 → `compare_exchange_weak` 提交，失败时引用参数被刷新成最新值、直接重试；循环里优先用 weak。
- **Treiber 无锁栈**：单个 `atomic<Node*> head` 上做 CAS，push 用 release 发布新节点、pop 用 acquire 消费；它是 lock-free 但非 wait-free。
- **进展保证**：lock-free（系统整体总有线程前进）、wait-free（每线程有界步数完成）、obstruction-free（无争用时单线程能完成），强弱递减。
- **ABA 问题**：CAS 只比较值不比较历史，指针“变回原样”会让 CAS 错误地成功；用带版本号的标签指针根除（`(指针,版本)` 整体比较），或用 hazard pointer / RCU 从安全回收角度解决（模块 I）。
- **SPSC 环形缓冲**：`head`/`tail` 各由一方独占写 → 无写-写竞争 → 不需要 CAS；靠 release（写下标）/acquire（读对方下标）配对传递槽位数据可见性；留一格法区分满空。
- **回收难题**：pop 释放节点会 use-after-free，本模块刻意泄漏规避，完整解法（hazard pointer / RCU）是模块 I 的内容。
