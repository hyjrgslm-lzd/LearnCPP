# 08 原子操作：先确定一次操作的边界

假设服务器需要统计已经处理的请求。一个线程执行 `++count` 时，我们习惯把它看成“一次加一”。但表达式看起来短，不意味着它在并发中不可分割。把 count 改成原子对象，也不意味着之后任意长的一组表达式都自动成为事务。本章从这个最容易混淆的边界开始，建立后面学习内存模型所需的操作词汇。

先读[原子性、RMW 与旗标](../topics/atomics/01-atomic-operations.md)，运行 [E1](../exercises/E1_atomic_basics/README.md)。实验安排两个线程都先读取旧值，再分别写回，所以即使所有访问都用默认 seq_cst，两次“加一”仍然可以只留下 1。这是有定义、可重复的逻辑丢更新。普通 int 无同步并发自增则涉及数据竞争，不能拿它的输出当作可解释的实验结果。随后把复合动作换成 fetch_add，才能在同一个原子对象的修改顺序中保留每次增量。

理解操作边界之后，再读[CAS 循环](../topics/atomics/02-cas-and-minmax.md)并完成 [E3](../exercises/E3_cas_loop/README.md)。CAS 让“如果值仍然是我刚才读到的值，就提交修改”成为一个原子动作。失败并不只是返回 false，它还会更新调用者的 expected；下一轮计算必须使用这个观察值。我们的乘法 Reference 会检查溢出，最大值 Reference 则刻意区分“只保证数值最大值”和“即使数值未变也执行 RMW”的两种契约。

最后读[atomic_ref 的访问阶段](../topics/atomics/03-atomic-ref.md)，运行 [E2](../exercises/E2_atomic_ref/README.md)。这里改变的是存储形式：对象仍然是普通字段，但在受约束的阶段内只经 atomic_ref 访问。对齐、底层对象寿命、全部引用何时销毁，和原子操作本身同样重要。数组首地址对齐并不普遍保证每个元素都符合更严格的原子引用对齐要求。

## 本章完成后的检查

能否解释 `count.store(count.load() + 1)` 与 `count.fetch_add(1)` 的区别？前者包含两个原子动作，中间允许其他操作插入；后者是一个 RMW。加强前者的内存序不会把两步合并。

能否解释“原子类型支持隐式取值”与“课程推荐显式 load”并不矛盾？`atomic<T>` 的取值转换等价于 load，赋值也可调用 store；显式写法的价值是展示访存次数和 memory_order，不是绕过一个不存在的语法限制。

能否解释无锁查询的范围？`is_always_lock_free` 是编译期属性，`is_lock_free()` 是运行期查询。即使底层原子操作无锁，用它写成的自旋锁仍会因持锁线程暂停而阻塞所有竞争者。整个算法的进展保证必须单独证明。

本课程默认 C++23；C++26 的 fetch_min/max 仅在能力宏可用时运行，consume 的变化放在[内存模型](09-memory-model.md)。规范固定使用 [N5050](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/n5050.pdf)；正文给出稳定的条款名，不把滚动草案中可能属于 C++29 的新接口当作本章前提。
