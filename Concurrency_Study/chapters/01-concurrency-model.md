# 01 并发心智模型：分别画出工作、结果和执行者

假设要处理三份输入，得到三个整数，再汇总。最直接的程序是在主线程依次调用三次函数。现在产品希望在计算期间仍能处理别的请求，或者希望用多个核心缩短耗时。这是两个不同需求：一个关注等待期间调用方能做什么，一个关注执行资源能否同时推进工作。先把需求拆开，才能知道需要 future、线程、任务队列，还是根本不需要改变执行方式。

本章沿用 [P1 的调用观察](../exercises/P1_object_lifetime/solution.cpp)，并用 [P2 结果状态](../exercises/P2_result_states/solution.cpp)、[D2 执行策略](../exercises/D2_async_policies/solution.cpp)、[D3 任务批次](../exercises/D3_packaged_task/solution.cpp)展示完整实验路线。此时不要求会写 D2/D3 的实现；先预测它们描述的事件关系，第 02、03 章再逐行解释机制。

## 1. 四个事件不能合成“任务已经好了”

一次任务至少有四个值得分别命名的事件：提交、开始执行、完成、取值。提交意味着工作被某个接口接受；开始执行意味着某个执行者调用了函数体；完成意味着本任务的结果已经确定；取值意味着调用者消费或观察结果。

这四个事件不是在所有接口里都有独立 API。直接函数调用时，调用者进入函数体、执行到返回、得到结果，都发生在同一调用链。D3 把 packaged_task 放进队列则明确分离了它们：主线程保存 future 并入队完成提交；worker 调用 `task()` 才开始执行；被包装函数返回或抛异常后结果通道就绪；主线程 `get()` 才取得值或收到重抛异常。

| 观察 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 队列接受了任务 | 所有权按队列协议完成交接 | worker 已开始执行 |
| 手上有有效 future | 句柄关联一个共享状态 | 结果已经就绪、一定有后台线程 |
| future ready | 有可取得的值或异常 | 一定成功、普通 promise 的生产线程已经结束 |
| future.get 返回值 | 已取得这个结果 | 所有其他任务都结束 |
| worker.join 返回 | 这个线程已结束且关联被解除 | 被它启动或转交的其他独立任务都结束 |

D3 的教学批次先把七个任务全部入队，再创建一个 worker。因此可以确定“提交了七个任务”发生在任何一个任务开始前。不是因为主线程更快，而是程序此时根本还没有调用任务的执行者。这个朴素实验能让我们用很少的代码观察到提交与执行分离。

## 2. 同步与异步描述调用关系

本课程把同步调用理解为：调用方在该调用返回前等待所请求操作完成；异步接口则允许先返回代表未完成操作的句柄或通知约定，之后再观察完成。每次使用“异步”都要指出边界。例如异步发起之后马上调用 `get()`，调用方仍会在那里等待；此前的异步发起没有消失，但这条调用路径可能没有利用任何重叠工作。

future 是结果句柄，不是异步执行的保证。P2 在一个线程中先 `set_value(42)`，再 `get()`，完全不需要后台线程。`std::async(launch::deferred, ...)` 则把函数暂存起来，到第一个非定时等待才在等待线程执行。API 的名字不能代替对执行方式的分析。

也不要把同步原语中的“同步”只理解成“等一下”。`join`、锁交接以及结果通道就绪还承担建立跨线程顺序与可见性的职责。它们使某些对象访问能够合法地接续发生。这一层是 C++ 内存模型意义的同步，与接口是否异步返回是不同维度。

## 3. 并发与并行描述工作如何推进

多个任务的执行区间允许重叠、交错推进时，我们谈并发。单核上轮流推进多个线程也能出现这种关系。多个执行单元在物理时间上同时执行工作时，我们谈并行。线程数、核心数、任务数不能彼此替代：三个线程可能争用一个核心，一个线程也能依次执行很多任务。

并发程序和并行程序都必须正确；并发也可能服务于吞吐和响应时间，并行也需要对象寿命与同步协议。不能把它们记成“前者只关心正确、后者只关心速度”。硬件与操作系统如何调度属于实现和环境事实，标准库接口通常不承诺特定的运行时间、核绑定或加速倍数。

D2 保存三个 async future，并让三个任务等待同一个释放事件。三个发起调用均能返回，释放事件打开前结果都不能就绪。这证明程序允许多个尚未完成任务同时存在；并不证明三条指令曾在三个核心上同一时刻执行，更不证明运行时间是串行的三分之一。

若工作很小，创建执行资源、传递参数、唤醒等待者以及缓存流量可能占主要开销。若工作有依赖或争用同一把锁，增加线程还可能增加等待。性能假设应在后续测量章节保持输入、成功工作量和计时边界一致后检验，本章不把速度写成通过条件。

## 4. 任务是工作，线程是执行资源

P1 的闭包可以表达一个任务，却没有线程。D3 的 packaged_task 保存调用对象和结果通道，也不主动安排执行。`thread`/`jthread` 则管理执行线程的关联关系，入口函数的普通返回值不会自动变成创建者可用的返回值。

一个 worker 可以调用很多 packaged_task。反过来，一个业务任务也可能拆分成多个子任务。因此“有一千份工作”不自动推出“创建一千个线程”。后续线程池章节会在任务与有限执行资源之间增加调度策略；本章只需要先建立这两个层次。

实际成本不能仅靠“线程重、任务轻”四个字决定。任务捕获大型数据也可能很贵；线程的栈、启动及调度成本取决于平台。先画清楚哪个对象拥有输入、谁调用它、谁保存结果，再评估这些成本。

## 5. 共享状态与消息交接：重点是访问契约

把值经 promise 传给 future 是一种交接方式，但标准库内部依然通过共享状态实现。队列消息也可能只是指向同一可变对象的指针。把代码命名为“消息传递”或“sender”并不会自动消除数据竞争；要检查消息携带的对象到底是副本、独占所有权，还是借用路径。

本课程优先选择能够解释清楚的所有权边界。独立输入和独立输出可以使线程各自工作；真正共享可变状态时，再用合适的协议连接访问。P1 的值捕获与引用捕获，正是这一设计选择的单线程原型。

在 C++ 中，两次求值可能冲突，例如一方修改一个内存位置、另一方读取它，或一方开始/结束相应对象寿命。两个潜在并发的冲突操作，至少一个不是原子操作，且二者之间没有所需的 happens-before 顺序，就可能形成数据竞争，导致未定义行为。这里应从内存位置和求值看问题，不能只凭“两个变量名不同”判断无关。精确定义见 [数据竞争条款](https://eel.is/c++draft/intro.races)，固定检查基准为 [N5050](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/n5050.pdf) `[intro.races]`。

两个对已经安全发布、仍存活对象的纯读取不会相互形成读写冲突，但“两个读取永远安全”省略了初始化、寿命及隐藏修改条件。例如另一个线程正在析构对象，读取仍可能出错；一个看似 const 的成员函数也可能修改 mutable 缓存。原子标志也只保证该原子操作的相应规则，不会自动保护旁边的普通对象。

## 6. 用偏序证明，而不是用墙钟猜测

单线程内部仍有标准规定的求值顺序，并发没有让全部顺序失效。例如两个连续完整表达式之间有顺序；但一个表达式的不同子求值不一定按从左到右执行，应查具体表达式规则。编译器优化仍必须遵守 C++ 抽象机对合法程序的要求，不能简单说“编译器不知道有别的线程”。

跨线程可以通过 synchronizes-with 关系连接顺序。第 03 章的 A3 用最简单的链条传异常：

```text
worker:  捕获异常 -> 写 captured -> 线程结束
                                      |
                                      | join 同步
main:                            join 返回 -> 读 captured -> 重抛
```

worker 的写在结束之前，成功 join 返回在主线程读之前，中间有标准指定的同步边，所以这次读可以安全取得写入结果。`captured` 无需额外变成原子；这份结论依赖“一位 worker 写，主线程只在 join 后读”，不是 exception_ptr 类型本身允许随意并发赋值。

锁的交接、future 结果就绪的观察，以及满足条件的 release/acquire 通信也能建立相应边。后续章节会精确推导。CPU 缓存、写缓冲与执行优化有助于理解实现成本，但“缓存还没刷新”不能替代语言层证明。若程序已经有数据竞争，观察旧值或新值都不能使它重新成为合法程序。

`sleep_for` 只表达等待一段时间的请求，不连接另一个线程的写与本线程的读。`yield` 也不建立发布关系。日志的时间戳只能记录本次观察，日志工具内部的锁还可能改变交错。因此本课程先给出同步边，再用输出说明运行结果；不会用“睡了 100ms，所以对方已经做完”作为证明。

## 7. 等待与进展保证要看完整操作

`get()`、`join()`、`mutex::lock()` 都可能等待某个条件，但“阻塞”不保证实现一定让线程进入内核睡眠。它可能先短暂自旋，也可能条件早已满足而立即返回。接口的等待契约和实现采用的机制需要分开。

“不等待数据”也不等于无锁。队列 `try_pop` 可以只在有元素时成功，却仍然要获取 mutex；样章 [Q0 基线](../topics/queues/01-mutex-baseline.md) 正好展示这种情况。lock-free 与 wait-free 是对算法进展的更强要求；其中 lock-free 不能推出每个调用者都不饥饿，wait-free 要求更强的逐操作完成界限。一个 CAS 循环外包了可能阻塞的分配器，并不能仅凭用了 CAS 就宣称完整操作无锁。标准背景见 [进展保证](https://eel.is/c++draft/intro.progress)。

本批次依赖标准库线程与阻塞等待，不宣称 lock-free，也不承诺固定最大延迟。实验采用有限工作量；对于本应结束但因改错协议而卡住的程序，用进程级超时报告失败，而不是继续加 sleep。

## 8. Part 与自测答案

**Part 1：把 P1 的一次 invoke 画成四个事件。** 这里没有独立排队；调用进入函数体，完成之后调用返回并给出结果。仅保存闭包不算执行，闭包创建可能复制输入对象。

**Part 2：预测 P2 为什么能在没有第二线程时得到 future 结果。** promise 与 future 连接的是结果状态，谁设置它与谁读取它可以是同一线程。必须先设置再阻塞等待，否则若只有自己负责设值，就没有任何执行者能使等待完成。

**Part 3：读 D2 `part2_temporary_and_retained`，说明保留句柄改变了什么。** 临时 async future 的最后释放位于每次完整表达式末尾，形成任务完成后才能继续下一次发起的边界；保留句柄把该边界后移，允许三个未完成任务都提交。Reference 检查这个事件关系，不检查加速。

**Part 4：读 D3 `part2_and_3_batch_queue`，为什么当前 queue 不需要 mutex？** 提交全部发生在创建 worker 之前；执行期间只有一个 worker 访问 queue；主线程在 join 后才检查它。访问阶段由线程启动与 join 连接。若新增并发生产者或第二个消费者，原契约不再成立，必须改用队列章节的同步实现。

**如果测试跑一万次都通过，就证明没有危险交错了吗？** 没有。运行只能覆盖实际调度；协议证明需说明所有允许的交错下，访问的对象活着、冲突访问有序、结果状态只完成一次。测试补充证据，不能替代这些前提。

做题时固定画五项：执行者、对象拥有者、同步边、值或异常的流向、销毁与退出位置。随后问：谁还能修改它？失败时谁唤醒等待者？等待者是否挡住唯一能完成它的人？这些问题会比记住更多 API 名字更早暴露错误。
