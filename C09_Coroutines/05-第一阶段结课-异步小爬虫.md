# 05 第一阶段结课：异步小爬虫

这个项目把 A/B/C 的局部能力拼成一条小流水线：并发抓取几个模拟 URL，逐行解析响应内容，最后汇总报告。它不做真实 HTTP；真实网络会把注意力从协程拓扑上拿走。这里所有输入都在 [url_table.hpp](exercises/Capstone1_async_crawler/url_table.hpp)，解析器在 [parser.hpp](exercises/Capstone1_async_crawler/parser.hpp)，项目入口在 [main.cpp](exercises/Capstone1_async_crawler/main.cpp)，可运行参考在 [solution.cpp](exercises/Capstone1_async_crawler/solution.cpp)。

先画拓扑，再写代码：

```text
main
  -> std::stop_source src
  -> watchdog thread after 200ms: src.request_stop()
  -> sync_wait(aggregate(records, src.get_token()))

aggregate
  -> co_await when_all_fetch(records, token)
       -> task_scope scope
       -> spawn fetch_into(record[0], token, out[0])
       -> spawn fetch_into(record[1], token, out[1])
       -> spawn fetch_into(record[2], token, out[2])
       -> scope.join()
  -> for each successful fetch_result
       -> capstone1::parse_lines(body) generator
       -> aggregate counters
  -> co_return report
```

这张图里有五种对象：root task、多个 fetch task、一个 `task_scope`、一个 stop state、多个 parser generator。每种对象都要能回答“谁启动它、谁等待它、谁持有它需要的状态”。

## 一、输入表：固定数据让时序可预测

项目使用三条模拟 URL：

```text
data/1.csv -> 150ms -> Alice/Bob
data/2.csv -> 100ms -> Carol/Dave
data/3.csv -> 300ms -> Eve/Frank
```

200ms 超时下，前两条通常完成，第三条被取消。这个设置让并发和取消都有可观察结果。若全部延迟都小于超时，你看不到 stopped 路径；若全部大于超时，又看不到部分成功聚合。

## 二、fetch：一个 URL 一条 lazy task

fetch task 接收 `UrlRecord` 和 `std::stop_token`：

```cpp
coroutine_study::lazy_task<fetch_result>
fetch_one(worker_group& workers, UrlRecord rec, std::stop_token st) {
    if (st.stop_requested()) co_return stopped(rec.url);
    co_await timer_awaiter{workers, rec.latency, st};
    if (st.stop_requested()) co_return stopped(rec.url);
    co_return ok(rec.url, rec.body);
}
```

两次检查分别覆盖两个窗口。第一次覆盖“还没开始等就已经超时”；第二次覆盖“等待期间超时”。`timer_awaiter` 自己也观察 token，让睡眠能尽快醒来并恢复协程。恢复后 fetch 决定返回 `ok` 还是 `stopped`。

这里的 stopped 是报告状态。超时是项目允许的结果，报告保留其它已经成功完成的 URL。

## 三、parse：generator 逐行交付记录

parser 接收一段响应字符串，返回 `std::generator<capstone1::Record>`。`parse_lines(std::string body)` 按值保存响应内容，因为 generator 构造后会延迟到遍历时才执行，调用点传入的临时字符串可能已经离开作用域。它跳过 header，按行拆分；格式正确时 yield `Record{name, score, true}`，格式错误时 yield `ok=false` 的记录并继续。

generator 在这里有两个作用。第一，它把“解析一行”和“消费一行”交替起来，和 A1 的 `read_lines()` 一致。第二，它让 aggregate 的代码只关心当前记录，不需要先构造一个完整 vector。

```cpp
for (auto row : capstone1::parse_lines(fetch.body)) {
    if (row.ok) {
        ++report.total_lines;
        report.total_score += row.score;
    } else {
        ++report.err;
    }
}
```

本项目数据很小，即使用 vector 也能工作；选择 generator 是为了练习按需生产模型。后续接真实流式下载时，这个结构可以继续扩展。

## 四、when_all_fetch：并发启动，等齐结果

如果逐个 `co_await fetch_one`，总耗时接近 `150 + 100 + 300ms`，超时行为也会被串行等待扭曲。项目需要并发发起全部 fetch，然后等齐已经完成或被取消的结果。

starter 和 reference 都使用同一形状的 `timer_awaiter{workers, delay, token}`。`worker_group` 拥有后台等待线程并在流程结束时 join；`stop_token` 让等待循环能在超时后尽快恢复 fetch。reference 中 `when_all_fetch` 建立一个结果数组 `out`，再用 `task_scope` 启动 N 个 `fetch_into`：

```text
out[0], out[1], out[2] 预先分配
scope.spawn(fetch_into(record[0], out, 0))
scope.spawn(fetch_into(record[1], out, 1))
scope.spawn(fetch_into(record[2], out, 2))
scope.join()
co_return out
```

每个 task 只写自己的下标，没有共享 push_back 竞争。`scope.join()` 是合流点：它保证所有 fetch task 已经到达完成状态，aggregate 随后可以安全读取 `out`。

`worker_group` 负责 timer awaiter 的后台等待线程；`task_scope` 负责 fetch task 的生命周期。两者职责不同：一个模拟等待资源，一个收束协程任务。

## 五、超时：一个 stop state 控制全局

main 创建一个 `std::stop_source`，把 token 传给 aggregate，再由 aggregate 传给所有 fetch。watchdog 在 200ms 后调用 `request_stop()`。

```text
watchdog request_stop()
  -> stop state becomes requested
  -> timer awaiter observes token and resumes fetch
  -> fetch_one sees token after await
  -> returns fetch_status::stopped
  -> aggregate counts stopped URL
```

取消从共享 stop state 传播，再由 awaiter 和协程体协作响应。这个项目最重要的验收点之一，是第三条 URL 超时后，前两条已经完成的 URL 仍然进入报告。

## 六、aggregate：汇合后只处理成功结果

aggregate 是 root task 的主要业务流程：

1. 记录开始时间。
2. `co_await when_all_fetch(...)` 得到每个 URL 的 fetch_result。
3. 遍历结果，按 `ok/stopped/error` 分类。
4. 对 ok 的 body 调用 parser generator，累计行数和分数。
5. 计算整体耗时，`co_return report`。

这段代码展示了第一阶段的组合方式：`co_await` 负责异步阶段连接，`generator` 负责同步惰性解析，`stop_token` 负责超时传播，scope 负责动态 fetch 的生命周期。

## 七、建议实现顺序

按下面顺序填 starter，少走弯路：

1. 先补 `fetch_one` 的两次 stop 检查，保持串行占位也能看到状态。
2. 补 `parser.hpp`，让格式正确行产生 name/score，错误行产生 `ok=false`。
3. 把 `when_all_fetch` 从串行 `sync_wait` 改成 scope 并发，结果数组按下标写入。
4. 把 watchdog 阈值改回 200ms，确认慢 URL 进入 stopped。
5. 在文件顶部注释补全拓扑图，标出 owner 和 join 点。

完成后，对照 reference 的断言：总 URL 数为 3，成功 2，stopped 1，总解析行数 4，总分 343，整体耗时低于串行总和。

## 项目完成后

你应该能不看代码说明：

- 每个 fetch 协程何时创建、何时第一次启动、由哪个 scope 收束。

  **答案解析：** `aggregate` 调用 `when_all_fetch` 后，`when_all_fetch` 为每条 URL 创建一个 `fetch_into` task，并用 `scope.spawn(...)` 启动。真正执行发生在 scope 管理的任务被驱动时，`fetch_one` 内部的 timer worker 只负责等待后恢复对应协程。`scope.join()` 是 fetch 分支全部收束的点，之后 aggregate 才消费结果数组。

- stop token 从 main 经过 aggregate 传到每个 fetch 的路径。

  **答案解析：** main 创建 `std::stop_source src`，把 `src.get_token()` 传给 `aggregate(workers, recs, token)`。aggregate 再把同一个 token 传给 `when_all_fetch`，每个 `fetch_into`/`fetch_one` 都拿到这份 token。watchdog 200ms 后调用 `src.request_stop()`，所有持有同一 stop state 的 token 都能在检查点看见请求。

- 超时请求为什么不会破坏已经完成的结果。

  **答案解析：** 已完成的 100ms 和 150ms fetch 已经把 `FetchStatus::Ok` 与 body 写进自己的下标槽；200ms 的 stop 请求只影响之后仍在等待或后续检查 token 的任务。300ms URL 在 timer 等待中观察到 stop 后返回 `Stopped`，不会覆盖前两条 `Ok` 结果。aggregate 按状态分类，所以成功报告和 stopped 计数分开累加。

- parser generator 为什么是按行推进，何时销毁它的协程状态。

  **答案解析：** `parse_lines(std::string body)` 按值接收 body，generator 帧持有响应正文；aggregate 的 range-for 每请求一行，parser 才从上一个 `co_yield` 后继续解析下一行。这个 generator 对象只活在处理某个 `Ok` body 的循环期间，循环结束或对象析构时销毁它的协程状态。按值持有 body 可以避免循环还没结束时底层字符串失效。

- 报告中的每个计数来自哪条完成路径。

  **答案解析：** URL 总数来自输入表大小 3；成功数来自两个 `FetchStatus::Ok` fetch；stopped 来自 300ms URL 被 200ms watchdog 取消；错误数为 0。解析成功行数只统计前两条成功 body 中的有效数据行：Alice、Bob、Carol、Dave 共 4 行。总分是 85 + 92 + 78 + 88 = 343。

这些都能说清，第一阶段就达标。后续模块会把本项目里使用的教学 runtime 拆开：promise hook、awaiter 变换、allocator、symmetric transfer、sender bridge。
