# 02 模块 A：三关键字与最小协程

模块 A 的目标是把 `co_yield`、`co_return`、`co_await` 三个关键字和可观察的执行过程连起来。你不需要先记完整 promise hook 表；先看每个关键字让协程“暂停、交付、继续”的哪一部分发生变化。

本模块依赖 [00 预备知识](00-预备知识-执行模型与标准库.md) 的 future 与 generator 模型，也依赖 [01 心智模型](01-心智模型.md) 对协程帧、promise 和非拥有 handle 的解释。做题时请同时打开对应 starter 和 reference，不要只看任务清单。

<a id="a1"></a>

## 一、`co_yield`：消费者推进，生产者才前进

`std::generator<T>` 把协程包装成一个 input range。调用 generator 函数时，返回对象先持有一份协程状态；协程体通常还没跑到第一行。消费者调用 `begin()` 时，generator 第一次恢复协程，协程执行到第一个 `co_yield`，把当前值交给迭代器，然后暂停。

可以把一次迭代看成这条链：

```text
main 构造 generator
  -> generator 持有协程状态，协程体待启动
main 调用 begin()
  -> 协程执行到第一个 co_yield
  -> 当前值保存在 generator promise 中
main 解引用迭代器
  -> 读取当前值
main 执行 ++it
  -> 协程从上一个 co_yield 后继续
  -> 运行到下一个 co_yield 或结束
```

`co_yield` 交出一个当前值并暂停。下一次推进迭代器时，协程从 `co_yield` 后面的语句继续执行。因此，在协程体的 `co_yield` 前后打日志，再在 main 的循环中打日志，能直接看到生产者和消费者交替推进。

### 有限 Fibonacci

有限 Fibonacci 的状态非常小：`a` 是当前要产出的数，`b` 是下一个数。每次 `co_yield a` 后，协程暂停；恢复后才计算下一对状态。

```cpp
std::generator<int> fibonacci(int n) {
    int a = 0;
    int b = 1;
    for (int i = 0; i < n; ++i) {
        co_yield a;
        int next = a + b;
        a = b;
        b = next;
    }
}
```

请注意 `a`、`b`、`i` 都跨越了挂起点。`co_yield` 暂停后，这些变量保存在协程状态里。消费者保持当前位置时，这些状态保持原样；消费者推进一次，生产者最多跑到下一次 yield。

在 [练习 A-1](exercises/A1_first_generator/README.md) 中，先把 starter 的占位 `0..n-1` 改成上面的状态转移。然后预测：`auto gen = fibonacci(10);` 后，协程体日志是否出现；第一次进入循环前，哪一步会触发首次恢复。

**答案解析：** `auto gen = fibonacci(10);` 后不应出现协程体日志，因为 generator 函数调用只创建返回对象和协程状态。第一次恢复通常发生在消费端取得起始迭代器时，也就是 range-for 展开里的 `begin()`；协程运行到第一个 `co_yield` 后暂停，把第一个值交给迭代器。之后每次推进迭代器，才会从上一个 yield 后继续。

参考实现 [A1 solution.cpp](exercises/A1_first_generator/solution.cpp) 用 `resumed` 计数验证了这点：构造 generator 后计数仍为 0，遍历后变为 1。

### 无限序列与 `views::take`

无限 generator 只是把循环条件换成 `for (;;)`:

```cpp
std::generator<int> fibonacci_inf() {
    int a = 0;
    int b = 1;
    for (;;) {
        co_yield a;
        int next = a + b;
        a = b;
        b = next;
    }
}
```

它可以存在，是因为 generator 按需推进。无限序列本身不会一次性算完；真正危险的是消费者写出没有边界的循环。`std::views::take(10)` 给消费端设置最多交付十个元素的边界。不同 range adaptor 和循环展开细节下，为确认结束状态可能还会尝试推进底层迭代器；所以不要用 `take(10)` 推断“生产者只恢复十次”。要精确观察恢复次数，请单独做计数实验，或用手写循环在拿到第十个值后立即 `break`。

这和 [00 的 generator 模型](00-预备知识-执行模型与标准库.md#generator-model) 一致：当前值只在迭代器推进时改变。A1 reference 用 `fibonacci_inf() | std::views::take(10)` 验证前缀；推进次数的因果观察放在有限 generator 日志或手动 `break` 实验里做。

### 逐行文本

`co_yield` 交付的类型不限于数字。逐行读取最适合练 generator，因为每一行天然是一个元素。

```cpp
std::generator<std::string> read_lines() {
    co_yield "alpha";
    co_yield "beta";
    co_yield "gamma";
}
```

真实文件读取时，数据来源可能是文件、网络缓冲或内存字符串；本题只模拟几行文本。目标是观察“行号推进一次，生产者才产出下一行”。如果后续要重复遍历这些行，就把 generator 的产出收集到 `std::vector<std::string>`，这对应 [00 的 materialization](00-预备知识-执行模型与标准库.md#materialization)。

## 二、`co_return`：结果进入 promise，返回对象稍后取走

普通函数 `return value` 直接把值交回当前调用表达式。协程里的 `co_return value` 先调用 promise 的 `return_value(value)`，再进入 `final_suspend`。调用方在协程函数调用点拿到返回对象，比如 `coroutine_study::lazy_task<int>`；结果值由这个返回对象的消费动作稍后取出。

本仓库的 `lazy_task<T>` 在 [lazy_task.hpp](exercises/include/coroutine_study/lazy_task.hpp) 中。它是教学用的 move-only task。重要契约如下：

- `initial_suspend()` 选择挂起，所以创建 task 时协程体不执行。
- `co_return` 的值存在 promise 中。
- `final_suspend()` 通知等待者，协程帧在结果被消费前保持存在。
- `sync_wait(std::move(task))` 消费 task：启动 root 协程一次，等待完成通知，再取值或重抛异常。

最小练习是三步值变换：

```cpp
coroutine_study::lazy_task<int> compute_async(int x) {
    int step1 = x + 10;
    int step2 = step1 * 2;
    int step3 = step2 - 5;
    co_return step3;
}

auto task = compute_async(5);                 // 协程体还没执行
int value = coroutine_study::sync_wait(std::move(task));
```

你要观察两个时刻。第一，构造 `task` 后，协程体日志没有出现。这说明调用协程函数只创建了协程状态和返回对象。第二，`sync_wait` 后三步日志依次出现，最终值回到调用方。这个差异对应 [00 的 deferred 惰性求值](00-预备知识-执行模型与标准库.md#deferred-shared)，但 task 的启动和完成由协程 promise/awaiter 协作完成。

在 [练习 A-2](exercises/A2_co_return_lazy_task/README.md) 中，请同时写一个普通 `compute_sync`。普通函数调用即执行；lazy task 创建后待启动。把两条日志放在一起，惰性启动就很直观。

所有权也要一起看。`lazy_task` 是 move-only，因为一个协程帧只能有一个明确拥有者。`coroutine_handle` 可复制，但它本身非拥有；拥有权由 `lazy_task` 这种返回对象定义。`sync_wait(std::move(task))` 消费 task 后，原对象不再持有可继续使用的结果入口。

## 三、`co_await`：把暂停点交给 awaiter 管

`co_await expr` 会把 `expr` 转换成 awaiter，然后依次调用三方法：

```cpp
if (!awaiter.await_ready()) {
    awaiter.await_suspend(current_coroutine_handle);
    // 当前协程暂停，稍后被某处 resume
}
auto result = awaiter.await_resume();
```

三方法各自存在的原因很具体：

- `await_ready()`：给已经完成的操作一条快速路径。返回 `true` 时不挂起，也不会调用 `await_suspend`。
- `await_suspend(h)`：当前协程已经稳定暂停，awaiter 拿到非拥有 handle，可以把它交给 worker、事件循环或回调，决定后续在哪里恢复。
- `await_resume()`：协程恢复后取出结果；它的返回值就是 `co_await` 表达式的值，异常也通常在这里重新抛出。

### 为什么 future 需要包装

`std::future<T>` 的标准接口没有协程 awaiter。用户代码的扩展点放在自己的包装类型或包装函数上。本题使用用户命名空间里的包装函数：

```cpp
auto fut = std::async(std::launch::async, [] { return 42; });
int result = co_await await_future(std::move(fut));
```

包装对象持有 `std::future<T>`，再提供 awaiter 三方法。这样调用点清楚表达“我正在把 future 适配为协程可等待对象”。

### ready 快路径

如果 future 已经 ready，`await_ready()` 返回 `true`。协程不会挂起，`await_suspend()` 不执行，后面直接调用 `await_resume()`。

```cpp
bool await_ready() {
    return fut.wait_for(0s) == std::future_status::ready;
}
```

这条路径看起来普通，但很重要。它避免为已经完成的结果启动 worker，也避免无意义的线程切换。A3 reference 用 `std::promise<int>` 先 `set_value(21)`，再 `co_await` 它的 future，断言 ready 路径不会进入 suspend。

### 异步等待路径

未 ready 的 future 需要等待。等待线程可以阻塞在 `future.get()` 或 `wait()` 上；为了不阻塞当前协程的启动线程，本题把等待交给外部拥有的 `worker_group`。worker 完成后调用 `h.resume()`，协程恢复点就运行在这个 worker 线程上。

```text
协程线程：
  co_await await_future(fut)
  await_ready -> false
  await_suspend(h) 把 h 和 future 交给 worker
  返回调用方

worker 线程：
  future.get()
  保存值或异常
  h.resume()
  协程进入 await_resume()
```

这里的 `h` 是非拥有句柄。它允许 worker 恢复协程，但不代表 worker 拥有协程帧。协程帧仍由 task/`sync_wait` 的运行时结构管理。worker 的生命期也要有 owner；本题用 `worker_group` 收集 `std::jthread` 并在结束前 join，不使用 `detach()`。

### 异常路径

`std::future<T>::get()` 如果发现共享状态里保存了异常，会重新抛出。awaiter 可以在 worker 中捕获异常并保存 `exception_ptr`，然后恢复协程；`await_resume()` 再重新抛出。这样，异常出现在协程体的 `co_await` 表达式位置，父 task 的 `unhandled_exception()` 会继续保存它，最后由 `sync_wait` 抛给 main。

A3 reference 覆盖三条路径：未 ready future 跨线程恢复、ready future 跳过 suspend、future 异常传播。未 ready 路径用 `std::promise<void>`/`std::future<void>` 做启动信号：producer 线程先等待信号，awaiter 进入 `await_suspend` 并记录状态后再放行 producer，因此 `await_ready()` 必定先观察到未完成状态。reference 的 `await_future(fut, workers, state)` 比 starter 多两个教学参数：`workers` 是等待线程 owner，`state` 保存观测线程、ready 标记、结果或异常。starter 先完成 `await_future(std::move(fut))` 这个用户包装入口，再对照 reference 理解 owner/state 如何补齐观测和生命周期。

## 模块 A 完成后

做完 A1/A2/A3，你应该能用同一套语言解释三件事：

- `co_yield` 让 generator 在迭代器推进时生产下一个值，局部状态跨 yield 存活。

  **答案解析：** A1 的 Fibonacci 中，`a`、`b`、`i` 都跨过 `co_yield`，所以它们必须保存在 generator 的协程帧里。调用 generator 函数只得到 range 对象；`begin()` 或 `++it` 恢复生产者，生产者跑到下一次 `co_yield` 后再次停住。结论是消费端每推进一次，生产端最多交付一个新值。

- `co_return` 把最终结果交给 promise，再由 task 的消费者取走。

  **答案解析：** A2 的 `compute_async(5)` 三步结果是 `(5 + 10) * 2 - 5 = 25`。这个 25 不会直接回到调用表达式，而是先经 `promise.return_value(25)` 存进协程状态，随后停在 `final_suspend()`。`sync_wait(std::move(task))` 启动并等待 task 完成后，才从 promise 里取出这个值。

- `co_await` 把挂起点交给 awaiter，awaiter 决定是否挂起、交给谁恢复、怎样返回值或异常。

  **答案解析：** A3 的 ready future 走 `await_ready()==true`，直接进 `await_resume()`；未 ready future 走 `await_suspend(h)`，把非拥有 handle 交给 `worker_group` 里的 worker，worker 等到 future 完成后 `resume()`。值和异常最后都在 `await_resume()` 回到协程体，所以 `co_await` 这一行同时是暂停点、恢复点和结果入口。

继续进入 [模块 B](03-模块B-generator与task的使用.md) 前，请打开每个 reference，找出协程帧 owner、非拥有 handle 的暂存位置、结果通道和恢复线程。只会写语法还不够；能画出这些关系，才算通过模块 A。
