# 00 预备知识：执行模型与标准库

学习协程时，你会反复遇到两类问题：一段工作何时执行，以及执行产生的结果怎样交给下一段代码。这一章先借助普通函数、`std::future` 和 `std::generator` 建立可以亲手观察的模型。之后的协程语法会连接到这些已经熟悉的行为上。

这里假定你能阅读函数、类、模板和基本 RAII 代码。涉及线程、异步结果、迭代器和对象生命周期时，正文会逐步补足本章所需的知识。阅读一个小节后，就运行相应实验；带着已经看到的现象继续往下读。

<a id="execution-model"></a>

## 一、从一次普通函数调用理解执行与结果

### 调用方等待的究竟是什么

考虑一个普通函数：

```cpp
int calculate(int input) {
    int adjusted = input + 10;
    return adjusted * 2;
}

int answer = calculate(5);
std::cout << answer;
```

执行线程先进入 `calculate`，算出结果并返回，随后执行输出语句。这形成了一个熟悉的约定：函数返回时，这次计算已经结束，调用表达式提供最终结果。局部对象 `adjusted` 的有效期覆盖这次函数执行。

如果计算中加入一次等待网络响应的操作，调用方就要等这次响应结束，才能继续执行输出。**阻塞**描述的是执行线程在等待期间无法继续推进当前调用链的状态。线程即使由操作系统暂时调度出去，调用方的后续语句仍然在等。

有些程序希望在网络结果到达前继续处理别的事情。这需要把“发起工作”和“获得结果”分成两个时刻：发起时先交还一个结果入口，完成时再通过这个入口传递值或错误。这个入口可以是回调，也可以是 future。

### 同步、异步、并发和并行

这几个词描述不同的观察角度。先看具体问题，再选择相应术语：

| 你在判断什么 | 对应概念 | 一个具体例子 |
| --- | --- | --- |
| 调用返回时是否已经取得此次操作的最终结果 | 同步完成 | `calculate(5)` 返回 `30` |
| 发起操作后，最终结果是否通过后续步骤交付 | 异步接口 | 提交读取请求，完成时调用回调 |
| 多项工作是否处在相互重叠的推进区间 | 并发 | 单线程事件循环轮流处理多个连接 |
| 多项工作是否在同一时刻实际执行 | 并行 | 两个 CPU 核心同时计算两块数据 |
| 当前线程是否停在等待操作里 | 阻塞等待 | 在结果尚未就绪时调用 `future.get()` |

因此，异步接口可以由单线程事件循环实现，也可以由工作线程完成。线程数量属于执行方案；结果何时、通过什么接口交付属于调用约定。掌握这两个角度，后面就能分别讨论协程的挂起方式与运行它的线程。

### 回调怎样保存后续工作

假设某个库提供下面的接口。此处用于说明接口形状，具体实现会在 B3 中出现：

```cpp
// 完成后把结果传给 on_complete。
void start_calculation(int input, std::function<void(int)> on_complete);

start_calculation(5, [](int result) {
    std::cout << result;
});
```

原先写在函数调用后面的输出逻辑，被放进回调对象。库保存这个对象，计算完成后调用它。于是“后续要做的事情”也成为一个有生命周期的对象。

如果回调需要外层变量，就必须同时考虑那些变量的存活时间。按值捕获会把相应值保存进闭包对象；按引用捕获保存的是对外部对象的访问关系，外部对象需要活到回调使用结束。A3 和 B3 会进一步观察：恢复协程的工作，也需要这种明确的保存位置与存活关系。

## 二、future：先取得入口，随后取得结果

### 提供方、共享状态和消费方

`std::promise<T>` 和 `std::future<T>` 把结果传递拆成两端：promise 提供结果，future 消费结果。它们通过一个**共享状态**连接。共享状态可以保存一个 `T`，也可以保存一次异常。

```text
提供方                           共享状态                         消费方
promise<int> -- set_value(42) --> [值或异常，就绪标记] <-- get() -- future<int>
```

用一段完全在当前线程执行的代码，就能建立这条关系：

```cpp
std::promise<int> producer;
std::future<int> result = producer.get_future();

producer.set_value(42);
int value = result.get();
```

`get_future()` 为该 promise 取得消费端。`set_value(42)` 在共享状态中存入结果，并使状态就绪。`get()` 等待状态就绪，然后取出结果。这个例子中的值已经提前提供，所以取值可以立即完成。

当提供方位于另一线程时，连接关系保持相同。值存入与消费方成功等待之间具有标准规定的同步关系，因此消费方能够看到提供的结果。future 负责这条结果通道；线程的创建和工作安排由使用它的代码决定。

### valid 与 ready：两个不同的问题

`valid()` 回答“这个 future 是否关联着共享状态”。**ready** 回答“这份共享状态是否已经准备好了值或异常”。刚从 promise 取得的 future 可以同时满足 `valid() == true` 和尚未 ready。

| 操作 | 回答的问题或产生的效果 |
| --- | --- |
| `valid()` | 当前对象是否关联共享状态 |
| `wait()` | 等待共享状态就绪，保留结果供随后消费 |
| `wait_for(duration)` | 有界等待，报告 `ready`、`timeout` 或 `deferred` |
| `get()` | 等待并消费值，或重新抛出共享状态中的异常 |

`wait_for(0ms)` 适合观察当前状态。零时长表示检查时无需等待一段指定时长；对于 deferred 工作，它会报告相应策略状态。

`future<T>` 提供一次结果消费。正常完成 `get()` 后，这个 future 已释放自己的共享状态关联，`valid()` 变为 `false`。如果 `get()` 重抛的是共享状态中保存的异常，也会完成这次消费。接下来可以销毁该对象，或给它移动赋入另一份 future；下一次取值需要一个有效的结果入口。

## 三、async：把结果通道连接到实际执行

### 显式选择执行策略

`std::async` 接收一个可调用对象，返回代表其结果的 future。可调用对象的返回值会进入共享状态；它抛出的异常也会进入同一状态。

```cpp
auto result = std::async(std::launch::async, [] {
    return 6 * 7;
});
int answer = result.get();
```

显式指定 `std::launch::async` 时，可调用对象按独立执行线程的语义运行。调用方可以先做别的工作，最后在需要结果的位置调用 `get()`。如果那时结果尚未就绪，`get()` 会阻塞调用它的线程。

另一个策略是 `std::launch::deferred`。此时工作先被保存起来，第一次对这个状态执行非定时等待的函数才触发求值，求值发生在执行这次等待的线程上。`get()` 和 `wait()` 都能触发它；`wait_for()`、`wait_until()` 会报告 deferred 状态。

省略策略参数时，标准接口允许从 async 与 deferred 中选择。实验需要明确观察一种行为时，写出策略可以让结果更容易解释。

### 用信号控制时机

下面这段代码为计算设置了一个明确的开始信号：

```cpp
std::promise<void> release;
auto result = std::async(std::launch::async,
    [gate = release.get_future()]() mutable {
        gate.wait();
        return 42;
    });

auto before = result.wait_for(std::chrono::milliseconds{0});
release.set_value();
int value = result.get();
```

`promise<void>` 只传递“已经完成”这个事件。lambda 按移动捕获取得它的 future，工作线程进入 `gate.wait()` 后，必须等 `release.set_value()` 才能继续。

调用方观察 `result` 时，放行语句尚未执行，所以计算结果必定尚未完成。这个因果关系来自代码中的信号关系，与操作系统此刻是否已经调度工作线程无关。

lambda 的 `mutable` 允许修改捕获对象；这里捕获的 future 拥有这一次等待入口。future 采用移动语义，把消费权从临时表达式转移到闭包对象中。

### 练习 P-1，Part 2：观察真正的异步执行

在第二个作用域完成计算结果和线程 ID 的观察。先记录状态，随后发出信号，最后取值。参考实现输出：

```text
P1/2 pending_before_release=true value=42 other_thread=true
```

理解这行输出需要把两件事连起来：promise 信号决定计算何时允许完成，async 策略决定计算在哪个执行线程中发生。`get()` 则把调用方与最终结果重新汇合。

这个结构也带来一个直接的顺序要求：调用方需要先放行再取值。如果它先阻塞在 `result.get()`，负责放行的后续语句就失去了执行机会。画出“谁等待谁”的箭头，可以很快找出这种相互等待。

### 结果入口也有生命周期

作用域结束时，future 会释放它持有的共享状态。由 `std::async` 的 async 策略创建、仍在执行的工作，其最后一个共享状态引用的释放可能等待相关线程完成。因此，把 async 返回的 future 保存到变量里，再明确安排取值位置，能让工作重叠区间和等待位置清楚地体现在代码中。

后面学习 `std::jthread` 时，你会看到另一种所有权约定：线程对象负责在析构时请求停止并 join。A3 将结合实际 worker 示例讲解这一约定。现在先建立一个共同习惯：看到异步工作，就同时找到其完成信号与负责等待结束的对象。

## 四、异常也是结果通道的一部分

### 把错误传回消费位置

同步函数抛出异常时，异常沿当前调用栈传播。对于稍后完成的工作，调用方可能已经离开发起操作的调用点，因此需要先保存错误，随后在消费结果时重新抛出。

`std::exception_ptr` 可以保存捕获到的异常。下面直接创建一份异常对象并放入共享状态：

```cpp
producer.set_exception(
    std::make_exception_ptr(std::runtime_error("calculation failed")));

try {
    int value = result.get();
    use(value);
} catch (const std::runtime_error& error) {
    report(error.what());
}
```

这里的 `use`、`report` 代表应用自己的处理代码。`set_exception` 让共享状态就绪；`get()` 发现状态中存放的是异常，就在调用 `get()` 的位置重新抛出。这样，业务代码可以围绕“取结果”处理成功与失败。

对于 `std::async`，可调用对象抛出的异常由设施捕获并保存。对于手动管理的 promise，提供方通常在 `catch (...)` 中使用 `std::current_exception()` 保存当前异常，再调用 `set_exception()`。

## 五、延迟求值和重复读取

### deferred 把执行推迟到等待位置

观察以下三个时刻：创建入口、查询状态、消费结果。

```cpp
bool executed = false;
auto result = std::async(std::launch::deferred, [&] {
    executed = true;
    return 42;
});

auto status = result.wait_for(std::chrono::milliseconds{0});
int value = result.get();
```

创建入口后，`executed` 仍为 `false`。定时等待报告 `deferred`，工作继续保持待执行状态。调用 `get()` 时，可调用对象在当前等待线程中执行，修改 `executed` 并返回结果。

这是一种**惰性执行**：执行请求先被表示出来，直到某个明确的消费动作才真正求值。下一节的 generator 也采用按需推进的方式，但它连续交付多个元素。后续 A2 的 lazy task 则会展示协程任务自己的启动约定。

<a id="shared-future"></a>

### shared_future：共享一份已经产生的结果

有时多段代码都要读取同一份配置计算结果。`std::shared_future<T>` 为这种重复读取提供共享消费入口：

```cpp
std::promise<int> producer;
auto first = producer.get_future().share();
auto second = first;
producer.set_value(7);

const int& a = first.get();
const int& b = second.get();
```

`share()` 把 future 的共享状态关联转交给 shared_future。复制 shared_future 会让多个入口共同关联这份状态。对于普通对象类型 `T`，`shared_future<T>::get()` 返回 `const T&`，可以重复调用。

`a`、`b` 引用共享状态中保存的同一个整数。持有该状态的 shared_future 对象需要覆盖这些引用的使用期。这样的只读共享让“同一个结果被多个地方观察”很方便；结果所指向的其他可变对象仍要遵循自己的同步约定。

### 练习 P-1，Part 5：重复消费同一结果

到这里，你已经能区分计算的执行、结果状态、等待动作和消费方式。A3 将在这套基础上构造一个显式 awaitable 包装，让 future 的完成能够连接到协程恢复。

## 六、从容器与迭代器走向 generator

### 序列接口表达了什么

`std::vector<int>` 保存一组已经存在的整数。range-for 使用迭代器读取这些元素：先取得 `begin()` 与 `end()`，比较位置，解引用读取，再递增到下一位置。

可以用下面的代码理解基本过程：

```cpp
auto it = values.begin();
auto end = values.end();
for (; it != end; ++it) {
    int value = *it;
    consume(value);
}
```

这里的 `consume` 代表消费当前元素的操作。range 接口把“读取当前位置”和“前进到下一位置”分开。于是，提供这个接口的对象既可以访问已保存的元素，也可以在前进时计算下一个元素。

迭代器能力决定了算法能提出哪些要求。**input range** 提供单遍输入；消费者向前推进后，通常无法再从旧位置重新开展独立遍历。vector 的迭代器提供更强能力，可以多遍遍历并随机访问。对流式输入，单遍模型往往已经足够。

### generator 在消费动作中推进生产者

`std::generator<T>` 是标准库提供的同步协程生成器，可以作为 input range 使用。先看一个三元素例子：

```cpp
std::generator<int> numbers() {
    co_yield 1;
    co_yield 2;
    co_yield 3;
}
```

`co_yield value` 在这个类型定义的协议下交付一个当前值，并暂停生产者。消费者继续推进迭代器时，生产者从上一次暂停位置之后继续执行。

从使用者角度看，时序如下：

| 消费动作 | 生产者执行 | 当前可读值 |
| --- | --- | --- |
| `auto sequence = numbers()` | 创建生成器并保持协程体待启动 | 尚未取得元素 |
| `auto it = sequence.begin()` | 执行到第一个 `co_yield` | `1` |
| `*it`，再一次 `*it` | 读取当前元素 | 都是 `1` |
| `++it` | 从第一个 yield 之后执行到第二个 yield | `2` |
| 再次 `++it` | 继续到第三个 yield | `3` |
| 再次 `++it` | 执行到协程体结束 | `it == sequence.end()` |

上表中的惰性启动与交替推进由 `std::generator` 的库协议实现。之后学习自定义协程类型时，你会看到，返回类型及其 promise 定义了启动、产出、完成等行为。

generator 的生产代码在发起迭代动作的调用链中同步运行。一次 `++it` 会执行生产者到下一个产出或结束；如果生产者在途中执行一个阻塞操作，这次推进也会等待那个操作。这个认识对区分“惰性序列”和“异步 I/O”很有帮助。

打开 [P2 练习入口](exercises/P2_generator_basics/README.md)。Starter 在协程入口、每个 yield 前后和局部对象析构时打印日志。

`continued` 统计执行到 yield 后一条语句的次数。最后一次递增使第三次 yield 后的语句得到执行，随后协程体结束。协程体内的局部对象也在正常离开其作用域时析构。

解引用只负责读取当前值；递增负责让计算继续。这组实验把两种动作清楚地分开了。

## 七、暂停期间，局部变量如何继续存活

### 观察一个跨 yield 存活的对象

假设生产者内部有一个记录析构的 RAII 对象：

```cpp
std::generator<int> numbers() {
    local_lifetime local;  // 析构时打印日志。
    co_yield 1;
    co_yield 2;
}
```

取得第一个元素时，函数体停在第一次 yield。`local` 的作用域还未结束，所以它继续存活。协程需要保存这种跨暂停仍然有效的状态。下一章会逐步介绍用于保存状态的协程帧及其与普通调用栈的关系。

当生产者正常执行结束时，函数体局部对象按作用域规则析构。生成器对象仍然负责管理协程状态的剩余生命周期。**函数体局部对象的析构**和**整个协程状态的释放**是两个可以发生在不同时间的事件。

还有一种很常见的情况：消费者只需要第一个值，就结束本次遍历。此时，生成器仍停在 yield，局部对象还存活。拥有该协程状态的 generator 对象析构时，会销毁暂停的状态，同时析构这些仍存活的局部对象。

### 练习 P-2，Part 2：提前结束消费

在第二个作用域中，调用一次 `begin()` 并读出第一个值，随后让生成器离开作用域。参考输出：

```text
P2/2 yielded=1 continued=0 local_destroyed=1
```

读到这一行时，试着指出每个数字的原因：生产者只交付过一个值；销毁沿局部对象的清理路径展开；yield 后的业务语句保持尚未执行状态。

这也解释了迭代器的使用期：它访问的是生成器管理的执行状态，owner 需要覆盖迭代器的使用。把生成器保存为具名局部变量，可以直观看到这段所有权关系。range-for 也能管理适当临时 range 的生命周期；具体安全性取决于被迭代对象及其引用的数据各自能存活多久。

### 按值保存数据与引用外部数据

P2 的参考生成器接收 `observations&`，将计数写回调用方。调用方先创建 `observations`，再在其内部作用域创建生成器；这种嵌套保证了观察对象覆盖生成器的使用期。

如果生成器需要独立保存一份数据，可以按值接收可拥有数据的对象，例如 `std::string`。如果接收 `std::string_view`、指针或引用，就要由调用方保证对应数据足够长寿。A1 的逐行生成例子、J 模块的生命周期诊断会继续使用这一区别。

## 八、需要多次遍历时保存结果

一个 generator 表示一次推进中的生产过程。使用它时，对同一对象进行一次 `begin()` 启动，然后沿迭代器逐步消费。若希望再次从头生成，可以重新调用生成器函数，创建一个新的过程。

若希望重读同一份已经取得的数据，可以先把元素存入容器：

```cpp
auto sequence = numbers();
std::vector<int> saved;
for (int value : sequence) saved.push_back(value);

for (int value : saved) inspect(value);
for (int value : saved) aggregate(value);
```

`inspect`、`aggregate` 代表两次消费。第一轮收集推进生成器并复制每个整数。后面两轮遍历只访问 vector 已保存的元素，因此不会再次执行生产者。代价是保存这些元素所需的内存；收益是可以重复访问和使用更强的迭代器能力。

### 练习 P-2，Part 3：比较过程与保存的结果

完成 Starter 的第三个作用域，记录两次遍历之和与生产者进入次数：

```text
P2/3 first_sum=6 second_sum=6 body_entries=1
```

A1 会把这个三值例子扩展为 Fibonacci 和逐行文本，并介绍 `std::views::take` 怎样限制消费区间。B1 再研究递归生成器；这些例子都建立在本章的启动、推进与所有权模型上。

## 九、带着哪些问题进入协程

到这里，你可以从结果与执行两个角度描述一段程序。进入 [01 心智模型](01-心智模型.md) 前，用具体例子回答下面的问题：

1. **future 已经 valid，为什么还要等待？**

   **答案解析：** `valid()` 表示 future 关联着共享状态，ready 表示其中的值或异常已经可以取得。P1-1 刚执行 `producer.get_future()` 时，消费入口已经存在，提供方还未设置结果，所以 `valid()` 为 true，`wait_for(0ms)` 返回 timeout。`set_value(42)` 使状态就绪；`wait()` 保留消费入口，`get()` 取出 42 后释放该 future 对共享状态的关联，此时 `valid()` 为 false。

2. **async 工作何时执行，何时取结果？**

   **答案解析：** 显式选择 `std::launch::async` 时，可调用对象按独立线程的语义执行；调用方在自己需要结果的位置调用 `get()`，届时结果尚未完成就等待。选择 `std::launch::deferred` 时，第一次非定时等待（例如 `get()` 或 `wait()`）在执行该等待的线程上触发求值。P1-2 用 promise 信号决定何时允许工作完成，P1-4 则通过 `executed` 的变化观察 `get()` 如何触发 deferred 工作。

3. **deferred 与 generator 的共同点是什么？**

   **答案解析：** 两者都先保存执行所需的状态，再由消费动作触发求值。deferred 工作在一次触发后计算最终结果；`std::generator` 由 `begin()` 启动到第一个产出，后续递增再推进到下一个产出或结束。P1-4 的状态查询保持工作待执行，P2 的连续解引用保持生产者位置不变，这两种观察都说明了“查询或读取当前位置”和“推动执行”各自的作用。

4. **generator 的当前值何时改变？**

   **答案解析：** 对 P2 的三值生成器，`begin()` 先取得 1；两次 `*it` 都读取这个当前位置。`++it` 让生产者从第一次 yield 后继续运行，到第二次 yield 时当前值成为 2。再推进可取得 3，最后一次推进使协程体结束，此时迭代器与 end 相等，后续操作应按结束状态处理。

5. **暂停后，谁负责保存和清理局部对象？**

   **答案解析：** 实现用协程状态保存跨暂停仍需存活的局部对象和执行进度；本章的 generator 对象拥有对应状态。完整消费时，函数体离开作用域，已构造的局部对象先按作用域规则析构，generator 随后负责状态的最终释放。提前结束消费时，generator 析构会清理暂停状态中的存活对象；P2-2 中 `continued=0`、`local_destroyed=1` 说明清理会析构局部对象，而 yield 后面的业务语句尚未执行。

下一章将把第五个答案拆开：普通调用怎样变成可恢复的执行过程，返回对象、promise 和 handle 在其中各自负责什么。
