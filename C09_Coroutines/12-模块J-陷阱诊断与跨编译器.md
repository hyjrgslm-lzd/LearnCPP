# 12 模块 J：陷阱诊断与跨编译器

模块 J 是工程排错模块。前面你已经能写协程库和真实 I/O awaiter；现在要把常见事故归类：对象生命周期、同步锁、detached 协程、跨模块 ABI、HALO 观察和 tracing。

C++ 标准定义了协程语言变换、`coroutine_handle` 接口、`promise_type` 查找和 coroutine state 的生命周期规则。它没有标准化协程帧布局、调试元数据、异常实现 ABI、跨 DLL/so 的 resume/destroy 函数边界。J 模块因此按“机制 -> 症状 -> 定位 -> 安全写法”来学。

参考入口：

- C++ coroutine language rules：<https://en.cppreference.com/w/cpp/language/coroutines>
- Microsoft C++ coroutine debugging：<https://learn.microsoft.com/en-us/visualstudio/debugger/debug-coroutines>
- GDB coroutine debugging：<https://sourceware.org/gdb/onlinedocs/gdb/Coroutines.html>
- Windows Parallel Stacks：<https://learn.microsoft.com/en-us/visualstudio/debugger/get-started-debugging-multithreaded-apps>
- P0912R5：<https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2019/p0912r5.html>

## J-1：八类生命周期陷阱

J-1 的 reference 不默认触发 UB。它输出八类陷阱、分类和安全规则，并运行安全路径断言。真正想看崩溃，需要显式打开 unsafe demo 或自己拆单文件配 ASan/TSan。

### 1. lambda 引用捕获跨挂起

机制：协程帧会保存协程自己的局部变量；按引用捕获的外部栈对象不因此延寿。`task` 被保存、调度、稍后恢复时，外部函数可能已经返回。

症状：恢复后读取 lambda 捕获的引用，可能打印旧值、随机值、ASan stack-use-after-scope，或直接崩溃。

定位：查 lambda capture list 和协程返回对象是否越过创建者作用域。看到 `[&]`、`int&`、`std::string_view`、裸指针跨 `co_await`，先问对象是否进入协程帧。

安全写法：按值捕获，或把共享状态移动进 frame，必要时用 `shared_ptr` 表达共享所有权。

### 2. awaiter 保存临时对象派生指针

机制：`std::string("x").c_str()` 产出的指针依赖临时 string。awaiter 跨挂起点存活，不代表它内部保存的裸指针所指对象也存活。

症状：`await_resume` 或 completion callback 使用指针时读到悬空内存。

定位：查 awaiter 构造参数，尤其是 `c_str()`、`data()`、`string_view`、span、引用包装。

安全写法：把对象命名为协程局部变量，让它的生命周期覆盖整个 `co_await`；或者 awaiter 自己按值拷贝需要的数据。

### 3. 同步锁跨 `co_await`

机制：`std::mutex` ownership 绑定加锁线程。`co_await` 后协程可能在别的线程恢复，`lock_guard` 析构时在非 owner 线程解锁是 UB。即使恢复在同线程，挂起期间持锁也会阻塞其他协程和取消路径。

症状：偶发死锁、跨线程解锁崩溃、TSan 报告，或测试环境完全看不出问题。

定位：查 `lock_guard`、`unique_lock`、`scoped_lock` 的作用域是否覆盖 `co_await`。

安全写法：锁内复制必要数据，挂起前释放锁；需要异步互斥时用 async mutex/channel/scope 设计。

### 4. `initial_suspend` 抛异常

机制：协程创建顺序是分配 coroutine state、构造参数副本和 promise、调用 `get_return_object()`，然后 `co_await initial_suspend()`。这里抛异常时，清理和诊断会受实现细节影响。

症状：不同编译器上的栈、泄漏报告、返回对象状态不一致。

定位：查 `initial_suspend` awaiter 是否分配、加锁、格式化日志或可能抛异常。

安全写法：`initial_suspend` / `final_suspend` 都按 `noexcept` 设计；失败工作移到协程体或启动前。

### 5. detached 协程越过创建者生命周期

机制：协程生命周期独立于创建者。丢弃 `task`、裸 `detach()`、`asio::detached` 这类不可观察启动会让后台工作完成时间失去拥有者。

症状：shutdown 后仍有 callback 访问对象；pending map 不归零；异常丢失。

定位：查 `co_spawn` completion token、future 所有者、async scope、in-flight 计数。

安全写法：用 `sync_wait`、`async_scope`、future 或 completion handler 收束后台协程；shutdown 等所有 in-flight 归零。

### 6. 消费者把 yield 窗口内指针持久化

机制：当前 `co_yield` 挂起窗口内，yield 出来的借用对象可能仍可读；一旦推进 generator，上一轮 block 或 full-expression 结束，借用可能悬空。

症状：保存的指针在下一次 `++it` 后失效。

定位：查 generator 是否 yield 指针、引用、`string_view`，消费者是否保存到容器或成员字段。

安全写法：需要跨 yield 窗口保存时复制值；generator API 优先按值产出。

### 7. promise 析构抛异常

机制：`coroutine_handle::destroy()` 会销毁 promise。析构函数抛异常会进入 `std::terminate`。

症状：没有可恢复异常，程序直接终止。

定位：查 promise 析构和清理对象析构是否可能 throw。

安全写法：析构 `noexcept`，清理错误只记录或在析构前显式处理。

### 8. 自写 generator 持久暴露 `string_view`

机制：`co_yield expr` 会调用 `promise.yield_value(expr)`。如果 promise 只保存 `string_view`，而 `expr` 是临时 string，消费者推进后 view 指向的 buffer 失效。

症状：当前 yield 点看起来可读，下一次 resume 后保存 view 变脏。

定位：看 promise 的 `yield_value` 到底按值保存还是按引用/view 保存。

安全写法：按值保存 `std::string`；只在当前 yield 窗口暴露 view，并在接口上避免长期保存。

## J-2：跨编译器 ABI 与 HALO 记录实验

J-2 对应练习目录是 `exercises/J2_cross_compiler_abi`，包含 starter 和 `J2_cross_compiler_abi_reference`。先在本机完成同一翻译单元内的观测：empty body、五个 int 局部变量、立即就绪的 `co_await`、wrapper/handle 尺寸和 promise 分配次数。具备其他工具链或独立模块环境时，可以扩展记录不同优化级别与 DLL/so 的行为。

核心机制：`coroutine_handle` 是标准接口，帧布局没有标准 ABI。promise 偏移、resume/destroy 函数、异常路径、STL 类型和分配器都由实现决定。裸 `coroutine_handle` 跨 DLL/so 暴露会把这些细节变成接口承诺。

先记录参考程序实际给出的数据：

| 指标 | 本机记录 | 对应含义 |
| --- | --- | --- |
| 编译器、标准库与构建配置 | | 解释实现观察的上下文 |
| `sizeof(task<int>)` | | 返回包装对象的体积 |
| `sizeof(coroutine_handle<>)` | | 句柄对象的体积 |
| `promise allocations observed` | | 四条参考路径合计调用分配函数的次数 |

完整协程帧还包含 promise 和执行状态。研究它的存储需求时，可以结合 F 模块的分配 size 与编译器产物，额外记录每种程序形状的观察结果。保留工具链和优化选项，后续才能对照不同条件下的变化。

当前 CMake 为 J2 注入的诊断选项是：MSVC `/Zc:__cplusplus /utf-8 /await:strict /Zi`，Clang `-Rpass=coroutine-elide -Rpass-missed=coroutine-elide`，GCC `-fdump-tree-coro`。额外帧布局 dump 或跨模块实验可在本地临时命令中加入；HALO 是优化观察，不能写进性能预算承诺。

安全写法：模块边界暴露普通值、sender、callback、future 或库自有 opaque token；resume/destroy ownership 留在同一实现侧。

## J-3：协程调试与 tracing

传统 backtrace 只能看到当前线程栈。协程挂起后，逻辑调用链在协程帧、continuation、awaiter storage 和调度器队列里。J-3 通过 `traced_awaitable` 给每个 `co_await` 打点。

reference 的最小链：

```text
task_c()
  co_await task_b()
    co_await task_a()
      co_await a.step1
      co_await a.step2
    co_await b.step2
```

`traced_awaitable` 在 `await_suspend` 记录 SUSPEND、frame opaque id、线程 id；在 `await_resume` 记录 RESUME。`traced_task` 还在 `initial_suspend` / `final_suspend` 注册和清理全局 registry。reference 结束时断言 registry 为空，说明 tracing 没有留下悬空 frame 记录。

预测结果：`task_c` 返回 `(1 + 2 + 10) * 2 = 26`。日志中会看到多个 `SUSPEND/RESUME`，同一个 coroutine frame 有稳定的 opaque id。Debug 模式有日志，Release 可用宏关闭。

调试建议：MSVC 用 Parallel Stacks 的 Tasks 视图看逻辑链；GDB 14+ 用 `info coroutines` 辅助观察。trace 日志回答“谁在等谁、在哪个线程恢复、哪个等待点最长”；调试器回答“当前暂停时协程链停在哪里”。

完成模块 J 后，看到协程代码应能马上指出：哪些对象在 frame 内，哪些只是引用；哪个 awaiter 保存 OS 或框架身份；谁负责 resume；谁负责 destroy；异常和取消各走哪条通道。

**答案解析：** frame 内对象通常包括 promise、需要跨挂起存活的参数副本、局部变量和 awaiter；引用、裸指针、`string_view`、`coroutine_handle` 只是指向外部对象或 frame 的非拥有入口。awaiter 或 operation state 保存 OS/framework 身份，例如 io_uring `user_data`、IOCP `OVERLAPPED*`、Asio handler 绑定；resume 由 completion、scheduler 或 `final_suspend` continuation 触发，destroy 由 task/scope/operation owner 负责。异常一般经 promise 或 error channel 传播，取消经 stop token、stopped channel、OS cancel 或业务 cancel frame 传播，具体答案要沿当前库的 API 契约确认。
