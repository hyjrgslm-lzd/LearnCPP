# 05 模块 C2：算法·投影·范围边界

## 模块目标

前三个模块建立了"视图工厂 → 基础适配器 → 结构适配器"的管道直觉。这个模块把目光从 view 管道转向另一半：**`std::ranges::` 算法**。

你会发现 ranges 算法不只是"给 C++17 算法加了 concept 约束"——它们在三个维度上做了根本性提升：

1. **niebloid 身份**：不被 ADL 劫持，可作为一等值传递，内部 concept 约束错误信息比裸模板清晰。
2. **projection 参数**：算法的 comparator / predicate 在 `proj(*it)` 之后才被调用，把"映射步骤"和"判断步骤"显式分离。
3. **富返回类型**：不再只返回单个迭代器，而是返回 `in_out_result`、`min_max_result`、`subrange`，甚至 `ranges::dangling`——最后一种是 **borrowed_range 判定机制**在类型层面的直接体现。

反向引用 `01-心智模型.md` 的两段：

- **projection 段**（"投影（projection）这一层"）：你在那里初次见到 `ranges::sort(people, std::less{}, &Person::age)` 的用法；本模块把它从"看过"升级为"条件反射"。
- **borrowed_range 段**（"借用（borrowed）与悬垂（dangling）"）：你在那里初次看到 `ranges::dangling` 的返回机制；本模块解释 `enable_borrowed_range` 的 opt-in 机制和 `borrowed_iterator_t` / `borrowed_subrange_t` 的用法。

反向引用 `04-模块C1-结构适配器.md` 的 `common_range` 段：C++17 `std::sort` / `std::find` 要求 begin/end 同类型，但 ranges 算法无此要求，这是两者差异的直接体现；模块 C1 用 `views::common` 桥接，本模块把这条分界线说清楚。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- `std::ranges::algo` 与 `std::algo` 的四项差异：niebloid 身份、concept 约束、projection 参数、富返回类型。
- projection 在算法内部的应用位置：`comp(proj(*it1), proj(*it2))`——先投影再比较，不是先比较再投影。
- `ranges::borrowed_iterator_t<R>` 与 `ranges::borrowed_subrange_t<R>` 的含义：当 `R` 是 borrowed_range 时展开为真实迭代器/subrange，否则展开为 `ranges::dangling`。
- `ranges::dangling` 何时被返回：实参是右值且该类型不是 `borrowed_range`（即未特化 `enable_borrowed_range = true`）。
- `std::from_range_t` 与 `std::ranges::to` 的职责区分：前者是容器构造侧的标签类型，后者是算法侧的统一收束入口，两者协作但不同层。
- 为什么 C++17 `std::algo` 无法搭配 sentinel / niebloid：前者要求 begin/end 同类型，后者以函数对象形式存在不参与重载查找。

## 练习 C2-1：projection 模式

### 目标

让 projection 成为条件反射，彻底甩掉"每次都写 lambda 捕获 member pointer"的惯性。在本练习结束后，你应该能在看到"对结构体集合排序/查找/统计"时，立刻想到 projection 而不是 lambda 包装。

### 前置理解

- 你已经在 `01-心智模型.md` 的"投影（projection）这一层"段读过 `ranges::sort(employees, std::greater{}, &Employee::salary)` 的用法，知道 projection 是算法第三个（或第四个）参数。
- 你知道 `std::identity` 是恒等映射，是所有 ranges 算法的默认 projection。
- 你接受这题的重点不是输出值本身，而是"projection vs lambda"在代码表达力上的差异，以及 projection 可以是任意 Callable 这一事实。

### 预计练习方向

**基础任务：成员指针作为 projection**

```cpp
// C++20
#include <ranges>
#include <algorithm>
#include <vector>
#include <string>
#include <iostream>
#include <functional>

struct Person {
    std::string name;
    int age;
};

int main() {
    std::vector<Person> people = {
        {"Bob",   30},
        {"Alice", 25},
        {"Carol", 35},
        {"Dave",  25},
    };

    // ---- sort by age（升序）----
    // projection 是 &Person::age；comp 是 std::less{}（默认可省略）
    std::ranges::sort(people, std::less{}, &Person::age);
    std::cout << "sorted by age: ";
    for (const auto& p : people)
        std::cout << p.name << '(' << p.age << ") ";
    std::cout << '\n';
    // Alice(25) Dave(25) Bob(30) Carol(35)

    // ---- find by name ----
    // projection 把 Person 映射到 string，predicate 是 == "Alice"（来自 ranges::find 的值参数）
    auto it = std::ranges::find(people, std::string{"Alice"}, &Person::name);
    if (it != people.end())
        std::cout << "found: " << it->name << ", age=" << it->age << '\n';
    // found: Alice, age=25

    // ---- max by age ----
    // ranges::max 返回元素值（不是迭代器），使用 projection
    const Person& oldest = std::ranges::max(people, std::less{}, &Person::age);
    std::cout << "oldest: " << oldest.name << '(' << oldest.age << ")\n";
    // oldest: Carol(35)

    // ---- C++17 等价写法（lambda）对比 ----
    // std::sort(people.begin(), people.end(),
    //           [](const Person& a, const Person& b){ return a.age < b.age; });
    // 以上写法的问题：排序键 a.age 与比较器混在一起，意图不如 projection 清晰。

    return 0;
}
```

**min_max_result：接收 minmax 的富返回类型**

```cpp
// C++20
#include <ranges>
#include <algorithm>
#include <vector>
#include <string>
#include <iostream>

struct Person {
    std::string name;
    int age;
};

int main() {
    std::vector<Person> people = {
        {"Bob", 30}, {"Alice", 25}, {"Carol", 35}, {"Dave", 28}
    };

    // ranges::minmax 返回 ranges::minmax_result<T>，即 { min, max }
    // 注意：返回的是元素的拷贝（值语义），不是迭代器
    auto [youngest, oldest] =
        std::ranges::minmax(people, std::less{}, &Person::age);

    std::cout << "youngest: " << youngest.name << '(' << youngest.age << ")\n";
    std::cout << "oldest:   " << oldest.name   << '(' << oldest.age   << ")\n";
    // youngest: Alice(25)
    // oldest:   Carol(35)

    // ranges::minmax_element 返回 minmax_result<iterator>
    auto [min_it, max_it] =
        std::ranges::minmax_element(people, std::less{}, &Person::age);
    std::cout << "min_element: " << min_it->name << '\n';
    std::cout << "max_element: " << max_it->name << '\n';

    return 0;
}
```

**count_if 与 lambda projection 混用**

```cpp
// C++20
#include <ranges>
#include <algorithm>
#include <vector>
#include <string>
#include <iostream>

struct Person {
    std::string name;
    int age;
};

int main() {
    std::vector<Person> people = {
        {"Bob", 30}, {"Alice", 25}, {"Carol", 35}, {"Dave", 28}
    };

    // count_if：projection 先于 predicate 执行
    // projection = &Person::age，predicate = [](int a){ return a >= 30; }
    auto n = std::ranges::count_if(people,
                                   [](int a){ return a >= 30; },
                                   &Person::age);
    std::cout << "age >= 30 count: " << n << '\n';  // 2（Bob 30, Carol 35）

    // 用 lambda 作为 projection（不只是成员指针）：
    // 取 name 的首字母做比较
    auto it = std::ranges::find_if(people,
                                   [](char c){ return c == 'C'; },
                                   [](const Person& p){ return p.name[0]; });
    if (it != people.end())
        std::cout << "first 'C' name: " << it->name << '\n';  // Carol

    // std::identity 显式化：projection 默认是 identity，显式写出让意图清晰
    std::vector<int> nums = {3, 1, 4, 1, 5, 9, 2, 6};
    std::ranges::sort(nums, std::less{}, std::identity{});  // 与 ranges::sort(nums) 等价
    for (int x : nums) std::cout << x << ' ';
    std::cout << '\n';  // 1 1 2 3 4 5 6 9

    return 0;
}
```

### 进阶预计方向

**projection 的可组合性：嵌套 Callable**

```cpp
// C++20
#include <ranges>
#include <algorithm>
#include <vector>
#include <string>
#include <iostream>

struct Department {
    std::string name;
    int headcount;
    double budget;
};

int main() {
    std::vector<Department> depts = {
        {"Engineering", 50, 1200000.0},
        {"Marketing",   15,  300000.0},
        {"Finance",     20,  500000.0},
    };

    // projection 是任意 Callable，不仅限于成员指针
    // 这里用 lambda 计算人均预算作为排序键
    auto per_capita_budget = [](const Department& d) {
        return d.budget / d.headcount;
    };

    std::ranges::sort(depts, std::greater{}, per_capita_budget);
    std::cout << "sorted by per-capita budget (desc):\n";
    for (const auto& d : depts)
        std::cout << "  " << d.name
                  << " per_capita=" << d.budget / d.headcount << '\n';

    // partial_sort_copy + projection：把前 2 名按预算最大值摘出来
    std::vector<Department> top2(2);
    std::ranges::partial_sort_copy(depts, top2, std::greater{}, &Department::budget, &Department::budget);
    // 注意：partial_sort_copy 有两个 projection 参数（in-proj 和 out-proj）
    // 这里两个都用 &Department::budget
    std::cout << "top2 by budget: ";
    for (const auto& d : top2)
        std::cout << d.name << ' ';
    std::cout << '\n';

    return 0;
}
```

### 验收点

- 你能把 `sort / find / max / count_if / minmax_element` 的 projection 版本与 C++17 lambda 版本并排写出，并说出 projection 在可读性和代码意图上的优势。
- 你能用 `static_assert` 验证 `std::ranges::minmax_result` 的结构（它有 `min` 和 `max` 两个成员）。
- 你能说出 projection 的两类合法类型：成员指针（`&T::member`）和任意 Callable（lambda、函数指针、function object）。
- 你能解释 `std::identity{}` 作为显式 projection 的语义：它使算法行为与不提供 projection 时完全一致，但代码意图更清晰。

### 观察点

- projection 的应用位置是算法的内部热点：每次需要比较时，算法先对两个元素各自调用 `proj`，再把结果传给 `comp`。伪代码是 `comp(proj(*it1), proj(*it2))`。不存在"先 comp 后 proj"的情况。
- projection 比 lambda 的优势不只是"更短"：当 projection 是成员指针时，编译器通常能更好地内联（成员访问是已知偏移量，比 lambda closure 调用层次浅）。更重要的是语义分离："`sort` by `age`"与"`sort` where `a.age < b.age`"表达的意图精度不同。
- `ranges::count_if(r, pred, proj)` 中 `pred` 的参数类型是 `proj` 的返回类型，不是元素类型。如果你搞错了 predicate 的签名（接受 `Person` 而不是 `int`），concept 约束会给出比裸模板更清晰的编译错误。
- projection 只能在 ranges 算法中使用。C++17 的 `std::sort` / `std::find` 不接受 projection 参数，这是两者接口设计的根本差异之一。

### 常见坑

- **以为 projection 只能是成员指针**：成员指针是最常见的用法，但 projection 的 concept 约束是 `std::invocable<Proj, element_type>`——任何 Callable 都可以，包括自由函数指针、lambda、`std::mem_fn` 包装等。
- **把 projection 和 comparator 顺序搞错**：`ranges::sort(v, proj, comp)` 是错的；正确签名是 `ranges::sort(range, comp, proj)`——comp 在第三个位置，proj 在第四个位置（对二元算法）；对一元谓词算法（find_if、count_if），是 `algo(range, pred, proj)`。记忆技巧：先写"判断标准"（comp/pred），再写"映射方式"（proj）。
- **对 minmax/min/max 期待返回迭代器**：`ranges::min` / `ranges::max` / `ranges::minmax` 返回的是元素的**值**（引用），不是迭代器；想要迭代器请用 `min_element` / `max_element` / `minmax_element`。
- **用 C++17 `std::sort` 传 projection**：`std::sort(v.begin(), v.end(), comp, proj)` 在 C++17 中根本不存在这个重载，会静默地把 proj 当成第四个不认识的参数报错，不是"proj 被忽略了"。

### 提示

- 把 `std::ranges::sort(v, std::less{}, &Person::age)` 和 `std::sort(v.begin(), v.end(), [](auto& a, auto& b){ return a.age < b.age; })` 放在同一个文件里，通过 diff 直观感受 projection 带来的精简度。
- 检查 `minmax_result` 的成员：用 `auto [lo, hi] = std::ranges::minmax(v)` 做结构化绑定时，`lo` 对应 `.min`，`hi` 对应 `.max`；绑定顺序是按成员声明顺序，不要搞反。
- 如果 projection 是 lambda，要确保它是无状态（无捕获）或只读捕获的——带可变状态的 lambda 在 const 上下文下会遇到与模块 B transform_view 类似的 const operator() 问题。

### 复盘问题

- 假设你有一个 `std::vector<std::pair<int, std::string>>`，用 `ranges::sort` 按 `second`（string）升序排列，projection 应该写什么？comp 应该写什么？
- `ranges::find(people, "Alice", &Person::name)` 中，第二个参数 `"Alice"` 是与 `proj(*it)` 的结果做 `==` 比较的——如果 name 是 `std::string` 而传入的是 `const char*`，这里的类型提升是隐式发生的，你能解释原因吗？
- `std::identity{}` 作为 projection 和完全不传 projection 在运行时行为上是否有差异？在编译期有差异吗（零开销）？
- 为什么 C++17 风格算法无法添加 projection 参数——这是接口设计约束还是语言机制约束？能通过重载的方式添加吗？

## 练习 C2-2：富返回类型与 borrowed_range

### 目标

观察 `ranges::find` / `ranges::copy` / `ranges::minmax_element` 等算法返回的不是"单个裸迭代器"，而是 `in_out_result` / `min_max_result` / `subrange` / `ranges::dangling`，并用 `static_assert` + `std::same_as` 在类型层面验证 borrowed_range 判定的完整逻辑。

### 前置理解

- 你已经在 `01-心智模型.md` 的"借用（borrowed）与悬垂（dangling）"段理解了 `ranges::dangling` 的基本概念：对右值非 borrowed_range 调用返回迭代器的算法，得到 `ranges::dangling`。
- 你知道 `std::string_view` 是 `borrowed_range`（它不拥有字符数据），而 `std::vector<int>` 不是（它拥有元素）。
- 你了解 `enable_borrowed_range` 是一个 opt-in 机制：标准库中少数类型默认特化为 `true`（`string_view`、`span`、`subrange`、`iota_view`、`empty_view` 等），其余类型默认是 `false`。

### 预计练习方向

**基础任务：ranges::dangling 验证**

```cpp
// C++20
#include <ranges>
#include <algorithm>
#include <vector>
#include <string_view>
#include <iostream>

// 返回右值 vector（非 borrowed_range）
auto make_vec() -> std::vector<int> {
    return {3, 1, 4, 1, 5, 9, 2, 6};
}

int main() {
    // ---- 右值非 borrowed_range → ranges::dangling ----
    auto it_dangling = std::ranges::find(make_vec(), 4);
    // make_vec() 产生右值 vector，vector 不是 borrowed_range
    // 因此 ranges::find 无法安全返回迭代器，返回 ranges::dangling
    static_assert(
        std::same_as<decltype(it_dangling), std::ranges::dangling>,
        "right-value non-borrowed range must produce dangling"
    );
    // it_dangling 没有 operator*，尝试解引用会是编译错误：
    // auto val = *it_dangling;  // 编译错误

    // ---- string_view 是 borrowed_range → 返回真实迭代器 ----
    std::string_view sv = "hello ranges";
    auto it_sv = std::ranges::find(sv, 'r');
    // string_view 是 borrowed_range：迭代器有效性不依赖 sv 对象本身
    static_assert(
        !std::same_as<decltype(it_sv), std::ranges::dangling>,
        "borrowed_range must return a real iterator"
    );
    // string_view::iterator 的具体类型是实现定义（libstdc++ 用 const char*，
    // MSVC 用包装类），所以不要写死成 const char*；应断言更稳定的性质：
    static_assert(std::contiguous_iterator<decltype(it_sv)>);
    static_assert(std::same_as<decltype(it_sv), std::string_view::iterator>);
    if (it_sv != sv.end())
        std::cout << "found 'r' at offset: "
                  << (it_sv - sv.begin()) << '\n';  // 6

    // ---- borrowed_iterator_t 类型别名 ----
    // ranges::borrowed_iterator_t<R> 展开规则：
    //   R 是 borrowed_range → iterator_t<R>
    //   R 不是 borrowed_range → ranges::dangling
    static_assert(std::same_as<
        std::ranges::borrowed_iterator_t<std::string_view>,
        const char*
    >);
    static_assert(std::same_as<
        std::ranges::borrowed_iterator_t<std::vector<int>>,
        std::ranges::dangling
    >);

    return 0;
}
```

**in_out_result：ranges::copy 的结构化绑定**

```cpp
// C++20
#include <ranges>
#include <algorithm>
#include <vector>
#include <iostream>
#include <iterator>

int main() {
    std::vector<int> src = {1, 2, 3, 4, 5};
    std::vector<int> dst(5, 0);

    // ranges::copy 返回 in_out_result<iterator, out_iter>
    // 其中 .in 是 src 的 end（消费完毕），.out 是 dst 的写入终止位置
    auto [in_end, out_end] = std::ranges::copy(src, dst.begin());

    std::cout << "src copied, dst: ";
    for (int x : dst) std::cout << x << ' ';
    std::cout << '\n';  // 1 2 3 4 5

    // in_end 指向 src.end()
    // out_end 指向 dst.begin() + 5（即 dst.end()）
    std::cout << "in==src.end(): "
              << std::boolalpha << (in_end == src.end()) << '\n';   // true
    std::cout << "out==dst.end(): "
              << (out_end == dst.end()) << '\n';                     // true

    // ranges::copy_if 同样返回 in_out_result，.in 指向源的 end，.out 指向目标写入终止
    std::vector<int> evens;
    auto [_, out2] = std::ranges::copy_if(src, std::back_inserter(evens),
                                          [](int x){ return x % 2 == 0; });
    std::cout << "evens: ";
    for (int x : evens) std::cout << x << ' ';
    std::cout << '\n';  // 2 4

    return 0;
}
```

**equal_range：ranges::subrange 返回值**

```cpp
// C++20
#include <ranges>
#include <algorithm>
#include <vector>
#include <iostream>

int main() {
    std::vector<int> v = {1, 2, 2, 3, 3, 3, 4, 5};

    // ranges::equal_range 在已排序序列上查找等值范围
    // 返回 subrange<iterator, iterator>，代表 [lower_bound, upper_bound)
    std::ranges::subrange<std::vector<int>::iterator> r =
        std::ranges::equal_range(v, 3);

    std::cout << "equal_range(3): ";
    for (int x : r) std::cout << x << ' ';
    std::cout << '\n';  // 3 3 3

    std::cout << "size=" << r.size() << '\n';  // 3

    // ranges::search 也返回 subrange（找到的子序列）
    std::vector<int> needle = {2, 3};
    auto found = std::ranges::search(v, needle);
    if (!found.empty()) {
        std::cout << "search found at offset: "
                  << (found.begin() - v.begin()) << '\n';  // 1
    }

    return 0;
}
```

### 进阶预计方向

**自定义 my_borrowed_span：enable_borrowed_range opt-in 机制**

```cpp
// C++20
#include <ranges>
#include <algorithm>
#include <iostream>

// 一个轻量的"指针+长度"span，语义上是借用的
template<typename T>
struct my_borrowed_span {
    T* ptr;
    std::size_t len;

    // 满足 range concept 需要的 begin/end
    T* begin() const { return ptr; }
    T* end()   const { return ptr + len; }
};

// 特化前：my_borrowed_span 不是 borrowed_range（默认 false）
static_assert(!std::ranges::borrowed_range<my_borrowed_span<int>>);

// 显式 opt-in：声明 my_borrowed_span<T> 的迭代器有效性不依赖对象本身
template<typename T>
inline constexpr bool std::ranges::enable_borrowed_range<my_borrowed_span<T>> = true;

// 特化后：my_borrowed_span 是 borrowed_range
static_assert(std::ranges::borrowed_range<my_borrowed_span<int>>);

int main() {
    int arr[] = {5, 3, 8, 1, 9, 2};
    my_borrowed_span<int> span{arr, 6};

    // 特化前（如果去掉 enable_borrowed_range 特化），对右值 my_borrowed_span
    // 调用 ranges::find 会得到 ranges::dangling
    // 特化后，可以安全返回真实迭代器：
    auto it = std::ranges::find(my_borrowed_span<int>{arr, 6}, 8);
    // 右值 my_borrowed_span，因为已特化 enable_borrowed_range = true，
    // 返回真实的 int* 而不是 dangling
    static_assert(!std::same_as<decltype(it), std::ranges::dangling>);
    static_assert(std::same_as<decltype(it), int*>);

    if (it != span.end())
        std::cout << "found 8 at index: " << (it - arr) << '\n';  // 2

    // borrowed_subrange_t 类型别名：
    // R 是 borrowed_range → subrange<iterator_t<R>>
    // R 不是 borrowed_range → ranges::dangling
    static_assert(std::same_as<
        std::ranges::borrowed_subrange_t<my_borrowed_span<int>>,
        std::ranges::subrange<int*>
    >);
    static_assert(std::same_as<
        std::ranges::borrowed_subrange_t<std::vector<int>>,
        std::ranges::dangling
    >);

    return 0;
}
```

**常见 borrowed view 一览：哪些是，哪些不是**

```cpp
// C++20
#include <ranges>
#include <span>
#include <string_view>
#include <vector>
#include <list>

int main() {
    // 默认 borrowed（标准库特化 enable_borrowed_range = true）：
    static_assert(std::ranges::borrowed_range<std::string_view>);
    static_assert(std::ranges::borrowed_range<std::span<int>>);
    static_assert(std::ranges::borrowed_range<std::ranges::subrange<int*>>);
    static_assert(std::ranges::borrowed_range<std::ranges::iota_view<int,int>>);
    static_assert(std::ranges::borrowed_range<std::ranges::empty_view<int>>);

    // 默认非 borrowed（拥有数据，enable_borrowed_range = false）：
    static_assert(!std::ranges::borrowed_range<std::vector<int>>);
    static_assert(!std::ranges::borrowed_range<std::list<int>>);
    static_assert(!std::ranges::borrowed_range<std::string>);

    // ref_view 是 borrowed_range（只持有指针，不拥有数据）：
    std::vector<int> v = {1, 2, 3};
    auto rv = std::views::all(v);  // ref_view<vector<int>>
    static_assert(std::ranges::borrowed_range<decltype(rv)>);

    // owning_view 不是 borrowed_range（它拥有数据）：
    auto ov = std::views::all(std::vector<int>{1, 2, 3});  // owning_view
    static_assert(!std::ranges::borrowed_range<decltype(ov)>);

    return 0;
}
```

### 验收点

- 你能用 `static_assert(std::same_as<decltype(it), std::ranges::dangling>)` 在编译期验证右值 vector 场景。
- 你能用 `static_assert` 验证 `string_view` 场景下返回的是真实的 `const char*`。
- 你能解释 `enable_borrowed_range` 是 opt-in 而非 opt-out：标准默认所有类型为 `false`，只有少数类型（`string_view`、`span`、`iota_view` 等）被特化为 `true`，用户自定义类型需要显式特化。
- 你能用代码演示 `my_borrowed_span` 在特化前后，`ranges::find` 对右值实例的返回类型变化。
- 你能说出 `ranges::copy` 的返回类型是 `in_out_result`，并用结构化绑定正确读取 `.in` 和 `.out`。

### 观察点

- `ranges::dangling` 是一个 empty 类型，没有任何成员函数（没有 `operator*`、没有 `operator->`）。任何试图"使用"它的操作都会在编译期报错，这正是它作为"类型级安全守卫"的价值——把运行时悬垂迭代器的 UB 升级为编译期错误。
- `borrowed_range` 的判定发生在**调用点的模板实例化期**，不是运行时。`enable_borrowed_range` 是一个编译期 `constexpr bool`，ranges 算法通过 `if constexpr` 或 concept 约束在编译期选择返回类型。
- `enable_borrowed_range` 的语义承诺：一旦你把某个类型特化为 `true`，就相当于向标准库承诺"这个类型的迭代器有效性不依赖对象本身的生命周期"。如果这个承诺是假的（例如你的类型实际上拥有数据），那么通过 `ranges::find` 拿到的"真实迭代器"在对象销毁后变成悬垂——这是你撒谎的后果，不是标准库的 bug。
- 不要夸大"view 都是 borrowed"：只有极少数 view 在标准库中默认是 `borrowed_range`。`transform_view`、`filter_view`、`take_view`、`owning_view` 等都**不是** `borrowed_range`，对它们的右值调用返回迭代器的算法会得到 `dangling`。

### 常见坑

- **以为所有 view 都是 borrowed_range**：错误。只有 `string_view`、`span`、`subrange`、`iota_view`、`empty_view` 等少数类型在标准库中默认特化为 `true`。`transform_view`、`filter_view`、`take_view`、`join_view` 等都不是 borrowed_range。
- **以为 `std::vector` 是 borrowed_range**：`vector` 拥有其元素的存储，当 vector 对象销毁时，迭代器立即悬垂，所以它不是 borrowed_range，这与它是容器还是视图无关。
- **忘记 dangling 没有 operator***：有时候人们写 `auto it = ranges::find(get_vec(), 42); *it;` 并期待运行时崩溃告诉他们出了问题——实际上这是编译期错误，`ranges::dangling` 根本没有 `operator*`。
- **混淆 borrowed_range 和 view**：view 和 borrowed_range 是正交概念。一个类型可以是 view 但不是 borrowed_range（如 `owning_view`）；也可以是 borrowed_range 但不是 view（如 `std::span` 满足 view concept，但普通数组不是 view 却可以通过 subrange 包装成 borrowed_range）。

### 提示

- 验证 `enable_borrowed_range` 特化前后的行为变化时，最直接的方法是把特化行注释掉，对比同一段代码在有/无特化时的编译结果——前者编译通过，后者编译失败（尝试解引用 `dangling`）。
- 用 `std::ranges::borrowed_iterator_t<R>` 和 `std::ranges::borrowed_subrange_t<R>` 作为返回类型声明，能在函数签名层面直接表达"这个函数的返回类型依赖于 R 是否为 borrowed_range"的意图。

### 复盘问题

- `ranges::find(std::string_view{"hello"}, 'e')` 对右值 `string_view` 能返回真实迭代器，但 `ranges::find(std::string{"hello"}, 'e')` 对右值 `string` 返回 `dangling`——两者的根本差异是什么？
- 如果你有一个自定义类型既是 view 又应该是 borrowed_range（例如一个持有外部数组引用的轻量 view），你需要做什么操作让标准库算法认可这个事实？
- `ranges::copy` 返回的 `in_out_result::in` 和 `::out` 分别指向什么位置？为什么需要返回这两个迭代器，而不是只返回输出迭代器？
- `enable_borrowed_range` 的特化写在哪里（命名空间）？可以在用户代码里特化标准库类型吗？（提示：partial specialization in `std::ranges` is allowed for user types but not for standard types）

## 练习 C2-3：ranges::to 与 from_range_t

### 目标

掌握 C++23 把 view 管道"收束"为容器的统一入口，以及 `std::from_range_t` 在容器构造侧的职责；清楚区分两者在层次上的分工，消除"为什么需要两个机制"的疑惑。

### 前置理解

- 你已经在模块 A 的练习 A-2 进阶方向里初次见到 `ranges::to<std::vector<int>>` 的用法，知道它是 C++23 把 range 转为容器的统一接口（P1206R7）。
- 你理解 view 的惰性：管道在被 for-range / `ranges::to` / 算法调用前不会真正迭代——`ranges::to` 是其中一种消费端。
- 你接受这题的重点是理解 `ranges::to` 的四阶选择逻辑和 `from_range_t` 的标签协议，而不只是会写 `| ranges::to<vector>()`。

### 预计练习方向

**基础任务：ranges::to 的基本用法**

```cpp
// C++23: -std=c++23
#include <ranges>
#include <vector>
#include <list>
#include <string>
#include <iostream>

int main() {
    // ---- 管道语法（range adaptor closure 形式）----
    // 注意：必须写 ranges::to<vector<int>>()，括号不能省
    // ranges::to<vector<int>>（无括号）是一个模板，不是 range adaptor closure
    auto v1 = std::views::iota(1, 11)
            | std::views::filter([](int x){ return x % 2 != 0; })
            | std::ranges::to<std::vector<int>>();
    std::cout << "odd 1-10: ";
    for (int x : v1) std::cout << x << ' ';
    std::cout << '\n';  // 1 3 5 7 9

    // ---- 函数调用语法 ----
    auto src = std::views::iota(1, 6);
    auto v2 = std::ranges::to<std::vector<int>>(src);
    std::cout << "1..5: ";
    for (int x : v2) std::cout << x << ' ';
    std::cout << '\n';  // 1 2 3 4 5

    // ---- CTAD 形式：让 ranges::to 推导元素类型 ----
    // ranges::to<vector>() 而非 ranges::to<vector<int>>()
    // 编译器从 range 的 value_type 推导出 vector<int>
    auto v3 = std::views::iota(1, 6)
            | std::ranges::to<std::vector>();  // CTAD
    static_assert(std::same_as<decltype(v3), std::vector<int>>);
    std::cout << "CTAD vector: ";
    for (int x : v3) std::cout << x << ' ';
    std::cout << '\n';  // 1 2 3 4 5

    // ---- 转成其他容器 ----
    auto lst = std::views::iota(1, 6)
             | std::ranges::to<std::list<int>>();
    static_assert(std::same_as<decltype(lst), std::list<int>>);

    auto str = std::views::iota('a', 'f')
             | std::ranges::to<std::string>();
    std::cout << "string: " << str << '\n';  // abcde

    return 0;
}
```

**from_range_t：容器构造侧的标签协议**

```cpp
// C++23: -std=c++23
#include <ranges>
#include <vector>
#include <iostream>

int main() {
    // std::from_range_t 是一个空标签类型（tag type），
    // std::from_range 是它的 constexpr 实例。
    // 用途：作为容器构造函数的第一个参数，
    // 明确告诉容器"我要用 range 构造你"，
    // 避免与接受 (size, value) 或 (iterator, iterator) 的构造函数歧义。

    // vector 的 from_range 构造（P2781R5 之前 vector 已通过 P1206R7 支持这个）
    auto range = std::views::iota(1, 6);
    std::vector<int> v1(std::from_range, range);
    std::cout << "from_range vector: ";
    for (int x : v1) std::cout << x << ' ';
    std::cout << '\n';  // 1 2 3 4 5

    // 对比：无 from_range_t 时可能的歧义
    // std::vector<int> v2(range);  // 在 C++23 之前这不合法（vector 无单参 range 构造）
    //                               // from_range_t 标签使接口明确

    // from_range_t 的职责：
    // - 它是"容器侧"的 opt-in 标志
    // - 告知容器实现：用 ranges::begin/end 遍历传入的 range
    // - ranges::to 在决定如何构造容器时，会优先尝试 from_range_t 构造路径

    // 验证 from_range 标签的类型
    static_assert(std::is_same_v<decltype(std::from_range), const std::from_range_t>);

    return 0;
}
```

**ranges::to 的四阶选择逻辑**

```cpp
// C++23: -std=c++23
#include <ranges>
#include <vector>
#include <iostream>

// ranges::to<C>(range) 的内部选择顺序（伪代码描述）：
//
// 以 P1206R7 + P2781R5 最终文本为准，实际优先级大致如下：
//
// 1. 如果 C 可由 range 直接构造（C(R&&) 合法）→ 直接用。
//
// 2. 否则，如果 C 有 (from_range_t, R&&) 构造函数（P2781R5 为标准容器加的）
//    → C(std::from_range, range)。
//
// 3. 否则，如果 C 可由迭代器-sentinel 对构造（C(begin, end)，需 common_range；
//    不是则内部包一层 common_view 再调用）→ 走迭代器对路径。
//
// 4. 否则，默认构造 C，再：
//      - 有 `append_range(R&&)` / `insert_range(R&&)` → 成员追加；
//      - 否则用 `emplace_back` / `push_back` / 末端 `insert` 逐元素追加。
//
// 这四条回退路径保证了几乎所有现有容器都可以被 ranges::to 收束，
// 不需要容器侧做任何改造。

// 演示第 4 条路径：只有 push_back 的最小容器
struct MinimalContainer {
    std::vector<int> data;
    void push_back(int x) { data.push_back(x); }
    // 没有 from_range 构造、没有 (iter,iter) 构造、没有 insert_range
    auto begin() const { return data.begin(); }
    auto end()   const { return data.end(); }
};

// 使 ranges::to 能输出 MinimalContainer
// 需要让它满足 range（已满足：有 begin/end）

int main() {
    // push_back 路径：ranges::to 逐一 push_back
    auto mc = std::views::iota(1, 6)
            | std::ranges::to<MinimalContainer>();

    std::cout << "MinimalContainer via push_back: ";
    for (int x : mc) std::cout << x << ' ';
    std::cout << '\n';  // 1 2 3 4 5

    // 验证 std::vector 走的是第 1 条路径（from_range_t 构造）
    // 通过 ranges::to 时，它使用 vector(std::from_range, range) 而非逐一 push_back
    // 这意味着如果 range 是 sized_range，vector 可以预先 reserve 容量
    auto v = std::views::iota(1, 6) | std::ranges::to<std::vector<int>>();
    static_assert(std::same_as<decltype(v), std::vector<int>>);

    return 0;
}
```

### 进阶预计方向

**嵌套形式：map<string, vector<int>> 递归应用 ranges::to**

// C++23: -std=c++23
#include <ranges>
#include <map>
#include <vector>
#include <string>

int main() {

    using nested_t = std::map<std::string, std::vector<int>>;

**from_range_t 与 ranges::to 的职责分工对比**

```cpp
// C++23: -std=c++23
#include <ranges>
#include <vector>
#include <iostream>

// 职责分工一句话总结：
//
// std::from_range_t（P2781R5）：
//   - 属于"容器侧"
//   - 是一个标签类型，容器的构造函数用它标记"我接受 range 构造"
//   - 容器通过 (from_range_t, range) 重载告知编译器自己支持 range 直接初始化
//   - 不需要 ranges::to 就能使用：std::vector<int> v(std::from_range, some_range)
//
// std::ranges::to（P1206R7）：
//   - 属于"算法/管道侧"
//   - 是 range adaptor，把 view 管道"收束"为容器
//   - 不关心容器实现细节，通过四阶回退路径兼容所有容器
//   - 依赖 from_range_t 作为第一选择（如果容器支持）
//
// 两者协作：ranges::to 调用容器的 from_range_t 构造函数（若存在），
//             但你也可以单独用 from_range_t 直接构造，不经过 ranges::to。

int main() {
    auto range = std::views::iota(1, 6);

    // 路径 A：直接用 from_range_t 构造（容器侧，不经过 ranges::to）
    std::vector<int> va(std::from_range, range);

    // 路径 B：通过 ranges::to（算法侧，内部调用 from_range_t 路径）
    auto vb = range | std::ranges::to<std::vector<int>>();

    // 两者结果相同
    std::cout << std::boolalpha
              << (va == vb) << '\n';  // true

    return 0;
}
```

### 验收点

- 你能写出 `ranges::to` 的三种语法形式：管道语法、函数调用语法、CTAD 形式，并说出各自的适用场景。
- 你能解释"忘记括号"的错误：`ranges::to<vector<int>>` 是一个不完整的模板表达式，不是 range adaptor closure；必须写 `ranges::to<vector<int>>()` 才能成为可管道的 closure。
- 你能用代码演示 `MinimalContainer`（只有 `push_back`）被 `ranges::to` 收束，说明四阶回退路径的第 4 条被触发。
- 你能用一句话区分 `from_range_t` 和 `ranges::to` 的职责：前者是容器构造侧的标签，后者是管道算法侧的统一入口。
- 你能解释为什么现有容器不需要任何改造就能被 `ranges::to` 收束：四阶回退路径覆盖了所有合理的容器接口组合。

### 观察点

- `ranges::to` 的四阶选择不是运行时分支，而是编译期的概念检测：`if constexpr` 或 concept 约束在模板实例化时决定走哪条路径。对于 `std::vector`，因为它有 `(from_range_t, range)` 构造，走第 1 条路径；对于只有 `push_back` 的容器，走第 4 条路径。
- `from_range_t` 解决了一个微妙的构造歧义问题：`vector<int>(range)` 在旧标准中不合法，因为 `vector` 的构造函数不接受单个 range 参数；`vector<int>(from_range, range)` 通过新增重载明确了意图，不会与 `vector<int>(size, value)` 或 `vector<int>(it, it)` 产生歧义。
- CTAD 形式 `ranges::to<vector>()` 依赖 P1206R7 专门定义的"从 range 的 `value_type` 推导容器完整模板参数"机制（在 `ranges::to` 内部用一个中介类型触发类模板的 CTAD），这不是通用的 alias-template CTAD；这样你可以只写容器类模板名，不用显式给元素类型。
- `ranges::to` 是这个练习包中最终的"消费端"——它把整条惰性 view 管道强制求值，一次性构造出容器。它与 for-range、`ranges::copy` 并列为三种主要消费方式，区别在于 `ranges::to` 直接产出新容器，不需要预先分配目标空间。

### 常见坑

- **忘记括号**：`r | std::ranges::to<std::vector<int>>` 不是有效的管道表达式，`ranges::to<vector<int>>` 是类模板不是 closure；必须写 `ranges::to<std::vector<int>>()` 才能被 `|` 右折叠。这是初学者最常见的编译错误之一。
- **以为需要在容器侧做改造**：四阶回退路径保证了只要容器有 `push_back`，`ranges::to` 就能工作，不需要实现 `from_range_t` 构造函数或 `insert_range`——这些只是优化路径，不是必要条件。
- **混淆 from_range_t 和 ranges::to 的层次**：`from_range_t` 是在构造函数里用的，`ranges::to` 是在管道末尾用的；前者是容器接口扩展，后者是算法入口——两者协作但不可互换。
- **认为 ranges::to 是立即求值的**：从管道角度看，`ranges::to` 是消费端，触发惰性迭代；但它不会在你写下 `| ranges::to<vector>()` 时立即执行，只有整个表达式被求值（赋给变量、传给函数等）时才触发。对大多数用法这是透明的，但在调试时要清楚它的触发时机。

### 提示

- 验证"忘括号"的错误：故意写 `r | std::ranges::to<std::vector<int>>`（无括号），读编译器报错，通常是"no operator| found"或"not a range adaptor closure"。这个错误信息比文档更能帮助你记住括号的必要性。
- 测试 `MinimalContainer` 时，可以在 `push_back` 里加一行 `std::cout << "push_back: " << x`，直观验证确实走了第 4 条路径（逐一 push_back）。
- 如果编译器的 C++23 `ranges::to` 支持不完整，可以用 `std::vector<int> v(std::ranges::begin(r), std::ranges::end(r))` 作为临时替代，同时理解它等价于 `ranges::to` 的第 2 条路径（迭代器对构造）。

### 复盘问题

- `ranges::to<vector>()` 的 CTAD 推导链是什么：从 range 的哪个 trait 得到 `int`，进而推导出 `vector<int>`？
- 如果你有一个只满足 `forward_range` 但没有 `size()` 的自定义 range，`ranges::to<vector<int>>` 走哪条路径？`vector` 能不能在这条路径下预分配容量？
- `from_range_t` 是在 P2781R5 中引入的，比 `ranges::to`（P1206R7）晚。在 P2781R5 之前，`ranges::to` 是如何实现"直接构造容器"的？（提示：迭代器对路径）
- 如果你的自定义容器同时有 `from_range_t` 构造和 `push_back`，`ranges::to` 会走哪条路径？四阶选择的优先级顺序是确定的吗？

## 做完模块 C2 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- `std::ranges::sort` 和 `std::sort` 的差异有四个维度：niebloid 身份（函数对象，不被 ADL 劫持）、concept 约束（编译期拦截非法迭代器）、projection 参数（先 proj 后 comp/pred）、富返回类型（返回 `in_out_result` / `subrange` 而不是单个迭代器）。
- projection 在算法内部的应用点是 `comp(proj(*it1), proj(*it2))`——不存在"先 comp 后 proj"的情况；不提供 projection 时默认是 `std::identity`，行为与 C++17 算法一致。
- `ranges::dangling` 在且仅在"实参是右值且该类型未特化 `enable_borrowed_range = true`"时返回；`enable_borrowed_range` 是 opt-in，不是默认；只有 `string_view`、`span`、`subrange`、`iota_view`、`empty_view` 等少数类型在标准库中默认特化。
- `std::from_range_t` 是容器构造侧的标签（`P2781R5`），容器通过 `(from_range_t, range)` 重载宣告支持 range 直接初始化；`std::ranges::to`（P1206R7）是管道/算法侧的统一收束入口，内部通过四阶回退路径兼容所有容器，不要求容器侧做改造。
- C++17 `std::algo` 无法搭配 sentinel：因为它要求 begin/end 同类型（`common_range`）；无法搭配 niebloid：因为 niebloid 是函数对象，不参与 C++17 的重载解析和 ADL 查找。

**一句话 take-away**：ranges 不是只有视图和管道——算法层的 projection 与富返回类型、borrowed_range 的类型级判定、`ranges::to` 的统一收束，构成了与 view 管道同等重要的另一半。

**指向模块 D**：模块 D 进入 C++23 高阶视图（`views::zip` / `views::zip_transform` / `views::adjacent` / `views::chunk` / `views::chunk_by` / `views::slide` / `views::stride` / `views::join_with` / `views::as_const` / `views::as_rvalue`）以及 `std::generator` 协程桥接——惰性序列与协程的设计相遇，产生了 C++23 中最强的值序列抽象。
