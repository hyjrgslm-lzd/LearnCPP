# 09 模块 F：概念精化与迭代器分类

## 模块目标

前面的模块让你学会了如何使用 ranges 管道、理解惰性语义（01 心智模型），以及理解 CPO/niebloid 的定制化机制（模块 E）。这个模块要把你拉进更深的一层：

- 把"读代码时能立刻说出迭代器概念"从直觉升级为"能自己写出完整的 concept 链和约束"
- 从零构造满足六层迭代器 concept 链的自定义 iterator，逐步精化
- 理解 sentinel 的设计意图，以及 `sized_sentinel_for` 与 `disable_sized_sentinel_for` 的配合
- 理解 `iterator_concept` 与 `iterator_category` 双轨存在的根本原因——proxy reference 使两者产生分歧
- 理解 P1207R4 让 move-only iterator 合法化的历史意义

如果你跳过这一层，你在阅读 `zip_view`、`chunk_view` 的迭代器实现时就会被 `iterator_concept`/`iterator_category` 的双重声明弄糊涂，也无法自己实现一个正确的自定义 view（模块 G 会用到）。

## 模块完成标准

做完本模块，你至少要能稳定说清楚：

- 为什么 concept 链是 refinement 而不是 OR：`forward_iterator` 是 `input_iterator` 的细化，不是替代，不能互换
- 为什么 `output_iterator<T>` 不在 input 主链上，而是独立的分支
- 为什么 `sized_sentinel_for<S, I>` 允许 O(1) 的 `it - s`，但必须配合 `disable_sized_sentinel_for` 显式禁用来防止误判
- 为什么 `iterator_concept` 和 `iterator_category` 要双轨：proxy reference 让两者分歧——`zip_view` 迭代器的 `iterator_concept` 可以是 `random_access_iterator_tag` 但 `iterator_category` 只能是 `input_iterator_tag`，因为 reference 是 prvalue tuple
- 为什么 P1207R4 让 move-only iterator 成为合法 `input_iterator`，打破 C++17 要求迭代器必须 copyable 的成见

## 使用建议

- 本模块以 `static_assert` 为主要验证手段——concept 是编译期断言，运行期行为是次要的
- 每道题都从"最小满足 concept 的版本"开始，再逐步精化，不要一上来就追求完整实现
- 编译错误信息在这个模块里是最重要的调试工具：concept 不满足时的诊断会告诉你缺少哪个表达式要求
- concept 链中每层 refinement 的检查是叠加的，不是替换的——往往缺少一个小操作就会让整条链断掉

## 迭代器 concept 链速览

在进入练习之前，先把整条链固定在脑子里：

```
weakly_incrementable
    └─ input_or_output_iterator
           ├─ input_iterator          ←── input 主链
           │       └─ forward_iterator
           │               └─ bidirectional_iterator
           │                       └─ random_access_iterator
           │                               └─ contiguous_iterator
           └─ output_iterator<T>     ←── 独立输出分支
```

range concept 链：

```
range
  ├─ borrowed_range
  ├─ sized_range
  ├─ input_range / forward_range / bidirectional_range / random_access_range / contiguous_range
  ├─ common_range
  ├─ view  ─── viewable_range（可被 views::all 安全接受）
  └─ output_range<T>
```

迭代器关联类型：

| 别名 | 含义 |
|------|------|
| `iter_value_t<I>` | 解引用后去掉引用和 cv 的"拥有类型" |
| `iter_reference_t<I>` | `*it` 的实际类型（可能是 proxy） |
| `iter_rvalue_reference_t<I>` | `ranges::iter_move(it)` 的类型 |
| `iter_difference_t<I>` | 两个迭代器相减的类型 |
| `iter_common_reference_t<I>` | `iter_value_t<I>&` 和 `iter_reference_t<I>` 的公共引用类型 |

## 练习 F-1：自定义一个 forward_iterator

### 目标

从零构造一个最小 iterator，逐步满足六层 concept 要求，把"concept 链是叠加精化"刻进直觉。

### 前置理解

- 你已读过 01 心智模型，知道 iterator 和 sentinel 分离的基本概念。
- 你知道 C++20 concept 语法：`template <typename T> concept C = requires(T t) { ... };`。
- 你接受这题的重点是 concept 约束验证，不涉及复杂数据结构。
- 你知道 `static_assert` 可以在编译期验证 concept 是否满足。

### 必做任务

1. **定义 `my_range`，包含最小 iterator**：

   从零开始构造一个包装 `std::vector<int>` 的自定义 range。先只满足 `forward_iterator`，暂不追求更高级别。

   需要提供的成员：
   - `operator*()` 返回 `int&`
   - `operator++()` 前置自增，返回 `iterator&`
   - `operator++(int)` 后置自增，返回 `iterator`（拷贝）
   - `operator==(const iterator&) const` 相等比较
   - 内嵌类型别名：`value_type`、`reference`、`difference_type`、`iterator_category`

   ```cpp
   // C++20
   #include <ranges>
   #include <iterator>
   #include <vector>
   #include <cassert>

   struct my_range {
       std::vector<int> data;

       struct iterator {
           using value_type        = int;
           using reference         = int&;
           using difference_type   = std::ptrdiff_t;
           using iterator_category = std::forward_iterator_tag;
           // iterator_concept 是可选 typedef：若不提供，concept 推导回退到
           // iterator_category 映射（forward_iterator_tag 映射到 forward_iterator concept）
           using iterator_concept  = std::forward_iterator_tag;

           int* ptr = nullptr;

           iterator() = default;                   // forward_iterator 要求默认可构造
           explicit iterator(int* p) : ptr(p) {}

           int& operator*() const { return *ptr; }

           iterator& operator++() {
               ++ptr;
               return *this;
           }

           iterator operator++(int) {
               iterator tmp = *this;
               ++ptr;
               return tmp;
           }

           bool operator==(const iterator& other) const {
               return ptr == other.ptr;
           }
       };

       iterator begin() { return iterator(data.data()); }
       iterator end()   { return iterator(data.data() + data.size()); }
   };

   // 验证：forward_iterator 满足 input_iterator（refinement，不是替代）
   static_assert(std::forward_iterator<my_range::iterator>);
   static_assert(std::input_iterator<my_range::iterator>);    // forward 蕴含 input
   static_assert(std::ranges::forward_range<my_range>);
   static_assert(std::ranges::input_range<my_range>);
   // 尚未满足 bidirectional：
   // static_assert(!std::bidirectional_iterator<my_range::iterator>);
   ```

2. **理解 `forward_iterator` 要求 copyable**：

   `forward_iterator` 要求迭代器可以被拷贝，这样才能在不消耗迭代器的情况下"重复遍历"。`input_iterator` 不要求可拷贝（P1207R4）。验证：

   ```cpp
   // C++20
   static_assert(std::copyable<my_range::iterator>);
   // 如果你删掉拷贝构造函数（= delete），
   // forward_iterator concept 会立即失败
   ```

3. **升级到 `bidirectional_iterator`**：

   增加 `operator--`（前置和后置），并将 `iterator_category` / `iterator_concept` 改为 `bidirectional_iterator_tag`：

   ```cpp
   // C++20
   struct iterator {
       using value_type        = int;
       using reference         = int&;
       using difference_type   = std::ptrdiff_t;
       using iterator_category = std::bidirectional_iterator_tag;
       using iterator_concept  = std::bidirectional_iterator_tag;

       int* ptr = nullptr;

       iterator() = default;
       explicit iterator(int* p) : ptr(p) {}

       int& operator*() const { return *ptr; }

       iterator& operator++()    { ++ptr; return *this; }
       iterator  operator++(int) { auto t = *this; ++ptr; return t; }
       iterator& operator--()    { --ptr; return *this; }
       iterator  operator--(int) { auto t = *this; --ptr; return t; }

       bool operator==(const iterator&) const = default;
   };

   static_assert(std::bidirectional_iterator<my_range::iterator>);
   static_assert(std::forward_iterator<my_range::iterator>);   // 仍然成立
   static_assert(std::input_iterator<my_range::iterator>);     // 仍然成立
   ```

4. **升级到 `random_access_iterator`**：

   `random_access_iterator` 在 bidirectional 基础上额外要求：
   - `operator+=` / `operator-=`
   - `operator+` / `operator-`（和整数）
   - `operator-`（两迭代器相减，返回 `difference_type`）
   - `operator[]`（下标访问）
   - `operator<=>` 或全套比较运算符

   ```cpp
   // C++20
   struct iterator {
       using value_type        = int;
       using reference         = int&;
       using difference_type   = std::ptrdiff_t;
       using iterator_category = std::random_access_iterator_tag;
       using iterator_concept  = std::random_access_iterator_tag;

       int* ptr = nullptr;

       iterator() = default;
       explicit iterator(int* p) : ptr(p) {}

       int& operator*()  const { return *ptr; }
       int& operator[](std::ptrdiff_t n) const { return ptr[n]; }

       iterator& operator++()    { ++ptr; return *this; }
       iterator  operator++(int) { auto t = *this; ++ptr; return t; }
       iterator& operator--()    { --ptr; return *this; }
       iterator  operator--(int) { auto t = *this; --ptr; return t; }

       iterator& operator+=(difference_type n) { ptr += n; return *this; }
       iterator& operator-=(difference_type n) { ptr -= n; return *this; }

       friend iterator operator+(iterator i, difference_type n) { i += n; return i; }
       friend iterator operator+(difference_type n, iterator i) { i += n; return i; }
       friend iterator operator-(iterator i, difference_type n) { i -= n; return i; }
       friend difference_type operator-(const iterator& a, const iterator& b) {
           return a.ptr - b.ptr;
       }

       // spaceship 运算符：一次性提供全套有序比较
       auto operator<=>(const iterator&) const = default;
       bool operator==(const iterator&)  const = default;
   };

   static_assert(std::random_access_iterator<my_range::iterator>);
   static_assert(std::bidirectional_iterator<my_range::iterator>);   // 仍成立
   static_assert(std::forward_iterator<my_range::iterator>);         // 仍成立
   static_assert(std::ranges::random_access_range<my_range>);
   ```

5. **升级到 `contiguous_iterator`**：

   若元素在内存中连续存储，可再进一步满足 `contiguous_iterator`。需要：
   - `iterator_concept = std::contiguous_iterator_tag`
   - `operator->()` 返回裸指针，或特化 `std::to_address`

   ```cpp
   // C++20
   // 在 iterator 内增加：
   using iterator_concept  = std::contiguous_iterator_tag;

   int* operator->() const { return ptr; }

   static_assert(std::contiguous_iterator<my_range::iterator>);
   static_assert(std::ranges::contiguous_range<my_range>);
   ```

6. **对比每步需要添加的接口**：

   | concept 层 | 新增要求（相对上一层） |
   |------------|----------------------|
   | `input_iterator` | `operator*`、前置 `operator++`、`value_type`、`difference_type` |
   | `forward_iterator` | copyable、默认构造、后置 `operator++`、`iterator_category` |
   | `bidirectional_iterator` | `operator--`（前置 + 后置） |
   | `random_access_iterator` | `+=`、`-=`、`+`、`-`、`[]`、`<=>` |
   | `contiguous_iterator` | `iterator_concept = contiguous_iterator_tag`、`operator->` |

7. **验证 concept 是 refinement 而非 OR**：

   ```cpp
   // C++20
   // 如果一个算法要求 forward_iterator，
   // 传入 random_access_iterator 完全合法（因为 random_access 蕴含 forward）
   template <std::forward_iterator It>
   void demo_forward(It first, It last) {
       for (auto it = first; it != last; ++it) {
           (void)*it;
       }
   }

   my_range r{{1, 2, 3, 4, 5}};
   demo_forward(r.begin(), r.end());   // OK：random_access_iterator 满足 forward_iterator
   ```

### 进阶任务

- 把 `iterator_concept` 和 `iterator_category` 设置为不一致（例如 `iterator_concept = random_access_iterator_tag`，`iterator_category = forward_iterator_tag`），观察 `std::ranges::sort`（使用 `iterator_concept`）可以编译通过，但 `std::sort`（使用 `iterator_category`）的行为退化为 O(n²) 的插入排序路径。
- 用 `requires` 子句为 `demo_forward` 加上更精确的 concept 约束，对比有无约束时编译错误信息的差异。
- 实现 P1207R4 风格的 move-only iterator：删除拷贝构造函数，只保留移动构造函数，验证 `std::input_iterator` 仍然满足，`std::forward_iterator` 不再满足。

### 验收点

- 你能从零写出满足 `forward_iterator` / `bidirectional_iterator` / `random_access_iterator` / `contiguous_iterator` 的自定义迭代器。
- 你能用 `static_assert` 证明每层满足的同时也满足所有低层 concept（refinement 方向）。
- 你能说清楚为什么 `forward_iterator` 要求 copyable 而 `input_iterator` 不要求。
- 你能对比每层需要新增的运算符/类型别名。

### 观察点

- concept 链是叠加的：`random_access_iterator` 同时满足 `bidirectional_iterator`、`forward_iterator`、`input_iterator`。这不是巧合，这是 refinement 的定义。
- `iterator_concept` 是**可选 typedef**：若不存在，concept 推导会回退到 `iterator_category` 映射。两者都存在时，C++20 concept 优先使用 `iterator_concept`。
- 忘记 `difference_type` 或 `value_type` 会让 concept 直接失败，而且错误信息很长——学会从错误末尾的 "note:" 找到真正缺失的约束。
- `operator<=>` 是 `random_access_iterator` 的必要条件之一（以便支持 `<`、`<=`、`>`、`>=` 比较）。只有 `==` 是不够的。

### 常见坑

- 忘记 `difference_type` / `value_type` 的 typedef，导致 concept 直接失败，错误信息非常难懂（一堆 requires 展开失败）。
- `operator==` 用 `const_iterator` 比较时 type mismatch：如果你定义了 const 版本的迭代器，需要为两种组合都提供 `operator==`。
- 以为满足 `operator++/--` 就自动 bidirectional：`bidirectional_iterator` 的 concept 约束还检查后置 `operator--` 的返回类型必须是 `iterator`（右值），不能是 `void`。
- `random_access_iterator` 缺少 `operator[]`：有些实现者只加了 `+=` 和 `-=`，忘记 `[]`，导致 concept 失败。
- 以为只加 `iterator_concept = contiguous_iterator_tag` 就满足 `contiguous_iterator`：还需要 `operator->()` 返回裸指针。

### 提示

- 每升级一层，先写新运算符，再 `static_assert` 验证，不要等全部写完再验证。
- concept 约束失败时，错误信息会展示一长串 "note: ... expression ... is not satisfied"——找到第一个 "the required expression" 就知道缺少什么。
- 用 `std::iterator_traits<my_range::iterator>::iterator_category` 来确认 traits 推导正确。
- `operator<=>` 加 `= default` 会同时生成 `==`，但如果要分开控制，用 `bool operator==(const iterator&) const = default;` 单独提供。

### 复盘问题

- 为什么 `forward_iterator` 要求默认可构造，而 `input_iterator` 不要求？（提示：multipass guarantee——forward iterator 需要能保存当前位置并从头重放。）
- `random_access_iterator` 相比 `bidirectional_iterator` 增加的 `operator[]` 和 `operator<=>` 各自解决了什么问题？
- 如果你把 `iterator_category` 设为 `random_access_iterator_tag`，但不提供 `operator-`（两迭代器相减），会发生什么？
- `contiguous_iterator` 和 `random_access_iterator` 的语义区别是什么？对 SIMD 优化有什么影响？

### 对应官方参考

- P0896R4：C++20 ranges 迭代器 concept 定义
- P1207R4：move-only iterator 合法化
- cppreference：[iterator concepts](https://en.cppreference.com/w/cpp/iterator#Iterator_concepts)

## 练习 F-2：sentinel_for 与 sized_sentinel_for

### 目标

自己写一个 sentinel，演示 `sized_sentinel_for` 何时应开启、何时应通过 `disable_sized_sentinel_for` 显式禁用，把"sentinel 的 O(1) 语义是合约，不是默认"刻进直觉。

### 前置理解

- 你已完成 F-1，有可用的自定义 iterator。
- 你知道 iterator 和 sentinel 分离的基本概念（01 心智模型中已建立）。
- 你接受 sentinel 只需要与 iterator 可比较，不必是同一类型。
- 你知道 `std::unreachable_sentinel_t` 是标准库提供的"永远不终止"哨兵。

### 必做任务

1. **定义一个计数 sentinel 和配套 iterator**：

   `count_down_sentinel` 记录还剩多少步，当 iterator 报告的剩余步数为 0 时，认为序列结束。

   ```cpp
   // C++20
   #include <ranges>
   #include <iterator>
   #include <concepts>

   struct count_down_sentinel {
       std::ptrdiff_t remaining;
   };

   struct my_counted_iterator {
       using value_type      = int;
       using difference_type = std::ptrdiff_t;
       using iterator_concept = std::input_iterator_tag;

       int* ptr      = nullptr;
       std::ptrdiff_t steps = 0;   // 已经走了多少步

       my_counted_iterator() = default;
       my_counted_iterator(int* p, std::ptrdiff_t s) : ptr(p), steps(s) {}

       int& operator*() const { return *ptr; }

       my_counted_iterator& operator++() {
           ++ptr;
           ++steps;
           return *this;
       }

       my_counted_iterator operator++(int) {
           auto t = *this;
           ++*this;
           return t;
       }

       // sentinel_for 要求：iterator == sentinel 是合法表达式
       friend bool operator==(const my_counted_iterator& it,
                              const count_down_sentinel& s) {
           return s.remaining - it.steps <= 0;
       }
   };
   ```

2. **验证 `sentinel_for`**：

   `sentinel_for<S, I>` 要求：
   - `S` 是 semiregular（可默认构造 + 可拷贝）
   - `I` 满足 `input_or_output_iterator`
   - `operator==(I, S)` 是合法表达式（对称：`I == S` 和 `S == I` 均可）

   ```cpp
   // C++20
   static_assert(std::sentinel_for<count_down_sentinel, my_counted_iterator>);

   // 用法示例：
   int arr[] = {10, 20, 30, 40, 50};
   my_counted_iterator it{arr, 0};
   count_down_sentinel end{3};          // 走 3 步后停止

   for (; it != end; ++it) {
       // 只会迭代 arr[0], arr[1], arr[2]
   }
   ```

3. **添加 `operator-`，满足 `sized_sentinel_for`**：

   `sized_sentinel_for<S, I>` 在 `sentinel_for<S, I>` 基础上额外要求：
   - `s - it` 和 `it - s` 都是合法表达式
   - 返回 `iter_difference_t<I>`
   - 语义上必须是 O(1)（这是合约，编译器无法强制验证，需要实现者自觉保证）

   ```cpp
   // C++20
   friend std::ptrdiff_t operator-(const count_down_sentinel& s,
                                   const my_counted_iterator& it) {
       return s.remaining - it.steps;      // O(1): 直接计算，不需要遍历
   }

   friend std::ptrdiff_t operator-(const my_counted_iterator& it,
                                   const count_down_sentinel& s) {
       return it.steps - s.remaining;
   }

   static_assert(std::sized_sentinel_for<count_down_sentinel, my_counted_iterator>);

   // sized_sentinel_for 让 ranges::distance 走 O(1) 路径：
   my_counted_iterator it2{arr, 0};
   count_down_sentinel end2{5};
   auto dist = std::ranges::distance(it2, end2);  // O(1)，直接 end2 - it2
   // dist == 5
   ```

4. **显式禁用 `sized_sentinel_for`——防止误判**：

   有时虽然有 `operator-`，但其语义并非 O(1)（例如对链表迭代器，两者相减需要遍历）。此时应通过特化 `disable_sized_sentinel_for` 显式禁用，防止 `ranges::distance` 等算法误以为可以 O(1) 取距离：

   ```cpp
   // C++20
   struct fake_sized_sentinel {
       std::ptrdiff_t limit;
   };

   struct slow_iterator {
       using value_type      = int;
       using difference_type = std::ptrdiff_t;
       using iterator_concept = std::forward_iterator_tag;

       struct node { int val; node* next; };
       node* current = nullptr;
       std::ptrdiff_t pos = 0;

       slow_iterator() = default;
       slow_iterator(node* n, std::ptrdiff_t p) : current(n), pos(p) {}

       int& operator*() const { return current->val; }
       slow_iterator& operator++() {
           current = current->next;
           ++pos;
           return *this;
       }
       slow_iterator operator++(int) { auto t = *this; ++*this; return t; }
       bool operator==(const slow_iterator&) const = default;

       // operator- 存在，但实际上是 O(n)（遍历节点计数）
       friend std::ptrdiff_t operator-(const fake_sized_sentinel& s,
                                       const slow_iterator& it) {
           // 假设这里需要遍历链表：实际是 O(n)
           return s.limit - it.pos;   // 简化：直接用 pos（假装 O(1)，仅为演示）
       }
       friend std::ptrdiff_t operator-(const slow_iterator& it,
                                       const fake_sized_sentinel& s) {
           return it.pos - s.limit;
       }
   };

   // 没有 disable：sized_sentinel_for 会被认为满足（错误！）
   // static_assert(std::sized_sentinel_for<fake_sized_sentinel, slow_iterator>);

   // 显式禁用：告诉标准库"虽然有 operator-，但不要用它做 O(1) 距离计算"
   template <>
   inline constexpr bool
   std::disable_sized_sentinel_for<fake_sized_sentinel, slow_iterator> = true;

   // 禁用后，sized_sentinel_for 不再满足：
   static_assert(!std::sized_sentinel_for<fake_sized_sentinel, slow_iterator>);
   // ranges::distance 现在走 O(n) 路径（逐步推进直到到达 sentinel）
   ```

5. **与 `std::unreachable_sentinel_t` 对比**：

   ```cpp
   // C++20
   // unreachable_sentinel_t 是标准库提供的"永远不终止"哨兵
   // 它满足 sentinel_for<unreachable_sentinel_t, any_input_iterator>
   // 但永远不满足 sized_sentinel_for（因为距离语义无意义）
   static_assert(std::sentinel_for<std::unreachable_sentinel_t,
                                   my_counted_iterator>);
   // 以下应该不满足（unreachable_sentinel 没有提供 operator-）：
   // static_assert(!std::sized_sentinel_for<std::unreachable_sentinel_t,
   //                                         my_counted_iterator>);

   // unreachable_sentinel 的典型用途：无界序列，调用方自己保证终止
   int buf[100];
   auto it3 = my_counted_iterator{buf, 0};
   // it3 != std::unreachable_sentinel 永远为 true
   // 必须外部条件终止循环
   ```

### 进阶任务

- 为 `count_down_sentinel` 增加 `sized_sentinel_for` 后，用 `ranges::next(it, end)` 验证它能 O(1) 跳转（而不是逐步递增）。
- 构造一个场景：`disable_sized_sentinel_for` 的效果让 `ranges::for_each` 走不同的实现路径——用计数器验证调用次数差异。
- 实现 `operator-` 为负数情况也正确（`it - s` 返回负值时表示 iterator 已超过 sentinel），用 `static_assert` 验证语义一致性。

### 验收点

- 你能实现满足 `sentinel_for` 的自定义 sentinel。
- 你能为 sentinel 增加 `operator-` 并验证 `sized_sentinel_for` 满足。
- 你能通过特化 `disable_sized_sentinel_for` 显式禁用 sized 语义，并验证 concept 检查结果变化。
- 你能说明 `disable_sized_sentinel_for` 的存在意义：防止算法对"形似 O(1) 但实际是 O(n)"的距离计算做错误优化假设。

### 观察点

- `sentinel_for` 的对称性要求：`it == s` 和 `s == it` 都要合法。C++20 的 `==` 对称性通过重写规则（rewrite rules）自动处理：如果你只提供 `friend bool operator==(I, S)`，编译器会为 `s == it` 自动生成反向形式。
- `sized_sentinel_for` 是一个"自报家门"的合约：编译器看到 `operator-` 就认为 O(1)——这是一个信任机制，不是强制验证。`disable_sized_sentinel_for` 是你主动撤销这个信任的机制。
- `ranges::distance(first, last)` 的实现路径：若 `sized_sentinel_for<decltype(last), decltype(first)>` 满足则直接 `last - first`（O(1)）；否则循环推进计数（O(n)）。

### 常见坑

- `operator==` 的参数顺序只提供了 `(It, Sent)` 但忘记 `(Sent, It)` 的 symmetric 形式——C++20 的重写规则会自动处理，但某些旧编译器版本可能需要显式提供。
- 实现 `operator-` 却语义不是 O(1)，又忘记 opt-out，导致 `ranges::distance` 用了错误的 O(1) 路径，产生难以察觉的性能 bug。
- `semiregular` 要求 sentinel 可默认构造：`count_down_sentinel` 如果只提供带参构造，需要额外提供 `count_down_sentinel() = default;`（或给成员设初始值）。
- 混淆 `disable_sized_sentinel_for` 和 `disable_sized_range`：前者针对迭代器对，后者针对 range 类型，它们是不同的 opt-out 机制。

### 提示

- 先不加 `operator-`，验证只满足 `sentinel_for`；再加 `operator-`，验证满足 `sized_sentinel_for`；最后特化 `disable_sized_sentinel_for`，验证退回 `sentinel_for`。这三步分开做，每步一个 `static_assert`。
- `std::ranges::distance` 的实现在 cppreference 上有伪代码，可以直接对照验证你的 sentinel 走了哪条路径。
- `disable_sized_sentinel_for` 特化必须在 `std` 命名空间里：`template <> inline constexpr bool std::disable_sized_sentinel_for<...> = true;`。

### 复盘问题

- 为什么 sentinel 不需要是与 iterator 相同的类型？这个设计给 `take_while_view` 带来了什么好处？
- `sized_sentinel_for` 的语义合约是"O(1) 距离计算"，但编译器无法验证这一点。标准为什么选择信任机制而不是运行期检查？
- `disable_sized_sentinel_for` 特化的作用范围是编译期 concept 检查，不影响运行期——这意味着什么？（提示：如果你忘了 opt-out，`ranges::distance` 会在编译期选错路径，运行期才暴露 O(n) 的结果被当成 O(1) 使用。）
- `std::counted_iterator`（标准库提供的计数迭代器包装）和你手写的 `my_counted_iterator` 有什么语义区别？

## 练习 F-3：iterator_concept 双轨与 proxy reference

### 目标

亲手复现 "iterator_concept != iterator_category" 的场景，理解 C++20 为何需要两套系统，把"proxy reference 导致 concept 双轨分歧"刻进直觉。

### 前置理解

- 你已完成 F-1 / F-2，有自定义 iterator 和 sentinel 的实现经验。
- 你从 01 心智模型中了解了 `iterator_concept` / `iterator_category` 双轨的基本概念。
- 你知道 `std::tuple` 是 prvalue（临时值），不是左值引用。
- 你接受这题的核心是验证编译期 concept 行为，不需要复杂的数据结构。

### 必做任务

1. **构造一个 proxy reference 迭代器**：

   模拟 `zip_view` 迭代器的简化版本：解引用时产生 `std::tuple<int&, double&>`，这是一个临时 prvalue，不是真实的左值引用。

   ```cpp
   // C++20
   #include <tuple>
   #include <iterator>
   #include <ranges>
   #include <concepts>

   struct zip_like_it {
       using value_type = std::tuple<int, double>;

       // reference 是 proxy：临时 tuple prvalue，不是 value_type 的左值引用
       using reference  = std::tuple<int&, double&>;

       using difference_type = std::ptrdiff_t;

       // iterator_concept：C++20 concept 系统看这里
       // 我们支持随机访问，所以是 random_access_iterator_tag
       using iterator_concept  = std::random_access_iterator_tag;

       // iterator_category：C++17 legacy 算法看这里
       // 因为 reference 不是真实的 lvalue reference（是 proxy prvalue），
       // C++17 算法无法正确处理，必须降级为 input_iterator_tag
       using iterator_category = std::input_iterator_tag;

       int*    a_ptr = nullptr;
       double* b_ptr = nullptr;

       zip_like_it() = default;
       zip_like_it(int* a, double* b) : a_ptr(a), b_ptr(b) {}

       // 解引用返回 proxy：临时 tuple 持有两个引用
       reference operator*() const {
           return {*a_ptr, *b_ptr};
       }

       zip_like_it& operator++()    { ++a_ptr; ++b_ptr; return *this; }
       zip_like_it  operator++(int) { auto t = *this; ++*this; return t; }
       zip_like_it& operator--()    { --a_ptr; --b_ptr; return *this; }
       zip_like_it  operator--(int) { auto t = *this; --*this; return t; }

       zip_like_it& operator+=(difference_type n) { a_ptr += n; b_ptr += n; return *this; }
       zip_like_it& operator-=(difference_type n) { a_ptr -= n; b_ptr -= n; return *this; }

       friend zip_like_it operator+(zip_like_it i, difference_type n) { i += n; return i; }
       friend zip_like_it operator+(difference_type n, zip_like_it i) { i += n; return i; }
       friend zip_like_it operator-(zip_like_it i, difference_type n) { i -= n; return i; }
       friend difference_type operator-(const zip_like_it& a, const zip_like_it& b) {
           return a.a_ptr - b.a_ptr;
       }

       reference operator[](difference_type n) const {
           return {a_ptr[n], b_ptr[n]};
       }

       auto operator<=>(const zip_like_it&) const = default;
       bool operator==(const zip_like_it&)  const = default;
   };
   ```

2. **验证双轨分歧**：

   ```cpp
   // C++20
   // iterator_concept 通道：C++20 concept 系统认为它是 random_access_iterator
   static_assert(std::random_access_iterator<zip_like_it>);
   static_assert(std::bidirectional_iterator<zip_like_it>);
   static_assert(std::forward_iterator<zip_like_it>);
   static_assert(std::input_iterator<zip_like_it>);

   // iterator_category 通道：legacy 路径认为它只是 input_iterator
   static_assert(std::same_as<
       std::iterator_traits<zip_like_it>::iterator_category,
       std::input_iterator_tag>);

   // 所以 std::sort 不能使用它（C++17 sort 通过 iterator_category 判断，
   // 看到 input_iterator_tag 就拒绝或退化）
   // 但 std::ranges::sort 可以使用它（C++20 sort 通过 iterator_concept 判断）

   int   a[] = {3, 1, 4, 1, 5};
   double b[] = {3.0, 1.0, 4.0, 1.0, 5.0};
   zip_like_it first{a, b};
   zip_like_it last{a + 5, b + 5};

   // 需要实现 iter_move 才能让 ranges::sort 正确交换元素（见进阶任务）
   // std::ranges::sort(first, last);   // 暂时注释，进阶任务中实现
   ```

3. **验证三个关联类型**：

   ```cpp
   // C++20
   // iter_value_t：去掉引用和 cv 的"拥有类型"
   static_assert(std::same_as<
       std::iter_value_t<zip_like_it>,
       std::tuple<int, double>>);

   // iter_reference_t：*it 的实际类型（proxy）
   static_assert(std::same_as<
       std::iter_reference_t<zip_like_it>,
       std::tuple<int&, double&>>);

   // iter_rvalue_reference_t：ranges::iter_move(it) 的类型
   // 默认 iter_move 的定义就是 std::move(*it)，所以默认
   // iter_rvalue_reference_t<I> = remove_reference_t<iter_reference_t<I>>&&
   // ——对 proxy reference = tuple<int&, double&>，默认得到 tuple<int&, double&>&&
   // 问题不在"公式不等于 reference&&"，而在"这个类型语义上没用"：
   // 把 tuple 本身当右值绑定并不会让其内部的 int& / double& 变成右值引用，
   // 下游把元素 move 走时依旧只是按左值引用赋值。
   // 因此 proxy iterator 必须通过自定义 iter_move 把
   // tuple<int&, double&> 映射为 tuple<int&&, double&&>（元素级 rvalue）。
   ```

4. **理解为什么 `iterator_category` 必须设为 `input_iterator_tag`**：

   C++17 的 `RandomAccessIterator` 要求：
   - `*it` 的类型可以绑定到 `value_type&`（即必须是真实的左值引用）
   - `std::sort` 等算法会做 `value_type tmp = *it; *it = std::move(*other_it);` 这样的赋值

   对于 proxy reference `tuple<int&, double&>`，这些操作的语义是有问题的：`tmp` 是拷贝而不是真实对象，对 `*it` 赋值会修改引用对象而不是"移动元素"。所以如果把 `iterator_category` 报告为 `random_access_iterator_tag`，C++17 `sort` 会尝试"正确"操作，结果产生错误行为。

   ```cpp
   // C++20：展示为什么必须降级
   // 如果把 iterator_category 改为 random_access_iterator_tag：
   struct wrong_zip_it : zip_like_it {
       using iterator_category = std::random_access_iterator_tag; // 危险！
   };

   // std::sort 会基于这个 category 假设 *it 是真实左值引用，
   // 并尝试 std::swap(*it1, *it2)——对 proxy 这会产生错误行为
   // （swap tuple 本身，而不是 swap 被引用的元素）
   ```

5. **实现 `iter_move` 让 proxy iterator 正确参与 `ranges::sort`**：

   `ranges::sort` 内部使用 `ranges::iter_move`（CPO）而不是直接 move `*it`。`iter_move` 的默认实现是把 `*it` 的结果强转为右值（`std::move(*it)`），对于 proxy 这是错误的——它会移动 tuple 本身，而不是移动 tuple 持有的引用所指向的元素。

   正确实现：通过 ADL 提供 `iter_move` friend：

   ```cpp
   // C++20
   // 在 zip_like_it 内部增加：
   friend std::tuple<int&&, double&&> iter_move(const zip_like_it& it) {
       return {std::move(*it.a_ptr), std::move(*it.b_ptr)};
   }

   // 现在 iter_rvalue_reference_t 变为 tuple<int&&, double&&>：
   static_assert(std::same_as<
       std::iter_rvalue_reference_t<zip_like_it>,
       std::tuple<int&&, double&&>>);

   // 有了正确的 iter_move，ranges::sort 可以正确交换元素：
   // std::ranges::sort(first, last);  // 现在可以编译通过，语义也正确
   ```

6. **实现 `iter_swap` 让元素交换语义正确**：

   `ranges::iter_swap` 默认用 `iter_move` 做三步交换。对于 proxy iterator，如果两个迭代器指向的元素在物理上是分开存储的（如 `zip_view` 中 `a` 数组和 `b` 数组独立），`iter_swap` 需要分别交换两对引用：

   ```cpp
   // C++20
   // 在 zip_like_it 内部增加：
   friend void iter_swap(const zip_like_it& x, const zip_like_it& y) {
       std::ranges::swap(*x.a_ptr, *y.a_ptr);
       std::ranges::swap(*x.b_ptr, *y.b_ptr);
   }
   ```

### 进阶任务

- 把三个关联类型（`iter_value_t`、`iter_reference_t`、`iter_rvalue_reference_t`）全部 `static_assert` 出来，验证它们在有无自定义 `iter_move` 时的变化。
- 验证不实现 `iter_move` 时 `std::ranges::sort(first, last)` 编译失败，实现后编译通过，并用运行期验证（打印数组）确认排序结果正确。
- 研究 P1207R4 的 move-only iterator：为 `zip_like_it` 删除拷贝构造，保留移动构造，验证 `input_iterator` 仍满足，`forward_iterator` 不再满足（因为 forward 要求 copyable = multipass guarantee）。

### 验收点

- 你能写出 `iterator_concept != iterator_category` 的 proxy reference 迭代器。
- 你能用 `static_assert` 验证 C++20 concept 层面可以是 random_access，而 C++17 legacy 层面只是 input。
- 你能解释为什么 `iterator_category` 必须设为 `input_iterator_tag`，而不是 `random_access_iterator_tag`。
- 你能实现正确的 `iter_move` friend，让 `ranges::sort` 对 proxy iterator 正常工作。
- 你能说清 `iter_rvalue_reference_t` 和 `iter_reference_t` 的区别：前者是 `iter_move` CPO 的结果，后者是 `*it` 的类型。

### 观察点

- proxy reference 不是"奇怪的边缘情况"，而是 C++20 ranges 设计中的核心场景：`zip_view`、`enumerate_view`（C++26）、`transform_view`（返回 prvalue）都涉及这个问题。
- C++17 算法之所以不能处理 proxy reference，根本原因是 C++17 的 `RandomAccessIterator` 要求"解引用返回真实左值引用"——这是一个隐性的"no proxy"假设，C++20 通过 `iter_move`/`iter_swap` CPO 显式打破了这个假设。
- `iter_rvalue_reference_t<I>` 在默认 `iter_move` 下等价于 `remove_reference_t<iter_reference_t<I>>&&`；对 proxy reference 来说，把 tuple 整体变右值对元素级移动毫无帮助——所以需要通过自定义 `iter_move` friend 让 `iter_rvalue_reference_t<I>` 改为 `tuple<T&&, U&&>` 这类元素级 rvalue 形式。
- `iterator_concept` 是可选的：若不提供，C++20 concept 系统会从 `iterator_category` 反推（`random_access_iterator_tag` 映射到 `random_access_iterator` concept，以此类推）。只有当你需要"C++20 能力 > C++17 能力"时，才必须显式声明 `iterator_concept`。

### 常见坑

- 以为 `iterator_category` 可以不定义：不定义时 `iterator_traits` 会退化，某些算法找不到迭代器类型信息，产生奇怪的编译错误。
- 对 `iter_rvalue_reference_t` 语义的误解：默认 `iter_move` 下它就是 `remove_reference_t<iter_reference_t<I>>&&`（对 proxy 是 `tuple<int&, double&>&&`），这没错；错在以为 tuple 整体变右值就能完成元素级 move。对 proxy iterator，必须提供自定义 `iter_move`，让返回类型变成 `tuple<int&&, double&&>`（元素级 rvalue），下游赋值时才真正移动被引用的对象。
- 让 `reference = tuple<int&>` 而 `value_type = int`：`iter_common_reference_t` 需要计算 `value_type&` 和 `reference` 的公共引用类型，类型不对称会导致计算失败，进而让某些 concept 约束断掉。
- 忘记实现 `iter_swap` 只提供 `iter_move`：`ranges::sort` 的某些路径会直接调用 `iter_swap`，如果没有自定义实现，默认的 `iter_swap` 会用 `iter_move` + `iter_move` + 赋值做三步交换，对某些 proxy iterator 语义是错误的。

### 提示

- 先不加 `iter_move`，看看 `std::ranges::sort(first, last)` 的编译错误——错误信息会告诉你哪个 concept 约束失败，进而找到缺少什么。
- `iter_move` 的 ADL 查找：`ranges::iter_move(it)` 会先查找与 `it` 类型关联的 `iter_move` ADL 名称，找不到才用默认实现。所以把 `iter_move` 声明为 `friend` 函数是标准的 ADL 友元模式。
- `std::iter_rvalue_reference_t<I>` 等价于 `decltype(std::ranges::iter_move(std::declval<I>()))`，这可以帮助你验证 `iter_move` 的实现是否正确。

### 复盘问题

- 为什么 `std::ranges::sort` 能排序 proxy reference 迭代器，而 `std::sort` 不能（或行为错误）？根本区别在哪里？

## 做完模块 F 之后，你现在应该能说清楚什么

至少把下面几句话说顺：

- concept 链是 refinement，不是 OR：`random_access_iterator` 同时满足 `bidirectional_iterator`、`forward_iterator`、`input_iterator`。这是叠加精化，不是互相替代。算法对高层 concept 的要求自动被低层满足，这就是 refinement 的价值。
- `output_iterator<T>` 不在 input 主链上：它是独立分支，满足 `output_iterator<T>` 不意味着满足任何 input 层级 concept。两条链的设计意图不同：input 链描述"可读序列"，output 描述"可写目标"。
- `sized_sentinel_for<S, I>` 的 O(1) 语义是合约，不是强制验证：标准信任实现者提供 `operator-`时保证 O(1)；`disable_sized_sentinel_for` 是实现者主动撤销这个信任的机制，防止算法误用。
- `iterator_concept` 和 `iterator_category` 双轨的根本原因是 proxy reference：C++17 算法假设 `*it` 是真实左值引用，C++20 concept 放宽了这个要求。当两者分歧时，`iterator_category` 保守降级（向 C++17 报告弱能力），`iterator_concept` 如实报告（向 C++20 报告真实能力）。
- `iter_rvalue_reference_t<I>` 是 `iter_move` CPO 的结果类型；在默认 `iter_move = std::move(*it)` 下它就是 `remove_reference_t<iter_reference_t<I>>&&`。对 proxy iterator，这个默认形式语义上没用（tuple 整体右值化不等于元素级 move），所以才要提供自定义 `iter_move` friend，把返回类型改成元素级 rvalue（如 `tuple<int&&, double&&>`）。
- P1207R4 让 move-only iterator 成为合法 `input_iterator`：打破了 C++17"迭代器必须 copyable"的成见。`std::generator` 的协程 range 是最直接的受益者——协程帧是 move-only 的，其 iterator 不能也不应该被复制。

## 指向下一模块

模块 G 会把这些概念用到实处：自己继承 `view_interface`、标记 `enable_borrowed_range`、实现 `range_adaptor_closure` 让 `operator|` 工作。你在本模块建立的 iterator concept 链知识，在模块 G 里会成为你设计迭代器类型决策的直接依据——你写的每个自定义 view 都必须决定：迭代器应该满足哪一层 concept？sentinel 应该如何设计？是否需要 `iterator_concept` 和 `iterator_category` 分开声明？
